# v1.10.5 Phase 1 - Release Checklist Final-State Hygiene

Status: Complete

## Purpose

Phase 1 defines final-state hygiene rules for release checklists and phase-status documents.

The issue discovered after v1.10.4 was that release documentation could remain accurate for PR preparation while still not fully reflecting the final published release state after PR, merge, tag, and publication were complete.

The expected invariant is:

> Release status/checklist artifacts should accurately represent the final state of a completed release.

## Scope

Included:

- document the v1.10.4 final-state hygiene gap
- define v1.10.5 final-state checklist/status policy
- add explicit final release gates for PR, CI, Codacy, merge, tag, publication, feature-branch removal, and post-release status closure
- define how future releases should close final-state docs after publication
- update v1.10.5 release control artifacts

Excluded:

- production code changes
- test implementation changes
- CI workflow changes
- dependency/toolchain changes
- tracker/matrix closure
- v1.10.4 retagging or release republishing
- broad historical release-doc rewrites

## Design Rule

Phase 1 is a process/documentation hygiene phase.

It should define and enforce final-state checklist/status expectations for v1.10.5 without changing product behavior.

## Final-State Policy

A release is not considered fully closed in release-control documentation until all applicable final-state gates are explicitly recorded.

Final-state gates include:

- PR opened
- PR CI completed green
- Codacy / code-quality review completed
- release-delta findings fixed or documented
- PR merged into `main`
- release tag created from current `main`
- tag pushed
- GitHub release published
- feature branch removed after merge
- checklist final-state gates updated
- phase status updated to published/final state
- working tree clean after release publication

For v1.10.5 and later, release checklist/status files should distinguish:

1. release-candidate readiness,
2. PR readiness,
3. merge readiness,
4. tag readiness,
5. published-release completion.

A release may be technically published without this final-state documentation update, but the next release should treat that as process debt.

## Final Phase-Status Closure Format

For v1.10.5 and later, after publication, `v1.10.x-phase-status.md` should be updated with a final published-release state.

Recommended final section:

```markdown
## Final Release State

Status: Published

Final tag: `v1.10.x`

Published from: `main`

Publication date: YYYY-MM-DD

Final gates:

- PR CI: green
- Codacy/code quality: complete
- Merge to main: complete
- Tag push: complete
- GitHub release: published
- Feature branch: removed
```

Before PR publication, this section may exist as `Status: Pending publication` or may be added during final release closure.
