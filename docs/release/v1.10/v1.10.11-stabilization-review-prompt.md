# v1.10.11 Stabilization Review Prompt

Use this prompt when reviewing or implementing any v1.10.11 stabilization task.

## Mission

Proceed with v1.10.11 stabilization and regression burn-down.

The goal is to reduce known release risk and prepare v1.10 behavior for freeze before engine-boundary preparation.

## Core Invariant

v1.10.11 stabilization work must only reduce known release risk, preserve v1.10 behavior, and avoid engine extraction, catalog abstraction, product features, broad refactors, or untracked behavior drift.

## Before Editing

Identify:

1. the issue or risk being addressed;
2. the affected invariant;
3. the severity;
4. whether the change is behavior-preserving;
5. whether a regression test is needed;
6. whether SQLite/PostgreSQL compatibility is affected;
7. whether packed/legacy parity is affected;
8. whether CLI/JSON/exit-code contracts are affected;
9. whether restore/verify/GC/recovery/snapshot/migration behavior is affected;
10. what is explicitly out of scope.

## Allowed Work

Allowed:

- S0/S1 review and closure;
- suppression audit;
- accepted/deferred risk audit;
- long-run/adversarial/regression evidence;
- flaky test classification;
- narrow fixes required by real stabilization findings;
- release evidence cleanup;
- known-issues documentation.

## Forbidden Work

Do not do:

- engine extraction;
- catalog abstraction;
- daemon work;
- API work;
- UI work;
- NAS/cloud/network behavior;
- broad refactors;
- style-only cleanup;
- default database backend changes;
- new product features;
- unrelated Codacy cleanup;
- large architecture movement.

## Fix Policy

For a real bug:

1. write or update a regression test where practical;
2. make the smallest safe fix;
3. run targeted tests;
4. run package tests;
5. document behavior impact;
6. update risk/issue evidence.

For a scanner finding:

1. determine if it is real, false positive, accepted, or deferred;
2. document rationale;
3. do not chase style-only findings;
4. do not claim fixed unless actually fixed or suppressed with rationale.

For a flaky test:

1. reproduce or cite evidence;
2. classify cause if possible;
3. fix only the narrow cause;
4. avoid weakening assertions;
5. do not delete a test unless replacement coverage exists.

## Final Response Format

Report:

- invariant protected;
- files changed;
- behavior change yes/no;
- tests run;
- risk status;
- remaining risk;
- next phase impact.
