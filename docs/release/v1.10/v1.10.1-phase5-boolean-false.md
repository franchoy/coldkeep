# v1.10.1 Phase 5 — Boolean Explicit False Semantics

Status: Complete

## Purpose

Phase 5 fixes CLI boolean flags where explicit false values are incorrectly interpreted as true.

The expected invariant is:

> Boolean flags with explicit false must not be interpreted as true.

## Scope

Included:

- boolean flags accepting `--flag=false`
- boolean flags accepting `--flag=true`
- deterministic rejection of invalid boolean values
- preserving intended presence-only shorthand, where supported
- regression tests for affected command families

Excluded:

- unexpected positional argument handling, already covered by Phase 3
- value-flag token handling, already covered by Phase 4
- duplicate singleton flag behavior
- JSON shorthand behavior
- JSON output contract behavior
- storage, GC, packed-storage, restore/recovery internals
- CI workflow changes
- dependency/toolchain changes

# Implementation Summary

Phase 5 changed boolean flag parsing for the following command families:

| Command / Family | Flag(s) | Change | Test coverage |
|---|---|---|---|
| CLI parser (`parseCommandLine`) | boolean flags in `flagsWithoutValues` | `--flag=false` now parses as false, `--flag=true` as true, invalid boolean values are rejected deterministically at parse time | `TestParseCommandLineBooleanFlagExplicitValues`, `TestParseCommandLineRejectsInvalidBooleanValue` |
| Inspect command options | `--reverse` | explicit false no longer enables reverse behavior; presence-only shorthand still enables reverse | `TestRunInspectCommandFlagsPassedThrough`, `TestRunInspectCommandReverseExplicitFalseDoesNotEnableReverse` |
| Snapshot delete gate | `--force`, `--dry-run` | explicit false no longer satisfies the force/dry-run requirement | `TestRunSnapshotCommandDeleteRequiresForceAndForwards` |
