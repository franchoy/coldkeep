# v1.10.4 Phase 2 — Snapshot Retention Reachability

Status: Complete

## Purpose

Phase 2 validates and documents snapshot-retention reachability protection for GC.

The expected invariant is:

> Any data reachable from a retained snapshot must be protected from GC deletion until the snapshot is explicitly deleted or retention semantics allow release.

- survey snapshot-retention data model and table relationships
- survey GC candidate-selection integration with snapshot roots
- validate snapshot-retained logical files/chunks/blocks are GC roots
- validate dry-run excludes snapshot-retained data from reclaimability
- validate destructive GC cannot delete snapshot-retained physical data

- validate regression tests cover retained-data protection
- document validation contract

## Snapshot Data Model Survey

| Entity / table | Reference role | Retention meaning | GC relevance |
|---|---|---|---|
| `snapshot` | Root retention metadata | Snapshot is a named point-in-time data retention marker | Snapshot ID is key for root set exclusion |
| `snapshot_path` | Path normalization cache | Normalized filesystem paths referenced in snapshots | Used in snapshot_file edges |
| `snapshot_file` | File retention linkage | Logical files reachable/visible at snapshot time | Directly references `logical_file_id` as GC root |
| `logical_file` | File identity | Persistent file representation across current/snapshot views | Root target when snapshot_file.logical_file_id == logical_file.id |
| `file_chunk` | Chunk reference from files | Chunks composing logical files | Transitively reachable from snapshot → logical_file → file_chunk |
| `chunk` | Chunk identity and liveness | Dedup unit; live_ref_count tracks current+pin usage | Reachable from snapshot_file via logical_file → file_chunk |
| `blocks`, `storage_blocks` | Physical storage mapping | Chunks → physical container storage | Reachable from chunk; containers retained if any block reachable |
| `container` | Physical storage unit | Sealed or active storage container holding packed blocks | Deletion target; protected if any contained chunk is snapshot-retained |

## Snapshot Retention Validation Contract

### Root Rules

- A retained snapshot is a GC root via `snapshot_file` entries.
- Logical files referenced by retained `snapshot_file` rows are protected.
- Chunks reachable from protected logical files are protected.
- Blocks reachable from protected chunks are protected.
- Physical containers holding protected blocks are protected.

### Candidate Rules

- GC candidates must exclude snapshot-retained logical-file roots.
- Dry-run candidate output must not include snapshot-retained containers in reclaimability estimate.
- Destructive GC must skip or refuse snapshot-retained containers.
- Ambiguous snapshot reachability must fail closed (retain conservatively).

### Release Rules

- Snapshot-retained data may become collectible only after snapshot deletion or explicit release semantics.
- Snapshot deletion must update root set before next GC run.
- GC must not infer release from missing snapshot metadata silently (fail closed).

### Error Behavior

- If snapshot-reachability cannot be evaluated, GC must fail deterministically or conservatively retain.
- Snapshot-retention violations must be observable in tests or produce error codes.

- Snapshot-retained data is treated as protected from GC deletion.
- Dry-run does not classify snapshot-retained data as collectible.
- Destructive GC does not delete snapshot-retained data.
- Snapshot-retained physical data remains intact while snapshot exists.
- Snapshot deletion enables GC reclamation of now-unretained data.
- Multi-snapshot scenarios correctly preserve retention for shared data.
- Packed storage blocks retain same semantics.
