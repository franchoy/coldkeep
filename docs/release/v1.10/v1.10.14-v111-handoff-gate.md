# v1.10.14 v1.11 Handoff Gate

Status: Complete

## Purpose

This document closes the v1.10.x stabilization train and defines the entry rules for v1.11.

v1.11 may begin only after v1.10.14 is complete.

## Release Position

v1.10.x completed the reliability freeze and correctness-hardening train.

v1.10.13 completed the final post-release correctness-hardening pass.

v1.10.14 closes release evidence, public release documentation, tracker source-of-truth clarification, and v1.11 handoff documentation.

## v1.11 Allowed Starting Scope

v1.11 may start with behavior-preserving engine facade work only.

The first v1.11 work must wrap current behavior before moving logic.

The first v1.11 work must prove parity before lifting logic.

## v1.11 Forbidden Starting Scope

The first v1.11 phase must not:

- change CLI syntax;
- change CLI behavior;
- change JSON output shape;
- change exit codes;
- change storage format;
- change repository format;
- change schema behavior;
- change migration behavior;
- change restore semantics;
- change verify semantics;
- change GC safety semantics;
- change snapshot semantics;
- change SQLite behavior;
- change PostgreSQL behavior;
- change the default database backend;
- remove PostgreSQL compatibility;
- introduce SQLite-only assumptions;
- introduce catalog abstraction;
- create `internal/catalog`;
- perform broad refactors;
- introduce product features;
- merge unrelated cleanup.

## Wrapper-First Rule

The first v1.11 implementation must create a facade around existing behavior.

The facade must call the existing implementation first.

Existing behavior must remain the source of truth until parity is proven.

No logic should be lifted, split, or rewritten before wrapper parity evidence exists.

## Parity-Before-Lifting Rule

A v1.11 PR may lift or move logic only after proving that the facade preserves current behavior.

Parity evidence must include:

- affected command or operation;
- affected invariant;
- before/after CLI behavior;
- before/after JSON behavior, if applicable;
- before/after exit-code behavior;
- before/after storage behavior, if applicable;
- before/after repository-format behavior, if applicable;
- before/after SQLite behavior, if applicable;
- before/after PostgreSQL behavior, if applicable;
- tests run;
- reason behavior is unchanged.

## Required v1.11 PR Evidence

Every v1.11 PR must include:

- release phase;
- affected invariant;
- affected files;
- affected command/operation;
- explicit behavior-change statement;
- CLI compatibility statement;
- JSON compatibility statement;
- exit-code compatibility statement;
- storage/repository-format compatibility statement;
- SQLite/PostgreSQL compatibility statement;
- tests run;
- validation result;
- rollback risk.

## Required v1.11 Invariants

v1.11 must preserve:

- deterministic restore;
- verify fail-closed behavior;
- GC safety;
- snapshot correctness;
- chunk/container integrity;
- packed and legacy storage compatibility;
- SQLite/PostgreSQL compatibility;
- CLI compatibility;
- JSON compatibility;
- exit-code compatibility;
- release evidence discipline.

## Catalog Boundary Rule

v1.11 must not introduce catalog abstraction unless a later v1.11 phase explicitly scopes it.

Catalog migration remains deferred unless intentionally promoted with a separate scope document and parity gate.

## SQLite/PostgreSQL Rule

v1.11 must not assume SQLite-only behavior.

v1.11 must not remove PostgreSQL compatibility.

Any engine facade must preserve both SQLite and PostgreSQL behavior unless a later release explicitly changes product direction.

## Release Evidence Rule

v1.11 PR summaries must not claim:

- tracker rows are closed unless the PR actually closes or updates them;
- Codacy findings are fixed unless the finding is removed, suppressed, or dismissed with rationale;
- full release readiness unless the full release gate was run;
- behavior preservation unless parity evidence exists.

## Handoff Decision

Complete.

v1.10.14 authorizes v1.11 planning and implementation only under the behavior-preserving engine facade rules above.

v1.10.14 does not start v1.11 implementation.
