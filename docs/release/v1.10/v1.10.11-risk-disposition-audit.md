## Method

For each `needs_review` S1 item:

1. Re-read the original source finding from remediation-matrix.csv and issue-tracker.csv.
2. For scanner/static-analysis findings: review the flagged source code location to determine
   whether the finding is a confirmed vulnerability, a false positive, or a deferred concern.
3. Apply the disposition classification:
   - `fixed` — confirmed closed by a prior release with explicit matrix evidence
   - `accepted` — risk explicitly accepted with documented rationale; tracking reference assigned
   - `deferred` — requires future work; target release or backlog recorded
   - `suppressed` — confirmed false positive after code review; rationale documented
   - `still_needs_review` — cannot be dispositioned without additional information

## Accepted Risks

### CK-11011-S1-009 — dependencies / CK-110-M009

**Finding:** Go toolchain CVE baseline — 46 Codacy scanner findings grouped under M009
(CVE-2025-58185 and CVE-2026-27139 in Go standard library).

**Disposition: accepted**

**Rationale:** `go.mod` specifies `go 1.25` with `toolchain go1.25.10`. This is an actively
maintained Go toolchain. No individual CVE within the 46-finding M009 grouping has been
confirmed to affect a coldkeep-specific code path in a way that would trigger a production data
invariant. Scanner-sourced CVE groupings at the standard library level are addressed by tracking
the maintained toolchain version. go1.25.10 represents the appropriate mitigation posture for
these findings.

**Deferred target:** Future toolchain upgrades (v1.10.12+) will address specific CVEs as patches
are published. The maintained toolchain version is the mitigation.

**Evidence:** `go.mod` (go 1.25; toolchain go1.25.10); issue-tracker.csv CK-110-0012 and
CK-110-0058 (both triaged, no confirmed code-path exploitation).

### CK-11011-S1-014 — benchmark / CK-110-M018

**Finding:** OS command injection in `internal/benchmark/scenarios.go` — `exec.Command` called
with `spec.Executable` and `spec.Args...` without explicit validation at the call site.

**Disposition: accepted**

**Rationale:** Code review of `defaultCommandRunner()` (line 441) confirms `spec.Executable`
is sourced from `ScenarioConfig.ColdkeepExecutable`. When empty, `withDefaults()` falls back
to the hardcoded literal string `"coldkeep"`. Callers supply configuration-time values, not
untrusted user input at runtime. The benchmark package is an internal testing tool, not a
production data path. There is no route from untrusted user input to `spec.Executable` in normal
operation. OS command injection risk in benchmark configuration tooling is accepted for v1.10.11.

**Evidence:** `internal/benchmark/scenarios.go` (line 441 `defaultCommandRunner`; `withDefaults()`
hardcoded fallback); issue-tracker.csv CK-110-0046 (triaged, benchmark domain).

## Suppressed Findings

### CK-11011-S1-010 — security / CK-110-M012

**Finding:** Dynamic SQL injection scanner findings — 3 source issues grouped under M012:
CK-110-0013, CK-110-0040 (both in `internal/observability/stats.go`) and CK-110-0014
(in `internal/repository/capabilities/derive.go`).

**Disposition: suppressed — all 3 sub-findings are confirmed scanner false positives.**

#### CK-110-0013 and CK-110-0040 (stats.go — dynamic SQL)

Code review of `internal/observability/stats.go` lines 340–430 confirms both flagged areas
use correct parameterized queries. The scanner flags `fmt.Sprintf("$%d", i+1)` which appears
in:

```go
placeholders[i] = fmt.Sprintf("$%d", i+1)
args[i] = chunkID
// ...
query := `SELECT id, size FROM chunk WHERE id IN (` + strings.Join(placeholders, ", ") + `)`
rows, err := s.db.QueryContext(ctx, query, args...)
```

This is the standard Go pattern for building IN-clause queries with a variable number of
parameters. The `fmt.Sprintf` call constructs positional placeholder indices (`$1`, `$2`, etc.),
not SQL values. The actual values are passed as bound arguments via `args...` to `QueryContext`.
There is no SQL injection vector. The scanner incorrectly classified the placeholder construction
as dynamic SQL insertion.

#### CK-110-0014 (derive.go — PRAGMA table_info)

Code review of `internal/repository/capabilities/derive.go` line 348:

```go
rows, err := dbconn.QueryContext(ctx, fmt.Sprintf("PRAGMA table_info(%s)", tableName))
```

Analysis:
1. **SQLite PRAGMA cannot be parameterized.** `PRAGMA table_info()` requires a literal table
   name — SQLite does not accept `?` or `$1` placeholders for PRAGMA identifiers. The use of
   `fmt.Sprintf` here is the only technically valid approach.
2. **`tableName` is not user input.** The function `columnExists()` is called from compile-time
   application schema introspection logic. Callers pass hardcoded schema constants:
   `"blocks"`, `"storage_blocks"`, `"chunk_block_refs"`. There is no code path from user CLI
   input or stored data to the `tableName` parameter.
3. **Read-only introspection.** `PRAGMA table_info` is a read-only schema inspection call. Even
   in a theoretical injection scenario, the impact would be limited to schema metadata reads.

This is a scanner false positive. No code fix is required or appropriate.

migration, snapshot, and storage domains (37 + 5 + 2 + 11 + 3 + 12 + 1 = 71 total findings).

### Restore hardening — M087 (1 item)

**CK-11011-S1-013 (restore / M087):** Mode-specific flag cross-contamination (CK-110-1500,
CK-110-1501) is a genuine restore hardening concern: restore mode flags must be rejected
outside their valid mode. Addressing this requires production code changes to restore mode
validation logic. Code changes to production restore logic are out of scope for v1.10.11
stabilization.

**Deferred target:** post-v1.10.11 (requires dedicated restore hardening phase).

### CI / tooling — M043, M045 (2 items)

**CK-11011-S1-015 (ci / M043):** `DB_SSLMODE` propagation in release scripts is a CI
reliability concern. It does not directly affect production data invariants or stored data

**CK-11011-S1-016 (tooling / M045):** 28 scanner findings across release and benchmark scripts
(`scripts/smoke.sh`, `scripts/validate_regression_thresholds.py`, and others). Script robustness
improvements are out of scope for v1.10.11.

**Deferred target:** backlog.

No S0/S1 item remains unknown or unexplained after Phase 3. Every Phase 2 `needs_review` row

  recovery correctness invariants are covered by existing test suites.
- **Restore hardening (M087):** The mode-specific flag validation gap is tracked and explicitly
  deferred. It does not compromise the primary path-safety invariant addressed in v1.10.5.
- **CI/tooling (M043, M045):** Release scripts do not affect production stored data.
