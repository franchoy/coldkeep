# v1.10.9 — Filesystem Fault Injection Phase 1

Status: Active

## Release Goal

v1.10.9 introduces deterministic, test-only filesystem fault injection for Coldkeep.

The goal is to prove that filesystem failures in correctness-critical paths do not cause silent corruption, unsafe metadata, broken restore, unsafe GC, or unrecoverable repository state.

v1.10.9 builds on the v1.10.8 filesystem abstraction groundwork.

## Core Invariant

v1.10.9 must prove that deterministic filesystem failures do not cause silent corruption, unsafe metadata, broken restore, unsafe GC, or unrecoverable repository state.

## Included Scope

v1.10.9 may include:

- deterministic scripted fault filesystem for tests;
- ENOSPC simulation;
- write failure simulation;
- partial write simulation;
- fsync failure simulation;
- close failure simulation where relevant;
- rename failure simulation;
- mkdir failure simulation where relevant;
- stat failure simulation where relevant;
- remove failure simulation where relevant;
- restore fault-injection tests;
- container write/seal fault-injection tests;
- recovery/quarantine fault-injection tests;
- GC delete failure tests;
- no-silent-corruption verification matrix;
- release evidence and test inventory updates.

## Excluded Scope

v1.10.9 must not include:

- production user-facing fault injection controls;
- randomized chaos by default;
- nondeterministic fault scheduling in PR CI;
- broad storage rewrites;
- engine extraction;
- catalog abstraction;
- default database changes;
- CLI behavior changes;
- repository format changes;
- container format changes;
- CI workflow rewrites unless strictly needed for fault tests;
- performance benchmarking expansion;
- mutation testing;
- cross-platform matrix expansion.

## Fault Classes

Initial deterministic fault classes:

1. fail next write;
2. partial write;
3. fail fsync;
4. fail close;
5. fail rename;
6. fail mkdir;
7. fail stat;
8. fail remove;
9. ENOSPC after N bytes.

## Primary Packages of Interest

The likely packages of interest are:

- `internal/fsx`
- `internal/storage`
- `internal/container`
- `internal/recovery`
- `internal/maintenance`
- `internal/verify`

Supporting package:

- `internal/fsx/faultfs` or equivalent test-only fault helper package.

## Release Philosophy

Fault injection exists to validate safety, not to create a new product feature.

Every injected failure must have a deterministic script and an explicit expected safe outcome.

The default no-fault path must remain behavior-preserving.

## Success Criteria

v1.10.9 succeeds when:

- deterministic test-only fault filesystem exists;
- restore failure scenarios are covered;
- container write/seal failure scenarios are covered;
- recovery/quarantine failure scenarios are covered;
- GC delete failure scenarios are covered;
- no-silent-corruption matrix exists and passes;
- injected failures fail closed or recover deterministically;
- no production user-facing fault injection behavior is added;
- local validation passes.
