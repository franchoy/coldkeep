# v1.10.4 Phase 1 — GC Reachability Survey & Invariants

Status: Complete

## Purpose

Phase 1 defines the GC reachability and deletion correctness contract for v1.10.4.

The expected invariant is:

> GC must never delete data reachable from any live logical file, snapshot, retained object, or required metadata path.

- survey snapshot-retention reachability

## GC Reachability and Deletion Invariants

### Reachability Invariants

- GC must not delete any block reachable from a live logical file.
- GC must not delete any block reachable from a retained snapshot.
- GC must not delete any physical file referenced by a reachable stored block.
- GC must treat snapshot reachability as an additional root set.
- GC candidate selection must be based on the same reachability model as verification/reporting.

### Reference Integrity Invariants

- Logical-file references to chunks must be internally consistent.
- Chunk references to blocks must be internally consistent.
- Block references to physical files/containers must be internally consistent.
- Missing reference edges must fail deterministically where they affect GC safety.
- Duplicate/conflicting references must not lead to unsafe deletion.

### Candidate Selection Invariants

- GC candidates must be unreferenced by all live logical roots.
- GC candidates must be unreferenced by all snapshot-retained roots.
- GC candidates must be unreferenced by required metadata roots.
- Candidate selection must not rely on stale or partial query results.
- Candidate selection must fail closed when reachability is ambiguous.

### Dry-Run / Destructive-Run Invariants

- Dry-run and destructive-run candidate sets must match under equivalent repository state.
- Dry-run must not mutate storage.
- Destructive-run must delete only candidates that dry-run would report.
- Any state mutation between dry-run and destructive-run must invalidate parity assumptions or be explicitly guarded.

### Physical Deletion Invariants

- Physical deletion must only happen after reachability checks pass.
- Physical deletion must be scoped to Coldkeep-owned physical storage paths.
- Missing physical files must be reported deterministically.
- Physical deletion must not remove files outside managed storage roots.
- Partial deletion failures must be reported clearly.

### Orphan / Report Invariants

- Orphan reports must distinguish unreachable metadata from missing physical data.
- Reports must not classify snapshot-retained data as orphaned.
- Reports must be stable enough for release-gate validation.
- Reported candidate counts must match actionable deletion candidates where applicable.

### Concurrency / Mutation Invariants

- GC must not run concurrently with mutations that can change reachability unless guarded.
- GC destructive mode should fail closed if mutation safety cannot be guaranteed.
- Snapshot deletion/creation and GC destructive mode require clear serialization or refusal semantics.
