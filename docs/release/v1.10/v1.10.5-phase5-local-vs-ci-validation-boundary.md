# v1.10.5 Phase 5 — Local-vs-CI Validation Boundary Clarification

Status: Complete

## Purpose

Phase 5 clarifies how local validation and CI validation should be interpreted for v1.10.5 and future releases.

The expected invariant is:

> Local validation exceptions must be explicitly classified, and CI remains the authoritative release gate for environment-sensitive tests.

## Scope

Included:

- define local validation categories
- define CI validation authority
- define when local failures are release-blocking
- define when local failures may be documented as environment constraints
- define how Phase 12 and the Pre-PR gate should record local-vs-CI differences
- update v1.10.5 release-control artifacts

Excluded:

- changing CI workflows
- changing test implementation
- changing product code
- changing dependencies/toolchain
- tracker/matrix closure
- broad flaky-test remediation
- replacing the pre-release checklist

- v1.10.5 Phase 4 full-suite timeout investigation

## Design Rule

Phase 5 is a validation-policy phase.

It clarifies how to interpret local and CI results without changing code, tests, or CI workflows.

## Validation Categories

v1.10.5 uses the following validation categories.

| Category | Meaning | Release impact |
| --- | --- | --- |
| local required gate | Must pass locally before PR or be fixed | Blocking if failed |
| local environment-sensitive gate | May depend on local DB, Docker, filesystem, or resource limits | Blocking only if reproducible in CI or not classified |
| CI authoritative gate | GitHub CI result for PR/release branch | Blocking if failed |
| advisory static/security gate | Analyzer output that may include baseline findings | Blocking only for new release-delta issues |
| archived/non-gating check | Historical checklist item retained for documentation | Not blocking if explicitly marked archived |

## Local Failure Classification Rules

A local validation failure must be classified before release.

| Classification | Meaning | Required action |
| --- | --- | --- |
| release-blocking local failure | Failure is deterministic, relevant, and not environment-specific | Fix before PR/release |
| local environment constraint | Failure caused by missing DB/Docker/service/resource available in CI | Document, rerun relevant targeted gates, rely on CI |
| known bounded exception | Previously investigated and unchanged exception | Document and verify no new symptoms |
| new unclassified failure | Failure not previously investigated | Blocking until classified |
| analyzer baseline finding | Existing static/security finding not introduced by release delta | Document/defer |
| analyzer release-delta finding | Static/security finding introduced by current release | Fix or explicitly accept with rationale |

Rules:

- A new unclassified local failure is always release-blocking.
- CI failure is always release-blocking unless the CI configuration itself is proven invalid.
- Local environment constraints must name the missing prerequisite or bounded condition.
- Bounded exceptions must point to the phase/report where they were classified.

## Phase 12 Recording Requirements

During Phase 12 — Full Local PRE_RELEASE_CHECKLIST.md Execution, the execution report must record:

- active checklist sections executed
- archived/non-gating sections skipped or treated as historical
- local required gates and pass/fail result
- environment-sensitive gates and prerequisites
- any local failure classification
- any bounded exception reference
- targeted reruns used to support release readiness
- final workspace cleanliness
- whether CI is required to confirm an environment-sensitive result

If any full-suite local exception occurs, the Phase 12 report must include:

- command that failed or timed out
- package/test involved
- whether it matches a known bounded exception
- targeted validation that passed
- CI expectation
- release decision rationale

## Pre-PR Gate Recording Requirements

During the Pre-PR Code Quality / Codacy-Risk Gate, the checklist or optional evidence doc must record:

- command bundle executed
- pass/fail result for each command
- unavailable tool handling
- analyzer baseline findings
- analyzer release-delta findings
- changed files from `origin/main...HEAD`
- changed Go files reviewed
- changed docs reviewed
- final working tree cleanliness

If `gosec`, `golangci-lint`, `staticcheck`, or another analyzer reports findings, the result must distinguish:

- fixed release-delta issue
- documented baseline finding
- false positive
- tooling exception

## CI Authority Policy

For v1.10.5 and later:

- PR CI is authoritative for release merge readiness.
- Local validation is required before PR but may have documented environment-sensitive exceptions.
- If local validation passes but CI fails, the release is blocked until CI is fixed or the CI failure is classified.
- If local validation has a bounded environment exception but CI passes, the release may proceed.
- If the same bounded exception reproduces in CI, the release is blocked until re-investigated.
- If Codacy reports new release-delta issues, they must be fixed or explicitly accepted before merge.

This policy does not reduce local validation requirements. It clarifies how to handle differences between local and CI environments.
