# v1.10.12 v1.11 Transition Checklist

Status: Complete

## Purpose

This document converts the v1.10.12 engine-boundary readiness evidence into a
concrete transition checklist for future v1.11 behavior-preserving
engine-boundary work.

It records v1.11 entry gates, release blockers, phase blockers, required v1.11
evidence, and explicit v1.12 handoff items synthesized from all Phase 2–7
inventories.

This document is handoff evidence only. It does not start v1.11 implementation
work, define production engine APIs, or define production catalog APIs.

## Core Invariant

v1.10.12 may prepare the v1.11 transition checklist, but it must not start
v1.11 implementation work.

v1.11 may only extract engine boundaries in a behavior-preserving, correctness-
first manner. Every v1.11 change must pass all invariants documented here before
merging.

## Release / Phase Blockers

**Release blockers (27):** Checks that must pass before the corresponding v1.11
gate or the v1.10.12-to-v1.11 transition itself is permitted. A release blocker
that is not satisfied must block the relevant v1.11 PR from merging.

Key release-blocker themes:

- v1.11 must start only from a released v1.10.12 tag; no branching from an
  unreleased commit.
- SQLite and PostgreSQL must remain dual targets; the PostgreSQL 16 CI service
  must not be removed.
- All Phase 5 invariants (31 rows) must have documented future owners before
  v1.11 branching.
- Catalog abstraction must not precede the Phase 7 assumption inventory
  completion (already satisfied).
- Frozen contracts (CLI exit codes 1/2/3/4; JSON error envelope shape) must
  not change.
- Path traversal rejection for restore must remain in the filesystem boundary.
- Write durability chain (fsync-before-DB-commit; temp/rename/sync) must be
  preserved.
- Every mutating operation must continue to use explicit BeginTx/Commit/Rollback.

**Phase blockers (11):** Checks that must pass before the phase that introduces
the relevant facade or boundary. A phase blocker prevents the specific facade
from being created until the check passes, but does not block the entire v1.11
release if the facade is not yet being built.

## v1.11 First Implementation Rule

The first v1.11 implementation phase must wrap existing behavior only.

Specifically:

1. The first v1.11 PR must create wrapper facade functions that delegate to
   existing implementations without moving any business logic.
2. No business logic may be moved in the wrapping phase.
3. No behavior may change.
4. No CLI behavior, JSON output, or exit code may change.
5. Tests must pass without modification.
6. The PR diff must show only new wrapper functions and any new tests for those
   wrappers.

This is the `wrap_existing_behavior` migration mode recorded in the Phase 4
operation contract candidate inventory (OPC-11012-001 through OPC-11012-032).

## Required v1.11 Evidence

Every v1.11 implementation PR must include the following evidence before merging:

1. **Affected invariant ID** — the INV-11012-XXX row from the Phase 5 invariant
   ownership map that this PR affects or preserves.
2. **Affected operation candidate ID** — the OPC-11012-XXX row from the Phase 4
   operation contract candidate inventory.
3. **Source checklist rows** — the CHK-11012-XXX rows from this document that
   are satisfied by this PR.
4. **Reason behavior is unchanged** — a written statement explaining why the
   change does not alter any observable behavior, CLI output, JSON output, or
   exit code.
5. **Before/after CLI behavior** — smoke test output before and after the change.
6. **Before/after JSON behavior** — JSON output diff showing no change.
7. **Before/after exit-code behavior** — exit code confirmation.
8. **Backend compatibility status** — SQLite and PostgreSQL integration test
   results; confirmation that COLDKEEP_TEST_DB=1 tests pass.

## Release Boundary

v1.10.12 establishes the readiness evidence base. v1.11 is the first release
permitted to begin behavior-preserving engine-boundary work, subject to all
gates in this checklist.

v1.11 must not:

- change runtime behavior
- change CLI output
- change JSON output
- change exit codes
- change default database backend
- remove PostgreSQL compatibility
- introduce SQLite-only behavior
- define production catalog APIs
- start catalog abstraction
- start engine extraction beyond facade wrapping
- implement daemon behavior
- implement SQLite-first local productization
- implement PostgreSQL server-mode behavior
