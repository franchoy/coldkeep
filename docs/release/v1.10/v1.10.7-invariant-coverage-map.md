# v1.10.7 Invariant Coverage Map

Status: Captured

## Purpose

This document maps v1.10.7 critical-path coverage evidence to named Coldkeep correctness invariants.

The goal is to prevent coverage from becoming a raw percentage exercise.

Coverage is only meaningful when it protects a correctness property that matters for data safety, deterministic restore, GC safety, verification integrity, recovery safety, catalog compatibility, or automation reliability.

## Interpretation Rule

A package can have acceptable line coverage but still be weak if the wrong invariant paths are covered.

A package can have moderate line coverage but still provide strong release confidence if the critical invariant paths are directly exercised.

Therefore, v1.10.7 records three evidence states:

| State          | Meaning                                                                                          |
| -------------- | ------------------------------------------------------------------------------------------------ |
| `covered`      | Existing coverage and release evidence appear sufficient for the invariant at this phase.        |
| `partial`      | Existing coverage is visible but the invariant should be treated as a future hardening priority. |
| `observe-only` | The invariant is useful to watch, but should not block v1.10.7.                                  |

## Tier 1 Invariants

### CK-INV-GC-REACHABILITY

GC must never delete snapshot-reachable or current-live data.

Primary packages:

* `internal/gc`
* `internal/maintenance`

Evidence status: `covered`

Coverage signal:

* `internal/gc`: 81.2%
* `internal/maintenance`: 47.6%

Interpretation:

The direct GC package has strong baseline coverage. Maintenance orchestration is lower visibility and should remain a future hardening priority, but Phase 4 does not add tests or enforce thresholds.

### CK-INV-RESTORE-DETERMINISM

Restore must be deterministic and must reconstruct the intended bytes and paths.

Primary package:

* `internal/storage`

Evidence status: `partial`

Coverage signal:

* `internal/storage`: 67.7%
* `internal/container`: 62.1%
* `internal/blocks`: 85.1%

Interpretation:

Storage coverage is visible, but restore is broad and correctness-critical. Future hardening should focus on stored-path modes, overwrite behavior, packed/legacy restore parity, and interrupted restore evidence.

### CK-INV-VERIFY-FAIL-CLOSED

Verify must fail closed on corrupted or inconsistent catalog/storage state.

Primary package:

* `internal/verify`

Evidence status: `covered`

Coverage signal:

* `internal/verify`: 66.6%
* `internal/storage`: 67.7%
* `internal/container`: 62.1%
* `internal/blocks`: 85.1%

Interpretation:

Verify has moderate coverage but strong correctness relevance. Future work should map individual corruption classes to tests rather than chase raw coverage.

### CK-INV-RECOVERY-FAIL-CLOSED

Recovery must not legitimize corrupt mappings or ambiguous physical state.

Primary package:

* `internal/recovery`

Evidence status: `partial`

Coverage signal:

* `internal/recovery`: 44.9%
* `internal/storage`: 67.7%
* `internal/db`: 76.6%

Interpretation:

Recovery is the most important low-visibility Tier 1 package after Phase 3. It should become a future targeted hardening area.

### CK-INV-SNAPSHOT-ROOTS

Snapshots must remain immutable roots for restore and retention.

Primary package:

* `internal/snapshot`

Evidence status: `covered`

Coverage signal:

* `internal/snapshot`: 86.3%
* `internal/gc`: 81.2%
* `internal/retention`: 82.1%
* `internal/graph`: 75.3%

Interpretation:

Snapshot and supporting graph/retention/GC packages have strong baseline evidence. The priority is preventing regression.

### CK-INV-PACKED-LEGACY-PARITY

Packed and legacy storage behavior must remain semantically aligned.

Primary packages:

* `internal/storage`
* `internal/blocks`

Evidence status: `covered`

Coverage signal:

* `internal/storage`: 67.7%
* `internal/blocks`: 85.1%
* `internal/verify`: 66.6%
* `internal/container`: 62.1%

Interpretation:

Packed/legacy behavior has visible evidence across storage, blocks, verify, and container packages. Future work should explicitly track packed-only, legacy-only, and mixed-repository cases.

### CK-INV-PHYSICAL-METADATA-REUSE

Reclaim/rebuild must not reuse stale or inconsistent physical metadata.

Primary package:

* `internal/storage`

Evidence status: `covered`

Coverage signal:

* `internal/storage`: 67.7%
* `internal/db`: 76.6%
* `internal/container`: 62.1%

Interpretation:

This invariant comes directly from the v1.10.6 adversarial `aes-gcm` CI blocker fix. It must stay mapped because it protects against stale physical metadata reuse and payload mismatch regressions.

## Future Hardening Priorities

Phase 4 identifies these future coverage-hardening priorities:

1. `internal/recovery` fail-closed behavior.
2. `internal/maintenance` orchestration paths.
3. Restore determinism subpaths inside `internal/storage`.
4. Container placement and encrypted/compressed payload accounting.
5. Explicit packed-only / legacy-only / mixed-repository invariant mapping.

These are not Phase 4 implementation tasks.
