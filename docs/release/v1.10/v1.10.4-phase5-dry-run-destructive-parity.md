# v1.10.4 Phase 5 — Dry-Run vs Destructive-Run Parity

Status: Complete

## Purpose

Phase 5 validates dry-run and destructive-run GC parity.

The expected invariant is:

> For the same repository state, GC dry-run and destructive-run must evaluate the same candidate set before destructive deletion occurs.

## Dry-Run / Destructive Path Survey

Both paths enter through `RunGCWithContainersDirResult(dryRun bool, containersDir string)` in [internal/maintenance/gc.go](internal/maintenance/gc.go) L89. The `dryRun` bool is the sole mode selector.

### Shared Pre-Flight Logic (Both Paths)

The following code is executed identically by both dry-run and destructive GC, before any candidate divergence:

| Step | Function / query | Location | Purpose |
|---|---|---|---|
| 1 | `pg_try_advisory_lock($1)` | gc.go L105–120 | Exclusive advisory lock prevents concurrent GC |
| 2 | `gcPhysicalIntegrityCheck()` | gc.go L122–168 | Refuses GC if orphan rows, ref_count mismatches, or negative ref_counts detected |
| 3 | `gcComputeReachability()` | gc.go L172 | Returns snapshot-retained logical file IDs |
| 4 | `gcMarkReachableChunks()` | gc.go L183 | Computes reachable chunk set from all roots (live + snapshot) |
| 5 | `gcLoadLivePackedBlockIDs()` | gc.go L187 | Resolves live chunks to packed block IDs |
| 6 | `gcLoadLiveLegacyContainerIDs()` | gc.go L193 | Resolves live chunks to legacy container IDs |
| 7 | Candidate query | gc.go L199–207 | `SELECT id, filename FROM container WHERE quarantine=FALSE AND sealed=TRUE ORDER BY id ASC` |
| 8 | `containerHasReachableChunks()` | gc.go L303–317 | Safety net: excludes any container whose chunks are still reachable from any root |

### Divergence Points (4)

| # | Point | Dry-run path | Destructive path | Risk |
|---|---|---|---|---|
| DP-1 | Empty container check | Non-locking SQL: no `FOR UPDATE`; reads live_ref_count and pin_count without write lock (gc.go L215–235) | Locking SQL: `FOR UPDATE` on container row, then chunk rows; re-evaluates emptiness under lock (gc.go L236–298) | None: same criteria, different locking level; dry-run is non-committing so no race risk |
| DP-2 | Transaction outcome | `tx.Rollback()` — all writes within tx discarded; candidate recorded in result; no `os.Remove()` (gc.go L318–325) | `SweepUnreachableChunks()`, `DELETE FROM container`, `tx.Commit()`, then `os.Remove()` (gc.go L327–375) | None: by design; rollback ensures non-mutation |
| DP-3 | Active container cleanup | **Skipped** — `cleanupFullyDeadActiveContainers()` not called; fully-dead active (unsealed) containers not reflected in dry-run output (gc.go L376–382) | `cleanupFullyDeadActiveContainers()` runs after sealed container loop; fully-dead active containers deleted | Acceptable conservative gap: dry-run undercounts edge-case active containers; trustworthy as a lower-bound preview |
| DP-4 | Reporting | `result.ContainerFilenames` and `result.AffectedContainers` populated identically to destructive path for sealed container candidates | Same | None: both paths use identical append logic for sealed candidates |

## Candidate Set Representation

| Field | Source | Dry-run available | Destructive available | Parity use |
|---|---|:---:|:---:|---|
| `AffectedContainers` | `GCResult.AffectedContainers` int | ✅ Yes | ✅ Yes | Primary parity proxy: sealed candidate count |
| `ContainerFilenames` | `GCResult.ContainerFilenames` []string | ✅ Yes | ✅ Yes | Filename-level parity: same filenames in same order |
| `SnapshotRetainedContainers` | `GCResult.SnapshotRetainedContainers` int | ✅ Yes | ✅ Yes | Retained count parity |
| `SnapshotRetainedLogicalFiles` | `GCResult.SnapshotRetainedLogicalFiles` int | ✅ Yes | ✅ Yes | Snapshot root set size parity |
| `DryRun` | `GCResult.DryRun` bool | ✅ Yes (true) | ✅ Yes (false) | Mode flag only; not a candidate field |
| Active container reclaimable | Not in `GCResult` | ❌ No (DP-3) | Not in `GCResult` either (silent cleanup) | Not usable for parity; documented gap |

The `AffectedContainers` count and `ContainerFilenames` slice are the stable parity proxies. Both are populated identically for sealed container candidates before the dry-run/destructive divergence at DP-2.

## Dry-Run / Destructive Parity Contract

### Candidate-Set Rules

- Dry-run and destructive-run must compute the same candidate set under equivalent repository state.
- Destructive-run must delete only candidates that dry-run would report for the same state.
- If dry-run cannot compute a safe candidate set, destructive-run must not proceed.
- If destructive-run computes a candidate not represented by dry-run logic, that is a parity failure.

### Non-Mutation Rules

- Dry-run must not mutate repository metadata.
- Dry-run must not delete physical data.
- Dry-run must not change candidate eligibility for future GC runs.
- Dry-run output must be safe to use as a preview.

### State Assumption Rules

- Parity applies to equivalent repository state.
- Repository mutations between dry-run and destructive-run can change candidate sets.
- DP-3 (active container cleanup) is an accepted conservative exception: dry-run does not report fully-dead active containers.
- Destructive-run must still revalidate candidate safety immediately before deletion (via `FOR UPDATE` locks and `containerHasReachableChunks`).

### Reporting Rules

- Dry-run report counts must represent actionable sealed-container candidate counts.
- Destructive-run deletion counts must be traceable to the same sealed-container candidate set.
- Protected data must not appear as reclaimable in either mode.
- DP-3 gap must be treated as documentation, not a reporting correctness issue.
