# v1.10.12 Engine Boundary Scope Contract

Status: Complete

## Purpose

This contract defines what v1.10.12 may and may not do while preparing Coldkeep for v1.11 engine-boundary work.

## Core Invariant

v1.10.12 may prepare engine-boundary work, but it must not implement engine extraction or catalog abstraction.

## Allowed Work

v1.10.12 may:

- inventory CLI/business-logic coupling;
- inventory direct database access;
- inventory filesystem/storage-context access;
- identify engine operation contract candidates;
- identify request/result shapes for future engine operations;
- map invariant ownership;
- define no-behavior-change migration rules;
- inventory SQLite/PostgreSQL assumptions;
- create v1.11 transition checklists;
- create documentation and release-control evidence.

## Forbidden Work

v1.10.12 must not:

- create `internal/engine`;
- create `internal/catalog`;
- move business logic into an engine package;
- move catalog logic behind a new abstraction;
- change runtime behavior;
- change repository format;
- change container format;
- change database schema;
- change default database backend;
- change CLI behavior;
- change JSON output shape;
- change exit-code behavior;
- introduce daemon behavior;
- introduce API/UI behavior;
- add product features;
- perform broad refactors;
- chase style-only cleanup;
- remove PostgreSQL compatibility;
- introduce SQLite-only assumptions into future engine contracts.

## Behavior Change Policy

The default behavior-change policy is:

```text
no behavior changes
```

If a behavior issue is discovered during v1.10.12, do not fix it inside a readiness/inventory phase unless it is an active S0/S1 correctness blocker.

Instead:

1. record it;
2. classify it;
3. decide whether it belongs to a later corrective release or v1.11 planning;
4. avoid hiding it behind the future engine boundary.

## Engine Boundary Readiness Definition

v1.10.12 is successful when v1.11 can start with:

* known CLI/business-logic coupling points;
* known direct DB access points;
* known filesystem/storage-context access points;
* candidate engine operations;
* request/result shape sketches;
* invariant ownership map;
* no-behavior-change migration rules;
* SQLite/PostgreSQL assumption inventory;
* transition checklist.

## Release Claim Boundary

v1.10.12 may claim:

```text
engine-boundary readiness evidence is complete
```

v1.10.12 must not claim:

```text
engine extraction started
engine facade implemented
catalog abstraction implemented
CLI decoupled from business logic
database backend changed
```

## Scope Violation Examples

The following are scope violations in v1.10.12:

* adding `internal/engine/service.go`;
* renaming/moving CLI-owned command logic;
* introducing engine request/result structs in production code;
* replacing direct DB usage with a new catalog interface;
* changing command behavior to make future extraction easier;
* rewriting restore/GC/snapshot internals for shape;
* changing JSON output to simplify future API usage;
* making SQLite the default local backend;
* removing PostgreSQL paths or tests.

## Handoff

This contract controls Phases 1–10 of v1.10.12.
