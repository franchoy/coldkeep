## Design Rule

Phase 8 validates mutation-safety boundaries.

Do not broaden into daemon architecture, global scheduler, queue system, or engine extraction. If current v1.x cannot serialize every operation globally, document the boundary and ensure destructive GC fails closed where practical.

## Mutation-Sensitive Operation Survey

- Operation: store
  Mutates: DB + filesystem (container append + metadata writes in `internal/storage/store.go`)
  GC risk: liveness graph can change after dry-run candidate preview
  Existing guard: destructive GC locks container/chunk rows and checks liveness at delete time
  Phase 8 action: documented boundary + revalidation evidence via dry-run-not-authorization test
- Operation: delete logical file
  Mutates: DB metadata (`physical_file`, `logical_file`, `file_chunk`, `chunk` refs) in `internal/storage/remove.go`
  GC risk: can reduce reachable refs and alter candidate set
  Existing guard: remove path checks snapshot retention (`retention.IsLogicalFileReferencedBySnapshot`) and uses backend-aware row locks where supported
  Phase 8 action: documented as mutation-sensitive path with existing retention guards
- Operation: snapshot create
  Mutates: DB metadata (`snapshot`, `snapshot_file`) in `internal/snapshot/snapshot.go`
  GC risk: adds retained roots that must not be reclaimed
  Existing guard: GC computes reachability and applies snapshot-retention safety net (`containerHasReachableChunks`)
  Phase 8 action: existing behavior documented; overlap treated as point-in-time boundary
- Operation: snapshot delete
  Mutates: DB metadata (`snapshot_file`, `snapshot`) in `internal/snapshot/snapshot.go`
  GC risk: can make data newly reclaimable
  Existing guard: destructive GC recomputes and evaluates live state on each run; dry-run is point-in-time preview
  Phase 8 action: existing dry-run/delete transitions retained and documented
- Operation: repair
  Mutates: DB metadata rewrites (`logical_file.ref_count`, `chunk.live_ref_count`) in `internal/maintenance/repair_refcounts.go`
  GC risk: drift can invalidate candidate assumptions
  Existing guard: GC pre-flight refuses on integrity drift (`CodeGCRefusedIntegrity`) until repaired
  Phase 8 action: fail-closed repair overlap behavior confirmed by existing tests
- Operation: destructive GC
  Mutates: DB + filesystem metadata deletion in `internal/maintenance/gc.go`
  GC risk: unsafe overlap could delete now-live data
  Existing guard: advisory lock singleton (PostgreSQL), per-container row/chunk lock checks, retention safety net, and fail-closed integrity gate
  Phase 8 action: added deterministic guardrail tests and boundary documentation

## Transaction / Locking Survey

- Mechanism: `pg_try_advisory_lock` singleton
  Location: `internal/maintenance/gc.go`
  Protects: prevents overlapping destructive GC sessions on PostgreSQL
  Does not protect: no equivalent advisory primitive on SQLite
  Phase 8 conclusion: covered by `TestRunGCRefusesWhenAdvisoryLockAlreadyHeld`; SQLite boundary documented
- Mechanism: pre-flight graph integrity refusal
  Location: `internal/maintenance/gc.go` and `internal/verify`
  Protects: blocks destructive GC when orphans/refcount drift/negative counts are present
  Does not protect: does not serialize all writers globally
  Phase 8 conclusion: fail-closed safety confirmed by existing GC integrity refusal tests
- Mechanism: per-container `FOR UPDATE` and chunk lock query
  Location: `internal/maintenance/gc.go` via `internal/db/backend.go`
  Protects: stabilizes destructive delete decision on PostgreSQL during container sweep
  Does not protect: SQLite lacks `FOR UPDATE` and relies on backend transaction semantics
  Phase 8 conclusion: boundary documented; deterministic mutation guard test confirms re-evaluation
- Mechanism: snapshot-retention safety net (`containerHasReachableChunks`)
  Location: `internal/maintenance/gc.go`
  Protects: prevents reclaiming chunks retained by snapshot roots even with zero live_ref_count
  Does not protect: dry-run results are still point-in-time and can become stale
  Phase 8 conclusion: dry-run non-authorization contract explicitly documented and tested
- Mechanism: backend capability gates (`QueryWithOptionalForUpdate*`)
  Location: `internal/db/backend.go`
  Protects: backend-specific lock SQL only where supported
  Does not protect: not a global cross-process serializer
  Phase 8 conclusion: explicit PostgreSQL vs SQLite behavior captured in Phase 8 notes
- Mechanism: SQLite lock wait policy (`busy_timeout`)
  Location: `internal/db/db.go`
  Protects: reduces transient lock churn under SQLite contention
  Does not protect: not a singleton GC lock or cross-process queue
  Phase 8 conclusion: documented as operational boundary, not full serialization

## GC Concurrency / Mutation Guardrail Contract

### Destructive GC Rules

- Destructive GC must not delete based on stale reachability assumptions.
- Destructive GC must revalidate candidate safety before deletion.
- Destructive GC must fail closed if reference integrity changes during candidate/deletion flow.
- Destructive GC must not run concurrently with metadata repair that can rewrite reachability.
- Destructive GC must not overlap snapshot create/delete in a way that can invalidate retained roots.

### Dry-Run Rules

- Dry-run is non-mutating and may run concurrently only if it reports a point-in-time or best-effort view.
- Dry-run output must not be treated as an authorization token for later destructive deletion without revalidation.
- Dry-run must not lock or mutate unnecessarily.

### Mutation Rules

- Store/delete/snapshot/repair mutations that change reachability must either serialize with destructive GC or destructive GC must revalidate after them.
- Snapshot retention roots must be recomputed or protected immediately before destructive deletion.
- Physical deletion must occur only after final safety checks.

### Boundary Rules

- v1.x does not introduce daemon/global queue architecture.
- If full cross-process serialization is not implemented, the documented boundary must be explicit.
- Tests should prove practical fail-closed behavior for supported local execution paths.
