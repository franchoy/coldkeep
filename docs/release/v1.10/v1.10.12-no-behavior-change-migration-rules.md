## Release-Blocking Rules

The following 21 rules carry `violation_severity = release_blocker`. v1.11 must not proceed on any affected surface if these rules are violated:

- **MIG-11012-001** (behavior_preservation): Wrap existing behavior before lifting any orchestration
- **MIG-11012-002** (behavior_preservation): Wrap store pipeline before lifting write internals
- **MIG-11012-003** (behavior_preservation): Wrap restore orchestration before lifting chunk-sequencing
- **MIG-11012-004** (behavior_preservation): Wrap GC reachability before extracting live-data computation
- **MIG-11012-006** (filesystem_boundary): Preserve restore destination sanitization and traversal rejection
- **MIG-11012-007** (filesystem_boundary): Preserve temp-write-rename-fsync durability chain
- **MIG-11012-008** (filesystem_boundary): Preserve GC commit-then-delete ordering
- **MIG-11012-010** (catalog_boundary): Preserve snapshot create atomicity (all-or-nothing)
- **MIG-11012-013** (transaction_boundary): Preserve transaction boundaries across all mutating operations
- **MIG-11012-014** (failure_semantics): Preserve verify fail-closed behavior and exit code 3
- **MIG-11012-016** (failure_semantics): Preserve recovery quarantine fail-closed behavior
- **MIG-11012-017** (ordering_preservation): Preserve startup recovery gate ordering
- **MIG-11012-021** (json_cli_contract): Preserve CLI exit codes 1/2/3/4
- **MIG-11012-022** (json_cli_contract): Preserve JSON error envelope shape
- **MIG-11012-025** (validation_boundary): Preserve CLI command names and flag syntax
- **MIG-11012-027** (catalog_boundary): Preserve SQLite/PostgreSQL compatibility
- **MIG-11012-028** (release_control): Do not introduce production engine APIs before contract evidence
- **MIG-11012-029** (release_control): Do not introduce catalog abstraction before Phase 7 inventory
- **MIG-11012-030** (release_control): Do not introduce SQLite-only behavior
- **MIG-11012-031** (release_control): Do not remove PostgreSQL paths or tests
- **MIG-11012-034** (test_evidence): Prove invariant tests still pass after wrapping

## v1.11 Application Rules

v1.11 must use these rules as preconditions before engine facade work.

Minimum expected v1.11 flow:

```text
1. wrap existing behavior;
2. prove CLI/JSON/exit-code parity;
3. prove invariant tests still pass;
4. only then lift orchestration;
5. do not refactor internals while defining the initial facade;
6. do not change database defaults;
7. do not remove PostgreSQL compatibility;
8. do not introduce catalog abstraction before catalog assumptions are inventoried (Phase 7).
```

## Evidence Requirements

Every future v1.11 migration step must record:

- affected invariant
- operation candidate
- before/after command behavior
- JSON/CLI behavior
- exit-code behavior
- tests run
- database backend coverage
- reason behavior is unchanged
