# v1.10.6 CI/Codacy Release Gate Boundary

Status: Active for v1.10.6

## Purpose

This policy defines which CI and Codacy outcomes block a v1.10.x release and which outcomes remain advisory.

## Core Rule

CI and Codacy gates must protect correctness and release integrity without turning style-only or baseline-noise findings into release blockers.

## Release-Blocking CI Outcomes

The following CI outcomes block merge/release:

- required GitHub CI workflow failure;
- failed correctness-critical Go tests;
- failed race tests in release-relevant packages;
- failed snapshot/restore/GC/verify/repair validation;
- failed CLI/JSON contract validation;
- failed release checklist validation;
- failed security/dependency scan with plausible reachable production exposure;
- failed documentation/release consistency validation for release-control files;
- missing required release evidence.

## Release-Blocking Codacy Outcomes

Codacy findings block merge/release only when they are:

- release-delta findings;
- unclassified;
- actionable;
- in production code or release-critical scripts;
- tied to correctness, security, determinism, resource safety, data safety, or release integrity.

Examples:

- unchecked errors in restore, verify, GC, store, repair, migration, or release scripts;
- unsafe filesystem/path handling;
- possible SQL/command injection;
- resource leak in production path;
- dependency vulnerability with plausible reachable exposure;
- hardcoded secret in production code;
- unsafe temp/rename behavior in production path.

## Advisory / Non-Blocking CI Outcomes

The following outcomes are advisory unless tied to release-delta correctness/security risk:

- style-only lint warnings;
- naming-only warnings;
- generic maintainability scoring;
- complexity warnings without correctness impact;
- documentation formatting preferences;
- baseline scanner findings already classified;
- test-only scanner warnings with rationale;
- advisory coverage trends without critical-path gap.

## Advisory / Non-Blocking Codacy Outcomes

Codacy findings are advisory when they are:

- baseline-deferred;
- false-positive with rationale;
- test-only accepted;
- duplicate analyzer finding;
- tooling/config noise;
- style-only;
- generic maintainability or complexity signal;
- intentionally duplicated invariant checks.

## Required Gate Decision Model

Each gate result must be classified as:

| Decision | Meaning | Release behavior |
|---|---|---|
| pass | Gate passed | Release may continue |
| fail-blocking | Gate failed and blocks release | Fix or explicitly accept only with strong rationale |
| advisory | Gate produced signal but does not block | Document/defer |
| baseline-classified | Known baseline finding | Document and continue |
| false-positive | Not a real defect in context | Document rationale |
| environment-sensitive | Local-only/environment-specific issue | Classify and rely on CI if applicable |
| not-applicable | Gate does not apply to current scope | Document reason |

## Local vs CI Boundary

Local validation is required before PR, but CI is authoritative for merge readiness.

A local issue may be non-blocking only when:

- it is environment-sensitive;
- it is already classified;
- relevant targeted gates pass;
- CI passes;
- the release notes or checklist record the exception.

A CI failure is blocking unless the CI configuration itself is proven invalid.

## Pre-PR Requirement

Before opening a PR:

- run local validation;
- run the Pre-PR Code Quality / Codacy-Risk Gate;
- classify scanner findings;
- document baseline findings;
- confirm no unclassified release-delta issues remain;
- confirm final working tree is clean.

## Merge Requirement

Before merge:

- required CI must be green;
- Codacy analysis must complete;
- Codacy findings must be classified;
- release-delta actionable findings must be fixed or explicitly accepted;
- no release-blocking unknown findings may remain;
- PR/release docs must reflect the final state.

## Prohibited Gate Behavior

Do not:

- block releases on style-only findings;
- block releases on baseline findings already classified;
- treat Codacy as architecture authority;
- add hard quality gates without release scope approval;
- use scanner warnings to justify broad refactors;
- convert unknown findings to accepted without review;
- ignore CI failures because local tests passed.
