# v1.10.2 Phase 4 — Restore Destination Safety

Status: Complete

## Purpose

Phase 4 hardens restore destination handling so restore output paths remain inside the selected restore root and unsafe destination/path combinations fail before any writes.

The expected invariant is:

> Restore destinations must stay contained under the selected root, must reject symlinked destination roots or path components, and must preserve create-missing-parent behavior without allowing destination escape.

## Scope

Included:

- restore destination containment in snapshot restore planning
- restore destination containment in storage restore resolution
- final write-boundary validation before temp file creation and rename
- prefix-mode root containment
- override-mode destination containment
- stored-path restore re-entry validation
- traversal / absolute / drive-style / UNC-like / NUL rejection for restore destination planning inputs where applicable
- focused regression tests

Excluded:

- symlink policy expansion beyond restore destination containment
- temp/rename redesign
- CLI batch semantics
- Phase 3 snapshot path ingestion changes
- container filename validation, Phase 2
- script validation, Phase 10
- CI/workflow changes
- dependency/toolchain changes
- tracker/matrix closure work beyond the required row update

## Design Rule

Phase 4 reuses the shared path-safety helpers instead of duplicating containment policy in snapshot or storage restore code.

## Implementation Summary

Phase 4 hardens two restore trust boundaries:

| Area | Change |
|---|---|
| Snapshot restore planning | `planSnapshotRestoreOutputs` revalidates stored snapshot paths and uses `pathsafe.SafeJoin` for prefix-mode output construction. |
| Storage restore resolution | `resolveRestoreOutputPath` now rejects unsafe original/prefix/override destinations, and `restoreFileWithDBAndDir` validates the final output path before mkdir/temp/rename. |
