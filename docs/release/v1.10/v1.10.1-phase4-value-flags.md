# v1.10.1 Phase 4 — Value Flags Reject Flag Tokens

Status: Complete

## Purpose

Phase 4 fixes CLI value flags that can accidentally accept another flag token as their value.

The expected invariant is:

> Value flags must reject another flag token as their value.

## Scope

Included:

- value flags that require a non-empty user value
- validation of values that begin with `-` or `--` when those values are not valid for the flag
- deterministic error behavior
- validation before stateful work where practical
- regression tests for affected command families

Excluded:

- unexpected positional argument handling, already covered by Phase 3
- boolean explicit false semantics
- duplicate singleton flag behavior
- JSON shorthand behavior
- JSON output contract behavior
- storage, GC, packed-storage, restore/recovery internals
- CI workflow changes
- dependency/toolchain changes

# Implementation Summary

Phase 4 changed value-flag validation for the following command families:

| Command / Family | Flag(s) | Change | Test coverage |
|---|---|---|---|
| CLI parser (`parseCommandLine`) | `--output`, value flags in `flagsWithValues` | Rejects known flag tokens (both `--flag value` and `--flag=--other`) as missing required values for value flags | `TestParseCommandLineRejectsKnownFlagTokenForOutput`, `TestParseCommandLineRejectsKnownFlagTokenForOutputEqualsForm` |
| CLI parser numeric value-flag path | `--limit` | Rejects known flag token values before numeric parsing | `TestParseCommandLineRejectsKnownFlagTokenForLimit` |
| CLI parser literal compatibility | dash-prefixed literals not known as flags | Preserves unknown dash-prefixed literals as valid values | `TestParseCommandLineAcceptsLiteralDashPrefixedUnknownValue` |
