# v1.10.6 Codacy Passive-Mode Policy

Status: Active for v1.10.6

## Purpose

This policy defines how Codacy should be used during the v1.10.x stabilization train.

Codacy is useful as passive signal and release-risk visibility, but it must not become architectural authority, correctness authority, or a style-only release blocker.

## Core Rule

Codacy is signal, not authority.

Coldkeep remains correctness-first. The primary invariant is:

> Never lose user data.

Codacy findings must be interpreted through Coldkeep's domain invariants:

- GC safety;
- restore determinism;
- verification integrity;
- crash/recovery safety;
- packed/legacy parity;
- SQLite/PostgreSQL compatibility;
- CLI and JSON contract stability;
- release reproducibility.

## Allowed Codacy Uses

Codacy may be used for:

- PR annotations;
- quality trend visibility;
- dependency/security surfacing;
- unchecked-error visibility;
- possible resource-leak visibility;
- duplicate-code visibility in correctness-critical paths;
- suspicious security pattern surfacing;
- maintainability trend tracking;
- baseline comparison.

## Codacy Must Not Be Used For

Codacy must not be used as:

- architecture authority;
- correctness authority;
- invariant authority;
- a reason for broad refactors during v1.10.x;
- a blocker for style-only findings;
- a reason to simplify explicit safety logic;
- a reason to remove apparently duplicated invariant checks;
- a reason to change CLI/JSON contracts;
- a reason to introduce engine extraction or catalog abstraction.

## Blocking Policy

Codacy findings are release-blocking only when they are:

- release-delta findings;
- real or plausibly real;
- in production code or release-critical scripts;
- connected to correctness, security, determinism, resource safety, or release integrity.

Examples of potentially blocking findings:

- unchecked errors in restore, verify, GC, store, repair, migration, or release scripts;
- resource leaks in production paths;
- path traversal or unsafe filesystem operations;
- SQL injection or command injection risks;
- dependency vulnerabilities with plausible reachable exposure;
- hardcoded secrets in production code;
- unsafe temporary file handling in production paths.

## Non-Blocking / Advisory Policy

Codacy findings are advisory when they are:

- style-only;
- naming-only;
- generic maintainability scoring;
- generic complexity without correctness risk;
- duplicate-code warnings around explicit invariant checks;
- test-only warnings with documented rationale;
- baseline findings already classified;
- false positives with rationale;
- documentation formatting preferences.

Advisory findings may be documented, deferred, suppressed, or accepted with rationale.

## Required Classification

Each Codacy finding reviewed during v1.10.6 must be classified as one of:

- release-delta actionable;
- release-delta accepted with rationale;
- baseline deferred;
- duplicate analyzer finding;
- false positive;
- test-only accepted;
- tooling/config noise;
- release-blocking unknown.

Unknown release-delta findings block merge until classified.

## Suppression / Acceptance Requirement

Suppressions and accepted findings must include rationale.

Acceptable rationale examples:

- test-only fixture with no production exposure;
- explicit invariant check duplicated intentionally;
- scanner cannot model Coldkeep's fail-closed behavior;
- finding is baseline-wide and not introduced by this release;
- finding is advisory and outside v1.10.6 scope.

Unacceptable rationale examples:

- "Codacy is annoying";
- "style only" without explaining why it is not correctness-relevant;
- "will fix later" without classification;
- suppressing production security/correctness risk without evidence.

## PR Requirement

Before merging a v1.10.6 PR:

- Codacy analysis must complete.
- All release-delta findings must be classified.
- Actionable release-delta findings must be fixed or explicitly accepted.
- No release-blocking unknown findings may remain.
- Baseline findings must not trigger unrelated broad cleanup.
