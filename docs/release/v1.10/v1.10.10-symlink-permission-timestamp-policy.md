# v1.10.10 Symlink / Permissions / Timestamp Policy

Status: Complete

## Purpose

This document defines Coldkeep's v1.10.10 policy for platform-sensitive filesystem metadata.

The policy exists to avoid overclaiming behavior that differs across Linux, macOS, and Windows.

## Core Invariant

Coldkeep must not overclaim metadata equivalence across Linux, macOS, and Windows. Symlink, permission, timestamp, and case-sensitivity behavior must be tested where safe and documented where platform-dependent.

## Scope

This policy covers:

- symlink behavior;
- permissions and file modes;
- timestamps;
- case sensitivity;
- host filesystem metadata semantics.

## Actual Metadata Behavior

Coldkeep stores the following metadata fields per physical file in the database:

- `mode` — `os.FileMode` stored as INT64;
- `mtime` — modification time stored as DATETIME;
- `uid` — user ID (POSIX);
- `gid` — group ID (POSIX);
- `is_metadata_complete` — completeness flag.

On restore, Coldkeep applies `os.Chmod`, `os.Chtimes`, and `os.Chown` to the restored file when metadata is complete. The `--no-metadata` flag skips this application. The `--strict` flag causes restore to fail if metadata is incomplete.

This behavior is tested on Linux. Cross-platform equivalence on macOS and Windows is not tested in v1.10.10.

## Policy Summary

| Area | v1.10.10 Policy |
|---|---|
| File bytes | Must restore byte-identically where restore succeeds |
| Stored paths | Must remain path-safe and traversal-safe |
| Permissions (Linux) | Stored and restored via os.Chmod on Linux when metadata is complete |
| Permissions (macOS) | Stored and likely restored; cross-platform equivalence not tested in v1.10.10 |
| Permissions (Windows) | Must not be claimed as equivalent to POSIX mode bits |
| Timestamps (Linux) | Stored and restored via os.Chtimes on Linux when metadata is complete |
| Timestamps (cross-platform) | Must not be claimed as equivalent across filesystems/platforms |
| Symlinks | Must not be claimed as portable; resolved at store time; rejected at restore time |
| Case sensitivity | Must be treated as host/filesystem-dependent |
| Windows metadata | Must be validated on Windows CI before support claims are made |

## Symlink Policy

Coldkeep does not store or restore symlinks as symlinks.

At store time, symlinks are resolved via `filepath.EvalSymlinks` to their canonical real path. The resolved path is stored; the symlink itself is not.

At restore time, `pathsafe.ValidatePathHasNoSymlinkComponents` rejects any destination path that contains a symlinked component. This prevents restore from writing outside the intended destination root via a symlink traversal.

Symlink behavior can differ because:

- Windows may require privileges or developer mode for symlink creation;
- symlink permissions and target resolution behavior differ across platforms;
- path traversal through symlinks can create safety risks;
- backup tools must define whether they store the symlink itself or the target contents.

For v1.10.10:

- symlink behavior is documented conservatively;
- unsupported or untested symlink behavior remains a documented limitation;
- path traversal safety must not rely on symlink behavior being identical across platforms.

## Permissions Policy

Coldkeep stores and restores POSIX mode bits on Linux. Cross-platform equivalence is not tested in v1.10.10.

Permission behavior can differ because:

- Windows does not map directly to POSIX mode bits;
- umask and default ACL behavior can change resulting file modes;
- macOS and Linux may differ in default metadata handling;
- CI runners may have different default umask settings.

For v1.10.10:

- byte-identical restore is the correctness baseline;
- permission preservation is confirmed on Linux via `os.Chmod`;
- permission equivalence across platforms is not a release guarantee unless explicitly tested;
- documentation must avoid claiming permission identity on Windows.

## Timestamp Policy

Coldkeep stores and restores modification timestamps on Linux. Cross-platform equivalence is not tested in v1.10.10.

Timestamp behavior can differ because:

- filesystem timestamp precision varies;
- access time behavior can be disabled or lazy;
- modification times can round differently across filesystems;
- restore operations may create new filesystem timestamps.

For v1.10.10:

- byte-identical restore is the correctness baseline;
- timestamp restoration is confirmed on Linux via `os.Chtimes`;
- timestamp identity across platforms is not a release guarantee unless explicitly tested;
- timestamp differences must not be interpreted as byte corruption.

## Case-Sensitivity Policy

Coldkeep must treat case sensitivity as host/filesystem-dependent.

Coldkeep does not case-fold stored paths. Identity is preserved aligned with case-sensitive filesystems.

Examples:

- Linux filesystems are commonly case-sensitive;
- macOS default APFS setups may be case-insensitive;
- Windows filesystems are commonly case-insensitive but can vary by configuration.

For v1.10.10:

- tests must avoid assuming global case sensitivity unless running on a controlled filesystem;
- documentation must avoid claiming identical behavior across all host filesystems;
- path safety checks must not depend on case-sensitivity assumptions unless documented.

## Release Claim Boundary

v1.10.10 may claim:

- byte-identical restore for tested restore paths;
- path safety for tested path validation paths;
- permission and timestamp restoration on Linux where metadata is complete;
- documented platform limitations for metadata-sensitive behavior.

v1.10.10 must not claim:

- portable symlink preservation;
- POSIX permission equivalence on Windows;
- timestamp identity across platforms;
- universal case-sensitive path behavior;
- full Windows/macOS production support beyond what CI proves.

## Handoff

Later v1.10.10 phases may add CI matrix coverage and update this policy if platform-specific tests prove stronger behavior.
