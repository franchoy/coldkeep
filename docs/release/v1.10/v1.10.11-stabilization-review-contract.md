# v1.10.11 Stabilization Review Contract

Status: Complete

## Purpose

This document defines the review contract for v1.10.11 stabilization and regression burn-down work.

v1.10.11 is not a feature release. It is the release that closes the v1.10 stabilization train and prepares Coldkeep for later engine-boundary preparation.

## Core Invariant

v1.10.11 stabilization work must only reduce known release risk, preserve v1.10 behavior, and avoid engine extraction, catalog abstraction, product features, broad refactors, or untracked behavior drift.

## Review Goal

Every v1.10.11 change must answer:

1. What release risk does this reduce?
2. Which invariant does it protect?
3. Is this S0/S1/S2/S3/S4?
4. Is the change behavior-preserving or behavior-changing?
5. If behavior-changing, is the change required for correctness?
6. Is there regression evidence?
7. Does it affect SQLite/PostgreSQL compatibility?
8. Does it affect packed/legacy storage parity?
9. Does it affect CLI, JSON, or exit-code contracts?
10. Does it affect restore, verify, GC, recovery, snapshot, or migration behavior?

## Allowed Work

v1.10.11 may include:

- S0/S1 issue review and closure;
- S2 issue closure only when related to the same invariant;
- suppression audit;
- accepted-risk audit;
- deferred-risk audit;
- long-run validation;
- adversarial validation;
- regression validation;
- flaky-test classification or narrow fix;
- release evidence cleanup;
- known-issues-after-v1.10 documentation;
- release-candidate gate preparation.

## Not Allowed

v1.10.11 must not include:

- engine extraction;
- catalog abstraction implementation;
- daemon work;
- API work;
- UI work;
- NAS/cloud/network behavior;
- default database backend changes;
- product features;
- broad refactors;
- style-only cleanup;
- large architecture movement;
- untracked behavior changes.

## Severity Review

Use the v1.10 severity model:

| Severity | Meaning | v1.10.11 Handling |
|---|---|---|
| S0 | Catastrophic correctness/data-loss risk | Must fix or explicitly prove impossible before release |
| S1 | Critical correctness/recovery/GC/restore risk | Must fix or explicitly document accepted/deferred rationale |
| S2 | Major reliability/contract/test/CI risk | Fix if related to stabilization scope |
| S3 | Minor consistency/UX/docs risk | Fix only if low-risk and scoped |
| S4 | Optional/style/refactor | Defer unless needed for release evidence |

## Required Review Questions

Before accepting a v1.10.11 change, check:

- Does this reduce known release risk?
- Does this preserve existing validated behavior?
- Is a regression test needed?
- Is the risk documented if not fixed?
- Does this introduce a new platform claim?
- Does this accidentally begin v1.11 engine work?
- Does this accidentally begin v1.12 catalog work?
- Does this hide a known risk behind cleaner wording?

## Behavior Change Policy

Behavior changes are allowed only when required to fix correctness, validation, recovery, CLI contract, JSON contract, CI integrity, or release evidence integrity.

All behavior changes must be:

- explicit;
- tested where practical;
- documented;
- scoped to the affected invariant;
- included in PR and release notes.

## Suppression / Accepted / Deferred Risk Policy

A finding may be suppressed, accepted, or deferred only if the rationale is explicit.

Do not suppress scanner findings only because they are noisy.

Do not mark a risk accepted unless the consequence is understood.

Do not mark a risk deferred unless there is a future target or clear rationale.

## Release Claim Boundary

v1.10.11 may claim:

- stabilization review completed;
- remaining high-risk issues audited;
- accepted/deferred risks documented;
- regression suites executed;
- flaky risks classified;
- v1.10 behavior prepared for freeze.

v1.10.11 must not claim:

- engine extraction completed;
- catalog abstraction completed;
- SQLite-first transition completed;
- v2.x readiness completed;
- full Windows/macOS production support;
- zero all-risk perfection;
- zero Codacy warnings.

## Exit Rule

v1.10.11 can proceed to release only when no known S0/S1 issue remains unknown, unreviewed, or untracked.
