# v1.10.7 Soft Threshold Policy

Status: Defined

## Purpose

This policy defines how v1.10.7 interprets critical-path coverage thresholds.

The policy is intentionally soft. It provides release visibility and future hardening direction without making v1.10.7 fail because of known baseline gaps.

## Core Principle

Coverage thresholds exist to protect correctness invariants, not to chase global coverage percentages.

A package should not be improved merely to raise a number. Coverage should be improved when it protects a named invariant such as GC reachability, deterministic restore, verify fail-closed behavior, recovery fail-closed behavior, packed/legacy parity, snapshot roots, or catalog compatibility.

## Threshold Classes

v1.10.7 uses four threshold classes.

| Class               | Meaning                                                        | Release Behavior                                              |
| ------------------- | -------------------------------------------------------------- | ------------------------------------------------------------- |
| Baseline required   | Coverage must be measurable and recorded for tracked packages. | Missing or malformed baseline evidence is release-blocking.   |
| Regression warning  | Coverage below the committed baseline should be explained.     | Warning in v1.10.7 unless tied to missing invariant evidence. |
| Soft target         | Desired future coverage level for Tier 1/Tier 2 packages.      | Advisory only in v1.10.7.                                     |
| Hard gate candidate | Future candidate for CI enforcement after policy matures.      | Not enforced in v1.10.7.                                      |

## v1.10.7 Threshold Direction

### Tier 1 — Release-critical

Tier 1 packages:

* `internal/storage`
* `internal/verify`
* `internal/maintenance`
* `internal/gc`
* `internal/snapshot`
* `internal/recovery`

Policy:

* baseline evidence is required;
* invariant mapping is required;
* regression from committed baseline must be explained;
* below-50% baseline packages are future hardening priorities;
* no absolute percentage failure is introduced in v1.10.7.

Soft target direction:

```text
Tier 1 target: 75%+ initially, 85%+ long-term where practical.
```

Known low-visibility Tier 1 packages:

```text
internal/maintenance: 47.6%
internal/recovery: 44.9%
```

These are not release blockers in v1.10.7 because they are known baseline facts and are mapped as future hardening priorities.

### Tier 2 — Catalog / graph / storage infrastructure critical

Tier 2 packages:

* `internal/db`
* `internal/graph`
* `internal/blocks`
* `internal/container`
* `internal/retention`

Policy:

* baseline evidence is required;
* invariant mapping is required;
* regression from committed baseline must be explained;
* no absolute percentage failure is introduced in v1.10.7.

Soft target direction:

```text
Tier 2 target: 70%+ initially, 80%+ long-term where practical.
```

### Tier 3 — Observe-only

Tier 3 areas:

* `cmd/coldkeep`
* `internal/observability`
* `internal/benchmark`
* `scripts`
* `tests/adversarial`
* `tests/integration`

Policy:

* report-only;
* no release blocking based on package coverage percentage;
* coverage may inform future work only when tied to a correctness or automation invariant.

## What Blocks v1.10.7

The following are release-blocking in v1.10.7:

1. Missing formal baseline coverage CSV.
2. Malformed baseline coverage CSV.
3. Missing Tier 1 package from baseline evidence.
4. Missing Tier 1 invariant from invariant coverage map.
5. Missing evidence state for a Tier 1 invariant.
6. Accidental introduction of hard absolute coverage enforcement.
7. Accidental introduction of global coverage gates.
8. Accidental CI workflow blocking based on raw coverage percentage.
9. Coverage script failure in report mode.
10. Coverage artifact generation failure.

## What Does Not Block v1.10.7

The following do not block v1.10.7 by themselves:

1. A known Tier 1 baseline below 75%.
2. A known Tier 1 baseline below 50%.
3. Tier 3 observe-only coverage gaps.
4. Lack of mutation testing.
5. Lack of global coverage enforcement.
6. Lack of hard threshold implementation.
7. Existing low coverage that is documented and mapped to future hardening.

## Regression Interpretation

If a future coverage run differs from the committed baseline:

* small variation should be reviewed but not automatically blocked;
* package removal or missing package coverage is suspicious;
* Tier 1 regression must be explained;
* Tier 2 regression should be explained;
* Tier 3 regression is advisory unless tied to a release-critical invariant.

For v1.10.7, regression interpretation remains policy-only.

Regression checking is designed in Phase 7.

## Future Hard-Gate Candidates

The following may become hard gates after v1.10.7 or in a later phase if implemented carefully:

1. baseline artifact exists and is parseable;
2. all Tier 1 packages appear in the coverage report;
3. all Tier 1 invariants appear in the invariant coverage map;
4. no unexplained Tier 1 coverage regression from committed baseline;
5. no package marked release-blocking has `n/a` coverage;
6. no global threshold gate is used as a substitute for invariant mapping.

## Explicit Non-Goals

v1.10.7 does not introduce:

* global coverage gates;
* hard absolute package thresholds;
* mutation testing;
* broad test refactors;
* coverage-driven product changes;
* CI blocking on raw coverage percentage;
* CodeRabbit adoption;
* Codacy zero-warning requirements.

## Release Interpretation

v1.10.7 succeeds if Coldkeep can say:

```text
We know the current critical-path coverage baseline.
We know which invariants are mapped.
We know which Tier 1 areas are low visibility.
We have a policy for interpreting soft thresholds.
We have not confused coverage percentage with correctness proof.
```
