# v1.10 Issue Tracker Source of Truth

Status: Complete

## Purpose

This document clarifies how v1.10 issue-tracker evidence should be interpreted after the v1.10.x stabilization train.

## Scope

This document applies to the v1.10 release train and to imported issue-tracker evidence used during v1.10.0 through v1.10.14.

It does not reopen completed releases and does not silently close tracker rows.

## Source-of-Truth Rule

The imported v1.10 issue tracker (`issue-tracker.csv`) is a frozen baseline.

Rows that remain `triaged`, `open`, `pending`, or otherwise unresolved in the imported baseline are not automatically current release blockers.

A finding becomes a current blocker only if it is explicitly carried forward into one of the following current evidence sources:

- a current release known-issues document;
- a current release final gate;
- a current release checklist;
- a current PR review;
- current CI evidence;
- current Codacy evidence;
- a current manually accepted blocker list.

## Current Release Readiness

Current release readiness is determined by per-release evidence, not by stale imported tracker state alone.

For v1.10.14, the release-readiness sources are:

- `docs/release/v1.10/v1.10.14-scope.md`;
- `docs/release/v1.10/v1.10.14-known-issues.md`;
- `docs/release/v1.10/v1.10.14-phase-status.md`;
- `docs/release/v1.10/v1.10.14-checklist.md`;
- `docs/release/v1.10/v1.10.14-final-release-gate.md`;
- PR CI evidence;
- main CI evidence after merge;
- Codacy review evidence;
- GitHub tag and release evidence.

## Tracker Row Closure Rule

A tracker row must not be described as closed unless the repository contains evidence that the row was actually fixed, dismissed, suppressed, superseded, or intentionally deferred.

Acceptable closure evidence includes:

- a commit that fixes the issue;
- a release document that records the fix;
- a final gate that records the decision;
- a Codacy dismissal/suppression with rationale;
- a known-issues document that intentionally defers it;
- a documented decision that the issue is obsolete or not applicable.

## Codacy Policy

Codacy is signal, not authority.

Codacy findings should be reviewed against Coldkeep invariants before action.

A Codacy finding should be fixed when it identifies a real issue affecting one of the following:

- data safety;
- restore determinism;
- verify fail-closed behavior;
- GC safety;
- snapshot correctness;
- catalog consistency;
- SQLite/PostgreSQL compatibility;
- release/CI integrity.

A Codacy finding may be dismissed or suppressed when it is a false positive, obsolete, non-applicable, style-only, or correctness-risky to fix.

## False-Positive Handling

False positives must be documented with rationale.

The rationale should include:

- finding identifier or rule name;
- affected file and line if available;
- why the finding is not applicable;
- whether any runtime behavior changed;
- whether any schema or repository-format behavior changed;
- whether the finding was dismissed, suppressed, or disabled.

## RAC_* SQL Pattern Decision

The Codacy / Opengrep pattern `Enforce Access to RAC_* Tables in SQL Queries` is not applicable to Coldkeep.

Coldkeep intentionally uses SQLite/PostgreSQL schema tables such as `storage_blocks`.

The RAC_* rule is an enterprise table-naming policy, not a SQL-injection finding for Coldkeep.

Static schema DDL such as:

```sql
CREATE UNIQUE INDEX IF NOT EXISTS idx_storage_blocks_container_id_offset
ON storage_blocks(container_id, container_offset);
```

does not contain user input, dynamic SQL construction, or an SQL injection vector.

Coldkeep must not rename schema tables to satisfy this rule.

If this pattern is reported against Coldkeep schema files, it may be dismissed or disabled with this rationale.

## Style-Only Findings

Style-only findings must not drive correctness-risky changes.

A style-only cleanup must not be described as correctness hardening.

## Deferred Rows

Rows left in the frozen imported tracker remain historical evidence unless carried forward into current release evidence.

They may be revisited in later releases, but they are not v1.10.14 blockers unless explicitly promoted.

## v1.10.14 Decision

v1.10.14 clarifies tracker semantics only.

It does not:

- close tracker rows without evidence;
- mass-edit imported tracker data;
- change runtime behavior;
- change tests;
- change CI;
- change scripts;
- change dependencies;
- start engine extraction;
- start catalog abstraction.
