# v1.10.6 Scanner Suppression / Acceptance Policy

Status: Active for v1.10.6

## Purpose

This policy defines how Coldkeep records scanner findings from tools such as Codacy, gosec, staticcheck, golangci-lint, govulncheck, and future analyzers.

The policy exists to prevent silent risk hiding.

## Core Rule

Scanner findings must never be silently ignored.

Every reviewed finding must have:

- decision,
- rationale,
- release impact classification,
- evidence or follow-up path.

## Decision Categories

| Decision | Meaning | Required evidence |
|---|---|---|
| fixed | Real issue fixed in this release | Fix commit, test/validation evidence |
| suppressed | Tool finding intentionally suppressed in code/config | Suppression comment and rationale |
| accepted | Real or plausible issue intentionally accepted | Risk rationale and owner/date/release context |
| deferred | Real or plausible issue deferred to later release | Target follow-up or deferral reason |
| duplicate | Same root cause as another finding | Link to canonical finding |
| baseline | Existing issue not introduced by current release | Baseline evidence and non-release-delta rationale |
| false-positive | Tool finding is not a real defect in context | Technical explanation |
| test-only-accepted | Finding exists only in test/fixture code | Test-only scope explanation |
| tooling-noise | Finding caused by analyzer limitation or config noise | Tooling/context explanation |
| release-blocking-unknown | Finding cannot be classified yet | Blocks release until resolved |

## Release Impact Classification

Each finding should be classified as one of:

| Impact | Meaning | Release behavior |
|---|---|---|
| release-blocking | Could affect correctness, security, determinism, data safety, or release integrity | Must fix or explicitly accept before merge |
| release-delta-actionable | Introduced/touched by current release and likely real | Fix before merge unless accepted with rationale |
| advisory | Useful signal but not release-blocking | Document/defer/suppress as appropriate |
| baseline-deferred | Existing finding not introduced by current release | Document and defer |
| test-only | Test/fixture-local finding | Accept with test-only rationale |
| false-positive | No real defect in context | Document rationale |
| not-applicable | Tool does not apply to this path or context | Document why |

## Suppression Rules

Suppressions are allowed only when:

- the finding is reviewed;
- the finding is not a hidden correctness/security risk;
- the suppression is as narrow as possible;
- the rationale is written near the suppression or in release evidence;
- the finding is not merely inconvenient.

Suppression comments should explain:

- what the tool reported;
- why the finding is safe or accepted;
- whether it is test-only, false-positive, baseline, or accepted risk;
- whether follow-up is required.

## Acceptance Rules

Accepted findings must include:

- what is being accepted;
- why it does not block the release;
- whether it is temporary or permanent;
- whether it has follow-up;
- release/version context.

Do not accept production correctness/security findings without explicit rationale.

## Deferral Rules

Deferred findings must include:

- reason for deferral;
- why deferral is safe for this release;
- whether the finding is baseline or release-delta;
- suggested future release or tracker reference when available.

## False-Positive Rules

False-positive classifications must include a technical explanation, not only a statement that the tool is wrong.

Examples:

- scanner cannot model fail-closed validation;
- scanner cannot see test fixture boundaries;
- scanner flags intentionally duplicated invariant checks;
- scanner reports a path that is unreachable in production.

## Required Release Evidence

For each release, scanner evidence should record:

- tool name;
- command or platform source;
- finding ID/rule;
- path;
- release-delta status;
- decision;
- rationale;
- release impact;
- validation/fix evidence if applicable.

## Prohibited Practices

Do not:

- suppress findings without rationale;
- mass-suppress scanner output;
- close findings only because they are noisy;
- convert unknown findings to accepted without review;
- use style-only findings to justify broad refactors;
- hide production correctness/security findings in baseline buckets;
- claim a scanner issue is fixed unless the finding is removed, suppressed with rationale, or documented with evidence.
