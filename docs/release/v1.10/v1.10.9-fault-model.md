# v1.10.9 Fault Model

Status: Draft for Phase 0

## Purpose

This document defines the deterministic filesystem fault model for v1.10.9.

The fault model is test-only. It exists to validate Coldkeep's behavior under realistic filesystem failure modes.

## Core Invariant

Injected filesystem failures must not cause silent corruption, unsafe metadata, broken restore, unsafe GC, or unrecoverable repository state.

## Determinism Requirement

Faults must be scripted and deterministic.

Allowed targeting mechanisms:

- fail operation by operation name;
- fail operation after N calls;
- fail write after N bytes;
- fail the next matching operation;
- fail only a named scenario.

Disallowed in v1.10.9:

- randomized failures in PR CI;
- timing-based nondeterministic faults;
- background chaos;
- global monkey-patching;
- production user-facing injection controls.

## Fault Classes

| Fault Class | Description | Example Operation | Expected Safe Outcome |
|---|---|---|---|
| fail-write | return write error before accepting bytes | container payload write | operation fails closed |
| partial-write | accept fewer bytes than requested and return error | restore temp write | no corrupted final file |
| fail-fsync | return sync error | restore temp fsync / container sync | no false success |
| fail-close | return close error where relevant | container close | error propagated or documented |
| fail-rename | return rename error | restore temp install | final destination not falsely reported as restored |
| fail-mkdir | return mkdir error | restore parent creation | operation fails before unsafe state |
| fail-stat | return stat error | recovery file-state check | recovery fails closed or reports diagnostic |
| fail-remove | return remove error | GC physical delete | GC remains retry-safe |
| enospc-after-bytes | fail after N total written bytes | container or restore write path | no silent corruption |

## Target Surfaces

### Restore

Initial target phases:

- parent directory creation;
- temp file creation/opening where seam permits;
- chunk/payload write;
- temp file fsync;
- final rename/install;
- directory fsync where seam permits;
- cleanup/remove.

Expected safe outcomes:

- no silent success;
- no corrupted final file;
- no unsafe overwrite;
- error identifies failed phase where possible;
- recovery behavior is deterministic.

### Container

Initial target phases:

- container open/create;
- header write;
- payload write;
- sync before commit/rotate;
- close where relevant;
- seal/quarantine metadata operation where applicable.

Expected safe outcomes:

- DB must not falsely claim successful sealed data;
- incomplete containers are detectable;
- verify detects partial writes;
- recovery/quarantine behavior remains deterministic.

### Recovery / Quarantine

Initial target phases:

- stat checks;
- read-dir orphan discovery;
- quarantine file-state handling.

Expected safe outcomes:

- recovery does not legitimize corrupt mappings;
- diagnostics remain accurate;
- quarantine classification remains safe.

### GC Delete

Initial target phases:

- physical file remove;
- retry after remove failure;
- simulated/live mode distinction.

Expected safe outcomes:

- no reachable data deletion;
- partial GC remains recoverable;
- failed deletes do not corrupt reachability state;
- retry behavior is safe.

## Non-Goals

v1.10.9 does not define:

- production fault injection;
- user-facing CLI flags for fault injection;
- randomized chaos tests;
- mutation testing;
- cross-platform fault matrix;
- performance benchmarks under faults.

## Handoff

Phase 1 should implement a deterministic test-only scripted fault filesystem helper based on this model.
