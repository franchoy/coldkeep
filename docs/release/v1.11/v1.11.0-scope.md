# v1.11.0 Scope

Status: In progress
Owner phase: v1.11.0 Phase 0 — Documentation Alignment and Engine-Facade Scope Declaration

## Release

v1.11.0 — Behavior-Preserving Engine Facade Baseline

## Purpose

v1.11.0 introduces the engine boundary for coldkeep without changing any observable behavior.

v1.10.x is closed. v1.11.0 starts from v1.10.16.

The goal is to create `internal/engine`, define request/result contracts, introduce `DefaultEngine`,
and route selected low-risk CLI commands through the engine — all while preserving exact parity with
the current CLI output, JSON output, exit codes, storage format, repository format, and schema behavior.

v1.11 is the first architecture phase after v1.10.x stabilization. It must not become a deep rewrite.
The engine facade is introduced before any logic migration. Parity must be proven before lifting.

## v1.10.x Closure

v1.10.x is complete as of v1.10.16. No v1.10.17 or later v1.10.x release is justified.

The starting point for all v1.11.0 development is the published v1.10.16 `main` baseline.

## Behavior-Preserving Rule

v1.11.0 is behavior-preserving. This rule is not optional.

Every change in v1.11.0 must be accompanied by evidence that:

- CLI human output is unchanged.
- JSON output shape is unchanged.
- Exit codes are unchanged.
- Error messages are unchanged in substance.
- Storage format is unchanged.
- Repository format is unchanged.
- Schema behavior is unchanged.
- Migration behavior is unchanged.
- GC, restore, verify, recovery, and snapshot behavior are unchanged.
- SQLite and PostgreSQL compatibility are preserved.

## Included Scope

v1.11.0 may include:

- creating `internal/engine` with request/result types and a `DefaultEngine` shell;
- defining engine operation contracts (Store, Restore, Remove, CreateSnapshot, RestoreSnapshot,
  DeleteSnapshot, RunGC, Verify, Stats, Inspect, Recover);
- implementing wrapper-only `DefaultEngine` methods that delegate to existing packages;
- routing selected low-risk CLI commands through the engine (starting with `stats`, `inspect`,
  `verify system`);
- adding equivalence tests proving CLI-before and CLI-after parity;
- adding dependency-direction CI checks proving `internal/engine` does not import `cmd/coldkeep`;
- lifting correctness invariants from CLI parsing into engine entry points (without removing CLI
  validation);
- SQLite and PostgreSQL compatibility baseline evidence;
- mutating operation wrappers (Store, Remove, GC, Snapshot, Recover) only after low-risk parity
  is proven and only as wrapper-first delegates;
- release documentation for each phase.

## Excluded Scope

v1.11.0 must not include:

- storage format changes;
- repository format changes;
- schema or migration behavior changes;
- default database backend changes (SQLite-first is future/local-first direction, not v1.11.0);
- SQLite-only assumptions in engine or catalog contracts;
- PostgreSQL compatibility removal;
- catalog abstraction (belongs to v1.12 unless explicitly re-scoped);
- daemon, API, or UI work (belongs to v2.x);
- local-first productization features (belongs to v2.x);
- network, NAS, cloud, or multi-user work (belongs to v3.x);
- broad refactors unrelated to the engine boundary;
- style-only or generic maintainability cleanup;
- CLI behavior changes;
- JSON output shape changes;
- exit-code changes;
- moving business logic without proven parity evidence.

## Planned Phase Sequence

This sequence is a draft and may be refined. The behavior-preserving rule is not refinable.


## Engine Boundary Rules

```
cmd/coldkeep          may import internal/engine
internal/engine       may import domain packages
domain packages       must not import internal/engine
internal/engine       must not import cmd/coldkeep
```

These rules must be enforced by Phase 5 at minimum, and preferably by automated CI checks.

## Required Invariants

The following invariants apply to all v1.11.0 work and must not be weakened:

```
GC must never delete reachable data.
Restore must never write outside the intended destination.
Verify must fail closed on inconsistent catalog/storage state.
Recovery must not legitimize corrupt mappings.
Packed and legacy storage behavior must remain aligned.
CLI parsing must not be the only place where correctness invariants live.
Engine APIs must not weaken existing safety guarantees.
```

## SQLite and PostgreSQL Stance

Coldkeep is moving toward SQLite-first local repositories. PostgreSQL remains the tested
server/centralized backend direction.

In v1.11.0:

- No default database backend change is made.
- Engine request/result types must contain no SQLite-only or PostgreSQL-only assumptions.
- PostgreSQL compatibility must remain continuously tested.
- SQLite behavior must remain unchanged.

SQLite-first local portability becomes real in v1.12/v1.13 if compatibility work is complete.
PostgreSQL remains continuously tested through v1.x, v2.x, and beyond.

## Roadmap Forward

```
v1.11.0  — Behavior-preserving engine facade
v1.12    — Orchestration migration and catalog facade
v1.13    — Engine contract stabilization and SQLite/PostgreSQL compatibility gates
v2.x     — Local-first productization: daemon, API, CLI thin client, UI, scheduling
v3.x     — Network, NAS, cloud, multi-user
```

v1.12 will:

- move more orchestration logic into the engine;
- introduce `internal/catalog` or equivalent;
- move restore-plan, GC-plan, snapshot graph, and reachability resolution behind catalog APIs;
- remove direct DB queries from CLI;
- begin formal SQLite-first local catalog preparation.

v1.13 will:

- freeze engine request/result contracts;
- standardize engine error taxonomy;
- remove CLI dependencies from the engine;
- enforce dependency direction;
- validate no-data-loss, deterministic restore, GC safety, and verify integrity at the engine level;
- make SQLite-first local portability real if v1.12 compatibility work is complete.

v2.x will have a reliable base for coldkeepd, local operation queue, CLI as thin client, local API,
local UI, automation/scheduling, and portable SQLite repositories.

## Success Criteria

v1.11.0 is successful when:

- `internal/engine` exists and `DefaultEngine` wraps selected existing operations;
- selected CLI commands route through the engine;
- no user-visible behavior has changed;
- JSON output is unchanged;
- exit codes are unchanged;
- repository, storage, and schema are unchanged;
- PostgreSQL compatibility is preserved;
- no catalog abstraction has been introduced accidentally;
- dependency direction is enforced;
- release documentation includes parity evidence for each promoted command.
