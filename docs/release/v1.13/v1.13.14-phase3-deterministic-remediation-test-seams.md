## 3. Verification observation

The private verification observer records only successful boundaries named
`physical_hash`, `compressed_hash`, `decompression`, `logical_hash`, and
`block_verification_complete`. Each event identifies `legacy` or `packed` and
the authoritative legacy block row or packed `storage_block` ID. A failed
stage is not reported, while prior successful observations remain available.
The observer is test infrastructure only: it does not implement the Phase 4
ledger, result counters, deduplication, or Engine/maintenance transport.

## 4. GC execution options

`RunGCWithDB` retains its public signature and delegates to a private options
path. Nil options use `fsx.Default()`, no observer, and the existing serial
sealed-then-active execution. The injected filesystem reaches only the
invocation that supplied it. Dispatch events distinguish sealed and active
physical units and fire synchronously immediately before the current unit
begins, permitting channel-based tests without sleeps. Workers, reclaimed-byte
accounting, candidate ordering, transactions, and partial-result behavior are
unchanged.

## 5. Restore, Doctor, and truncate seams

The former `TestRestoreBeforeChunkReadHook` and
`TestRestoreFailBeforeRenameHook` globals were removed. A narrowly documented
module-internal test helper configures immutable hooks on one supplied
`StorageContext`; Engine restore fixtures carry that context without adding an
Engine API. Concurrent context A/context B proof shows a blocking/failing hook
cannot affect an unhooked restore.

The four private Doctor callback families now accept the operation context.
Injected tests can observe or wait on that exact context, while nil callbacks
retain the prior production fallbacks and ordering. This does not implement
the caller-context remediation owned by Phase 5.

`faultfs.File.Truncate` now consults `OpTruncate` before delegating. Configured
faults return deterministically without treating the underlying truncate as
successful; an unconfigured operation delegates exactly as before. Rollback
and quarantine behavior remain unchanged for Phase 7.

## 6. Existing infrastructure sufficiency

Source inspection confirmed existing injected `ContainerWriter` behavior and
Store interleaving hooks are sufficient for Phase 6 finalization tests and,
with `OpTruncate`, Phase 7 rollback/quarantine tests. No Store hook or duplicate
quarantine layer was added. The Phase 2 test-only SQL-driver design remains
sufficient for Remove failures, so no production Remove hook was added.
