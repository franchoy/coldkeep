# Coldkeep v1.13.8 Restore / Remove Contract-Split Design

**Release:** `v1.13.8 — Restore / Remove Contract Split and Stored-Path Boundary`
**Phase:** Phase 4
**Status:** Complete
**Branch:** `release/v1.13.8`

## Purpose

Turn the accepted Phase 1 restore inventory, Phase 2 remove inventory, and
Phase 3 path taxonomy into one exact implementation contract for Phases 5
through 8.

## Executive decision

`Engine.Restore` and `Engine.Remove` become truthful, mode-free by-ID methods.
Stored-path restore receives its own dedicated single-operation engine method.
Stored-path removal receives one dedicated batch-capable engine method that can
serve both single-target and multi-target CLI flows.

Internal engine requests and results may become source-incompatible in
`v1.13.8` when required to make them truthful. User-facing CLI syntax, human
output, JSON output, ordering, exit behavior, retention policy, GC ownership,
backend behavior, and on-disk formats remain unchanged.

## Target engine interface

Target engine interface:

```go
type Engine interface {
	Restore(
		ctx context.Context,
		req RestoreRequest,
	) (RestoreResult, error)

	RestoreStoredPath(
		ctx context.Context,
		req RestoreStoredPathRequest,
	) (RestoreStoredPathResult, error)

	Remove(
		ctx context.Context,
		req RemoveRequest,
	) (RemoveResult, error)

	RemoveStoredPaths(
		ctx context.Context,
		req RemoveStoredPathsRequest,
	) (RemoveStoredPathsResult, error)
}
```

Semantic split:

- `Restore` means logical file IDs only
- `RestoreStoredPath` means exactly one persisted `physical_file.path`
- `Remove` means logical file IDs only
- `RemoveStoredPaths` means one or more persisted `physical_file.path` mappings
- no active restore/remove request requires an addressing-mode discriminator
  after the split

## By-ID restore contract

By-ID restore remains batch-capable and keeps current direct-engine dry-run and
fail-fast semantics.

### RestoreRequest

Final request:

```go
type RestoreRequest struct {
	FileIDs         []int64
	DestinationRoot string
	Overwrite       bool
	DryRun          bool
	FailFast        bool
}
```

Field semantics:

- `FileIDs`
  - logical-file IDs only
  - one or more values
  - request order remains significant
  - direct engine callers may submit multiple IDs
  - normal CLI routing may continue one-item calls to preserve current
    orchestration
- `DestinationRoot`
  - replaces the semantically vague `OutputDir`
  - required and non-blank
  - restore destination root only
  - not a stored path, repository root, or payload path
- `Overwrite`
  - preserves current by-ID overwrite behavior
- `DryRun`
  - preserves current by-ID dry-run behavior
  - does not imply proof that live execution will succeed
- `FailFast`
  - preserves direct engine multi-item behavior
  - normal CLI batch fail-fast remains CLI-authoritative while CLI still
    invokes one item at a time

Current restore request field disposition:

| Current field | Disposition | Final meaning |
|---|---|---|
| `Mode` | removed | method selection now expresses addressing |
| `FileIDs` | retained | by-ID targets |
| `OutputDir` | renamed | `DestinationRoot` |
| `StoredPath` | moved to dedicated request | `RestoreStoredPathRequest.StoredPath` |
| `DestinationMode` | moved to dedicated request | stored-path destination behavior |
| `Destination` | split and moved | `DestinationRoot` or `DestinationPath` by mode |
| `Strict` | renamed and moved | `StrictMetadata` on stored-path restore |
| `NoMetadata` | moved | stored-path restore only |
| `Overwrite` | retained | by-ID overwrite |
| `DryRun` | retained | by-ID dry-run |
| `FailFast` | retained | by-ID direct-engine fail-fast |
| `InputPath` | removed | CLI transport only |
| `Workers` | removed | non-goal in `v1.13.8` |
| `Limit` | removed | non-goal in `v1.13.8` |

### RestoreResult

Final result:

```go
type RestoreResult struct {
	DryRun        bool
	ExecutionMode ExecutionMode
	Items         []RestoreItemResult
	Summary       BatchSummary
	Warnings      []OperationWarning
}
```

Semantics:

- `DryRun` preserves current by-ID simulation reporting
- `ExecutionMode` continues to use the existing shared type
- `Summary` and `Warnings` continue to use existing shared types
- result remains batch-capable for direct engine callers

### RestoreItemResult

Final item:

```go
type RestoreItemResult struct {
	FileID          int64
	DestinationPath string
	RestoredHash    string
	Status          BatchItemStatus
	Error           string
}
```

Field disposition:

| Current field | Disposition | Final meaning |
|---|---|---|
| `FileID` | retained | restored logical file ID |
| `StoredPath` | removed | stored-path restore gets a dedicated result |
| `OutputPath` | renamed | `DestinationPath` |
| `RestoredHash` | retained | successful restore hash |
| `Status` | retained | shared item status |
| `Error` | retained | per-item failure text |

Naming decision:

- `DestinationPath` is the resolved exact output object
- it replaces ambiguous internal result name `OutputPath`
- CLI adapters may continue emitting the existing `output_path` JSON field for
  compatibility

## Stored-path restore contract

Stored-path restore becomes a dedicated single-operation engine contract. It
does not gain batch semantics, dry-run, or fail-fast.

### RestoreStoredPathRequest

Final request:

```go
type RestoreStoredPathRequest struct {
	StoredPath      string
	DestinationMode RestoreDestinationMode
	DestinationRoot string
	DestinationPath string
	Overwrite       bool
	StrictMetadata  bool
	NoMetadata      bool
}
```

Field semantics:

- `StoredPath`
  - means only `physical_file.path`
  - required
  - trimmed at the engine boundary
  - validated as non-blank
  - passed to storage for exact catalog mapping lookup
  - not canonicalized against the caller's current filesystem by the engine
- `DestinationMode`
  - retains existing typed destination modes
  - remains distinct from addressing semantics
- `DestinationRoot`
  - used only for prefix mode
  - establishes the allowed restore boundary
- `DestinationPath`
  - used only for override mode
  - exact requested output object
- `StrictMetadata`
  - replaces vague `Strict`
- `NoMetadata`
  - retains existing meaning

Fields deliberately absent:

- `DryRun`
- `FailFast`
- `InputFile`
- `Workers`
- `Limit`
- `FileIDs`

### Destination representation

Destination field rules:

- original mode:
  - `DestinationRoot == ""`
  - `DestinationPath == ""`
  - final output remains derived under current original-mode behavior
- prefix mode:
  - `DestinationRoot != ""`
  - `DestinationPath == ""`
- override mode:
  - `DestinationRoot == ""`
  - `DestinationPath != ""`

This split is naming and ownership clarification only. The current CLI
`--destination` flag remains unchanged and is translated at the compatibility
boundary.

### RestoreStoredPathResult

Final result:

```go
type RestoreStoredPathResult struct {
	StoredPath      string
	FileID          int64
	DestinationMode RestoreDestinationMode
	DestinationPath string
	RestoredHash    string
}
```

Semantics:

- `StoredPath` is the normalized persisted mapping target
- `FileID` identifies the owning logical file
- `DestinationMode` records the executed destination interpretation
- `DestinationPath` is the resolved exact output
- `RestoredHash` preserves the current successful restore hash

Deliberately absent:

- batch summary
- item status
- dry-run
- fail-fast
- performance spans
- payload locations

Execution failures remain top-level errors rather than failed item results.
That preserves current single stored-path CLI semantics.

## By-ID remove contract

By-ID remove remains the logical-file deletion operation. It does not mean
unlinking one current stored mapping.

### RemoveRequest

Final request:

```go
type RemoveRequest struct {
	FileIDs  []int64
	DryRun   bool
	FailFast bool
}
```

Field disposition:

| Current field | Disposition | Final meaning |
|---|---|---|
| `Mode` | removed | method selection now expresses addressing |
| `FileIDs` | retained | by-ID logical-file deletion targets |
| `StoredPath` | removed from by-ID request | moved to dedicated stored-path remove request |
| `StoredPaths` | removed from by-ID request | moved to dedicated stored-path remove request |
| `DryRun` | retained | by-ID dry-run |
| `FailFast` | retained | by-ID direct-engine fail-fast |
| `InputPath` | removed | CLI transport only |

### RemoveResult

Final result:

```go
type RemoveResult struct {
	DryRun        bool
	ExecutionMode ExecutionMode
	Items         []RemoveItemResult
	Summary       BatchSummary
	Warnings      []OperationWarning
}
```

Semantics:

- remains batch-capable
- continues using existing shared `ExecutionMode`, `BatchSummary`, and
  `OperationWarning`
- preserves current direct-engine dry-run and fail-fast shape

### RemoveItemResult

Final item:

```go
type RemoveItemResult struct {
	FileID                   int64
	LogicalFileRemoved       bool
	RemovedChunkAssociations int
	Status                   BatchItemStatus
	Error                    string
	InvariantCode            string
	RecommendedAction        string
}
```

Field disposition:

| Current field | Disposition | Final meaning |
|---|---|---|
| `FileID` | retained | removed logical file ID |
| `StoredPath` | removed | stored-path remove gets a dedicated item type |
| `RemovedMappings` | renamed | `RemovedChunkAssociations` |
| `RemainingRefCount` | removed from by-ID item | dedicated stored-path remove meaning only |
| `Removed` | renamed | `LogicalFileRemoved` |
| `Status` | retained | shared item status |
| `Error` | retained | per-item failure text |
| `InvariantCode` | retained | shared invariant metadata |
| `RecommendedAction` | retained | shared invariant guidance |

Naming corrections:

- `LogicalFileRemoved` means the logical file row and its active content
  associations were deleted
- `RemovedChunkAssociations` means removed `file_chunk` associations, matching
  the current value derived from chunk IDs
- it does not claim to count deleted `physical_file` rows

CLI compatibility note:

- human output may temporarily preserve existing wording in `v1.13.8`
- internal engine field names must still become honest

## Stored-path remove contract

Stored-path unlinking becomes one dedicated batch-capable engine method that
can serve both one-target and many-target callers.

### RemoveStoredPathsRequest

Final request:

```go
type RemoveStoredPathsRequest struct {
	StoredPaths []string
	DryRun      bool
	FailFast    bool
}
```

Why one plural method:

- it serves one `--stored-path` target
- it serves many `--stored-paths` targets
- it supports future API callers submitting one or more mapping targets
- no separate `RemoveStoredPath` engine method is needed

Batch-input ownership:

- `InputPath` and `InputFile` do not appear in engine requests
- CLI owns opening `--input`, reading lines, preserving raw order, and file I/O
  errors
- engine receives resulting stored-path target strings only

Target preparation ownership:

- engine owns domain-level preparation after request acceptance
- trim surrounding whitespace
- reject blank targets as item failures
- preserve first-occurrence order
- mark later exact duplicates as skipped
- preserve original raw target for diagnostics
- execute valid unique targets sequentially
- duplicate comparison remains exact after trimming
- no filesystem canonicalization is introduced

### RemoveStoredPathsResult

Final result:

```go
type RemoveStoredPathsResult struct {
	DryRun        bool
	ExecutionMode ExecutionMode
	Items         []RemoveStoredPathItemResult
	Summary       BatchSummary
}
```

Top-level errors remain reserved for:

- cancelled context before execution
- structurally invalid request such as zero targets
- unavailable engine dependencies
- unrecoverable setup failure

Per-item errors remain the location for:

- blank target
- duplicate target as skipped
- never-stored path
- snapshot-retained refusal
- ref-count mismatch
- concurrent removal
- database execution failure

### RemoveStoredPathItemResult

Final item:

```go
type RemoveStoredPathItemResult struct {
	RawTarget         string
	StoredPath        string
	LogicalFileID     int64
	RemainingRefCount int64
	MappingRemoved    bool
	Status            BatchItemStatus
	Error             string
	InvariantCode     string
	RecommendedAction string
}
```

Field semantics:

- `RawTarget`
  - original caller-provided text before trimming
- `StoredPath`
  - trimmed and normalized stored physical path used for catalog lookup
- `LogicalFileID`
  - owning logical file
- `RemainingRefCount`
  - number of current physical mappings remaining after live success
  - for dry-run, include only when current behavior can determine it honestly;
    otherwise preserve current zero/default posture and document it
- `MappingRemoved`
  - means exactly one `physical_file` mapping was deleted
  - never means the logical file was deleted

## Single stored-path CLI projection

The existing single stored-path remove command continues to produce its current
non-batch output.

Required adapter shape:

```text
CLI validates single-mode flag combinations
    ↓
Engine.RemoveStoredPaths with one target
    ↓
inspect the single item
```

Success must project into the existing command-level success shape:

```json
{
  "status": "ok",
  "command": "remove",
  "data": {
    "stored_path": "...",
    "logical_file_id": 1,
    "remaining_ref_count": 0,
    "removed": true
  }
}
```

Compatibility rule:

- JSON field `removed` remains at the CLI boundary
- its internal source becomes `MappingRemoved`

Failure rule:

- a single failed item must translate back into the same command-level error
  behavior currently produced by direct storage execution
- no batch envelope is exposed for `--stored-path`

## Batch stored-path CLI projection

The existing `--stored-paths` command continues using the generic batch
envelope.

CLI responsibilities after the split:

1. load positional/input-file text
2. pass ordered raw targets to `Engine.RemoveStoredPaths`
3. translate engine items into the existing generic batch report
4. preserve current human and JSON field names
5. preserve current status, summary, and exit behavior
6. preserve performance spans as CLI-layer metadata

The CLI must no longer perform domain trim/duplicate preparation after Phase
8. Input-file reading remains CLI-owned.

## Validation ownership

CLI retains syntax and command-shape validation for:

- unknown flags
- mutually exclusive CLI modes
- illegal positional combinations
- `--input` availability by mode
- single stored-path prohibition of dry-run/fail-fast
- textual parsing of destination mode
- output-mode parsing
- early usage errors required for compatibility

Engine validates every typed request independently:

- required IDs or targets
- positive file IDs
- required destination root
- stored path non-blank
- destination-mode field consistency
- strict/no-metadata exclusivity
- request-level target presence
- context cancellation

Storage/domain retains:

- exact catalog lookup
- traversal and destination safety
- symlink safety
- overwrite enforcement
- metadata application
- ref-count transitions
- snapshot-retention checks
- transaction invariants
- payload reconstruction
- temporary pin management

Defensive duplication rule:

- CLI and engine may both validate the same rule when necessary to preserve CLI
  usage errors and direct-engine safety
- duplicated validation must share semantics even if implemented separately

## Normalization ownership

Stored paths:

- engine performs surrounding-whitespace trimming for dedicated stored-path
  requests
- storage may normalize defensively again using the established stored-path
  helper
- engine must not resolve symlinks, convert to current-machine absolute paths,
  or apply filesystem case canonicalization

Destination values:

- engine validates field presence and mode consistency
- storage/path-safety layers perform filesystem normalization and safe
  resolution

File IDs:

- engine validates positive numeric IDs
- CLI raw-text parsing remains CLI-owned

## Error taxonomy

By-ID operations retain:

- top-level request validation errors
- per-item execution errors after request acceptance
- invariant metadata on affected items

Stored-path restore uses:

- top-level validation errors for malformed typed request
- top-level execution error for stored-path lookup, destination, payload, or
  filesystem failure
- successful result only when restore completes

Stored-path removal uses:

- top-level structural request errors
- per-item target errors
- invariant code and recommended action on retained/ref-count failures

Unsupported classification decision:

- after the split, stored-path addressing modes must no longer be represented
  as unsupported modes of by-ID methods
- dedicated methods are active in the design
- `ErrNotImplemented` remains for genuinely deferred engine operations only

## Dry-run policy

By-ID restore:

- preserves current dry-run behavior

Stored-path restore:

- no dry-run field
- no new dry-run capability in `v1.13.8`

By-ID remove:

- preserves current dry-run behavior, including live-parity limits

Stored-path removal:

- preserves current batch dry-run behavior
- does not gain snapshot-retention or full invariant parity beyond current
  observable behavior

Required documentation truth:

- dry-run means plan using the current non-mutating checks
- dry-run does not mean proof that all live transaction preconditions will pass

## Fail-fast policy

By-ID restore/remove:

- direct engine multi-item requests retain fail-fast
- normal CLI may continue one-item engine calls and own CLI batch fail-fast

Stored-path restore:

- no fail-fast field because it is one operation

Stored-path removal:

- engine owns batch fail-fast after Phase 7
- CLI translates the result but does not reimplement execution stopping
- fail-fast stops after the first executable target failure
- it does not stop because an earlier prepared target was blank/invalid or
  duplicate/skipped
- remaining unexecuted valid targets must continue to be represented according
  to the current batch-summary behavior

All execution remains sequential. No new concurrency or parallelism is
introduced.

## Context policy

All new engine methods accept caller `context.Context`.

Required behavior:

- reject already-cancelled context before setup
- pass context into engine-level storage calls where the existing storage API
  supports it
- do not broaden Phases 6 and 7 into a full storage context-propagation
  refactor

Current technical debt accepted in `v1.13.8`:

- existing storage functions that internally use `context.Background()` may
  remain unchanged
- complete transaction-context propagation remains separate technical debt
  unless a narrow wrapper can preserve behavior safely

## Restore mutation honesty

Restore contract truth:

- restore does not mutate logical-file identity, physical mappings, snapshots,
  or ref-count ownership
- restore may temporarily mutate `chunk.pin_count` while protecting payloads
  during execution
- restore must restore pin state correctly on success or failure

The split must not describe restore as completely catalog-read-only.

## Remove, reachability, and GC ownership

Contract truth:

- `Remove` and `RemoveStoredPaths` change catalog reachability state
- neither method directly deletes container files, storage blocks, or payload
  bytes
- GC remains the sole physical payload-reclamation owner

Stored-path unlink preserves:

- logical file
- file-chunk graph
- chunk live-reference counts

By-ID remove may delete:

- current physical mappings
- file-chunk associations
- logical file

and may decrement chunk live-reference counts.

## Snapshot-retention policy

`v1.13.8` preserves current strict refusal for:

- by-ID remove of a snapshot-retained logical file
- stored-path unlink of a snapshot-retained logical file

Invariant code remains:

- `SNAPSHOT_RETAINED_DELETE_BLOCKED`

The contract split must not reinterpret stored-path unlink as permissible
merely because snapshot data would remain technically restorable.

## Backend and dependency requirements

Restore methods require:

- catalog DB
- effective container/payload directory
- existing storage readers and path-safety behavior

Remove methods require:

- catalog DB
- no payload writer
- no direct container-directory mutation

Engine configuration may still contain `ContainerDir` globally. Remove methods
must not begin using it merely because it is available.

Backend parity rule:

- SQLite and PostgreSQL must preserve identical operation meaning
- backend differences are limited to SQL adaptation, locking behavior, and
  transaction implementation details

## Source-compatibility policy

Phase 4 decision:

- `v1.13.8` may make source-incompatible changes to internal engine
  request/result types when required to make them truthful
- every in-repository caller and test must migrate in the same release
- no user-facing CLI compatibility break is permitted

Migration rule:

- do not retain misleading fields solely for internal source compatibility
- do not add deprecated aliases unless they materially reduce migration risk
  without preserving ambiguity

## Addressing-mode enum removal

These addressing-mode enums must be removed when no active code requires them:

- `RestoreMode`
- `RestoreModeFileIDs`
- `RestoreModeStoredPath`
- `RemoveMode`
- `RemoveModeFileIDs`
- `RemoveModeStoredPath`
- `RemoveModeStoredPaths`

Reason:

- method selection now expresses addressing semantics
- a by-ID method cannot receive a stored-path mode
- dedicated stored-path methods are active
- unsupported addressing combinations become unrepresentable

`RestoreDestinationMode` remains because it describes destination behavior, not
object addressing.

If temporary staging requires old enums to survive one intermediate commit,
they must be gone by completion of Phase 8.

## Shared and dedicated types

Reuse existing shared types where their meaning is genuinely common:

- `ExecutionMode`
- `BatchItemStatus`
- `BatchSummary`
- `OperationWarning`
- invariant code and recommended-action representation

Do not force reuse where entity meaning differs.

Keep dedicated result types:

- `RestoreItemResult`
- `RestoreStoredPathResult`
- `RemoveItemResult`
- `RemoveStoredPathItemResult`

Do not create one universal restore/remove item containing every possible
field.

## Implementation sequence

The implementation order is fixed:

### Phase 5

- narrow active by-ID contracts only
- remove addressing modes
- remove stored-path-only fields
- remove input/provisional fields
- rename honest destination/result fields
- correct by-ID remove result names
- migrate engine implementation and tests
- preserve existing CLI behavior
- stored-path CLI remains direct

### Phase 6

- add `Engine.RestoreStoredPath`
- add `RestoreStoredPathRequest`
- add `RestoreStoredPathResult`
- test engine behavior directly
- stored-path restore CLI remains direct

### Phase 7

- add `Engine.RemoveStoredPaths`
- add `RemoveStoredPathsRequest`
- add `RemoveStoredPathsResult`
- add `RemoveStoredPathItemResult`
- move target trim/invalid/duplicate/fail-fast orchestration into the engine
- stored-path remove CLI remains direct

### Phase 8

- route CLI stored-path restore and remove through the new engine methods
- remove direct CLI/storage execution seams
- preserve output and exit behavior
