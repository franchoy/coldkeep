## Purpose

This document reviews the current ownership, dependency direction, result
ownership, renderer ownership, JSON ownership, and taxonomy boundaries for the
`snapshot show` read-side surface.

The goal is to decide whether the current mixed `snapshot show` ownership model
is acceptable for `v1.13.x` and what, if anything, should be deferred to later
releases.

This phase is documentation-only and does not change runtime behavior.

## Current `snapshot show` flow

Observed current production flow:

`runSnapshotShowCommand` -> CLI validation -> `parseSnapshotQuery` ->
`getSnapshotPhase` -> `listSnapshotFilesPhase` -> `snapshotStatsPhase` ->
CLI JSON assembly or renderer human output

Current path details:

- CLI entrypoint is `runSnapshotShowCommand` in `cmd/coldkeep/main.go`
- CLI parsing and validation stay in `cmd/coldkeep` through:
  - `ensureAllowedFlags`
  - positional arity checks
  - `validateNonNegativeIntegerFlag`
  - `snapshotID` trim and empty check
  - `parseSnapshotQuery`
- metadata path uses `getSnapshotPhase`
  - `getSnapshotPhase` constructs an engine and calls `eng.SnapshotShow`
  - the helper then reprojects `engine.SnapshotShowResult.Snapshot` back into
    `snapshot.Snapshot`
- file listing path uses `listSnapshotFilesPhase`
  - `listSnapshotFilesPhase` is a direct alias to `snapshot.ListSnapshotFiles`
- stats/count path uses `snapshotStatsPhase`
  - `snapshotStatsPhase` constructs an engine and calls `eng.SnapshotStats`
  - the helper then reprojects `engine.SnapshotStatsResult` back into
    `snapshot.SnapshotStats`
- engine seams are therefore active for metadata and stats helpers
- direct snapshot package seam remains active for file listing
- human renderer path uses `clirender.RenderSnapshotShowHuman`
- JSON success output path is CLI-owned and assembled in `runSnapshotShowCommand`
- JSON error output path remains CLI-owned through propagated command errors
- taxonomy-boundary behavior currently centers on:
  - empty snapshot ID remaining a usage error
  - missing snapshot remaining the current domain/general error path
  - invalid query flags remaining usage errors
  - taxonomy helper names not surfacing in public JSON

## Current flow diagram

```text
runSnapshotShowCommand
  -> CLI validation
  -> parseSnapshotQuery
  -> getSnapshotPhase
       -> engine SnapshotShow
       -> metadata reprojection to snapshot.Snapshot
  -> listSnapshotFilesPhase
       -> snapshot.ListSnapshotFiles
  -> snapshotStatsPhase
       -> engine SnapshotStats
       -> stats reprojection to snapshot.SnapshotStats
  -> CLI JSON assembly or renderer human output
```

## Public behavior baseline

Current public behavior that must not drift:

- required snapshot ID behavior:
  - exactly one snapshot ID positional is required
- empty snapshot ID behavior:
  - trimmed empty snapshot ID remains a usage error
- missing snapshot behavior:
  - missing valid snapshot remains the current domain/general error path
- empty snapshot success behavior:
  - success remains valid even when the snapshot has zero matched files
  - human output can render `(no files)`
  - JSON success output can report zero matched files
- query/filter behavior:
  - query flags remain CLI-parsed through `parseSnapshotQuery`
  - listing remains snapshot-package-applied
- `matched_file_count`:
  - remains based on the number of filtered files returned by
    `listSnapshotFilesPhase`
- `total_snapshot_file_count`:
  - remains sourced from the stats path
- file list behavior:
  - JSON uses `snapshotFilesJSON`
  - human output uses `RenderSnapshotShowHuman`
- human output behavior:
  - remains renderer-owned
- JSON output envelope:
  - remains CLI-owned with `status`, `command`, and `data`
- JSON error envelope:
  - remains unchanged
- exit-code behavior:
  - remains unchanged

## Ownership finding

The current `snapshot show` ownership model is acceptable for `v1.13.x` as a
documented mixed transitional seam: metadata and stats/count paths are
engine-backed, file listing remains snapshot-package-backed, and public JSON
assembly remains CLI-owned.

Observed findings supporting that decision:

- metadata is engine-backed through `getSnapshotPhase`
- stats/counts are engine-backed through `snapshotStatsPhase`
- file listing remains direct snapshot-package logic
- CLI owns query parsing and final result assembly
- CLI owns JSON success envelopes
- renderer owns human output
- CLI owns JSON error envelopes and error propagation
- taxonomy helper names are not exposed publicly
- backend behavior remains protected by existing read-side and snapshot tests

This is a mixed-but-stable seam rather than a broken seam. The repo evidence
shows active production use, preserved counts and output behavior, and no
current correctness or contract bug that requires consolidation in `v1.13.4`.

## Why not consolidate now

`v1.13.4` should not immediately consolidate all `snapshot show` logic behind a
single new engine-owned result type.

Reasons:

- consolidating now risks `matched_file_count` drift
- it also risks `total_snapshot_file_count` drift
- it risks JSON envelope drift
- it risks query/filter drift
- it risks missing-snapshot behavior drift
- it risks duplicating snapshot result shapes
- it would be a broad routing/result migration during a review release
- `v1.13.4` is an ownership-review release, not a broad migration release

## Gaps and deferred work

| Gap | Risk | Recommended handling |
| --- | ---: | --- |
| Mixed engine/snapshot package ownership | Medium | Document as transitional and defer broad consolidation |
| CLI-owned query parsing and result assembly | Medium | Review cross-surface JSON ownership in Phase 6 |
| File listing not engine-owned | Medium | Defer engine result-ownership decision |
| Stats/count reprojection into snapshot-owned shape | Medium | Defer broader ownership consolidation |
| Backend parity evidence mostly indirect at CLI level | Low/Medium | Review in Phase 8 |

These are ownership and guardrail gaps, not current correctness blockers.

## Decision for v1.13.4

For `v1.13.4`, keep the current `snapshot show` ownership model unchanged.

Treat metadata/stats engine seams plus snapshot-package file listing plus CLI
JSON assembly as a documented mixed transitional seam.

Preserve counts, query behavior, output, and error behavior rather than
introducing a new consolidated engine-owned result in this release.
