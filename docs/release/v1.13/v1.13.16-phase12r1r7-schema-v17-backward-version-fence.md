# v1.13.16 Phase 12R1R7 Schema-v17 Backward-Version Fence

**Mode:** BUILD
**Finding:** CK-V11316-015
**Authority:** Local-only; push and hosted execution prohibited

## Decision

Historical schema-16 binaries at
`2212ddd2981f3535fb71f38232bda6c1b7b35e97` silently accept a
`schema_version.version` value above 16. This becomes release-blocking because
CK-V11316-015 introduces schema-17 repair-attempt and retired-occupancy
semantics that those binaries do not understand. It is a completion
requirement of CK-V11316-015, not a new finding.

The repository-side fence retains the `schema_version` table but changes its
committed schema-17 representation to exactly one integer-primary-key column,
`catalog_version`, with exactly one row containing `17`. The legacy `version`
column is absent. Historical binaries therefore find the table and fail on
their mandatory old-column query before schema application, recovery, session
construction, or command execution. Downgrade is unsupported.

```text
PRE_V17_BINARY_NEWER_SCHEMA_BEHAVIOR: SILENT_ACCEPT
FINDING_BOUNDARY: CK015_COMPATIBILITY_REQUIREMENT
NEW_FINDING: NOT_REQUIRED
SCHEMA_V17_OLDER_BINARY_ACCESS: TECHNICALLY_REJECTED
SCHEMA_V17_DOWNGRADE: UNSUPPORTED
SCHEMA_V17_METADATA_CARDINALITY: EXACTLY_ONE_ROW
SCHEMA_V17_METADATA_VALUE: 17
ZERO_SEMANTIC_REPOSITORY_MUTATION: REQUIRED
```

## Transaction and metadata contract

The v16-to-v17 migration begins a backend transaction before metadata
inspection, derives the legacy current version using the historical backend
rule, validates it, completes every required migration, renames `version` to
`catalog_version`, deletes all version rows, inserts only `17`, validates the
final representation, and commits. Any failure restores the complete original
legacy column and rows.

SQLite accepts one or more distinct integer legacy rows in the range 1..17
and derives the current version with `MAX(version)`. PostgreSQL accepts exactly
one integer legacy row in that range; multiple PostgreSQL rows are malformed
because its canonical primary-key update sequence is singleton. A normalized
v16 repository has exactly one `version=16` row on either backend. The local,
unpushed legacy-column `version=17` candidate is accepted only for
transactional normalization to the same fenced singleton.

Fresh bootstrap produces the fenced singleton. Reopen rejects zero or
multiple rows, both or neither recognized column, unexpected metadata columns,
an invalid column type or key, a fenced value below 17, and either
representation above 17.
