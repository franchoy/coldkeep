# v1.13.0 Engine Request/Result Contract Inventory

## Purpose and Classification Rules

This document inventories the current engine contract types after v1.12.3. It is documentation
only. It does not change routing, behavior, JSON, or implementation. The key question is not
whether a type exists or compiles, but whether it looks safe to freeze as a future engine contract
for v2 daemon/API use.

Classification rules used here:

- Contract classification:
  - `request`: operation input type
  - `result`: operation output type
  - `candidate`: shared support type, enum, per-item batch type, or operation contract that is not
    a clearly frozen active request/result
- Current status:
  - `stable`: active, engine-shaped, backend-neutral, and clear enough to freeze without obvious
    contract risk
  - `provisional`: active or currently relied upon, but still exposing domain leakage, thin error
    semantics, partial validation ownership, or CLI-shaped assumptions
  - `candidate`: defined as a future-facing or not-yet-frozen contract and not ready to freeze
  - `deferred`: tied mainly to deferred engine behavior and not yet meaningful as a stable contract
  - `unclear`: repo evidence is insufficient to classify confidently
- Shape:
  - `CLI-shaped`: mirrors current command syntax, batch file inputs, dry-run toggles, fail-fast
    toggles, worker knobs, destination flags, or report formatting assumptions
  - `engine-shaped`: expresses operation intent or outcomes independent of current CLI syntax
- Backend-neutral:
  - `yes`: no DB handle, SQL dialect, or storage implementation type leakage
  - `partial`: structurally neutral, but semantically still tied to current domain/service behavior
  - `no`: wraps domain/service result types or otherwise leaks current implementation shape

## Findings

### Highest-Risk Freeze Blockers

1. Active read-side contracts in `types.go` still leak `internal/observability` types directly.
   `StatsResult` and `InspectResult` are the clearest freeze blockers because they are wrapper-only
   result shells around domain/service result types.
2. `VerifyResult` is too thin to freeze. It communicates success only by returning `nil` error and
   carries no stable result payload.
3. `SnapshotQuery` is not ready to freeze as a shared filter contract because the current engine
   seam narrows CLI semantics. `engineQueryToSnapshotQuery` and `snapshotQueryOrNil` preserve only a
   subset of the richer CLI query model, and Phase 1 already showed `snapshot diff` loses repeatable
   `--path` / `--prefix` detail in translation.
4. `RestoreRequest`, `RemoveRequest`, `SnapshotRestoreRequest`, and `RepairRequest` are too
   CLI-shaped for daemon/API freeze in their current form. `InputPath`, `DryRun`, `FailFast`,
   `Workers`, and destination-mode fields mirror current CLI mechanics rather than clean engine
   intent.
5. `SnapshotListResult` carries `TreeMode` and `TreeLines`, which makes the current shape too close
   to a rendered CLI view model for confident engine freeze.

### Helper-Level Evidence That Affects Contract Interpretation

- `validateInspectRequest` and `validateVerifyRequest` show that some correctness validation has
  moved into engine helpers, but the request/result types themselves do not fully communicate those
  rules.
- `verifyLevelFromString` confirms that `VerifyRequest.Level` is still string-and-flag oriented
  instead of enum-and-intent oriented.
- `validateRemoveRequest` and `validateRestoreRequest` show that active engine support is narrower
  than the full type surfaces imply; non-file-ID variants remain constrained even though the request
  contracts look broader.
- `engineQueryToSnapshotQuery` and `snapshotQueryOrNil` show semantic narrowing between engine
  contracts and snapshot domain queries, which is a direct contract-freeze risk for snapshot
  filtering.

### Bottom Line

The current engine contract surface is useful for routing and inventory work, but it is not ready
to be frozen wholesale as a v2 engine contract. The biggest blockers are:

- direct domain/service type leakage in active read contracts
- empty or error-only success semantics
- partial validation ownership hidden in helpers
- CLI-shaped batch, dry-run, and destination controls
- snapshot query/filter semantics that are broader in the CLI than in the current engine contract

v1.13.x should treat this inventory as a stabilization baseline, not as a freeze approval.
