# v1.13.0 Correctness Invariant Ownership Map

## Purpose and Mapping Rules

This document records the v1.13.0 correctness invariant ownership baseline. It is
documentation/inventory only. It does not change Go code, tests, schema, migrations, CLI behavior,
JSON output, exit codes, storage format, repository format, default backend behavior, engine
routing, catalog implementation, CI behavior, or scripts.

Mapping rules used here:

- Runtime ownership matters more than test existence alone.
- CLI validation does not count as daemon/API protection unless the same safeguard also exists
  below CLI.
- Catalog surface existence does not count as catalog ownership when logic still lives in domain
  packages.
- Mixed ownership is a real risk signal, not a transitional success label.
- Test coverage helps prove an invariant, but tests do not become the runtime owner by themselves.

### Invariants Currently Protected Mostly or Only by CLI

- `CK-1130-INV-007` snapshot delete must not break retained data
- `CK-1130-INV-010` repair must not legitimize corrupt mappings
- `CK-1130-INV-014` CLI JSON output must be deterministic and machine-safe

These are the clearest examples where a future daemon/API caller would not inherit the current CLI
protection story automatically.

### Invariants with Acceptable Lower-Layer or Runtime Protection Today

- `CK-1130-INV-004` GC cannot delete reachable data has a real active engine path plus explicit
  engine tests, even though catalog-plan ownership is still deferred.
- `CK-1130-INV-017` dependency direction has the cleanest protection story because runtime layering
  is reinforced by dedicated dependency tests and already-clean back-edge rules.

### Where Catalog Tests Help But Do Not Prove Runtime Ownership

- `internal/catalog/backend_contract_test.go` gives strong evidence for implemented lookup parity
  and explicit deferred-method behavior.
- That does not prove runtime ownership for restore planning, GC planning, snapshot graph, or
  placement, because those boundaries still return `ErrNotImplemented` or remain bypassed by domain
  packages and CLI paths.

### Where Backend Parity Risk Materially Affects the Invariant

- GC behavior is backend-sensitive because SQLite live GC is explicitly refused.
- Packed/legacy alignment and verify coverage remain backend-sensitive because parity evidence is
  still stronger at lower layers than at the engine/catalog contract level.
- Restore, remove, recovery, and snapshot flows remain parity-sensitive because operational
  evidence is uneven between SQLite-heavy unit coverage and PostgreSQL-heavy end-to-end coverage.

## Bottom Line

Guarantees that still meaningfully hold below CLI today:

- active GC reachability protection on the current engine path
- dependency direction guardrails that prevent the most dangerous architectural back-edges
- explicit failure of deferred catalog methods and unsupported engine modes instead of silent
  pretend-completeness

Guarantees that are only partially protected below CLI today:

- restore destination safety
- restore determinism and fail-closed behavior
- verify fail-closed behavior
- packed/legacy alignment
- catalog/storage reference consistency
- backend compatibility where engine/catalog contracts are still provisional

Guarantees that would be unsafe to assume for a daemon/API caller without more engine/catalog work:

- snapshot delete retention safety as an engine-owned guarantee
- repair correctness as an engine-owned guarantee
- recovery quarantine safety as an engine-owned guarantee
- any claim that CLI-only validation is no longer part of the safety story for partial or deferred
  operations

That is the Phase 8 answer: some core guarantees already survive below CLI, but many correctness
promises still rely on split ownership, direct domain paths, or explicit deferral. v1.13.x must
stabilize those ownership boundaries before v2-style direct engine callers can safely inherit the
full Coldkeep safety model.
