# Coldkeep v1.13.5 Remove Engine Validation and Snapshot-Retention Invariant Boundary Review

**Release:** `v1.13.5 — Release Record Closure and Engine-Level Invariant Ownership`
**Phase:** Phase 3
**Status:** Complete
**Branch:** `release/v1.13.5`

## Purpose

This document reviews the active `Remove` engine-facing path and records where
validation, destructive-operation safety, snapshot-retention blocking,
invariant propagation, unsupported-mode boundaries, and public batch/error
rendering currently live.

This phase performs no ownership migration and no behavior change.

## Reviewed surfaces

- `Engine.Remove`
- `RemoveRequest`
- `RemoveResult`
- `RemoveItemResult`
- `validateRemoveRequest`
- CLI remove routing
- by-ID remove dry-run and live execution
- stored-path and stored-paths remove seams
- snapshot-retention blocking
- invariant metadata propagation
- public CLI batch rendering and exit-code classification
- current test protection

## Current remove flow

The active by-ID remove path currently flows as:

```text
cmd/coldkeep
  -> parse public CLI args and mode
  -> batch-load and validate fileID inputs
  -> removeByIDPhase
  -> Engine.Remove
  -> validateRemoveRequest
  -> removeFileIDs / removeFileID
  -> dryRunRemoveByID or storage.RemoveFileWithDBResult
  -> per-item result shaping
  -> CLI-owned batch text / JSON rendering and exit classification
```

The active engine seam exists only for `RemoveModeFileIDs`.

At the CLI boundary, `runRemoveCommand` decides whether the invocation is:

- by-ID engine-backed remove
- single `--stored-path` direct CLI/storage remove
- `--stored-paths` direct CLI/storage batch remove

At the engine boundary, `DefaultEngine.Remove` validates only the active by-ID
request seam and then processes file IDs sequentially.

At the domain boundary, `internal/storage/remove.go` owns destructive mutation
semantics, snapshot-retention refusal, ref-count consistency, and physical
mapping deletion rules.

The CLI remains the public batch/output boundary: it renders human and JSON
results, projects invariant metadata into batch output, and chooses exit-code
classification for partial or total failures.

## Request and result ownership

- `RemoveRequest` currently includes:
  - `Mode RemoveMode`
  - `FileIDs []int64`
  - `StoredPath string`
  - `StoredPaths []string`
  - `DryRun bool`
  - `FailFast bool`
  - `InputPath string`
- `RemoveResult` is an engine-owned structured result.
- `RemoveItemResult` is an engine-owned structured per-item result with:
  - batch status
  - error string
  - `RemovedMappings`
  - `RemainingRefCount`
  - `Removed`
  - `InvariantCode`
  - `RecommendedAction`

Unlike `Verify`, `Remove` already has a meaningful engine-owned result shape.
That makes the active by-ID seam less transitional than the current verify
boundary.

The current ownership shape is:

- CLI owns command semantics, raw input parsing, stored-path mode selection,
  and public rendering
- engine owns the active by-ID request seam and per-item result shaping
- storage owns destructive-operation semantics and snapshot-retention safety

## CLI validation

CLI-owned validation currently includes:

- command-shape validation:
  - `remove` requires positional IDs unless `--stored-path` or
    `--stored-paths` is selected
  - `--stored-path` and `--stored-paths` are mutually exclusive
  - `--stored-path` rejects positional IDs, `--input`, `--dry-run`, and
    `--fail-fast`
- positional and input-file parsing:
  - by-ID mode uses `batch.LoadRawTargets` and `batch.PrepareTargets`
  - malformed textual file IDs remain CLI-owned validation failures before
    engine routing
  - empty or non-materialized prepared ID sets remain CLI-shaped usage failures
- stored-path parsing:
  - stored-path trim/duplicate handling is CLI-owned in the direct stored-path
    path helpers
- public success and failure rendering:
  - CLI renders batch text and JSON output
  - CLI decides whether failure is reported as usage, general execution, or
    verify-class exit behavior based on public batch item data

These validations are intentionally public-command concerns rather than
engine-request concerns.

## Engine validation

Engine-owned validation currently includes:

- `validateRemoveRequest`
  - accepts only `RemoveModeFileIDs`
  - rejects empty `FileIDs`
  - returns `ErrNotImplemented` for `stored_path` and `stored_paths`
- `removeFileID`
  - rejects non-positive file IDs at the per-item level
  - returns a failed item result rather than a top-level engine error for
    invalid item values
- `DefaultEngine.Remove`
  - validates the active request seam once and then routes into sequential
    item execution

This creates a clear split between:

- top-level request validation:
  - active mode supported
  - non-empty file-ID batch required
- per-item validation:
  - each file ID must be positive

That distinction is visible today in the public behavior: malformed textual
IDs fail in CLI parsing, unsupported modes fail at the engine request
boundary, and typed but invalid item IDs fail as structured item-level
results.

## Domain package validation and destructive-operation invariants

Below engine, `internal/storage/remove.go` owns the actual destructive and
fail-closed semantics for live remove behavior.

Storage-owned responsibilities currently include:

- logical-file existence lookup
- `PROCESSING` status refusal
- snapshot-retention blocking
- removal of physical-file mappings
- logical-file deletion when mappings are removed
- ref-count and mapping-count consistency checks
- semantic consistency between by-ID remove and stored-path remove

For live by-ID remove, `storage.RemoveFileWithDBResult` performs the key domain
checks before mutation. If the file is still `PROCESSING`, the remove is
refused. If the logical file is retained by one or more snapshots, the remove
is refused before deletion begins.

Stored-path remove uses separate direct CLI/storage entry points, but the same
domain layer still owns the destructive mutation semantics and retention
blocking.

This means the engine does not own destructive safety; it owns only the active
request seam and result shaping around domain outcomes.

## Snapshot-retention invariant ownership

Snapshot-retained delete blocking is domain-owned.

`internal/storage/remove.go` creates the invariant-coded refusal when a
logical file is still referenced by one or more snapshots. That refusal is
created through `internal/invariants` with
`SNAPSHOT_RETAINED_DELETE_BLOCKED`.

For the active engine-backed by-ID path:

- storage creates the invariant-coded error
- engine captures it in `failedRemoveItemWithInvariant`
- engine copies:
  - `InvariantCode`
  - `RecommendedAction`
  - error text
- CLI renders that metadata in batch text and JSON output

This is an important boundary distinction:

- snapshot-retention safety is not enforced by CLI
- snapshot-retention safety is not created by engine
- snapshot-retention safety is enforced in the storage/domain layer and then
  propagated outward

The current by-ID path therefore fails closed without turning retained-delete
refusals into top-level engine request errors.

## Invariant metadata propagation

Invariant metadata for remove currently flows in two different shapes depending
on the path:

- by-ID engine path:
  - domain layer emits invariant-coded error
  - engine projects invariant metadata into `RemoveItemResult`
  - CLI renders those fields publicly
- direct stored-path paths:
  - domain layer emits invariant-coded error
  - CLI attaches invariant metadata to `batch.ItemResult` directly via
    `annotateBatchFailureFromError`
  - CLI renders those fields publicly

This means invariant metadata is preserved across both active public remove
paths, but the projection owner differs:

- engine owns per-item invariant projection for the by-ID seam
- CLI owns per-item invariant projection for direct stored-path seams

That split is transitional, but the public output behavior is stable enough for
`v1.13.5` because both paths preserve invariant code and recommended action
without changing the exposed JSON or text contract.

Dry-run by-ID remove is narrower:

- `dryRunRemoveByID` checks file existence
- `dryRunRemoveByID` rejects `PROCESSING` files
- it does not mutate storage state
- it does not currently claim to model every live invariant outcome

The review should therefore describe current dry-run behavior as-is rather than
overstating it as a full live-operation invariant simulation.

## Unsupported and deferred seams

The current remove boundary still has intentional transitional seams:

- engine support is active only for `RemoveModeFileIDs`
- `stored_path` and `stored_paths` remain explicit `ErrNotImplemented`
  boundaries at the engine layer
- those same stored-path behaviors still exist publicly as direct CLI/storage
  paths
- invariant metadata projection is engine-owned for by-ID remove but CLI-owned
  for stored-path remove
- public batch rendering and exit-code classification remain CLI-owned

These seams are transitional but acceptable for `v1.13.5` because this phase
is a review-only release phase and does not expand engine scope by default.

They should not be described as bugs unless a later phase finds conflicting
behavior.

## Findings

### Stable enough for v1.13.5

- by-ID remove has a real engine-owned request/result seam rather than a
  minimal placeholder
- live destructive-operation safety and snapshot-retention blocking are owned
  by the storage/domain layer, which is the correct fail-closed boundary for
  mutation
- invariant metadata is preserved publicly across both engine-backed and direct
  CLI/storage remove paths
- unsupported engine modes remain explicit `ErrNotImplemented` boundaries

### Transitional but acceptable

- engine supports only `RemoveModeFileIDs`, while stored-path remove remains
  outside the active engine seam
- invariant metadata projection is not owned uniformly across all remove paths
- public batch rendering and exit-code classification remain CLI-owned even
  when the engine supplies structured item results
- by-ID dry-run checks are intentionally narrower than full live mutation
  semantics

### Candidate guard gaps

- preserve snapshot-retention invariant metadata all the way through CLI batch
  text and JSON rendering
- preserve the unsupported stored-path engine boundaries against accidental
  routing expansion
- preserve the distinction between top-level request validation failures and
  per-item invalid-ID failures

These are candidate guard/test concerns for Phase 8, not current bug claims.

## Phase 3 decision

The current `Remove` ownership boundary is acceptable for `v1.13.5`.

The active by-ID engine request validation, structured engine result shape, and
storage-layer destructive-operation invariants are separated clearly enough for
the current engine-facing path.

No Phase 3 ownership migration, production code change, or test change is
required.

If later phases choose to add coverage, it should be a narrow Phase 8 guard
pass rather than a Phase 3 behavioral rewrite.

## Impact statement

Phase 3 documents current remove ownership only.

It changes no production code, no tests, no scripts, no CI behavior, no public
CLI behavior, no JSON output, no error envelope shape, no exit codes, and no
runtime behavior.
