# Coldkeep v1.13.4 Renderer and JSON Assembly Boundary Review

**Release:** `v1.13.4 — Read-Side Dependency Direction and Result Ownership Review`  
**Phase:** Phase 6  
**Status:** Complete  
**Branch:** `release/v1.13.4`

## Purpose

This document reviews human renderer ownership, JSON success envelope
ownership, JSON error envelope ownership, and taxonomy-leak boundaries across
the `v1.13.4` read-side surfaces:

- `stats`
- `inspect`
- `snapshot show`
- `snapshot diff`

The goal is to decide whether the current renderer and JSON assembly
boundaries are acceptable for `v1.13.x` and what should be deferred to later
releases.

This phase is documentation-only and does not change runtime behavior.

## Boundary definitions

- human renderer:
  the code path that formats successful human/text output for a read-side
  command
- JSON success envelope:
  the public JSON shape emitted on successful command completion
- JSON error envelope:
  the public JSON shape emitted on stderr for CLI-visible failures
- CLI JSON assembly:
  direct payload construction in `cmd/coldkeep/main.go` rather than inside a
  renderer helper
- renderer JSON helper:
  a renderer-owned success JSON emitter such as
  `internal/cli/render.JSONRenderer`
- taxonomy leak:
  exposure of internal helper concepts such as unsupported/deferred
  classification names in public CLI output
- public output contract:
  the currently shipped human output, JSON success fields, JSON error fields,
  and exit-code behavior that must not drift in `v1.13.4`

## `stats` boundary

Current observed boundary:

- human output owner:
  `internal/cli/render.HumanRenderer.RenderStats`
- JSON success envelope owner:
  `internal/cli/render.JSONRenderer.RenderStats`
- JSON error envelope owner:
  `cmd/coldkeep`, through `observabilityWrappedError` and `printCLIError`
- result shape consumed by rendering:
  observability-shaped stats data returned from the engine wrapper seam as
  `result.Raw`
- final JSON success owner:
  the renderer, not the CLI
- taxonomy-leak protection:
  read-side preservation and translation tests assert that success and error
  payloads do not expose internal taxonomy helper names
- deferred seams carried forward from Phase 2:
  engine wraps observability-owned stats data, renderer consumes
  observability-shaped results directly, and success/error JSON ownership is
  split between renderer and CLI

`stats` therefore keeps the most renderer-heavy JSON ownership model of the
four read-side surfaces: both human output and success JSON are renderer-owned,
while public error translation remains CLI-owned.

## `inspect` boundary

Current observed boundary:

- human output owner:
  `internal/cli/render.HumanRenderer.RenderInspect`
- JSON success envelope owner:
  `internal/cli/render.JSONRenderer.RenderInspect`
- JSON error envelope owner:
  `cmd/coldkeep`, through `observabilityErrorf`,
  `observabilityWrappedError`, and `printCLIError`
- observability result shape consumed by rendering:
  `observability.InspectResult`
- supported target output stability:
  public targets and alias behavior remain unchanged, and the renderer still
  consumes observability-owned inspect results directly
- taxonomy-leak protection:
  preservation tests assert that not-found and invalid-argument error payloads
  stay public-contract-oriented rather than exposing internal taxonomy labels
- deferred seams carried forward from Phase 3:
  production inspect routing remains `CLI -> observability`, renderer consumes
  observability-shaped results directly, and success/error JSON ownership is
  split between renderer and CLI

`inspect` therefore matches `stats` in broad boundary shape even though its
production dependency direction differs: renderer owns human output and success
JSON, while the CLI owns public error translation.

## `snapshot show` boundary

Current observed boundary:

- human output owner:
  `internal/cli/render.RenderSnapshotShowHuman`
- JSON success envelope owner:
  `cmd/coldkeep`
- JSON error envelope owner:
  `cmd/coldkeep`
- metadata/file-list/stats result assembly owner:
  `cmd/coldkeep`, after calling `getSnapshotPhase`,
  `listSnapshotFilesPhase`, and `snapshotStatsPhase`
- count field ownership:
  CLI owns `file_count`, `matched_file_count`, and
  `total_snapshot_file_count` projection in the final payload
- empty/missing snapshot output behavior:
  remains unchanged, with empty snapshots still producing success output and
  missing snapshots still flowing through the current CLI-visible error path
- taxonomy-leak protection:
  preservation and translation tests keep the public payload free of internal
  taxonomy-helper terms
- deferred seams carried forward from Phase 4:
  mixed metadata/file-list/stats ownership remains active, and the CLI keeps
  final JSON success assembly

`snapshot show` therefore uses a different success-output boundary from
`stats` and `inspect`: renderer owns only the human path, while the CLI owns
the public JSON success envelope and all public count-field assembly.

## `snapshot diff` boundary

Current observed boundary:

- human output owner:
  `internal/cli/render.RenderSnapshotDiffSummaryHuman` and
  `internal/cli/render.RenderSnapshotDiffDetailedHuman`
- JSON success envelope owner:
  `cmd/coldkeep`
- JSON error envelope owner:
  `cmd/coldkeep`
- summary JSON behavior:
  summary-mode fast-path JSON omits `entries` and sets `summary_mode: true`
- detailed JSON behavior:
  detailed JSON includes `entries` unless `--summary` is set on the
  detailed/general path
- entries inclusion/omission behavior:
  remains CLI-owned in the final payload branch
- matched/total count ownership:
  CLI owns `matched_entry_count` and `total_diff_entry_count` projection
- filter post-processing impact:
  CLI-owned `--filter` post-processing changes final matched entries and final
  matched counts without changing the preserved pre-filter total count
- taxonomy-leak protection:
  preservation and translation tests keep public success and error output free
  of internal taxonomy-helper terms
- deferred seams carried forward from Phase 5:
  summary/detailed split, count-field assembly, and JSON success ownership
  remain CLI-owned over the mixed CLI/engine/snapshot seam

`snapshot diff` therefore matches `snapshot show` in success-envelope owner but
adds extra CLI-owned behavior around summary-versus-detailed JSON, `entries`
inclusion, and matched-versus-total count projection.

## JSON contract fields that must not drift

Two success-envelope families currently exist and must not be flattened into a
single notional shape in `v1.13.4`.

Renderer-envelope fields for `stats` and `inspect`:

- `generated_at_utc`
- `type`
- `data`
- `warnings`
- `meta`
- `meta.version`
- `meta.exact`

CLI-envelope fields for `snapshot show` and `snapshot diff`:

- `status`
- `command`
- `data`

CLI-owned read-side data fields that must remain stable where currently used:

- `action`
- `file_count`
- `matched_file_count`
- `total_snapshot_file_count`
- `files`
- `entry_count`
- `matched_entry_count`
- `total_diff_entry_count`
- `entries`
- `summary`
- `summary_mode`
- `duration_ms`

CLI JSON error-envelope fields that must remain stable across the read-side
surfaces:

- `status`
- `error_class`
- `exit_code`
- `message`
- `error`
- `error.code`
- `error.message`

Not every field belongs to every surface. `stats` and `inspect` do not use the
top-level `status` / `command` / `data` success envelope, while
`snapshot show` and `snapshot diff` do not use the renderer schema envelope
family.

## Error envelope and taxonomy boundary

Public error rendering remains CLI-owned through `printCLIError`.

Observed current behavior:

- read-side commands return public-facing errors from command code such as:
  - `observabilityErrorf`
  - `observabilityWrappedError`
  - `usageErrorf`
- `printCLIError` owns the JSON error envelope written to stderr
- read-side command wrappers choose public codes such as:
  - `INVALID_ARGUMENT`
  - `NOT_FOUND`
  - `INTERNAL`
- `printCLIError` owns:
  - `status`
  - `error_class`
  - `exit_code`
  - `message`
  - nested `error` node

Taxonomy boundary finding:

- taxonomy helper names such as `engine.IsUnsupported` and
  `catalog.IsDeferred` remain internal-only helper concepts
- `v1.13.2` and `v1.13.3` no-taxonomy-leak expectations carry forward through
  the current preservation and translation tests
- current success and error tests explicitly reject leaked fields and leaked
  helper-name strings in public output

The error boundary is therefore intentionally CLI/public-contract-owned even
when the success boundary varies by surface.

## Boundary finding

The current renderer and JSON assembly boundaries are acceptable for
`v1.13.x` as documented transitional seams. Human rendering remains
renderer-owned where renderer functions exist, JSON success ownership remains
surface-specific rather than unified, and JSON error envelopes remain
CLI-owned/public-contract-owned. No JSON consolidation should be performed in
`v1.13.4`.

Observed findings supporting that decision:

- human rendering remains renderer-owned across all four surfaces
- success JSON ownership is intentionally split by surface rather than unified
- `stats` and `inspect` retain renderer-owned success JSON
- `snapshot show` and `snapshot diff` retain CLI-owned success JSON
- JSON error envelopes remain CLI-owned across the read-side surfaces
- current test coverage actively protects the no-taxonomy-leak boundary

This is a split-but-stable boundary rather than a broken one.

## Why not consolidate JSON ownership now

`v1.13.4` should not introduce a unified read-side JSON envelope or shared
result abstraction now.

Reasons:

- consolidating now risks public JSON drift
- it risks count-field drift on `snapshot show` and `snapshot diff`
- it risks summary-versus-detailed diff drift
- it risks inspect target output drift
- it risks renderer result-shape drift for `stats` and `inspect`
- it risks taxonomy-helper leakage into public output
- `v1.13.4` scope is ownership review and guardrails, not broad
  public-output migration

## Gaps and deferred work

| Gap | Risk | Recommended handling |
| --- | ---: | --- |
| Surface-specific JSON success ownership | Medium | Document and defer consolidation |
| CLI-owned JSON error envelopes | Low/Medium | Preserve public contract |
| Renderer consumes transitional result shapes | Medium | Defer result-shape migration |
| Snapshot show/diff count fields assembled across seams | Medium | Preserve and guard |
| Taxonomy helper leak protection relies on tests | Low/Medium | Strengthen in Phase 7 only if underprotected |

These are ownership and guardrail gaps, not current correctness blockers.

## Decision for v1.13.4

For `v1.13.4`, keep the current renderer and JSON assembly boundaries
unchanged.

Treat the current renderer/JSON split as a documented transitional seam.

Do not introduce a unified read-side JSON result abstraction in this release.

Preserve all public JSON fields, human output, JSON error envelopes, exit
codes, and taxonomy visibility.

Use Phase 7 only for narrow guard tests if current protection is underpowered.
