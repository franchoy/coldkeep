# v1.13.1 Validation Checklist

## Phase-Level Validation Expectations

- Phase 0: run `git diff --check` and `git status -sb`, then confirm the phase is docs/scope only.
- Phase 1: validate that the deferred-boundary target matrix stays aligned with the completed
  `v1.13.0` inventories and `v1.13.x` release-train rules.
- Phases 2 through 7: run validation proportional to the narrow boundary-hardening work performed,
  with explicit confirmation that behavior does not broaden beyond the scoped boundary target.
- Phase 8: validate documentation updates against the actual hardened boundaries and remaining
  deferred areas.
- Phase 9: run the full release gate and record actual commands, actual outcomes, and any honest
  limits on what could not be run.

## Targeted Test Expectations for Later Phases

- Engine deferred-boundary work must include targeted tests for explicit unsupported behavior where
  current engine surfaces already exist.
- Catalog deferred-boundary work must include targeted tests proving deferred methods remain
  explicit and consistent across supported backends.
- Candidate-only operation guardrails must include tests showing those operations cannot be
  mistaken for active engine support.
- Partial-routing hardening must include route-preservation tests so narrowed engine ownership does
  not masquerade as full workflow ownership.
- Request/result clarification work must include tests or assertions that supported versus deferred
  semantics are explicit for the narrowed surfaces under change.
- CLI boundary preservation must include targeted parity or preservation coverage for any command
  path touched by later phases.

## Required Full Release Gate Expectations

```bash
git status -sb
git diff --check
gofmt -l $(git ls-files '*.go')
go test -count=1 ./...
go test -race -count=1 ./...
go vet ./...
golangci-lint run ./...
```

- Record `git status -sb` before and after the final validation run.
- Record the exact command lines executed and whether each command passed, failed, or could not be
  run.
- Record any unavailable validation honestly, including why it was unavailable and what risk
  remains because of that gap.
- Confirm that no Go/runtime behavior changes were introduced unless a later phase explicitly
  scoped a narrow boundary-hardening change.

## No-Go Checks

- No schema or migration changes.
- No storage format or repository format changes.
- No CLI behavior changes.
- No JSON output changes.
- No exit-code changes.
- No default backend behavior changes.
- No broad engine routing changes.
- No catalog implementation expansion beyond narrowly scoped boundary hardening.
- No CI behavior changes.
- No script changes.
- No daemon, API, UI, or v2.0 implementation work.
- No broad refactors presented as release hardening.

## Documentation and Honesty Requirements

- `v1.13.1` docs must state clearly that the release makes boundaries more explicit and safe; it
  does not claim engine or catalog completeness.
- `v1.13.1` docs must preserve SQLite/PostgreSQL compatibility expectations.
- Validation records must distinguish confirmed facts from assumptions.
- If a validation step is unavailable, blocked, or intentionally not run, the release notes and
  gate record must say so plainly rather than implying coverage that did not happen.

## Runtime-Change Constraint

No Go or runtime behavior changes are allowed in `v1.13.1` unless a later phase explicitly scopes
a narrow boundary-hardening change tied to deferred, partial, or candidate-only contract safety.
Even then, the change must preserve CLI behavior, JSON output, exit codes, repository format,
storage format, schema, migrations, default backend behavior, and PostgreSQL compatibility.
