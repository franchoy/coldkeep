## Status

`complete`

## Purpose

This document maps the current `snapshot diff` read-side contract and
identifies the safe cleanup and test-hardening plan for later `v1.13.3`
phases.

This document does not change `snapshot diff` behavior.

This document does not change `snapshot diff` routing.

This document does not change `snapshot diff` query semantics.

## Relationship to Phase 1

Phase 1 established the key `snapshot diff` finding that drives this phase:

`snapshot diff` still narrows richer CLI semantics into a provisional engine
seam and reprojects the result back out for current CLI/render behavior.

Current `snapshot diff` ownership summary:

- current CLI entry point: `runSnapshotDiffCommand`
- current engine involvement: CLI constructs `engine.SnapshotDiffRequest`,
  calls engine-backed diff phase vars, and depends on engine summary fast-path
  and detailed diff routing
- current snapshot package ownership: detailed results are reprojected back
  into `snapshot.SnapshotDiffResult` / `snapshot.SnapshotDiffEntry`, and the
  engine detailed path still delegates to `snapshot.DiffSnapshots`
- current renderer ownership: `internal/cli/render` owns human summary and
  detailed output
- current backend, catalog, and storage dependencies: snapshot diff reads
  snapshot metadata, snapshot file rows, normalized path rows, and
  logical-file identity through snapshot and engine seams
- current base/target snapshot behavior: both snapshot IDs are required and
  missing active snapshots surface through the current direct not-found error
  path
- current query, filter, and narrowing behavior: the CLI can parse richer
  repeated exact paths and prefixes than the current engine seam preserves,
  and detailed results are then re-filtered and re-summarized in the CLI

## Current Snapshot Diff Flow

Current code-path flow:

```text
CLI snapshot diff command
  -> flag parsing and validation
  -> base and target snapshot ID parsing
  -> filter parsing
  -> snapshot query parsing
  -> storage context / DB opening
  -> summary fast-path check
  -> if summary fast path:
       diffSnapshotSummaryPhase
       -> engine.New
       -> eng.SnapshotDiff(Summary=true)
       -> CLI JSON assembly or RenderSnapshotDiffSummaryHuman
  -> else:
       diffSnapshotsPhase
       -> engine.New
       -> richer snapshot.SnapshotQuery narrowed into engine.SnapshotQuery
       -> eng.SnapshotDiff(...)
       -> engine detailed path delegates to snapshot.DiffSnapshots
       -> detailed result reprojected back to snapshot.SnapshotDiffResult
       -> CLI applies filter summary shaping and matched/total counts
       -> CLI JSON assembly or RenderSnapshotDiffDetailedHuman
```

## Current Snapshot Diff Behavior To Preserve

Verified current public behavior that must remain unchanged:

- command name is `snapshot diff`
- usage is:
  - `coldkeep snapshot diff <baseSnapshotID> <targetSnapshotID> [--summary] [--filter <added|removed|modified>] [--path <exact>] [--prefix <dir/>] [--pattern <glob>] [--regex <re>] [--min-size <bytes>] [--max-size <bytes>] [--modified-after <timestamp>] [--modified-before <timestamp>] [--output <text|json>]`
- accepted flags are `--filter`, `--summary`, `--output`, `--json`, `--path`,
  `--prefix`, `--pattern`, `--regex`, `--min-size`, `--max-size`,
  `--modified-after`, and `--modified-before`
- `baseSnapshotID` and `targetSnapshotID` are required, trimmed, and empty
  values are usage errors
- `--filter` only accepts `added`, `removed`, or `modified`
- invalid regex values are validation or usage errors from query parsing
- detailed mode returns matched and total counts separately
- summary fast path is only used when `--summary` is set, no filter is set, and
  query is `nil`
- summary-mode JSON omits `entries`
- detailed-mode JSON includes `entries`
- empty diff and no-match filtered diff remain successful outputs, not errors
- human summary output is renderer-owned and shows only aggregate counters
- human detailed output is renderer-owned and shows base, target, entries,
  matched and total counts, summary, duration, and hint
- JSON success output uses the legacy CLI envelope with:
  - `status: "ok"`
  - `command: "snapshot diff"`
  - `data.base`
  - `data.target`
  - `data.entry_count`
  - `data.matched_entry_count`
  - `data.total_diff_entry_count`
  - `data.summary`
  - `data.duration_ms`
  - `data.summary_mode` only in summary mode
  - `data.entries` only in detailed mode
- failures otherwise route through the current shared CLI behavior with no
  snapshot diff-specific exit-code redesign
- backend-visible behavior is expected to remain equivalent across supported
  backends

## Query And Narrowing Semantics

This is the most provisional current surface.

Current behavior appears to be:

- accepted query filters are exact `path`, `prefix`, `pattern`, `regex`,
  `min-size`, `max-size`, `modified-after`, and `modified-before`
- accepted change filter is `--filter <added|removed|modified>`
- query parsing happens in `parseSnapshotQuery(parsed)`
- the CLI query can preserve multiple exact paths and multiple prefixes in
  `snapshot.SnapshotQuery`
- the current code path shows `diffSnapshotsPhase` narrowing that richer query
  into `engine.SnapshotQuery`
- current code path shows:
  - only one exact path crosses the engine seam
  - only one prefix crosses the engine seam
  - `pattern`, `min-size`, `max-size`, `modified-after`, and
    `modified-before` are preserved into the engine query shape
  - regex is re-expressed as a string for the engine seam
- tests found that repeated CLI prefixes can exist before the seam and that the
  current engine seam preserves only the first prefix
- current engine detailed diff applies the engine query before returning
  detailed results, and the CLI then applies `--filter` after the detailed diff
  result comes back
- narrowing changes matched and total counts:
  - `matched_entry_count` reflects the current filtered or narrowed result
  - `total_diff_entry_count` reflects the pre-filter detailed diff size
- invalid regex values are validation or usage errors today, not runtime
  errors
- invalid size or time filters appear to be validation or usage errors through
  shared snapshot query parsing, but this is not fully established by the
  focused Phase 5 reads and should be treated as a candidate for later
  preservation test
- empty filters broaden results by leaving the query unset or leaving the
  filter blank
- whitespace-only base or target IDs are rejected
- whitespace-only filter values are trimmed and then rejected if not one of the
  allowed values
- behavior is partially documented by current tests today, but the full
  narrowing contract is not yet fully established

## Error Taxonomy Mapping For Snapshot Diff

| Error family | Current source | Current representation | Public behavior | v1.13.3 decision |
| --- | --- | --- | --- | --- |
| validation / usage errors | CLI parsing in `runSnapshotDiffCommand`, `ensureAllowedFlags`, and usage checks | `usageErrorf(...)` / `cliError` | usage-style message and shared usage exit classification | `preserve as-is` |
| missing required base / target snapshot ID | empty or missing positional base or target ID | usage errors such as `baseSnapshotID cannot be empty` | usage-style public behavior | `candidate for Phase 7 preservation test` |
| invalid base / target snapshot ID | malformed empty or whitespace-only IDs in CLI path | usage-style errors today | current validation behavior must remain stable | `document as current validation behavior` |
| invalid query / filter values | invalid `--filter` and shared query parsing failures | usage-style errors today | current validation behavior must remain stable | `candidate for Phase 6 and Phase 7 protection` |
| invalid regex | snapshot query parsing failure | error containing `invalid --regex value` | validation or usage behavior | `candidate for Phase 6 and Phase 7 protection` |
| domain missing base snapshot | engine/snapshot diff lookup miss for valid base ID | direct `snapshot "... not found"` style error | current missing-snapshot behavior must remain stable | `candidate for Phase 6 and Phase 7 protection` |
| domain missing target snapshot | engine/snapshot diff lookup miss for valid target ID | direct `snapshot "... not found"` style error | current missing-snapshot behavior must remain stable | `candidate for Phase 6 and Phase 7 protection` |
| empty diff | no changes or no matched rows after narrowing | successful output with zero entries and zero summary counts | empty diff is not an error today | `preserve as-is` |
| invariant / integrity errors | indirect only unless lower-level snapshot metadata or normalized path checks surface impossible relationships | no dedicated snapshot diff invariant family today | must not be invented or overstated in Phase 5 | `document as indirect / provisional` |
| runtime DB errors | engine, snapshot summary SQL, or detailed diff query/read failures | wrapped query, iteration, or lookup errors | shared CLI general failure behavior | `candidate for Phase 6 and Phase 7 protection` |
| catalog-origin errors | snapshot existence checks and metadata-backed diff preconditions | wrapped lookup or existence-check failures | current direct failure behavior | `document honestly; no new helper` |
| storage-origin errors | indirect through file-entry and path-backed metadata | not a first-class typed snapshot diff seam | surfaces, if at all, through lower-level wrapped failures | `document as indirect` |
| environment / config errors | repository context open, DB open, nil DB, or engine setup failure | wrapped setup or DB-open failures | shared CLI general failure behavior | `candidate for later preservation checks` |
| unsupported / deferred errors | no active snapshot diff unsupported-engine or deferred seam found | not current behavior | should not be introduced accidentally | `document as not current behavior` |
| unknown / provisional errors | provisional query narrowing and mixed ownership seams | documentation-only classification | no public taxonomy leakage | `document as provisional only` |

Important mapping constraints:

- do not claim unified `snapshot diff` taxonomy wrapping
- do not introduce new helper names
- do not classify missing snapshot as invariant corruption
- do not classify empty diff as an error
- do not classify invalid query or filter values as runtime errors when current
  behavior treats them as usage
- do not classify runtime DB failure as domain not-found

## Domain Vs Invariant Boundary For Snapshot Diff

Current boundary guidance from repo truth:

- missing required base or target snapshot arguments are validation or usage
  behavior
- malformed IDs or invalid filters are validation or usage behavior today
- valid base or target snapshot IDs that do not exist are current domain
  missing-snapshot behavior
- empty diff and no-match query or filter narrowing remain successful reads
- impossible snapshot graph metadata, broken parent relationships, impossible
  file mappings, or inconsistent diff rows are invariant or integrity concerns
  only if current code already detects them or later phases establish them
  with tests
- runtime DB and read failures remain runtime, catalog-origin, storage-origin,
  or environment-origin failures, not domain missing-snapshot behavior

## Public CLI Preservation Notes

Preservation concerns that later phases must keep explicit:

- human output preservation:
  - summary and detailed layouts, labels, matched and total counts, duration,
    and hint lines must not drift accidentally
- JSON output preservation:
  - legacy success envelope fields, command naming, summary mode behavior, and
    count semantics must remain stable
- JSON error-envelope preservation:
  - `snapshot diff` must not gain taxonomy fields or helper-name leakage in
    public JSON errors
- exit-code preservation:
  - `snapshot diff` depends on shared CLI exit classification and must not get
    a custom redesign
- startup / logging / noise concerns:
  - JSON mode must remain a clean single-object success output without extra
    startup noise
- taxonomy helper leakage concerns:
  - no taxonomy helper names or internal classification fields should appear
    in public `snapshot diff` JSON
- query / filter preservation concerns:
  - current path, prefix, pattern, regex, size, time, and filter semantics
    must remain stable until a later explicit contract-cleanup phase changes
    them intentionally
