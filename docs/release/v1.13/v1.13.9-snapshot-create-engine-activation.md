## Purpose

Activate snapshot create as a real engine mutation boundary while preserving
the frozen Phase 2 create contract and leaving the production CLI on its
existing direct snapshot-domain route.

Phase 6 activates `Engine.SnapshotCreate`. It does not:

- route `snapshot create` CLI through the engine;
- remove `createSnapshotPhase`;
- remove CLI `generateSnapshotID`;
- remove the CLI post-create `COUNT(*)` query;
- activate snapshot delete or snapshot restore; or
- change snapshot create human output, JSON output, or exit behavior.

## Executive result

Phase 6 makes snapshot create active in the engine and keeps the rest of the
snapshot mutation work deferred.

The implemented outcome is:

- `SnapshotCreate` is now part of the active `Engine` interface;
- `DefaultEngine.SnapshotCreate` implements the frozen Phase 2 request/result
  contract;
- omitted IDs are generated inside the engine through an instance-owned
  generator seam;
- full versus partial type derivation and request-only validation now happen at
  the engine boundary;
- the snapshot-domain create transaction remains the atomic execution core;
- `FilesInserted` now comes from the committed mutation result rather than a
  later query on the engine path;
- failed create attempts return zero results and leave no committed snapshot or
  membership rows; and
- snapshot delete and snapshot restore remain inactive and candidate-only.

## Interface activation

`Engine` now exposes:

```go
SnapshotCreate(ctx context.Context, req SnapshotCreateRequest) (SnapshotCreateResult, error)
```

The active-interface update preserves these boundaries:

- snapshot create is now active;
- snapshot delete remains inactive;
- snapshot restore remains inactive; and
- no placeholder mutation methods were added.

The interface comment freezes these active truths:

- snapshot create is engine-owned;
- the operation is catalog-only;
- snapshot type is derived from request paths;
- the mutation must be atomic; and
- omitted IDs are generated by the engine.

## Engine create behavior

`DefaultEngine.SnapshotCreate` now:

1. normalizes a nil context to `context.Background()`;
2. copies request paths before downstream use;
3. trims `ID`, `Label`, and `ParentID`;
4. generates an ID when the trimmed request ID is empty;
5. derives `SnapshotTypeFull` or `SnapshotTypePartial` from `Paths`;
6. rejects parent-plus-paths requests before mutation;
7. rejects self-parenting before mutation;
8. validates request-only path syntax before domain mutation;
9. calls the snapshot-domain create transaction through a result-returning
   core; and
10. returns only committed create facts in `SnapshotCreateResult`.

Frozen compatibility points preserved in Phase 6:

- whitespace-only direct engine IDs mean generate;
- CLI explicit-empty `--id`, `--label`, and `--from` rejection remains
  unchanged because CLI routing is unchanged;
- no generated-ID collision retry was added;
- no new snapshot-ID syntax restrictions were added; and
- no storage-writer or filesystem dependency was added to create.

## Instance-owned ID generator

Phase 6 implements the frozen generator seam as immutable engine state:

```go
type snapshotIDGenerator func() (string, error)
```

`DefaultEngine` now owns that generator internally.

Rules preserved by the implementation:

- no package-global mutable generator exists;
- no environment-variable hook exists;
- no public `Config` test field exists;
- each engine instance keeps its own generator;
- `New` defaults the generator to the secure production implementation; and
- test injection stays package-private.

The secure default generator preserves the current CLI format exactly:

- prefix `snap-`
- 16 lowercase hexadecimal characters
- 8 bytes from `crypto/rand`

Generator failures still preserve the stable wrapped entropy substring:

- `generate snapshot id entropy: ...`

## Snapshot-domain result core

Phase 6 keeps the existing atomic snapshot-domain create flow but introduces a
result-returning core:

```go
type CreateSnapshotResult struct {
	SnapshotID    string
	Type          string
	PathsCount    int
	FilesInserted int
	Label         string
	ParentID      string
}
```

The new `CreateSnapshotWithOptionsResult` path:

- owns the same create transaction as before;
- assembles `FilesInserted` from the committed membership insert set;
- returns the result only after successful commit; and
- returns a zero result on failure.

The compatibility wrapper remains in place:

- `CreateSnapshotWithOptions(...) error` still exists for existing direct
  callers;
- `CreateSnapshot(...) error` continues to route through that error-only
  wrapper.

The production CLI therefore still:

- generates omitted IDs itself;
- derives create type itself;
- calls `createSnapshotPhase` directly; and
- performs its existing post-create `COUNT(*)` query.
