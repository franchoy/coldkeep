## 3. GATE-001 — isolated CLI storage identity

`tests/utils.DefaultCLIEnv(string)` retains its signature. It now panics on
blank or whitespace-only input, applies `filepath.Clean`, resolves the result
with `filepath.Abs`, and panics if absolute resolution fails. Its supplied
test root is authoritative; parent `COLDKEEP_STORAGE_DIR` is not consulted.

Every subtest of `TestSchemaStartupOperatorMessagingReleaseGate` now passes a
separate `filepath.Join(t.TempDir(), "containers")`. The resulting subprocess
environment is absolute and remains identical under an alternate subprocess
cwd. The regression proves blank, relative, absolute, inherited-environment,
alternate-cwd, unique-root, and TempDir cleanup behavior.

The first full-suite closure attempt correctly stopped when the same forbidden
zero-byte lock reappeared after the schema gate itself had already proved
clean. A read-only reproduction from the trusted entry commit isolated a
second GATE-001 test root:
`TestRunCLISimulateGCRunsStartupRecoveryWithinCoordination` invoked the
coordinated production CLI path while package-global `container.ContainersDir`
still named repository-relative `./storage/containers`. Owner review extended
the Phase 14 allowlist by exactly `cmd/coldkeep/main_test.go`. That one test now
saves and restores the global, assigns an absolute unique `t.TempDir` before
`runCLI`, and retains its original exit, recovery-call, recovery-output, and GC
simulation assertions. No product source or production storage default changed.

The preserved hard-stop artifact was exactly
`cmd/coldkeep/storage/containers/.coldkeep-control/repository.lock`, a zero-byte
regular file with no other content below `cmd/coldkeep/storage`. After evidence
capture, owner authorization permitted removal of that file and only its empty
test-generated parents. The focused culprit regression then passed with the
path absent both before and after execution.

The complete validation stack was then repeated. The focused culprit test,
both PostgreSQL schema-gate codec contexts, and the uncached full repository
suite all passed. Without any post-suite cleanup, the lock remained absent and
`cmd/coldkeep/storage` had zero runtime state because the directory itself did
not exist. No third repository-relative caller surfaced.

Before and after the focused schema release gate and the full suite, the known
repository-local lock path is required to be absent. A Phase 14 pass may not
use the former cleanup exception: creation of the lock is a gate failure.

## 4. GATE-002 — tracked-source evidence names

`scripts/validate_snapshot_evidence_names.sh` is the executable source of
truth for the 19 frozen snapshot-retention, GC, Stats, Verify, Doctor, and
adversarial declarations formerly embedded in `PRE_RELEASE_CHECKLIST.md`.
It accepts optional `--repo-root`, requires that path to be the Git toplevel,
and checks each exact declaration with tracked Git authority equivalent to:

```text
git -C "$repo_root" grep -F -- "func ${name}(" -- '*.go'
```

It never uses `grep -R`, `find | grep`, filesystem exclusions, or permission-
dependent traversal. Complete tracked fixtures pass; one missing name fails
with the exact missing name; an untracked file cannot supply a missing name;
unreadable untracked and ignored directories are irrelevant; and a non-Git
root fails.

`PRE_RELEASE_CHECKLIST.md` now invokes this validator. The local CI-enforcement
audit requires an executable regular non-symlink validator, verifies its
tracked-source implementation, and runs it against the repository.

```text
GATE_002_TRACKED_SOURCE_ONLY: YES
GATE_002_UNREADABLE_UNTRACKED_IRRELEVANT: YES
GATE_002_EVIDENCE_NAMES_RENAMED: NO
```

## 6. GATE-003 — retained lifecycle

The only new retained root is:

```text
$REPO_ROOT/.release-evidence/v1.13.14/<candidate-SHA>/
```

`scripts/run_release_benchmark_evidence.sh` creates one external `mktemp -d`
root and installs success, failure, interrupt, and termination cleanup traps.
The four unchanged integrity/timing profiles use disjoint
`profiles/<profile>/integrity` and `profiles/<profile>/timing` directories.
It preserves the existing datasets, workers, compression modes, integrity
semantics, timing advisory exits, baselines, thresholds, codec requirements,
PostgreSQL image identity, and lock-retry settings.

`scripts/release_benchmark_evidence.sh` owns four narrow operations:

- `prepare` verifies the existing integrity and timing checksum manifests,
  creates an exhaustive per-profile checksum manifest, and writes a
  deterministic top manifest containing release, candidate/source SHA,
  expected profile set, relative paths, per-profile manifest identities, Go,
  PostgreSQL, database-image, benchmark-tool, and timing-tool identities;
- `validate` rejects missing profiles or files, symbolic links, partial or
  staging names, unexpected inventories, candidate/source mismatch, profile
  identity mismatch, and any nested, per-profile, or top checksum failure;
- `promote` validates external transient evidence, copies it to one unique
  same-filesystem hidden staging directory below the canonical parent,
  revalidates, then atomically renames it to the final exact-SHA directory;
- `inventory` rejects retained non-SHA entries and any staging residue,
  validates every v1.13.14 SHA bundle, verifies ignore authority, and can also
  require an ordinary untracked-inclusive clean worktree.

A valid existing exact-SHA bundle is reusable only after complete validation.
An incomplete, corrupt, or different existing exact-SHA bundle fails without
overwrite. Promotion failure or signal removes only the invocation's unique
staging directory; any previously valid final directory remains untouched.
No rename is attempted from `/tmp` across filesystems, and filesystem-root
`/.release-evidence` is never used.

Synthetic process tests prove valid promotion, exact candidate path,
checksums, top-manifest mismatch, missing profile, stale-staging rejection,
deterministic signal cleanup, corrupt-existing refusal, idempotent reuse,
external/disjoint transient roots, ignored inventory, and clean ordinary
status without running real benchmarks.


## 7. GATE-004 — branch-relative release linearity

`scripts/validate_release_linearity.sh` is strict when explicitly invoked. It
requires the Git toplevel and `refs/remotes/origin/main`, computes:

```text
base=$(git merge-base HEAD refs/remotes/origin/main)
git rev-list --merges "${base}..HEAD"
```

and fails if the base is absent or the post-base merge list is non-empty. A
merge failure reports every offending merge SHA. It does not inspect inherited
whole history.

Temporary graph fixtures prove direct ancestry, an inherited authoritative-
main merge, and independent later main advancement pass. A release-local merge,
a release merge of updated main, missing `origin/main`, and unrelated histories
fail. The local CI-enforcement audit runs real-repository validation only for
release or release-tag lifecycle contexts, while fixture tests always run, so
ordinary contributor branches do not receive a false release-candidate gate.

The actual `release/v1.13.14` proof resolves `origin/main` and its merge base to
`f3b75dc0fbee44e4fe91eb2df1df724f9426640e`; the post-base merge list is empty.

The remote enforcement audit now also proves the unchanged Phase 0 ruleset:
`Protect release branches` is active, targets exactly
`refs/heads/release/**/*`, has zero bypass actors, contains only
`non_fast_forward`, and omits `required_linear_history`. No GitHub setting is
changed.
