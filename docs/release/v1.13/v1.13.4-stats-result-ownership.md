the `stats` read-side surface.

for `v1.13.x` and what, if anything, should be deferred to later releases.

This phase is documentation-only and does not change runtime behavior.

## Current `stats` flow

Observed current production flow:

`runStatsCommand` -> CLI flag validation and trace parsing ->
`runObservabilityStatsPhase` -> engine `Stats` ->
observability `Stats` -> renderer

Current path details:

- CLI entrypoint is `runStatsCommand` in `cmd/coldkeep/main.go`
- CLI parsing and validation stay in `cmd/coldkeep` through:
  - `ensureAllowedFlags`
  - positional count checks
  - `resolveTraceOptions`
  - `--containers` flag handling
- `runObservabilityStatsPhase` loads the default storage context, constructs
  the engine, calls `eng.Stats`, and returns `result.Raw`
- engine request type is `engine.StatsRequest`
- engine result type is `engine.StatsResult`
- observability option type is `observability.StatsOptions`
- observability result type is `observability.StatsResult`
- `internal/observability.Service.Stats` owns the concrete stats aggregation
  logic by:
  - calling `maintenance.RunStatsResultWithDB`
  - mapping maintenance output into `observability.StatsResult`
  - enriching with graph-derived snapshot reachability
  - calculating efficiency metrics
- backend access stays behind engine -> observability -> maintenance/database
  and graph reads
- human rendering path uses `internal/cli/render.HumanRenderer.RenderStats`
- JSON success output path uses `internal/cli/render.JSONRenderer.RenderStats`
- JSON error output path remains CLI-owned through
  `observabilityWrappedError(exitGeneral, "INTERNAL", "stats collection failed", err)`
- taxonomy-boundary behavior stays outside unsupported/deferred classifications
  under the current read-side tests

## Current result ownership

| Layer | Current owner | Type/function | Notes |
| --- | --- | --- | --- |
| CLI command | `cmd/coldkeep` | `runStatsCommand` | owns command entrypoint and renderer selection |
| CLI validation | `cmd/coldkeep` | `ensureAllowedFlags`, positional checks, `resolveTraceOptions` | owns usage and flag validation |
| Engine request | `internal/engine` | `StatsRequest` | stable backend-neutral request wrapper |
| Engine result | `internal/engine` | `StatsResult{Raw *observability.StatsResult}` | thin wrapper around observability-owned stats data |
| Observability options | `internal/observability` | `StatsOptions` | carries include-containers and trace controls |
| Observability result | `internal/observability` | `StatsResult` | concrete stats model consumed by renderer |
| Human rendering | `internal/cli/render` | `HumanRenderer.RenderStats` | renders observability-shaped stats directly |
| JSON success envelope | `internal/cli/render` | `JSONRenderer.RenderStats` | owns the public stats success envelope |
| JSON error envelope | `cmd/coldkeep` | CLI error wrappers | CLI owns public error translation |
| Backend access | `internal/observability` over maintenance/db/graph | `Service.Stats`, `RunStatsResultWithDB`, graph enrichment | concrete aggregate and enrichment logic stay below CLI |
| Taxonomy boundary | mixed CLI/engine test protection | read-side boundary tests | no dedicated stats taxonomy layer exists |

## Ownership finding

The current `stats` result ownership is acceptable for `v1.13.x` as a
transitional read-side seam.

Observed findings supporting that decision:

- `engine.StatsResult` is a thin wrapper around observability-owned stats data
- the renderer still consumes observability-shaped data directly
- the CLI does not own the stats success envelope, but it still owns public
  error translation
- observability still owns the concrete stats aggregation logic
- backend-sensitive behavior remains behind observability, maintenance,
  database, and graph code
- no public behavior change is justified in `v1.13.4`

This is a mixed-but-stable seam rather than a broken seam. The repo evidence
shows active production use, existing coverage, and no current contract bug
that requires a result-ownership rewrite.

## Why not refactor now

`v1.13.4` should not introduce a new stats result type or broad ownership
migration now.

Reasons:

- introducing a new stats result type would create shape-duplication risk
  between engine, observability, and renderer layers
- moving renderer ownership now risks human-output and JSON-envelope drift
- a broad ownership cleanup conflicts with the review-first scope of
  `v1.13.4`
- no discovered correctness bug justifies changing `engine.StatsResult`,
  `observability.StatsResult`, or the renderer
- current behavior is already documented and test-protected enough to review
  ownership without performing a refactor in this phase

  - protects representative human output behavior

  - protects engine-side success/runtime-failure classification boundaries

  - protects human rendering, JSON rendering, determinism, sorting, and schema

- `internal/observability/stats_test.go`
  - protects mapping from maintenance stats to stable observability result
  - covers nil/zero-result handling and trace behavior

  - protects backend-facing equivalence expectations for stats-related output

  - protects cross-surface consistency between stats and inspect-derived facts

What this protection establishes today:

- success and JSON output are protected
- validation behavior is protected
- taxonomy boundary behavior is protected
- backend behavior is indirectly protected through engine surface compatibility
  and observability/maintenance tests
- empty repository behavior is covered at the maintenance layer
- representative no-taxonomy-helper leakage is covered at the CLI layer

## Gaps and deferred work

| Gap | Risk | Recommended handling |
| --- | ---: | --- |
| Engine result wraps observability result | Medium | Defer to later result-ownership migration |
| Stats renderer depends on observability-shaped result | Medium | Review in Phase 6 |
| CLI/renderer split between success envelope and error envelope ownership | Low/Medium | Review in Phase 6 |
| Backend parity evidence is indirect at CLI level | Low/Medium | Review in Phase 8 |
| Broader empty-repository taxonomy assertions remain limited | Low | Defer unless later phases need stronger guardrails |

These are ownership and guardrail gaps, not current correctness blockers.

## Decision for v1.13.4

For `v1.13.4`, keep the current `stats` result ownership unchanged.

Treat the `engine.StatsResult` wrapper over observability-owned stats data as a
documented transitional seam.

Protect behavior with existing coverage and later guard-test phases rather than
performing a broad result-type migration in this release.
