# v1.13.2 Scope

## Release Name

`v1.13.2 - Engine Error Taxonomy Baseline`

## Status

`Planning / in progress`

## Release Objective

`v1.13.2` exists to define the first stable baseline for classifying engine and catalog errors
without changing user-facing behavior.

This release is a taxonomy-baseline release, not a behavior-migration release.

## Context From v1.13.1

`v1.13.1` made unsupported, deferred, candidate-only, partial, and CLI-owned boundaries explicit.
It clarified where current engine and catalog surfaces are active, where they remain intentionally
deferred, and where exported shapes should not be read as proof of complete ownership.

`v1.13.2` builds on that baseline by classifying the errors around those explicit boundaries. The
goal is to make unsupported, deferred, validation, domain, invariant, and runtime-style failures
more precise without claiming that all deferred behavior is now implemented.

## Included Scope

- release-scope and validation documents for `v1.13.2`
- current error-surface inventory for active and near-active engine and catalog seams
- taxonomy names and baseline meanings
- unsupported versus deferred distinction
- validation versus unsupported distinction
- domain versus invariant distinction
- runtime versus storage versus catalog versus external/environment distinction
- preservation of engine `ErrNotImplemented` as distinct from other failure classes
- preservation of catalog `ErrNotImplemented` as distinct from other failure classes
- focused tests where current behavior can be protected without broad behavior change
- documentation that distinguishes code-backed classifications from doc-backed classifications
- CLI translation-preservation tests where classification work could otherwise blur existing
  command behavior

## Excluded Scope

- recursive store implementation
- stored-path restore engine implementation
- stored-path remove engine implementation
- snapshot create, snapshot delete, or snapshot restore engine implementation
- repair or recovery engine implementation
- deferred catalog graph, placement, restore-plan, or GC-plan implementation
- broad engine routing
- CLI thin-wrapper conversion
- CLI behavior changes
- JSON output changes
- exit-code changes
- schema or migration changes
- storage format changes
- repository format changes
- default backend behavior changes
- CI changes
- script changes
- daemon, API, UI, or `v2` work
- SQLite default switch
- PostgreSQL compatibility removal

## Compatibility Statement

`v1.13.2` must preserve:

- CLI behavior
- JSON output shape
- exit codes
- runtime behavior unless a later phase explicitly documents a non-user-facing internal
  classification addition
- database schema
- storage format
- repository format
- backend compatibility
- PostgreSQL compatibility

## Error Taxonomy Baseline Intent

The target baseline categories for `v1.13.2` are:

- `Unsupported`
- `Deferred`
- `Validation`
- `Domain`
- `Invariant`
- `Runtime`
- `Catalog`
- `Storage`
- `External/Environment`

These categories are release targets, not a claim that every category will be fully implemented in
code during `v1.13.2`.

Some distinctions may be documented first and only become code-backed where a stable current
behavior already exists and can be protected honestly.

Most importantly, `ErrNotImplemented` must remain distinct from validation failure, domain
failure, invariant failure, and runtime or environment failure.

## Release Success Definition

`v1.13.2` is complete when Coldkeep has a documented and test-protected baseline for
distinguishing unsupported, deferred, validation, domain, invariant, runtime, catalog, storage,
and environment errors without changing CLI behavior, JSON output, exit codes, routing, schema,
storage format, repository format, or backend defaults.
