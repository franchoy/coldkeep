## End-to-end `init` flow

User-facing `coldkeep init` is not repository or database initialization.

Current call chain in `cmd/coldkeep/init.go`:

1. CLI parses `coldkeep init` and optional compression flags.
2. CLI generates an AES-GCM key with `blocks.GenerateKeyHex()`.
3. CLI validates compression codec and optional compression level.
4. CLI checks whether `.env` already exists.
5. CLI either prints manual export instructions or writes a new `.env`.
6. CLI prints next-step guidance for `export $(cat .env | xargs)` and later
   storage commands.

Ownership classification:

| Step | Current behavior | Owner |
| --- | --- | --- |
| command parsing | parse `init`, reject extra args, validate flags | CLI |
| pre-repository validation | compression flag validation only | CLI |
| backend/config resolution | none | CLI |
| filesystem preparation | optional `.env` write in cwd | CLI |
| database connection | none | none |
| schema bootstrap or migration | none | none |
| repository capability derivation | none | none |
| storage-directory preparation | none | none |
| result rendering | human-readable key/setup output | CLI |
| error handling and cleanup | CLI errors only | CLI |

No hidden repository/catalog init path was found behind `coldkeep init`.

## End-to-end normal startup flow

For commands that use storage context, the current normal startup chain is:

1. `runCLI()` in `cmd/coldkeep/main.go` decides whether startup recovery runs.
2. `runStartupRecoveryWithOptionalLogBuffering()` calls
   `startupRecoveryPhase(container.ContainersDir)` before command execution for
   commands that require recovery.
3. Command-specific handlers call `loadDefaultStorageContextPhase`, which
   defaults to `storage.LoadDefaultStorageContext`.
4. `storage.LoadDefaultStorageContext()` resolves
   `COLDKEEP_STORAGE_CONTEXT`, defaulting blank/unset values to `local`.
5. `ParseStorageContext("local")` calls `db.ConnectDB()`.
6. `db.ConnectDB()` builds a PostgreSQL DSN from env, opens the DB, pings it,
   configures connection pool settings, and calls `EnsurePostgresSchema()`.
7. `ParseStorageContext("local")` creates a local container writer using
   `container.ContainersDir`.
8. Command code uses the resulting `StorageContext`, and selected paths create
   `storage.NewRepository(sgctx.DB)` or `engine.New(...)`.
9. Results are rendered by command-specific CLI code in text or JSON mode.

Current ownership classification:

| Stage | Current behavior | Owner |
| --- | --- | --- |
| CLI parsing | parse command, flags, output mode | CLI |
| startup recovery gate | optional recovery before command execution | CLI + recovery layer |
| storage-context resolution | `COLDKEEP_STORAGE_CONTEXT` resolution, default `local` | shared configuration + storage layer |
| backend resolution | implicit through storage context choice | shared configuration + storage layer |
| DB connect/open | PostgreSQL env resolution and `sql.Open("postgres", ...)` | database layer |
| schema bootstrap or migration | `EnsurePostgresSchema()` for normal local mode | database layer |
| repository capability derivation | on-demand via `storage.GetRepositoryCapabilities` / `repository/capabilities.Derive` | repository layer |
| writer/container-dir setup | local writer with `container.ContainersDir` | storage layer |
| command execution | engine-routed or direct command-specific path | engine and/or CLI/storage layer |
| result rendering | command-specific text/JSON output | CLI |

## Current backend-default conclusion

Current normal CLI/runtime default is PostgreSQL-backed local mode through
`COLDKEEP_STORAGE_CONTEXT=local`.

Supporting behavior:

- `storage.LoadDefaultStorageContext()` defaults `COLDKEEP_STORAGE_CONTEXT` to
  `local`
- `ParseStorageContext("local")` calls `db.ConnectDB()`
- `db.ConnectDB()` only opens PostgreSQL by building a PostgreSQL DSN from env
  and calling `sql.Open("postgres", ...)`

SQLite is currently active for simulated mode and tests, not the default
normal local runtime path.

SQLite-first is documented direction, not current default runtime behavior.

## SQLite catalog-path behavior

Current observed SQLite behavior is confined to simulated mode and tests.

- active runtime SQLite path found in production code:
  `ParseStorageContext("simulated")` in `internal/storage/context.go`
- simulated mode creates a temp file with `os.CreateTemp("", "coldkeep-sim-*.db")`
- the resulting path is absolute because it comes from `os.CreateTemp`
- the temp SQLite file is outside any repository root by default
- simulated mode does not derive SQLite catalog location from repository root
- simulated mode stores the path in `StorageContext.TempDBPath` and removes it
  on `StorageContext.Close()`
- `sql.Open("sqlite3", tempDBFile.Name())` opens the SQLite file
- `ApplySQLiteSessionPragmas()` applies:
  - `PRAGMA busy_timeout = <statement-timeout-ms>`
  - `PRAGMA foreign_keys = ON`
- simulated mode pins `SetMaxOpenConns(1)` and `SetMaxIdleConns(1)`
- `RunMigrations()` is the active SQLite schema/bootstrap path
- `RunMigrations()` detects fresh installs by checking that no non-`sqlite_%`
  user tables exist and no `schema_version` table exists
- for fresh installs, the SQLite migration path seeds
  `repository_config.default_chunker` to `v2-fastcdc`
- for non-fresh installs, `RunMigrations()` preserves a previously configured
  default chunker where present
- `RunMigrations()` re-enables `PRAGMA foreign_keys = ON` before applying the
  embedded schema and custom migration steps

Test-only SQLite examples found:

- many unit tests use `sql.Open("sqlite3", ":memory:")`
- `internal/storage/phase1_compat_matrix_test.go` uses
  `filepath.Join(dir, "cold.db")`

These test-only filenames should not be promoted to current runtime defaults.

Current WAL/SHM posture:

- no explicit runtime `PRAGMA journal_mode=WAL` was found in current SQLite
  setup code
- no explicit code handling for `-wal` or `-shm` companion files was found in
  current production startup code
- Phase 2 should revisit whether the absence of explicit WAL setup is a
  placement/portability concern

Current reopen/path-consistency posture:

- simulated mode reuses the exact temp file path it creates
- no normal user-facing SQLite repository-open path was found in current
  production startup code

## PostgreSQL connection behavior

Current normal local runtime PostgreSQL behavior is implemented in
`internal/db/db.go`.

- DSN builder: `buildPostgresConnStringForDatabase`
- parameter resolution: `resolvePostgresConnParams`
- component validation:
  - host/user/dbname: non-empty, no NUL
  - port: base-10 integer `1..65535`
  - sslmode: allowlisted values only
  - password: no NUL
- defaults:
  - `DB_HOST=127.0.0.1`
  - `DB_PORT=5432`
  - `DB_USER=coldkeep`
  - `DB_NAME=coldkeep`
  - `DB_SSLMODE=disable`
- values are escaped with `escapePostgresConnValue` before interpolation into
  the PostgreSQL connection string
- `ConnectDB()`:
  - opens `sql.Open("postgres", connStr)`
  - applies pool settings from the `COLDKEEP_DB_*` env vars
  - pings with a bounded connect timeout
  - calls `EnsurePostgresSchema()`

Schema/bootstrap behavior:

- if `schema_version` is missing and `COLDKEEP_DB_AUTO_BOOTSTRAP` is false or
  unset, `EnsurePostgresSchema()` fails with an actionable schema-not-initialized
  error
- if `schema_version` is missing and `COLDKEEP_DB_AUTO_BOOTSTRAP` is true,
  `EnsurePostgresSchema()` loads embedded `db/schema_postgres.sql` and applies
  it to bootstrap schema objects
- if the PostgreSQL schema version is below the required minimum,
  `EnsurePostgresSchema()` reapplies embedded PostgreSQL schema SQL and then
  rechecks version
- this path bootstraps or migrates schema objects inside an existing database;
  it does not create the PostgreSQL database itself

Test/CI selection posture:

- integration helpers in `tests/utils/common.go` build PostgreSQL env maps
  using the same DB env names and defaults
- `RequireDB()` gates PostgreSQL-backed integration suites on
  `COLDKEEP_TEST_DB=1`
- PostgreSQL bootstrap/auto-migrate behavior has direct integration coverage in
  `tests/integration/integration_test.go` and live migration tests in
  `internal/db/migrations_test.go`

## Schema bootstrap and migration behavior

| Concern | SQLite path | PostgreSQL path | Shared behavior | Backend-specific behavior |
| --- | --- | --- | --- | --- |
| fresh bootstrap | `RunMigrations()` applies embedded SQLite schema and custom migration steps | `EnsurePostgresSchema()` applies embedded PostgreSQL schema SQL when `schema_version` is missing and auto-bootstrap is enabled | both use embedded schema assets and version checks | SQLite bootstrap is tied to `RunMigrations`; PostgreSQL bootstrap is gated by `COLDKEEP_DB_AUTO_BOOTSTRAP` |
| migration entry | `RunMigrations()` | `EnsurePostgresSchema()` | both are called through `EnsureSchema()` when caller uses backend-aware routing | normal local runtime calls PostgreSQL path through `ConnectDB()` |
| schema version | `schema_version` table managed by SQLite migration code | `schema_version` table checked with `to_regclass` and version query | both rely on `schema_version` | required PostgreSQL version is `16`; SQLite migration code also performs data-shape migrations |
| transaction behavior | embedded SQLite schema SQL is applied before a follow-up migration transaction; custom migration steps run in a transaction | PostgreSQL bootstrap/migration executes against the opened DB connection through schema SQL execution and version recheck | both may execute multiple statements against a live DB connection | current SQLite path is not a single all-in-one transaction from first schema SQL statement through final custom migration |
| FK behavior | explicit `PRAGMA foreign_keys = ON` in setup and migration | PostgreSQL uses native FK semantics from schema | both expect FK-enforced repository semantics | SQLite FK enforcement is session pragma-based |
| capability derivation | `repository/capabilities.Derive` can run against SQLite handles in tests/simulated contexts | `repository/capabilities.Derive` can run against PostgreSQL runtime DB handles | shared derivation logic adapts SQL placeholders via backend detection | derivation reads repository config through backend-specific placeholder style |
| unsupported legacy refusal | SQLite migration can fail on incompatible legacy shapes during custom migration steps | PostgreSQL bootstrap/migration fails when schema remains too old after auto-migration or when auto-bootstrap is disabled for missing schema | both surface explicit errors rather than silently proceeding | PostgreSQL missing-schema refusal message is explicit and actionable |

Normal repository opening automatically validates schema on PostgreSQL local
startup through `db.ConnectDB()`.

## Existing repository-open behavior

Current startup paths are not perfectly unified.

Shared storage-context path:

- many mutating and storage-aware commands in `cmd/coldkeep/main.go` call
  `loadDefaultStorageContextPhase()`
- this path resolves storage context, opens the DB, prepares the writer, and
  later closes the `StorageContext`
- `config` also uses this path, then wraps `sgctx.DB` in `storage.NewRepository`

Direct database-open path:

- `runListCommand` and `runSearchCommand` call `db.ConnectDB()` directly
- helper functions in `internal/storage/remove.go` and
  `internal/storage/restore.go` also offer direct `db.ConnectDB()` variants
- `db.QueryCurrentSchemaVersion()` opens its own DB via `ConnectDB()`

Observed differences:

- normal local startup and direct DB helpers both end up using PostgreSQL env
  resolution through `db.ConnectDB()`
- storage-context paths also prepare a writer and container directory
- direct DB-open paths do not prepare a writer or storage context
- simulated mode is only reachable through explicit storage-context parsing, not
  through direct `db.ConnectDB()`
- current normal command startup does not use one backend-neutral DB resolver
  that can choose PostgreSQL vs SQLite for all commands

## Phase 1 findings

### Backend-neutral behavior

- CLI startup recovery is a pre-command gate controlled in `runCLI()`
- repository capability derivation is shared logic in
  `repository/capabilities.Derive` with backend-sensitive SQL placeholder
  adaptation
- both backends use embedded schema assets and `schema_version`-based upgrade
  logic

### SQLite-specific behavior

- active production SQLite path is simulated mode, not default local runtime
- simulated mode uses a temp SQLite file plus per-session pragmas
- `RunMigrations()` is SQLite-only and rejects non-SQLite backends
- SQLite tests heavily use in-memory DB handles and explicit `RunMigrations()`

### PostgreSQL-specific behavior

- normal local runtime DB open path is PostgreSQL-only through `db.ConnectDB()`
- PostgreSQL connection settings come from DB env vars plus `COLDKEEP_DB_*`
  timeout/pool tuning vars
- schema bootstrap for missing PostgreSQL schema is controlled by
  `COLDKEEP_DB_AUTO_BOOTSTRAP`

### Shared dialect-adapted behavior

- `EnsureSchema()` dispatches by detected backend
- repository capability reads adapt SQL placeholder style by backend
- both backends preserve repository metadata semantics through schema versioning
  and repository config

### Ambiguities for Phase 2

- current normal runtime does not expose a user-facing SQLite local repository
  catalog path, so Phase 2 must define catalog-placement review boundaries
  carefully
- WAL/SHM companion-file expectations are not explicit in current startup code
- repository-owned catalog/manifests/locks/logs paths are not fully defined for
  a future SQLite-first local repository posture

### Evidence questions for Phase 4

- how much of current SQLite evidence is simulated/test-only versus
  user-representative startup behavior
- whether PostgreSQL-backed reopen and bootstrap coverage is broad enough across
  all command classes
- whether repository capability derivation has meaningful PostgreSQL parity
  coverage

### Documentation questions for Phase 8

- release docs say SQLite-first is the intended local direction, while current
  runtime quickstart still presents PostgreSQL-backed local mode
- Phase 8 should reconcile roadmap wording with present runtime behavior without
  implying a backend-default change that has not happened

### Immediate blockers

None found.

The current repository initialization and backend-selection behavior is
sufficiently inventoried for Phase 2.

Phase 1 makes no backend-default change and no repository-placement decision.

SQLite-first remains the intended local direction, while PostgreSQL
compatibility remains mandatory.
