# Coldkeep v1.13.6 Logical/Physical Mapping Contract Review

**Release:** `v1.13.6 — Catalog Contract Expansion and Backend Parity Review`  
**Phase:** Phase 3  
**Status:** Complete  
**Branch:** `release/v1.13.6`

## Purpose

This document reviews the current contract between logical content identity and
physical filesystem representation.

It covers how `logical_file`, `physical_file`, stored paths, snapshot paths,
restore, remove, read-side commands, verify, repair, retention, GC, and
backend behavior interact today.

This phase performs no implementation work and adds no tests.

## Contract under review

The current logical/physical mapping contract is defined by:

- logical content identity
  - `logical_file` is the content-identity row
  - identity is anchored on `file_hash` plus `total_size`, with lifecycle and
    recipe metadata such as `status`, `ref_count`, and `chunker_version`
- physical filesystem representation
  - `physical_file` is the current-state path mapping layer
  - the stored path is the row identity, and each row points at a
    `logical_file_id`
- logical-to-physical relationship
  - one logical file may have multiple current-state `physical_file` rows
  - `logical_file.ref_count` tracks the number of current-state physical
    mappings and is treated as an invariant
- stored path identity
  - current-state path identity is represented by `physical_file.path`
  - stored-path restore/remove target this current-state identity directly
- snapshot path identity
  - snapshot path identity is represented separately through normalized
    `snapshot_path.path` referenced by `snapshot_file.path_id`
  - snapshot membership persists normalized path identity plus
    `logical_file_id`, not a `physical_file` primary key
- path normalization expectations
  - snapshot paths are normalized and validated as stored relative paths before
    persistence
  - current-state stored paths are normalized through storage-layer helpers and
    remain distinct from snapshot-relative normalization
- deduplication expectations
  - content deduplication is logical-first: identical content claims or reuses
    a logical file, then reuses chunk/block graph state when valid
  - path multiplicity does not itself create new content identity
- restore path reconstruction
  - by-ID restore resolves current logical content and chooses an output path at
    restore time
  - stored-path restore uses current `physical_file.path`
  - snapshot restore reconstructs output targets from normalized snapshot paths
- remove and retention behavior
  - remove-by-ID and remove-by-stored-path both operate through current-state
    logical/physical mappings
  - snapshot-retained logical content blocks destructive remove even when the
    current physical mapping is the immediate target
- read-side exposure
  - read-side commands expose logical-file counts, physical-file counts,
    snapshot-retention counts, and inspectable logical-file state
  - output-shape guards exist, but they are separate from proving full mapping
    semantics or backend parity

## Store-time mapping

Store-time mapping is currently owned below the catalog facade in
`internal/storage`.

- Logical identity creation:
  - store first prepares logical content and computes the logical hash
  - `prepareLogicalFileForStoreWithContext` claims or inserts a `logical_file`
    row keyed by `file_hash` and `total_size`
  - `logical_file` lifecycle is explicit: `PROCESSING`, `COMPLETED`, or
    `ABORTED`
  - reuse is content-based and validated against reusable graph state before a
    completed logical file is accepted
- Physical row creation:
  - once the logical file is claimed or reused, store finalization attaches the
    current stored path through `physical_file`
  - current-path attachment is separate from logical-file claiming, which keeps
    content identity distinct from current filesystem presence
- Multiple physical rows per logical row:
  - the current contract allows more than one `physical_file` row to point at
    the same `logical_file_id`
  - `logical_file.ref_count` is the active count of those current mappings
- Deduplication relationship:
  - dedup is centered on logical content identity, not on stored path identity
  - equal content can reuse a prior logical file and its chunk graph
  - chunk reuse and block reuse sit beneath the logical mapping contract, but
    they are triggered by the same logical identity decision
- Path representation and safety:
  - current-state stored paths are normalized before `physical_file` attachment
  - restore-side path helpers show explicit safe-join and unsafe-symlink
    refusal behavior, indicating that path safety remains an operational
    concern outside catalog
  - snapshot path normalization is separate and should not be conflated with
    current-state stored-path identity
- Backend-sensitive observations:
  - logical-file claiming uses `INSERT ... ON CONFLICT ... DO NOTHING RETURNING`
  - concurrent reuse and retry behavior depends on transaction semantics and
    row visibility
  - later current-path attachment and replacement semantics remain outside a
    dedicated catalog write contract

## Snapshot mapping interaction

Snapshot mapping uses current-state physical mappings as source input, but it
persists a different identity shape.

- Snapshots consume current `physical_file` state:
  - `snapshotSourceQuery` reads `physical_file.path`, `physical_file.logical_file_id`,
    and `logical_file` metadata for completed logical files
  - source enumeration is ordered by `pf.path, pf.logical_file_id`
- Snapshots persist normalized path plus logical identity:
  - snapshot membership stores normalized `snapshot_path` identity plus
    `logical_file_id`
  - it does not persist a `physical_file` primary key, so snapshot state is not
    a direct mirror of current physical rows
- Show and diff semantics:
  - snapshot show reads metadata via catalog, then reads snapshot members
    directly from snapshot helpers
  - snapshot diff compares normalized path identity and `logical_file_id`
  - same path with different `logical_file_id` is treated as changed content
  - snapshot diff is therefore path-plus-logical-identity oriented, not raw
    physical-row oriented
- Restore interaction:
  - snapshot restore starts from snapshot membership rows and reconstructs
    output paths from snapshot-relative normalized paths
  - physical-file current mappings are the source for snapshot creation, but
    they are not required to still exist in the same form at snapshot restore
    time
- Phase boundary:
  - Phase 2 documented snapshot membership sufficiency and consumers
  - Phase 3 only maps how snapshot membership relates to logical identity,
    current physical mapping, and restore/remove/read-side behavior
- Backend-sensitive observations:
  - snapshot creation still uses optional PostgreSQL `FOR UPDATE` behavior
  - snapshot path resolution relies on portable upsert behavior, while broader
    snapshot mapping behavior remains mixed across packages

## Restore-time mapping

Restore-time mapping is currently split across storage and snapshot layers.

- By-ID restore:
  - current-state restore loads a completed `logical_file` row and reconstructs
    bytes through `file_chunk`, chunk, block, and container metadata
  - this path restores logical content by file ID, not by stored path identity
- Stored-path restore:
  - stored-path restore first resolves a current `physical_file` mapping and
    uses that mapping as the address of the logical file to restore
  - current-state stored-path restore is therefore path-addressed but still
    content-backed once the logical file is resolved
- Snapshot restore:
  - snapshot restore selects normalized `snapshot_path` rows plus
    `logical_file_id`
  - output paths are reconstructed from snapshot-relative path identity rather
    than from current `physical_file.path`
- Output destination modes:
  - snapshot restore and current-state restore both enforce destination rules
  - prefix and override destinations are validated explicitly, and unsafe
    symlink or path-escape behavior is fail-closed
- Fail-closed observations:
  - missing logical file or snapshot selection fails
  - missing exact snapshot path selections fail
  - overwrite rules are enforced at restore-plan execution time
  - restore metadata application is separate from logical content resolution
- Determinism expectations:
  - restore queries rely on ordered file-chunk or snapshot-member traversal
  - snapshot restore keeps ordered path selection and deterministic plan output
- Backend-sensitive observations:
  - ordering, placeholder handling, and row-locking behavior remain relevant
  - packed/legacy block reconstruction and chunk pinning are outside catalog and
    should remain descriptive only in this phase

## Remove-time mapping and retention

Remove-time mapping is defined by current-state logical/physical relationships
plus snapshot-retention refusal logic.

- Remove target identity:
  - remove-by-ID targets a `logical_file` row directly
  - remove-by-stored-path targets a current `physical_file.path`, then resolves
    the owning `logical_file_id`
- Remove-by-stored-path behavior:
  - removing a stored path deletes one current physical mapping
  - it decrements `logical_file.ref_count` and checks that the resulting count
    still matches the number of remaining `physical_file` rows
  - if the path was never stored, the failure is reported at the
    `physical_file[path]` level
- Remove-by-ID behavior:
  - removing by file ID first checks status and snapshot retention
  - it removes all current `physical_file` mappings for the logical file, then
    removes `file_chunk` and `logical_file` metadata
  - this keeps remove-by-ID and remove-by-stored-path semantically aligned on
    current physical mapping cleanup
- Snapshot-retained logical content:
  - both remove modes are blocked when the logical file is retained by one or
    more snapshots
  - retention is about logical content reachability, not just about whether a
    current physical mapping still exists
- Current/live versus snapshot-retained state:
  - a logical file may stop being current-state reachable through
    `physical_file` while still remaining snapshot-retained through
    `snapshot_file`
  - this split is safety-critical for later reachability and GC review
- Unsupported stored-path boundaries:
  - engine candidate contracts still model stored-path restore/remove modes
  - active engine routes treat some stored-path modes as outside the active
    engine path, while the CLI still has direct stored-path execution paths
  - this is a boundary observation, not a Phase 3 migration decision
- Phase 5 follow-up areas:
  - whether current-only versus snapshot-only logical roots are treated
    consistently across remove, retention, and GC
  - how deletion simulation and root exclusion should treat logical files that
    have lost current paths but remain snapshot-retained
  - whether any corrupt/orphan current-path rows could mislead retention safety

## Read-side mapping

Read-side mapping exposure remains primarily observability- and CLI-owned.

- List/search exposure:
  - list/search surfaces still live outside catalog and remain closer to
    current-state file/path behavior
  - Phase 3 treats them as read-side consumers of mapping state, not as owners
    of the mapping contract
- Inspect behavior:
  - `Inspect` supports repository, snapshot, logical-file, chunk, and container
    paths
  - logical-file inspection is active
  - physical-file inspection is still a transitional or unsupported boundary in
    observability/engine tests rather than a full public mapping contract
- Stats behavior:
  - `Stats` delegates to maintenance-derived repository stats and graph
    enrichment
  - reported counts distinguish logical-file totals, physical-file totals, and
    snapshot-retention classifications such as current-only, snapshot-only, and
    shared logical files
- Stored-path-facing CLI exposure:
  - CLI store returns `stored_path`
  - stored-path remove dry-run and live execution both surface path-shaped
    results while anchoring success or failure back to logical-file identity
- Output-shape versus mapping correctness:
  - read-side guards protect field presence, count stability, and route
    boundaries
  - they do not by themselves prove that logical/physical mapping semantics are
    backend-neutral or catalog-owned
- Phase 7 evidence buckets:
  - logical-file inspect semantics
  - physical-file exposure or unsupported-boundary behavior
  - retention-count summaries
  - list/search consistency with path-shaped filters
  - stored-path batch ordering and failure-shape behavior

## Verify, repair, and GC mapping assumptions

Mapping integrity assumptions remain active below the catalog facade.

- Verify checks:
  - verify explicitly checks for orphan `physical_file` rows
  - verify checks for `logical_file.ref_count` mismatches against actual
    `physical_file` row counts
  - verify also treats snapshot-to-logical and file-chunk consistency as part
    of broader repository coherence
- Repair assumptions:
  - refcount repair recomputes `logical_file.ref_count` from current
    `physical_file` rows
  - repair refuses to proceed when orphan `physical_file` rows exist, which
    makes current logical/physical mapping integrity a precondition for repair
- Reachability and GC roots:
  - current logical roots come from `physical_file`
  - snapshot logical roots come from `snapshot_file`
  - catalog and graph reachability both operate in terms of retained logical
    file IDs rather than stored paths
- Invariant/refusal behavior:
  - remove and repair already use invariant-coded refusal paths for retained or
    orphan conditions
  - these refusals depend on the correctness of logical/physical mapping, but
    Phase 3 does not yet decide the GC consequences
- Phase 5 follow-up areas:
  - how current-only, snapshot-only, and shared logical roots should influence
    GC eligibility decisions
  - how orphan `physical_file` rows or refcount drift should affect GC refusal
    safety
  - whether catalog reachability roots, retention helpers, and graph GC roots
    make identical retained-root assumptions
  - how delete simulation should treat logical files that lose current paths but
    remain snapshot-protected

## Backend posture

### Backend-neutral mapping surfaces

- logical identity is expressed through `logical_file` content metadata rather
  than backend-specific row types
- current reachability roots from `physical_file` and snapshot roots from
  `snapshot_file` are logical-file based
- snapshot path resolution uses portable `ON CONFLICT DO NOTHING`
- catalog lookup queries use `$1`-style placeholders and are intended to remain
  portable
- snapshot mapping comparisons are phrased in normalized path plus
  `logical_file_id` terms rather than backend-specific row identity

### Backend-sensitive mapping surfaces

- path collation and case sensitivity can affect path ordering, matching, and
  duplicate interpretation across backends
- LIKE/filter behavior for read-side or path-shaped queries may differ in subtle
  ways across SQLite and PostgreSQL
- NULL/default handling matters for metadata-bearing path rows and optional
  fields such as mtimes and lineage metadata
- JOIN cardinality assumptions matter where logical, physical, snapshot, and
  chunk graphs are aggregated together
- DISTINCT/GROUP BY aggregation differences matter for reachability and
  retention summaries
- ORDER BY determinism matters for snapshot listing, snapshot restore planning,
  and path-oriented read-side output
- `RETURNING`-based insert and claim behavior matters in logical-file and
  snapshot-member creation paths
- FK enforcement differences matter for orphan physical mappings, orphan
  snapshot references, and corruption/refusal behavior
- placeholder/dialect handling stays distributed across catalog, snapshot,
  storage, and tests

### SQLite-specific assumptions, if any

- many focused unit tests and fixtures run on in-memory SQLite
- some setup helpers use SQLite-native conveniences such as `INSERT OR IGNORE`
  or `?` placeholders in test code
- SQLite bootstrap, pragma, and metadata-table inspection remain explicit
  lower-layer concerns outside this mapping review

### PostgreSQL-specific assumptions, if any

- optional `FOR UPDATE` behavior appears in snapshot and remove/store-adjacent
  concurrency paths
- PostgreSQL schema inspection and host-backed validation remain narrower and
  more release-gate-oriented than the SQLite unit-test footprint
- broader PostgreSQL mapping confidence still depends heavily on focused
  backend-contract suites plus final release-gate validation

### Dialect-adapted areas

- backend detection and `QueryWithOptionalForUpdate` behavior adapt locking
  semantics by backend
- repository capability inspection branches by backend metadata tables
- some test/setup paths differ by backend even when production mapping intent is
  the same

### Phase 6 follow-up items

- path collation and case-sensitivity stability for stored-path and
  snapshot-path identity
- LIKE/filter parity for path-oriented read-side queries
- NULL/default handling across physical metadata and snapshot metadata fields
- JOIN/DISTINCT/GROUP BY parity for retention and reachability summaries
- ORDER BY determinism for path-oriented restore, diff, and read-side output
- `RETURNING` and conflict-handling behavior in logical-file and snapshot-path
  insert flows
- FK enforcement differences on orphan or dangling logical/physical mappings
- PostgreSQL-only lock behavior around current-state enumeration and mutation
- release-gate-only PostgreSQL evidence outside the focused contract suites

## Phase 3 findings

### Stable current contract observations

- `logical_file` is the durable content-identity row, while `physical_file`
  represents current-state path ownership.
- one logical file may legitimately have multiple current physical mappings, and
  `ref_count` is the explicit bridge between those layers.
- snapshot state preserves normalized path identity plus logical identity rather
  than persisting `physical_file` row identity.
- current restore/remove/read-side behavior intentionally remains distributed
  across storage, snapshot, observability, engine, and CLI seams rather than a
  single catalog-owned mapping implementation.

### Backend-sensitive observations for Phase 6

- content-claim and snapshot-insert paths rely on conflict-handling and
  `RETURNING` behavior.
- row-locking and optional `FOR UPDATE` behavior affect current-state mapping
  enumeration and mutation safety.
- path ordering, collation, and filter behavior can influence visible mapping
  results.
- aggregate retention/reachability logic depends on JOIN, DISTINCT, GROUP BY,
  and FK behavior below the catalog facade.

### Coverage evidence for Phase 7

- store-time logical identity claim, reuse, and dedup behavior
- current-state physical mapping attachment and replacement behavior
- snapshot path-plus-logical mapping semantics
- restore routing differences between file ID, stored path, and snapshot path
- remove and snapshot-retention refusal behavior
- read-side logical/physical exposure and output-shape guards
- verify/repair/refcount integrity and retained-root summaries
- focused backend parity tests versus release-gate-only PostgreSQL evidence

### Phase 5 follow-up items

- alignment between current-state roots from `physical_file` and
  snapshot-retained roots from `snapshot_file`
- delete and remove behavior when a logical file is no longer current but still
  snapshot-retained
- orphan or refcount-drift handling as GC safety prerequisites
- consistency of retained-root assumptions across retention helpers, catalog
  reachability, graph reachability, and GC planning

### Immediate blockers

None found.

## Phase 3 decision

The current logical/physical mapping contract is broad but reviewable.

No Phase 3 production or test change is required.

`v1.13.6` can proceed to placement and restore-plan catalog contract review in
Phase 4.

Backend parity and test sufficiency remain intentionally deferred to Phases 6
and 7.
