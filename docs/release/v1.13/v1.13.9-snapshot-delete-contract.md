## Purpose

Convert the accepted Phase 1 snapshot-mutation inventory into the exact target
contract for a future engine-owned snapshot delete operation, covering both
read-only preview and live metadata deletion.

This phase is contract-design only. It does not:

- activate `SnapshotDelete`;
- change the active `Engine` interface;
- change CLI parsing, output, SQL, schema, tests, or runtime routing; or
- begin Phase 4 restore-contract work.

## Executive decision

Snapshot delete should later become an honestly engine-owned mutation boundary,
but the target contract must preserve the full Phase 1 behavior freeze.

The final Phase 3 design is:

- `SnapshotDeleteRequest` replaces contradictory `Force` and `DryRun` booleans
  with one explicit mode enum;
- `SnapshotDeleteResult` separates preview and execute honestly through
  `Mode`, `Deleted`, and `Preview`;
- parent state becomes explicit and renderer-neutral instead of exposing
  `sql.NullString`;
- preview counts remain membership/reference metrics only and stay out of any
  reclaim or GC claim;
- warning rendering remains CLI-owned and derives from raw preview child facts;
  and
- execute success must prove that the target snapshot row was actually deleted,
  not merely that a transaction committed.

## Current candidate inventory

Current candidate request:

```go
type SnapshotDeleteRequest struct {
	SnapshotID string
	Force      bool
	DryRun     bool
}
```

Current candidate result:

```go
type SnapshotDeleteResult struct {
	SnapshotID    string
	DryRun        bool
	ParentID      string
	ParentMissing bool
	Children      []string
	TotalFiles    int
	UniqueFiles   int
	SharedFiles   int
	Warnings      []OperationWarning
}
```

Current runtime truth from Phase 1:

- CLI owns `--dry-run`, `--dryRun`, `--force`, preview-wins precedence, and
  explicit-false behavior.
- CLI routes dry-run preview to `snapshotDeleteLineagePreviewPhase`.
- CLI routes live deletion to `deleteSnapshotPhase`.
- preview output includes lineage and membership-reference information.
- live deletion does not load preview data and emits sparse/default
  preview-shaped JSON fields.
- normal parent deletion uses `ON DELETE SET NULL`.
- missing-parent preview is a compatibility state, not the normal consequence
  of current-schema deletion.
- delete is metadata-only, does not remove payload bytes, and does not run GC.
- no active `Engine.SnapshotDelete` method exists.

## Final mode contract

Final enum:

```go
type SnapshotDeleteMode string

const (
	SnapshotDeleteModePreview SnapshotDeleteMode = "preview"
	SnapshotDeleteModeExecute SnapshotDeleteMode = "execute"
)
```

Mode decisions:

- use renderer-neutral values `preview` and `execute`, not CLI flag names;
- `Mode == ""` is an engine request-validation error;
- any unknown mode is an engine request-validation error;
- the engine never receives both preview and execute concepts at once; and
- CLI flag precedence remains outside the engine contract.

## Final request contract

Final request shape:

```go
type SnapshotDeleteRequest struct {
	SnapshotID string
	Mode       SnapshotDeleteMode
}
```

### Request invariants

- `SnapshotID` is required after trimming.
- surrounding whitespace is trimmed before any downstream use.
- whitespace-only direct-engine `SnapshotID` is invalid.
- the result returns the normalized final ID.
- request-only validation completes before any catalog mutation.
- no CLI flag concepts remain in the engine request.

CLI compatibility remains:

- the CLI continues owning flag aliases, preview-wins precedence, arity, and
  explicit-false behavior;
- `--dry-run` and `--dryRun` remain accepted CLI spellings;
- malformed boolean values remain CLI errors before repository initialization;
- blank snapshot ID remains rejected before repository initialization.

## Final result contract

Final result shape:

```go
type SnapshotDeleteParentState string

const (
	SnapshotDeleteParentNone    SnapshotDeleteParentState = "none"
	SnapshotDeleteParentPresent SnapshotDeleteParentState = "present"
	SnapshotDeleteParentMissing SnapshotDeleteParentState = "missing"
)

type SnapshotDeleteParent struct {
	ID    string
	State SnapshotDeleteParentState
}

type SnapshotDeletePreviewResult struct {
	Parent      SnapshotDeleteParent
	Children    []string
	TotalFiles  int64
	UniqueFiles int64
	SharedFiles int64
}

type SnapshotDeleteResult struct {
	SnapshotID string
	Mode       SnapshotDeleteMode
	Deleted    bool
	Preview    *SnapshotDeletePreviewResult
}
```

### Result invariants

Preview success must satisfy:

- `Mode == SnapshotDeleteModePreview`
- `Deleted == false`
- `Preview != nil`

Execute success must satisfy:

- `Mode == SnapshotDeleteModeExecute`
- `Deleted == true`
- `Preview == nil`

Invalid combinations must never be returned.

`Deleted` is retained explicitly because:

- preview success must never imply mutation;
- execute success must be commit-truthful; and
- later CLI translation can preserve sparse live JSON without fabricating a
  preview result.

## Parent-state contract

Parent state is explicit and renderer-neutral:

- `SnapshotDeleteParentNone`
  - `Parent.ID == ""`
  - no recorded parent
- `SnapshotDeleteParentPresent`
  - `Parent.ID != ""`
  - recorded parent row exists
- `SnapshotDeleteParentMissing`
  - `Parent.ID != ""`
  - a parent ID is recorded but the row is absent

Contract decisions:

- missing-parent remains a compatibility state for legacy or deliberately
  malformed metadata;
- missing-parent must not be described as the normal outcome of current-schema
  parent deletion;
- preview exposes sorted child IDs;
- execute does not load or return child IDs; and
- the engine result must not expose `sql.NullString`.

Current-schema live deletion semantics remain:

- child snapshots survive;
- child `parent_id` becomes `NULL`;
- children become lineage roots; and
- no child snapshot membership is deleted.

## Preview count contract

`TotalFiles`:

- number of `snapshot_file` membership rows for the target snapshot

`UniqueFiles`:

- number of target membership rows whose `(path_id, logical_file_id)` pair
  appears in no other snapshot

`SharedFiles`:

- `TotalFiles - UniqueFiles`

Count decisions:

- all count fields use `int64`;
- counts are membership/reference facts only;
- counts are not reclaim estimates, payload-uniqueness claims, or GC metrics;
- all counts must be non-negative;
- `UniqueFiles <= TotalFiles`; and
- `SharedFiles` must match `TotalFiles - UniqueFiles`.

No separate SQL query is justified solely for shared count.

## Warning ownership

Delete warnings do not belong in the future engine result.

Final decision:

- remove speculative delete-result `Warnings` from the target contract;
- return raw deterministic facts through `Preview.Children`;
- keep current preview warning rendering in the CLI/renderer layer; and
- preserve the current JSON warning shape from raw child facts.

Semantic warning condition:

- `len(Preview.Children) > 0`

Current rendered warning truth that must remain reproducible later:

- type: `lineage_breakage`
- message: lineage-visualization breakage warning
- details.affected_snapshots: child snapshot IDs
- details.note: children remain fully usable

## Preview contract

Preview is a read-only catalog operation.

It must not:

- call live delete execution;
- delete `snapshot_file` rows;
- delete snapshot rows;
- mutate lineage;
- remove `snapshot_path` rows;
- change logical or physical file metadata;
- delete payload bytes;
- run GC;
- alter retention state; or
- create repair or recovery state.

Dependency boundary:

- catalog DB only

It must not require:

- storage writer
- storage reader
- container directory
- chunker
- codec
- encryption key
- filesystem mutation

### Preview consistency

Current implementation uses independent DB reads rather than one transactionally
stable catalog view.

Target design decision:

- preview fields should describe one internally coherent catalog view when
  feasible;
- prefer one read-only transaction or backend-equivalent stable read scope;
- do not redesign repository-wide mutation locking; and
- if a coherent read scope cannot be added without disproportionate churn, the
  weaker guarantee must be documented explicitly and backed by a regression
  note rather than overstated as atomic.

## Execute contract

Live execute owns snapshot metadata deletion only.

The committed transaction must cover:

1. transactionally relevant target existence validation;
2. deletion of target `snapshot_file` rows;
3. deletion of the target `snapshot` row;
4. foreign-key `ON DELETE SET NULL` handling for children; and
5. commit.

After success:

- the target snapshot row is absent;
- the target snapshot membership rows are absent;
- child snapshots remain and become lineage roots if they depended on the
  deleted parent;
- payload bytes remain;
- logical files remain;
- other snapshots remain protective;
- current-state ownership remains protective;
- no GC has run; and
- no reclaimed-space promise is made.

Compatibility decision:

- `snapshot_path` orphan cleanup stays out of scope for snapshot delete in
  `v1.13.9`.

## Honest execute success

Current runtime sequence is:

```text
existence check
begin transaction
delete snapshot_file
delete snapshot
commit
```

This is not an honest enough future contract if the snapshot disappears between
the precheck and the delete.

Final decision:

- execute must check the affected-row count of the snapshot-row delete;
- `Deleted == true` is valid only when the snapshot-row delete affected one row
  and commit succeeded;
- zero affected rows becomes not-found or concurrent-disappearance behavior;
- commit success alone is insufficient to claim deletion; and
- no partial membership deletion may commit when the snapshot row was not
  deleted.

## Domain adaptation strategy

### Preview

Smallest honest migration:

- preserve a domain preview loader;
- translate its result into renderer-neutral engine types;
- convert parent state away from `sql.NullString`;
- copy child slices before returning them; and
- preserve sorted child ordering and `int64` counts.

### Execute

Smallest honest migration:

- add a result-returning delete core;
- keep an error-only compatibility wrapper while direct callers still exist;
- future engine activation uses the result-returning core;
- do not duplicate delete SQL inside the engine; and
- do not run a post-delete preview query just to enrich execute output.

No callback or mutable output-parameter pattern is needed.

## Validation ordering

Target validation order:

| Validation | Owner | Requires DB | Requires transaction | Before mutation | Compatibility note |
|---|---|---:|---:|---:|---|
| CLI arity, unknown flags, malformed bools, aliases | CLI | no | no | yes | unchanged |
| CLI preview-wins precedence | CLI | no | no | yes | unchanged |
| CLI neither-mode / explicit-false behavior | CLI | no | no | yes | unchanged |
| Engine mode validation | engine | no | no | yes | new internal contract |
| Engine snapshot-ID trimming and empty check | engine | no | no | yes | normalized ID |
| Preview target lookup | domain | yes | preferably yes | yes | preserve current not-found substring |
| Preview missing-parent detection | domain | yes | same read scope | yes | compatibility-only state |
| Preview count invariant checks | domain/engine | yes | same read scope | yes | deterministic |
| Execute target existence and delete truth | domain | yes | yes | yes | must be transactionally honest |
| Execute affected-row check | domain | yes | yes | yes | no false success |
| Commit failure handling | domain | yes | yes | n/a | error only |

## Error contract

Phase 3 does not introduce a broad new error framework.

Preserve useful wrapped causes and stable substrings across these categories:

- request validation
  - origin: CLI or engine
  - no mutation begun
- snapshot not found
  - preserve `snapshot "<id>" not found`
- preview lookup/query failure
  - preserve layer-specific context
- begin transaction
  - preserve `begin snapshot delete transaction:`
- membership delete failure
  - preserve `delete snapshot_file rows snapshot_id=...`
- snapshot-row delete failure
  - preserve `delete snapshot row id=...`
- concurrent disappearance / zero affected rows
  - no success result
  - later activation may choose narrow classification if needed
- commit failure
  - preserve `commit snapshot delete transaction:`
- context cancellation and backend/runtime failures
  - preserve wrapped driver/runtime causes

Typed or sentinel errors are optional and should be added only if later routing
proves a concrete need, especially for invalid mode or not-found
classification.

- `--dry-run`

- `action: "delete_dry_run"`
- `snapshot_id: normalized ID`
- `dry_run: true`
- `parent_id: null|string`
- `parent_missing: bool`
- `children: []` when preview loaded and there are no children
- `total_files: int64-backed JSON number`
- `unique_files: int64-backed JSON number`
- `shared_files: int64-backed JSON number`
- `warnings: current rendered warning array or null`
- `duration_ms: CLI-owned`

Execute JSON translation target:

- `action: "delete"`
- `snapshot_id: normalized ID`
- `dry_run: false`
- `parent_id: null`
- `parent_missing: false`
- `children: null`
- `total_files: 0`
- `unique_files: 0`
- `shared_files: 0`
- `warnings: null`
- `duration_ms: CLI-owned`

Nil and empty-shape compatibility that must remain reproducible:

- preview with no children emits `children: []`;
- execute emits `children: null`;
- preview with no warnings emits `warnings: null`;
- execute emits `warnings: null`.

The engine contract must contain enough raw information to let the CLI preserve
this shape without issuing extra preview queries during execute.

## Security and correctness review

This target contract prevents or constrains the key risks:

- contradictory preview and execute requests cannot be represented;
- execute without explicit mode cannot be represented;
- preview cannot honestly report mutation success;
- execute cannot honestly claim preview metrics it did not compute;
- successful execute cannot be reported when no snapshot row was deleted;
- child snapshots cannot be cascade-deleted by contract;
- payload deletion and hidden GC are not implied;
- reclaim promises are not inferred from membership counts;
- `database/sql` types do not leak into the engine boundary;
- renderer-specific warnings do not leak into the engine contract;
- mutable child slices do not escape the engine boundary; and
- delete does not gain storage or codec dependencies.

Phase 3 does not justify redesigning repository mutation locking.

The required correctness improvement is explicit affected-row and commit-truth
honesty, not a broader serialization redesign.
