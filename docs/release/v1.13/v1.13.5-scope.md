# Coldkeep v1.13.5 Scope

**Release:** `v1.13.5 — Release Record Closure and Engine-Level Invariant Ownership`
**Branch:** `release/v1.13.5`
**Status:** Open

## Purpose

`v1.13.5` closes the `v1.13.4` post-release record gap and reviews
engine-level validation and invariant ownership for active engine-facing
operations.

The release is narrow and correctness-focused. It should strengthen
documentation and targeted guard coverage without broad routing migration or
public behavior changes.

## Why this release exists

`v1.13.4` completed the read-side dependency-direction review and added narrow
read-side guard tests.

After release, the final `v1.13.4` tree also included two narrow production
hardenings:

- database environment integer parsing hardening in `internal/db/db.go`
- `verify file` fileID bounds validation in `cmd/coldkeep/main.go`

`v1.13.5` starts by closing that release-record gap, then proceeds into the
next `v1.13.x` concern: making sure validation and invariant ownership are
correctly documented and guarded below CLI-only paths where appropriate.

## Reviewed surfaces

`v1.13.5` may review:

- `Verify`
- `Remove`
- `Restore`
- `Stats`
- `Inspect`
- `SnapshotShow`
- `SnapshotDiff`
- GC / maintenance invariant propagation

## Primary goals

- close stale `v1.13.4` post-release documentation
- record final `v1.13.4` production hardening honestly
- inventory validation ownership across active engine-facing paths
- distinguish CLI-only validation from engine-owned validation
- distinguish engine request validation from domain invariant enforcement
- review invariant error propagation
- add only narrow guard tests if existing coverage is insufficient
- preserve SQLite and PostgreSQL compatibility

## Non-goals

`v1.13.5` must not introduce:

- broad read-side routing migration
- unified read-side result abstraction
- unified JSON envelope abstraction
- engine-owned inspect migration unless explicitly proven narrow and
  behavior-preserving
- full `snapshot show` consolidation
- full `snapshot diff` query/result migration
- restore/remove stored-path expansion
- snapshot mutation routing
- repair/recovery routing migration
- catalog facade rewrite
- schema or migration changes
- storage or repository format changes
- backend default changes
- SQLite-only assumptions
- PostgreSQL compatibility removal
- daemon/API/UI/v2 work

## Compatibility constraints

Preserve:

- CLI behavior
- human output
- JSON output
- JSON error envelopes
- exit codes
- command routing
- engine routing unless explicitly scoped and guarded
- schema/migrations
- storage format
- repository format
- backend defaults
- SQLite compatibility
- PostgreSQL compatibility

## Release success criteria

`v1.13.5` is successful if:

- `v1.13.4` release records are historically accurate
- engine-level validation and invariant ownership are documented
- any new tests map directly to documented gaps
- no public behavior changes are introduced
- PostgreSQL-backed validation remains part of the final release gate
- `PRE_RELEASE_CHECKLIST.md Profile A` passes before PR opening
