## 1. `stats`

### Current flow

Production flow:

`runStatsCommand` -> CLI flag validation and trace parsing ->
`runObservabilityStatsPhase` -> engine `Stats` ->
observability `Stats` -> renderer

Observed current path details:

- CLI entrypoint is `runStatsCommand` in `cmd/coldkeep/main.go`
- CLI parsing and validation stay in `cmd/coldkeep` via
  `ensureAllowedFlags`, positional count checks, `resolveTraceOptions`, and
  `--containers`
- `runObservabilityStatsPhase` loads the default storage context, constructs
  the engine, calls `eng.Stats`, and returns `result.Raw`
- engine `Stats` is active in production and wraps observability
- observability `Service.Stats` owns the concrete read logic and maps
  maintenance output into `observability.StatsResult`
- `resolveRenderer(outputMode)` chooses the renderer
- both human and JSON stats rendering are provided by `internal/cli/render`
- JSON success output is emitted by the renderer, not assembled in the CLI
- JSON error output is still CLI-owned through `observabilityWrappedError`

### Current ownership

| Concern | Current owner | Notes |
| --- | --- | --- |
| CLI parsing | `cmd/coldkeep` | `runStatsCommand` parses flags, trace options, and positional usage |
| CLI validation | `cmd/coldkeep` | allowed-flags checks, positional count checks, trace-option validation |
| Engine entrypoint | `internal/engine` | `eng.Stats` is active in production via `runObservabilityStatsPhase` |
| Core read logic | `internal/observability` | `Service.Stats` owns the concrete aggregate read path |
| Result type | mixed: engine wrapper over observability result | `engine.StatsResult` contains `Raw *observability.StatsResult` |
| Human rendering | `internal/cli/render` | `HumanRenderer.RenderStats` renders observability-shaped stats |
| JSON success output | `internal/cli/render` | `JSONRenderer.RenderStats` owns the JSON success envelope |
| JSON error output | `cmd/coldkeep` | CLI wraps failures with `observabilityWrappedError` |
| Backend access | engine -> observability -> maintenance/db | active path reaches DB through observability and maintenance |
| Taxonomy boundary | mixed CLI/engine test protection | protected by read-side taxonomy tests, not a dedicated stats taxonomy layer |

## 2. `inspect`

### Current flow

Production flow:

`runInspectCommand` -> CLI validation and supported-target mapping ->
direct `runObservabilityInspectPhase` -> observability service -> renderer

Observed current path details:

- CLI entrypoint is `runInspectCommand` in `cmd/coldkeep/main.go`
- CLI parsing and validation stay in `cmd/coldkeep`, including:
  - allowed-flag validation
  - supported-target mapping
  - repository-versus-ID arity rules
  - numeric-ID validation for `file`, `chunk`, and `container`
  - `--limit` parsing
  - trace-option parsing
- supported CLI targets are:
  - `repository`
  - `file`
  - `logical-file`
  - `snapshot`
  - `chunk`
  - `container`
- production `runObservabilityInspectPhase` explicitly bypasses engine and
  constructs the observability service directly
- engine `InspectRequest` and `InspectResult` exist, and engine `Inspect` is
  implemented, but it is not the active production owner
- observability `Service.Inspect` owns the concrete read logic and concrete
  result type
- renderer selection is CLI-owned through `resolveRenderer(outputMode)`
- JSON success output is emitted by the renderer, not assembled in the CLI
- JSON error output remains CLI-owned with explicit `NOT_FOUND`,
  `INVALID_ARGUMENT`, and internal-failure mapping

### Current ownership

| Concern | Current owner | Notes |
| --- | --- | --- |
| CLI parsing | `cmd/coldkeep` | `runInspectCommand` parses entity, ID, limit, trace, and flags |
| CLI validation | `cmd/coldkeep` | supported-target validation, arity validation, numeric-ID validation |
| Engine entrypoint | `internal/engine` exists but is inactive in production | engine inspect wrappers exist but the production path bypasses them |
| Core read logic | `internal/observability` | `Service.Inspect` owns repository/file/snapshot/chunk/container inspection |
| Result type | `internal/observability` in production | concrete result is `observability.InspectResult`; engine wrapper is unused by CLI |
| Human rendering | `internal/cli/render` | `HumanRenderer.RenderInspect` renders observability-shaped inspect results |
| JSON success output | `internal/cli/render` | `JSONRenderer.RenderInspect` owns the JSON success envelope |
| JSON error output | `cmd/coldkeep` | CLI maps not-found and invalid-argument failures explicitly |
| Backend access | CLI -> observability -> DB reads | production path reaches DB through observability service queries |
| Taxonomy boundary | mixed CLI/engine test protection | protected by CLI and engine boundary tests, not a dedicated inspect taxonomy layer |

## 3. `snapshot show`

### Current flow

Production flow:

`runSnapshotShowCommand` -> CLI flag/query parsing -> `getSnapshotPhase`
metadata lookup -> `listSnapshotFilesPhase` file listing ->
`snapshotStatsPhase` stats lookup -> CLI JSON assembly or human renderer

Observed current path details:

- CLI entrypoint is `runSnapshotShowCommand` in `cmd/coldkeep/main.go`
- CLI parsing and validation stay in `cmd/coldkeep`, including:
  - allowed-flag validation
  - positional arity validation
  - `snapshotID` trimming and empty check
  - non-negative `--limit` validation
  - `parseSnapshotQuery` ownership of query parsing
- metadata is fetched through `getSnapshotPhase`, which remains a direct CLI
  helper seam rather than a renderer concern
- file listing uses `listSnapshotFilesPhase`, which points at
  `snapshot.ListSnapshotFiles`
- stats lookup uses `snapshotStatsPhase`, which currently constructs the engine,
  calls `eng.SnapshotStats`, and reprojects the result into
  `snapshot.SnapshotStats`
- JSON success payload is assembled directly in the CLI
- human output is delegated to `clirender.RenderSnapshotShowHuman`
- JSON error behavior remains CLI-owned by propagated errors from the mixed
  metadata/file/stats path

### Current ownership

| Concern | Current owner | Notes |
| --- | --- | --- |
| CLI parsing | `cmd/coldkeep` | `runSnapshotShowCommand` parses limit, query flags, and output mode |
| CLI validation | `cmd/coldkeep` | usage validation, non-negative limit validation, empty-ID checks |
| Engine entrypoint | mixed | engine is active only through `snapshotStatsPhase`, not for metadata or file listing |
| Core read logic | mixed catalog/snapshot/CLI helpers | metadata uses `getSnapshotPhase`, file listing uses `snapshot.ListSnapshotFiles`, stats use engine-backed reprojection |
| Result type | mixed snapshot/package shapes | metadata is `snapshot.Snapshot`, files are `[]snapshot.SnapshotFileEntry`, stats are reprojected to `*snapshot.SnapshotStats` |
| Human rendering | `internal/cli/render` | `RenderSnapshotShowHuman` owns human output |
| JSON success output | `cmd/coldkeep` | CLI assembles the success envelope and field set |
| JSON error output | `cmd/coldkeep` | errors propagate through CLI-owned command path |
| Backend access | mixed catalog/snapshot/engine seams | metadata, files, and stats touch different package owners over the same DB |
| Taxonomy boundary | mixed CLI/engine test protection | protected by read-side boundary tests without a dedicated snapshot-show taxonomy layer |

## 4. `snapshot diff`

### Current flow

Production flow:

`runSnapshotDiffCommand` -> CLI ID/filter/query parsing -> summary fast path or
detailed/general path

Summary fast path:

- CLI chooses the fast path when `--summary` is used with no `--filter` and no
  query
- `diffSnapshotSummaryPhase` constructs engine `SnapshotDiffRequest` in summary
  mode and calls engine `SnapshotDiff`
- engine summary routing uses `snapshot.DiffSnapshotsSummarySQL`
- CLI assembles the summary JSON envelope or uses
  `RenderSnapshotDiffSummaryHuman`

Detailed/general path:

- CLI parses query flags through `parseSnapshotQuery`
- `diffSnapshotsPhase` maps CLI query data into engine `SnapshotDiffRequest`
- engine detailed routing delegates to snapshot package diff logic through
  `snapshot.DiffSnapshots`
- CLI performs `--filter` post-processing over the returned entries
- CLI recomputes matched summary counts after filtering
- CLI owns JSON assembly for `entry_count`, `matched_entry_count`,
  `total_diff_entry_count`, `summary_mode`, and whether `entries` are omitted
- human output uses either `RenderSnapshotDiffSummaryHuman` or
  `RenderSnapshotDiffDetailedHuman`

### Current ownership

| Concern | Current owner | Notes |
| --- | --- | --- |
| CLI parsing | `cmd/coldkeep` | base/target IDs, `--summary`, `--filter`, and query flags are CLI-owned |
| CLI validation | `cmd/coldkeep` | usage validation, empty-ID checks, filter validation, query validation |
| Engine entrypoint | `internal/engine` | engine `SnapshotDiff` is active through both summary and detailed helper phases |
| Core read logic | mixed engine/snapshot/CLI | engine routes summary and detailed modes; detailed work delegates to snapshot diff helpers; CLI still post-processes filters and counts |
| Result type | mixed engine and snapshot shapes | engine returns engine diff results inside helper phases; CLI reprojects to snapshot-owned entries and summary values |
| Human rendering | `internal/cli/render` | summary and detailed human rendering are renderer-owned |
| JSON success output | `cmd/coldkeep` | CLI assembles diff success envelopes and field-shape decisions |
| JSON error output | `cmd/coldkeep` | errors propagate through CLI-owned command path |
| Backend access | engine -> snapshot package -> DB | summary fast path uses SQL-only summary helper; detailed path uses snapshot diff logic |
| Taxonomy boundary | mixed CLI/engine test protection | protected by CLI and engine read-side boundary tests, not by a dedicated diff taxonomy layer |

## Closing summary

Current baseline after `v1.13.3` and Phase 0 of `v1.13.4`:

- `stats`: engine-wrapped but observability-result-owned
- `inspect`: direct CLI-to-observability path remains active
- `snapshot show`: mixed ownership remains active
- `snapshot diff`: mixed CLI/engine/snapshot ownership remains active

All four surfaces remain candidates for later `v1.13.4` ownership decisions.

This Phase 1 inventory does not recommend a migration. It records the current
state so later phases can make narrow, evidence-backed decisions without
accidentally broadening the release into a routing refactor.
