# v1.13.1 Boundary Summary

## Release Name

`v1.13.1 — Explicit Deferred-Contract Boundaries`

## Release Objective

`v1.13.1` exists to make deferred, partial, candidate-only, and misleading engine/catalog
boundaries explicit and safe before later `v1.13.x` releases continue contract cleanup.

`v1.13.1` is a boundary-hardening release, not an implementation or migration release.

It does not claim engine completeness, catalog completeness, broad routing progress, or migration
progress. It turns ambiguous support surfaces into explicit boundaries so later releases can build
on honest constraints instead of guessed ownership.

## Completed Phases

- Phase 0: baseline scope, phase, and validation docs created
- Phase 1: 37 explicit boundary targets mapped into the release target matrix
- Phase 2: active unsupported engine modes locked behind explicit unsupported tests
- Phase 3: deferred catalog methods locked behind explicit deferred-method tests
- Phase 4: candidate-only engine operation contracts marked and guarded as future-facing only
- Phase 5: partial engine routing seams made explicit and test-protected
- Phase 6: request/result support-surface limitations clarified and shape-tested
- Phase 7: CLI transitional ownership preserved and test-protected
- Phase 8: boundary summary and `v1.13.2` handoff recorded

## Boundary Target Summary

`v1.13.1` carried forward the Phase 1 result: the release had 37 explicit boundary targets.

Later phases hardened those targets. They did not expand architecture scope, activate deferred
operations, route new workflows through engine, or claim broader implementation ownership.

## What Was Made Explicit

### Explicit Unsupported Engine Modes

- recursive `Engine.Store` is unsupported and must fail explicitly
- stored-path `Engine.Restore` is unsupported and must fail explicitly
- stored-path `Engine.Remove` is unsupported and must fail explicitly
- stored-paths `Engine.Remove` is unsupported and must fail explicitly

These modes are now documented and test-backed as unsupported engine boundaries rather than latent
or downgraded support.

### Deferred Catalog Surfaces

The exported-but-deferred catalog surfaces remain explicit deferred boundaries:

- snapshot graph
- chunk placement loading
- restore-plan metadata loading
- GC-plan metadata loading

These methods remain exported contract surfaces, but `v1.13.1` makes it explicit that export
status is not proof of implemented catalog ownership.

### Candidate-Only Engine Contracts

The following engine request/result families remain future-facing candidate contracts only:

- snapshot create
- snapshot delete
- snapshot restore
- repair
- recover

Their type presence no longer implies active engine ownership. They remain placeholders for later
release work rather than live engine operation contracts.

### Partial Routing Boundaries

The following mixed or split ownership seams are now explicit:

- `inspect`: engine method exists, but CLI inspect still uses direct observability ownership
- `snapshot show`: metadata, listing, and stats remain mixed across seams
- `snapshot diff`: CLI query richness still narrows before the engine seam
- `restore`: by-ID routing differs from stored-path routing
- `remove`: by-ID routing differs from stored-path and stored-paths routing

These surfaces no longer silently imply complete engine-owned workflows.

### Request and Result Support-Surface Limits

`v1.13.1` also made explicit that several request/result shapes remain narrower or more provisional
than their exported fields might suggest, including:

- `StoreRequest`
- `RestoreRequest`
- `RemoveRequest`
- `SnapshotQuery`
- `SnapshotListRequest`
- `SnapshotListResult`
- `SnapshotShowResult`
- `SnapshotDiffRequest`
- `SnapshotDiffResult`
- `VerifyResult`

The key clarification is that current request/result shape must not be read as proof of broad
support, full routing ownership, or stable daemon/API-ready contract completeness.

### CLI-Owned Transitional Paths

The following paths remain intentionally CLI/domain-owned in `v1.13.1`:

- snapshot create
- snapshot delete
- snapshot restore
- repair
- doctor/recovery

`v1.13.1` made that ownership explicit instead of allowing those flows to look like “almost
engine-owned” behavior.

## What Was Test-Protected

### Engine Unsupported Boundary Proof

`v1.13.1` added focused engine tests proving that unsupported active engine modes:

- fail with `ErrNotImplemented`
- do not silently downgrade
- do not report success
- do not obviously mutate repository state

### Catalog Deferred-Method Proof

`v1.13.1` added focused catalog tests proving that deferred catalog methods:

- fail explicitly with the existing deferred/not-implemented error
- return nil rather than zero-value success
- do not obviously mutate catalog state
- remain consistent through the existing backend parity harness

### Candidate-Only Guardrails

`v1.13.1` added engine guardrail tests proving that candidate-only operations are not exposed as
active `engine.Engine` methods.

### Partial-Routing Seam Proof

`v1.13.1` added command-path seam tests proving that partial routes remain partial and should not
be mistaken for complete engine ownership.

### Request/Result Shape Proof

`v1.13.1` added focused tests proving:

- empty snapshot query handling remains explicit
- current engine snapshot query shape carries only one exact path and one prefix
- snapshot diff summary mode and detailed mode remain intentionally distinct
- `VerifyResult` remains a minimal placeholder

### CLI Ownership-Preservation Proof

`v1.13.1` added preservation tests proving that stored-path restore/remove, snapshot mutation,
repair, and doctor/recovery paths still intentionally execute through their current CLI/domain
owners rather than silently becoming new engine routes.

## What Remains Intentionally Incomplete

### CLI or Domain-Owned Paths Still Outside Engine

The following areas remain intentionally outside active engine ownership:

- stored-path restore
- stored-path remove
- stored-paths remove
- snapshot create/delete/restore
- repair
- doctor/recovery

### Candidate-Only Contracts Still Future-Facing

The following surfaces remain candidate-only rather than active engine contracts:

- snapshot create/delete/restore engine contracts
- repair engine contracts
- recover engine contracts
- adjacent simulation and benchmark/tooling surfaces

### Deferred Catalog Ownership Still Unimplemented

The following catalog ownership areas remain deferred:

- snapshot graph behavior
- placement behavior
- restore-plan behavior
- GC-plan behavior

### Partial or Provisional Engine Contracts Still Await Cleanup

The following boundaries still need later release cleanup rather than being considered complete in
`v1.13.1`:

- `inspect` read-side ownership
- `snapshot show` mixed ownership
- `snapshot diff` narrowed request seam
- restore/remove by-ID versus stored-path contract split
- provisional request/result support surfaces
- error taxonomy distinction between unsupported, validation, invariant, domain, and runtime
  failures

## No-Behavior-Change Statement

Phase 8 itself is documentation-only.

Across `v1.13.1`, the release stayed within its narrow boundary-hardening scope. It did not
implement unsupported engine functionality, broad engine routing, new catalog behavior, CLI
behavior changes, JSON output changes, exit-code changes, schema or migration changes, storage
format changes, repository format changes, default backend behavior changes, CI behavior changes,
or script changes.

## Compatibility Statement

`v1.13.1` preserved repository, storage, schema, migration, and backend compatibility
expectations.

`v1.13.1` also preserved current SQLite/PostgreSQL compatibility expectations. It did not remove
PostgreSQL compatibility or narrow the release to SQLite-only support claims.

## v1.13.2 Handoff

`v1.13.2` should use `v1.13.1` as the boundary baseline for engine error taxonomy work.

Its focus should be:

- define a stable engine error taxonomy baseline
- classify unsupported, deferred, validation, domain, invariant, and runtime failures clearly
- keep `ErrNotImplemented` distinct from validation failure and runtime failure
- avoid broad routing changes while error semantics are being stabilized
- avoid CLI behavior drift
- preserve JSON output and exit-code behavior
- prepare later releases to route or split contracts safely without guessing which surfaces are
  truly unsupported

The key `v1.13.1` handoff is simple: unsupported, partial, candidate-only, and deferred surfaces
are now explicit enough that `v1.13.2` no longer needs to infer which boundaries are really
unsupported.

## v2.0 Warning

`v1.13.1` did not claim engine completeness.

`v1.13.1` did not claim catalog completeness.

`v2.0` must not infer readiness from exported request/result shapes, exported deferred methods,
partial routes, candidate-only contracts, or CLI-owned transitional flows alone.

`v1.13.12` remains the readiness gate for any honest `v2.0` handoff.
