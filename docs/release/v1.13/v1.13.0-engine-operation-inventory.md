# v1.13.0 Engine Operation Inventory

## Purpose

This document inventories the current engine operation surface after v1.12.3. It is descriptive
only. It does not claim behavior ownership beyond what the current CLI paths and `internal/engine`
implementation prove today.

Conservative rule used here:

- `implemented`: active engine method exists and the related CLI path routes through it without
  obvious direct CLI-owned execution fallback for the same operation variant.
- `partial`: active engine method exists, but important command variants, query handling, or
  execution orchestration still remain CLI- or domain-owned.
- `deferred`: the active engine surface exists but explicitly returns `ErrNotImplemented` for the
  relevant operation variant.
- `candidate`: request/result contract exists, but there is no active engine interface method and no
  CLI routing through engine for the operation.
- `unclear`: evidence is incomplete or mixed enough that ownership should not be claimed yet.

## Key Findings

1. The active engine interface currently covers 11 methods: `Stats`, `Inspect`, `Verify`,
   `SnapshotList`, `SnapshotShow`, `SnapshotStats`, `SnapshotDiff`, `GarbageCollect`, `Store`,
   `Restore`, and `Remove`.
2. Only 4 operations are conservative `implemented` end-to-end today: `Stats`, `GarbageCollect`,
   `SnapshotList`, and `SnapshotStats`.
3. `Inspect` still bypasses the engine entirely in the CLI even though `DefaultEngine.Inspect`
   exists.
4. `Verify` executes through engine, but CLI still owns the verification-summary query path, so it
   is not fully engine-owned.
5. `Store`, `Restore`, and `Remove` are all split by mode. The routed engine path covers only the
   safer/narrower variants; folder store and stored-path variants stay direct.
6. `SnapshotShow` is only partially routed. The CLI uses engine for snapshot metadata but still
   calls `snapshot.ListSnapshotFiles` directly and separately queries stats.
7. `SnapshotDiff` is not fully aligned with current CLI query semantics. The CLI parser accepts
   repeatable `--path` and `--prefix`, while the engine seam currently forwards only a single
   `Path` and a single `Prefix`.
8. `SnapshotCreate`, `SnapshotDelete`, `SnapshotRestore`, `Repair`, and `Recover` have engine
   contracts but no active engine methods or CLI routing.
9. `SimulateGC` and benchmark/determinism flows are explicitly absent from the engine interface
   today and remain CLI/service-level operations.

## Known Direct CLI / Domain Coupling Worth Watching

- `coldkeep inspect` still calls the observability service directly instead of `engine.Inspect`.
- `coldkeep snapshot show` splits execution across engine and direct snapshot package calls.
- `coldkeep snapshot diff` uses engine, but the request adaptation does not fully preserve the CLI's
  repeatable query flags.
- `coldkeep snapshot create` performs direct snapshot mutation and then direct SQL counting from the
  CLI path.
- `coldkeep snapshot delete` and `coldkeep snapshot restore` remain entirely direct-wired.
- `coldkeep repair`, startup recovery, and `coldkeep doctor` still live outside the engine surface.

## Scope Reminder

This inventory is a baseline only. It does not recommend changing behavior in v1.13.0, and it does
not claim engine ownership where the current CLI still performs direct orchestration.
