# Coldkeep v1.13.2 — Current Error-Surface Inventory

## Status

`complete`

## Purpose

This document inventories the current error-producing surfaces relevant to the
`v1.13.2` engine and catalog error-taxonomy baseline.

This is not implementation work.

This is not behavior migration.

This is not a claim that all surfaces are already cleanly classified.

This inventory is input for Phases 2 through 7.

## Scope

Packages and directories inspected:

- `internal/engine`
- `internal/catalog`
- `cmd/coldkeep`
- `internal/storage`
- `internal/snapshot`
- `internal/maintenance`
- `internal/recovery`
- `internal/verify`
- `internal/observability`
- `internal/cli/render`

The original discovery prompt referenced `internal/clirender`; that directory
does not exist in this repo. The actual CLI rendering package is
`internal/cli/render`.

## Discovery Commands

Main discovery command families used:

```bash
rg -n "ErrNotImplemented|not implemented|unsupported|deferred" internal/engine internal/catalog cmd/coldkeep internal/storage internal/snapshot internal/maintenance internal/recovery internal/verify internal/observability
rg -n "fmt\\.Errorf|errors\\.New|errors\\.Join|errors\\.Is|errors\\.As|wrap|%w" internal/engine internal/catalog cmd/coldkeep internal/storage internal/snapshot internal/maintenance internal/recovery internal/verify internal/observability
rg -n "usageError|validation|invalid|missing|required|must|cannot|failed|not found|mismatch|invariant|corrupt|integrity|permission denied|context canceled" internal/engine internal/catalog cmd/coldkeep internal/storage internal/snapshot internal/maintenance internal/recovery internal/verify internal/observability
rg -n "error_class|exit_code|render.*Error|classifyExitCode|ExitCode|usage" cmd/coldkeep internal/cli internal/clirender internal/engine internal/catalog
```

Summary of discovery results:

- Explicit unsupported or deferred sentinels already exist in `internal/engine`
  and `internal/catalog` via separate `ErrNotImplemented` values.
- CLI validation and exit-code translation are concentrated in
  `cmd/coldkeep/main.go`, with both typed classification and narrow message
  fallback matching.
- `internal/verify` already exposes machine-readable category strings and a
  typed `VerifyFailure` wrapper, but not sentinel errors for those categories.
- `internal/invariants` already exposes machine-readable invariant errors via
  `errors.As`, and some engine and maintenance flows already preserve those
  codes.
- `internal/observability` already has typed sentinels for unsupported entity,
  invalid target, and not-found target cases.
- `internal/clirender` was requested in the prompt but is absent; the actual
  renderer package is `internal/cli/render`.

## Engine Surfaces

### `engine.ErrNotImplemented`

- Defined in `internal/engine/engine.go` as a sentinel error with the message
  `"engine operation not implemented"`.
- Current behavior is explicit unsupported behavior for engine methods that are
  not active yet, not generic validation failure.
- `errors.Is(err, engine.ErrNotImplemented)` is expected to work today and is
  already relied on by existing engine tests.
- Phase 2 should define the taxonomy meaning of this sentinel without changing
  its current behavior.
- Deeper implementation ownership stays with later releases, not `v1.13.2`
  Phase 1.

### Recursive store

- `DefaultEngine.Store` returns `ErrNotImplemented` when `StoreRequest.Recursive`
  is true.
- Current mechanism is sentinel-based unsupported behavior, not a usage or
  validation failure.
- Existing tests already assert `errors.Is` and no-obvious-mutation behavior.
- Preliminary classification candidate: `Unsupported`.
- Real folder-store implementation remains outside the current release scope.

### Stored-path restore

- `validateRestoreRequest` in
  `internal/engine/default_engine_routing_helpers.go` returns
  `ErrNotImplemented` for any mode other than `RestoreModeFileIDs`.
- Current mechanism is sentinel-based unsupported engine routing for the
  stored-path seam.
- `errors.Is(err, engine.ErrNotImplemented)` should work today and is covered by
  tests.
- Preliminary classification candidate: `Unsupported`.
- `v1.13.7` owns the stored-path restore boundary cleanup and contract split.

### Stored-path remove and stored-paths remove

- `validateRemoveRequest` returns `ErrNotImplemented` for any mode other than
  `RemoveModeFileIDs`.
- Current mechanism is sentinel-based unsupported engine routing for non-file-ID
  remove paths.
- `errors.Is(err, engine.ErrNotImplemented)` should work today and is covered by
  tests.
- Preliminary classification candidate: `Unsupported`.
- `v1.13.7` owns the stored-path remove boundary cleanup.

### Snapshot diff and query narrowing behavior

- `SnapshotQuery` in `internal/engine/candidates.go` documents current support
  limits: only one exact `Path` and one `Prefix` survive the current engine seam.
- `snapshotDiffSummaryFastPath` and `snapshotDiffDetailed` in
  `internal/engine/default_engine_routing_helpers.go` route current behavior
  without exposing a separate taxonomy layer yet.
- Current mechanism is mixed: partial contract comments, direct delegated
  errors, and ordinary validation strings where request shape is invalid.
- `errors.Is` does not define a dedicated seam-level classification here today.
- Preliminary classification candidate: `Unknown / Needs later decision`.
- `v1.13.3` owns read-side contract cleanup for `snapshot diff`, `inspect`,
  `snapshot show`, and related query narrowing.

### Minimal and provisional `VerifyResult`

- `VerifyResult` in `internal/engine/types.go` is intentionally empty; success
  is represented by `nil` error and failure preserves the underlying verify
  error chain.
- Current mechanism is pass-or-fail plus delegated verify errors, not a rich
  engine-owned taxonomy object.
- `errors.Is` depends on the delegated underlying error; `errors.As` can work
  when the underlying failure is a typed verify or invariant error.
- Preliminary classification candidate: `Unknown / Needs later decision`.
- Phase 2 should define naming boundaries; `v1.13.5` owns deeper verification
  and invariant ownership work.

### Candidate-only snapshot create/delete/restore

- These request/result families are present in `internal/engine/candidates.go`
  but are not part of the active `engine.Engine` interface.
- Current mechanism is documentation and contract presence only; they are not
  runtime engine-owned surfaces yet.
- `errors.Is` is not the current decision point because the methods are not
  active engine routes.
- Preliminary classification candidate: `Deferred`.
- `v1.13.8` owns snapshot mutation boundary cleanup.

### Candidate-only repair and recover

- Repair and recover request/result families are present in
  `internal/engine/candidates.go` but remain candidate-only.
- Current mechanism is documentation and contract presence only; active runtime
  behavior remains CLI/domain-owned.
- `errors.Is` is not the current decision point because these are not active
  engine methods.
- Preliminary classification candidate: `Deferred`.
- `v1.13.9` owns repair/recovery boundary decisions.

## CLI Validation And Translation Surfaces

Representative CLI validation and translation surfaces are concentrated in
`cmd/coldkeep/main.go`.

### Usage errors, invalid flags, and missing required values

- `usageErrorf` and `cliError` drive the main validation path for command-line
  usage failures.
- Representative current cases include unknown commands, unknown flags, missing
  values for flags, invalid numeric arguments, unsupported flag combinations,
  empty required identifiers, and invalid inspect/restore/remove/snapshot
  parser inputs.
- Current mechanism is typed CLI usage errors first, with fallback message
  matching still present in `classifyExitCode`.
- Preliminary classification candidate: `Validation`.

### JSON error envelope

- The CLI emits JSON errors with explicit `error_class` and `exit_code` fields
  in `cmd/coldkeep/main.go`.
- This is a stable CLI translation surface, not an engine or catalog taxonomy
  decision point.
- Preliminary classification candidate: `CLI Translation`.

### Exit-code classification

- `classifyExitCode` and `exitErrorClassLabel` map CLI-visible failures to
  `USAGE`, `VERIFY`, `RECOVERY`, or `GENERAL`.
- Current mechanism is mixed:
  - typed `cliError` handling is authoritative when available
  - fallback matching still inspects message text for usage, verify, and
    recovery cases
- This behavior is already test-backed and must not change during `v1.13.2`
  Phase 1.
- Preliminary classification candidate: `CLI Translation`.

### Errors before repository initialization

- Examples include parser failures, invalid flags, missing command, invalid
  output mode, and invalid config or benchmark arguments.
- These are currently CLI-owned usage or validation failures, not engine-owned
  runtime failures.
- Preliminary classification candidate: `Validation`.

### Errors after engine or domain operations

- The CLI currently translates downstream engine, maintenance, verify, storage,
  recovery, and observability failures into exit codes and optional JSON error
  envelopes.
- Current behavior depends partly on typed errors and partly on message text.
- `v1.13.2` must preserve CLI behavior, JSON output, and exit codes.

## Domain/State Surfaces

Representative domain or repository-state failures already visible in code or
tests include:

- `snapshot %q not found`
  - returned by engine and snapshot helpers for valid-but-missing snapshot IDs
- logical file not found or file with ID does not exist
  - represented in observability, maintenance verify commands, and related tests
- `snapshot_path not found for path_id=%d`
  - emitted by snapshot path resolution helpers
- valid delete or restore requests blocked by current repository state
  - for example retained snapshot references surfaced through invariant-backed
    remove results

Current mechanism varies by package:

- plain string errors for many domain or not-found cases
- `%w` wrapping around `sql.ErrNoRows` in some lower-level helpers
- observability sentinel wrapping for read-side not-found targets

`errors.Is` is not consistently available for all domain-state failures today.

Preliminary classification candidate: `Domain`.

Later owners:

- `v1.13.3` for read-side contract cleanup
- `v1.13.7` for restore/remove contract cleanup
- `v1.13.6` for deeper catalog responsibility where metadata ownership expands

## Invariant/Integrity Surfaces

Representative invariant and integrity surfaces already exist today.

### Machine-readable invariant wrapper

- `internal/invariants/errors.go` defines a typed `Error` with stable
  machine-readable codes and `Unwrap`.
- `errors.As` is expected to work today through `invariants.Code`.
- Preliminary classification candidate: `Invariant`.

### Representative invariant codes already in use

- `PHYSICAL_GRAPH_REFCOUNT_MISMATCH`
- `GC_FK_VIOLATION`
- `REPAIR_REFUSED_ORPHAN_ROWS`
- `SNAPSHOT_RETAINED_DELETE_BLOCKED`

These show that some correctness failures are already separated from generic
runtime failures in code, even though taxonomy naming is not yet release-wide.

### Representative invariant/integrity examples

- refcount mismatch and physical graph integrity failures
- GC refusal because integrity is unsafe
- repair refusal because orphan rows exist
- snapshot-retained delete blocked
- verify failures on catalog/storage inconsistency
- database invariant violation text in deep verify flows

Current mechanism is mixed:

- typed invariant wrapper for some maintenance and engine paths
- verify-specific typed/category failures for verification flows
- plain strings for some lower-level integrity helpers

`v1.13.5` owns deeper invariant authority and engine-level validation or
invariant ownership.

## Runtime/Storage/Catalog/Environment Surfaces

Representative runtime, storage, catalog, and environment failures include:

- filesystem read/write/open/stat/remove/rename failures in storage,
  maintenance, recovery, and verify paths
- database query, scan, row-iteration, and transaction failures across storage,
  verify, maintenance, snapshot, catalog, and observability
- context cancellation checks such as `ctx.Err()` in engine store
- missing configuration or injected dependency failures such as:
  - `engine: Config.DB is required`
  - `engine: store requires injected StoreContext`
  - `observability service requires non-nil db`
  - `db connection is nil`
- unsupported storage or restore mode failures such as:
  - `unsupported compression codec`
  - `unsupported restore destination mode`
  - `unsupported storage context`
- verify physical or container read failures and decode failures surfaced
  through category-prefixed verify errors

Current mechanism is mostly wrapped `fmt.Errorf(... %w ...)` chains, with some
plain string errors and some sentinel usage for observability and storage codec
support.

Preliminary classification candidates:

- `Runtime`
- `Storage`
- `Catalog`
- `External/Environment`

Phase 2 should name these boundaries without changing current behavior.

## Verify And Observability Special Cases

### Verify category-prefixed failures

- `internal/verify/verify_repository.go` defines stable category strings such as
  `metadata_missing`, `metadata_invalid`, `physical_missing`,
  `physical_hash_mismatch`, `compressed_hash_mismatch`,
  `block_hash_mismatch`, `chunk_hash_mismatch`, and
  `unsupported_block_format`.
- `verifyCategoryError` and `VerifyFailure` produce typed failures that still
  encode category meaning prominently in the error text.
- Current mechanism is typed wrapper plus string category prefix, not sentinel
  values.
- `errors.As(err, *VerifyFailure)` should work today; `errors.Is` does not
  classify these categories by itself.
- Preliminary classification candidate:
  `Invariant / Storage / Runtime / Unknown / Needs later decision`.

### Observability sentinels

- `internal/observability/errors.go` defines:
  - `ErrUnsupportedEntity`
  - `ErrNotFound`
  - `ErrInvalidTarget`
- Read-side observability methods wrap these with `%w`, for example invalid
  entity IDs and missing snapshot/logical-file/chunk/container lookups.
- `errors.Is` should work today for these sentinels.
- Preliminary classification candidates:
  - `Validation` for invalid target
  - `Domain` for not found
  - `Unsupported` or `Validation` for unsupported entity, pending Phase 2 naming
- `v1.13.3` owns deeper read-side contract cleanup.

## Wrapping And Compatibility Observations

- Sentinel-backed paths already relying on `errors.Is`:
  - `engine.ErrNotImplemented`
  - `catalog.ErrNotImplemented`
  - observability sentinels such as `ErrInvalidTarget` and `ErrNotFound`
  - some OS and fault-injection errors in recovery and maintenance tests

- Invariant-wrapped errors already exposed via `errors.As`:
  - `internal/invariants.Error`
  - engine remove item annotation via `invariants.Code`
  - maintenance and CLI tests expecting invariant-code extraction

- Verify uses a different style:
  - typed `VerifyFailure`
  - string category prefixes
  - `errors.As` works for the wrapper
  - `errors.Is` does not classify verify categories today

- CLI exit translation depends on both:
  - typed CLI errors when available
  - fallback message matching when typed errors are absent

- Wrapping must be preserved where existing behavior and tests depend on it:
  - engine and catalog `ErrNotImplemented` flows
  - observability sentinels wrapped with `%w`
  - invariant codes retrievable through wrapped errors
  - verify failures carrying category, detail, and cause information
  - CLI exit-code classification that still uses message fallback matching

- String-only errors still exist across snapshot, storage, maintenance, and
  some engine validation paths. Phase 1 records them; it does not normalize
  them.

## Preliminary Risks

- unsupported versus validation confusion
- domain versus invariant confusion
- runtime versus catalog or storage confusion
- engine `ErrNotImplemented` versus catalog `ErrNotImplemented` confusion
- verify category-prefix semantics not mapping cleanly onto future taxonomy
  names
- CLI translation drift if error text or wrapped types change
- adding an oversized error framework instead of preserving narrow,
  behavior-safe semantics
- overclaiming taxonomy completeness before code-backed behavior is actually
  stable
