# Coldkeep v1.13.5 Backend-Neutral Invariant Coverage Review

**Release:** `v1.13.5 — Release Record Closure and Engine-Level Invariant Ownership`  
**Phase:** Phase 7  
**Status:** Complete  
**Branch:** `release/v1.13.5`

## Purpose

This document reviews whether the validation, invariant ownership, and guard
decisions documented in Phases 1–6 remain backend-neutral across SQLite and
PostgreSQL.

This phase performs no backend migration, no ownership migration, and no
behavior change.

## Reviewed surfaces

- `Verify`
- `Remove`
- `Restore`
- `Stats`
- `Inspect`
- `SnapshotShow`
- `SnapshotDiff`
- GC / maintenance invariants
- candidate Phase 8 guard gaps
- existing SQLite/PostgreSQL coverage

## Backend posture

- SQLite compatibility is preserved.
- PostgreSQL compatibility is preserved.
- No backend defaults change.
- No SQLite-only assumptions are introduced.
- PostgreSQL-backed validation remains required in the final Phase 10
  `PRE_RELEASE_CHECKLIST.md Profile A` gate.
- This phase does not expand the backend matrix.
- One existing backend rule remains explicit and unchanged:
  live GC is intentionally refused on SQLite while dry-run is supported.

## Verify backend review

Backend-neutral validation:

- CLI parsing for target shape, verify level, and `fileID` string/range
  handling is backend-neutral.
- `DefaultEngine.validateVerifyRequest` is backend-neutral.
- `VerifyRequest` and the Phase 2 candidate guards are request/CLI/engine
  boundary concerns rather than backend-specific ones.

Backend-sensitive execution:

- maintenance dispatch and `internal/verify` execution are catalog/storage
  sensitive.
- seeded corruption and repository-state checks depend on DB-backed metadata,
  chunk layout, and storage/catalog relationships.

Existing coverage:

- SQLite-heavy protection exists in
  `internal/maintenance/verify_command_test.go`,
  `internal/verify/verify_system_test.go`, and
  `internal/verify/verify_corruption_fixtures_test.go`.
- `internal/engine/verify_db_ownership_test.go` protects backend-neutral DB
  ownership behavior.
- PostgreSQL coverage is mostly indirect for verify-specific review work and
  remains part of the final `COLDKEEP_TEST_DB` / Profile A posture.

Phase 8 guard implication:

- verify invariant metadata plus verify-failure public detail guard is
  backend-neutral if it stays at CLI/engine error projection level.
- verify empty-target default guard is backend-neutral.
- no verify Phase 7 blocker was found.

## Remove backend review

Backend-neutral validation:

- `validateRemoveRequest` is backend-neutral.
- unsupported stored-path engine boundaries are backend-neutral.
- request-shape and per-item invalid-ID guards remain backend-neutral.

Backend-sensitive destructive checks:

- live destructive semantics depend on catalog and storage state.
- snapshot-retention blockers are catalog-sensitive.
- ref-count consistency and fail-closed delete semantics are domain/correctness
  checks over backend-managed state.

Existing coverage:

- SQLite-heavy protection exists in `internal/storage/remove_test.go`,
  `internal/engine/remove_engine_test.go`, and CLI routing/output tests.
- `tests/integration/read_path_regression_test.go` provides public-path
  retained-delete coverage in the DB-backed integration layer.
- PostgreSQL posture remains mostly integration/release-gate based rather than
  a dedicated Phase 7 remove-only dual-backend suite.

Phase 8 guard implication:

- remove unsupported stored-path fails-before-mutation guard is
  backend-neutral.
- remove snapshot-retained invariant metadata guard is backend-sensitive
  because it depends on seeded catalog state and retention relationships.
- current coverage is already sufficient to avoid adding a backend-sensitive
  Phase 8 guard by default.

## Restore backend review

Backend-neutral validation:

- `validateRestoreRequest` is backend-neutral.
- unsupported stored-path engine boundaries are backend-neutral.
- empty output directory and request-mode guards are backend-neutral.

Storage/catalog-sensitive execution:

- by-ID restore execution depends on catalog metadata, recipe rows, chunk
  state, and write-path semantics.
- overwrite behavior, metadata strictness, and chunk ordering all depend on
  seeded repository state.

Filesystem-sensitive path safety:

- path safety is primarily filesystem-sensitive rather than backend-specific.
- this remains separate from SQL backend neutrality even though restore uses
  DB-backed metadata to derive its work.

Existing coverage:

- SQLite-heavy package coverage exists in `internal/storage/restore_test.go`,
  `internal/storage/restore_recipe_validation_test.go`, and engine/CLI restore
  tests.
- DB-backed integration coverage exists in `tests/integration/integration_test.go`.
- PostgreSQL posture remains mostly integration and final Profile A rather than
  a dedicated restore-only dual-backend contract suite.

Phase 8 guard implication:

- restore unsupported stored-path fails-before-mutation guard is
  backend-neutral.
- restore empty output directory engine-level guard is backend-neutral.
- restore dry-run/live result ownership guard is mostly backend-neutral if it
  stays at result-shape level, but deeper dry-run/live safety parity is still
  catalog/storage-sensitive.

## GC / maintenance backend review

Backend-neutral invariant metadata model:

- `internal/invariants.Error` and `errors.As` extraction are backend-neutral.
- CLI rendering of `invariant_code` and `recommended_action` is
  backend-neutral.

Backend-sensitive GC/repair detection paths:

- GC integrity and catalog-state refusals depend on DB-backed graph and
  maintenance state.
- FK behavior is backend-sensitive and explicitly requires care because the
  backend error surface differs.
- repair orphan-row refusal depends on catalog-state inspection below the CLI.

Existing coverage:

- SQLite-heavy coverage exists in `internal/maintenance/gc_phase3_test.go`,
  `internal/maintenance/gc_phase6_test.go`,
  `internal/maintenance/repair_refcounts_test.go`, and CLI tests.
- `internal/maintenance/gc_phase3_test.go` explicitly recognizes both
  PostgreSQL and SQLite FK error forms.
- `internal/maintenance/gc_test.go` and `internal/maintenance/gc_parity_test.go`
  provide `COLDKEEP_TEST_DB`-gated DB-backed GC coverage.
- integration/adversarial tests plus final Profile A provide the broader
  PostgreSQL-backed posture.

Phase 8 guard implication:

- GC invariant wrapping/extraction guard is backend-neutral.
- repair orphan-row refusal invariant metadata guard is mostly backend-neutral
  at public rendering level but depends on backend-seeded orphan state below it.
- CLI maintenance invariant JSON error guard is backend-neutral at envelope
  level.
- deeper GC/repair refusal-state guards are backend-sensitive but already
  sufficiently covered for `v1.13.5`.

## Read-side backend review

- The `v1.13.4` and Phase 6 read-side output-shape guards are mostly
  backend-neutral because they protect envelope families, counts, public
  targets, and taxonomy boundaries.
- `stats`, `inspect`, `snapshot show`, and `snapshot diff` execution remains
  backend-sensitive below the guard layer because the data still comes from
  observability, catalog, snapshot, and maintenance/database paths.
- The current v1.13.4 backend posture remains valid:
  the strongest dual-backend anchor is still
  `internal/catalog/backend_contract_backends_test.go`, while other read-side
  PostgreSQL evidence remains partly indirect and finalized through Profile A.
- Phase 6 found no read-side Phase 8 guard justified, and this backend review
  does not change that decision.

## Findings

### Backend-neutral and safe for Phase 8 if needed

- verify invariant metadata plus verify-failure public detail guard
- verify empty-target default guard
- remove unsupported stored-path fails-before-mutation guard
- restore unsupported stored-path fails-before-mutation guard
- restore empty output directory engine-level guard
- GC invariant wrapping/extraction guard
- CLI maintenance invariant JSON error guard

### Backend-sensitive but already sufficiently covered

- remove snapshot-retained invariant metadata depends on seeded retention and
  catalog state, and current engine/domain/integration coverage is already
  sufficient for this release
- restore dry-run/live result ownership sits above catalog/storage-sensitive
  execution and already has engine, CLI, and integration protection
- repair orphan-row refusal invariant metadata depends on backend-seeded orphan
  state, and current maintenance/CLI coverage plus Profile A posture is
  sufficient
- GC and FK-related refusal behavior already has explicit backend-aware
  coverage and final Profile A posture

### Backend-sensitive and not justified for v1.13.5

- no candidate guard requires broad new backend-sensitive coverage in
  `v1.13.5`
- no SQLite/PostgreSQL-specific gap was found that justifies adding new tests
  or changing backend posture in this phase

### No longer justified

- read-side extra guards are no longer justified after the completed Phase 6
  follow-up
- no new backend-specific read-side guard is needed in `v1.13.5`

## Phase 7 decision

The `v1.13.5` validation and invariant ownership decisions remain
backend-neutral at the request/guard level and backend-compatible at the
domain execution level.

No Phase 7 production or test change is required.
No SQLite-only assumption was found.
PostgreSQL compatibility remains part of the final Profile A release gate.
Any Phase 8 tests, if still needed, should be limited to backend-neutral guard
gaps or should explicitly justify why backend-sensitive coverage is necessary.
