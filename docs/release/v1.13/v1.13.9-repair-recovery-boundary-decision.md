# v1.13.9 Phase 14 — Repair and Recovery Boundary Decision

Starting SHA: `c6cbfdf38695a078c18474d57f562d4e88d3015c`

## Summary

Phase 14 defines the repair and recovery ownership boundary after production
CLI `snapshot create`, `snapshot delete`, and `snapshot restore` became
engine-owned mutation routes.

This phase is a boundary decision only. It does not:

- add engine repair or recovery methods;
- route new CLI commands through engine;
- change verify, doctor, repair, GC, create, delete, or restore behavior;
- change CLI text or JSON output;
- change schemas, migrations, storage format, or workflows.

## Ownership decision table

| Responsibility | Phase 14 decision |
| --- | --- |
| Detecting corruption | `internal/verify` and targeted storage/container checks |
| Verifying snapshot metadata | verify/audit helpers below CLI |
| Verifying stored payload/container integrity | `internal/verify` plus storage/container primitives |
| Detecting missing payloads | `internal/recovery` and `internal/verify` |
| Detecting orphaned metadata | verify/audit and maintenance checks |
| Detecting orphaned payloads | `internal/recovery` orphan-container scan and GC/verify checks |
| Rebuilding derived metadata | explicit `internal/maintenance` repair primitives only |
| Repairing parent/child lineage issues | deferred; not owned by current engine or CLI flows |
| Repairing snapshot membership rows | deferred; not owned by current engine or CLI flows |
| Repairing storage/container indices | lower-layer storage/container or DB primitives only |
| Recovering files from surviving payload data | existing restore path only; not a new repair API |
| Refusing unsafe automatic repair | lower layers must fail closed; CLI must not auto-upgrade into execution |
| Producing repair plans | deferred future candidate |
| Executing repair plans | deferred future candidate |
| Rendering human/JSON repair output | CLI-owned responsibility |

## In scope for v1.13.9

- make the ownership boundary explicit and checked in;
- keep `doctor` and `repair` honestly CLI-owned for `v1.13.9`;
- keep verify, maintenance, recovery, and storage/container responsibilities
  separated rather than implied to be engine-owned;
- define what future engine ownership would have to cover before activation;
- define forbidden automatic repair behaviors explicitly.

## Explicitly out of scope for v1.13.9

- adding `Engine.SnapshotRepair`, `Engine.SnapshotRecovery`, `RepairPlan`, or
  `RecoveryPlan`;
- adding CLI dry-run/execute repair orchestration beyond current behavior;
- implementing snapshot-lineage repair or snapshot-membership repair;
- implementing file recovery from partially surviving data outside current
  restore semantics;
- changing verify, doctor, repair, GC, or restore contracts;
- changing schemas, migrations, storage format, PostgreSQL compatibility, or
  path-safety policy.

## Engine-owned future candidates

The engine may eventually own a repair/recovery boundary, but only as a later
phase and only with explicit behavior-preserving design. Candidate future
ownership includes:

- corrective-operation request validation;
- explicit dry-run versus execute mode;
- structured warnings and structured errors;
- renderer-neutral result summaries;
- unsupported-boundary honesty where lower-layer primitives remain separate.

The engine does not own these behaviors yet.

## CLI-owned responsibilities

- command parsing and target-shape parsing;
- `doctor` sequencing across recovery, schema/version check, verify, and audit;
- `repair` target selection, batch handling, fail-fast behavior, and result
  rendering;
- human and JSON output projection;
- user-facing hints, destructive messaging, and exit-code shaping;
- any future confirmation/force flags unless a later phase explicitly moves
  them.

## Snapshot-domain responsibilities

- snapshot create/delete/restore mutation semantics only;
- snapshot metadata and reachability verification through verify/audit layers;
- no direct ownership of repair execution in `v1.13.9`;
- no automatic snapshot mutation as a side effect of doctor, verify, or repair.

## Storage/container responsibilities

- direct SQL primitives and transaction boundaries for existing corrective
  maintenance;
- quarantine of unsafe containers and recovery of interrupted sealing state;
- packed/transform-aware payload validation and restore primitives;
- rebuild of stale chunk/logical-file mappings during store safety flows;
- filesystem safety and trusted-path enforcement;
- fail-closed handling when corruption, missing payloads, or unreadable state is
  detected.

## Forbidden automatic repairs

- no silent payload deletion;
- no automatic data-lossful repair;
- no repair that hides corruption from verify;
- no automatic snapshot mutation without explicit execute-mode design;
- no repair that broadens restore behavior into “best effort” recovery;
- no repair that bypasses path-safety rules;
- no repair that bypasses packed/transform-aware invariants;
- no repair that weakens PostgreSQL compatibility or DB-backed safety checks.

## Safety invariants

- repair and recovery must remain fail-closed on ambiguous or unsafe state;
- verify remains the source of corruption detection, not a repair side effect;
- doctor/recovery counters indicate corrective actions, not success-by-masking;
- GC must continue refusing unsafe state instead of repairing it implicitly;
- restore must remain a restore path, not a hidden recovery planner;
- lower-layer rebuild/quarantine helpers remain internal safeguards, not public
  repair APIs.

## PostgreSQL and backend compatibility notes

- current repair and recovery paths are DB-backed and must preserve PostgreSQL
  support;
- no SQLite-default transition is authorized by this phase;
- any future engine-owned repair/recovery work must preserve current backend
  neutrality claims honestly and add explicit parity proof before activation;
- packed-storage, quarantine, verify, and maintenance paths remain the most
  backend-sensitive areas and must not be abstracted away casually.

## Deferred v1.14+ work

- decide whether to activate a narrow engine-owned corrective boundary or keep
  repair/recovery permanently outside engine;
- if engine ownership is pursued, define unsupported-boundary honesty first;
- decide whether repair planning and repair execution should be separate phases;
- decide whether any snapshot-specific repair surface is ever safe to expose;
- strengthen backend parity proof for corrective paths before any activation.

## Recommended Phase 15 scope

Recommended next phase:

- implement only the smallest follow-up required by this decision, likely one
  of:
  - explicit unsupported-boundary proof for engine repair/recovery candidates;
  - boundary-honesty tests showing `doctor` and `repair` remain CLI-owned; or
  - a narrower corrective-path safety review if the tracker prefers more proof
    before any engine activation.

Phase 15 should not begin repair or recovery execution redesign by default.
