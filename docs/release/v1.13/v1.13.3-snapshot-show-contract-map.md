# Coldkeep v1.13.3 — Snapshot Show Contract Cleanup Map

## Status

`complete`

## Purpose

This document maps the current `snapshot show` read-side contract and
identifies the safe cleanup and test-hardening plan for later `v1.13.3`
phases.

This document does not change `snapshot show` behavior.

This document does not change `snapshot show` routing.

This document does not change `snapshot show` JSON output.

This document does not change `snapshot show` exit codes.

This document does not introduce new `snapshot show` request or result types.

This document is input for Phases 6, 7, and 8.

## Relationship to Phase 1

Phase 1 established the key `snapshot show` finding that drives this phase:

`snapshot show` still uses direct snapshot helpers and CLI-assembled or
renderer-mediated output rather than a fully engine-owned read-side contract.

Current `snapshot show` ownership summary:

- current CLI entry point: `runSnapshotShowCommand`
- current engine involvement: `getSnapshotPhase` creates an engine and calls
  `eng.SnapshotShow(...)`, but only reprojects metadata back to
  `snapshot.Snapshot`; `snapshotStatsPhase` creates an engine and calls
  `eng.SnapshotStats(...)`, then reprojects back to `snapshot.SnapshotStats`
- current snapshot package ownership: `listSnapshotFilesPhase` remains direct
  `snapshot.ListSnapshotFiles` and the active show flow still depends on
  snapshot-owned metadata, file-entry, and stats-shaped types
- current renderer ownership: `internal/cli/render` owns the human
  `snapshot show` layout through `RenderSnapshotShowHuman`
- current backend, catalog, and storage dependencies: metadata lookup uses the
  engine catalog-backed seam, file listing uses direct snapshot helpers and DB
  reads, stats use engine-backed snapshot stats, and file/path details remain
  storage-adjacent through snapshot file-entry rows
- current snapshot ID behavior: `snapshotID` is required, trimmed, and empty
  input is a usage error

## Current Snapshot Show Flow

Current code-path flow:

```text
CLI snapshot show command
  -> flag parsing and validation
  -> snapshot ID parsing
  -> query parsing
  -> storage context / DB opening
  -> getSnapshotPhase
  -> engine.New
  -> eng.SnapshotShow(engine.SnapshotShowRequest{SnapshotID})
  -> metadata reprojected back to snapshot.Snapshot
  -> listSnapshotFilesPhase
  -> snapshot.ListSnapshotFiles
  -> snapshotStatsPhase
  -> engine.New
  -> eng.SnapshotStats(engine.SnapshotStatsRequest{SnapshotID})
  -> stats reprojected back to snapshot.SnapshotStats
  -> CLI JSON assembly or RenderSnapshotShowHuman
```

## Current Snapshot Show Behavior To Preserve

Verified current public behavior that must remain unchanged:

- command name is `snapshot show`
- usage is:
  - `coldkeep snapshot show <snapshotID> [--limit <count>] [--path <path>] [--prefix <dir/>] [--pattern <glob>] [--regex <re>] [--min-size <bytes>] [--max-size <bytes>] [--modified-after <timestamp>] [--modified-before <timestamp>] [--output <text|json>]`
- accepted flags are `--limit`, `--output`, `--json`, `--path`, `--prefix`,
  `--pattern`, `--regex`, `--min-size`, `--max-size`, `--modified-after`, and
  `--modified-before`
- `snapshotID` is required, trimmed, and empty input is a usage error
- query parsing is delegated to `parseSnapshotQuery(parsed)`
- filtered file counts come from `len(files)` and total snapshot file count
  comes from `stats.SnapshotFileCount`
- JSON success output uses the legacy CLI envelope with:
  - `status: "ok"`
  - `command: "snapshot"`
  - `data.action: "show"`
  - `data.snapshot`
  - `data.file_count`
  - `data.matched_file_count`
  - `data.total_snapshot_file_count`
  - `data.files`
  - `data.duration_ms`
- human output is renderer-owned and prints snapshot metadata, matched and
  total file counts, file paths, duration, and hint
- empty snapshots are still successful reads; they render zero counts and
  `(no files)` in human output when no files are returned
- missing snapshot behavior currently surfaces through the mixed seam's
  existing error path and must not be silently reclassified
- failures otherwise route through shared CLI error behavior with no
  `snapshot show`-specific exit-code redesign
- backend-visible behavior is expected to remain equivalent across supported
  backends

## Error Taxonomy Mapping For Snapshot Show

| Error family | Current source | Current representation | Public behavior | v1.13.3 decision |
| --- | --- | --- | --- | --- |
| validation / usage errors | CLI parsing in `runSnapshotShowCommand`, `ensureAllowedFlags`, `validateNonNegativeIntegerFlag`, and usage checks | `usageErrorf(...)` / `cliError` | usage-style message and shared usage exit classification | `preserve as-is` |
| invalid snapshot ID or missing required ID | empty or missing positional `snapshotID` | usage error such as `snapshotID cannot be empty` | usage-style public behavior | `candidate for Phase 7 preservation test` |
| domain missing snapshot | engine `SnapshotShow` metadata lookup miss | plain error containing `not found` from mixed seam | current missing-snapshot behavior must remain stable even though it is not a dedicated CLI taxonomy translation seam | `candidate for Phase 6 and Phase 7 protection` |
| domain empty snapshot | empty file listing for existing snapshot | successful output with zero or empty file list | empty snapshot is not an error today | `preserve as-is` |
| invariant / integrity errors | indirect only unless lower-level snapshot, lineage, or metadata reads surface impossible relationships | no dedicated `snapshot show` invariant family today | must not be invented or overstated in Phase 4 | `document as indirect / provisional` |
| runtime DB errors | engine, catalog, or snapshot helper query/read failures | wrapped query, lookup, or helper errors | shared CLI general failure behavior | `candidate for Phase 6 and Phase 7 protection` |
| catalog-origin errors | snapshot metadata lookup through engine catalog seam | wrapped catalog-backed lookup failures or missing metadata | current mixed-seam failure behavior | `document honestly; no new helper` |
| storage-origin errors | indirect through snapshot file-entry and path loading | not a first-class typed `snapshot show` seam | surfaces, if at all, through lower-level wrapped failures | `document as indirect` |
| environment / config errors | repository context open, DB open, nil DB, or engine setup failure | wrapped setup or DB-open failures | shared CLI general failure behavior | `candidate for later preservation checks` |
| unsupported / deferred errors | no active `snapshot show` unsupported-engine or deferred seam found | not current behavior | should not be introduced accidentally | `document as not current behavior` |
| unknown / provisional errors | mixed ownership and provisional engine result seams | documentation-only classification | no public taxonomy leakage | `document as provisional only` |

Important mapping constraints:

- do not claim unified `snapshot show` taxonomy wrapping
- do not introduce new helper names
- do not classify missing snapshot as invariant corruption
- do not classify empty snapshot as an error
- do not classify runtime DB failure as domain not-found

## Domain Vs Invariant Boundary For Snapshot Show

Current boundary guidance from repo truth:

- missing snapshot ID argument is validation or usage behavior
- empty or whitespace-only `snapshotID` is validation or usage behavior
- valid `snapshotID` that does not exist is current domain missing-snapshot
  behavior through the mixed metadata lookup seam
- empty snapshot contents remain a successful read, not an error
- broken parent links, impossible snapshot graph metadata, impossible file
  mappings, or retained snapshot inconsistencies are invariant or integrity
  concerns only if current code already detects them or later phases add
  tests that establish them
- runtime DB and read failures remain runtime, catalog-origin, storage-origin,
  or environment-origin failures, not domain missing-snapshot behavior

## Public CLI Preservation Notes

Preservation concerns that later phases must keep explicit:

- human output preservation:
  - renderer-owned snapshot metadata lines, matched and total counts, file
    list, duration, and hint must not drift accidentally
- JSON output preservation:
  - legacy success envelope fields, command naming, action naming, and count
    semantics must remain stable
- JSON error-envelope preservation:
  - `snapshot show` must not gain taxonomy fields or helper-name leakage in
    public JSON errors
- exit-code preservation:
  - `snapshot show` depends on shared CLI exit classification and must not get
    a custom redesign
- startup / logging / noise concerns:
  - JSON mode must remain a clean single-object success output without extra
    startup noise
- taxonomy helper leakage concerns:
  - no taxonomy helper names or internal classification fields should appear
    in public `snapshot show` JSON

## Final Phase 4 Decision

relies on direct snapshot helpers and current CLI/render output ownership,
provided later phases protect public CLI/JSON/exit-code behavior and document
direct snapshot ownership as provisional for later engine-contract cleanup.
