# Coldkeep v1.13.7 Repository Portability Smoke-Test Design

**Release:** `v1.13.7 — SQLite-First Repository Portability Baseline`
**Phase:** Phase 6
**Status:** Complete
**Branch:** `release/v1.13.7`
**Starting commit:** `f98da00`

## Purpose

This document designs the minimum executable guard needed to cover the missing
direct portability evidence identified in Phase 4.

This phase adds no tests and changes no runtime behavior.

## Scope boundaries

- design only
- no Phase 7 implementation yet
- no runtime SQLite local mode
- no backend-default change
- no repository-root product API
- no copy or move command
- no backup or clone semantics
- no broad backend parity suite
- PostgreSQL compatibility preserved

## Missing direct evidence

Current evidence is already strong for SQLite bootstrap and migration,
store/restore behavior, verification, integrity failure behavior, and related
catalog and payload continuity checks.

Current evidence does not directly prove end-to-end directory relocation of a
complete SQLite local repository root that is moved to a new path, reopened
from the destination only, verified, and restored successfully without any
source-root dependency.

## Existing reusable seams

| Seam/helper | Location | Production equivalence | Proposed use |
| --- | --- | --- | --- |
| File-backed SQLite open | `database/sql` with `sql.Open("sqlite3", path)` as already used by current storage seams and tests | Equivalent low-level DB open primitive | Open the repository-owned SQLite catalog at `<source-root>/.coldkeep/catalog.sqlite` and again at the destination path |
| SQLite session pragmas | `internal/db.ApplySQLiteSessionPragmas` | Current SQLite session configuration seam | Apply the same SQLite session configuration before store and after reopen |
| Schema bootstrap and reopen migration | `internal/db.RunMigrations` | Current schema bootstrap/migration seam | Create and reopen the catalog through the existing SQLite migration path |
| Storage context assembly | `internal/storage.StorageContext` | Current store/restore dependency carrier | Bind the explicit DB handle, writer, and repository-owned payload path into the future guard |
| Local payload writer | `internal/container.NewLocalWriterWithDirAndDB` | Current local payload writing seam | Write payload into `<source-root>/containers` and later `<destination-root>/containers` |
| Store | `internal/storage.StoreFileWithStorageContextAndCodecResult` | Current store seam | Store one deterministic file and capture the returned file ID |
| Restore | `internal/storage.RestoreFileWithDB` and storage restore seams | Current restore seam | Restore the captured file ID from the destination repository only |
| Verify | `internal/verify.VerifySystemStandardWithContainersDir` and engine verification wrappers | Current verification seam | Prove semantic continuity after relocation using destination DB plus destination payload root |
| Backend detection / safety context | `internal/db/backend.go`, accepted Phase 5 compatibility review | Documentary support only | Support the release record without introducing new behavior |

## Candidate approaches

### Rename-based relocation

Pros:

- directly proves root-path relocation
- keeps the scenario narrow and deterministic
- avoids introducing recursive-copy helpers
- avoids clone semantics, partial-copy semantics, and cross-filesystem policy

Cons:

- does not prove interrupted-copy handling
- does not prove cross-filesystem moves

### Recursive copy

Pros:

- closer to real backup-copy behavior

Cons:

- introduces copy-helper complexity
- raises partial-copy and mixed-generation questions immediately
- pulls in clone and trust-boundary semantics that Phase 6 does not need

### CLI subprocess workflow

Pros:

- closer to user-facing behavior

Cons:

- depends on CLI/runtime paths that still default to PostgreSQL-backed local mode
- would blur the line between test-only SQLite seam coverage and product runtime claims

### PostgreSQL operational-transfer workflow

Pros:

- relevant to PostgreSQL operational portability

Cons:

- does not cover the missing SQLite local root-relocation gap
- belongs to a different portability class

### Conclusion

Phase 7 should prefer one narrow, same-parent
`os.Rename(sourceRoot, destinationRoot)` relocation guard.

That is the smallest design that directly proves root-path relocation without
introducing copy-helper complexity, clone semantics, partial-copy handling, or
production move behavior. Recursive copy, partial-copy refusal, clone identity,
and cross-filesystem behavior remain deferred.

## Proposed repository fixture

The conceptual fixture should be:

```text
<temp-parent>/
  source-repo/
    .coldkeep/
      catalog.sqlite
    containers/
  restored-output/
```

Add a repository-owned payload directory such as `blocks/` only if the actual
store path naturally requires it. Do not expand scope unnecessarily.

## SQLite setup

The Phase 7 design target is:

1. create `<source-root>/.coldkeep/`
2. open a file-backed SQLite DB at `<source-root>/.coldkeep/catalog.sqlite`
3. apply `db.ApplySQLiteSessionPragmas`
4. run `db.RunMigrations`
5. if needed for lock stability, set `SetMaxOpenConns(1)` and `SetMaxIdleConns(1)` consistently with current SQLite seams
6. construct an explicit storage seam using the opened DB and a repository-owned payload directory under the source root

This stays aligned with current SQLite seam usage without claiming that normal
local runtime startup already does this in production.

## Representative store scenario

Use one deterministic scenario only:

- one small input file outside the repository root
- plain codec only
- one representative active storage path only
- no packed/legacy matrix
- no snapshot matrix
- no AES-GCM unless it is effectively free and already proven safe; default remains plain-only
- capture the returned file ID from store

Recommended deterministic content:

```text
coldkeep-v1.13.7-portability-smoke
```

## Source close boundary

Before relocation, the future guard should close all resources that may retain
SQLite or filesystem ownership:

- DB handle
- writer or storage context that owns handles
- any rows or statements if applicable
- any engine/storage seam that owns shared resources

The guard should avoid deferred closures that leave source handles open through
`os.Rename`. It should not use retries or sleeps. If SQLite reports locking
errors during rename, that should be treated as evidence that closure ownership
is incomplete.

## Relocation operation

The proposed move is:

- `os.Rename(sourceRoot, destinationRoot)` under the same temp parent
- source root must disappear
- destination root must exist
- destination catalog path must differ from source catalog path
- destination payload path must differ from source payload path

This is intentionally narrower than backup-copy or clone semantics.

## Destination reopen

Destination-only reopening should:

- reopen SQLite using the destination catalog path only
- re-apply SQLite pragmas
- run the normal reopen or migration seam if applicable
- reconstruct storage, verify, and restore seams using destination-root-derived paths only
- avoid relying on the original working directory, original absolute paths, or source-root presence

## Verification assertion

The required verify assertion is:

- run repository verification against the destination DB and destination payload root only
- treat success as proof of semantic continuity, not just successful DB open

Preferred seam:

- `verify.VerifySystemStandardWithContainersDir(destinationDB, destinationContainersDir)`

An engine-backed wrapper is acceptable only if it preserves the same
destination-only ownership boundary.

## Restore and byte-equality assertion

The required restore assertion is:

- restore the captured file ID from the destination repository only
- write restored output outside both source and destination repository roots
- compare restored bytes exactly with the original input bytes

Preferred seam:

- `storage.RestoreFileWithDB(destinationDB, fileID, outputPath)`

## Source-independence assertions

The future guard should require assertions that prove true relocation:

- source root no longer exists after rename
- source catalog path no longer exists
- source payload path no longer exists
- destination root differs from source root
- destination catalog path differs from source catalog path
- destination payload path differs from source payload path
- reopened destination uses destination-root-derived paths only

Where feasible, the guard may also confirm that reopened DB filename resolution
lands under the destination root and that no old absolute source path remains
necessary for required internal storage access.

Do not add brittle assertions over incidental SQLite internals.

## Phase 7 authorization criteria

Phase 7 is authorized only if all of the following are true:

- a file-backed SQLite seam already exists
- schema can be created through existing migration seams
- store can run with explicit SQLite DB plus repository-owned payload dir
- verify can run against the relocated destination
- restore can run against the relocated destination
- all source handles can be closed before rename
- no production or runtime change is needed
- the guard remains narrow and deterministic

## Phase 7 decision

Phase 7 is authorized to add one narrow, test-only, rename-based SQLite
repository relocation guard.

The authorized guard should:

- create a file-backed SQLite catalog under `<source-root>/.coldkeep/catalog.sqlite`
- initialize it through existing SQLite pragmas and migration seams
- store one deterministic file into a repository-owned payload directory
- capture the returned file ID
- close all source handles
- rename the complete repository root
- reopen from the destination root only
- run repository verification
- restore the stored file
- compare restored bytes exactly
- prove the source root is no longer required
