# Coldkeep v1.13.5 Engine-Level Validation and Invariant Ownership Inventory

**Release:** `v1.13.5 — Release Record Closure and Engine-Level Invariant Ownership`
**Phase:** Phase 1
**Status:** Complete
**Branch:** `release/v1.13.5`

## Purpose

This document inventories where validation and invariant ownership currently
live for active engine-facing operations.

The goal is to distinguish:

- CLI-only validation
- engine request validation
- domain package validation
- invariant metadata creation
- public error-envelope ownership
- unsupported or deferred engine seams

No code or tests changed in this phase.

## Inventory principles

This document is descriptive, not a migration plan.

`v1.13.5` does not move validation by default.

A later phase may add narrow guard tests only if a documented gap is found.

Public CLI, JSON, human output, error envelopes, exit codes, routing, schema,
storage, repository format, and backend defaults must remain unchanged.

## `Verify`

- Active engine operation: yes, `Engine.Verify` is part of the active engine
  interface in [engine.go](/home/franchoy/vscode/coldkeep/coldkeep/internal/engine/engine.go:52).
- Request type: `engine.VerifyRequest` in
  [types.go](/home/franchoy/vscode/coldkeep/coldkeep/internal/engine/types.go:37).
- Result type: `engine.VerifyResult` in
  [types.go](/home/franchoy/vscode/coldkeep/coldkeep/internal/engine/types.go:57).
- CLI validation:
  - `runVerifyCommand` validates target shape, parses level flags, and rejects
    malformed or non-positive `fileID` values before routing.
  - `verify file` platform-int bounds validation remains CLI-owned in
    [main.go](/home/franchoy/vscode/coldkeep/coldkeep/cmd/coldkeep/main.go:3057).
- Engine validation:
  - `verifyLevelFromString` validates allowed levels.
  - `validateVerifyRequest` enforces `system` or `file` target and positive
    `fileID` for file mode in
    [default_engine.go](/home/franchoy/vscode/coldkeep/coldkeep/internal/engine/default_engine.go:83).
- Domain validation:
  - `maintenance.VerifyCommandWithDBAndContainersDir` dispatches verify target
    and level.
  - `verifyFile` checks logical-file existence before deeper verification in
    [verify_command.go](/home/franchoy/vscode/coldkeep/coldkeep/internal/maintenance/verify_command.go:62).
  - deeper verification and invariant detection live in `internal/verify`.
- Invariant and error propagation:
  - invariant-coded errors are created below engine by `internal/verify`, such
    as physical and snapshot graph invariants.
  - engine returns these errors unchanged.
  - CLI extracts `invariant_code` and `recommended_action` from the error chain
    in [main.go](/home/franchoy/vscode/coldkeep/coldkeep/cmd/coldkeep/main.go:914).
  - verify-stage metadata remains verify-specific string/category detail, not a
    dedicated engine result payload.
- Explicit unsupported modes:
  - none for the active `system` and `file` targets.
  - validation errors are intentionally distinct from unsupported-mode
    classification.
- Existing tests:
  - direct engine-level test:
    `internal/engine/engine_test.go` covers `validateVerifyRequest`.
  - direct engine-level test:
    `internal/engine/verify_db_ownership_test.go` proves engine-owned DB use.
  - CLI preservation test:
    `cmd/coldkeep/verify_engine_routing_test.go` covers routing and pre-routing
    fileID rejection.
  - CLI preservation test:
    `cmd/coldkeep/main_test.go` and
    `cmd/coldkeep/cli_translation_preservation_test.go` cover invariant-code
    and verify error-envelope translation.
  - domain package test:
    `internal/verify/verify_system_test.go` covers invariant-coded verify
    failures.
- Candidate Phase 2 questions:
  - which verify validations remain CLI-only by design versus duplicated in
    engine intentionally
  - whether engine should surface richer invariant/error metadata than the
    empty success-only `VerifyResult`
  - whether maintenance-layer existence checks are the right long-term owner

## `Remove`

- Active engine operation: yes, `Engine.Remove` is active for `file_ids` mode.
- Request type: `engine.RemoveRequest` in
  [candidates.go](/home/franchoy/vscode/coldkeep/coldkeep/internal/engine/candidates.go:309).
- Result type: `engine.RemoveResult` in
  [candidates.go](/home/franchoy/vscode/coldkeep/coldkeep/internal/engine/candidates.go:359).
- CLI validation:
  - `runRemoveCommand` still parses positional IDs, batch input, dry-run, and
    CLI-level usage failures before engine routing.
  - malformed textual file IDs remain CLI-owned validation failures.
- Engine validation:
  - `validateRemoveRequest` enforces `Mode == file_ids` and requires at least
    one file ID in
    [default_engine_routing_helpers.go](/home/franchoy/vscode/coldkeep/coldkeep/internal/engine/default_engine_routing_helpers.go:160).
  - per-item positive-ID validation remains engine-owned in `removeFileID`.
- Domain validation:
  - live removal delegates to `storage.RemoveFileWithDBResult`.
  - snapshot-retained deletion blocking is enforced in
    [remove.go](/home/franchoy/vscode/coldkeep/coldkeep/internal/storage/remove.go:95)
    via retention lookup and invariant-coded refusal.
  - ref-count consistency checks and logical-file removal invariants remain in
    `internal/storage`.
- Invariant and error propagation:
  - `internal/storage` creates `SNAPSHOT_RETAINED_DELETE_BLOCKED` invariant
    errors.
  - engine converts invariant-coded domain errors into per-item
    `InvariantCode` and `RecommendedAction` fields via
    `failedRemoveItemWithInvariant`.
  - invalid file IDs are item-level validation failures with no invariant code.
  - CLI owns final public batch JSON/text rendering.
- Explicit unsupported modes:
  - `stored_path` and `stored_paths` return `ErrNotImplemented`.
- Existing tests:
  - direct engine-level test:
    `internal/engine/remove_engine_test.go` covers live, dry-run, retained
    snapshot failure, and unsupported stored-path mode.
  - direct engine-level test:
    `internal/engine/validation_vs_unsupported_test.go` covers request
    validation versus unsupported classification and invalid file ID item
    behavior.
  - CLI preservation test:
    `cmd/coldkeep/remove_engine_routing_test.go` covers routed remove output.
  - domain package test:
    `internal/storage/remove_test.go` covers snapshot-retained and ref-count
    invariants.
  - integration test:
    `tests/integration/read_path_regression_test.go` covers snapshot-retained
    remove failures through CLI behavior.
- Candidate Phase 3 questions:
  - whether the current split between top-level request validation and item
    validation is the intended stable seam
  - whether remove dry-run/live semantics expose enough structured invariant
    metadata consistently
  - whether unsupported stored-path modes need more explicit documentation only

## `Restore`

- Active engine operation: yes, `Engine.Restore` is active for `file_ids` mode.
- Request type: `engine.RestoreRequest` in
  [candidates.go](/home/franchoy/vscode/coldkeep/coldkeep/internal/engine/candidates.go:202).
- Result type: `engine.RestoreResult` in
  [candidates.go](/home/franchoy/vscode/coldkeep/coldkeep/internal/engine/candidates.go:273).
- CLI validation:
  - `runRestoreCommand` still owns positional parsing, stored-path mode flags,
    destination semantics outside file-ID mode, and textual file-ID rejection.
  - malformed file IDs and stored-path destination policy remain CLI-owned.
- Engine validation:
  - `validateRestoreRequest` enforces `Mode == file_ids`, requires at least one
    file ID, and requires non-empty `OutputDir`.
  - per-item positive-ID validation remains engine-owned in `restoreFileID`.
- Domain validation:
  - dry-run delegates to `dryRunRestoreByID`, which checks logical-file
    completion state and output-path existence.
  - live restore delegates to `storage.RestoreFileWithStorageContextResultOptions`.
  - chunk recipe, container, hash, codec, and restore-safety invariants remain
    in `internal/storage/restore.go`.
- Invariant and error propagation:
  - restore currently propagates domain errors mainly as string messages in
    item results.
  - unlike remove, restore item results do not currently carry structured
    invariant code fields.
  - CLI owns final public success and error rendering.
- Explicit unsupported modes:
  - `stored_path` mode returns `ErrNotImplemented` at engine boundary.
  - stored-path destination-mode fields remain deferred contract shape.
- Existing tests:
  - direct engine-level test:
    `internal/engine/restore_engine_test.go` covers dry-run by ID, fail-fast,
    and unsupported stored-path mode.
  - direct engine-level test:
    `internal/engine/validation_vs_unsupported_test.go` covers validation
    versus unsupported classification.
  - CLI preservation test:
    `cmd/coldkeep/restore_engine_routing_test.go` covers routed JSON/text
    output.
  - domain package test:
    `internal/storage/restore_recipe_validation_test.go`,
    `internal/storage/restore_crossplatform_test.go`, and related restore
    tests cover recipe/order/output safety below engine.
  - integration test:
    `tests/integration/read_path_regression_test.go` covers by-ID restore
    correctness on real persisted data.
- Candidate Phase 4 questions:
  - whether output-path and overwrite safety should remain split between engine
    and storage layers
  - whether restore item failures need structured invariant metadata like remove
  - whether deferred stored-path fields overstate active engine ownership

## Initial findings

### Clearly engine-owned today

- `Verify` request target and level validation
- `Remove` top-level mode and non-empty file-ID batch validation
- `Remove` per-item positive file-ID validation
- `Restore` top-level mode, file-ID batch presence, and output-dir validation
- `Restore` per-item positive file-ID validation
- `Inspect` request entity and entity-ID validation

### Clearly domain-owned today

- verify-file existence and deeper repository verification invariants in
  `internal/maintenance` and `internal/verify`
- snapshot-retained delete blocking and ref-count consistency in
  `internal/storage`
- restore recipe, chunk, hash, and output-safety validation in
  `internal/storage`
- GC integrity refusal and FK-violation classification in `internal/gc` and
  `internal/maintenance`
- invariant-code definitions and recommended-action mapping in
  `internal/invariants`

### Still CLI-owned today

- textual command parsing and usage validation for `verify`, `remove`, and
  `restore`
- `verify file` string-to-int parsing and platform-int bounds rejection
- stored-path restore/remove command semantics that do not enter active engine
  routes
- snapshot read-side query parsing, richer filter semantics, and public success
  JSON assembly
- public JSON/text error envelope formatting, exit-code classification,
  invariant-code projection, and recommended-action rendering

### Transitional seams

- `StatsResult` wrapping `observability.StatsResult`
- `InspectResult` wrapping `observability.InspectResult`
- `SnapshotShow` mixed engine/catalog/snapshot ownership
- `SnapshotDiff` mixed CLI/engine/snapshot ownership
- deferred stored-path fields on active `RestoreRequest` and `RemoveRequest`
- invariant metadata sometimes exposed as wrapped errors and sometimes projected
  into per-item result fields

### Candidate guard gaps

- restore item failures do not currently project structured invariant metadata
  the way remove item failures do
- read-side count and filter ownership still depends on mixed seams that may
  benefit from narrower documentation-backed guards
- GC and repair-adjacent invariant metadata is public through CLI translation,
  but engine-facing consumers outside CLI may still rely on raw error-chain
  knowledge

## Phase 1 decision

Phase 1 is an inventory-only phase. No ownership migration is performed.
The next phases should review the highest-risk surfaces individually before
deciding whether any narrow guard tests are needed.
