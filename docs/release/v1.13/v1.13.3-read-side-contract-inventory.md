# Coldkeep v1.13.3 — Read-Side Contract Inventory

## Status

`complete`

## Purpose

This document inventories the current read-side contract surface before any
cleanup, test hardening, or boundary adjustment work begins in later
`v1.13.3` phases.

This is not an implementation phase.

This is not a routing migration.

This is not a behavior-change phase.

This does not redefine public CLI behavior.

This does not claim every read-side error is already taxonomy-wrapped.

This inventory is input for Phases 2 through 8.

## Relationship to v1.13.2

`v1.13.2` established the taxonomy baseline that `v1.13.3` must apply
carefully to read-side contracts without inventing a broad framework.

Relevant carry-forward baseline:

- `engine.IsUnsupported(err)` is a narrow helper for active unsupported engine
  modes backed by `engine.ErrNotImplemented`
- `catalog.IsDeferred(err)` is a narrow helper for deferred catalog metadata
  seams backed by `catalog.ErrNotImplemented`
- validation-versus-unsupported boundaries already have focused tests
- domain, invariant, runtime, catalog-origin, storage-origin, and environment
  surfaces were mapped without claiming full unification
- CLI translation preservation already exists as a public-boundary constraint
- unknown and provisional surfaces were recorded explicitly rather than
  overclassified

`v1.13.3` applies that baseline to `stats`, `inspect`, `snapshot show`, and
`snapshot diff`.

## Current Request/Result Shape Inventory

### `stats`

- CLI request shape:
  - no positional arguments
  - flags: `--output`, `--json`, `--containers`, `--trace`, `--trace-json`
- CLI entrypoint: `runStatsCommand`
- CLI phase variable: `runObservabilityStatsPhase`
- Engine request shape: `engine.StatsRequest`
  - `IncludeContainers bool`
  - `Trace observability.TraceOptions`
- Engine result shape: `engine.StatsResult`
  - thin wrapper with `Raw *observability.StatsResult`
- Observability result shape: `observability.StatsResult`
  - stable renderer-facing structure with repository, logical, physical,
    chunk, block-layout, container, efficiency, snapshot, retention, graph,
    and warning sections
- JSON renderer:
  - `internal/cli/render.JSONRenderer.RenderStats`
  - emits CLI envelope with `type: "stats"` and `meta.version: "v1.7"`

Current shape conclusion:

- the active engine contract is wrapper-shaped, not yet an engine-native stats
  result
- the renderer contract is observability-shaped

### `inspect`

- CLI request shape:
  - entity plus optional ID
  - flags: `--output`, `--json`, `--relations`, `--reverse`, `--deep`,
    `--limit`, `--trace`, `--trace-json`
- CLI entrypoint: `runInspectCommand`
- CLI phase variable: `runObservabilityInspectPhase`
- Engine request shape exists: `engine.InspectRequest`
  - `Entity observability.EntityType`
  - `EntityID string`
  - `Options observability.InspectOptions`
- Engine result shape exists: `engine.InspectResult`
  - thin wrapper with `Raw *observability.InspectResult`
- Active production path:
  - CLI constructs `observability.InspectOptions`
  - CLI calls observability service directly, not `eng.Inspect`
- Observability result shape: `observability.InspectResult`
  - `EntityType`, `EntityID`, `Summary`, optional `Metadata`, `Relations`,
    and `Warnings`
- JSON renderer:
  - `internal/cli/render.JSONRenderer.RenderInspect`
  - emits CLI envelope with `type: "inspect"` and `meta.version: "v1.7"`

Current shape conclusion:

- engine inspect request/result types exist, but current production ownership is
  still observability-first with a CLI bypass

### `snapshot show`

- CLI request shape:
  - positional `snapshotID`
  - flags: `--limit`, `--path`, `--prefix`, `--pattern`, `--regex`,
    `--min-size`, `--max-size`, `--modified-after`, `--modified-before`,
    `--output`, `--json`
- CLI entrypoint: `runSnapshotShowCommand`
- Active helpers:
  - `getSnapshotPhase`
  - `listSnapshotFilesPhase`
  - `snapshotStatsPhase`
- Candidate engine request shape exists: `engine.SnapshotShowRequest`
  - `SnapshotID string`
  - `Query engine.SnapshotQuery`
- Candidate engine result shape exists: `engine.SnapshotShowResult`
  - explicitly documented as provisional in `internal/engine/candidates.go`
- Active result/data shape:
  - snapshot metadata from `snapshot.GetSnapshot`
  - file entries from `snapshot.ListSnapshotFiles`
  - counts from `snapshot.GetSnapshotStats` through `snapshotStatsPhase`
- JSON output:
  - assembled directly in `cmd/coldkeep/main.go`
  - command field is `"snapshot"`
  - data action is `"show"`
- Human output:
  - `clirender.RenderSnapshotShowHuman`

Current shape conclusion:

- metadata, listing, counts, and rendering are still mixed seams
- candidate engine result shape must not be read as proof of unified ownership

### `snapshot diff`

- CLI request shape:
  - positional `baseSnapshotID` and `targetSnapshotID`
  - flags: `--summary`, `--filter`, `--path`, `--prefix`, `--pattern`,
    `--regex`, `--min-size`, `--max-size`, `--modified-after`,
    `--modified-before`, `--output`, `--json`
- CLI entrypoint: `runSnapshotDiffCommand`
- Active helpers:
  - `diffSnapshotsPhase`
  - `diffSnapshotSummaryPhase`
- Candidate engine request shape exists: `engine.SnapshotDiffRequest`
  - `BaseID`, `TargetID`, `Summary`, `Filter`, `Query`
  - documented as provisional
- Candidate engine result shape exists: `engine.SnapshotDiffResult`
  - documented as provisional, especially `SummaryMode`,
    `MatchedEntryCount`, and `TotalEntryCount`
- Active CLI behavior:
  - parses richer `snapshot.SnapshotQuery`
  - narrows/adapts into engine request
  - converts engine result back into `snapshot.SnapshotDiffResult`
  - applies filter behavior in CLI after engine call for detailed mode
- JSON output:
  - assembled directly in `cmd/coldkeep/main.go`
  - command field is `"snapshot diff"`
- Human output:
  - `clirender.RenderSnapshotDiffSummaryHuman`
  - `clirender.RenderSnapshotDiffDetailedHuman`

Current shape conclusion:

- current diff semantics span CLI parsing, engine adaptation, snapshot-shaped
  result reprojection, and distinct summary-versus-detailed output seams

## Current Domain Not-Found Behavior

Representative current domain/state-miss behavior:

- `inspect`
  - observability service uses `ErrNotFound` for missing snapshot, logical
    file, chunk, and container targets
  - CLI translates `observability.ErrNotFound` and `sql.ErrNoRows` into
    `NOT_FOUND` public code with entity-specific messages such as
    `snapshot <id> not found`
- `snapshot show`
  - direct snapshot helpers return string-backed domain errors such as
    `snapshot "snap-id" not found`
  - filtered exact-path lookup can surface `path not found in snapshot ...`
- `snapshot diff`
  - direct snapshot diff helpers and engine-backed seams surface string-backed
    domain errors when either snapshot is missing
- `stats`
  - no command-specific domain not-found surface was found; failures are mostly
    runtime, catalog, or environment flavored rather than state-miss flavored

Current domain conclusion:

- `inspect` has the clearest typed not-found boundary today
- `snapshot show` and `snapshot diff` still rely primarily on snapshot package
  string errors for domain misses
- current read-side not-found behavior is not unified across the four surfaces

## Current Invariant / Integrity Behavior

Phase 1 did not find a dedicated, stable read-side invariant wrapper contract
for `stats`, `inspect`, `snapshot show`, or `snapshot diff`.

Observed current-state:

- `stats`
  - may surface graph reachability mismatch warnings through
    `observability.StatsResult.Warnings`
  - graph enrichment cross-checks can add warnings without changing the public
    envelope shape
- `inspect`
  - primarily exposes entity lookup and relation-loading behavior; no
    dedicated invariant translation layer is active in the CLI path
- `snapshot show`
  - lineage and count information come from direct snapshot stats helpers, but
    current behavior is still framed as snapshot-domain and runtime behavior,
    not a separate invariant contract
- `snapshot diff`
  - no dedicated invariant contract was found in the active CLI path
- shared CLI error handling can attach `invariant_code` and
  `recommended_action` when an underlying error chain contains an
  `invariants.Error`, but this is a global CLI behavior rather than a
  read-side-specific contract for the four target commands

Current invariant conclusion:

- invariant behavior is mostly adjacent or indirect here, not a settled
  read-side contract surface

## Current Runtime / Catalog / Storage / Environment Error Surfaces

### `stats`

- runtime path:
  - CLI creates engine
  - engine delegates to observability service
  - observability delegates to maintenance stats collection and graph queries
- current wrapped failure examples:
  - `collect observability stats: ...`
  - `collect observability stats: enrich with graph: ...`
- likely origins:
  - catalog/database query failures
  - graph query failures
  - environment/runtime setup failures such as opening storage context or DB

### `inspect`

- runtime path:
  - CLI loads storage context
  - CLI creates observability service
  - observability performs entity-specific DB queries and relation lookups
- current wrapped failure examples:
  - `inspect repository logical_file count: ...`
  - `inspect snapshot <id>: ...`
  - `inspect snapshot <id> load logical references: ...`
- likely origins:
  - catalog/database query failures
  - environment/runtime setup failures

### `snapshot show`

- runtime path:
  - CLI loads snapshot DB
  - direct snapshot helpers query snapshot metadata, file lists, and stats
- likely origins:
  - database query or scan failures
  - runtime parsing failures from snapshot query parsing
  - environment failures when loading DB/storage context

### `snapshot diff`

- runtime path:
  - CLI loads snapshot DB
  - summary fast path or detailed diff path is chosen
  - detailed path adapts query into engine request and reprojects result
- likely origins:
  - database query or scan failures
  - runtime parsing failures from filter/query parsing
  - environment failures when loading DB/storage context

Current origin conclusion:

- active read-side failures still mix runtime, catalog, storage-adjacent, and
  environment signals without a unified typed origin layer
- this is consistent with the `v1.13.2` baseline and must remain documented
  honestly rather than force-classified

## Current CLI Preservation Boundaries

### Human output

- `stats`
  - renderer-owned human output in `internal/cli/render.HumanRenderer.RenderStats`
- `inspect`
  - renderer-owned human output in `internal/cli/render.HumanRenderer.RenderInspect`
- `snapshot show`
  - human output owned by `clirender.RenderSnapshotShowHuman`
- `snapshot diff`
  - human output owned by `clirender.RenderSnapshotDiffSummaryHuman` and
    `clirender.RenderSnapshotDiffDetailedHuman`

### JSON success envelopes

- `stats`
  - renderer-owned JSON envelope
  - top-level `type: "stats"`
  - `meta.version: "v1.7"` and `meta.exact: true`
- `inspect`
  - renderer-owned JSON envelope
  - top-level `type: "inspect"`
  - `meta.version: "v1.7"` and `meta.exact: true`
- `snapshot show`
  - CLI-owned JSON payload assembled directly in `cmd/coldkeep/main.go`
  - top-level `status: "ok"`, `command: "snapshot"`, `data.action: "show"`
- `snapshot diff`
  - CLI-owned JSON payload assembled directly in `cmd/coldkeep/main.go`
  - top-level `status: "ok"`, `command: "snapshot diff"`

### JSON error envelopes and exit codes

- shared CLI error path: `printCLIError`
- current error JSON includes:
  - `status`
  - `error_class`
  - `exit_code`
  - `message`
  - `error.code`
  - `error.message`
- optional fields may appear for invariants or verify-specific details, but
  these are shared CLI behaviors rather than read-side-specific redesign space
- exit codes are still classified by `classifyExitCode`
  - typed `cliError` first
  - message fallback matching second

Current preservation conclusion:

- `stats` and `inspect` success JSON are renderer-envelope contracts
- `snapshot show` and `snapshot diff` success JSON are CLI-assembled contracts
- all four commands still share the global error-envelope and exit-code
  behavior that later phases must preserve

## Stable-Enough Surfaces for v1.13.3 Cleanup

Current surfaces stable enough to clean up or protect in later phases:

- `stats` command entrypoint and renderer contract are explicit
- `inspect` direct observability bypass is explicit and test-documented
- `snapshot show` mixed ownership seams are explicit and test-documented
- `snapshot diff` summary fast path versus detailed path split is explicit
- `observability.ErrNotFound`, `ErrInvalidTarget`, and
  `ErrUnsupportedEntity` are real current observability error seams
- candidate engine snapshot request/result shapes already declare themselves
  provisional, which makes them safe to discuss honestly without freezing them
- CLI preservation boundaries for success JSON, error JSON, and exit codes are
  concrete enough to test against

## Provisional or Later-Decision Surfaces

- `engine.StatsResult` and `engine.InspectResult` remain wrapper-only around
  observability shapes
- `inspect` production routing still bypasses `eng.Inspect`
- `snapshot show` still mixes metadata lookup, file listing, count lookup, and
  CLI-owned rendering rather than exposing one settled read-side contract
- `snapshot diff` still narrows richer CLI query semantics before the engine
  seam and reapplies some filtering behavior after the engine call
- `engine.SnapshotShowRequest`, `SnapshotShowResult`,
  `SnapshotDiffRequest`, and `SnapshotDiffResult` are explicitly provisional
- `snapshot diff` `SummaryMode`, `MatchedEntryCount`, and `TotalEntryCount`
  remain provisional semantics, not frozen daemon/API-ready contracts
- read-side invariant behavior remains mostly indirect rather than a unified
  contract surface
- global CLI exit classification still depends partly on message fallback
  matching

  inventory scope remains `stats`, `inspect`, `snapshot show`, and
