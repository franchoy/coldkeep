# Coldkeep v1.13.6 Placement and Restore-Plan Contract Review

**Release:** `v1.13.6 — Catalog Contract Expansion and Backend Parity Review`  
**Phase:** Phase 4  
**Status:** Complete  
**Branch:** `release/v1.13.6`

## Purpose

This document reviews the catalog contract that describes where stored bytes
live and how restore derives a deterministic reconstruction plan from catalog
state.

It covers chunk identity, file chunk ordering, legacy container placement,
packed block placement, restore descriptors, packed/legacy parity, verify
placement expectations, read-side placement exposure, and backend-sensitive
placement behavior.

This phase performs no implementation work and adds no tests.

## Contract under review

The current placement and restore-plan contract is defined by:

- chunk identity
  - `chunk` rows are the durable content fragments referenced by logical files
  - chunk identity is content-addressed and may be reused by more than one
    logical file
- logical file chunk ordering
  - `file_chunk` records the ordered relationship between a logical file and its
    chunks through `chunk_order`
  - restore relies on that ordering being zero-based and contiguous
- legacy container placement
  - legacy placement is represented through `blocks`, where one chunk maps to a
    block row carrying codec, stored size, container ID, and block offset
- packed storage block placement
  - packed placement is represented through `storage_blocks` plus
    `chunk_block_refs`
  - a packed block may contain multiple chunk segments, and chunk rows reach
    their packed location through `chunk_block_refs.block_id`
- block/chunk/container relationships
  - legacy path: `file_chunk` -> `chunk` -> `blocks` -> `container`
  - packed path: `file_chunk` -> `chunk` -> `chunk_block_refs` ->
    `storage_blocks` -> `container`
- offset and stored-size assumptions
  - restore assumes persisted offsets and stored sizes are sufficient to locate
    payload bytes in a container
  - packed mode additionally requires valid `offset_in_block` and
    `size_in_block` segment metadata
- codec/compression/encryption metadata
  - placement metadata includes block codec, format version, stored size, and
    packed-block compression/hash metadata
  - restore and verify treat this metadata as part of the reconstruction and
    integrity contract
- restore descriptor generation
  - current-state restore can first resolve a `RestoreDescriptor` from
    `physical_file`
  - that descriptor is a path-addressed wrapper over the underlying logical
    file restore recipe
- restore ordering
  - restore output order is chunk-order driven even when physical reads are
    grouped by packed block
  - block read order must not change file reconstruction order
- fail-closed placement expectations
  - missing logical files, missing physical-file restore targets, unresolved
    chunk placement, non-contiguous `chunk_order`, hash mismatches, corrupt
    payload metadata, and missing containers must fail closed
- packed/legacy parity expectations
  - both packed and legacy placement are active first-class repository states
  - restore, verify, stats, and maintenance must describe both without silently
    assuming one storage mode

## Store-time placement

Store-time placement is actively owned by `internal/storage`, not by catalog.

- Chunk creation and reuse:
  - store claims or reuses logical files first, then chunks
  - chunk rows are content-addressed and may be reused across logical files
  - dedup changes reference structure and placement reuse decisions more than it
    changes logical recipe order
- `file_chunk` ordering:
  - store persists ordered chunk membership through `file_chunk`
  - `file_chunk.chunk_order` is derived from prepared chunk index order
  - finalization verifies that chunk order is contiguous from `0..n-1`
- Legacy placement writes:
  - legacy placement persists one `blocks` row per chunk
  - each row carries codec, format version, stored size, nonce, container ID,
    and block offset
- Packed placement writes:
  - packed placement builds encoded blocks, persists one `storage_blocks` row
    per block, then persists `chunk_block_refs` rows for each chunk segment in
    that block
  - packed placement therefore separates block-level stored bytes from
    per-chunk offsets within the block payload
- Container metadata, offsets, sizes, and hashes:
  - store records container references, physical offsets, stored sizes, and
    multiple hash layers
  - packed placement persists logical, compressed, and physical hash metadata
    in `storage_blocks`
- Compression and encryption metadata:
  - packed storage records compression codec and compression level
  - encryption codec and nonce handling remain placement-relevant because they
    affect how bytes are decoded during restore and verify
- Immediate validation:
  - store validates chunk-order contiguity and checks for invalid or missing
    placement rows before accepting reusable or completed state
  - placement integrity is therefore validated both during store-time
    finalization and later by verify
- Backend-sensitive observations:
  - store uses upsert and `RETURNING`-style insert paths in placement writes
  - mixed `blocks` / `storage_blocks` / `chunk_block_refs` joins make
    placement-integrity validation sensitive to backend query behavior

## Restore-plan derivation

Active restore-plan derivation remains storage-owned and transitional rather
than catalog-owned.

- Ordered chunk selection:
  - restore loads logical-file metadata and then loads ordered chunk rows from
    `file_chunk`
  - `pinLogicalFileRestoreChunksWithContext` reads the chunk recipe ordered by
    `fc.chunk_order ASC`
- Descriptor and recipe construction:
  - current-state stored-path restore can first resolve a `RestoreDescriptor`
    from `physical_file`
  - restore then builds a semantic `restoreRecipe` from ordered chunk rows and
    pinned chunk IDs
  - `validateRestoreRecipeOrdering` defensively checks that recipe indices are
    contiguous and aligned with slice order
- Legacy versus packed resolution:
  - restore treats `blocks` placement as the legacy path
  - restore treats `chunk_block_refs` plus `storage_blocks` as the packed path
  - the same logical recipe may therefore resolve through either placement
    surface depending on chunk state
- Packed block grouping and output-order preservation:
  - packed restore resolves each chunk to a `ChunkSegment`
  - `buildBlockReadPlan` groups reads by `block_id` to avoid repeated block
    reads
  - output ordering still follows original chunk order, never packed block read
    order
- Deterministic ordering expectations:
  - restore depends on stable `ORDER BY fc.chunk_order`
  - packed restore additionally depends on consistent block grouping and segment
    slicing without changing chunk-index output order
  - snapshot restore later adds path reconstruction on top of this ordered
    placement recipe
- Fail-closed expectations:
  - missing logical file rows fail
  - missing physical-file restore targets fail
  - missing exact snapshot restore selections fail higher in snapshot restore
  - non-contiguous chunk order fails during recipe validation
  - unresolved chunk placement, missing blocks, missing containers, decode
    failures, hash mismatches, plaintext-size mismatches, and out-of-bounds
    segment slicing fail closed
  - restore also fails closed on output-path safety violations
- Ownership boundary:
  - `RestorePlanCatalog` exists in catalog as a deferred neutral surface
  - active restore-plan generation today is storage-owned, with snapshot and
    engine layers wrapping it rather than replacing it
- Backend-sensitive observations:
  - restore-plan row ordering, JOIN cardinality, and placement-null handling are
    query-sensitive
  - packed/legacy selection uses mixed joins and `COALESCE` patterns that Phase
    6 must review for backend parity

## Packed/legacy placement parity

Packed and legacy placement coexist as current repository behavior.

- Coexistence model:
  - repository capabilities already describe both `legacy-single` and
    `packed-multi` packing modes
  - verify comments explicitly allow chunk reachability through legacy blocks,
    packed refs, or migration companion state
- Restore parity:
  - restore can reconstruct the same logical file through legacy or packed
    placement state
  - packed restore groups block reads and slices chunk segments
  - legacy restore reads payloads directly from block offsets
- Verify parity:
  - verify includes legacy-path consistency checks and packed-block decode
    checks
  - stage-aware packed verification validates stored payload, compressed
    payload, decoded block layout, and chunk entry consistency
- Stats and inspect parity:
  - observability surfaces already expose chunk, block, container, and
    packed-block summaries
  - packed placement gets explicit read-side metrics such as live/dead packed
    blocks and retained dead bytes due to packed blocks
- Migration/bootstrap compatibility:
  - repository capability derivation already inspects whether packed tables are
    present
  - bootstrap and migrations must preserve the ability to interpret both
    placement models
- Phase 7 evidence areas:
  - direct packed restore tests
  - direct legacy restore tests
  - mixed packed/legacy maintenance and GC tests
  - repository capability derivation tests for packing-mode visibility
  - release-gate evidence that PostgreSQL preserves the same parity

## Verify placement expectations

Placement verification is active below catalog and broader than the public
verify output contract.

- Chunk ordering validation:
  - verify system rules explicitly require `file_chunk.chunk_order` to be
    gapless and start at `0`
  - store-time validation overlaps this, but verify remains the broader safety
    path
- Legacy container validation:
  - verify checks legacy placement consistency through `blocks`
  - store-side validation helpers also check block offsets and container bounds
    for logical-file reuse safety
- Packed block validation:
  - packed verification validates block codec metadata, compression metadata,
    stored payload hashes, decoded block layout, and chunk slicing bounds
  - packed verification is stage-aware rather than just row-presence-based
- Metadata consistency expectations:
  - verify expects alignment between logical files, chunks, `file_chunk`,
    legacy blocks, packed block refs, and container metadata
  - metadata corruption, offset drift, or size drift is treated as placement
    integrity failure
- Invariant and staged error behavior:
  - verify uses stage-specific error framing for packed payload decoding and
    metadata violations
  - maintenance and CLI may later translate these into invariant-oriented human
    or JSON output, but that renderer behavior is outside Phase 4
- Public output separation:
  - the public verify CLI output remains CLI-owned
  - Phase 4 only documents the underlying placement assumptions that feed those
    outputs

## GC and maintenance placement assumptions

This phase records placement-related GC and maintenance assumptions only.

- Objects reclaimable at the placement layer:
  - legacy container-backed `blocks`
  - packed `storage_blocks`
  - `chunk_block_refs`
  - chunk rows and containers as maintenance/GC consequences
- Packed block reclaimability assumptions:
  - packed blocks are reclaimable only when their referenced chunks are no
    longer retained
  - observability and GC simulation already summarize live, dead, and retained
    packed-block impact
- Legacy container reclaimability assumptions:
  - legacy container references remain relevant for reclaimability because
    legacy `blocks` still describe real stored payload locations
  - delete behavior must preserve container/file integrity until placement rows
    are truly dead
- Restore and verify dependency:
  - GC and maintenance implicitly depend on placement metadata being sufficient
    for restore and verify to succeed before data is reclaimed
  - packed block reclaimability therefore depends on correct chunk-to-block and
    block-to-container linkage
- Phase 5 follow-up boundary:
  - Phase 4 does not decide reachability or GC safety conclusions
  - Phase 5 must revisit how retained logical roots, placement rows, and
    reclaimability interact

## Read-side placement exposure

Read-side placement exposure is broader than catalog and remains mostly
observability-owned.

- Stats counts:
  - stats expose chunk counts, container counts, block-layout summaries, and
    packed-block-related graph or maintenance summaries
  - repository capabilities and observability together make packed/legacy
    placement visible without making catalog the active owner
- Inspect relationships:
  - inspect supports chunk and container entities, plus reverse and graph-style
    relations
  - read-side relationships expose placement-adjacent structure, but those
    outputs are derived from broader repository state rather than a unified
    placement catalog
- Output-shape separation:
  - public read-side guards protect field presence and route semantics
  - they do not by themselves prove placement correctness, restore parity, or
    backend-neutral placement behavior
- Phase 7 evidence areas:
  - chunk/container inspect contracts
  - stats block-layout summaries
  - packed-block simulation and cross-consistency tests
  - read-side output-shape stability for placement-adjacent fields

## Backend posture

### Backend-neutral placement surfaces

- catalog neutral types already describe placement and restore-plan metadata
  without exposing DB handles or renderer types
- restore recipe ordering is expressed in terms of `chunk_order`, not backend
  driver behavior
- packed and legacy placement are both modeled as repository metadata rather
  than backend-specific runtime modes

### Backend-sensitive placement surfaces

- chunk ordering determinism depends on stable `ORDER BY fc.chunk_order`
- JOIN cardinality assumptions matter across `file_chunk`, `chunk`, `blocks`,
  `chunk_block_refs`, `storage_blocks`, and `container`
- NULL/default handling matters when a chunk has legacy-only, packed-only, or
  mixed migration companion state
- COUNT/GROUP BY aggregation differences matter for placement summaries and
  reclaimability reporting
- ORDER BY stability matters for restore recipe loading and packed block
  verification walks
- packed/legacy selection consistency depends on mixed join surfaces and
  `COALESCE`-style resolution
- `RETURNING` and insert behavior matter in store-time placement writes
- FK enforcement differences matter for orphan placement rows and delete/refuse
  behavior
- transaction isolation and row visibility affect placement reuse validation and
  restore pin/unpin safety

### SQLite-specific assumptions, if any

- many direct store, restore, verify, and observability tests run on in-memory
  SQLite
- some setup fixtures use SQLite-native conveniences, but production placement
  queries still aim to remain portable
- SQLite behavior with weakened or disabled FK enforcement is a later parity
  concern, not an implementation target in Phase 4

### PostgreSQL-specific assumptions, if any

- PostgreSQL parity evidence is narrower and often concentrated in focused
  contract or release-gate validation
- placement and restore-plan behavior still depends on broader PostgreSQL
  compatibility even where the most visible tests are SQLite-heavy
- lock/isolation behavior may differ around reuse validation and metadata
  mutation paths

### Dialect-adapted areas

- repository capability derivation adapts by schema layout and backend metadata
  inspection
- placement writes and readback paths rely on portable placeholder behavior but
  still deserve backend review around mixed joins and row-shape assumptions

### Phase 6 follow-up items

- chunk-order determinism and ordering guarantees across backends
- JOIN cardinality behavior in mixed legacy/packed placement queries
- NULL/default handling where placement roots are partially present
- COUNT/GROUP BY parity for packed-block summaries and placement aggregates
- ORDER BY stability for restore-plan loading and verify traversal
- packed/legacy selection consistency in mixed migration-compatible states
- `RETURNING`/insert behavior for placement writes
- FK enforcement differences for orphan or dangling placement rows
- transaction isolation around store-time placement validation and restore pinning
- PostgreSQL locking/isolation behavior where placement state is reused or
  mutated
- release-gate-only PostgreSQL evidence outside focused placement tests

## Phase 4 findings

### Stable current contract observations

- placement and restore-plan execution are actively storage-owned, while catalog
  placement and restore-plan surfaces remain intentionally deferred
- `file_chunk.chunk_order` is the core deterministic recipe boundary for restore
- legacy and packed placement are both live repository states that restore and
  verify must understand
- packed restore may optimize physical reads by block grouping, but it preserves
  chunk-order output semantics

### Backend-sensitive observations for Phase 6

- mixed placement queries rely on multi-table joins, `COALESCE`, and ordered
  traversal that deserve direct backend parity review
- store-time placement writes and restore-time readback rely on insert/row-shape
  semantics that can differ subtly by backend
- aggregate packed-block and container summaries may vary if backend grouping or
  NULL semantics diverge
- transaction isolation and FK behavior remain relevant for placement reuse,
  orphan-row detection, and delete/refuse behavior

### Coverage evidence for Phase 7

- contiguous `chunk_order` persistence and validation
- legacy restore reconstruction
- packed block reconstruction and segment slicing
- mixed packed/legacy compatibility behavior
- placement verification and corruption handling
- packed-block and container read-side summaries
- placement-related maintenance and GC simulation behavior
- focused backend evidence versus release-gate-only PostgreSQL evidence

### Phase 5 follow-up items

- how reclaimability of legacy blocks, packed blocks, chunks, and containers
  depends on retained logical reachability
- whether placement rows in mixed legacy/packed states can affect GC safety
  decisions
- how restore/verify placement assumptions feed GC refusal logic
- consistency between placement-level reclaimability summaries and retained-root
  eligibility decisions

### Immediate blockers

None found.

## Phase 4 decision

The current placement and restore-plan contract is broad but reviewable.

No Phase 4 production or test change is required.

`v1.13.6` can proceed to reachability and GC eligibility review in Phase 5.

Backend parity and test sufficiency remain intentionally deferred to Phases 6
and 7.
