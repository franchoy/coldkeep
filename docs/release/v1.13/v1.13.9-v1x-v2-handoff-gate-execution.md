## Summary

Phase 22 closes the remaining local tracker gap after Phase 21 froze the later
handoff-gate execution checklist but still left the checked-in `v1.13.9`
Phase 22 section and local acceptance criteria undefined.

This phase is docs-only. It does not execute the readiness review, does not
claim `v2.0` readiness, and does not change any CLI, engine, schema, storage,
script, or workflow behavior.

Its purpose is to define the exact checked-in Phase 22 scope so the eventual
handoff review can be performed without inventing scope.

## Intended role of the later handoff review

If a later explicit handoff-review or pre-release closure phase proceeds from
this definition, its intended role is limited to:

- final readiness review against the checked-in `v2.0` handoff requirements
- explicit mandatory versus deferred remainder
- honest statement of whether `v2.0` work can begin
- final release-gate documentation and validation artifacts only if the
  checked-in tracker explicitly requires them there

That later pass must not hide runtime behavior work inside a supposed handoff
review and must not overclaim readiness.

## Required later execution checklist

The later execution phase should record, at minimum:

- phase-list, validation-checklist, and release-train consistency
- snapshot create/delete/restore engine-routing closure status
- repair/recovery boundary status and explicit deferrals
- SQLite/PostgreSQL compatibility gate status
- CLI thin-wrapper review status and remaining coupling honesty gaps
- all remaining `v1.x` blockers before an honest `v2.0` start
- mandatory versus deferred remainder
- explicit “not in `v1.13.9`” items
- final `v2.0` readiness decision with no hidden runtime work folded into it

## Required later execution evidence

The later execution phase should collect, at minimum:

- checked-in release-doc state
- exact local validation outputs
- full release-gate command outputs
- explicit deferred and emergency-only inventory
- explicit readiness decision with rationale
- exact-head CI, CodeQL, and Codacy outcomes
- benchmark rerun or gate-risk notes only when they materially affect release
  honesty for the exact head

## Required readiness-decision criteria

The later execution phase should claim `v2.0` readiness only when the
checked-in handoff requirements are truly met, including:

- deferred engine operations are explicit and safe
- engine error taxonomy exists
- engine request/result contracts are no longer accidentally CLI-shaped
- critical invariants are engine/domain/catalog protected, not CLI-only
- dependency direction is CI-enforced for key boundaries
- catalog contracts are honest about implemented versus deferred ownership
- SQLite-first direction has a documented portability baseline
- PostgreSQL compatibility gates remain active
- remaining CLI direct coupling is classified as acceptable, emergency-only, or
  deferred
- no known open blocker contradicts the release-train handoff requirements
- no readiness claim depends on hidden runtime work or unresolved boundary
  ambiguity

## Deferred and out-of-scope framing

Any later handoff review should keep these boundaries explicit:

- daemon, API, and UI implementation remain deferred to `v2.0` or later
- any runtime behavior not already completed in the checked-in `v1.13.x` train
  remains deferred
- any repair or recovery activation beyond current checked-in ownership remains
  deferred
- any broader routing or backend redesign not explicitly proven complete in
  `v1.13.x` remains deferred
- explicit out-of-scope items must stay visible rather than being silently
  reclassified as release-ready
