## 3. Exact v1 coordination claim

The authoritative v1 claim is repository-wide, exclusive, fail-fast,
non-reentrant coordination among cooperative Coldkeep processes on one host
using a supported local filesystem. It includes:

- canonical repository identity and same-process reservation;
- Linux/Darwin `flock` and Windows `LockFileEx` ownership;
- explicit close and kernel-owned process-death release;
- diagnostic owner metadata that is never lock authority;
- representative independent-process contention and killed-holder proof;
- exclusive live-GC exclusion; and
- one dedicated PostgreSQL advisory-lock session for live GC.

It does not include hostile same-user sabotage, external replacement of the
active control namespace, cross-host coordination, NFS, SMB, NAS, arbitrary
network filesystems, cloud-synchronized directories, multi-daemon mutation,
remote leases, replication, or distributed locks. The PostgreSQL advisory
lock does not broaden the filesystem repository identity.

## 4. Architecture inventory

`internal/coordination` owns the contract, canonical identity, control
namespace, process registry, native handles, owner metadata, production
Coordinator, and stable sentinels. `cmd/coldkeep` owns pure operation policy,
one top-level lease wrapper, output spooling, public error classification, and
application dispatch. `internal/application` deliberately composes DB,
storage, and Engine without acquiring a hidden lease. `internal/maintenance`
adds the PostgreSQL live-GC advisory barrier.

The actual state sequence is:

```text
UNOWNED
→ PREPARING CONTROL NAMESPACE
→ SAME-PROCESS RESERVED
→ NATIVE LOCK ACQUIRED
→ OWNER METADATA ACTIVE
→ OPERATION EXECUTING
→ POSTGRES ADVISORY OWNERSHIP ACTIVE (inside PostgreSQL live GC only)
→ POSTGRES ADVISORY RELEASED
→ OWNER METADATA REMOVED
→ NATIVE LOCK RELEASED
→ SAME-PROCESS RESERVATION RELEASED
→ RELEASED
```

Preparation precedes reservation because the canonical container and control
directory must exist before the native artifact can be opened. This
coordination-namespace setup is not schema, recovery, catalog, or payload
mutation.

## 5. Repository identity

`ResolveIdentity` rejects blank, NUL-containing, UNC, and network paths; makes
the path absolute and clean; resolves existing symlinks; resolves the nearest
existing ancestor for missing leaves; and hashes the resulting canonical
path. Preparation resolves again and refuses an identity change.

Relative/absolute forms, `..`, duplicate/trailing separators, symlink aliases,
and missing-leaf aliases converge in tests. Windows normalizes the drive
letter. Other case variants may have different diagnostic hashes, but on a
case-insensitive supported filesystem they still open the same native lock
artifact, which remains authoritative and prevents two owners. Cooperative
Coldkeep alias use therefore has no trivial lock bypass. Bind-mount aliases
qualify only when they reach the same local backing lock artifact.

## 6. Control namespace

The fixed namespace is `<canonical repository>/.coldkeep-control`, created as
a real directory with mode `0700` beneath a canonical directory created with
mode `0755`. Existing files and symlinks are rejected; path components are
derived rather than caller supplied; final identity re-resolution closes the
creation-time alias change. Concurrent cooperative creation accepts the one
real directory and converges on the same artifact names.

The persistent `repository.lock` is never removed by Coldkeep. A malicious
same-user process with directory permissions could sabotage filesystem
objects, but hostile same-user protection is not a frozen v1 requirement.
No ordinary Coldkeep path unlinks or replaces the active lock artifact.

## 7. Same-process reservation

All `NewCoordinator` instances share one package-global registry keyed by the
validated canonical identity hash. A mutex makes insertion and conflict
detection atomic. Repeated ownership returns
`ErrNestedRepositoryAcquisition`, never waits or reference-counts. Release is
idempotent and removes an entry only if it is still the exact reservation, so
a stale release cannot free a successor. Concurrent same-identity race tests
admit exactly one reservation; different repositories remain independent.

```text
SAME_PROCESS_RESERVATION:
PROVEN
```

## 8. Owner metadata

`owner.json` is diagnostic only. The native kernel handle is the ownership
authority. The record is strict schema version 1 JSON containing bounded,
path-free PID, operation, UTC time, optional hostname/executable basename,
version, identity hash, and exclusive mode. It contains no repository path,
DSN, credentials, arguments, source, or destination.

Publication uses a same-directory temporary file, exact write, sync, close,
and platform replacement while the native lock is held. Reads accept at most
64 KiB and require a non-symlink regular file. Missing, malformed, stale, or
PID-reused metadata never grants or denies ownership. Removal is idempotent;
its failure alone cannot turn a successfully released native lock into a
failed ownership transition. A killed holder may leave stale diagnostics,
which the next native owner safely replaces.

```text
OWNER_DIAGNOSTICS:
PROVEN
```

## 9. Unix native locking

Linux and Darwin compile the same implementation. It checks the artifact,
opens it with `O_RDWR|O_CREAT|O_CLOEXEC|O_NOFOLLOW`, verifies a regular file,
and calls `flock(LOCK_EX|LOCK_NB)`. `EWOULDBLOCK`/`EAGAIN` map to Busy;
unsupported errors map to `ErrRepositoryLockUnsupported`; all other errors
retain their causes. Release explicitly unlocks then closes and joins cleanup
errors. The persistent file is not ownership; the open file description and
kernel lock are.

Local Linux native and race tests pass. Darwin runtime is required in the
exact-head cross-platform hosted job.

```text
NATIVE_UNIX_LOCKING:
PROVEN_WITH_EXPLICIT_BOUND
```

## 10. Windows native locking

Windows opens the persistent artifact through `CreateFile` with read/write
access, read/write sharing, `OPEN_ALWAYS`, and
`FILE_FLAG_OPEN_REPARSE_POINT`. It validates a disk file that is neither a
directory nor a reparse point, then locks one byte with
`LOCKFILE_EXCLUSIVE_LOCK|LOCKFILE_FAIL_IMMEDIATELY`. Lock violations map to
Busy, unsupported behavior maps explicitly, and release calls
`UnlockFileEx` followed by `CloseHandle`.

The source and tests cover artifact creation/content preservation,
directory/reparse rejection, contention, successor safety, different
repositories, 32 contenders, and error mapping. Exact-head Windows hosted
runtime is required because the Linux host cannot execute this implementation.

```text
NATIVE_WINDOWS_LOCKING:
PROVEN_WITH_EXPLICIT_BOUND
```

## 11. Acquisition/unwind

The production order is validate, prepare, reserve, native acquire, then
publish diagnostics. A reservation failure acquires nothing. A native failure
releases the reservation. An owner-publication failure releases native
ownership before the reservation and preserves both the publication and any
native cleanup error. No callback runs after failed acquisition.

PostgreSQL advisory acquisition happens later, inside an already-held outer
lease. Failed connection reservation or lock acquisition closes/discards the
dedicated connection and returns through the operation; `WithLease` then
releases the outer lease. No partial acquisition path grants two owners.

## 12. Release lifecycle

Normal repository release removes the diagnostic owner, unlocks/closes the
native handle, then releases the process reservation. `sync.Once` makes
concurrent and repeated release idempotent. A native release error is returned
and remains authoritative; an owner-removal error is joined only when native
release also fails. Operation and release failures remain joined with the
operation first.

For live PostgreSQL GC, advisory release occurs before the Engine/application
call returns and therefore before the outer repository lease releases. A true
unlock closes the owning connection normally; a false/error result discards
the uncertain physical session.

## 13. Independent-process contention

The G6 proof builds a real holder using the production Coordinator and starts
a separate real CLI process against the exact same repository. While held,
the contender receives the stable Busy/exit-1 contract, writes no
`logical_file` row, and never enters mutation. After explicit release, the
same CLI store succeeds and verification plus restore/hash checks pass.

This is true subprocess evidence, not a goroutine substitute. It is required
at the exact Phase 5 SHA in both plain and AES-GCM adversarial jobs.

```text
INDEPENDENT_PROCESS_CONTENTION:
PROVEN_WITH_EXPLICIT_BOUND
```

## 14. Killed-holder reacquisition

The Linux G6 killed-holder test sends `SIGKILL`, waits for process reaping,
leaves stale owner metadata untouched, and immediately performs the first
successful real CLI reacquisition without sleep, PID liveness checks, or force
unlock. The kernel releases `flock` when the killed process loses its file
descriptors. Windows closes process handles and releases `LockFileEx` locks on
termination by OS semantics; macOS uses the same kernel-owned `flock` model.

The frozen requirement does not demand duplicate killed-holder subprocess
fixtures on macOS and Windows. Native lifecycle executes on all three OSes;
the abrupt-process executable proof is explicitly Linux-bound.

```text
KILLED_HOLDER_REACQUISITION:
PROVEN_WITH_EXPLICIT_BOUND
```

## 15. Fail-fast semantics

Native acquisition is nonblocking on every supported platform. There is no
wait mode, ownership stealing, retry fallback, shared mode, or weaker
coordination path after native failure. Stable cause classification covers
Busy, unsupported locking, invalid identity, nested ownership, permission,
cancellation, deadline, and unexpected coordination I/O. CLI JSON/text
surfaces use safe stable codes while `errors.Is` retains underlying causes.

PostgreSQL live GC uses `pg_try_advisory_lock`, not a blocking acquire. A held
lock returns an explicit GC-already-running failure before destructive work.

## 16. Production operation coverage

The
[operation coverage matrix](v1.13.13-coordination-operation-coverage-matrix.md)
accounts for all 25 active Engine methods plus startup/schema work and CLI-only
tooling. Store, Store Folder, Remove, Repair, Doctor, Config set, snapshot
mutations, live GC, recovery, and migrations are coordinated. All ordinary
read routes, restore, Verify, and GC dry-run are also exclusive under the
conservative v1 policy.

One route is noncompliant: `PlanGarbageCollection` is consumed by
`simulate gc`, but `repositoryCoordinationPolicyFor` bypasses every `simulate`
subcommand. This is `P5-COORD-001`. `init`, simulated store/folder,
benchmarks, help, version, and invalid input are safe bounded bypasses.

## 17. Read-only operation boundary

The v1 model intentionally has no shared lock mode. List, Search, Stats,
Inspect, snapshot list/show/stats/diff, Verify, GC dry-run, and Restore all take
the exclusive lease. Restore also retains its pin lifecycle and writes user
destinations while protected from repository mutation. Read-only commands may
run corrective startup recovery, which is why their complete command lifetime
must remain inside exclusive ownership.

`simulate gc` is called a simulation but is not isolated: it opens the live
repository and builds the production GC plan. Its underlying compound Catalog
statement is coherent, but statement coherence does not waive the frozen
outer repository policy or acquire-before-schema rule.

## 18. Startup recovery/migration ordering

The audit distinguishes operations precisely:

| Stage | Classification | Normal participating CLI order |
| --- | --- | --- |
| Identity resolution/control preparation | coordination setup | before native acquisition as required to create/open the lock artifact |
| DB `sql.Open`/ping/query | `OPEN/READ` | inside dispatch after lease acquisition |
| `EnsurePostgresSchema`/SQLite migrations | `SCHEMA_MUTATION` / `MIGRATION` | inside application/session construction after lease acquisition |
| startup `Engine.Recover` | `RECOVERY_MUTATION` | inside lease before normal command dispatch |
| recovery quarantine/abort/container reconciliation | `RECOVERY_MUTATION` / `CLEANUP_MUTATION` | inside the recovery Engine call and lease |
| command Engine method | `NORMAL_OPERATION` | inside lease |

Opening a DB connection would not alone be a blocker. Current participating
CLI paths go further and correctly keep schema/recovery mutations behind the
lease. Direct callers are explicitly required to acquire before application
or DB setup.

The exception is `simulate gc`: its bypass dispatch calls
`application.Open` → `storage.LoadDefaultStorageContext` → `db.ConnectDB` →
`EnsurePostgresSchema`. With auto-bootstrap or an older supported schema, this
can mutate schema before any repository ownership; it then reads the shared
GC plan without a lease. Both consequences are one root, `P5-COORD-001`.

## 19. Live-GC exclusion

The normal `gc` command acquires the outer native lease before startup
recovery, DB/schema setup, Engine construction, integrity preflight, planning,
transactions, row locks, and filesystem deletion. Therefore Store, Remove,
snapshot mutation, Repair, Recovery, another GC, Restore, Verify, and every
other participating CLI operation fail fast while live GC owns the repository.

The Linux G6 test holds a real PostgreSQL relation barrier until the child GC
is observed in preflight, verifies the published GC owner, proves an
independent Store is Busy and writes no row, then permits GC and proves the
successor plus repository restores. SQLite live GC remains explicitly refused;
SQLite dry-run keeps the outer native lease.

```text

PROVEN_WITH_EXPLICIT_BOUND
```

## 20. PostgreSQL advisory-session ownership

The fixed GC key is `847362`. Live PostgreSQL GC rejects a one-connection pool,
reserves one `*sql.Conn`, calls `pg_try_advisory_lock` on it, and stores that
exact connection in `gcAdvisoryLock` for the complete preflight, plan, sweep,
and cleanup lifetime. Protected SQL may use the pool because the advisory lock
is an additional server-side singleton barrier; the owning session remains
checked out and unchanged throughout.

Release uses a fresh bounded cleanup context and calls `pg_advisory_unlock` on
the same `*sql.Conn`. A true result returns it normally. SQL error or false
result reports cleanup failure and uses `driver.ErrBadConn` so an uncertain
lock-owning physical session cannot reenter the pool. Connection/process loss
causes PostgreSQL to release the session lock automatically.

The four required hosted tests prove acquisition/unlock backend-PID equality,
held-lock exclusion, release after success and operation error, session
discard for both uncertain-cleanup forms, and the pool-capacity boundary.

```text
POSTGRES_ADVISORY_SESSION_OWNERSHIP:
PROVEN_WITH_EXPLICIT_BOUND
```

## 21. Filesystem/advisory lock relationship

The two layers protect different domains and are strictly ordered:

```text
same-host native repository lease
→ configured DB/schema/session setup
→ PostgreSQL live-GC advisory session
→ database transaction/row locks
→ catalog and payload mutation
→ advisory cleanup
→ application cleanup
→ native repository release
```

If advisory acquisition fails, the native lease remains held until the
operation unwinds. The advisory lock is not a replacement for the native
repository identity and cannot coordinate two hosts accessing shared payload
storage. Different container roots sharing one database remain unsupported.

## 22. SQLite coordination bound

Supported SQLite operations use the same outer process reservation and native
repository lease, with SQLite transaction/file-lock behavior inside it. Local
tests prove dry-run GC is allowed and live GC fails closed before mutation.
Phase 4 already established that live SQLite mutation workflow is an explicit
v2 productization bound. Phase 5 finds no hidden v1 SQLite coordination defect
and does not require future daemon serialization.

## 23. Path alias/reentrancy behavior

Legitimate cooperative path aliases converge through canonicalization or, on
case-insensitive filesystems, still reach the same authoritative native lock
artifact. Symlink aliases collide in the process registry tests. Identity is
revalidated after namespace creation. No supported alias produced two native
ownership domains in current source.

Coordination is intentionally non-reentrant. Same-goroutine and same-process
nested acquisition fail explicitly with `ErrNestedRepositoryAcquisition`; no
deadlock or silent reference count exists. Engine/lower helpers do not acquire
nested leases. Direct shared-repository callers own one outer lease.

## 24. Cancellation/error semantics

Pre-acquisition cancellation/deadline stops before side effects. Native
acquisition is fail-fast rather than cancellable waiting. Operation contexts
run synchronously while the outer lease remains held; callback return triggers
release, so ownership is not released while synchronous work continues.

Advisory acquisition honors its caller context. Advisory cleanup deliberately
uses a new bounded background context so cancellation cannot strand an owned
session; uncertainty discards it. Stable CLI mapping preserves Busy,
unsupported, invalid, nested, permission, cancellation, deadline, and internal
causes. No coordination-specific error defect was found.

## 25. Same-host versus distributed boundary

The canonical identity is a local container path and the authority is a local
kernel lock artifact. This supports cooperative same-host processes reaching
the same local backing artifact. Source and current documentation explicitly
exclude UNC/network paths and say the contract is not distributed.

NFS/SMB/NAS lock semantics, cloud sync, cross-machine clients, multi-daemon
mutation, replication, and distributed leases remain v3 expansion. A shared
PostgreSQL database does not change that conclusion because payload and native
repository ownership remain outside the advisory session.

## 28. Findings

### `P5-COORD-001` — live-repository `simulate gc` bypasses the outer lease

- **Root invariant:** every real/shared-repository operation that can perform
  repository mutation or depends on the exclusive v1 view must acquire before
  DB/schema setup and retain ownership through cleanup.
- **Requirements:** `V1R-COORD-001`; operation coverage supporting
  `V1R-COORD-002`.
- **Platform/backend:** platform-neutral CLI policy; current production
  PostgreSQL application session on Linux, macOS, and Windows.
- **Source:** `repositoryCoordinationPolicyFor` returns zero policy for all
  `simulate`; `runSimulateGCCommand` calls `runObservabilitySimulateGCPhase`;
  that opens a real `application.Session`; `db.ConnectDB` calls
  `EnsurePostgresSchema`; Engine then runs `PlanGarbageCollection` against the
  shared catalog.
- **Production route:** `coldkeep simulate gc [options]`.
- **Reasoning:** unlike simulated store/folder, the GC simulation has no
  temporary SQLite context. It can auto-bootstrap or migrate schema before any
  lease and can plan against the live repository while another Coldkeep
  process owns the native lease.
- **Test evidence:** existing policy tests explicitly assert `simulate` bypass;
  `TestRunCLISimulateSkipsStartupRecovery` confirms the uncoordinated runtime
  branch; Phase 2 routing evidence confirms the live Engine application path.
- **Why guards missed it:** policy/static guards classify only the top-level
  command and inherited the stale “isolated simulation” premise. No guard
  separates `simulate gc` from isolated simulation subcommands or prohibits a
  shared application session on an uncoordinated route.
- **Consequence:** a normal cooperative Coldkeep process can bypass exclusive
  ownership, including the acquire-before-schema-mutation rule. A generic
  coherent SQL statement does not satisfy the repository coordination
  contract.
- **Scope:** one operation-policy root; schema and plan effects are not counted
  separately. This is not hostile same-user sabotage or distributed scope.
- **Remediation:** required; Phase 6 must freeze disposition. Phase 5 designs
  or implements no fix.
- **Relationship:** distinct from `P2-ARCH-001`, `P3-COR-001`–`003`, and
  `P4-BE-001`.

No other new coordination root was found. Static enforcement strongly pins
native and hosted process selectors but does not yet prevent this subcommand-
specific policy drift; that missing guard is evidence about the same root, not
a second finding.
