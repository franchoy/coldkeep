## Purpose

This document reviews the current dependency direction, result ownership,
renderer ownership, JSON ownership, and taxonomy boundaries for the `inspect`
read-side surface.

The goal is to decide whether the current direct CLI-to-observability inspect
path is acceptable for `v1.13.x` and what, if anything, should be deferred to
later releases.

This phase is documentation-only and does not change runtime behavior.

## Current `inspect` flow

Observed current production flow:

`runInspectCommand` -> CLI validation and supported-target parsing ->
`runObservabilityInspectPhase` -> observability service -> renderer

Current path details:

- CLI entrypoint is `runInspectCommand` in `cmd/coldkeep/main.go`
- CLI parsing and validation stay in `cmd/coldkeep` through:
  - `ensureAllowedFlags`
  - usage and positional arity checks
  - `resolveTraceOptions`
  - `validEntities` target parsing map
  - numeric-ID validation for `file`, `chunk`, and `container`
  - `--limit` parsing
- supported public CLI targets are:
  - `repository`
  - `file`
  - `logical-file`
  - `snapshot`
  - `chunk`
  - `container`
- `logical-file` is a public CLI alias that routes to
  `observability.EntityFile`
- internal-only observability entity:
  - `EntityPhysicalFile` exists in `internal/observability/types.go`
  - it is not exposed as a public CLI target
- `runObservabilityInspectPhase` loads the default storage context,
  constructs the observability service directly, and calls `svc.Inspect`
- production `inspect` bypasses engine even though engine wrappers exist
- result type owner in production is `observability.InspectResult`
- human renderer path uses `internal/cli/render.HumanRenderer.RenderInspect`
- JSON success output path uses `internal/cli/render.JSONRenderer.RenderInspect`
- JSON error output path remains CLI-owned through:
  - `observabilityErrorf` for invalid argument and not-found translation
  - `observabilityWrappedError` for internal failures
- taxonomy-boundary behavior currently centers on:
  - `observability.ErrInvalidTarget`
  - `observability.ErrNotFound`
  - `observability.ErrUnsupportedEntity`
  - these helpers do not surface as public taxonomy fields in CLI output

## Dependency-direction finding

The current `inspect` dependency direction is acceptable for `v1.13.x` as a
documented transitional seam: production `inspect` continues to call
observability directly rather than routing through engine.

Observed findings supporting that decision:

- production `inspect` bypasses engine and calls observability directly
- observability owns the concrete inspect read logic and inspect result shape
- CLI owns command validation and public error translation
- renderer owns human output and JSON success envelope emission
- unsupported/deferred taxonomy helpers are not exposed publicly

This is a mixed-but-stable seam rather than a broken one. The repo evidence
shows active production use, clear public target behavior, and no current
correctness or contract bug that requires routing `inspect` through engine in
`v1.13.4`.

## Why not route through engine now

`v1.13.4` should not move `inspect` behind a new engine seam now.

Reasons:

- routing through engine now risks public JSON drift
- it also risks error-mapping drift and supported-target drift
- it could duplicate result types or hide unresolved ownership questions behind
  a thin wrapper
- this release is an ownership-review release, not a broad routing migration
- no discovered correctness bug justifies changing routing in Phase 3

## Gaps and deferred work

| Gap | Risk | Recommended handling |
| --- | ---: | --- |
| Direct CLI-to-observability dependency | Medium | Document as transitional and defer engine inspect seam decision |
| Inspect result owned by observability | Medium | Defer result ownership migration |
| Public target list not engine-owned | Low/Medium | Preserve current behavior; consider later guard tests if needed |
| JSON success envelope remains renderer-owned while public error mapping stays CLI-owned | Low/Medium | Review in Phase 6 |
| Backend parity evidence mostly indirect at CLI level | Low/Medium | Review in Phase 8 |

These are ownership and guardrail gaps, not current correctness blockers.

## Decision for v1.13.4

For `v1.13.4`, keep the current `inspect` dependency direction unchanged.

Treat production `CLI -> observability` inspect routing as a documented
transitional seam.

Preserve supported targets, output, and error behavior rather than
introducing a new engine-owned inspect seam in this release.
