# Coldkeep v1.13.13 Release-State Validator Contract

**Release:** `v1.13.13 — Final v1.x and v2 Handoff Gate`
**Status:** Active
**Branch:** `release/v1.13.13`

## Applicability

v1.13.13 reuses the existing generic fail-closed release-state validator and
CKRS rule set without implementation changes. Active source identity is
`1.13.13`.

## Development contract

- The branch must be `release/v1.13.13`.
- No `v1.13.13` tag may exist during development.
- The phase topology is one contiguous, ordered Phase 0–16 sequence in both
  the phase list and validation checklist.
- Development progression is `Complete*`, exactly one `Next`, then
  `Not started*`.
- Active scope, phase-list, and validation-checklist release/title/status
  metadata must agree.
- Canonical v1.13.12 scope, gate, and current release-train evidence must prove
  released and operationally closed status.

The expected Phase 0 development result is:

```json
{"status":"ok","validator":"coldkeep-release-state","state":"development","active_version":"1.13.13","violations":[],"error":null}
```

## Lifecycle separation

Development, candidate/pre-release, merged-not-tagged, tag validation, and
released/publication states remain distinct. Candidate PASS does not imply a
merge, a tag, publication, or v1.x closure. Publication is separate from both
candidate and merge evidence.

v1.x closure cannot be inferred merely from release candidate PASS. It
requires the Phase 13 formal decision after all genuine blockers are closed
and complete local and hosted evidence is green.
