# Coldkeep v1.13.7 SQLite Local Catalog Placement Contract Review

**Release:** `v1.13.7 — SQLite-First Repository Portability Baseline`
**Phase:** Phase 2
**Status:** Complete
**Branch:** `release/v1.13.7`

## Purpose and status

This document records the proposed contract target for a future SQLite-first
local repository mode.

It does not claim that the contract is already implemented in current runtime
code.

This phase does not authorize:

- backend-default changes
- normal local SQLite mode enablement
- catalog relocation
- checkpoint commands
- portability tests
- runtime behavior changes

Current runtime behavior remains unchanged.

## Current-state baseline

Current normal local runtime behavior still resolves
`COLDKEEP_STORAGE_CONTEXT=local` to PostgreSQL-backed local mode.

Supporting current behavior:

- `storage.LoadDefaultStorageContext()` defaults blank or unset
  `COLDKEEP_STORAGE_CONTEXT` to `local`
- `storage.ParseStorageContext("local")` calls `db.ConnectDB()`
- `db.ConnectDB()` builds a PostgreSQL connection and validates PostgreSQL
  schema state

Current production SQLite behavior is limited to simulated mode, not normal
local runtime.

Current observed production SQLite path:

- `storage.ParseStorageContext("simulated")` creates a temp DB with
  `os.CreateTemp("", "coldkeep-sim-*.db")`
- the resulting SQLite path is absolute and outside any repository root
- `sql.Open("sqlite3", temp path)` opens that file
- simulated mode applies `SetMaxOpenConns(1)` and `SetMaxIdleConns(1)`
- `db.ApplySQLiteSessionPragmas()` applies
  `PRAGMA busy_timeout = <statement-timeout-ms>` and
  `PRAGMA foreign_keys = ON`
- `db.RunMigrations()` is the active SQLite schema/bootstrap path
- `StorageContext.Close()` closes the DB handle and removes the temp DB file

Current code does not establish an explicit runtime policy for:

- `PRAGMA journal_mode`
- `-wal` companion files
- `-shm` companion files
- rollback-journal ownership
- explicit checkpoint behavior

Tests create many additional SQLite handles, including `:memory:` and
test-specific on-disk paths, but those do not define current normal runtime
catalog placement.

## Terminology

**Repository root**
The intended stable top-level directory boundary for a portable local
repository.

**Catalog path**
The on-disk path of the metadata catalog database for a local repository mode.

**Payload-storage root**
The repository-owned root that contains payload/container files rather than
catalog metadata.

**Container directory**
The current packed-container path derived from `COLDKEEP_STORAGE_DIR` with
fallback `./storage/containers`.

**Packed-block storage**
The on-disk payload/container artifacts referenced by catalog rows.

**Repository-owned state**
Filesystem state that must travel with a portable local repository because it
belongs to the repository contract rather than host-local or process-local
configuration.

**Process-working-directory-relative path**
A path whose meaning changes with the caller's current working directory rather
than a stable repository-root-relative contract.

**External catalog**
A catalog that is not stored as repository-owned local files under a repository
root, such as the current PostgreSQL-backed normal local mode.

**Portable local catalog**
A future local catalog whose path and companion state are repository-owned and
portable as part of a repository directory contract.

**Active SQLite sidecar files**
SQLite companion files such as `catalog.sqlite-wal`, `catalog.sqlite-shm`, or
`catalog.sqlite-journal` whose presence may reflect active or recently active
catalog state.

**Cleanly closed repository**
A repository state where all known catalog DB handles are closed and no active
writer or process is expected to continue mutating repository state.

**Checkpointed-and-closed repository**
A stronger future portability state where catalog changes have been durably
consolidated before copy or move and the repository is also cleanly closed.

## Repository-root posture today

Coldkeep does not currently expose a formal repository-root abstraction in the
normal runtime path.

Current path ownership is split across independent surfaces:

- PostgreSQL catalog location is external and derived from `DB_*` env vars
- payload/container storage is derived from `COLDKEEP_STORAGE_DIR` with
  fallback `./storage/containers`
- simulated SQLite uses a temp DB path from `os.CreateTemp`

Current implications:

- a single common repository root is not guaranteed by current runtime code
- relative payload paths depend on process working directory unless
  `COLDKEEP_STORAGE_DIR` is set explicitly
- simulated SQLite catalog placement is not repository-root-relative
- PostgreSQL normal local mode uses an external catalog rather than a local
  repository-owned catalog file

This is why Phase 2 can define a future target contract but cannot claim that
the contract already exists in current runtime behavior.

## Proposed SQLite local catalog placement contract

The future target local catalog path should be:

`<repository-root>/.coldkeep/catalog.sqlite`

This path is the proposed contract target for a future normal local
SQLite-backed repository mode.

Contract expectations:

- `.coldkeep/` is repository-owned metadata state
- `catalog.sqlite` is the repository-owned local metadata catalog
- payload/container files remain outside the SQLite database
- payload/container files are not embedded in SQLite blobs as the local
  repository contract
- catalog placement should be deterministic from repository root, not from
  process working directory

This section defines the desired placement target only.

It does not mean current runtime already stores its normal local catalog there.

## Repository-owned SQLite sidecar contract

When present, the following files should be treated as repository-owned catalog
state:

- `catalog.sqlite-wal`
- `catalog.sqlite-shm`
- `catalog.sqlite-journal`

Future contract implications:

- these files are part of repository catalog state, not disposable clutter
- portability review must treat them as meaningful repository-owned artifacts
- move/copy safety cannot be judged by `catalog.sqlite` alone when sidecars are
  present

Current runtime code does not explicitly manage these files yet.

This section therefore defines the future contract target, not a current
runtime guarantee.

## Open, close, copy, and move safety boundaries

**Active repository**
A process may still hold SQLite handles, sidecar state may still be in flux, or
payload/container state may still be mutating.

**Cleanly closed repository**
All known DB handles are closed and no active writer or process is expected to
continue mutating repository state.

**Checkpointed-and-closed repository**
Catalog state has been durably consolidated before copy or move and the
repository is also cleanly closed.

Contract conclusions:

- an active repository is not portable-by-copy
- a cleanly closed repository is a portability precondition, not a full
  integrity proof
- checkpointed-and-closed is the strongest proposed portability state for a
  future SQLite-local repository contract

Current runtime does not yet guarantee a user-facing local SQLite repository can
be placed into these states because normal local SQLite mode is not yet the
runtime default and checkpoint behavior is not explicitly defined.

## Catalog and payload consistency limits

`catalog.sqlite` being readable or structurally valid is not sufficient to
prove repository portability.

Current code shape already shows that catalog durability and payload/container
durability are separate domains.

Observed implications:

- catalog rows can reference payload/container state
- payload/container artifacts can be incomplete, quarantined, missing, or
  otherwise inconsistent with catalog expectations
- repository portability therefore cannot be proven by catalog state alone

Future portability validation must consider both:

- catalog state
- payload/container state

The full cross-artifact portability contract belongs to Phase 3.

## Path and portability requirements

The future local portable contract should converge on deterministic
repository-owned paths under a repository root.

Contract direction:

- repository-owned paths should derive from repository root
- process-working-directory-relative fallbacks are weaker than
  repository-root-relative paths for portability
- current `./storage/containers` fallback is evidence of today's looser path
  contract, not the future target
- a future local SQLite catalog should not rely on host temp directories or
  transient process-owned locations

This phase does not change current path derivation.

It records the path discipline required before Coldkeep can claim a portable
SQLite-first local repository posture.

## Secrets and configuration boundary

Repository portability does not imply bundling secrets.

Current secret/config boundaries remain:

- encryption key/bootstrap material comes from env or a `.env` created by
  `coldkeep init`
- PostgreSQL credentials remain external env configuration

Future implications:

- a future SQLite-local portable repository may still depend on external
  secrets or configuration
- repository-owned catalog placement does not automatically mean
  self-contained secret portability

Phase 2 does not change this boundary.

## PostgreSQL coexistence

PostgreSQL compatibility remains mandatory.

Contract conclusions:

- PostgreSQL-backed repositories remain supported even if future local SQLite
  portability is introduced
- PostgreSQL mode remains an external-catalog mode
- copying payload/container directories alone does not make a PostgreSQL-backed
  repository directory-portable
- SQLite-first roadmap direction does not deprecate PostgreSQL in `v1.13.7`

This phase defines a local SQLite portability target while preserving
PostgreSQL-supported operation and release-gate expectations.

## Gaps and Phase 3 follow-up

Current gaps that prevent a stronger portability claim today:

- no normal local SQLite runtime path
- no formal repository-root abstraction
- no explicit sidecar/checkpoint contract in runtime code
- split path ownership between DB env, container-dir env, and temp SQLite paths

Phase 3 should use this contract review as input to define the broader
repository portability contract, including cross-artifact consistency
expectations and move/reopen validation posture.
