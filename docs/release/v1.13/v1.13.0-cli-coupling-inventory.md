# v1.13.0 CLI Direct-Domain Coupling Inventory

## Purpose and Coupling Rules

This document inventories direct `cmd/coldkeep` coupling into internal packages after v1.12.3. It
is documentation only. It does not change CLI behavior, engine routing, JSON, exit codes, schema,
or implementation.

Operation-type labels used here:

- `read-only`
- `mutating`
- `destructive`
- `maintenance`
- `recovery`
- `benchmark/tooling`
- `configuration/bootstrap`

Conservative rules used here:

- Direct imports are not automatically bad.
- Formatting and rendering coupling is usually acceptable; CLI-owned business behavior, mutation
  order, validation authority, restore/GC decisions, and recovery policy are the important risks.

## Import Surface Snapshot

Production `cmd/coldkeep/main.go` directly imports these internal packages:

- `internal/batch`
- `internal/benchmark`
- `internal/blocks`
- `internal/chunk` plus chunk benchmarkers
- `internal/container`
- `internal/db`
- `internal/engine`
- `internal/execution`
- `internal/invariants`
- `internal/iodebug`
- `internal/listing`
- `internal/maintenance`
- `internal/observability`
- `internal/recovery`
- `internal/snapshot`
- `internal/storage`
- `internal/verify`

This inventory does not treat every import as equally problematic. It focuses on meaningful direct
orchestration paths where the CLI still owns business behavior, mutation sequencing, destructive
policy, maintenance/recovery behavior, or read-shape assembly that matters to future daemon/API
ownership.

## Findings

- Total CLI coupling items inventoried: 24
- `read-only`: 6
- `mutating`: 7
- `destructive`: 4
- `maintenance`: 1
- `recovery`: 2
- `benchmark/tooling`: 1
- `configuration/bootstrap`: 3

### Count Summary By Engine Equivalent

- `yes`: 3
- `no`: 5
- `partial`: 10
- `candidate`: 6
- `unclear`: 0

### Highest-Risk Direct CLI Ownership Items

- `CK-1130-CLI-004` `inspect`: active engine equivalent exists, but production CLI still bypasses it.
- `CK-1130-CLI-009` and `CK-1130-CLI-010` restore paths: stored-path restore remains direct, and
  even by-ID restore still depends on substantial CLI orchestration.
- `CK-1130-CLI-011` and `CK-1130-CLI-012` remove paths: stored-path remove stays direct and the
  destructive batch semantics are still CLI-owned.
- `CK-1130-CLI-014`, `CK-1130-CLI-018`, and `CK-1130-CLI-019`: snapshot create/delete/restore are
  still fully CLI/domain-owned despite candidate contracts.
- `CK-1130-CLI-020`, `CK-1130-CLI-021`, and `CK-1130-CLI-022`: repair and recovery remain the most
  sensitive direct CLI-owned orchestration because they control corrective and emergency behavior.

### Acceptable Short-Term CLI Helpers Versus Real Ownership Risks

Reasonably acceptable short-term CLI helpers:

- storage-context bootstrap
- container-path/bootstrap defaults
- basic DB/context setup
- tooling and benchmark entrypoints that are explicitly outside engine scope

Business-logic ownership that still matters for v1.13.x stabilization:

- direct observability inspect path
- verify summary shaping outside engine results
- folder store orchestration
- stored-path restore/remove
- snapshot create/show/delete/restore orchestration
- repair and recovery sequencing

### Bottom Line

The remaining CLI coupling is not primarily a formatting problem. The real risks are:

- CLI-owned mutation/destructive sequencing
- CLI-owned validation and option authority
- CLI-owned maintenance and emergency recovery policy
- read workflows where the CLI still assembles business-significant result shape outside the engine

That means v1.13.x should prioritize separating engine ownership from CLI orchestration before any
daemon/API readiness claim.
