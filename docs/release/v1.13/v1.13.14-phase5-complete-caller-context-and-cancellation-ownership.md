`db.NewOperationContext(context.Background())` context. Batch methods must stop
before new dispatch and retain completed results. Operation and cleanup errors
must remain jointly discoverable through `errors.Is`.

## 3. Context ownership map

| Engine operation | Ordinary-work context path | Safety-cleanup owner |
| --- | --- | --- |
| Store | `Engine.Store` → context-aware single-file storage wrapper → prepare/claim/write/commit | bounded logical-file abort plus required writer finalization |
| Remove | `Engine.Remove` → per-item context-aware metadata lookup or remove transaction | transaction rollback; rollback failure joins the operation error |
| RemoveStoredPaths | `Engine.RemoveStoredPaths` → context-aware path lookup or unlink transaction | transaction rollback; rollback failure joins the operation error |
| Restore | `Engine.Restore` → context-aware metadata lookup, pin, read/decode, and publication | bounded unpin and restore-install abort |
| RestoreStoredPath | `Engine.RestoreStoredPath` → context-aware descriptor lookup and shared restore execution | bounded unpin and restore-install abort |
| Verify | `Engine.Verify` → result-bearing maintenance context entry → system/file verification graph | read-only resource cleanup; no detached ordinary work |
| Doctor Recovery | caller context → existing context-aware recovery | existing bounded recovery safety behavior |
| Doctor Schema | caller context → `CurrentSchemaVersionContext` | none |
| Doctor Verify | caller context → corrected Engine Verify path | Verify ownership above |
| Doctor Audit | caller context → context-aware physical and snapshot audit summaries | read-only resource cleanup |

Contextless lower APIs that remain part of existing compatibility behavior now
delegate through `context.Background()` to the context-aware implementation.
StoreFolder, snapshot operations, observability reads, GC, repair, and other
already-correct or unrelated methods were not rewritten.

## 4. Cancellation, deadline, and batch behavior

Remove, RemoveStoredPaths, and Restore check `ctx.Err()` before each new
sequential item. They also check after completed item execution so a signal at
the safe boundary returns immediately. This rule is independent of `FailFast`.
Earlier completed items remain in the public result and undispatched items are
reported by the existing summary semantics.

Focused proof covers both `FailFast` values, all three batch families, a
completed first item, a canceled boundary, one undispatched item, a non-nil
top-level cancelled error, and truthful partial results. Explicit canceled and
expired contexts retain `ErrorCancelled`; `errors.Is` finds
`context.Canceled` or `context.DeadlineExceeded`.

Verify cancellation returns the zero `VerifyResult` plus `ErrorCancelled`.
It is not translated to `ErrorVerificationFailed`. The Phase 4
fast/standard/full/deep, system/file, layout, compression, and failure-zero
counter suites remain unchanged and pass.

Doctor preserves its explicit nil-to-Background behavior. It passes the caller
context to Recovery, Schema, Verify, and Audit and checks cancellation after
each successful stage, so a canceled caller cannot start the next stage.
Schema and Audit cancellation now retain `ErrorCancelled` just like Recovery
and Verify.

## 5. Bounded safety cleanup and error composition

Ordinary work never replaces the caller context with a background context.
Mandatory cleanup remains independently bounded:

- Store marks an incomplete logical file aborted under a bounded cleanup
  context and always performs required single-file writer finalization;
- Remove rolls back failed transactions and joins rollback failure;
- Restore unpins every pinned chunk under a bounded cleanup context and aborts
  the secure temporary installation even after caller cancellation;
- cancellation, deadline, finalization, rollback, unpin, and temporary-abort
  causes remain visible through `errors.Is`.

Deterministic cleanup regressions prove joined Store cancellation/finalization,
Remove cancellation/rollback, and Restore cancellation/abort failures. Restore
also proves pin counts return to zero and the failed result is zero. Existing
temporary-file cleanup and destination-preservation suites remain green.

contracts and are backend-neutral. SQLite supplies deterministic local
fixtures. Existing backend contract suites and exact-head hosted CI retain the
PostgreSQL matrix. Restore cleanup remains platform-neutral and existing Linux,
macOS, and Windows restore suites remain the hosted authority.

the race detector. Test state is per Engine, `StorageContext`, or SQL connector;
there is no shared mutable production hook, sleep synchronization, blocked
goroutine, double cleanup, stale pin, or post-cancellation dispatch.
