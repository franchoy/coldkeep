## Executive freeze

- `snapshot create`, `snapshot delete`, and `snapshot restore` are still
  direct CLI/domain-owned candidate operations.
- No active `Engine` interface methods own these mutation commands today.
- Candidate request/result types exist in `internal/engine/candidates.go`, but
  they are not activated.
- `snapshot create` is CLI-owned for snapshot ID generation, snapshot-type
  derivation, and post-create `COUNT(*)` SQL.
- `snapshot delete` is CLI-owned for preview-vs-live branching and output
  shaping.
- `snapshot restore` is CLI-owned for destination-mode parsing, path/query
  parsing, and direct snapshot-package execution.
- Preview/live delete semantics and restore destination safety are currently
  enforced outside an active engine boundary.
- `snapshot restore` human output is still assembled inline in
  [main.go](/home/franchoy/vscode/coldkeep/coldkeep/cmd/coldkeep/main.go:5326),
  not through an active snapshot-mutation renderer boundary.
- This phase is inventory-only and does not activate any candidate engine
  method.

## Current CLI ownership

### `runSnapshotCreateCommand`

```text
runSnapshotCreateCommand
  -> ensureAllowedFlags(id,label,from,output,json)
  -> positional path split
  -> CLI snapshot type derivation (full vs partial)
  -> CLI snapshot ID generation via generateSnapshotID when --id omitted
  -> CLI label/parent trimming
  -> loadDefaultStorageContextPhase
  -> db.NewOperationContext
  -> createSnapshotPhase(ctx, db, snapshot.SnapshotCreateOptions{...})
  -> direct CLI COUNT(*) on snapshot_file
  -> inline human/JSON rendering
```

1. parsing owner: CLI
2. validation owner: CLI for empty `--id`, `--label`, and `--from`; snapshot
   package for semantic lineage and path checks
3. ID generation owner: CLI via `generateSnapshotID`
4. type derivation owner: CLI sets `full` when no positional paths and
   `partial` otherwise
5. repository initialization point: `loadDefaultStorageContextPhase`
6. operation-context creation point: `db.NewOperationContext`
7. domain call: `snapshot.CreateSnapshotWithOptions`
8. post-operation SQL: direct `COUNT(*)` by snapshot ID for `files_inserted`
9. renderer/output owner: inline CLI human and JSON assembly
10. duration/perf owner: CLI `perfTimer`
11. error propagation: direct return from CLI and domain
12. test seam vars: `loadDefaultStorageContextPhase`, `createSnapshotPhase`
13. behavior that remains CLI-owned unless explicitly changed later: ID
    generation, parser syntax, output envelope, and perf spans
14. behavior targeted for later ownership decision: create execution contract,
    type derivation semantics, and result ownership for file counts

### `runSnapshotDeleteCommand`

```text
runSnapshotDeleteCommand
  -> ensureAllowedFlags(force,dry-run,dryRun,output,json)
  -> require snapshotID and one of --force/--dry-run
  -> loadSnapshotDB
  -> db.NewOperationContext
  -> if dry-run: snapshotDeleteLineagePreviewPhase(ctx, db, snapshotID)
  -> else: deleteSnapshotPhase(ctx, db, snapshotID)
  -> preview/live JSON assembly or human formatting
```

1. parsing owner: CLI
2. validation owner: CLI for allowed flags, required snapshot ID, and
   `--force|--dry-run` requirement; snapshot package for preview/delete
   runtime checks
3. mode-selection owner: CLI
4. preview/live branching owner: CLI
5. repository initialization point: `loadSnapshotDB`
6. operation-context creation point: `db.NewOperationContext`
7. preview domain call: `snapshot.LoadDeleteLineagePreview`
8. live domain call: `snapshot.DeleteSnapshot`
9. post-operation SQL in CLI: none
10. human preview output owner: CLI wrapper plus `clirender`
11. human live output owner: inline CLI
12. JSON success owner: inline CLI
13. JSON error owner: common CLI error envelope on stderr
14. test seam vars: `loadDefaultStorageContextPhase`,
    `snapshotDeleteLineagePreviewPhase`, `deleteSnapshotPhase`

Frozen facts:

- `--dry-run` wins over `--force` when both are present.
- `--force=false` and `--dry-run=false` do not satisfy the requirement.
- preview mode must not call `deleteSnapshotPhase`.
- live mode must not load preview.
- human preview output is delegated through
  `formatSnapshotDeleteDryRunOutput`.
- JSON preview/live success envelopes are assembled inline in CLI.
- no direct engine route exists.
- test seam vars are the routing proof.

## Correct lineage deletion semantics

### Normal parent deletion

Current schema and migrations prove that normal parent deletion does not create
missing-parent metadata.

Evidence:

- [migrations.go](/home/franchoy/vscode/coldkeep/coldkeep/internal/db/migrations.go:330)
  defines `parent_id TEXT REFERENCES snapshot(id) ON DELETE SET NULL`
- migration guards reject `snapshot.parent_id` without `ON DELETE SET NULL`
- [DeleteSnapshot](/home/franchoy/vscode/coldkeep/coldkeep/internal/snapshot/snapshot.go:666)
  deletes the target snapshot row and its `snapshot_file` rows only
- migration tests in both SQLite and PostgreSQL assert that deleting the parent
  makes child `parent_id` become `NULL`

Frozen behavior for current-schema delete:

- child snapshots remain
- child `parent_id` becomes `NULL`
- child snapshots become lineage roots
- normal parent deletion does not produce `ParentMissing=true`

### Missing-parent compatibility state

Missing-parent preview and stats logic are compatibility behavior for
non-normal metadata states.

Supported evidence:

- [delete_lineage_preview.go](/home/franchoy/vscode/coldkeep/coldkeep/internal/snapshot/delete_lineage_preview.go:35)
  checks whether a stored `parent_id` still resolves to a live snapshot row
- tests deliberately construct missing-parent state by bypassing or defeating
  foreign-key enforcement
- mixed-lineage integration coverage keeps preview, stats, and restore usable
  when such metadata remains

This state may arise from:

- legacy repositories
- deliberately constructed tests
- externally modified metadata
- migration-compatibility fixtures
- inconsistent repositories repaired only partially outside current schema

It is not the normal result of a successful current-schema `DeleteSnapshot`.

### Partial failure and non-atomicity

- planning happens before any file write
- collision detection happens during planning
- all outputs are planned before execution
- directories are created after planning and before file writes
- files restored before a later failure remain on disk
- there is no rollback cleanup of already written outputs
- no atomic multi-file restore contract exists today

Primary evidence:

- `planSnapshotRestoreOutputs`
- `TestPlanSnapshotRestoreOutputsDoesNotCreateDestinationDirectories`
- metadata failure tests showing post-write error behavior

## Invariants, retention, and backend notes

- snapshot create/delete/restore remain high-risk mutation surfaces
- delete semantics must preserve snapshot immutability and retention safety
- create lineage metadata is descriptive and currently constrained to full
  snapshots for `--from`

  trusted-root behavior

- no current CLI special-cases SQLite vs PostgreSQL in snapshot mutation
  entrypoints
- backend coverage is primarily test-backed through SQLite unit/routing tests,
  migration tests that include PostgreSQL semantics, and integration coverage
  where present
