# Coldkeep v1.13.13 Phase 2 Engine/Catalog Ownership Audit

**Release:** `v1.13.13 — Final v1.x and v2 Handoff Gate`
**Phase:** `2 — Engine/Catalog Ownership Audit`
**Status:** Complete
**Branch:** `release/v1.13.13`
**Starting HEAD:** `ec1f6305e417e7b9a26e9664054975751d9ea854`

## 1. Audit purpose

Independently determine whether the frozen v1 Engine, Catalog, CLI, and
composition ownership requirements are present and adopted in production.
This phase records architecture truth without remediation. It does not decide
Phase 3 correctness, Phase 4 backend equivalence, or v1 closure.

## 2. Normative requirements audited

The audit covers `V1R-ENG-001`–`007`, `V1R-CAT-001`–`005`, and
`V1R-CLI-001`–`004` from the
[v1.x normative requirements matrix](v1.13.13-v1x-normative-requirements.md).
`PROVEN`, `PROVEN_WITH_EXPLICIT_BOUND`, `PARTIAL`, and `BLOCKER` are evidence
classifications, not implementation pass/fail labels.

## 3. Source inventory

The read-only audit inspected `internal/engine`, `internal/catalog`,
`internal/application`, production `cmd/coldkeep` files, direct and transitive
dependency guards, contract-neutrality and typed-error guards, routing tests,
backend contract tests, planning implementations and consumers, production
sentinel searches, and current architecture/release documents. Test files
were evidence, never substitutes for production source traces.

## 4. Engine surface enumeration

Mechanical enumeration of `engine.Engine` found 25 exported operations and 25
corresponding `DefaultEngine` implementations. The complete one-row-per-method
trace is the
[Engine operation ownership matrix](v1.13.13-engine-operation-ownership-matrix.md).
Private receiver helpers are not separately counted.

## 5. Engine production adoption

Every operation has a production CLI consumer or a production startup/
compatibility seam that obtains an Engine from `application.Open`. Routing
tests cover command projection and reject lower-layer fallback on relevant
read, snapshot, store, restore, remove, verify, GC, and stored-path paths.
Source adoption, not a green hosted backend job, establishes this result.

## 6. Engine contract neutrality

Requests and results are Engine-owned neutral structs, enums, scalars, slices,
maps, and tagged values. The recursive neutrality guard walks pointers,
arrays, slices, maps, and nested structs; the active-operation coverage guard
prevents an operation from avoiding inspection. No CLI renderer, Cobra, or
lower presentation contract appears in the active contract graph.

## 7. Engine error taxonomy

Stable Engine codes distinguish validation, not-found, unsupported, conflict,
invariant, cancellation, deadline, and operation failure. Causes are private
but support `Unwrap`; cancellation/deadline and pretyped classifications are
preserved; unknown codes fail closed. All 25 public implementations have a
deferred `TranslateError` boundary, with deterministic Catalog translation.

## 8. Engine validation ownership

The CLI retains syntax parsing, ingestion, selector normalization, and prompt
decisions. Engine and lower owners repeat execution-critical validation and
own sequencing, dependency checks, catalog invariant translation, and
operation semantics. No correctness invariant was found to depend solely on
CLI parsing. Restore destination installation is explicitly not judged here:
`RESTORE_INSTALL_CONTRACT` remains unresolved for Phase 3.

## 9. Catalog responsibility inventory

Mechanical enumeration found ten responsibility interfaces and thirteen
methods, all implemented by `catalog.Service`: logical file, physical file,
current file list/search, repository configuration get/set, snapshot
find/list, snapshot graph, reachability roots, placement, restore plan, and GC
plan. Ten methods have active production consumers; logical-file lookup,
physical-file lookup, and the simpler reachability-root facade are currently
library-only. See the
[Catalog adoption matrix](v1.13.13-catalog-contract-adoption-matrix.md).

## 10. Snapshot graph ownership

`Service.LoadSnapshotGraph` performs ordered metadata loading and fails with a
typed invariant for missing parents or cycles. `DefaultEngine.SnapshotList`
tree mode consumes it before projection. Repository-wide production search
found no active equivalent graph planner. Result: `PROVEN`.

## 11. Placement ownership

`Service.LoadChunkPlacements` produces a strict packed-or-legacy tagged union
and fails closed on missing or incomplete placement. It is adopted by restore
planning. A packed placement is authoritative when a legacy companion row is
also present, preserving the required mixed-repository bound. Storage consumes
the plan for payload reads; it does not become the placement authority. Result:
`PROVEN_WITH_EXPLICIT_BOUND`.

## 12. Restore-plan ownership

`Service.LoadRestorePlanMetadata` resolves the supported selector forms,
loads complete logical metadata, and invokes the placement contract.
`internal/storage/restore.go` adopts it within the restore transaction for all
active Engine restore routes. This is the normative split: Catalog decides
metadata, storage handles payload bytes, Engine orchestrates. Result:
`PROVEN_WITH_EXPLICIT_BOUND`; install correctness is not claimed.

## 13. GC-plan ownership

`Service.LoadGCPlanMetadata` loads coherent planning metadata and validates
exclusions. Live GC, maintenance GC, and Engine live-repository simulation
consume it; the observability use is supplemental. Downstream calculation is
not a competing metadata authority. Result: `PROVEN`.

## 14. Catalog contract neutrality

The recursive Catalog guard derives all methods from the aggregate interface,
walks nested contract graphs, and rejects backend, Engine, CLI, Cobra, and
renderer types. Catalog DTOs describe logical metadata only. SQL abstractions
remain private implementation dependencies.

## 15. Catalog error taxonomy

Catalog codes are invalid argument, not found, unsupported, invariant
violation, conflict, cancelled, and operation failed. Causes remain private
and unwrap correctly; unknown codes fail closed. Eight methods use that stable
boundary. The logical-file, physical-file, snapshot find/list, and
reachability methods still emit raw wrapped database errors; Engine translation
stabilizes the two production snapshot consumers but does not make their
Catalog contracts typed. This is `P2-ARCH-001` and makes Catalog architecture
partial.

## 16. Dependency direction

Static package inspection proves Catalog has no direct or transitive Engine or
CLI dependency, Engine has no CLI dependency, other internal packages do not
import Engine except the explicit application composition root, production CLI
does not import Catalog, and application imports exactly Engine, DB, and
storage. The guards inspect the repository package graph rather than a hand
selected file subset.

## 17. Application composition

`application.Open` selects configured DB and storage resources, constructs the
Engine, owns their lifecycle, and exposes operation context. It contains no
operation-specific business rules or alternate command execution. Verdict:
`APPLICATION_COMPOSITION: NARROW`.

## 18. Thin CLI audit

Every production command was traced through parsing/composition to an Engine
method and then to rendering/exit projection. Startup recovery, Doctor, stored-
path compatibility commands, and live simulate-GC were included. No direct
production database, Catalog, domain, or storage operation bypass was found.
Verdict: `THIN_CLI: COMPLETE`.

## 19. CLI lower-layer exception review

The guard contains 18 exact call exceptions and 13 exact import exceptions.
Its broader projection rule currently admits five unique live call tuples.
All 36 rows, including duplicate import/call accounting, have an explicit
safety rationale in the
[CLI boundary exception matrix](v1.13.13-cli-boundary-exception-matrix.md).
There are zero `ARCHITECTURAL_BYPASS` rows.

## 20. Compatibility adapter review

Observability adapters translate Engine-neutral DTOs into established renderer
types and replay Engine-produced traces. Stored-path adapters open the
application session or accept an Engine, invoke `Recover`, `Doctor`,
`RestoreStoredPath`, or `RemoveStoredPaths`, and project legacy results. They
are `SAFE_COMPATIBILITY_ADAPTER` instances, not alternate authorities. No
removal is required before v1 closure.

## 21. Startup recovery ownership

The CLI owns trigger timing, lease/outer coordination, buffered reporting, and
exit projection. `startupRecoveryPhase` resolves to `runRecoveryThroughEngine`,
which opens the application session and invokes `Engine.Recover`; corrective
recovery work is therefore headless and Engine-owned.

## 22. Direct SQL/domain-access review

Direct CLI SQL is confined to isolated benchmark/determinism diagnostics;
direct storage mutation is confined to synthetic simulation setup. Live
operations route through Engine. Direct SQL inside Engine was not prohibited
categorically: it was classified as a defect only if it duplicated or bypassed
Catalog-owned graph, placement, restore-plan, or GC-plan decisions. No such
active competing authority was found.

## 23. Production stub/deferred-surface review

Production searches and the operation-set/sentinel guard found zero promised
production stubs and no active unimplemented/deferred sentinel. The two Engine
panics are exhaustive internal impossible-state assertions: conversion of
trusted primitive values and an already-validated restore destination enum.
They do not represent missing operations or caller-reachable deferred modes.

## 24. Test/evidence review

The complete Engine, Catalog, application, and CLI package suites pass. The
targeted guards for operation completeness, recursive neutrality, typed-error
coverage, dependency direction, application composition, routing, thin CLI,
and production sentinels pass. JSON events identify 46 PostgreSQL-dependent
skips in the local no-service environment and no SQLite skip. Those skips are
recorded, not converted into ownership gaps: Phase 4 owns backend-equivalence
decisions and hosted PostgreSQL can only supplement this source audit.

## 26. Architecture blockers/partials

`P2-ARCH-001` affects `V1R-CAT-003` and is `PARTIAL`, not a blocker.

- **Severity for v1 closure:** mandatory architecture requirement is not fully
  satisfied; Phase 6 must classify whether remediation is required before
  closure.
- **Files/functions:** `logical_files.go::FindLogicalFile`,
  `physical_files.go::FindPhysicalFilesForLogicalFile`,
  `snapshots.go::FindSnapshot`, `snapshots.go::ListSnapshots`, and
  `reachability.go::LoadReachabilityRoots` plus its scan helpers.
- **Production path:** `FindSnapshot` and `ListSnapshots` are consumed by
  Engine and receive stable Engine translation; the other three methods have
  no active production consumer.
- **Why guards did not prevent it:** neutrality and operation-set guards cover
  shapes and enumeration; Catalog error tests cover taxonomy behavior but do
  not require every method implementation to translate its boundary.
- **Minimum consequence:** direct Catalog callers cannot rely on stable typed
  errors across the complete aggregate interface.
- **Likely remediation:** code changes would be needed; none are authorized in
  this audit.
- **Deferral:** Phase 6 must classify the item; Phase 2 does not design a fix.

No finding is classified `BLOCKER`, so `ARCHITECTURE_V1_BLOCKERS: 0`.

`P2-DOC-001` is `DOCUMENTATION_DEBT`: stale pre-v1.13.12 paragraphs in
`docs/architecture/engine-boundary-plan.md` still describe operations and
planning contracts as incomplete. Current source independently disproves those
old gaps, so the stale text does not downgrade architecture. Phase 10 owns its
reconciliation.
