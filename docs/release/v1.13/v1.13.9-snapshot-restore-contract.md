## Purpose

Convert the accepted Phase 1 snapshot-mutation inventory into the exact target
contract for a future engine-owned snapshot restore operation, covering
selection, destination, metadata, warnings, and result ownership.

This phase is contract-design only. It does not:

- activate `SnapshotRestore`;
- change the active `Engine` interface;
- change CLI parsing, output, SQL, schema, tests, or runtime routing; or
- begin Phase 5 snapshot mutation request/result cleanup work.

## Executive decision

Snapshot restore should later become an honestly engine-owned mutation
boundary, but the target contract must preserve the full Phase 1 behavior
freeze and the live restore semantics that current CLI and snapshot-domain code
already enforce.

The final Phase 4 design is:

- `SnapshotRestoreRequest` separates positional selectors, query selectors,
  destination, overwrite policy, and metadata mode;
- restore uses a restore-specific selection contract instead of reusing the
  narrower read-side `engine.SnapshotQuery`;
- destination mode becomes explicit through a restore-specific destination
  object and enum;
- original-mode current-working-directory discovery is moved out of the future
  engine boundary and becomes CLI-owned;
- lexical/display paths stay distinct from canonical trusted safety paths;
- metadata handling becomes one explicit mode enum plus restore-specific
  structured warnings for best-effort metadata failures;
- override-mode eligibility preserves the current positional-exact-path-only
  contract exactly;
- the engine result becomes renderer-neutral and commit-truthful without
  carrying CLI `type`, human strings, or timing; and
- restore remains non-atomic across files, with explicit documentation of
  partial side effects on failure.

## Current candidate inventory

Current candidate request:

```go
type SnapshotRestoreRequest struct {
	SnapshotID      string
	Paths           []string
	DestinationMode RestoreDestinationMode
	Destination     string
	Overwrite       bool
	Strict          bool
	NoMetadata      bool
	Query           SnapshotQuery
}
```

Current candidate result:

```go
type SnapshotRestoreResult struct {
	SnapshotID    string
	Type          SnapshotType
	RestoredFiles int
	OutputRoot    string
	Warnings      []OperationWarning
}
```

Current runtime truth from Phase 1 and source review:

- CLI owns positional parsing, `parseSnapshotQuery`, destination-mode parsing,
  strict-versus-no-metadata conflict rejection, JSON `type`, timing, and
  human/JSON output;
- current engine `SnapshotQuery` is too narrow for restore because it models
  one exact path, one prefix, and a `Limit` field that restore does not use;
- current snapshot-domain restore query supports repeated exact-path filters,
  repeated prefixes, regex, pattern, size bounds, and time bounds;
- positional exact paths and query exact paths do not have the same missing-path
  guarantee today;
- current original-mode planning calls `os.Getwd()` inside snapshot-domain
  output planning; and
- current domain restore already returns `SnapshotID`, `RestoredFiles`,
  `RequestedPaths`, and lexical `OutputPaths`.

## Final request contract

Final request shape:

```go
type SnapshotRestoreRequest struct {
	SnapshotID  string
	Paths       []string
	Selection   SnapshotRestoreSelection
	Destination SnapshotRestoreDestination
	Overwrite   bool
	Metadata    SnapshotRestoreMetadataMode
}
```

### `SnapshotID`

- trim surrounding whitespace before downstream use;
- empty after trimming is a request-validation error;
- reject before catalog or storage work begins; and
- return the normalized ID on success.

### `Paths`

`Paths` are raw positional restore selectors only.

Contract decisions:

- items ending in `/` are positional directory-prefix selectors;
- other items are positional exact-path selectors;
- repeated values are accepted;
- the engine copies the slice and never retains caller memory;
- raw positional count is preserved for later `RequestedPathsCount`; and
- positional paths remain distinct from query selectors because current CLI
  `type`, override eligibility, and missing-exact behavior depend on that
  distinction.

## Final selection contract

Restore uses a restore-specific selection type:

```go
type SnapshotRestoreSelection struct {
	ExactPaths     []string
	Prefixes       []string
	Pattern        string
	Regex          string
	MinSize        *int64
	MaxSize        *int64
	ModifiedAfter  *time.Time
	ModifiedBefore *time.Time
}
```

Selection decisions:

- preserve every repeated exact path and every repeated prefix at the engine
  boundary;
- copy slices and pointed-to values before downstream use;
- keep regex as a string across the engine boundary and compile it in the
  engine/domain layer;
- do not add a `Limit` field;
- all criteria remain ANDed;
- zero `Selection` means no query filtering; and
- active read-side `engine.SnapshotQuery` remains unchanged and explicitly too
  narrow for restore in Phase 4.

### Positional versus query selectors

This distinction is frozen explicitly:

- positional exact paths continue to guarantee explicit missing-path errors;
- positional directory-prefix selectors remain eligible as positional prefixes
  only;
- query exact-path selectors filter matches but do not guarantee the same
  missing-path error contract as positional exact selectors; and
- Phase 4 preserves that difference instead of silently collapsing the two
  concepts into one selector surface.

## Final destination contract

Final destination enum and object:

```go
type SnapshotRestoreDestinationMode string

const (
	SnapshotRestoreDestinationOriginal SnapshotRestoreDestinationMode = "original"
	SnapshotRestoreDestinationPrefix   SnapshotRestoreDestinationMode = "prefix"
	SnapshotRestoreDestinationOverride SnapshotRestoreDestinationMode = "override"
)

type SnapshotRestoreDestination struct {
	Mode SnapshotRestoreDestinationMode
	Path string
}
```

Mode semantics:

- `original`
  - `Path` is the explicit lexical destination root beneath which
    snapshot-relative paths are reconstructed
- `prefix`
  - `Path` is the explicit lexical prefix root
- `override`
  - `Path` is the exact lexical destination file path

Validation decisions:

- zero or unknown mode is invalid at the engine boundary;
- CLI omission translates explicitly to `original`;
- the engine never silently defaults mode and never infers mode from a target
  path;
- reject `original` without a root;
- reject `prefix` without a root;
- reject `override` without an exact path; and
- do not expose CLI `--destination` presence metadata in the request.

## Original-mode CWD ownership

Final decision:

- CLI owns `os.Getwd()`;
- it happens after request-only CLI validation but before engine invocation;
- the engine must never read process CWD;
- CLI passes the CWD as the explicit original destination root; and
- canonicalization is safety-only and must not replace lexical/display
  identity.

Compatibility note:

- current domain behavior is imperfect because `planSnapshotRestoreOutputs`
  calls `os.Getwd()` internally;
- Phase 4 treats that as a contract correction rather than a behavior broadening;
  and
- original-mode JSON continues omitting `output_root`.

## Lexical path versus trusted safety path

Two path concepts remain distinct.

### Lexical/display path

- caller-supplied or CLI-derived path
- used for `OutputTarget`, `OutputPaths`, current human behavior, current JSON
  behavior, and alias-preserving diagnostics

### Trusted/canonical safety path

- derived internally only
- used to validate below-root writes, reject root and inner symlinks, allow
  outer aliases, and enforce override-parent safety

Contract rules:

- the request carries only lexical target paths;
- engine and storage derive trusted safety paths internally;
- outer aliases remain accepted;
- root and inner symlinks remain rejected;
- Windows drive-letter and UNC path behavior remain supported;
- canonical paths never replace displayed output paths; and
- raw string-prefix containment checks remain disallowed.

## Final metadata contract

Replace `Strict` and `NoMetadata` booleans with one explicit mode:

```go
type SnapshotRestoreMetadataMode string

const (
	SnapshotRestoreMetadataBestEffort SnapshotRestoreMetadataMode = ""
	SnapshotRestoreMetadataStrict     SnapshotRestoreMetadataMode = "strict"
	SnapshotRestoreMetadataNone       SnapshotRestoreMetadataMode = "none"
)
```

Metadata decisions:

- zero value means current default best-effort mode;
- `strict` means metadata failure returns an error after content write;
- `none` means metadata application is skipped entirely;
- unknown values are invalid; and
- the request cannot represent both strict and no-metadata simultaneously.

CLI compatibility remains:

- CLI continues rejecting effective `--strict` plus `--no-metadata` before
  repository initialization.

## Final warning contract

Restore warnings are restore-specific structured warnings for best-effort
metadata failures:

```go
type SnapshotRestoreWarningCode string

const (
	SnapshotRestoreWarningMetadata SnapshotRestoreWarningCode = "metadata_apply_failed"
)

type SnapshotRestoreWarning struct {
	Code      SnapshotRestoreWarningCode
	Path      string
	Operation string
	Detail    string
}
```

Warning decisions:

- warnings are renderer-neutral;
- warning `Path` uses the lexical output path;
- warnings carry no CLI formatting or log-prefix text;
- warnings expose no storage/backend implementation types;
- warning order must be deterministic;
- warnings appear only on successful best-effort restore;
- strict metadata failure returns an error, not a success warning; and
- no-metadata restores return no metadata warnings.

Compatibility decision:

- migration may preserve current warning logs temporarily if desired; however,
  Phase 4 does not add new CLI text lines or JSON fields merely because the
  future engine result becomes richer.

## Override-mode eligibility

Current override compatibility is preserved exactly.

Override restore later requires:

- exactly one positional exact path;
- no positional directory prefix;
- no query-only selection broadening;
- exactly one matched snapshot file;
- exactly one destination file path; and
- no output collision unless overwrite is enabled.

Phase 4 explicitly preserves current rejection of:

- no positional path plus one `--path`;
- query-only single-result selection;
- positional directory-prefix restore that happens to select one file;
- multiple positional exact paths;
- zero exact matches; and
- multiple matched rows.

## Final result contract

Final renderer-neutral result:

```go
type SnapshotRestoreResult struct {
	SnapshotID          string
	DestinationMode     SnapshotRestoreDestinationMode
	RequestedPathsCount int
	RestoredFiles       int64
	OutputTarget        string
	OutputPaths         []string
	Warnings            []SnapshotRestoreWarning
}
```

Field semantics:

- `SnapshotID`
  - normalized snapshot ID
- `DestinationMode`
  - explicit effective destination mode
- `RequestedPathsCount`
  - raw positional path count before normalization or deduplication
- `RestoredFiles`
  - exact successful restore count
- `OutputTarget`
  - original mode: lexical original root supplied by caller
  - prefix mode: lexical prefix root
  - override mode: lexical destination file path
- `OutputPaths`
  - copied lexical output paths in deterministic restore order
- `Warnings`
  - structured best-effort metadata warnings only

The engine result does not include:

- CLI `type`;
- duration or perf spans;
- JSON field names;
- human strings;
- parser state; or
- writer handles.

## CLI-owned `type`

Current JSON `type` remains CLI-owned only:

- no positional paths -> `full`
- any positional paths -> `partial_restore`
- query-only restore continues rendering `type=full`

`type` is not part of the future engine result contract.

## Empty selection and missing-path semantics

The current restore selection contract stays explicit:

- missing positional exact selector => error:
  `path not found in snapshot ...`
- non-exact filters matching zero rows => success
- empty selection success returns:
  - `RequestedPathsCount` still reflects raw positional input count
  - `RestoredFiles == 0`
  - empty `OutputPaths`
  - no filesystem writes

The current human suffix `(empty snapshot selection)` remains CLI-owned.

## Partial-failure contract

Restore remains non-atomic across files.

Frozen behavior:

- selection and output planning complete before writes begin;
- restore execution is sequential;
- a later file failure returns an error after earlier restored files may already
  exist;
- strict metadata failure happens after content write and leaves the file in
  place;
- created directories may remain; and
- per-file temporary cleanup remains required by the execution path; and
- there is no cross-file rollback.

Final recommendation:

- return zero result plus error on failure; and
- document filesystem side effects explicitly instead of inventing a partial
  success result contract in `v1.13.9`.

## Domain adaptation strategy

Smallest honest migration path:

- keep `snapshot.RestoreSnapshot` as the execution core initially;
- add an engine adapter that translates the final request into domain options;
- move original-mode CWD discovery out of `planSnapshotRestoreOutputs` and into
  the later CLI translation layer;
- add a restore-specific selection adapter so repeated exact paths and prefixes
  are not narrowed at the engine boundary;
- evolve domain result and warning shapes only where needed to expose explicit
  destination mode, lexical output target, and structured metadata warnings;
- keep direct CLI/domain ownership until a later routing phase; and
- avoid duplicating planning or execution logic inside the engine.

## Dependency boundary

Future `Engine.SnapshotRestore` should require:

- `context.Context`;
- engine-owned catalog DB access;
- engine-owned storage context;
- engine-owned payload readers;
- engine-owned codec and key configuration;
- filesystem write access;
- filesystem read/write helpers needed for safe output materialization.

The request must not contain:

- `*sql.DB`;
- `*storage.StorageContext`;
- loggers;
- output writers; or
- CLI state.

## Immutability and concurrency

Contract expectations:

- copy request `Paths`;
- copy selection slices and pointed-to values;
- compile regex per request or via immutable internal state;
- return copied `OutputPaths` and `Warnings`;
- retain no caller memory after return;
- use no package-global mutable hooks; and
- allow concurrent restores subject to existing filesystem and database
  behavior.

Phase 4 does not introduce global restore serialization.

## Validation and error contract

Target validation ordering:

1. CLI arity, unknown flags, explicit `--strict` plus `--no-metadata`, and
   query-parse failures remain CLI-owned.
2. Engine trims `SnapshotID`, validates non-empty ID, validates destination
   mode, validates metadata mode, and copies request inputs.
3. Engine or domain compiles regex and validates size/time bounds when restore
   becomes engine-routed.
4. Domain selection resolution preserves current positional-exact missing-path
   behavior and zero-match success for non-exact filters.
5. Output planning enforces destination safety and current override-mode
   eligibility.
6. Execution performs sequential content restore, then metadata behavior
   according to mode.

Stable compatibility expectations:

- blank snapshot ID remains a validation failure;
- invalid regex, size, and time bounds remain request failures;
- missing positional exact path preserves the current stable substring
  `path not found in snapshot`;
- strict metadata failures remain errors after content write;
- best-effort metadata failures remain non-fatal to overall restore success; and
- no success result is returned on failure.

## SQLite and PostgreSQL parity requirements

Selection parity must cover:

- snapshot not found;
- positional exact selectors;
- positional directory-prefix selectors;
- repeated exact query values;
- repeated prefixes;
- combined filters;
- missing positional exact selector behavior;
- zero non-exact matches succeeding;
- deterministic ordering; and
- duplicate suppression in final selected rows.

Execution parity must cover:

- content restore;
- best-effort, strict, and no-metadata modes;
- partial-failure behavior;
- packed and legacy storage coverage; and
- PostgreSQL-specific existence, query, and ordering behavior where restore
  selection depends on catalog reads.

Filesystem and native parity must cover:

- Ubuntu, macOS, and Windows destination safety; and
- lexical-path preservation alongside trusted-root validation.

## Security and correctness review

This contract prevents or explicitly constrains the key restore risks:

- positional and query selectors no longer blur into one misleading request
  field;
- contradictory strict/no-metadata state becomes unrepresentable at the engine
  boundary;
- original-mode process-CWD dependence no longer leaks into a future engine
  method;
- lexical user-facing paths remain stable while safety checks rely on trusted
  canonical paths;
- override restore stays constrained to one positional exact path;
- best-effort metadata failures can be exposed structurally without changing
  successful content-restoration truth;
- partial side effects on failure remain documented rather than implied away;
- no DB, storage, or CLI implementation pointers leak into the request/result
  surface; and
- no new serialization, schema, or backend-policy change is smuggled into the
  restore contract.
