# Coldkeep v1.13.7 Repository Portability Contract

**Release:** `v1.13.7 — SQLite-First Repository Portability Baseline`
**Phase:** Phase 3
**Status:** Complete
**Branch:** `release/v1.13.7`

## Purpose

This document defines the proposed repository portability contract for a future
SQLite-first local Coldkeep repository.

It builds on the Phase 2 catalog placement target:

`<repository-root>/.coldkeep/catalog.sqlite`

This contract is not a claim that directory portability is currently
implemented.

This phase changes no runtime behavior.

## Scope boundaries

This phase is:

- contract definition only
- not a runtime SQLite local mode
- not a backend-default change
- not a catalog relocation
- not a repository-root implementation
- not a move/copy command
- not a checkpoint command
- not automatic path rewriting
- not a portability test
- still PostgreSQL-compatible by requirement

## Current runtime baseline

Accepted current-state facts from Phases 1 and 2:

- current normal local runtime is PostgreSQL-backed `local` mode
- current production SQLite exists only in simulated mode and tests
- current path ownership is split across DB env, `COLDKEEP_STORAGE_DIR`, and
  temp SQLite paths
- current runtime has no formal repository-root abstraction
- current runtime has no explicit repository-owned SQLite sidecar contract
- current runtime has no explicit checkpoint contract for a user-facing local
  SQLite repository mode

The rest of this document defines a future portability target, not current
runtime truth.

## Terminology

**Local repository**
A Coldkeep catalog and its required payload/storage state operated as one
logical storage system on a single machine.

**Repository root**
The directory intended to contain all durable state required for directory-based
local repository portability, except explicitly external secrets and
configuration.

**Directory-portable repository**
A repository that can be cleanly closed, copied or moved as a directory,
reopened from the new location, verified, and used without catalog or payload
loss.

**Operationally portable repository**
A repository that can be transferred only through an explicit multi-part
procedure, such as external catalog backup/restore plus payload copying.

**Repository generation**
A mutually consistent point in repository history containing compatible catalog
and payload state.

**Cleanly closed repository**
A repository with no active Coldkeep mutation, no Coldkeep-owned DB handle left
open, no in-progress payload commit, no unresolved Coldkeep temporary write,
and required database close/checkpoint behavior completed.

**Reopened repository**
A moved or copied repository whose catalog and payload roots are resolved from
the new location and whose required validation has passed.

**Portability verification**
The set of checks proving that catalog state, payload state, paths, encryption
requirements, and repository identity remain valid after reopening.

**Relocation**
A move where the repository remains the same logical repository after transfer.

**Backup copy**
A non-active copy intended as a safety copy, not as an independently writable
peer.

**Independent clone**
A destination copy intended to become separately writable with explicit
identity/divergence semantics.

| State | Classification | Required for directory portability | Current posture |

| SQLite catalog | required durable repository state | yes | future contract target only; current normal local runtime uses external PostgreSQL |
| SQLite sidecar files | active transient state that may become required durable transfer state | yes when present | not explicitly managed in current runtime |
| legacy containers | required durable repository state | yes | currently referenced through catalog container metadata |
| packed blocks / payload container storage | required durable repository state | yes | currently referenced through `storage_blocks` and container metadata |
| quarantine state | required durable repository state | yes | currently split across DB metadata and container-root state |
| recovery metadata | not yet formally owned | likely yes when repository-owned | recovery behavior exists, but repository-owned path contract is not defined |
| manifests | not yet formally owned | only if later defined as required | no active repository-owned manifest contract found |
| repository identity metadata | not yet formally owned | required for independent clone semantics, not for documenting relocation contract | no obvious stable repository ID found in current schema/runtime exploration |
| lock state | active transient state | required for correct clean-close handling, not durable trust by itself | no explicit repository-owned lock path contract found |
| temporary payload-write state | active transient state | must be absent or resolved before portability claim | write/recovery lifecycle exists, but portable ownership path is not yet formalized |
| temporary restore files | optional operational state | no | output-path-dependent temp artifacts, not repository-owned durable state |
| logs | optional operational state | no | stdout/stderr or host logging, not repository-owned runtime state |

| encryption key material | external secret | operationally required for encrypted reopen/verify/restore | currently external env or `.env` bootstrap material |
| PostgreSQL credentials | external configuration | required only for PostgreSQL operational portability | currently external env configuration |

Source-backed current evidence:

- `container.filename` plus container-root configuration show payload
  references are catalog-tracked
- `storage_blocks` metadata records packed payload placement against container
  rows
- `physical_file.path` and `snapshot_path.path` preserve logical/external path
  semantics rather than repository-owned payload-root placement
- no stable repository ID is evident in the explored schema/runtime surfaces
- `.env` and `COLDKEEP_KEY` remain external key/config surfaces

## Conceptual repository shape

The future contract model is a complete repository rooted at one directory:

```text
<repository-root>/
  .coldkeep/
    catalog.sqlite
    catalog.sqlite-wal
    catalog.sqlite-shm
    catalog.sqlite-journal
    locks/
    manifests/
    quarantine/
    recovery/
    metadata/
  containers/
  blocks/
```

This is a conceptual ownership model, not an implemented layout.

Contract discipline:

- do not assume every listed directory exists today
- do not freeze every optional subdirectory as a stable storage format
- distinguish conceptual ownership from final naming
- focus on completeness and ownership, not premature path-format lock-in

## Portability classes

| Class | Catalog | Payload | Portability mechanism |
| --- | --- | --- | --- |
| directory-portable local repository | SQLite inside repository root | inside repository root | clean close/checkpoint, directory copy or move, reopen and verify |
| conditional local repository | SQLite outside repository root or payload outside root | split across configured roots | all referenced roots must move together and be revalidated together |
| PostgreSQL-backed repository | external PostgreSQL catalog | local or external payload | catalog backup/restore plus payload transfer and validation |
| non-portable configuration | missing or contradictory required state | incomplete or machine-bound | portability claim refused |

Only the first class is a candidate for simple directory portability.

Split-root, machine-bound, or externally anchored configurations are at most
conditional, not simple directory-portable.

PostgreSQL-backed repositories remain operationally portable, not
directory-portable by copying payload directories alone.

## Safe copy contract

Future safe-copy sequence:

1. identify repository root and backend
2. prevent new mutations
3. wait for active mutations to finish
4. complete pending payload commits
5. complete required SQLite checkpoint behavior
6. close all Coldkeep-owned DB handles
7. confirm no unresolved repository-owned temporary state
8. copy the complete repository root
9. do not modify the source during the copy
10. open the destination as a separate repository instance
11. validate repository identity and paths
12. run required catalog/storage verification
13. perform restore validation before treating the copy as trusted

Contract conclusions:

- live filesystem copying is not guaranteed safe
- copying only `catalog.sqlite` is insufficient
- copying only payload directories is insufficient
- successful file copying does not prove semantic consistency
- a destination copy must not be trusted until validation passes
- no current command is claimed to automate this sequence

## Safe move contract

Move is distinct from copy.

Future safe-move sequence:

1. satisfy all safe-copy preconditions
2. move or copy the complete repository root
3. do not run source and destination as independent writable repositories
4. reopen only from the new location
5. validate path resolution
6. validate repository identity
7. run catalog/storage verification
8. perform restore validation before treating the moved repository as trusted

Same-filesystem rename is a special case, not an exemption.

Contract conclusions:

- same-filesystem rename may reduce partial-copy risk
- it does not remove DB-close, checkpoint, path-resolution, or post-move
  validation requirements
- open file handles and working-directory-relative assumptions can still
  invalidate the move

## Repository identity and clone boundary

Current evidence:

- no obvious stable repository ID appears in the explored schema/runtime
  surfaces
- `repository_config` exists, but does not clearly provide a backend-neutral
  repository identity field

Phase 3 posture:

- relocation preserves repository identity
- backup copies preserve identity but remain non-active
- independent writable cloning requires explicit identity and divergence
  semantics and is deferred
- repository identity must not depend only on absolute path

If stable identity metadata is absent today, that is an implementation gap, not
an immediate blocker for documenting relocation and backup-copy posture.

Independent writable cloning is not part of `v1.13.7`.

## Reopen and repository discovery contract

A future directory-portable local repository should be reopenable by repository
root.

The target resolver should conceptually derive from repository root:

- catalog path
- container path
- block path
- repository metadata path

Contract requirements:

- path derivation is deterministic
- repository discovery does not depend on the original working directory
- old absolute root paths must not remain necessary
- explicit external-path configuration must be revalidated
- missing required files or directories cause refusal
- unknown or ambiguous repository roots cause refusal
- fallback to an unrelated PostgreSQL catalog must not occur silently

This phase does not define new CLI syntax.

## Path portability and machine-specific path risks

Path categories relevant to portability:

- logical user paths
- repository-relative storage references
- machine-specific absolute paths
- external source paths
- restore destination paths
- unclear cases

Current evidence:

- `physical_file.path` stores user/source path identity, not necessarily a
  repository-owned payload location
- `snapshot_path.path` stores logical snapshot path identity
- `container.filename` is combined with `container.ContainersDir`
- current payload root can be working-directory-relative through
  `./storage/containers`

Contract conclusions:

- internal payload references should be repository-relative or resolvable from
  repository root
- logical stored paths may preserve user-visible semantics without becoming
  repository storage locations
- machine-specific absolute internal storage paths prevent simple directory
  portability
- external configured roots make portability conditional
- silent path rewriting during move must not occur

## Encrypted repository portability

Encrypted payload moves with the repository.

Key portability posture:

- encryption key material may remain external
- a repository may be copied without the key, but cannot be fully
  verified/restored operationally without the correct key
- reopening should fail closed when required key material is absent
- wrong keys must produce deterministic integrity or authentication failure
- key material must not be copied into the repository implicitly

Recommended statement:

An encrypted repository is structurally portable without embedding its key, but
operational portability requires the correct external key material.

Phase 3 does not redefine key management.

## Backend and configuration portability

Configuration classes:

- repository-intrinsic
- portable external requirement
- machine-specific external requirement
- backend-specific operational requirement

Examples:

- SQLite catalog placement: repository-intrinsic
- encryption key: portable external requirement
- PostgreSQL credentials: backend-specific external requirement
- absolute external storage root: machine-specific external requirement
- DB pool and process tuning: operational, not repository identity

Contract requirement:

Coldkeep should refuse portability claims when backend configuration
contradicts repository posture, layout, or required roots.

This phase does not implement repository metadata detection.

## Post-move validation requirements

The destination must not be trusted merely because it opens.

### Structural validation

- required repository-owned paths exist
- catalog file exists
- expected payload roots exist
- no required external root is missing

### Catalog validation

- database opens
- schema version is supported
- migrations are not unexpectedly required
- integrity checks pass where applicable
- foreign-key expectations hold

### Catalog and storage consistency validation

- referenced containers and blocks exist
- referenced ranges and sizes are valid
- catalog mappings are internally consistent
- no required payload is silently missing

### Integrity verification

- hashes and authentication checks pass
- encrypted payload decrypts with the supplied key
- packed and legacy payload paths remain readable

### Restore validation

- at least one representative restore or defined smoke restore succeeds
- restored bytes match expected content

Phase 6 will decide the minimum automated smoke scenario.

## Failure and refusal behavior

The portability contract is fail-closed.

Candidate refusal conditions:

- repository is active
- DB handles remain open
- checkpoint requirement is not satisfied
- required sidecar state is incomplete
- required payload root is absent
- catalog and payload appear to come from different generations
- backend selection contradicts repository posture
- repository root is ambiguous
- catalog is external but not supplied
- PostgreSQL catalog migration was not performed
- required encryption key is absent or wrong
- unsupported schema version
- machine-specific internal path cannot be resolved
- copied repository fails verify
- clone identity ambiguity exists

Coldkeep should refuse operation rather than silently repair, recreate,
redirect, or select another catalog.

This phase does not define final error messages or exit codes.

## Partial-copy and interrupted-move posture

Portability contract posture for partial or interrupted transfers:

- interrupted destination copies are not trusted
- catalog-only copies are incomplete
- payload-only copies are incomplete
- stale sidecar copies are not trusted by default
- copies made while the source changes are not trusted by default
- destinations that already contain repository files must not be silently
  merged
- partial overlays onto another repository must not be silently adopted
- resumed copies with mixed generations must not be trusted without full
  validation

Recommended behavior:

- no automatic trust
- destination remains unusable until full validation passes
- no silent merge of repositories
- no automatic creation of missing catalog state
- no automatic adoption of orphan payload during normal reopen
- repair and recovery remain explicit and separate
- destructive cleanup must not run before repository validation

## v1.13.7 versus later responsibilities

Appropriate for `v1.13.7`:

- contract definition
- evidence inventory
- future smoke-test design
- narrow guards if later justified
- documentation alignment
- final portability baseline summary

Deferred to later `v1.13.x` or `v2.x`:

- normal SQLite local backend implementation
- default backend change
- repository-root API
- daemon-controlled close and checkpoint behavior
- repository move command
- repository clone command
- job coordination
- UI or API portability workflows
- backup/export/import system
- advanced catalog recovery

This contract should not be treated as a `v2.x` implementation plan.

## Phase 3 decision posture

A future directory-portable Coldkeep repository is a complete
catalog-plus-payload system rooted at one repository directory.

Directory portability requires:

- an in-repository SQLite catalog
- all required payload storage inside the repository root
- no active mutation
- clean database close and required checkpoint or sidecar handling
- deterministic repository-root-based path resolution
- required external secrets supplied after the move
- catalog and storage consistency verification
- integrity verification
- restore validation

PostgreSQL-backed repositories remain operationally portable through separate
catalog backup/restore and payload transfer, but they are not
directory-portable by copying the payload directory alone.

Independent writable cloning is deferred until repository identity and
divergence semantics are explicitly defined.
