## 3. Engine boundary

`DefaultEngine.GarbageCollect` now rejects negative Workers as
`invalid_argument` before maintenance. Zero and one normalize to one; every
positive value above one is forwarded as a strict concurrency maximum.

The existing public `GarbageCollectRequest` and `GarbageCollectResult` shapes
are unchanged. Engine invokes the narrow worker-aware maintenance entry,
projects every maintenance field including `BytesReclaimed`, and only then
returns the maintenance error through the existing translation boundary. A
meaningful maintenance partial result therefore survives a translated non-nil
Engine error.

`RunGCWithDB` remains the serial compatibility entry and delegates with an
effective worker count of one. The Phase 3 filesystem and dispatch options
remain private and invocation-scoped.

## 4. Materialized bounded execution

All preflight work remains serial: advisory-lock acquisition, physical graph
integrity, reachability, retained-root classification, live packed-block
mapping, and live legacy-container mapping. Sealed candidate rows are scanned,
ordered by container ID and filename, and closed before a unit transaction or
worker starts.

The maintenance coordinator owns all scheduling:

1. dispatch at most the effective worker limit;
2. keep only those in-flight units, with no queued future-candidate backlog;
3. invoke the existing dispatch observer exactly once inside the executing
   unit at its begin boundary;
4. after any non-error terminal result—affected, retained, or skipped—dispatch
   the next candidate when one remains;
5. after a unit error or caller cancellation/deadline is observed, dispatch no
   new unit;
6. wait for every already-started unit to reach its existing safe terminal
   boundary; and
7. aggregate private unit outcomes by plan index, never completion timing.

Workers never mutate the shared `GCResult` or error collection. PostgreSQL
units each own an independent transaction from `sql.DB` while the invocation
retains its dedicated advisory-lock connection. Chunk-row deletions use stable
ascending IDs to preserve deterministic concurrent lock acquisition.
Production pool sizing is unchanged: Workers is an upper bound and a smaller
valid pool may serialize transactions naturally.

The sealed pass becomes fully terminal before active candidates are queried.
Active candidates are then materialized and assigned the global plan suffix.
Dry-run still has no active pass. Public filename and error ordering is sealed
plan order followed by active plan order.

## 5. Physical-byte and transaction boundary

`maintenance.GCResult` now carries internal `BytesReclaimed int64`. For every
potentially affected unit, GC resolves the authoritative path through
`SafeContainerPath` and calls the invocation filesystem's `Stat` exactly once,
after final eligibility/liveness/retention revalidation and before destructive
commit.

Invalid paths, missing files, `Stat` errors, and negative sizes roll back the
unit and receive no affected count, filename, or byte credit. Dry-run rolls
back after successful evaluation and credits the captured physical size as the
planned reclaimable amount.

Live execution retains the frozen order:

```text
begin transaction
revalidate eligibility, liveness, and retention
resolve safe path and Stat exactly once
sweep unreachable metadata
delete exactly one container row
commit
Remove physical file
```

A successful post-commit `Remove` credits the captured size, count, and
filename. `Remove` failure is now returned as a real operation error and earns
zero unit credit. Committed metadata is not synthetically recreated. A
successful fully-dead-active removal contributes to the same live affected,
filename, and byte population; active cleanup remains absent from legacy
dry-run.

## 6. Partial results and deterministic errors

Maintenance no longer converts sealed or active execution errors into
`GCResult{}`. Every terminal started-unit result is aggregated in global plan
order and returned with the non-nil error. Units not started after a stop
condition have no evidence. Preflight failure before meaningful execution
retains a zero result.

Multiple unit errors are joined in plan order. An otherwise unrepresented
caller cancellation/deadline follows unit errors. Advisory-unlock failure is
joined last by the existing named-result defer and does not erase successful
work. Tests prove `errors.Is` for every sentinel and show that reverse
completion order does not affect result or error order.

## 7. Checked overflow

Normal results describe one identical physically successful population in
`AffectedContainers`, `ContainerFilenames`, and `BytesReclaimed`. Byte addition
is checked in global plan order.

At the first addition that would exceed `math.MaxInt64`, GC records a
deterministic accounting error containing that plan index, kind, container ID,
and filename. All physically successful units—including the overflowing unit
and later successful units—remain counted and named. `BytesReclaimed` remains
the last exact non-overflowing plan-order prefix; the overflowing and later
byte additions are excluded. The value never wraps, saturates, becomes
negative, or erases earlier exact credit. This is the sole representational
exception to same-population exact byte reporting.

The Phase 11 tests prove:

- Engine negative Workers rejection and maintenance normalization of zero and
  one to serial execution;
- exact upper bounds for Workers 2 and N;
- any nil-error affected, retained, or skipped outcome continues dispatch;
- errors and cancellation stop new dispatch while preserving started outcomes;
- plan-ordered results and multi-errors under reverse completion;
- PostgreSQL Workers=2 actual overlap with two reclaimable units,
  `SetMaxOpenConns(3)`, begin observers, and channel gates without sleeps;
- PostgreSQL Workers=2 natural transaction serialization with a two-connection
  pool rather than rejection or production resizing;
- sealed-before-active pass ownership and live active accounting;
- zero, one, multiple, dry-run, live, legacy, packed, mixed, none, zstd, plain,
  and AES-GCM byte paths;
- independently observed physical sizes rather than metadata-derived expected
  values;
- exactly-one `Stat`, invalid path, missing file, Stat fault, negative size,
  and post-commit Remove fault behavior;
- successful units before/after an already-started failure, an unstarted fourth
  unit, zero failure credit, and truthful public partial results;
- successful work plus deterministic advisory-unlock failure; and
- exact `math.MaxInt64`, first/later overflow, retained prefix, later successful
  population evidence, unit identification, and nonnegative non-wrapping totals.

SQLite remains dry-run only and proves ceiling, ordering, stop-dispatch,
fault, and planned-byte semantics. PostgreSQL proves dry/live execution,
actual overlap, smaller-pool serialization, advisory ownership, independent
