# Coldkeep v1.13.5 to v1.13.6 Handoff

**From release:** `v1.13.5 — Release Record Closure and Engine-Level Invariant Ownership`
**Recommended next release:** `v1.13.6 — Catalog Contract Expansion and Backend Parity Review`
**Status:** Final post-release handoff
**Branch:** `release/v1.13.5`

## `v1.13.5` outcome

`v1.13.5` confirmed that the current transitional validation, invariant, and
output ownership seams are acceptable without production or test changes.

- no production code changed
- no tests changed
- no scripts or CI changed
- no runtime behavior changed
- SQLite compatibility remained preserved
- PostgreSQL compatibility remained preserved

## Why `v1.13.6` should focus on catalog/backend contracts

The remaining higher-risk areas after `v1.13.5` are no longer request-validation
or basic guard-boundary questions. They are catalog, storage, and backend-parity
questions that sit below the active CLI/engine seams.

Phases 3, 4, 5, 7, and 8 converged on the same conclusion:

- the active request boundaries are stable enough
- the remaining deferred work is mostly backend-sensitive
- the honest next step is catalog/backend contract review rather than engine
  output redesign

## Recommended `v1.13.6` scope

`v1.13.6` should focus on catalog/backend contract coverage for:

- SQLite/PostgreSQL catalog parity
- snapshot-retention contracts
- logical/physical file mapping contracts
- chunk ordering contracts
- restore metadata strictness contracts
- GC reachability/refcount contracts
- repair refusal contracts
- read-side query parity where appropriate

## `v1.13.6` non-goals

- broad read-side ownership redesign
- speculative engine-native result redesign without a concrete caller need
- backend default changes
- storage format changes
- repository format changes
- runtime behavior changes without a proven contract issue
