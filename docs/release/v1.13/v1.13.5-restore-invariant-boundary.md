# Coldkeep v1.13.5 Restore Engine Validation and Restore-Safety Boundary Review

**Release:** `v1.13.5 — Release Record Closure and Engine-Level Invariant Ownership`
**Phase:** Phase 4
**Status:** Complete
**Branch:** `release/v1.13.5`

## Purpose

This document reviews the active `Restore` engine-facing path and records where
validation, restore-safety ownership, dry-run/live behavior, unsupported-mode
boundaries, metadata application, and public output/error rendering currently
live.

This phase performs no ownership migration and no behavior change.

## Reviewed surfaces

- `Engine.Restore`
- `RestoreRequest`
- `RestoreResult`
- `RestoreItemResult`
- `validateRestoreRequest`
- CLI restore routing
- by-ID restore dry-run and live execution
- stored-path restore and destination modes
- restore-safety and path-safety helpers
- metadata strictness and application
- public CLI batch rendering and exit-code classification
- current test protection

## Current restore flow

The active by-ID restore path currently flows as:

```text
cmd/coldkeep
  -> parse public CLI args and route mode
  -> batch-load and validate fileID inputs
  -> ensure restore output dir semantics
  -> restoreByIDPhase
  -> Engine.Restore
  -> validateRestoreRequest
  -> restoreFileIDs / restoreFileID
  -> dryRunRestoreByID or storage.RestoreFileWithStorageContextResultOptions
  -> per-item result shaping
  -> CLI-owned batch text / JSON rendering and exit classification
```

The active engine seam exists only for `RestoreModeFileIDs`.

At the CLI boundary, `runRestoreCommand` decides whether the invocation is:

- by-ID engine-backed restore
- single `--stored-path` direct CLI/storage restore

At the engine boundary, `DefaultEngine.Restore` validates only the active
by-ID request seam and then processes file IDs sequentially.

At the domain boundary, `internal/storage/restore.go` owns the real restore
execution and the stronger write-safety invariants, including output-path
validation, overwrite protection, temporary-file commit behavior, hash
verification, and metadata application.

The CLI remains the public batch/output boundary: it renders human and JSON
results and determines exit-class behavior for batch failures.

## Request and result ownership

- `RestoreRequest` currently includes:
  - `Mode RestoreMode`
  - `FileIDs []int64`
  - `OutputDir string`
  - deferred stored-path and destination fields:
    - `StoredPath`
    - `DestinationMode`
    - `Destination`
  - `Strict`
  - `NoMetadata`
  - `Overwrite`
  - `DryRun`
  - `FailFast`
  - `InputPath`
  - provisional `Workers`
  - provisional `Limit`
- `RestoreResult` is an engine-owned structured result.
- `RestoreItemResult` is an engine-owned structured per-item result with:
  - `FileID`
  - `StoredPath`
  - `OutputPath`
  - `RestoredHash`
  - `Status`
  - `Error`

Unlike `Verify`, restore already has a real engine-owned per-item result
shape. Unlike `Remove`, restore item results do not currently carry structured
`InvariantCode` or `RecommendedAction` fields.

The current ownership shape is:

- CLI owns command semantics, raw input parsing, stored-path mode selection,
  and public rendering
- engine owns the active by-ID request seam and by-ID result shaping
- storage owns actual restore execution and restore-safety semantics

`restoreByIDPhase` remains a transitional CLI bridge:

- it uses engine-backed by-ID execution
- it still converts the engine result back into `storage.RestoreFileResult`
- it still looks up `OriginalName` directly from storage before shaping the
  CLI batch result

That means the active by-ID restore seam is engine-backed, but the CLI still
bridges between engine result data and older storage-shaped command handling.

## CLI validation

CLI-owned validation currently includes:

- command-shape validation:
  - by-ID restore requires one or more file IDs plus an output directory
  - `--stored-path` rejects positionals
  - `--stored-path` rejects `--input`, `--dry-run`, and `--fail-fast`
  - `--strict` and `--no-metadata` are only accepted with `--stored-path`
  - `--strict` and `--no-metadata` are mutually exclusive
- positional and input-file parsing:
  - by-ID mode uses `batch.LoadRawTargets` and `batch.PrepareTargets`
  - malformed textual file IDs remain CLI-owned validation failures before
    engine routing
  - a single non-numeric positional target is rejected with explicit
    path-restore guidance
  - empty or non-materialized prepared ID sets remain CLI-shaped usage
    failures
- output directory handling:
  - `ensureRestoreOutputDir` enforces non-empty output-dir shape for the CLI
    contract
  - in live by-ID mode it creates the output directory before execution
  - in dry-run mode it does not create the directory
- stored-path destination and metadata flag policy:
  - `parseRestoreDestinationMode` owns the public `--mode` flag contract
  - CLI enforces `--destination` required/forbidden combinations for
    `original`, `prefix`, and `override`
  - CLI owns the public `--strict` / `--no-metadata` policy
- public success and failure rendering:
  - CLI renders batch text and JSON output for by-ID restore
  - direct stored-path restore assembles its own public success JSON/text
    payload at the CLI layer
  - CLI determines public batch exit behavior from batch item outcomes

These validations are intentionally public-command concerns rather than
engine-request concerns.

## Engine validation

Engine-owned validation currently includes:

- `validateRestoreRequest`
  - accepts only `RestoreModeFileIDs`
  - rejects empty `FileIDs`
  - rejects empty `OutputDir`
  - returns `ErrNotImplemented` for stored-path restore
- `restoreFileID`
  - rejects non-positive file IDs at the per-item level
  - returns a failed item result rather than a top-level engine error for
    invalid item values
- `DefaultEngine.Restore`
  - validates the active request seam once and then routes into sequential
    item execution

This creates a clear split between:

- top-level request validation:
  - active mode supported
  - non-empty file-ID batch required
  - non-empty output directory required
- per-item validation:
  - each file ID must be positive

That distinction is visible in current behavior:

- malformed textual IDs fail in CLI parsing
- unsupported stored-path engine calls fail at the engine request boundary
- typed but invalid item IDs fail as structured item-level restore failures

This is the correct deeper guard for non-CLI callers on the active by-ID
restore seam.

## Domain package validation and restore-safety invariants

Below engine, `internal/storage/restore.go` owns the real restore execution
and the stronger write-safety semantics.

Storage-owned responsibilities currently include:

- logical-file existence and `COMPLETED`-state resolution
- chunk pinning before read and unpinning after execution
- restore recipe loading and ordering validation
- path validation for writes using `pathsafe`
- stored-path destination derivation for `original`, `prefix`, and `override`
  modes
- symlink rejection for unsafe write paths and symlinked prefix roots
- overwrite enforcement before write and again before rename
- temporary-file creation in the destination directory
- buffered write, flush, file fsync, atomic rename, and directory fsync
- chunk payload decode or block slicing, chunk hash validation, and final
  restored-file hash validation
- metadata completeness enforcement and metadata application policy

For by-ID live restore, `storage.RestoreFileWithStorageContextResultOptions`
does the actual work and owns the stronger safety boundary. The engine does
not itself enforce path traversal safety, rename durability, or content-hash
integrity; those are domain-layer concerns.

By-ID dry-run is narrower. `dryRunRestoreByID` currently checks:

- logical-file existence
- `COMPLETED` status
- derived output path from `OutputDir` plus `OriginalName`
- overwrite conflict when `--overwrite` is absent
- no mutation occurs

This dry-run path does not simulate every live restore invariant. It should be
documented as a narrower preview rather than as a full live-operation
equivalence claim.

Stored-path restore uses separate direct CLI/storage entry points, but the
same domain layer still owns the restore-safety invariants for destination
resolution, metadata handling, overwrite policy, and write-path safety.

## Invariant/error propagation

Restore currently propagates failures differently from remove.

For the active engine-backed by-ID path:

- storage returns plain Go errors for restore failures
- engine maps those failures into `RestoreItemResult.Error`
- engine does not currently project structured `InvariantCode` or
  `RecommendedAction` fields into restore item results
- `restoreByIDPhase` converts failed engine items back into ordinary errors
  for the CLI batch executor
- CLI renders those failures as batch item error strings

For the direct stored-path path:

- storage returns ordinary errors
- CLI returns those errors directly for the single-path command surface
- CLI-owned public error-envelope shaping remains unchanged

This means restore currently preserves error messages and public batch/error
behavior, but it does not expose remove-style structured invariant metadata at
the engine result level.

That is a transitional seam, not automatically a bug. Current evidence shows
public behavior is preserved, and the phase should document the difference
rather than infer a required migration.

The review should also note:

- current restore errors do not expose verify-style stage/block/container
  metadata
- current restore errors do not project internal helper names into the public
  contract
- public JSON/text envelopes remain CLI-owned

## Unsupported and deferred seams

The current restore boundary still has intentional transitional seams:

- engine support is active only for `RestoreModeFileIDs`
- stored-path restore remains an explicit `ErrNotImplemented` boundary at the
  engine layer
- stored-path restore still exists publicly as a direct CLI/storage path
- destination-mode semantics and metadata options belong to the direct
  stored-path path, not the active engine route
- `restoreByIDPhase` still bridges engine results back into
  `storage.RestoreFileResult`
- `RestoreRequest` still contains deferred stored-path and provisional batch
  fields that are not evidence of active engine support
- snapshot restore remains outside the active `Engine.Restore` seam
- restore item results do not currently expose structured invariant metadata

These seams are transitional but acceptable for `v1.13.5` because this phase
is a review-only release phase and does not expand engine scope by default.

They should not be described as bugs unless later phases find conflicting
behavior.

## Findings

### Stable enough for v1.13.5

- by-ID restore has a real engine-owned request/result seam rather than a
  minimal placeholder
- engine request validation protects non-CLI callers from invalid by-ID
  restore requests
- storage clearly owns the stronger restore-safety invariants and actual write
  behavior
- unsupported stored-path engine mode remains an explicit `ErrNotImplemented`
  boundary
- current public dry-run, overwrite, and batch-report behavior is already
  protected by existing CLI and integration coverage

### Transitional but acceptable

- engine supports only `RestoreModeFileIDs`, while stored-path restore remains
  outside the active engine seam
- `restoreByIDPhase` still converts engine results back into
  `storage.RestoreFileResult` for CLI command handling
- stored-path destination semantics and metadata options are not part of the
  active engine route
- restore item results do not currently expose structured invariant metadata
- by-ID dry-run is intentionally narrower than full live restore execution

### Candidate guard gaps

- preserve by-ID restore dry-run/output-path parity with live success output
- preserve the unsupported stored-path engine boundary against accidental
  routing expansion
- preserve the current restore seam where missing structured invariant
  metadata is a documented boundary rather than an accidental contract change
- preserve CLI validation around `--strict` / `--no-metadata` and stored-path
  destination semantics

These are candidate guard/test concerns for Phase 8, not current bug claims.

## Phase 4 decision

The current `Restore` ownership boundary is acceptable for `v1.13.5`.

The active by-ID engine request validation, structured by-ID result shape, and
storage-layer restore-safety invariants are separated clearly enough for the
current engine-facing path.

No Phase 4 ownership migration, production code change, or test change is
required.

If later phases choose to add coverage, it should be a narrow Phase 8 guard
pass rather than a Phase 4 behavioral rewrite.

## Impact statement

Phase 4 documents current restore ownership only.

It changes no production code, no tests, no scripts, no CI behavior, no
public CLI behavior, no JSON output, no error envelope shape, no exit codes,
and no runtime behavior.
