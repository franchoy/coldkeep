# Coldkeep v1.13.3 — Stats Contract Cleanup Map

## Status

`complete`

## Purpose

This document maps the current `stats` read-side contract and identifies the
safe cleanup and test-hardening plan for later `v1.13.3` phases.

This document does not change `stats` behavior.

This document does not change `stats` routing.

This document does not change `stats` JSON output.

This document does not change `stats` exit codes.

This document does not introduce new `stats` request or result types.

This document is input for Phases 6, 7, and 8.

## Relationship to Phase 1

Phase 1 established the key `stats` finding that drives this phase:

`stats` is engine-wrapped but still returns `observability.StatsResult`.

Current `stats` ownership summary:

- current CLI entry point: `runStatsCommand`
- current engine involvement: CLI opens the repository context, constructs an
  engine, and calls `eng.Stats(engine.StatsRequest{...})`
- current observability ownership: observability owns the actual `Stats`
  service logic and the concrete result model
- current renderer ownership: `internal/cli/render` owns public human and JSON
  success rendering
- current backend, catalog, and storage dependencies: observability reads
  maintenance-derived aggregate state, graph reachability state, and DB-backed
  repository metadata; the result includes storage-block, container, chunk,
  retention, and snapshot-derived views

## Current Stats Flow

Current code-path flow:

```text
CLI stats command
  -> flag parsing and validation
  -> output mode selection
  -> trace option resolution
  -> runObservabilityStatsPhase
  -> storage context / DB opening
  -> engine.New
  -> eng.Stats(engine.StatsRequest{IncludeContainers, Trace})
  -> observability.Service.Stats(StatsOptions)
  -> maintenance.RunStatsResultWithDB
  -> graph enrichment and efficiency calculation
  -> observability.StatsResult
  -> renderer human or JSON output
```

- `observability.StatsOptions` exists in `internal/observability`

## Current Stats Behavior To Preserve

Verified current public behavior that must remain unchanged:

- command name is `stats`
- accepted flags are `--output`, `--json`, `--containers`, `--trace`,
  `--trace-json`, `--help`, and `-h`
- non-empty positional arguments are usage errors
- human output is renderer-owned and includes the `Coldkeep stats` header
- JSON success output uses the renderer envelope with:
  - `type: "stats"`
  - `meta.version: "v1.7"`
  - `meta.exact: true`
- warnings remain in the JSON success envelope when present
- `--containers` affects inclusion of per-container detail records and human
  container-detail sections
- trace flags alter trace-sink behavior, not the semantic result shape
- empty repository is a valid successful stats read and must not be reframed as
  an error
- failures currently route through shared CLI error translation with no
  dedicated `stats` exit-code redesign
- backend-visible behavior is expected to remain equivalent across supported
  backends

## Error Taxonomy Mapping For `stats`

| Error family | Current source | Current representation | Public behavior | v1.13.3 decision |
| --- | --- | --- | --- | --- |
| validation / usage errors | CLI parsing in `runStatsCommand`, `ensureAllowedFlags`, `resolveTraceOptions`, positional validation | `usageErrorf(...)` / `cliError` | usage-style message and shared usage exit classification | `preserve as-is` |
| domain / state errors | no primary active `stats` state-miss seam found | not a first-class current `stats` category | empty repository remains success, not a domain failure | `document as not a primary stats surface` |
| invariant / integrity errors | indirect only, mainly warnings or shared CLI invariant handling if downstream errors surface | warnings in success payload or shared invariant error handling | no dedicated `stats` invariant contract today | `document as indirect / provisional` |
| runtime DB errors | observability and maintenance query/read failures | wrapped `fmt.Errorf("collect observability stats: ... %w", err)` chains and query-specific maintenance errors | shared CLI general failure behavior | `candidate for Phase 6 and Phase 7 protection` |
| catalog-origin errors | DB aggregate and graph queries through observability and maintenance | wrapped runtime-like DB/query errors | shared CLI general failure behavior | `document honestly; no new helper` |
| storage-origin errors | indirect through block/container/storage-derived aggregate fields | not a first-class typed `stats` seam | currently surfaces, if at all, through lower-level wrapped failures or aggregate values | `document as indirect` |
| environment / config errors | repository/context/DB open failures, nil DB, tool/runtime setup failures | wrapped setup or DB-open failures | shared CLI general failure behavior | `candidate for later preservation checks` |
| unsupported / deferred errors | no active `stats` unsupported or deferred seam found | not current behavior | should not be introduced accidentally | `document as not current behavior` |
| unknown / provisional errors | wrapper ownership and result-type ownership seam | document-backed only | no public taxonomy leakage | `document as provisional only` |

Important mapping constraints:

- do not claim unified stats taxonomy wrapping
- do not introduce new helper names
- do not classify empty-repository success as a domain error

## Domain Vs Invariant Boundary For `stats`

Current boundary guidance from repo truth:

- empty repository stats remain a valid successful read
- runtime DB/read failures are runtime, catalog-origin, or environment-origin
  failures, not domain not-found
- warnings or mismatch-style stats observations must not be overstated as a
  settled invariant contract unless current code already treats them that way
- zero-valued empty-repository output must not be reframed as an error
- impossible metadata totals, graph mismatches, or similar concerns should stay
  documented as warning or later-decision surfaces unless later phases add a
  test-backed invariant contract

## Backend Compatibility Notes

Current backend observations:

- `engine.StatsRequest` and `engine.Config` are backend-neutral by existing
  engine backend-compatibility tests
- observability and maintenance use `QueryRowContext` and aggregate SQL query
  patterns rather than exposing backend-specific fields through the public
  engine stats request surface
- `stats` covers packed and legacy storage metrics through
  `maintenance.BlockStats`
- `stats` covers storage blocks, chunk references, retention, container
  records, and snapshot reachability enrichment
- supported behavior is expected to be backend-equivalent

Tests already found that support backend or contract confidence:

- engine backend-neutral public type tests in
  `internal/engine/backend_compat_test.go`
- observability equivalence tests covering empty repo, large repo, multiple
  snapshots, deleted snapshots, and churn scenarios in
  `internal/observability/equivalence_phase7_test.go`
- observability cross-consistency tests in
  `internal/observability/cross_consistency_test.go`

Missing or later candidate checks:

- CLI-level backend parity preservation for `stats`
- explicit runtime-failure translation checks for `stats`

## Public CLI Preservation Notes

Preservation concerns that later phases must keep explicit:

- human output preservation:
  - renderer-owned layout and section naming must not drift accidentally
- JSON output preservation:
  - success envelope shape, `type`, `meta.version`, and warning handling must
    remain stable
- JSON error-envelope preservation:
  - `stats` uses shared CLI error JSON; later phases must not accidentally add
    stats-specific taxonomy fields
- exit-code preservation:
  - `stats` depends on shared CLI exit classification and must not get a
    custom behavior drift
- startup / logging / noise concerns:
  - trace flags intentionally send trace output to stderr sinks without
    redefining success result shape
- taxonomy helper leakage concerns:
  - no taxonomy helper names or internal classification fields should appear
    in public `stats` JSON

## Risks If `stats` Contract Is Cleaned Incorrectly

- accidental JSON drift
- accidental human-output drift
- accidental exit-code drift
- treating empty repository as error
- treating runtime DB failure as domain not-found
- hiding invariant-adjacent inconsistencies as ordinary zeros
- introducing SQLite-only SQL assumptions
- breaking PostgreSQL parity
- leaking internal taxonomy labels
- moving ownership before preservation tests exist
- duplicating result shapes without clarifying the real owner

## Final Phase 2 Decision

`Stats` is acceptable for `v1.13.3` as an engine-wrapped read-side surface that
still returns an observability-owned result type, provided later phases
protect public CLI/JSON/exit-code behavior and document the result ownership
as provisional for later engine-contract cleanup.
