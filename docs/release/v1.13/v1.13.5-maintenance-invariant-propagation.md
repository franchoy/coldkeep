# Coldkeep v1.13.5 GC and Maintenance Invariant Propagation Review

**Release:** `v1.13.5 — Release Record Closure and Engine-Level Invariant Ownership`
**Phase:** Phase 5
**Status:** Complete
**Branch:** `release/v1.13.5`

## Purpose

This document reviews how GC, maintenance, repair-adjacent, and
recovery-adjacent invariant errors are created, wrapped, propagated,
classified, and rendered publicly.

This phase performs no ownership migration and no behavior change.

## Reviewed surfaces

- `internal/invariants`
- GC dry-run/live safety paths
- GC integrity refusal paths
- GC foreign-key / catalog-consistency refusal paths
- repair/refcount orphan-row refusal paths
- recovery/quarantine adjacent paths
- CLI public error classification
- JSON and human error-envelope ownership
- current test protection

## Invariant metadata model

Invariant metadata is currently modeled by `internal/invariants.Error`.

The type carries:

- `Code string`
- `Message string`
- `Err error`

Current ownership and behavior:

- invariant code names are owned in `internal/invariants/errors.go`
- recommended actions are not stored as a second structured error field
- recommended actions are derived from code by
  `RecommendedActionForCode(code string)`
- `RecommendedActionForError(err error)` first extracts the invariant code and
  then resolves the recommendation
- `Unwrap()` returns the wrapped cause
- `Code(err)` uses `errors.As` to find `*invariants.Error`
- metadata survives ordinary wrapping such as `fmt.Errorf("...: %w", err)`

This means invariant metadata is stable as an error-chain concern rather than
as a CLI-owned payload object.

The current public/private boundary is:

- domain and maintenance layers create invariant-coded errors
- engine and intermediate wrappers usually preserve those errors unchanged
- CLI decides whether and how to project `invariant_code` and
  `recommended_action` into public JSON/text output

Public output does not read invariant fields directly from domain structs. It
projects invariant metadata through CLI-owned error rendering and batch item
rendering.

## Current GC invariant flow

The current GC invariant flow is:

```text
maintenance GC orchestration
  -> graph / physical integrity / reachability checks
  -> invariant-coded refusal when unsafe state is detected
  -> wrapped or preserved through engine / command path
  -> CLI classification and public error envelope
```

GC safety and invariant creation currently live below the CLI boundary.

The key GC invariant creation points are:

- `GC_REFUSED_INTEGRITY`
  - created in `gcIntegrityPreFlight`
  - used when the `physical_file` graph is unsafe for GC reasoning
  - covers orphan rows, ref-count mismatches, and negative ref counts
  - can wrap an existing invariant-coded cause or stand alone with a direct
    refusal message
- `GC_FK_VIOLATION`
  - created in `commitGCContainerDeletion`
  - used when container-row deletion fails on a foreign-key constraint because
    live references still exist
  - wraps the original FK failure

Current behavior also shows:

- dry-run and live GC share the same integrity pre-flight gate
- reachability and retention analysis remain below CLI and outside engine
  output shaping
- active engine GC preserves top-level maintenance errors instead of
  translating them into a richer engine-native invariant result structure
- public JSON/text success output for GC remains CLI-owned and does not expose
  invariant metadata on success

The current ownership shape is:

- maintenance owns GC orchestration and some invariant creation
- graph/reachability/retention logic owns the lower-level liveness inputs
- `internal/invariants` owns machine-readable code extraction and
  recommendation mapping
- CLI owns public error envelope rendering and exit classification

## Current repair/refcount invariant flow

The current repair/refcount invariant flow is centered on maintenance-layer
fail-closed checks.

The key repair invariant creation point is:

- `REPAIR_REFUSED_ORPHAN_ROWS`
  - created in `RepairLogicalRefCountsResultWithDB`
  - used when orphan `physical_file` rows exist
  - refuses repair rather than normalizing unsafe orphaned state

This is an explicit fail-closed boundary:

- repair does not silently legitimize orphan mappings
- repair stops before recomputing `logical_file.ref_count`
- invariant metadata is attached at the maintenance layer

Propagation differs by command mode:

- single-command repair (`coldkeep repair ref-counts`)
  - maintenance returns the invariant-coded error
  - CLI wraps it through `verifyError(...)`
  - invariant code and recommended action are still preserved through the
    error chain
  - public envelope rendering remains CLI-owned
- batch repair (`coldkeep repair --batch`)
  - CLI executes maintenance phases per target
  - when a maintenance call fails with an invariant-coded error, CLI projects:
    - `InvariantCode`
    - `RecommendedAction`
    into `batch.ItemResult`
  - public JSON/text batch output then renders those item fields

This means repair invariant propagation is:

- command-level for single-target repair
- per-item for batch repair

That split is transitional but acceptable for `v1.13.5` because public
behavior is preserved and the current phase is documentation-only.

## Recovery/quarantine adjacent behavior

Recovery and quarantine-adjacent paths currently behave differently from GC
and repair invariant-coded failures.

Current behavior:

- recovery/quarantine paths primarily return plain errors and direct recovery
  reports
- they do not currently rely on `internal/invariants` for most operator-facing
  failure reporting
- doctor preserves direct recovery ownership and classifies recovery failure as
  `RECOVERY` through CLI exit/error classification
- recovery fail-closed behavior is protected by direct recovery logic and test
  seams, not by invariant-code projection

This appears acceptable for `v1.13.5` because:

- public output remains stable
- safety is preserved
- recovery/quarantine failures are still classified explicitly at the CLI
  boundary
- doctor stops before later phases when recovery fails

The current classification for this release should be:

- current behavior:
  - recovery/quarantine paths use plain errors and recovery reports
- transitional seam:
  - recovery metadata is not aligned with the invariant-code model used by GC,
    repair, verify, and some remove failures
- future release work:
  - later releases may choose to align recovery/quarantine failures with
    invariant metadata if a narrow, behavior-preserving contract emerges

The absence of invariant metadata here is not, by itself, a bug finding in
Phase 5.

## CLI public error ownership

Public error envelopes are assembled by the CLI in `printCLIError`.

Current CLI-owned responsibilities include:

- exit-code classification via `classifyExitCode`
- `error_class` selection
- JSON error-envelope assembly
- human stderr formatting
- projection of:
  - `invariant_code`
  - `recommended_action`
  - verify-specific detail fields when applicable

Current behavior shows:

- `invariant_code` is exposed as a stable public field when an invariant-coded
  error reaches CLI rendering
- `recommended_action` is exposed as a stable public field when the invariant
  code maps to one
- exit-code ownership remains CLI-owned
- human and JSON rendering both preserve invariant metadata, but in different
  forms
- internal helper/type names are not intended as part of the public contract

GC and repair-specific implications:

- successful GC output does not include invariant fields
- failing GC errors can expose invariant metadata through the CLI error
  envelope
- single-command repair failures expose invariant metadata through the CLI
  error path
- batch repair failures can expose invariant metadata per item in public batch
  output

This confirms the current public boundary:

- domain and maintenance layers create invariant-coded errors
- CLI owns public classification and rendering

## Findings

### Stable enough for v1.13.5

- invariant metadata is modeled consistently by `internal/invariants.Error`
- invariant code extraction survives normal wrapping through `errors.As`
- GC integrity refusal and FK-violation boundaries are already explicit and
  machine-readable
- repair ref-count refusal already fails closed with invariant metadata
- CLI centrally owns public invariant rendering and preserves code/action in
  stable public fields

### Transitional but acceptable

- active engine GC preserves maintenance errors but does not expose a richer
  engine-native invariant result structure
- repair single-command mode and repair batch mode propagate invariant metadata
  differently
- recovery/quarantine-adjacent paths remain mostly plain-error/report based
  instead of using invariant-coded failures
- invariant metadata is public mainly through CLI translation rather than a
  uniform engine-facing structured result contract

### Candidate guard gaps

- preserve invariant code and recommended action through extra wrapping layers
  for GC maintenance failures
- preserve repair orphan-row invariant metadata in batch-mode public JSON items
- preserve CLI JSON error-envelope invariant fields for maintenance failures
- preserve recovery/quarantine plain-error behavior as intentionally outside
  invariant metadata for `v1.13.5` if that remains the intended contract

These are candidate guard/test concerns for Phase 8, not current bug claims.

## Phase 5 decision

The current GC and maintenance invariant propagation boundary is acceptable for
`v1.13.5`.

Invariant metadata is created in domain and maintenance layers, extracted
through the error chain, and rendered publicly by the CLI.

No Phase 5 ownership migration, production code change, or test change is
required.

If later phases choose to add coverage, it should be a narrow Phase 8 guard
pass rather than a Phase 5 behavioral rewrite.

## Impact statement

Phase 5 documents current GC and maintenance invariant ownership only.

It changes no production code, no tests, no scripts, no CI behavior, no
public CLI behavior, no human output, no JSON output, no JSON error envelope
shape, no exit codes, no routing, no backend defaults, no schema or migration,
no storage or repository format, and no runtime behavior.
