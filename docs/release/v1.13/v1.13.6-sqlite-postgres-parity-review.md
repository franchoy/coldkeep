# Coldkeep v1.13.6 SQLite/PostgreSQL Schema and Query Parity Review

**Release:** `v1.13.6 — Catalog Contract Expansion and Backend Parity Review`  
**Phase:** Phase 6  
**Status:** Complete  
**Branch:** `release/v1.13.6`

## Purpose

This document reviews whether the catalog contracts inspected in Phases 1–5
behave consistently across SQLite and PostgreSQL.

It consolidates backend-sensitive findings from the catalog inventory,
snapshot membership review, logical/physical mapping review, placement and
restore-plan review, and reachability/GC eligibility review.

This phase performs no implementation work and adds no tests.

## Backend posture under review

- SQLite compatibility must be preserved.
- PostgreSQL compatibility must be preserved.
- SQLite-first direction must not become SQLite-only.
- PostgreSQL-backed validation remains mandatory in the release gate.
- No backend default changes are allowed in `v1.13.6`.

## Backend selection and configuration

Backend selection is explicit in `internal/db`.

- `internal/db.BackendFromDB` detects the active backend from the concrete SQL
  driver and classifies it as SQLite, PostgreSQL, or unknown.
- `internal/db` keeps backend-sensitive behavior near the connection layer:
  - SQLite session pragmas are applied per connection
  - PostgreSQL session options are built from validated environment variables
  - optional `FOR UPDATE` helpers branch from the same backend discriminator
- Local-first posture:
  - the codebase remains SQLite-friendly for local and unit-test workflows
  - many direct tests use in-memory SQLite and explicit schema/bootstrap setup
- Compatibility-backend posture:
  - PostgreSQL remains a mandatory compatibility target rather than an
    optional afterthought
  - focused PostgreSQL coverage is activated through `COLDKEEP_TEST_DB=1`
    suites and the final release gate
- Relevant PostgreSQL env/config inputs are validated in `internal/db`:
  - `DB_HOST`
  - `DB_PORT`
  - `DB_USER`
  - `DB_PASSWORD`
  - `DB_NAME`
  - `DB_SSLMODE`
- Phase 6 observes no reviewed contract that changes the backend default:
  - backend selection stays a deployment/runtime concern
  - catalog contract review does not move the repo toward PostgreSQL-only or
    SQLite-only behavior

## Schema bootstrap and migration parity

Schema/bootstrap/migration ownership remains centralized in `internal/db`.

- SQLite behavior:
  - SQLite fresh bootstrap and migration logic owns schema creation,
    historical normalization, and some table rebuild paths
  - SQLite migration code reads `sqlite_master`, uses `PRAGMA table_info`, and
    explicitly enables `PRAGMA foreign_keys = ON`
  - SQLite schema normalization includes legacy compatibility handling where
    older layouts need reshaping
- PostgreSQL behavior:
  - PostgreSQL fresh bootstrap and automatic migration remain supported through
    `internal/db` schema loading and `ConnectDB`/ensure-schema paths
  - PostgreSQL schema inspection and direct live-bootstrap evidence are more
    focused and environment-gated than the broad in-memory SQLite coverage
- Shared schema-version posture:
  - schema-version tracking is explicit and part of both bootstrap and upgrade
    behavior
  - capability derivation and release-gate expectations depend on the same
    schema-version truth
- FK and constraint posture:
  - both schemas encode the catalog relationships needed by snapshot,
    physical-file, chunk, block, and placement contracts
  - SQLite FK enforcement depends on session pragmas being enabled
  - PostgreSQL enforces the same relationships through native backend
    constraints
- Evidence posture:
  - direct SQLite schema/migration evidence is strong in
    `internal/db/migrations_test.go`
  - direct PostgreSQL bootstrap/upgrade evidence exists, but is concentrated in
    `COLDKEEP_TEST_DB=1`-gated migration tests
  - final parity confidence for PostgreSQL still relies in part on
    release-gate-backed validation

## Dialect and placeholder handling

Dialect and placeholder behavior is mixed: some surfaces are intentionally
neutral, while others are explicitly adapted by backend.

- Backend-neutral placeholder posture:
  - `internal/catalog` documents `$1`, `$2`, and related placeholders as the
    neutral query style
  - the catalog contract relies on SQLite driver compatibility with positional
    `$N` placeholders rather than introducing a separate rebind layer
  - several production snapshot, graph, maintenance, and verify paths also use
    `$N` placeholders directly
- Explicit dialect branching:
  - `internal/repository/capabilities` branches by `BackendFromDB`
  - PostgreSQL metadata inspection uses `information_schema`
  - SQLite metadata inspection uses `sqlite_master` and `PRAGMA table_info`
  - some helper reads use `?` placeholders only inside explicit SQLite
    branches or tests
- `RETURNING` posture:
  - `RETURNING id` remains visible across active store/snapshot/maintenance
    paths and in many tests
  - existing behavior assumes both supported backends accept the production
    insertion patterns currently in use
- `ON CONFLICT` posture:
  - snapshot path upserts explicitly use `ON CONFLICT DO NOTHING`
  - this is documented in `internal/snapshot/path_resolver.go` as the portable
    production path
- `FOR UPDATE` posture:
  - row-lock helpers in `internal/db/backend.go` append `FOR UPDATE` only on
    backends that support it
  - snapshot source enumeration and some storage/container-related flows rely
    on this optional locking model
- SQLite-specific `PRAGMA` surfaces:
  - `PRAGMA foreign_keys = ON`
  - `PRAGMA busy_timeout = ...`
  - `PRAGMA table_info(...)`
- PostgreSQL-specific metadata/query surfaces:
  - `information_schema`
  - advisory-lock SQL
  - PostgreSQL session option strings
- Isolation of dialect handling:
  - capability derivation is clearly dialect-adapted and relatively isolated
  - catalog queries are intentionally neutral
  - broader storage/snapshot/maintenance behavior mixes neutral SQL,
    backend-aware helpers, and test-only SQLite convenience SQL

## Transaction and isolation parity

Transaction ownership remains below catalog and is spread across storage,
snapshot, repair, GC, and migration flows.

- Transaction ownership:
  - migrations, snapshot creation/deletion, restore, remove, store, repair,
    and live GC all open their own transactional boundaries in the active
    lower-layer packages
- Rollback/fail-closed posture:
  - the common pattern is `BeginTx` plus deferred rollback and explicit commit
  - many paths are intentionally fail-closed: incomplete metadata should not
    escape if commit does not succeed
- Snapshot row-locking assumptions:
  - snapshot source enumeration uses optional `FOR UPDATE`
  - PostgreSQL gets row-lock semantics there; SQLite intentionally does not
  - this is an adapted behavior rather than an attempt to pretend both
    backends lock identically
- GC isolation posture:
  - `gc.BuildPlan` is read-only and shared by simulation and live GC
  - live GC adds PostgreSQL advisory locking and transactional sweep behavior
  - SQLite remains dry-run-only for live GC semantics
- Repair isolation posture:
  - repair/refcount runs inside a transaction and refuses orphan rows before
    rewriting `logical_file.ref_count`
- Backend-sensitive observations:
  - advisory-lock behavior is PostgreSQL-specific
  - snapshot/store/remove concurrency semantics depend on the combination of
    transaction boundaries and optional row locks
  - dry-run/live equivalence is intentionally shared at the planning layer, but
    its mutating backend implications still need Phase 7 evidence
- Phase 6 conclusion:
  - transaction behavior is not identical in mechanism across backends
  - the current posture is that behavior is adapted where necessary rather than
    fully abstracted away

## FK and constraint parity

Constraint and orphan-handling behavior is an important backend-sensitive part
of the reviewed contracts.

- SQLite FK assumptions:
  - FK enforcement is not ambient; it must be enabled per connection through
    `PRAGMA foreign_keys = ON`
  - both production setup and some tests make this explicit
- PostgreSQL FK assumptions:
  - FK enforcement is native once the schema is in place
  - PostgreSQL-specific GC failure handling already recognizes backend FK error
    wording
- Orphan/dangling row behavior:
  - verify paths explicitly detect orphan physical rows, orphan snapshot path
    refs, orphan snapshot logical refs, orphan chunks, and dangling placement
    references
  - repair and GC refuse to proceed when critical graph drift is visible
- Refusal posture:
  - repair/refcount refuses orphan `physical_file` rows
  - GC refuses physical-graph drift before planning or sweeping
  - snapshot reachability verification surfaces orphan/dangling snapshot graph
    state rather than normalizing it away
- Corruption-test posture:
  - several tests intentionally disable SQLite FKs to create otherwise invalid
    states and assert refusal/invariant behavior
  - that evidence is useful for safety semantics, but it does not mean the
    production contract assumes FK-disabled operation
- Phase 6 parity reading:
  - the backends differ in how invalid states are prevented
  - the repo compensates with explicit SQLite pragma enabling plus verify,
    repair, and maintenance refusal paths

## Ordering, grouping, and aggregation parity

Many reviewed contracts depend on deterministic ordering and stable aggregate
behavior.

- Deterministic ordering assumptions:
  - snapshot metadata listing orders by creation time
  - snapshot membership and restore-related paths rely on deterministic path or
    `chunk_order` ordering
  - graph roots, placement reads, and some verify scans also use stable order
    for reproducible behavior and tests
- Aggregation assumptions:
  - `COUNT`, `DISTINCT`, `SUM`, and `COALESCE` are heavily used in capability
    derivation, snapshot stats, repair/refcount, verify, maintenance stats, and
    GC summaries
  - NULL/default handling matters in restore-plan metadata, snapshot metadata,
    packed/legacy summaries, and capability observation
- JOIN cardinality assumptions:
  - restore, packed placement, GC planning, and verification all rely on joins
    that must preserve expected row counts even when legacy and packed metadata
    coexist
- Areas that appear relatively backend-neutral:
  - catalog reachability roots
  - catalog logical/physical lookup ordering
  - snapshot path upsert/lookup behavior
  - simple current/snapshot logical-root aggregation
- Areas that remain more sensitive:
  - packed/legacy restore-plan joins
  - GC plan aggregates for dead/live packed blocks and reclaimable bytes
  - verify and maintenance queries over partially missing or corrupted graphs
  - read-side summary counts where grouped rows and fallback defaults matter
- Evidence posture:
  - many focused tests already assert deterministic ordering and aggregate
    stability
  - broader backend parity for the more complex aggregates still leans partly
    on focused suites plus release-gate-backed PostgreSQL validation

## String and path comparison parity

String/path behavior is mostly normalized in code before persistence, but a few
query surfaces remain worth documenting in parity terms.

- Snapshot path comparison:
  - snapshot path identity is normalized before persistence
  - production snapshot-path queries use exact path equality or normalized
    in-memory/path-based logic rather than backend-specific collation features
- Path filtering:
  - restore and snapshot helpers depend on explicit normalization rules more
    than backend collation rules
  - current stored-path behavior remains storage-owned and distinct from
    snapshot-relative normalization
- Name/extension filtering:
  - repository capability helpers and some read-side paths use Go-side string
    normalization or explicit query shapes rather than deep backend-specific
    text operators
- SQL `LIKE` posture:
  - snapshot list filtering and similar metadata queries use `LIKE`
  - this is a visible backend-sensitive area because text matching semantics
    and collation behavior are not identical in every SQL engine
- Go-side case handling:
  - `strings.EqualFold` is visible in some schema/capability inspection helpers
  - this reduces dependence on backend-specific case semantics in those paths
- Phase 6 parity reading:
  - normalized snapshot path identity appears backend-neutral
  - broader substring/text filtering is more likely dialect-sensitive and
    should be carried into Phase 7 evidence classification

## Phase 6 findings

### Backend-neutral observations

- Catalog lookup contracts intentionally use positional `$N` placeholders and
  document SQLite driver compatibility rather than branching by backend.
- Catalog reachability roots are explicitly documented as identical logical-ID
  queries across SQLite and PostgreSQL.
- Snapshot path normalization and `ON CONFLICT DO NOTHING` upsert behavior are
  treated as a portable production path.
- Narrow logical/physical metadata lookups appear relatively backend-neutral at
  the catalog-read layer.

### Dialect-adapted observations

- Repository capability derivation is explicitly dialect-adapted through
  `BackendFromDB`, `information_schema`, `sqlite_master`, and `PRAGMA
  table_info`.
- SQLite requires per-session pragma setup for FK enforcement and busy timeout,
  while PostgreSQL uses validated connection/session option strings.
- Optional `FOR UPDATE` behavior adapts snapshot and storage concurrency paths
  rather than pretending both backends share identical row-lock semantics.
- Live GC is intentionally adapted by backend: PostgreSQL supports advisory
  lock plus live mutation, while SQLite remains dry-run-only.

### Backend-sensitive observations for Phase 7

- Packed/legacy placement and restore-plan joins still depend on grouped
- aggregate parity, ordering stability, and NULL/default handling.
- Snapshot list/filter text matching and some other `LIKE`-based metadata
  filters remain worth classifying as true dual-backend evidence versus
  release-gate-only confidence.
- Repair/refcount and GC refusal semantics depend on FK behavior,
  transaction/isolation effects, and intentionally corrupted-state tests that
  often use SQLite with FKs disabled.
- Read-side stats/inspect semantics remain more SQLite-heavy than the narrow
  catalog contract suites and should be classified carefully in Phase 7.

### Candidate Phase 8 guard areas

- Snapshot metadata/text-filter parity where current confidence relies more on
  focused SQLite tests plus release-gate PostgreSQL validation than on one
  dedicated dual-backend suite.
- Packed/legacy placement aggregate parity if Phase 7 finds that PostgreSQL
  evidence is mostly indirect or release-gate-only.
- Read-side stats/inspect parity if Phase 7 finds the current evidence cluster
  too SQLite-heavy for the reviewed contract surface.

### Immediate blockers

None found.

## Phase 6 decision

The current SQLite/PostgreSQL catalog parity posture is reviewable.

No Phase 6 production or test change is required.

`v1.13.6` can proceed to existing catalog/backend test coverage classification
in Phase 7.

Test sufficiency and any Phase 8 guard decisions remain intentionally deferred
to Phase 7.
