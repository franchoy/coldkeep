# v1.13.0 SQLite/PostgreSQL Compatibility Baseline

## Purpose and Direction

This document records the Phase 7 SQLite/PostgreSQL compatibility baseline for v1.13.0. It is
documentation and inventory only. It does not change Go code, tests, schema, migrations, CLI
behavior, JSON output, exit codes, storage format, repository format, default backend behavior,
engine routing, catalog implementation, CI behavior, or scripts.

Direction and guardrails:

- SQLite-first local portability is a product goal, not a completed product state.
- PostgreSQL compatibility is a strategic constraint, not a legacy path to quietly weaken.
- Neither backend direction should silently weaken the other.
- Any future SQLite-default work still depends on engine/catalog contract stabilization first.

Current direction from repo evidence:

- `README.md` says current work is to prepare the SQLite-first local catalog direction and preserve
  PostgreSQL compatibility.
- `internal/storage/context.go` still defaults `LoadDefaultStorageContext()` to `local`, and the
  `local` path still calls `db.ConnectDB()`. That means Phase 7 must describe the current local
  path conservatively rather than claiming an explicit SQLite-default product switch.
- Simulated storage mode is explicitly SQLite-backed through a temp DB plus `db.RunMigrations`.
- `internal/db/migrations.go` makes the backend split explicit:
  - SQLite uses `RunMigrations`.
  - PostgreSQL uses `EnsurePostgresSchema`.

## Current Backend Evidence

- `internal/db/backend.go` detects both SQLite and PostgreSQL and exposes backend-aware locking
  helpers. `FOR UPDATE`, `FOR UPDATE SKIP LOCKED`, and `FOR UPDATE NOWAIT` are PostgreSQL-aware,
  not generic SQL assumptions.
- `internal/db/migrations.go` gives SQLite an embedded bootstrap and migration chain, while
  PostgreSQL gets embedded schema validation, optional bootstrap, and minimum-version enforcement
  through `EnsurePostgresSchema`.
- `internal/catalog/backend_contract_test.go` and
  `internal/catalog/backend_contract_backends_test.go` provide the strongest current dual-backend
  contract evidence:
  - SQLite catalog contract tests always run.
  - PostgreSQL catalog contract tests run when `COLDKEEP_TEST_DB=1`.
  - CI provides a `postgres:16` service and sets the needed environment.
- `internal/engine/gc_engine_test.go` shows a real backend-specific engine split today:
  - SQLite GC dry-run is exercised.
  - SQLite live GC is explicitly refused.
- `internal/engine/backend_compat_test.go` protects engine public types from backend-specific field
  names and keeps `engine.Config` caller-provided through `*sql.DB` rather than backend-opening
  logic.
- `tests/utils/common.go` and `tests/integration/...` show that the integration harness is still
  heavily PostgreSQL-oriented through `COLDKEEP_TEST_DB` and `DB_*`.
- `.github/workflows/ci.yml` runs multiple correctness and integration jobs against a PostgreSQL
  service, so current CI evidence is stronger for PostgreSQL-backed end-to-end flows than for
  SQLite-backed CLI/integration flows.
- `docs/release/v1.12/sqlite-postgres-baseline.md` remains useful prior evidence for two important
  backend-neutrality rules:
  - catalog placeholder use stays on `$1`-style positional placeholders accepted by both backends
  - catalog timestamp binds must use `time.Time` directly rather than preformatted RFC3339 strings

## Findings

Current backend direction:

- SQLite-first local direction is still preparatory, not complete.
- PostgreSQL remains the strongest end-to-end CI-backed backend today.
- The current default local product path should not be described as a finished SQLite-first switch.

Strongest current parity evidence:

- schema bootstrap and migration behavior in `internal/db`
- implemented catalog lookup contracts across SQLite and PostgreSQL
- backend-neutral engine type-shape safeguards that prevent explicit backend leakage into public
  engine fields

Highest-risk compatibility gaps:

- partial engine ownership still creates backend-risk amplification because a future daemon/API
  caller could over-assume operation parity from incomplete engine seams
- snapshot show/diff/restore/delete still mix catalog, engine, CLI, and direct domain behavior
- repair and recovery/doctor do not yet have parity evidence that is as explicit as the database
  and catalog layers
- deferred catalog graph/placement/restore-plan/GC-plan contracts must not be treated as
  parity-complete just because the interfaces and types exist
- SQLite live GC refusal versus PostgreSQL live-GC expectations is a real backend-specific
  behavioral split that must stay explicit

Could current docs be overread as "SQLite-first is already complete"?

- Yes, if readers confuse roadmap direction with current product default behavior.
- This baseline should make the distinction explicit: SQLite-first is the intended local direction,
  but current repo evidence does not justify claiming that the local product path has already fully
  switched or that engine/catalog contracts are ready to freeze around that assumption.

What must be protected before any future SQLite-default work:

- PostgreSQL compatibility must remain continuously tested.
- backend-specific locking behavior must stay isolated in `internal/db` helpers rather than leaking
  into engine/catalog contracts
- implemented catalog lookup parity must be preserved
- deferred catalog responsibilities must remain explicit until they are real
- engine request/result contracts must separate from current CLI/render/domain leakage before any
  backend-default story is treated as stable
