# Coldkeep v1.13.10 Phase 4 — Release-State Validator Contract

## Purpose

Freeze the complete contract for the dependency-free release-state validator
that Phase 5 will implement. The validator will compare locally available Git
state and bounded current release documentation without rewriting files,
querying remote services, or treating historical prose as current truth.

The active semantic version remains owned by
`internal/version/version.go`. No new release manifest is introduced.

## Drift classes addressed

The contract addresses these checked-in drift classes:

- the synchronized but duplicated executable, unit-test, and pre-release
  checklist version identities;
- the `v1.13.9` tagged changelog entry remaining `Unreleased` after the release;
- the tagged root README continuing to name `v1.13.9` as active;
- the tagged release README continuing to name the subsequently deleted
  `release/v1.13.9` branch as active;
- absence of the canonical `v1.13.9` release gate from the tagged tree and its
  required creation during the next release's closure pass;
- missing v1.13.9 Phase 7 and Phase 8 headings despite checklist evidence;
- completed Phase 24 evidence coexisting with conditional later-phase and
  pre-release language;
- retired v1.13.10–v1.13.13 proposals remaining visible without a structural
  current-versus-historical boundary; and
- review-time branch, pending, and recommendation statements being confused
  with mutable current release state.

No committed executable-versus-checklist mismatch was found. That case is a
preventable parity risk, not a claimed historical incident.

## Non-goals

The validator will not:

- query GitHub, Codacy, CI, CodeQL, or remote Git refs;
- prove PR merge state, publication, remote branch deletion, or external run
  results;
- repair or rewrite release documentation;
- become a general Markdown, spelling, or repository-link linter;
- evaluate generic uses of terms such as `active`, `pending`, or `authorized`
  outside bounded current sections;
- decide whether deferred work has been classified correctly on technical or
  product grounds;
- introduce a third-party dependency, release manifest, or suppression file;
- modify runtime, schema, storage-format, repository-format, or backend
  behavior; or
- retroactively rewrite tags or historical release evidence.

## Release lifecycle model

The supported states are `development`, `pre-release`,
`merged-not-tagged`, and `released`. The default selection mode is `auto`; an
explicit state override remains available for isolated fixtures and unusual
local execution, but it does not disable Git-context validation.

| State | Entry and Git context | Required document state | Gate, branch, and tag requirements | Valid next transition |
| --- | --- | --- | --- | --- |
| `development` | Attached `release/vX.Y.Z`, or a GitHub pull-request merge checkout whose `GITHUB_HEAD_REF` is that release branch; at least one phase is incomplete | Changelog is `Unreleased`; release trackers are `Active`; completed phases form a prefix, exactly one phase is `Next`, and the remainder are `Not started` | Previous release is closed; current gate may be absent or draft; the exact current-version tag does not exist | Complete all phases, date the changelog, create the pre-tag gate, and enter `pre-release` |
| `pre-release` | Matching release branch or accepted pull-request merge ref; all phases are complete | Changelog has an ISO date; release trackers are `Ready for release`; all phases are `Complete` | Current pre-tag gate is passed but awaiting publication; matching release branch identity is required; current tag is absent | Merge the reviewed head to `main` |
| `merged-not-tagged` | Attached `main` or CI `refs/heads/main`; the exact annotated tag is absent | Same immutable candidate content as pre-release | Release branch existence is not required; current tag is absent | Create the annotated tag from the exact merge commit |
| `released` | Exact annotated `vX.Y.Z` tag peels to `HEAD`; detached tag checkout and `main` at the tagged commit are accepted | Tagged tree retains dated, all-complete, `Ready for release` pre-publication truth | Annotated local tag is required; branch existence is ignored; later external facts are not required | Record post-release closure before activating the next version |

Automatic inference uses this precedence:

1. An exact annotated active-version tag at `HEAD` selects `released`.
2. `main` without that tag selects `merged-not-tagged`.
3. A matching release branch or accepted pull-request merge ref selects
   `pre-release` when every phase is complete and `development` otherwise.
4. A detached, untagged checkout without recognized GitHub pull-request or
   main context is ambiguous and is an exit-code `2` error unless an explicit
   state is supplied.

For pull-request checkouts, `refs/pull/<number>/merge` is accepted only when
`GITHUB_HEAD_REF` equals `release/vX.Y.Z`. `GITHUB_REF_NAME`, which may contain
`<number>/merge`, is never treated as the head branch. `GITHUB_REF`,
`GITHUB_REF_NAME`, `GITHUB_HEAD_REF`, and `GITHUB_EVENT_NAME` are the only CI
context inputs; no event API or network call is allowed.

`Active` is a release-level status. `Next` is a phase-level status, so those
two values may coexist at different levels. Phase-level `Active` is invalid.
The only phase statuses are `Complete`, `Next`, and `Not started`.

The immutable tag cannot contain facts produced after publication. A later
documentation closure commit is therefore mandatory before the next version
enters `development`. It closes the prior trackers and gate, records manually
verified external evidence, advances bounded current sections, and never moves
or rewrites the tag.

## Source-of-truth hierarchy

| Fact | Authoritative source | Secondary consistency sources | States | Automated? |
| --- | --- | --- | --- | --- |
| Semantic version | `Major`, `Minor`, and `Patch` in `internal/version/version.go` | Version unit test, pre-release `expected_version`, changelog, current docs | All | Yes |
| Current release title | Active scope `**Release:**` | Phase list, checklist, train, and changelog when present | All | Yes |
| Current release status | Active scope `**Status:**` | Phase list, checklist, and current train definition | All | Yes |
| Current phase | Phase-list status progression | Scope summary, checklist phase-status replicas, release README | Development | Yes |
| Phase ordering | Phase-list `## Phase N` sequence | Checklist phase headings | All | Yes |
| Release scope | Active scope | Current train and named reconciliation/contract artifacts | All | Presence only |
| Previous release closure | Previous scope/train status and canonical gate | Previous changelog entry and current README blocks | All | Yes |
| Previous release verdict | Previous gate `## Final verdict` | Historical handoff/review evidence | All | Structure only |
| Active branch | Local Git or GitHub head/ref environment | Active tracker `**Branch:**` | Development and pre-release | Yes, locally |
| Tag identity | Local annotated Git tag and peeled commit | Current gate tag field when present | Released | Yes |
| Publication evidence | GitHub release and release workflow | Post-release gate section | After tag | Manual |
| Deferred-work ownership | Active scope and reconciliation/handoff artifacts | Release train | All | Presence only |

The previous release is selected without assuming contiguous patches. The
validator locates the active version's recognized top-level changelog heading,
then selects the first subsequent distinct semantic-version heading. Both
`## vX.Y.Z ...` and `## [X.Y.Z] ...` are accepted changelog forms.

## Current-state and historical-evidence classification

| File or section | Classification | Mutable? | Enforced meaning |
| --- | --- | --- | --- |
| Source version and version unit test | Current | Yes | Executable version and replica |
| Anchored pre-release `expected_version` | Current field in mixed file | Yes | Version replica only |
| First changelog release section | Current section in mixed history | Yes | Active version and lifecycle state |
| Root README status badge and `## Current release state` | Current sections in mixed documentation | Yes | Active version and lifecycle wording |
| Release README `## Current Release State` | Current section | Yes | Active/prior identity and current phase |
| Active scope, phase list, and checklist | Current files | Yes | Release identity, status, phases, and artifacts |
| Active v1.13.10 train block | Current section | Yes | Unique current train definition |
| Train content below `## Historical proposed continuation and final disposition` | Historical planning evidence | No | Historical labels and boundary only |
| `v1.13.9-*` documents | Historical and closure evidence | No during v1.13.10 | Previous closure and gate structure only |
| Handoff review before `## Post-review release closure` | Immutable review-time evidence | No | No current-state keyword rules |
| Post-review and post-release operational evidence | Historical manual evidence | Later closure commit only | Closed status and section presence |
| GitHub, Codacy, CI, PR, and remote refs | External evidence | Outside repository | Manual only |

Historical branch references, historical pending recommendations, and retired
proposals are accepted. They do not require suppression entries because the
validator does not apply current-state rules to historical sections.

## Parsing and marker strategy

The parser uses a limited combination of exact Markdown headings and anchored
regular expressions:

- anchored Go declarations for exactly one integer `Major`, `Minor`, and
  `Patch`;
- anchored version-test expectation and `expected_version` assignment;
- exact current Markdown headings and line-oriented `**Release:**`,
  `**Status:**`, and `**Branch:**` metadata;
- `^## Phase ([0-9]+)\b` as the only phase-block delimiter, so nested
  `## Objective` and `## Validation` headings remain inside their phase;
- the exact release-train historical boundary
  `## Historical proposed continuation and final disposition`; and
- the next same-or-higher-level heading as the end of other bounded sections.

No manifest or HTML comment markers are required. The active validation
checklist uses one minimal structured replica under every Phase 0–8 heading:

```markdown
**Phase status:** Complete|Next|Not started
```

The phase list remains authoritative. Checklist phase-status fields exist only
to make parity explicit; disagreement is a violation rather than a second
ownership decision.

Line numbers are one-based physical file lines. Paths are normalized to
repository-relative POSIX form. A missing-file or whole-file violation uses
line `0`, which human output renders without a `:0` suffix.

## Automated rule catalogue

All automated rules have severity `error`. State abbreviations are D
(`development`), P (`pre-release`), M (`merged-not-tagged`), and R
(`released`). Violations are accumulated unless CKRS001 prevents derivation of
the active version.

| Rule | Name and category | States | Inputs and condition | Failure message | Required negative test |
| --- | --- | --- | --- | --- | --- |
| `CKRS001` | Source version parse / identity | D/P/M/R | Exactly one integer declaration for each source component forms `X.Y.Z` | `source version must contain exactly one integer Major, Minor, and Patch declaration` | Missing, duplicate, non-integer, or malformed component |
| `CKRS002` | Version-test parity / identity | D/P/M/R | Anchored expected `version.String()` value equals source | `version test expects {found}; source version is {expected}` | Test left on previous version |
| `CKRS003` | Pre-release checklist parity / identity | D/P/M/R | Exactly one anchored `expected_version` equals source | `pre-release expected_version is {found}; source version is {expected}` | Mismatch or duplicate assignment |
| `CKRS004` | Changelog identity and lifecycle / identity | D/P/M/R | First release heading equals source; D is `Unreleased`; P/M/R is ISO-dated | `active changelog entry {found} does not satisfy {state} version {expected}` | Wrong version or released candidate still unreleased |
| `CKRS005` | Root README identity / current state | D/P/M/R | Badge and bounded current section name source with compatible active/ready wording | `root README current release is {found}; expected {expected} in {state}` | Prior version remains active |
| `CKRS006` | Release README identity / current state | D/P/M/R | Bounded current section matches version/phase/state and does not activate prior version/branch | `release README current state conflicts with {expected} in {state}` | Deleted prior branch remains current |
| `CKRS007` | Tracker identity, title, and status / active uniqueness | D/P/M/R | Scope, phase list, and checklist agree; D is `Active`; P/M/R is `Ready for release` | `active tracker {field} values disagree: {values}` | One tracker differs |
| `CKRS008` | Release-train uniqueness / active uniqueness | D/P/M/R | Exactly one nonhistorical matching definition; retired proposals are labeled below historical boundary | `release train has {count} current definitions for {version}` | Duplicate active or unlabeled proposal |
| `CKRS009` | Previous changelog closure / prior closure | D/P/M/R | First subsequent distinct changelog version is ISO-dated, not unreleased | `previous release {version} is not recorded as released in CHANGELOG.md` | Prior entry unreleased; skipped patch accepted |
| `CKRS010` | Previous tracker and gate closure / prior closure | D/P/M/R | Prior gate is `Passed and released` with non-pending verdict; prior scope/train are operationally closed | `previous release {version} lacks closed canonical release evidence: {detail}` | Missing gate, pending verdict, or active prior tracker |
| `CKRS011` | Previous release excluded from current meaning / prior closure | D/P/M/R | Current README/train sections do not call prior version or branch active | `current section describes prior release {version} or branch {branch} as active` | Current claim fails; historical claim passes |
| `CKRS012` | Phase topology / tracker parity | D/P/M/R | Phase-list and checklist sets are identical, unique, contiguous from 0, and ordered | `phase topology mismatch: {detail}` | Missing, duplicate, gap, reorder, or checklist-only phase |
| `CKRS013` | Phase status progression / tracker parity | D/P/M/R | Statuses use allowed vocabulary; D is complete prefix, one Next, then not-started; P/M/R all complete | `invalid phase status progression at Phase {phase}: {detail}` | Two Next, Complete after Not started, phase Active, or incomplete candidate |
| `CKRS014` | Checklist and current-pointer parity / tracker parity | D/P/M/R | Checklist status replicas equal phase list; scope and release README point to same current phase | `phase {phase} status or current-phase pointer disagrees across active trackers` | Checklist or pointer mismatch |
| `CKRS015` | Completed artifact existence / artifacts | D/P/M/R | Explicit canonical/repository-relative Markdown artifacts in completed phase blocks exist inside root | `completed Phase {phase} references missing artifact {artifact}` | Missing artifact or root escape |
| `CKRS016` | Git branch/ref compatibility / Git context | D/P/M/R | D/P use matching release branch/accepted PR; M uses main; R accepts main/detached tag | `Git context {context} is incompatible with {state} for {version}` | Wrong branch or ambiguous detach; PR merge ref passes |
| `CKRS017` | Annotated tag identity / Git context | D/P/M/R | D/P/M lack exact tag; R has annotated exact tag peeling to HEAD | `tag v{version} does not satisfy {state}: {detail}` | Lightweight, wrong-target, or missing tag; detached annotated tag passes |
| `CKRS018` | Current gate lifecycle / release gate | D/P/M/R | D permits absent/draft and forbids premature pass; P/M/R require passed pre-tag gate and verdict | `current release gate is invalid for {state}: {detail}` | Missing/premature gate or fabricated post-tag fact |
| `CKRS019` | Required current document set / structure | D/P/M/R | Current inputs and named contract/reconciliation artifacts exist with unique required structure | `required release-state input {path} is missing or structurally ambiguous: {detail}` | Missing tracker, duplicate current heading, or missing historical boundary |

## Automated versus manual evidence

| Evidence | Local | CI | Manual | Rationale |
| --- | --- | --- | --- | --- |
| Source/test/checklist version | Automated | Automated | No | Checked-in and parseable |
| Changelog and README state | Automated | Automated | No | Structurally bounded |
| Phase parity and artifact existence | Automated | Automated | Artifact adequacy | Presence and state are local; quality is judgment |
| Gate existence and structural status | Automated | Automated | Readiness judgment | Gate structure is local |
| Local annotated tag | Automated | Automated on tag checkout | No | Local Git object |
| PR merge status/count | No | No | Yes | Remote GitHub fact |
| GitHub publication/timestamp | No | No | Yes | Post-tag external fact |
| Historical CI/CodeQL/tag workflow | No | No | Yes | The validator cannot verify its own or prior remote result |
| Codacy | No | No | Yes | External service |
| Remote branch deletion | No | No | Yes | Local absence is not remote proof |
| Deferred-work ownership | Artifact presence | Artifact presence | Semantics | Requires technical review |

## Command-line contract

```text
python3 scripts/validate_release_state.py
  [--json]
  [--repo-root PATH]
  [--state auto|development|pre-release|merged-not-tagged|released]
```

`--state` defaults to `auto`. The default repository root is derived from the
resolved script location, not the caller's working directory. `--repo-root`
overrides it. A valid root contains Git metadata,
`internal/version/version.go`, and `CHANGELOG.md`.

The implementation uses only the Python standard library and read-only
`git -C <root> ...` subprocesses. It performs no network access, writes no
file, performs no repair, and works from any current working directory.

## Human-output contract

Success is exactly:

```text
[release-state] OK state=<state> active_version=<version> violations=0
```

Each violation is:

```text
[<rule>] <path>:<line> <message>
```

Line `0` is omitted. The final violation summary is:

```text
[release-state] FAILED state=<state> active_version=<version-or-unknown> violations=<count>
```

An internal error is written to stderr:

```text
[release-state] ERROR <kind>: <message>
```

No output contains timestamps, absolute developer paths, ANSI color, or
environment-dependent ordering. CI uses the same output.

## JSON-output contract

JSON mode emits exactly one compact newline-terminated object on stdout and no
other output. Key order is `status`, `validator`, `state`, `active_version`,
`violations`, `error`:

```json
{"status":"ok","validator":"coldkeep-release-state","state":"development","active_version":"1.13.10","violations":[],"error":null}
```

A violation object has exactly `rule`, `path`, `line`, and `message`:

```json
{"rule":"CKRS004","path":"CHANGELOG.md","line":23,"message":"active changelog entry v1.13.9 does not satisfy development version v1.13.10"}
```

Errors use an empty violation list and an error object with `kind` and
`message`:

```json
{"status":"error","validator":"coldkeep-release-state","state":null,"active_version":null,"violations":[],"error":{"kind":"repository-layout","message":"repository root is missing required anchors"}}
```

## Exit-code contract

- `0`: the contract is satisfied;
- `1`: one or more CKRS violations exist; and
- `2`: invalid usage, repository layout, Git inspection, an undefined parser
  failure, or an unexpected internal error.

CKRS001 is a defined repository violation and returns `1` with
`active_version` set to `null`. Rules requiring a derived version are then
skipped deterministically.

## Determinism and safety requirements

- Accumulate all applicable violations rather than fail on the first one.
- Sort by rule ID, normalized path, line number, then message.
- Normalize all reported paths to repository-relative `/` form.
- Use one-based physical lines and `0` only for missing/whole-file conditions.
- Clear or explicitly set fixture GitHub environment values.
- Do not follow repository-relative artifact paths outside the repository.
- Do not invoke shells for Git commands or accept executable content from docs.
- Do not mutate the real repository in unit tests.
- Emit no timestamp, color, random identifier, or absolute temporary path.

## Test and fixture contract

Phase 5 uses standard-library `unittest` in
`scripts/test_validate_release_state.py`. Tests build minimal repositories in
`tempfile.TemporaryDirectory`, configure fixture-local Git identity, commit
their trees, and create branches or annotated/lightweight tags as needed.
Validator subprocesses use `sys.executable`. No fixture repository is checked
in and the real repository is never mutated.

Windows behavior is represented by direct path-normalization tests and by
asserting that human/JSON paths contain `/` and exclude the temporary absolute
root. The real-repository positive check is the separate CI invocation, not a
lifecycle-sensitive unit test.

These cases are mandatory:

1. source/changelog version mismatch;
2. version-test mismatch;
3. checklist expected-version mismatch;
4. changelog lifecycle mismatch;
5. previous release still `Unreleased`;
6. missing previous gate;
7. duplicate active definition;
8. previous release shown active;
9. previous branch shown currently active;
10. missing phase heading;
11. duplicate phase heading;
12. invalid phase progression;
13. current-phase mismatch;
14. missing referenced completed artifact;
15. historical branch accepted;
16. historical pending statement accepted;
17. retired proposal accepted;
18. pull-request merge ref accepted;
19. detached annotated tag accepted;
20. merged-not-tagged accepted;
21. byte-identical repeated human output;
22. byte-identical repeated JSON output;
23. violation exit code exactly `1`; and
24. invalid-root or Git internal-error exit code exactly `2`.

Also mandatory are skipped previous-version numbering, lightweight-tag
rejection, wrong-target tag rejection, unknown detached HEAD, phase-level
`Active` rejection, all-complete pre-release state, and invocation from a
different working directory.

## CI integration contract

`PRE_RELEASE_CHECKLIST.md` will run, in its quality-equivalent section:

```text
python3 scripts/test_validate_release_state.py
python3 scripts/validate_release_state.py --state auto
```

CI will run fixture tests as a blocking quality step in all contexts. The
real-repository command will be a blocking, context-gated step for:

- pushes to `release/**`;
- pull requests whose `GITHUB_HEAD_REF` starts with `release/`;
- pushes to `main`; and
- pushes of `v*` tags.

Other feature/hotfix contexts run the fixture tests but skip real-repository
lifecycle validation. No step may use `continue-on-error`, `|| true`, or
another failure suppression.

`scripts/audit_ci_enforcement.sh --local-only` will assert that the fixture
test command and context-gated real validation remain present and blocking,
and that release-branch, pull-request, main, and tag contexts remain covered.
Human output is retained in CI logs. Phase 5 will not upload a JSON artifact.

## Phase 5 implementation boundary

Phase 5 must:

- implement `scripts/validate_release_state.py` to this contract;
- add isolated standard-library fixture tests for every mandatory case;
- add the blocking CI unit and real-repository validation steps;
- add both local commands to `PRE_RELEASE_CHECKLIST.md`;
- extend the local CI audit to protect the integration; and
- update only the normal active Phase 5 tracker documentation required to
  record its implementation and validation.

Small validator-only helper modules under `scripts/` are permitted only if the
implementation genuinely needs them. Additional tests for existing CKRS rules
are permitted.

Phase 5 must not rewrite historical documents, query external services,
auto-fix state, add third-party dependencies, create a generic documentation
linter, upload JSON artifacts, introduce a new manifest or suppression file,
or change runtime source, schema, database, storage, repository, or backend
behavior.

## Deferred validator capabilities

Deferred capabilities include remote GitHub/PR/release verification, CI and
CodeQL run lookup, Codacy integration, remote branch-deletion proof, semantic
classification of deferred work, generic Markdown-link checking, automated
repair, JSON artifact upload, and support for release-document layouts outside
the bounded Coldkeep contract.
