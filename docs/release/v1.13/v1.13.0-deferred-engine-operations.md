# v1.13.0 Deferred Engine Operation Inventory

## Purpose and Category Rules

This document inventories deferred, unsupported, fallback, and not-yet-engine-owned operation
paths after v1.12.3. It is documentation only. It does not change routing, behavior, JSON, exit
codes, schema, or implementation.

Conservative rule used here:

- If the engine cannot fully represent or execute the current CLI behavior, the path is not treated
  as safe or fully engine-owned.

Categories used in this inventory:

- `explicit ErrNotImplemented`
- `candidate-only operation`
- `direct CLI bypass`
- `partial engine routing`
- `field/option narrowing`
- `unsupported mode`
- `fallback behavior`

## Explicit ErrNotImplemented and Unsupported Surface

The clearest explicit engine deferrals are:

1. `DefaultEngine.Store` rejects `StoreRequest.Recursive` with `engine.ErrNotImplemented`.
2. `validateRemoveRequest` rejects any `RemoveRequest.Mode` other than `RemoveModeFileIDs` with
   `engine.ErrNotImplemented`.
3. `validateRestoreRequest` rejects any `RestoreRequest.Mode` other than `RestoreModeFileIDs` with
   `engine.ErrNotImplemented`.

Supporting evidence exists in:

- `internal/engine/store_engine_test.go`
- `internal/engine/remove_engine_test.go`
- `internal/engine/restore_engine_test.go`

These tests are evidence only. The inventory above records the product paths rather than the test
assertions themselves.

## Findings

### Count Summary

- Total deferred/fallback paths inventoried: 20
- `explicit ErrNotImplemented`: 3
- `candidate-only operation`: 7
- `direct CLI bypass`: 1
- `partial engine routing`: 4
- `field/option narrowing`: 2
- `unsupported mode`: 0
- `fallback behavior`: 3

### Highest-Risk Items

- `CK-1130-DEFER-012` `inspect`: active engine method exists, but the CLI still bypasses it
  entirely.
- `CK-1130-DEFER-015` `restore`: file-ID mode routes through engine, but stored-path restore stays
  outside the active engine path.
- `CK-1130-DEFER-016` `remove`: file-ID mode routes through engine, but stored-path removal remains
  outside the active engine path.
- `CK-1130-DEFER-017` `snapshot show`: metadata is engine-backed, but file listing and supporting
  stats are still assembled outside the engine.
- `CK-1130-DEFER-018` `snapshot diff`: the current engine seam narrows richer CLI filter semantics.
- `CK-1130-DEFER-020` restore/remove request surfaces: contract fields advertise more engine-owned
  behavior than the active routes actually support.

### Most Dangerous Assumptions For Future Daemon/API Callers

1. Assuming an active engine method means the entire corresponding CLI workflow is engine-owned.
   This is false today for `inspect`, `verify`, `store`, `restore`, `remove`, `snapshot show`, and
   `snapshot diff`.
2. Assuming a request type field implies active support. This is false today for recursive store,
   stored-path restore/remove, and several batch-input and destination-mode fields.
3. Assuming candidate request/result types imply an active method exists. This is false today for
   snapshot create/delete/restore, repair, recover, simulation, and benchmark-adjacent flows.

### Bottom Line

The current engine is useful and increasingly valuable, but a future caller could still
over-estimate ownership in three ways:

- by trusting active method presence too broadly
- by trusting request contract shape too literally
- by assuming candidate operation types imply active engine support

v1.13.x should treat these paths as explicit stabilization targets before making daemon/API claims.
