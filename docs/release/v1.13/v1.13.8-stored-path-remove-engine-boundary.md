## Summary

Phase 7 added the dedicated batch-capable stored-path remove engine boundary:
`Engine.RemoveStoredPaths`.

The new engine method now exposes the existing stored-path unlink behavior
through a truthful request/result contract, owns batch target preparation and
fail-fast semantics, and delegates each live unlink to the mature storage
mutation path while intentionally leaving production CLI stored-path remove on
its current direct CLI/storage route until Phase 8.

## Active Interface Addition

Phase 7 added this active engine method:

```go
RemoveStoredPaths(
	ctx context.Context,
	req RemoveStoredPathsRequest,
) (RemoveStoredPathsResult, error)
```

And these dedicated active types:

```go
type RemoveStoredPathsRequest struct {
	StoredPaths []string
	DryRun      bool
	FailFast    bool
}

type RemoveStoredPathItemResult struct {
	RawTarget         string

type RemoveStoredPathsResult struct {
	DryRun        bool
	ExecutionMode ExecutionMode
	Items         []RemoveStoredPathItemResult

```

## Target Preparation Behavior

`DefaultEngine.RemoveStoredPaths` now:

1. rejects cancelled context before validation;
2. rejects an empty target set with
   `engine: remove stored paths requires at least one target`;
3. rejects a missing DB with
   `engine: remove stored paths database is required`;
4. preserves request order;
5. trims each raw target without absolutizing, cleaning, symlink-resolving,
   case-folding, or inspecting the caller filesystem;
6. turns blank trimmed targets into failed items with `RawTarget` preserved,
   `StoredPath=""`, `MappingRemoved=false`, and stable blank-target error text;
7. treats the first exact trimmed stored path as executable;
8. turns later exact trimmed duplicates into skipped items with `RawTarget`
   preserved, the trimmed `StoredPath`, `MappingRemoved=false`, and the
   existing duplicate message;
9. executes only the unique prepared targets, sequentially.

Blank prepared items and duplicate prepared items never trigger fail-fast.

## Dry-Run and Live Delegation

Dry-run preserves the current stored-path batch CLI semantics:

- read-only lookup of the current mapping and owning logical file ID;
- `Status=planned`;
- `MappingRemoved=false`;
- no mutation of `physical_file`, `logical_file.ref_count`, snapshots,
  `file_chunk`, chunk liveness, or payload state;
- the existing live-parity gaps remain intact for snapshot retention,
  ref-count mismatch, and transaction-time failures.

Live execution reuses
`storage.RemoveFileByStoredPathWithStorageContextResult` for each executable
unique target and maps its fields directly into engine item results.

The method never returns `ErrNotImplemented`.

## Mutation and Invariant Contract

Stored-path remove success may only:

- delete one `physical_file` row;
- decrement `logical_file.ref_count` once.

It must preserve:

- the `logical_file` row and identity;
- `logical_file.original_name`;
- all `file_chunk` rows;
- `chunk.live_ref_count`;
- `chunk.pin_count`;
- snapshot rows and `snapshot_file` rows;
- container files, block files, and payload bytes.

Last-mapping removal remains the valid current-state end condition:

- logical file retained;
- `ref_count=0`;
- zero `physical_file` rows.

Snapshot-retained unlink remains a strict refusal with rollback and existing
invariant metadata:

- no mapping deletion;
- no ref-count change;
- `InvariantCode=SNAPSHOT_RETAINED_DELETE_BLOCKED`;
- existing recommended action;
- `MappingRemoved=false`;
- `Status=failed`.

GC remains the only payload-reclamation owner, and the Phase 0C reopen/rerun
guarantee remains intact: last-mapping removal does not resurrect a synthetic
`/migrated/...` row on SQLite reopen or PostgreSQL schema rerun.

## Fail-Fast and Summary Policy

Execution remains sequential.

Fail-fast stops only after an executable unique target fails. Prepared blank
items and duplicate items do not stop execution.

`RemoveStoredPathsResult` keeps the shared batch summary semantics:

- successful live unlink and planned dry-run items count as `OK`;
- failed items count as `Failed`;
- duplicate prepared items and unexecuted trailing targets count as `Skipped`.
