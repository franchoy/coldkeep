# Coldkeep v1.13.7 SQLite/PostgreSQL Compatibility Guard Review

**Release:** `v1.13.7 — SQLite-First Repository Portability Baseline`
**Phase:** Phase 5
**Status:** Complete
**Branch:** `release/v1.13.7`

## Purpose

This document reviews the compatibility guards that protect SQLite and
PostgreSQL behavior while Coldkeep defines its SQLite-first local portability
direction.

This phase adds no tests and changes no runtime behavior.

## Scope boundaries

This phase is:

- compatibility review only
- not a runtime SQLite implementation
- not a backend-default change
- not a broad parity-suite project
- not Phase 7 implementation authorization
- still PostgreSQL-compatible by requirement

## Current backend posture

Current accepted posture from Phases 1 through 4:

- PostgreSQL is the current normal local runtime backend
- SQLite is currently simulated/test-only
- SQLite-first remains future direction
- runtime-product equivalence is not claimed
- PostgreSQL-backed validation remains mandatory in the release gate

## Compatibility classification model

**Backend-neutral invariant**
A required result or safety property must be the same on SQLite and
PostgreSQL.

**Dialect-adapted equivalent**
Implementation differs by backend, but the observable catalog or engine result
must remain equivalent.

**Intentionally backend-specific**
The behavior legitimately differs and should be documented rather than forced
into fake symmetry.

**Evidence gap**
A required invariant is not sufficiently covered on one or both backends.

**Portability-only requirement**
The requirement applies to future directory-portable in-repository SQLite and
does not imply the same filesystem behavior for PostgreSQL.

**Future product behavior**
The requirement belongs to later normal SQLite local mode or later product
scope, not current runtime behavior.

## Schema bootstrap and migration

Schema/bootstrap behavior is equivalent in intent but not identical in
mechanics.

- SQLite bootstrap and migration are owned by `RunMigrations()` and the
  `LoadSQLiteSchema`/SQLite migration path in `internal/db`.
- PostgreSQL bootstrap and migration are owned by `EnsurePostgresSchema()` and
  `ConnectDB()`.
- SQLite evidence is broad and seam-heavy in `internal/db/migrations_test.go`.
- PostgreSQL evidence is narrower but still direct in
  `internal/db/migrations_test.go`,
  `tests/integration/integration_test.go`, and smoke schema-message checks.
- Both backends rely on explicit schema-version truth and explicit failure when
  the supported state is not available.

Phase 5 conclusion:

- bootstrap and migration are dialect-adapted equivalents
- different migration implementations are not a parity defect by themselves
- current evidence is strong enough to preserve shared schema semantics without
  claiming identical runtime roles

## SQL and dialect adaptation

Current SQL portability posture is mixed and intentional.

Portable as written:

- many production queries use `$N` placeholders that work across the supported
  drivers
- `ON CONFLICT DO NOTHING` and `ON CONFLICT DO UPDATE` are used as shared
  production patterns
- shared ordering and aggregate semantics are exercised in catalog, snapshot,
  verify, stats, and integration paths

Adapted by shared helper:

- `internal/db/backend.go` appends `FOR UPDATE`, `SKIP LOCKED`, or `NOWAIT`
  only when the backend supports them
- backend detection in `internal/db.BackendFromDB` and related helpers keeps
  row-lock behavior explicit

Adapted by backend-specific implementation:

- SQLite introspection uses `sqlite_master` and `PRAGMA table_info`
- PostgreSQL introspection uses PostgreSQL-oriented schema checks and session
  options
- repository capability derivation branches on backend where schema inspection
  differs

Backend-sensitive and covered:

- snapshot source queries explicitly test that SQLite avoids `FOR UPDATE` while
  PostgreSQL appends it
- maintenance GC uses backend-sensitive row-lock helpers
- SQLite FK behavior depends on `PRAGMA foreign_keys = ON`
- PostgreSQL session behavior depends on validated timeout and pool settings

Backend-sensitive and weakly covered:

- deeper aggregation parity for all stats/inspect metrics is supported by broad
  tests, but not by a dedicated dual-backend metrics suite

Deferred compatibility gap:

- no broad runtime-product parity claim is justified for SQLite local mode

Phase 5 conclusion:

- SQL portability is mostly handled through portable query shapes plus narrow
  backend helpers
- current differences are intentional and source-backed
- no broad SQL-parity project is justified in `v1.13.7`

## Catalog contract compatibility

The strongest dual-backend compatibility evidence sits in the catalog layer.

- `internal/catalog/backend_contract_test.go` explicitly runs identical
  logical-file, physical-file, snapshot, listing, reachability, and deferred
  sentinel assertions across both backends
- `internal/catalog/backend_contract_backends_test.go` provides the SQLite and
  PostgreSQL dual-backend harness
- `internal/catalog/neutrality_test.go` protects exported catalog types from
  backend-coupled leakage
- `internal/catalog/service_test.go` protects deferred `ErrNotImplemented`
  behavior without mutation

Coverage posture by concern:

- tested on both backends:
  logical-file lookup, physical-file mapping, snapshot identity, snapshot
  listing/filtering basics, reachability roots, deferred sentinel behavior
- tested only through SQLite fixtures:
  many unit-seam variations around snapshot and maintenance logic
- tested only through PostgreSQL integration:
  full CLI/runtime lifecycle around active normal local mode
- backend-neutral unit seam:
  catalog exported types, service contracts, engine/catalog boundary tests
- deferred `ErrNotImplemented`:
  snapshot graph, placement, restore-plan metadata, GC-plan metadata
- not exercised directly as dual-backend runtime products:
  full runtime SQLite local-mode behavior

Phase 5 conclusion:

- catalog semantic invariants are one of the strongest existing compatibility
  guard families
- deferred catalog APIs remain explicit and safe rather than silently changing
  meaning by backend

## Engine request/result compatibility

The engine contract is intended to remain backend-neutral even when capability
availability differs.

- `internal/engine/unsupported_modes_test.go`,
  `store_engine_test.go`, `restore_engine_test.go`, and
  `remove_engine_test.go` protect unsupported-mode refusal via
  `engine.ErrNotImplemented`
- `internal/engine/validation_vs_unsupported_test.go` keeps validation errors
  distinct from unsupported errors
- CLI engine-routing tests in `cmd/coldkeep/*_engine_routing_test.go` protect
  request/result envelopes and routing meaning
- the active runtime path is still overwhelmingly PostgreSQL-backed, so runtime
  proof is stronger on PostgreSQL than SQLite

Phase 5 conclusion:

- supported engine request/result meaning must remain backend-neutral
- unsupported or deferred surfaces are already explicit rather than silent
- this is sufficient for Phase 6 smoke design, but not enough to claim
  full runtime backend parity

## Store and restore compatibility

Current evidence strongly protects store/restore correctness, but asymmetrically
by runtime role.

Backend-neutral component tests:

- many `internal/storage/*_test.go` suites protect logical identity, chunk
  ordering, rollback, and restore semantics

SQLite-backed test seams:

- in-memory and helper-created SQLite DBs cover storage write/read seams
- direct seam coverage exists for repository config, snapshot, verify, and
  restore logic

PostgreSQL-backed integration paths:

- `tests/integration/integration_test.go` heavily exercises live store, direct
  restore, snapshot restore, remove, GC interaction, wrong-key failure, and
  byte equality
- smoke script verifies restore-all and byte-perfect fidelity

Direct dual-backend comparison tests:

- catalog dual-backend tests exist
- no broad store/restore runtime dual-backend parity suite exists

Phase 5 conclusion:

- restore correctness is a shared invariant
- current runtime evidence is strongest on PostgreSQL, with substantial SQLite
  seam protection below that
- this supports a narrow future smoke design without justifying a broad new
  parity suite

## Snapshot compatibility

Snapshot semantics are guarded by a combination of catalog dual-backend
coverage, SQLite snapshot seams, and PostgreSQL runtime integration.

- SQLite snapshot tests explicitly cover parent/lineage, membership, path
  normalization, and backend-sensitive `FOR UPDATE` handling
- PostgreSQL integration covers create, show, stats, diff, restore, delete,
  lineage, and retention behavior through CLI/runtime paths
- known backend-sensitive behavior is already explicit:
  SQLite avoids `FOR UPDATE`; PostgreSQL appends it where supported

Phase 5 conclusion:

- snapshot lifecycle meaning is intended to remain backend-neutral
- locking mechanics are backend-specific but already documented in code and
  tests as adapted behavior

## Verify and integrity compatibility

Verify behavior is one of the strongest shared safety surfaces.

- SQLite verify unit/seam tests cover foreign-key, ordering, corruption,
  missing-payload, and invalid-metadata refusal
- PostgreSQL integration, smoke, and adversarial suites cover runtime verify
  behavior against real storage and catalog state
- low-level mechanisms differ:
  SQLite tests sometimes manipulate `PRAGMA foreign_keys` and
  `PRAGMA ignore_check_constraints` to construct corruption fixtures
  while PostgreSQL relies on native constraints and live runtime state

Phase 5 conclusion:

- high-level verify semantics are backend-neutral and fail-closed
- low-level backend mechanisms are adapted, not identical
- current evidence is strong enough to preserve the shared verify invariant

## Reachability and GC compatibility

Reachability meaning is shared; live-GC mechanics are not.

- catalog reachability contract tests explicitly run across both backends
- SQLite dry-run and plan-level seams cover reachability metadata logic
- PostgreSQL runtime integration and adversarial suites heavily cover live GC,
  dry-run/real consistency, repair/GC interaction, and fail-closed safety
- `internal/maintenance/gc.go` and `internal/db/backend.go` make row-lock use
  explicit and conditional

Phase 5 conclusion:

- equivalent safety does not require identical live-GC availability
- shared invariant: reachable data must not be deleted
- backend difference in locking/live execution is intentional and must remain
  explicit

## Inspect and stats compatibility

Inspect/stats contracts are broadly protected without needing a dedicated
dual-backend metrics-parity project.

- CLI and renderer tests protect output contracts and envelope ownership
- PostgreSQL integration strongly covers live JSON semantics and aggregate
  fields for stats, inspect, doctor, and snapshot stats
- SQLite unit/seam tests cover many lower-level aggregate and query behaviors
- no broad direct SQLite-versus-PostgreSQL metrics comparison suite exists

Phase 5 conclusion:

- public inspect/stats contracts are already strongly guarded
- broad metrics-parity expansion is out of scope for `v1.13.7`

## Backend-selection safeguards

Current startup and backend-selection safeguards are explicit, not implicit.

- `storage.LoadDefaultStorageContext()` defaults to `local`
- `ParseStorageContext("local")` routes to PostgreSQL through `db.ConnectDB()`
- `ParseStorageContext("simulated")` is explicit and remains distinct from
  normal local runtime
- unsupported storage contexts such as `nas` and `s3` return explicit
  not-implemented errors
- PostgreSQL DSN/env validation is covered in `internal/db/db_test.go`
- missing PostgreSQL schema refusal and auto-bootstrap policy are covered in
  integration tests and smoke
- current runtime does not expose a normal local SQLite reopen path that could
  silently fall back to PostgreSQL

Evidence-strength note:

- "no silent fallback" is strongly supported by the current startup shape and
  docs, but not by a full future SQLite-local runtime test because that runtime
  mode does not yet exist

Phase 5 conclusion:

- startup safeguards are adequate for the current runtime posture
- SQLite test injection remains separate from production startup
- no backend-selection change is justified in this release

## Concurrency and session behavior

Concurrency/session behavior is intentionally backend-specific at the mechanism
level.

SQLite-specific:

- `ApplySQLiteSessionPragmas()`
- `PRAGMA busy_timeout`
- `PRAGMA foreign_keys = ON`
- `SetMaxOpenConns(1)`
- `SetMaxIdleConns(1)`
- file-lock and journal/checkpoint concerns are filesystem-local and future
  portability-specific

PostgreSQL-specific:

- pool sizing and lifetime via `COLDKEEP_DB_*`
- `sslmode`
- row locks and `FOR UPDATE` variants
- external service availability

Shared invariants:

- no partial catalog state should escape a failed operation
- failures should be deterministic and explicit
- rollback should be safe
- reachable data must not be lost
- concurrent behavior must not silently corrupt the repository

Phase 5 conclusion:

- implementation details should not be forced to match across backends
- shared correctness invariants are the real compatibility target

## Encryption and codec behavior

Codec/encryption behavior is fundamentally storage-level and intended to remain
backend-neutral.

- integration, adversarial, CI, and smoke all run both `plain` and `aes-gcm`
  across the PostgreSQL-backed runtime path
- SQLite seams indirectly exercise the same storage/verify logic below the
  runtime backend layer
- `COLDKEEP_KEY` handling, wrong-key refusal, malformed-key refusal, and
  ciphertext/authentication failure behavior are already well covered

Phase 5 conclusion:

- codec semantics should be treated as backend-neutral
- test setup differs by backend, but the data-path contract should not

## Required shared invariants

The minimum compatibility invariants that must remain protected are:

- schema invariant: both backends represent the same supported logical catalog
  model
- catalog semantic invariant: supported catalog operations keep the same
  logical meaning
- engine semantic invariant: supported engine request/result contracts do not
  silently change meaning by backend
- restore invariant: the same logical content restores to identical bytes
- verify invariant: inconsistent catalog/storage state fails closed
- reachability invariant: live and snapshot-retained data remain reachable
- GC safety invariant: backend differences must never allow unsafe deletion
- error invariant: unsupported or unavailable behavior is explicit
- compatibility-gate invariant: PostgreSQL-backed validation remains mandatory

## SQLite portability-only requirements

The following concerns are SQLite portability-only and must not leak into
PostgreSQL contracts:

- catalog under repository root
- SQLite sidecar handling
- clean-close and checkpoint filesystem contract
- directory copy/move safety
- repository-root-derived SQLite path

These are future local portability concerns, not current shared backend
contracts.

## PostgreSQL operational-portability requirements

PostgreSQL portability remains operational, not directory-based.

- external catalog backup
- external catalog restore
- reconnect after transfer
- payload/catalog generation coordination

These remain compatible with SQLite-first direction without being the same
filesystem portability problem.

## Strong current guards

The strongest current compatibility guards are:

- dual-backend catalog contract tests in `internal/catalog/backend_contract_test.go`
- catalog neutrality and deferred-sentinel tests in `internal/catalog`
- SQLite migration/bootstrap coverage in `internal/db/migrations_test.go`
- PostgreSQL bootstrap/missing-schema/auto-migration coverage in
  `internal/db/migrations_test.go` and `tests/integration/integration_test.go`
- engine unsupported/validation boundary tests in `internal/engine`
- extensive PostgreSQL-backed integration, adversarial, smoke, and CI coverage
- CLI JSON and output contract tests in `cmd/coldkeep` plus integration tests

## Weak or missing guards

Confirmed weaker areas are:

- no normal local SQLite runtime product path
- no broad direct SQLite-versus-PostgreSQL runtime parity suite
- post-relocation compatibility remains unproven and belongs to Phase 6 design
- some inspect/stats aggregate parity is supported indirectly rather than by a
  dedicated dual-backend metrics suite
- PostgreSQL operational portability is not proven end to end

## Phase 6 inputs

Phase 6 smoke-test design must preserve:

- backend-neutral engine/catalog semantics
- no PostgreSQL regression
- no normal SQLite runtime claim
- use of the normal SQLite migration/catalog seam
- verify and restore assertions
- narrow execution cost

## Phase 7 candidate posture

No broad SQLite/PostgreSQL parity suite is justified for Phase 7.

Phase 7 may add only the narrow portability guard approved by Phase 6 and, if
required, a small compatibility assertion proving that shared engine/catalog
semantics remain backend-neutral.

## Phase 8 inputs

Documentation follow-up candidates for Phase 8:

- keep SQLite-first wording explicit about current simulated/test-only runtime
  posture
- keep PostgreSQL described as supported and mandatory in release validation
- avoid implying that SQLite filesystem portability requirements apply to
  PostgreSQL-backed repositories
- avoid language that suggests current runtime backend default has already
  switched

## Phase 5 conclusion

Current compatibility evidence is sufficient to proceed to Phase 6 smoke-test
design.

PostgreSQL remains the required normal-runtime and release-gate compatibility
target.

SQLite-first portability work must remain explicit about its current
simulated/test-only runtime posture.

No backend-default change and no broad compatibility implementation are
justified in `v1.13.7`.
