# v1.13.0 Catalog Contract and Deferred-Method Inventory

## Purpose and Classification Rules

This document inventories the current `internal/catalog` contract surface after v1.12.3. It is
documentation only. It does not change Go code, tests, routing, schema, or implementation.

Core distinction:

- Database schema exists != catalog contract is stable.
- Catalog package exists != engine/catalog boundary is complete.

Responsibility-area labels used here:

- `logical file identity`
- `physical file mapping`
- `snapshot graph`
- `snapshot file membership`
- `chunk/block/container placement`
- `reachability`
- `GC planning metadata`
- `restore planning metadata`
- `verify/integrity expectations`
- `migration/schema compatibility`
- `backend capability detection`
- `transaction boundary`
- `other`

Status values used here:

- `implemented`
- `partial`
- `deferred`
- `candidate`
- `test-only`
- `unclear`

Conservative rules used here:

- Exported types and interfaces are not treated as stable merely because they exist.
- Backend-neutral type shape is weaker evidence than real cross-backend contract tests.
- Deferred catalog methods are only considered safe where their incompleteness is explicit and not
  accidentally relied on as a complete boundary.

## Backend and Test Coverage Findings

### Backend Coverage Summary

- Strongest `both` coverage exists for:
  - `FindLogicalFile`
  - `FindPhysicalFilesForLogicalFile`
  - `FindSnapshot`
  - `ListSnapshots`
  - `LoadReachabilityRoots`
  - the four deferred methods, but only for explicit `ErrNotImplemented` consistency
- Strongest `backend-neutral` coverage exists for:
  - `DB`
  - `Service` constructors
  - deferred contract types whose shape is neutral but whose behavior is not yet implemented
- No meaningful catalog contract item should be treated as PostgreSQL-only or SQLite-only today,
  but some confidence still comes more from backend-contract tests than from the type shapes
  themselves.

### Contract-Test Coverage Summary

- `neutrality_test.go` protects exported-type neutrality and prevents direct SQL/renderer leakage.
- `dependency_test.go` protects catalog dependency direction and boundary intent.
- `service_test.go` covers constructors, implemented SQLite-facing behavior, and deferred-method
  consistency.
- `backend_contract_test.go` is the strongest cross-backend evidence for implemented lookup methods,
  snapshot metadata listing, reachability roots, and deferred-method `ErrNotImplemented`
  consistency.
- Test coverage is strongest for implemented read-side lookups and explicit deferred-method
  consistency, not for full graph/placement/restore-plan/GC-plan ownership.

## Boundary Gaps

The current catalog boundary is strongest for read-side metadata lookup, not for full metadata
ownership across the product.

Most important gaps:

1. Snapshot metadata is only partially catalog-owned. `FindSnapshot` and `ListSnapshots` exist and
   are used by engine, but snapshot file membership for `snapshot show` still routes through
   `internal/snapshot` rather than a catalog method.
2. Snapshot graph ownership is still only implied by exported interface and type shape. No real
   graph behavior exists behind `LoadSnapshotGraph`.
3. Placement ownership is still deferred. Packed/legacy placement unification remains outside the
   current catalog boundary.
4. Restore planning metadata is still outside catalog despite `RestorePlanCatalog`,
   `RestorePlanInput`, and `RestorePlanMetadata` existing.
5. GC planning metadata is still outside catalog despite `GCPlanCatalog`, `GCPlanInput`, and
   `GCPlanMetadata` existing.
6. Reachability roots are implemented in catalog, but broader verify/GC safety planning is still
   owned by other domain layers.
7. The engine currently uses catalog directly only for a narrow metadata subset, mostly snapshot
   list/show metadata helpers. That is useful progress, but it is not evidence that the full
   engine/catalog boundary is complete.

### Bottom Line

`internal/catalog` is real and useful, but it is not yet a complete metadata boundary.

What is truly contract-owned today:

- logical file identity lookup
- physical file mapping lookup
- snapshot metadata lookup/listing
- reachability-root lookup

What is not yet truly catalog-owned:

- snapshot graph
- snapshot file membership as a stable catalog boundary
- chunk/block/container placement
- restore planning metadata
- GC planning metadata
- broader verify/GC/restore/store safety planning that still lives in domain/engine logic

v1.13.x should treat catalog as an important stabilization seam, but not yet as a complete metadata
facade for v2 daemon/API use.
