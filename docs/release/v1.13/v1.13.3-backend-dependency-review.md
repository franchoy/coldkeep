# Coldkeep v1.13.3 — Backend Compatibility and Dependency-Direction Review

## Status

`complete`

## Purpose

This document reviews backend compatibility and dependency direction for the
`v1.13.3` read-side contract surfaces:

- `stats`
- `inspect`
- `snapshot show`
- `snapshot diff`

This document does not change backend behavior.

This document does not change SQL.

This document does not change dependency direction.

This document does not change routing.

This document does not change CLI, JSON, or exit-code behavior.

This document is input for Phase 9 documentation and release-gate drafting and
for Phase 10 `PRE_RELEASE_CHECKLIST.md` execution.

The current read-side backend and dependency state is acceptable for
`v1.13.3` because public behavior, taxonomy boundaries, and CLI preservation
are now documented and test-protected.

The remaining risk is not a release blocker for `v1.13.3`; it is the continued
presence of provisional ownership seams:

- `stats` still returns an observability-owned result through an engine wrapper
- `inspect` still uses a direct CLI-to-observability production path
- `snapshot show` still mixes engine-backed metadata/stats with direct snapshot
  file listing and CLI JSON assembly
- `snapshot diff` still mixes richer CLI parsing, a narrowed engine seam,
  snapshot-owned detailed logic, and CLI reprojection

## Backend Compatibility Principles

Rules for `v1.13.3`:

- SQLite compatibility must remain preserved.
- PostgreSQL compatibility must remain preserved.
- No SQLite-only assumption may be introduced into read-side contracts.
- No PostgreSQL compatibility may be removed from read-side behavior.
- Backend defaults must not change.
- Query behavior must remain equivalent where the current contract already
  expects equivalence.
- Any backend-specific difference must be documented rather than hidden behind
  generic language.
- Phase 10 must validate the release against `PRE_RELEASE_CHECKLIST.md`
  Profile A.

## Stats Backend Compatibility Review

Current ownership:

- CLI opens storage context and constructs the engine
- engine wraps the call surface
- observability owns the concrete stats logic
- maintenance and graph-adjacent reads provide much of the aggregate state

Current backend assumptions:

- request/config types are backend-neutral by test
- aggregate logic relies on `QueryRowContext`, `QueryContext`, `COUNT`, `SUM`,
  `COALESCE`, ordered snapshot iteration, and maintenance queries rather than
  backend-specific public fields
- packed and legacy block stats are both active in the returned surface

Current backend risk:

- low public compatibility risk, because the public result shape is already
  protected and the lower-layer aggregate semantics are covered by existing
  tests
- medium implementation risk, because the engine result is still observability
  owned and renderer coupling remains provisional

Backend parity evidence found:

- `internal/engine/backend_compat_test.go`
- `internal/observability/equivalence_phase7_test.go`
- `internal/observability/cross_consistency_test.go`
- Phase 7 CLI preservation tests

Missing or deferred backend checks:

- explicit CLI-level SQLite/PostgreSQL parity for `stats`
- deeper runtime DB-failure matrix for read-side aggregate failures

`v1.13.3` decision:

- `stats` is acceptable as-is for `v1.13.3`
- result ownership and renderer coupling remain provisional and should move to
  later review rather than Phase 8 implementation

## Inspect Backend Compatibility Review

Current ownership:

- production CLI path still calls observability directly
- engine inspect request/result wrappers exist but are not the active route
- renderer uses observability-owned result shapes

Current backend assumptions:

- direct `QueryRowContext` and `QueryContext` reads drive repository, file,
  snapshot, chunk, and container inspection
- snapshot and relation views use portable SQL primitives such as `CAST`,
  `COUNT`, `LIMIT`, and `COALESCE`
- `logical-file` is a CLI alias to the file entity path
- `EntityPhysicalFile` exists internally but is not a public CLI target

Current backend risk:

- medium public compatibility risk because direct query behavior is active
  across multiple entity shapes
- medium dependency risk because the direct CLI -> observability seam remains
  active and provisional

Backend parity evidence found:

- `internal/engine/backend_compat_test.go`
- `internal/observability/inspect_test.go`
- `internal/observability/service_test.go`
- Phase 6 read-side taxonomy boundary tests
- Phase 7 CLI preservation tests

Missing or deferred backend checks:

- explicit CLI-level SQLite/PostgreSQL parity for `inspect`
- wrong-entity or wrong-ID-type backend parity beyond current validation-path
  tests
- broader runtime DB-failure parity for entity-specific reads

`v1.13.3` decision:

- `inspect` remains acceptable but provisional
- direct observability ownership should be handed to a later dependency review,
  not changed in Phase 8

## Snapshot Show Backend Compatibility Review

Current ownership:

- metadata lookup uses engine-backed catalog routing
- file/path listing remains direct `snapshot.ListSnapshotFiles`
- stats lookup uses engine-backed snapshot stats and is then reprojected back
  into snapshot-owned shapes
- JSON success payload is assembled in the CLI
- human output is renderer-owned

Current backend assumptions:

- metadata and stats paths rely on engine/catalog seams that are intended to
  stay backend-neutral
- file/path listing still depends on direct snapshot helper reads across
  snapshot, snapshot_path, snapshot_file, and logical-file-derived state
- empty snapshot remains success
- missing snapshot remains the current mixed-seam error path rather than a
  dedicated public taxonomy layer

Current backend risk:

- medium compatibility risk because the surface spans metadata lookup, file
  listing, and stats with different active owners
- high dependency risk because the seam is intentionally mixed and still relies
  on reprojection plus CLI JSON assembly

Backend parity evidence found:

- `internal/engine/backend_compat_test.go`
- `internal/engine/snapshot_engine_test.go`
- `cmd/coldkeep/snapshot_engine_routing_test.go`
- `cmd/coldkeep/partial_routing_boundaries_test.go`
- existing snapshot show contract and CLI preservation tests

Missing or deferred backend checks:

- explicit SQLite/PostgreSQL parity for filtered snapshot show path and count
  behavior
- deeper runtime DB-failure parity across metadata lookup, file listing, and
  stats seams

`v1.13.3` decision:

- `snapshot show` is acceptable but provisional
- because it crosses multiple active seams, it deserves explicit Phase 10
  validation attention even though no fix belongs in Phase 8

## Snapshot Diff Backend Compatibility Review

Current ownership:

- CLI owns richer query parsing and `--filter` handling
- engine owns the active wrapper seam for diff requests
- summary fast path uses engine-backed summary SQL behavior
- detailed path delegates through engine to snapshot-owned detailed diff logic
- detailed results are reprojected back to snapshot-owned result shapes
- CLI assembles JSON success output
- renderer owns human summary and detailed output

Current backend assumptions:

- summary and detailed paths both rely on portable SQL primitives
- query/narrowing behavior is partly preserved into engine request shapes and
  partly applied again in the CLI
- empty diff and no-match filtered diff are success states
- repeated path/prefix inputs are richer in the CLI than in the current engine
  seam

Current backend risk:

- medium compatibility risk because the summary fast path and detailed path are
  separate active routes
- high dependency risk because the seam is both provisional and behaviorally
  narrowed before the engine boundary

Backend parity evidence found:

- `internal/engine/backend_compat_test.go`
- `internal/engine/snapshot_engine_test.go`
- `cmd/coldkeep/snapshot_engine_routing_test.go`
- `cmd/coldkeep/partial_routing_boundaries_test.go`
- Phase 6 taxonomy tests
- Phase 7 CLI preservation tests

Missing or deferred backend checks:

- explicit SQLite/PostgreSQL parity for summary fast path vs detailed path
- query/filter/backend equivalence for narrowed exact path and prefix inputs
- PostgreSQL-specific snapshot path/filter behavior beyond current lower-layer
  confidence
- SQLite-specific path/filter behavior beyond current lower-layer confidence

`v1.13.3` decision:

- `snapshot diff` is acceptable but provisional
- it needs Phase 10 validation attention because backend equivalence confidence
  is distributed across lower-layer tests, routing tests, and release-gate
  evidence rather than a single unified parity suite

## Dependency-Direction Principles

Rules for `v1.13.3`:

- Do not move routing in Phase 8.
- Do not refactor packages in Phase 8.
- Mixed ownership is acceptable when documented and test-protected.

- Engine seams marked provisional must remain provisional until explicitly
  migrated.
- Renderer coupling to existing result shapes is acceptable while public output
  remains protected.
- `v1.13.4` may own dependency-direction follow-up if the evidence supports it.

## Dependency-Direction Risks

Concrete risks if this area is changed too early:

- moving routing before preservation tests and contract docs are sufficient
- duplicating result shapes while trying to “clean up” ownership quickly
- renderer coupling to provisional observability or snapshot result types
- engine returning observability-owned results in a way that later looks
  unified when it is not
- CLI assembling JSON from snapshot-owned shapes that are not yet engine-owned
- preserving richer CLI query semantics than the current engine diff request
  can represent
- narrowing diff query semantics too early and silently changing behavior
- introducing circular dependencies during a package-direction refactor
- hiding backend-specific behavior behind generic engine wrappers without
  explicit parity proof
- using `v1.13.3` cleanup as a broad architectural refactor rather than a
  release-hardening pass

## Final Phase 8 Decision

The current read-side backend and dependency state is acceptable for
`v1.13.3`.

Public behavior, taxonomy boundaries, and CLI preservation are now documented
and test-protected.

Several ownership seams remain provisional:

- engine-wrapped `stats` with observability-owned results
- direct CLI -> observability `inspect`
- mixed engine/snapshot/CLI/render `snapshot show`
- provisional CLI -> engine -> snapshot `snapshot diff`

Those seams should remain documented and accepted for `v1.13.3` and should be
handed off to later `v1.13.x` work rather than changed in this review phase.
