# Coldkeep v1.13.8 Restore Contract Inventory

**Release:** `v1.13.8 — Restore / Remove Contract Split and Stored-Path Boundary`
**Phase:** Phase 1
**Status:** Complete
**Branch:** `release/v1.13.8`

## Purpose

Create one authoritative inventory of every current restore surface before
changing restore request types, engine methods, CLI routing, destination
handling, or result models.

## Executive conclusion

Coldkeep currently has one active by-ID `Engine.Restore` contract and one
supported stored-path restore implementation that bypasses `Engine.Restore`.
The mixed request/result model represents both, but its active semantics do
not.

## Current restore modes

- By-ID restore:
  - CLI batch orchestration
  - one-item `restoreByIDPhase` execution
  - `Engine.Restore` with `RestoreModeFileIDs`
  - storage restore by logical file ID
- Stored-path restore:
  - CLI validation and orchestration
  - direct `storage.RestoreFileByStoredPathWithStorageContextResultOptions`
  - no active engine stored-path method

## Active engine interface

Active signature:

```go
Restore(ctx context.Context, req RestoreRequest) (RestoreResult, error)
```

Current engine truth from `internal/engine/default_engine.go` and
`internal/engine/default_engine_routing_helpers.go`:

- context cancellation is checked first;
- `validateRestoreRequest` runs second;
- only `RestoreModeFileIDs` is accepted;
- non-file-ID engine restore returns `ErrNotImplemented`;
- accepted requests execute through `restoreFileIDs`;
- execution mode is sequential.

The `Engine` interface comment still describes restore as working "by ID or by
stored path", but implementation only activates by-ID mode today.

## By-ID CLI call graph

Normal by-ID CLI execution:

```text
runRestoreCommand
  -> batch.LoadRawTargets
  -> batch.PrepareTargets
  -> ensureRestoreOutputDir
  -> loadDefaultStorageContextPhase
  -> batch.ExecutePrepared
  -> executeRestoreDryRunItem / executeRestoreItem
  -> restoreByIDPhase
```

CLI-owned by-ID responsibilities:

- parse positional targets;
- identify the final positional as output directory;
- load optional `--input`;
- prepare duplicate and invalid targets through `batch`;
- decide whether any executable target exists;
- create or validate the output directory;
- batch iteration, ordering, and fail-fast;
- human rendering, JSON rendering, and perf spans.

## By-ID engine call graph

Direct engine path:

```text
DefaultEngine.Restore
  -> ctx.Err
  -> validateRestoreRequest
  -> restoreFileIDs
  -> restoreFileID per item
  -> dryRunRestoreFileID or liveRestoreFileID
  -> storage.RestoreFileWithStorageContextResultOptions
```

Engine-owned by-ID responsibilities:

- request validation;
- unsupported-mode classification;
- positive ID validation at item level;
- dry-run versus live execution;
- overwrite propagation;
- per-item result shaping;
- direct-engine fail-fast when multiple IDs are sent in one request.

Important freeze point:

CLI batch execution invokes the seam one item at a time, so CLI ordering and
CLI fail-fast are authoritative for normal CLI restore behavior. Engine batch
fail-fast exists for direct engine callers.

## Stored-path CLI call graph

Current stored-path route:

```text
runRestoreCommand
  -> CLI stored-path validation
  -> parseRestoreDestinationMode
  -> loadDefaultStorageContextPhase
  -> storage.RestoreFileByStoredPathWithStorageContextResultOptions
  -> CLI human/JSON rendering
```

Confirmed current truth:

- `Engine.Restore` is not called;
- `restoreByIDPhase` is not called;
- direct-path proof is `TestRestoreStoredPathPreservesDirectCLIStoragePath`.

## Current validation ordering

Top-level engine validation order:

1. context cancellation
2. `validateRestoreRequest`
3. by-ID execution

Engine validation behavior:

- mode other than `RestoreModeFileIDs` returns `ErrNotImplemented`;
- empty `FileIDs` returns a validation error;
- blank `OutputDir` returns a validation error;
- non-positive file IDs become per-item failures;
- top-level restore can succeed while items fail;
- `FailFast` stops after the first failed item;
- summary skipped count includes remaining unexecuted items;
- `DryRun` uses a separate by-ID planning path.

Stored-path CLI validation order:

1. reject unknown flags
2. reject blank `--stored-path`
3. determine whether stored-path mode is active
4. reject positional arguments
5. reject `--input`
6. reject `--dry-run`
7. reject `--fail-fast`
8. reject `--strict` with `--no-metadata`
9. parse destination mode
10. trim destination
11. reject destination with original mode
12. require destination for prefix mode
13. require destination for override mode
14. load storage context
15. execute storage operation

Supported stored-path flags:

- `--stored-path`
- `--mode original`
- `--mode prefix`
- `--mode override`
- `--destination`
- `--overwrite`
- `--strict`
- `--no-metadata`
- `--output text`
- `--output json`
- `--json`

Unsupported stored-path combinations:

- stored-path with positional arguments
- stored-path with `--input`
- stored-path with `--dry-run`
- stored-path with `--fail-fast`
- `--strict` with `--no-metadata`
- original mode with `--destination`
- prefix mode without `--destination`
- override mode without `--destination`

## Destination-mode semantics

Original mode:

- default when `--mode` is omitted;
- resolves to the stored physical path;
- path is normalized before descriptor lookup;
- write path is validated through `pathsafe.ValidateWritePathUnderTrustedRoot`;
- overwrite behavior is enforced in storage;
- metadata application is storage-owned.

Prefix mode:

- destination is interpreted as a root/prefix;
- stored path is reconstructed beneath that root;
- drive or volume prefixes are stripped before joining;
- traversal is rejected through `pathsafe.SafeJoin`;
- a symlinked prefix root is rejected;
- symlink traversal in joined path components is rejected;
- missing parent directories are created by the restore write path.

Override mode:

- destination is interpreted as the exact output path;
- parent path is validated for unsafe symlink traversal;
- overwrite enforcement remains storage-owned;
- symlinked override targets are rejected.

## Catalog mutation analysis

Restore reads:

- `logical_file`
- `physical_file`
- `file_chunk`
- `chunk`
- `blocks`
- `chunk_block_refs`
- `storage_blocks`
- `container`

Restore also creates or replaces destination filesystem objects and may apply
mode, mtime, uid, and gid metadata when available.

Current important nuance:

- restore does not insert, delete, or rewrite `logical_file` or `physical_file`
  rows;
- restore does temporarily update `chunk.pin_count` during execution to protect
  referenced chunks from GC;
- pinning is committed before content reconstruction and unpinned afterward;
- stale-pin cleanup is covered by restore tests.

Frozen truth:

Restore is read-only with respect to logical-file identity and physical-file
mapping state, but it currently performs temporary chunk pin/unpin bookkeeping
inside the catalog during execution.

## Human output contract

Stored-path success currently prints:

```text
File restored successfully: <output_path>
  FileID: <id>
  SHA256: <restored_hash>
  Hint: <doctor hint>
```

By-ID batch human output is controlled by `printBatchHumanReport`:

- header is `[restore]` or `[restore DRY-RUN]`;
- item ordering follows prepared target order;
- success items show `id`, optional `output_path`, and success message;
- dry-run items show `planned` wording;
- failed items show `error=...`;
- skipped items remain explicit;
- summary prints total plus success/planned/failed/skipped counts.

## JSON output contract

Stored-path success JSON currently emits:

```json
{
  "status": "ok",
  "command": "restore",
  "data": {
    "stored_path": "...",
    "output_path": "...",
    "file_id": 1,
    "restored_hash": "...",
    "mode": "original",
    "perf_spans": []
  }
}
```

By-ID batch JSON is emitted by `emitBatchCommandReport` and freezes:

- top-level `status`: `ok`, `partial_failure`, or `error`
- top-level `command`: `restore`
- top-level `dry_run`
- top-level `summary`
- top-level `results`
- top-level optional `perf_spans`

Per-item fields currently include the stable batch report fields already used by
CLI tests and rendering, including:

- `id`
- `status`
- `message`
- `output_path` when applicable
- `original_name` when applicable
- `invariant_code` when applicable
- `recommended_action` when applicable

Status meaning is frozen:

- `ok`: no failed items
- `partial_failure`: at least one failed item and at least one succeeded or was planned
- `error`: all executable items failed

## Error and unsupported taxonomy

| Layer | Error example | Current classification/projection |
|---|---|---|
| CLI usage | missing file IDs | usage error |
| CLI usage | invalid stored-path flag combination | usage error |
| CLI setup | storage-context failure | wrapped setup error |
| Engine | stored-path restore mode | `ErrNotImplemented`, `IsUnsupported=true` |
| Engine | empty by-ID request | validation error, not unsupported |
| Engine item | invalid file ID | failed item in `RestoreResult.Items` |
| Storage | stored path not found | direct stored-path command error |
| Storage | destination exists with overwrite false | direct or per-item restore failure |
| Storage | corruption or hash mismatch | restore failure |
| Filesystem | permission, temp-file, rename, short-read failure | restore failure |

Important distinction:

- stored-path restore is unsupported only when someone calls the mixed engine
  request directly;
- the actual CLI stored-path command is supported because it bypasses the
  engine restore route.

## Backend and storage-context coupling

`Engine.Restore` currently requires:

- `engine.Config.DB`
- `engine.Config.ContainerDir`

Stored-path restore currently receives:

- `storage.StorageContext`

Current coupling truth:

- catalog lookup depends on the active database connection;
- stored-path lookup uses `physical_file.path`;
- payload reading is backend-neutral after placement resolution;
- destination semantics do not vary by backend;
- storage writer injection is not required for restore;
- SQLite and PostgreSQL must preserve equivalent catalog meaning for restore.

Conclusion:

Catalog lookup differs by backend, but destination and payload-safety semantics
must remain backend-neutral.

## Misleading and provisional contract surfaces

Mixed addressing contract:

- `RestoreRequest` currently combines file IDs, stored path, destination mode,
  destination, metadata flags, CLI batch-input concerns, and provisional
  `Workers`/`Limit` fields.

Mixed result contract:

- `RestoreItemResult` combines `FileID` and `StoredPath`, although the active
  engine route only produces by-ID items.

Interface comment mismatch:

- `internal/engine/engine.go` still describes restore as working "by ID or by
  stored path" while implementation rejects stored-path mode.

Candidate comment debt:

- `RestoreRequest` and `RestoreResult` comments still carry candidate/deferred
  framing alongside active by-ID semantics.

Provisional fields:

- `InputPath` is CLI-owned and not an active engine execution control.
- `Workers` is not active for restore execution today.
- `Limit` is not active for restore execution today.

## Frozen behavior baseline

1. By-ID restore remains a CLI-orchestrated batch of one-item restore seam calls.
2. `Engine.Restore` supports `RestoreModeFileIDs` only.
3. Stored-path `Engine.Restore` calls return `ErrNotImplemented` before any logical-file or mapping mutation.
4. CLI stored-path restore remains supported through a direct storage route.
5. Stored-path restore does not support dry-run, fail-fast, or input files.
6. Stored-path destination mode defaults to original.
7. Prefix and override modes require a destination.
8. Original mode rejects a destination.
9. Strict and no-metadata are mutually exclusive.
10. Restore does not mutate logical-file identity or physical-file mapping state.
11. Destination safety remains storage/path-layer owned.
12. Existing human and JSON output shapes remain frozen.
13. Existing validation ordering remains frozen.
14. Existing errors and unsupported classification remain frozen.
15. SQLite and PostgreSQL catalog meaning remains equivalent.
