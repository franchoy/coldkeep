# Coldkeep v1.13.6 Snapshot Membership Contract Review

**Release:** `v1.13.6 — Catalog Contract Expansion and Backend Parity Review`  
**Phase:** Phase 2  
**Status:** Complete  
**Branch:** `release/v1.13.6`

## Purpose

This document reviews the catalog contract that determines which
logical/physical files belong to a snapshot and how that membership is consumed
by snapshot show, snapshot diff, snapshot restore, snapshot delete/retention,
reachability, and GC.

This phase performs no implementation work and adds no tests.

## Contract under review

The current snapshot membership contract is defined by:

- snapshot identity
  - `snapshot.id`, treated as immutable after insert
- parent/lineage relationship
  - `snapshot.parent_id`, optional lineage metadata
  - lineage affects stats, delete preview, and tree-oriented views, but not the
    raw `snapshot_file` row shape
- membership rows
  - `snapshot_file` rows are insert-only and store `snapshot_id`, `path_id`,
    `logical_file_id`, and optional `size` / `mode` / `mtime` metadata
- logical-file membership
  - content identity is represented by `logical_file_id`
- physical-file/path membership
  - path identity is represented by normalized `snapshot_path.path` through
    `path_id`
  - full snapshot creation reads current `physical_file` state, but persisted
    snapshot membership keeps path identity plus logical content identity rather
    than a `physical_file` primary key
- membership immutability expectations
  - snapshots and `snapshot_file` rows are treated as immutable after creation
- membership ordering expectations
  - active membership queries rely on deterministic ordering such as
    `ORDER BY sp.path, sf.logical_file_id` or on sorted in-memory path maps
- membership consumers
  - show
  - diff
  - restore
  - delete preview
  - retention
  - reachability
  - GC

## Snapshot creation membership

Snapshot creation currently lives below the catalog facade in
`internal/snapshot`.

- Membership selection:
  - full snapshots enumerate current completed `physical_file` +
    `logical_file` state through `snapshotSourceQuery`
  - `snapshotSourceQuery` orders source rows by path then logical file ID
  - selection excludes incomplete or non-completed logical file state where the
    current snapshot tests document that behavior
  - partial snapshots narrow the source set by normalized path filters
- Membership insertion:
  - `InsertSnapshot` writes immutable snapshot metadata
  - `InsertSnapshotFile` validates snapshot ID, normalizes the path, checks
    logical file existence, resolves `snapshot_path`, and inserts a
    `snapshot_file` row
  - batched creation uses resolved path IDs and transaction-scoped inserts
- Logical/physical identity involved:
  - persisted membership stores normalized path identity plus logical content
    identity
  - membership does not store a `physical_file` primary key
- Parent/source relationship:
  - `SnapshotCreateOptions.ParentID` is metadata-only lineage
  - parent lineage does not alter membership contents
- Determinism expectations:
  - source enumeration is ordered
  - path normalization is part of stable membership identity
  - insert-only membership expects the same normalized path to resolve to one
    `snapshot_path` row
- Backend-sensitive areas:
  - PostgreSQL-only row locking through `QueryWithOptionalForUpdate` in the
    snapshot source query
  - insert paths rely on `RETURNING id`
  - FK enforcement differences matter for corrupt or orphan membership rows

## Snapshot show/list/diff consumption

### Metadata vs membership usage

- snapshot list
  - `internal/catalog.ListSnapshots` and engine `SnapshotList` use snapshot
    metadata only
  - membership contents are not part of the list contract
  - tree/list presentation semantics remain outside a catalog-owned membership
    contract
- snapshot show
  - engine `SnapshotShow` loads metadata via catalog `FindSnapshot`
  - membership rows come from direct `snapshot.ListSnapshotFiles`
  - total counts come from separate `snapshot.GetSnapshotStats`
  - this remains a mixed seam: catalog-backed metadata over direct membership
    queries
- snapshot diff
  - summary fast path uses `snapshot.DiffSnapshotsSummarySQL`
  - detailed path uses `snapshot.DiffSnapshots`
  - diff identity is path identity plus `logical_file_id`, not
    size/mode/mtime metadata

### Count semantics

- snapshot show returns:
  - `matched_file_count` from the filtered `ListSnapshotFiles` result length
  - `total_snapshot_file_count` from `GetSnapshotStats`
- snapshot diff returns:
  - summary counts from either SQL-only summary or filtered detailed entries
  - detailed total vs matched counts through the engine wrapper
- Existing read-side guards protect output shape and count-field stability, but
  those guards do not by themselves prove backend-neutral membership semantics

### Filter semantics

- `snapshot.ListSnapshotFiles` loads ordered membership rows, normalizes paths,
  then applies `SnapshotQuery` in memory
- `snapshot.DiffSnapshots` classifies entries first, then applies query filters
  using target-side metadata for added/modified entries and base-side metadata
  for removed entries
- engine narrows CLI-shaped query state into the smaller `engine.SnapshotQuery`
  contract before reaching snapshot helpers

### Ordering semantics

- list/show membership ordering is deterministic through
  `ORDER BY sp.path, sf.logical_file_id`
- detailed diff ordering is deterministic through sorted path union handling
- list metadata ordering is snapshot-metadata ordering, not membership ordering

### Required separation

Phase 2 should keep these concepts separate:

- `public output-shape guard`
- `catalog membership correctness`
- `backend query parity`

## Snapshot restore consumption

Snapshot restore membership still lives below an implemented catalog restore
plan.

- Restore selection starts from `snapshot_file` joined to `snapshot_path`
- Restore resolves normalized snapshot membership paths into restore work items
- Logical identity and path reconstruction remain separated:
  - membership identifies `logical_file_id`
  - restore uses path identity to reconstruct output targets
- Deterministic ordering is expected through ordered membership queries and
  normalized restore selection
- Fail-closed assumptions currently visible:
  - missing snapshot ID is rejected
  - invalid or unnormalizable paths error
  - exact requested paths must be found or the selection fails
  - duplicate normalized paths with conflicting logical IDs fail in diff/load
    helpers rather than being silently merged
- Backend-sensitive areas:
  - membership query ordering
  - placeholder behavior
  - lower-layer restore and chunk pinning interactions remain outside catalog
    and should not be migrated in this phase

## Snapshot delete, retention, reachability, and GC consumption

### Delete

- `DeleteSnapshot` removes snapshot metadata and `snapshot_file` rows only
- snapshot delete does not directly delete logical content
- `LoadDeleteLineagePreview` reads:
  - parent/child lineage
  - total file counts
  - unique/shared file counts derived from `snapshot_file`

### Retention

- `internal/retention/reachability.go` directly treats `snapshot_file` rows as
  retained roots
- snapshot-referenced logical IDs are queried directly from `snapshot_file`
- some retention helpers intentionally treat a missing `snapshot_file` table as
  empty retention state rather than a hard failure

### Reachability

- `internal/catalog.LoadReachabilityRoots` exposes snapshot-protected logical
  IDs from `snapshot_file`
- `internal/graph.SnapshotRoots` and `GCRoots` directly consume snapshot
  membership as logical-file roots, with optional excluded snapshots

### GC

- `internal/gc/plan.go` documents GC roots as current `physical_file` roots
  plus snapshot roots, excluding requested deleted snapshots
- GC safety therefore depends on consistent snapshot membership assumptions even
  though catalog GC-plan metadata remains deferred

### Phase 5 follow-up items

- snapshot-root exclusion semantics for delete simulation
- orphan or dangling `snapshot_file` behavior in retention and GC helpers
- whether all consumers share the same retained-root assumptions
- membership assumptions that are safety-critical for GC refusal logic

## Backend posture

### Backend-neutral surfaces

- normalized path identity via `snapshot_path`
- `$1` placeholders in snapshot package production queries
- `ON CONFLICT DO NOTHING` path resolution
- logical-root reachability queries from `snapshot_file`
- detailed diff classification by path identity + logical identity

### Backend-sensitive surfaces

- `FOR UPDATE` row locking in snapshot source enumeration
- `RETURNING id` insert paths
- timestamp parsing and NULL parent handling
- direct delete/retention/reachability helpers that rely on backend FK
  enforcement or permissiveness below the catalog layer

### SQLite-specific assumptions, if any

- many membership tests run on in-memory SQLite
- some fixtures and tests use SQLite-native forms such as `INSERT OR IGNORE` or
  `?` placeholders in setup code
- those SQLite-specific setup conveniences are distinct from the production
  membership path

### PostgreSQL-specific assumptions, if any

- PostgreSQL locking path through optional `FOR UPDATE`
- host-backed coverage gated by `COLDKEEP_TEST_DB`
- stronger PostgreSQL evidence in focused contract/integration coverage and the
  final release gate than in one unified snapshot-membership parity suite

### Dialect-adapted areas

- snapshot source query behavior around optional `FOR UPDATE`
- some direct test/setup paths diverge by backend even when the production query
  contract is intended to stay portable

### Phase 6 follow-up items

- ordering and collation stability
- NULL/default parent handling
- FK enforcement differences on corrupt/orphan membership rows
- summary-vs-detailed diff parity across backends
- release-gate-only PostgreSQL evidence beyond focused contract tests

## Phase 2 findings

### Stable current contract observations

- snapshot membership is currently represented as normalized path identity plus
  logical content identity
- snapshot metadata/listing and full membership are intentionally split across
  catalog and snapshot packages
- snapshot show and diff remain mixed seams rather than pure catalog-owned
  membership contracts
- delete, retention, reachability, and GC all consume `snapshot_file`
  membership as a logical-file root source

### Backend-sensitive observations for Phase 6

- row-locking differences in snapshot source enumeration
- `RETURNING id` insert-path assumptions
- timestamp parsing and nullable parent lineage handling
- FK enforcement and orphan-row behavior below the catalog layer
- summary/detailed diff parity and ordering/collation behavior across backends

### Coverage evidence for Phase 7

- snapshot create membership selection and insert behavior
- show/list/diff membership semantics
- restore selection semantics derived from snapshot membership
- delete preview and retention behavior
- reachability and GC root consumption
- focused backend parity evidence versus release-gate-only evidence

### Phase 5 follow-up items

- snapshot-root exclusion semantics for delete simulation
- orphan/dangling `snapshot_file` handling in retention and GC helpers
- alignment between catalog reachability roots, graph snapshot roots, and GC
  root assumptions
- snapshot membership assumptions that feed GC refusal safety checks

### Immediate blockers

None found.

## Phase 2 decision

The current snapshot membership contract is broad but reviewable.

No Phase 2 production or test change is required.

`v1.13.6` can proceed to logical/physical mapping review in Phase 3.

Snapshot membership backend parity and test sufficiency remain intentionally
deferred to Phases 6 and 7.
