# Coldkeep v1.13.5 Verify Engine Validation and Invariant Boundary Review

**Release:** `v1.13.5 — Release Record Closure and Engine-Level Invariant Ownership`
**Phase:** Phase 2
**Status:** Complete
**Branch:** `release/v1.13.5`

## Purpose

This document reviews the `Verify` engine-facing path and records where
validation, result ownership, invariant propagation, and public error
classification currently live.

This phase performs no ownership migration and no behavior change.

## Reviewed surfaces

- `Engine.Verify`
- `VerifyRequest`
- `VerifyResult`
- `validateVerifyRequest`
- CLI verify routing
- `verify file` ID validation
- verify domain package failures
- invariant/error propagation
- public CLI error-envelope ownership
- current test protection

## Current verify flow

The active verify path currently flows as:

```text
cmd/coldkeep
  -> parse and validate public CLI args
  -> parse verify level and target/fileID
  -> verifyCommandPhase / engine-backed verify seam
  -> Engine.Verify
  -> verifyLevelFromString
  -> validateVerifyRequest
  -> maintenance.VerifyCommandWithDBAndContainersDir
  -> internal/verify package
  -> result or error
  -> CLI-owned public success output / error envelope
```

At the CLI boundary, `runVerifyCommand` validates command shape, parses level
selection, rejects malformed or out-of-range `fileID` inputs for `verify file`,
and assembles the public success payload.

At the engine boundary, `DefaultEngine.Verify` defaults empty target to
`system`, validates the request again, then delegates to
`maintenance.VerifyCommandWithDBAndContainersDir`.

At the maintenance/domain boundary, `verifySystem` and `verifyFile` dispatch to
the layered verification functions in `internal/verify`. Deeper verification
may return plain verify-category failures or invariant-wrapped failures.

The CLI remains the public error boundary: it classifies exit code, assembles
JSON/text envelopes, projects invariant codes and recommended actions, and
extracts verify-stage metadata from `verify.VerifyFailure`.

## Request and result ownership

- `VerifyRequest` currently has:
  - `Level string`
  - `Target string`
  - `FileID int`
- `VerifyResult` is still intentionally minimal and empty.
- `VerifyResult` remains transitional rather than a rich engine-owned result
  payload.
- request validation is split across:
  - CLI parsing and usage validation in `cmd/coldkeep/main.go`
  - engine request validation in `internal/engine/default_engine.go`
  - maintenance/domain pre-dispatch checks in `internal/maintenance`
- public success output is assembled in `runVerifyCommand`, not in engine or
  verify domain packages.

The current ownership shape is therefore:

- CLI owns public command semantics and public output
- engine owns the request seam and deeper guard for non-CLI callers
- maintenance owns target dispatch and file-existence precheck
- `internal/verify` owns the real verification logic

## CLI validation

CLI-owned validation currently includes:

- command shape validation:
  - `verify` requires a target and enforces the expected `system` or
    `file <fileID>` shapes
- verify level selection:
  - `parseVerifyLevel` handles flag/positional level combinations and usage
    errors
- `verify file` ID parsing:
  - CLI parses `fileID` from text using `strconv.Atoi`
  - CLI rejects malformed text before routing
  - CLI rejects `ErrRange` overflow with a specific platform-range message
  - CLI rejects zero and negative IDs before routing
- public success behavior:
  - CLI assembles both JSON and text verify success payloads
  - CLI collects and renders summary counters after successful verification
- public error behavior:
  - usage/validation errors remain CLI-shaped
  - public error class, exit code, message, and nested `error` object are
    assembled by CLI error printing/classification

### v1.13.4 `verify file` hardening

The final `v1.13.4` hardening in `cmd/coldkeep/main.go` is narrow and correct:

- it is primarily CLI-owned validation
- it closes unsafe string-to-`int` conversion before engine routing
- it rejects:
  - malformed file IDs
  - zero file IDs
  - negative file IDs
  - platform-range overflow values
- it leaves valid file IDs unchanged and still routes them through the existing
  engine-backed verify seam
- it does not change public verify success or error semantics beyond rejecting
  invalid/unsafe input earlier and more explicitly

`VerifyRequest.FileID` remains `int`, and no unsafe active CLI conversion path
remains after the `strconv.Atoi` plus `errors.Is(err, strconv.ErrRange)` guard.

## Engine validation

Engine-owned validation currently includes:

- `verifyLevelFromString`
  - accepts `fast`, `standard`, `full`, `deep`
  - treats empty string as `standard`
  - rejects unknown values
- `DefaultEngine.Verify`
  - defaults empty target to `system`
  - revalidates request before calling maintenance
- `validateVerifyRequest`
  - accepts only `system` or `file`
  - requires positive `fileID` for `file`
  - rejects unknown target values

This engine validation is the correct deeper guard for non-CLI callers. It is
not a full replacement for CLI parsing, because engine callers already supply
typed fields instead of raw command-line strings, but it does ensure that
correctness does not depend solely on CLI parsing.

There are no explicit unsupported verify modes today beyond ordinary validation
errors. Verify does not currently use `ErrNotImplemented` or an unsupported
mode taxonomy the way some other engine surfaces do.

## Domain package validation and invariants

Below engine, verification responsibility is split between `internal/maintenance`
and `internal/verify`.

Maintenance-layer validation currently includes:

- target dispatch in `VerifyCommandWithDBAndContainersDir`
- file existence precheck in `verifyFile`
- verify-level dispatch to the correct domain verification function
- invalid maintenance-level verify level rejection for both system and file
  paths

Domain verification in `internal/verify` currently includes layered checks
such as:

- repository metadata integrity
- chunk reachability and chunk/block reference integrity
- packed block metadata and bounds validation
- block payload verification
- logical chunk/file integrity
- file chunk ordering and logical reconstruction checks
- physical file graph integrity
- snapshot reachability integrity
- system-wide full/deep container and block verification
- corruption detection with verify-stage/category failures

Examples of deeper verify responsibilities visible in current code:

- `VerifyRepository` layers metadata, physical, decoded block, chunk-slice, and
  compatibility checks
- `VerifyFileStandardWithContainersDir` checks:
  - positive file ID
  - logical-file existence
  - `COMPLETED` status
  - non-empty `chunker_version`
  - chunk ordering continuity
  - chunk completeness and mapping integrity
- `VerifySystem*WithContainersDir` runs standard/full/deep repository-wide
  checks with increasing physical validation depth

These checks are domain-owned and remain intentionally below the engine seam.

## Invariant metadata propagation

Verify can surface two broad classes of failures today:

- verify-category failures
  - plain string/category-oriented failures such as
    `metadata_invalid`, `physical_missing`, `physical_hash_mismatch`,
    `compressed_hash_mismatch`, `block_hash_mismatch`,
    `chunk_hash_mismatch`, and `unsupported_block_format`
  - verify-stage detail is carried through `verify.VerifyFailure` and extracted
    by CLI
- invariant-wrapped failures
  - deeper packages such as `internal/verify` can produce
    `internal/invariants` errors for physical graph or snapshot graph
    integrity failures
  - invariant codes and recommended actions are preserved through the normal
    error chain

Current propagation behavior:

- engine does not reinterpret or enrich verify errors
- `VerifyResult` does not carry invariant metadata
- CLI extracts:
  - `invariant_code`
  - `recommended_action`
  - verify-specific `stage`
  - optional `block`
  - optional `container`
  - optional `offset`
  - derived human-readable `reason`
- CLI still exposes only stable public fields and does not leak internal helper
  names as part of the public envelope contract

This means invariant metadata is preserved where deeper layers emit it, but the
public projection remains CLI-owned rather than engine-result-owned.

## Unsupported and deferred seams

The current verify seam has no active unsupported mode branch like stored-path
restore/remove, but it still has transitional/deferred aspects:

- `VerifyResult` is intentionally minimal and empty
- public verify success output is CLI-owned
- public verify error envelopes are CLI-owned
- verify-stage/category taxonomy is exposed through CLI error extraction rather
  than an engine-native result structure
- deeper invariant and verify failure detail is not normalized into a richer
  engine result type

These are transitional but acceptable for `v1.13.5` because the phase is a
review-only release and not a request/result refactor release.

## Findings

### Stable enough for v1.13.5

- CLI rejects malformed, zero, negative, and overflow `verify file` IDs before
  routing.
- engine request validation still provides the correct deeper guard for
  non-CLI callers.
- maintenance clearly owns target dispatch and file-existence precheck.
- `internal/verify` clearly owns the real repository/file/system verification
  logic.
- invariant codes and recommended actions are preserved through CLI error
  rendering when deeper layers emit invariant-wrapped errors.
- valid verify routing and success output remain intact after the `v1.13.4`
  hardening.

### Transitional but acceptable

- `VerifyResult` remains intentionally minimal and empty.
- verify public success payloads are still CLI-owned rather than engine-result
  owned.
- verify error taxonomy is still exposed primarily through error chains and CLI
  extraction, not a richer engine result type.
- verify-stage metadata is public only through CLI error projection.

### Candidate guard gaps

- a narrow future Phase 8 guard could explicitly preserve the combined public
  JSON behavior for invariant metadata plus verify-stage detail fields in the
  same verify error path
- a narrow future Phase 8 guard could explicitly assert the empty-target
  default-to-`system` behavior at engine level if that becomes important to
  preserve as a documented contract

These are documentation-backed candidate guard gaps only, not bug findings.

## Phase 2 decision

The current Verify ownership boundary is acceptable for `v1.13.5` as a
documented transitional state.

CLI validation, engine request validation, and domain verify invariants are
separated clearly enough for the current engine-facing path.

The `v1.13.4` `verify file` `fileID` hardening is narrow and correct. It closes
unsafe/invalid CLI parsing before engine routing, while engine request
validation remains the correct deeper guard for engine callers.

No Phase 2 production or test change is required.

Any additional guard tests should be deferred to Phase 8 and limited to the
gaps documented here.
