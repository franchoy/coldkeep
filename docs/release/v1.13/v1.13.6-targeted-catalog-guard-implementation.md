# Coldkeep v1.13.6 Targeted Catalog/Backend Guard Implementation Decision

**Release:** `v1.13.6 — Catalog Contract Expansion and Backend Parity Review`  
**Phase:** Phase 8  
**Status:** Complete  
**Branch:** `release/v1.13.6`

## Purpose

This document records the Phase 8 decision for targeted catalog/backend guard
implementation.

Phase 7 classified the existing catalog/backend evidence and concluded that no
new Phase 8 tests are justified for v1.13.6.

This phase performs no implementation work and adds no tests.

## Phase 7 decision carried into Phase 8

Existing catalog/backend evidence is sufficient for v1.13.6.

No new Phase 8 tests are justified.

Phase 8 therefore records a no-new-tests decision.

## Candidate guard disposition

| Candidate | Phase 7 disposition | Phase 8 action | Rationale |
| --- | --- | --- | --- |
| snapshot metadata/text-filter parity | deferred as backend-sensitive and not suitable for a narrow Phase 8 guard | no test added | Remaining concern is parity-shaped and matrix-sensitive rather than a stable narrow guard gap. |
| packed/legacy placement aggregate parity | deferred as backend-sensitive and broader than a stable add-on guard | no test added | Remaining concern spans restore, GC, observability, and verify aggregate behavior rather than one narrow contract seam. |
| read-side stats/inspect parity | rejected as duplicate / over-brittle | no test added | Existing cross-consistency, service, inspect, and CLI coverage already exercises the area broadly enough that a new guard would mostly duplicate evidence or freeze incidental details. |

## Why no tests are added

New tests are not added in Phase 8 because the remaining candidate areas are
one or more of the following:

- already covered directly
- adequately covered indirectly
- adequately covered by release-gate matrix evidence
- too backend-sensitive for a narrow `v1.13.6` guard
- better suited for a future parity/matrix release
- likely to duplicate existing evidence
- likely to freeze incidental read-side or aggregate details

## Backend-sensitive areas intentionally deferred

The following areas remain intentionally deferred rather than ignored:

- broader SQLite/PostgreSQL parity posture
- PostgreSQL-only live GC mutation semantics
- packed/legacy aggregate parity questions
- snapshot/read-side text-filter parity concerns
- read-side stats/inspect matrix-shaped parity

These areas remain visible in the release record, but they are not suitable for
a narrow Phase 8 guard in v1.13.6.

## Phase 8 decision

No production code change is required.
No test change is required.
No catalog/backend guard is added in Phase 8.
`v1.13.6` can proceed to Phase 9 final catalog/backend contract decision summary.
