**Release:** `v1.13.6 — Catalog Contract Expansion and Backend Parity Review`

## Purpose

This document inventories current catalog ownership, query surfaces,
backend-sensitive paths, and existing contract-test coverage before `v1.13.6`
reviews individual catalog contracts.

This phase performs no implementation work and adds no tests.

## Query surface inventory

### Catalog lookups

`internal/catalog` currently owns the narrowest explicitly catalog-shaped SQL
surface.

- Reads:
  - `logical_file` identity lookups
  - `physical_file` mappings ordered by path
  - `snapshot` metadata and filtered listing
  - reachability root IDs from `physical_file` and `snapshot_file`
- Writes:
  - no active catalog write surface in the implemented methods
  - deferred methods return `ErrNotImplemented` without mutation
- Backend posture:
  - documented as backend-neutral through `$1`-style positional placeholders
  - `snapshots.go` uses portable filters and ordering
  - `reachability.go` documents identical SQLite/PostgreSQL semantics for the
    root-set queries
- Evidence:
  - direct SQLite service tests
  - dual-backend contract tests
  - neutrality/dependency guard tests

### Snapshot and path-resolution helpers

`internal/snapshot` still owns much of the active snapshot membership and path
resolution behavior.

- Reads:
  - snapshot membership rows
  - snapshot stats and diff/show data
  - `snapshot_path` hydration and lookup
- Writes:
  - snapshot path upsert/resolution
  - snapshot metadata and membership creation in the active domain flows
- Backend posture:
  - path resolution uses `ON CONFLICT DO NOTHING` and `$1` placeholders as a
    portable upsert path
  - snapshot source queries include backend-aware `FOR UPDATE` handling
  - ordering guarantees are explicit in some read paths
- Evidence:
  - `internal/snapshot/path_resolver_test.go`
  - `internal/snapshot/snapshot_test.go`
  - snapshot engine and CLI routing tests

### Repository capability inspection

`internal/repository/capabilities` owns schema/version-driven capability
derivation rather than runtime operation routing.

- Reads:
  - `schema_version`
  - `repository_config`
  - table/column existence for legacy and packed storage layouts
  - observed codec/compression/encryption values from `blocks` and
    `storage_blocks`
- Writes:
  - none
- Backend posture:
  - explicit backend branching through `db.BackendFromDB`
  - PostgreSQL inspection through `information_schema`
  - SQLite inspection through `sqlite_master` and `PRAGMA table_info`
- Evidence:
  - `internal/repository/capabilities/derive_test.go`
  - `internal/repository/capabilities/model_test.go`

### Migration, bootstrap, and schema ownership

`internal/db` owns backend detection, connection/session setup, and schema
bootstrap/migration behavior.

- Reads:
  - backend/driver identity
  - SQLite schema state from `sqlite_master`
  - PostgreSQL schema version expectations
  - connection/session env configuration
- Writes:
  - SQLite session pragmas
  - migration DDL and data-shaping migrations
  - connection/session option setup
- Backend posture:
  - backend detection is explicit
  - SQLite bootstrap and migration logic is the most dialect-specific area in
    this phase
  - PostgreSQL remains mandatory but much of its coverage is narrower and more
    gate-oriented than the SQLite in-memory bootstrap coverage
- Evidence:
  - `internal/db/backend_test.go`
  - `internal/db/migrations_test.go`
  - `internal/db/schema_version_test.go`
  - final release gate requirements

### Reachability, GC, repair, and verification

Catalog-level reachability is currently narrower than the active operational
surface.

- Reads:
  - root-set queries in `internal/catalog`
  - graph traversal and GC planning in `internal/graph` and `internal/gc`
  - repair/refcount and maintenance verification metadata in
    `internal/maintenance`
  - deeper integrity checks in `internal/verify`
- Writes:
  - repair/refcount correction and GC mutation planning remain outside catalog
  - verification remains read-mostly but enforces failure contracts below
    engine/catalog
- Backend posture:
  - root-set queries are neutral
  - FK behavior, transaction semantics, and repair/GC refusal paths remain more
    backend-sensitive
- Evidence:
  - `internal/catalog/backend_contract_test.go`
  - `internal/graph/*_test.go`
  - `internal/gc/plan_test.go`
  - `internal/maintenance/gc*_test.go`
  - `internal/maintenance/repair_refcounts_test.go`
  - `internal/verify/*_test.go`

### Observability and read-side queries

`internal/observability` remains the active read-side service for `stats` and
`inspect`, with graph-backed helpers below it.

- Reads:
  - repository and object-level state for stats/inspect
  - graph and cross-consistency read-side data
- Writes:
  - none in the core read-side paths
- Backend posture:
  - behavior is primarily exercised through SQLite unit tests and broader
    release-gate validation
  - no unified catalog contract currently owns these read-side queries
- Evidence:
  - `internal/observability/*_test.go`
  - CLI and engine read-side taxonomy/boundary tests

### Engine wrapper and delegation boundaries

`internal/engine` remains a transitional wrapper rather than the owner of the
full catalog/backend contract surface.

- Direct catalog-backed reads:
  - `SnapshotList` builds a `catalog.SnapshotFilter` and maps `SnapshotRef`
    into engine `SnapshotMeta`
  - `SnapshotShow` uses `catalog.FindSnapshot` for top-level snapshot metadata
- Delegated non-catalog reads:
  - `Stats` and `Inspect` delegate to `internal/observability`
  - `SnapshotShow`, `SnapshotStats`, and `SnapshotDiff` still call directly
    into `internal/snapshot` for membership/stats/diff data
- Delegated mutation and maintenance paths:
  - `Verify`, `Remove`, `Restore`, and `Store` remain wrappers over
    maintenance/storage/domain layers
- Evidence:
  - `internal/engine/contracts_test.go`
  - snapshot routing tests
  - dependency/boundary tests

## Backend abstraction and dialect handling

### Backend selection point

Backend selection is centered in `internal/db/backend.go` via
`BackendFromDB(*sql.DB)`, with helper functions for `FOR UPDATE`,
`FOR UPDATE SKIP LOCKED`, and `FOR UPDATE NOWAIT` support.

### Schema bootstrap and migration ownership

Schema bootstrap and migration ownership lives in `internal/db`.

- SQLite bootstrap/migration logic inspects `sqlite_master`, `PRAGMA
  table_info`, and pre-schema repository state.
- PostgreSQL schema support is tracked through embedded schema SQL and version
  expectations, with compatibility remaining mandatory in the release gate.

### Placeholder and dialect behavior

- `backend-neutral`
  - catalog contracts use `$1`-style placeholders and explicitly document them
    as portable across PostgreSQL and SQLite
  - catalog reachability queries are documented as identical across both
    backends
  - snapshot path upsert uses `ON CONFLICT DO NOTHING`
- `SQLite-specific but isolated`
  - `PRAGMA foreign_keys`
  - `PRAGMA busy_timeout`
  - `sqlite_master`
  - `PRAGMA table_info`
  - many package tests open in-memory SQLite databases and apply schema/migrations
- `PostgreSQL-specific but isolated`
  - `FOR UPDATE` capability helpers
  - `information_schema` inspection in capability derivation
  - host-backed catalog contract and integration coverage gated by
    `COLDKEEP_TEST_DB=1`
- `dialect-adapted`
  - repository capability derivation branches by backend
  - snapshot source query generation adapts `FOR UPDATE` usage by backend
  - some maintenance/recovery logic branches on backend-specific behavior
- `dual-backend tested`
  - `internal/catalog/backend_contract_test.go`
  - `internal/catalog/backend_contract_backends_test.go`
  - focused backend compatibility tests in adjacent packages
- `release-gate-only`
  - broader PostgreSQL validation outside the focused catalog contract suite
    remains concentrated in `PRE_RELEASE_CHECKLIST.md Profile A`
- `not yet clear`
  - full repo-wide parity for placement, restore-plan, GC-plan, and repair
    contract behavior is not yet owned by catalog and remains distributed

### Areas requiring deeper Phase 6 review

The clearest backend-sensitive follow-up areas are:

- schema bootstrap and migration differences
- capability derivation branches that inspect backend metadata tables
- snapshot source locking/query-shaping differences
- lower-layer GC, repair, and recovery behavior that relies on transactions or
  FK semantics below the catalog facade

## Engine-facing catalog usage

Current engine-facing catalog usage is narrow and explicitly transitional.

- Direct catalog-backed engine methods:
  - `SnapshotList` delegates to `catalog.NewServiceFromSQL(...).ListSnapshots`
  - `SnapshotShow` uses `catalog.FindSnapshot` for snapshot metadata lookup
- Engine methods that still delegate beneath catalog:
  - `Stats` and `Inspect` route to `internal/observability`
  - `SnapshotShow`, `SnapshotStats`, and `SnapshotDiff` still rely on
    `internal/snapshot` for membership, stats, and diff data
  - `Verify` routes to maintenance/verify logic
  - `Remove`, `Restore`, and `Store` remain storage/domain wrappers
- Transitional catalog-shaped results:
  - `SnapshotListResult` and the metadata portion of `SnapshotShowResult`
    already expose catalog-fed state
  - the file-list, stats, and diff portions of snapshot results remain mixed
    engine/catalog/snapshot seams rather than a pure catalog contract
- Domain layers that still own catalog-adjacent invariants below engine:
  - snapshot membership and path resolution
  - restore planning and chunk ordering
  - GC eligibility and repair/refcount refusal behavior
  - verification integrity expectations

## Phase 1 findings

### Stable enough to review in later phases

- `internal/catalog` implemented lookup contracts for logical files, physical
  files, snapshot metadata/listing, and reachability roots are explicit and
  already backed by focused tests.
- `internal/db` and `internal/repository/capabilities` make backend selection
  and dialect branching visible rather than implicit.
- Engine snapshot list/show metadata usage is narrow enough to review honestly
  in later phases without first migrating behavior.

### Backend-sensitive and requiring Phase 6 attention

- schema bootstrap and migration ownership in `internal/db`
- backend-aware capability derivation through `information_schema`,
  `sqlite_master`, and `PRAGMA table_info`
- snapshot source locking/query shaping around `FOR UPDATE`
- lower-layer GC, repair/refcount, and recovery behavior that depends on FK or
  transaction semantics below the catalog facade

### Coverage evidence found but not yet classified

- snapshot membership and path-resolution behavior
- logical/physical mapping outside the narrow catalog lookup surface
- placement and restore-plan behavior in storage/restore tests
- reachability and GC eligibility behavior below the root-set layer
- repair/refcount behavior
- verify expectations
- stats/inspect read-side behavior
- engine request/result equivalence and routing coverage
- full release gate / integration matrix evidence

### Immediate blockers

None found.

## Phase 1 decision

The current catalog/backend contract surface is broad but reviewable.

`v1.13.6` can proceed into targeted contract reviews for snapshot membership,
logical/physical mapping, placement/restore-plan assumptions,
reachability/GC eligibility, and SQLite/PostgreSQL parity.

No Phase 1 production or test change is required.
