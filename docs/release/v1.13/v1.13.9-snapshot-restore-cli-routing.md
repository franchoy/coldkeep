# Coldkeep v1.13.9 Phase 11 — Snapshot Restore CLI Routing

Starting SHA: `8fa16c03f8ad2d86d40657ac911c55425540bfc0`

Phase 11 routes production CLI `snapshot restore` through the active engine
method. The CLI still owns parsing, CWD discovery for original mode, duration,
and output projection.

## Files changed

- `cmd/coldkeep/main.go`
- `cmd/coldkeep/stored_path_engine_adapters.go`
- `cmd/coldkeep/main_test.go`
- `cmd/coldkeep/cli_boundary_preservation_test.go`
- `cmd/coldkeep/snapshot_restore_engine_routing_test.go`

## Old route

Production flow before Phase 11:

- `runSnapshotRestoreCommand`
- CLI parsing and validation
- `parseRestoreDestinationMode`
- `parseSnapshotQuery`
- `loadDefaultStorageContextPhase`
- `restoreSnapshotPhase`
- inline CLI human/JSON projection

## New route

Production flow after Phase 11:

- `runSnapshotRestoreCommand`
- CLI parsing and validation
- restore-specific request mapping
- `loadDefaultStorageContextPhase`
- `newSnapshotRestoreCommandEngine`
- `Engine.SnapshotRestore`
- inline CLI human/JSON projection

`restoreSnapshotPhase` remains available for lower-level compatibility tests and
direct domain callers, but production CLI restore no longer uses it.

## Request mapping

- snapshot ID is still trimmed in the CLI before execution
- positional restore paths still map only to `SnapshotRestoreRequest.Paths`
- restore query flags now map to `SnapshotRestoreRequest.Selection`
- repeated exact `--path` values are preserved as ordered slice entries
- repeated `--prefix` values are preserved as ordered slice entries
- pattern, regex string, min/max size, and modified-after/before remain
  CLI-validated before engine construction
- overwrite maps directly to `SnapshotRestoreRequest.Overwrite`
- metadata maps to explicit engine modes:
  - default -> `best effort`
  - `--strict` -> `strict`
  - `--no-metadata` -> `none`

## Original-mode explicit root

- the CLI now resolves original-mode lexical root through a CLI-local
  `currentWorkingDirectoryPhase` seam
- original mode passes that explicit root in
  `SnapshotRestoreRequest.Destination.Path`
- the engine path does not call `os.Getwd()`
- JSON compatibility is preserved by continuing to omit `output_root` in
  original mode, just as the old CLI route did

## Destination mapping

- original mode -> `Destination.Mode=original`, `Destination.Path=<explicit cwd root>`
- prefix mode -> `Destination.Mode=prefix`, `Destination.Path=<raw CLI destination>`
- override mode -> `Destination.Mode=override`, `Destination.Path=<raw CLI destination>`

Lexical destination identity is preserved. No canonicalized path is projected
into CLI success output.

## Output projection

CLI restore still owns:

- success/action wording
- JSON `type` compatibility
- requested-path count rendering
- `duration_ms`
- text duration and hint lines

Engine restore now owns:

- request validation below the CLI boundary
- selection execution
- destination handling
- overwrite semantics
- metadata semantics
- structured warning facts
- restore result facts

The CLI continues to project only the existing JSON fields:

- `action`
- `snapshot_id`
- `type`
- `requested_paths_count`
- `restored_files`
- optional `output_root`
- `duration_ms`

No new engine-only result fields are exposed in Phase 11.

## Warning projection

Engine restore now returns structured warning facts, but Phase 11 preserves the
existing CLI restore output contract by not adding new warning fields to text
or JSON success output.

## Error compatibility

- pre-initialization CLI usage errors still fail before storage or engine
  construction
- invalid regex, invalid size ranges, invalid time ranges, and contradictory
  metadata flags preserve existing CLI error substrings
- engine/domain restore errors continue to flow through the existing CLI error
  path without added wrapping at the CLI boundary

## Override eligibility preservation

Phase 11 preserves override compatibility by forwarding:

- positional restore paths in `Paths`
- query selectors in `Selection`

This keeps query-only restore distinct from positional exact-path restore and
does not broaden override eligibility.

## Create/delete unchanged proof

- `snapshot create` remains routed through `Engine.SnapshotCreate`
- `snapshot delete` remains routed through `Engine.SnapshotDelete`
- restore-specific engine construction uses a dedicated seam only because
  snapshot restore requires an injected `StoreContext`
- create/delete output contracts were not changed
