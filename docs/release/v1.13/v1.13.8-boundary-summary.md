# Coldkeep v1.13.8 Boundary Summary

**Release:** `v1.13.8 — Restore / Remove Contract Split and Stored-Path Boundary`
**Phase:** Phase 11
**Status:** Complete
**Branch:** `release/v1.13.8`

## Purpose

Record the final routed restore/remove boundary now present in the repository
and close the release documentation against the implemented topology.

## Final topology

- by-ID restore:
  `CLI -> Engine.Restore -> storage restore by logical file ID`
- stored-path restore:
  `CLI -> Engine.RestoreStoredPath -> storage.RestoreFileByStoredPathWithStorageContextResultOptions`
- by-ID remove:
  `CLI -> Engine.Remove -> storage.RemoveFileWithDBResult`
- stored-path remove:
  `CLI -> Engine.RemoveStoredPaths -> storage.RemoveFileByStoredPathWithStorageContextResult`

Stored-path CLI restore/remove no longer bypass the engine.

## Ownership split

- CLI owns:
  - flag and positional parsing
  - command-shape validation
  - batch-input file reading
  - destination-mode text parsing
  - human and JSON rendering
  - performance spans
  - compatibility projection
- Engine owns:
  - typed requests and results
  - request-level validation
  - addressing semantics through method selection
  - stored-path target preparation
  - dry-run/live dispatch
  - batch ordering and fail-fast execution
  - operation result meaning
- Storage owns:
  - catalog lookup and mutation
  - path-safety enforcement
  - overwrite behavior
  - metadata application
  - transactions
  - ref-count transitions
  - snapshot-retention enforcement
  - payload reconstruction
  - temporary chunk pinning
- GC alone owns physical payload reclamation.

## Restore mutation honesty

Restore does not persistently mutate logical identity, physical mappings,
logical ref counts, snapshots, file-chunk ownership, or chunk live-reference
ownership.

Restore may temporarily mutate `chunk.pin_count` while protecting payloads
during reconstruction, and pin state must be restored on success and failure.

## Remove and GC ownership

- `Engine.Remove` deletes logical identity and logical content associations by
  logical file ID.
- `Engine.RemoveStoredPaths` unlinks one or more current `physical_file.path`
  mappings and updates `logical_file.ref_count`.
- Neither remove path directly deletes payload bytes, block files, or container
  files.
- GC alone decides when physical payload becomes reclaimable.

## Snapshot-retention policy

Both live remove forms refuse snapshot-retained logical files:

- `Engine.Remove`
- `Engine.RemoveStoredPaths`

Required invariant code:

- `SNAPSHOT_RETAINED_DELETE_BLOCKED`

## No-bypass guarantee

Production CLI stored-path restore/remove execution now routes only through the
engine boundary. Boundary tests keep these guarantees explicit:

- stored-path restore must not call the by-ID restore seam
- single stored-path remove must not call the by-ID remove seam
- batch stored-path remove must not call the by-ID remove seam
