## 2. Current source map and defect proof

| Pass | Current planning and execution | Current public-result behavior | Confirmed defect |
| --- | --- | --- | --- |
| sealed dry-run | `sweepGCSealedContainers` queries eligible rows in container-ID order and executes each row while the cursor remains open; each unit owns a transaction and rolls it back after liveness and retention checks | the unit mutates the shared affected/filename result; no path resolution or `Stat` occurs | `Workers` is ignored and reclaimed physical bytes cannot be known |
| sealed live | each unit locks and revalidates container/chunk rows, checks live physical units and retention, sweeps unreachable metadata, deletes exactly one container row, commits, then resolves the safe path and removes the file | successful units mutate the shared affected/filename result; `Remove` failure is logged and discarded | serial execution, false success on filesystem removal failure, and no physical-byte credit |
| active live | after the sealed pass, `queryFullyDeadActiveContainers` materializes ID-ordered candidates that have blocks but no live or pinned legacy/packed chunks; `sweepDeadActiveContainer` rechecks deadness, sweeps metadata, deletes exactly one row, commits, then removes the file | successful active removals are absent from affected count, filenames, and bytes; there is no active dry-run pass | a real physical removal is invisible and a removal failure is discarded |

The invocation retains one dedicated PostgreSQL connection for the advisory
lock. Preflight integrity, reachability, reachable-chunk collection, live-unit
map construction, and candidate planning are serial. Per-container work already
owns an independent `sql.Tx`; there is no shared transaction. The existing
Phase 3 invocation-local filesystem and dispatch-observer seams are sufficient
for deterministic Phase 11 proof.

At the Engine boundary, negative `Workers` is already rejected but all other
values are ignored, maintenance is called through the serial compatibility
entry, and `BytesReclaimed` is hard-coded to zero. Inside maintenance, a sealed
or active pass error currently returns `GCResult{}`. The named-result deferred
unlock joins an unlock error, but the zeroing control flow still erases prior
work. These behaviors reproduce both findings directly from current source.

## 3. Source-backed design conclusions

### `ACTIVE_CONTAINER_ACCOUNTING_CONTRACT: VERIFIED`

The public `GarbageCollectResult.AffectedContainers` contract counts containers
deleted, or that would be deleted, without a sealed-only qualification. The GC
planning contract and its regressions include fully-dead active containers in
real physical reclaim. Current README and CLI simulation wording likewise
describe real GC, including fully-dead active containers. No current test or
document requires successful active deletion to remain invisible.

Therefore every successful live fully-dead-active physical removal belongs in
`AffectedContainers`, `ContainerFilenames`, and `BytesReclaimed`. The legacy GC
dry-run remains sealed-only; Phase 11 does not add active discovery or active
credit to that path.

### `TRANSACTION_CONCURRENCY_CONTRACT: VERIFIED`

`database/sql.DB` is concurrency-safe and each `sql.Tx` is bound to one pool
connection. The invocation's advisory lock continues to own its dedicated
connection while each started unit obtains its own transaction. Candidate rows
are materialized and their cursor is closed before dispatch; preflight maps are
immutable; workers return private unit results. PostgreSQL row locks, foreign
keys, exact-row checks, and valid-schema physical-unit ownership fail closed
instead of creating a shared-transaction or shared-result hazard.

Production pool sizing does not change. A pool with spare capacity can execute
up to the requested worker maximum; a smaller pool can naturally serialize.
The deterministic PostgreSQL overlap fixture uses `SetMaxOpenConns(3)`: one
advisory-lock connection plus two worker transactions. A separate smaller-pool
case proves natural serialization without rejecting `Workers=2`.

### `PARTIAL_RESULT_REPRESENTATION: VERIFIED`

Phase 11 deliberately replaces both maintenance zero-result error exits after
meaningful execution. It aggregates every terminal started-unit outcome and
returns the accumulated `GCResult` with the non-nil error. Preflight failure
before meaningful unit execution retains a zero result.

Engine maps the maintenance result before translating the error, then returns
the mapped non-zero result with the translated error. Advisory-unlock failure
is joined after unit and cancellation errors and never erases completed work.
The existing maintenance and Engine result-plus-error signatures represent this
contract without a public shape change.

## 4. Design-consistency audit

The frozen designs preserve these ordering and ownership constraints:

1. Serial preflight remains under one invocation advisory lock.
2. Sealed candidates are materialized, ordered by ID then filename, and their
   query is closed before execution.
3. Every started sealed unit reaches a terminal boundary before active
   discovery begins.
4. Active candidates are then materialized and ordered by the same key.
5. A bounded coordinator owns dispatch; workers own transactions and private
   outcomes, never shared result fields.
6. Any non-error terminal result—`affected`, `retained`, or `skipped`—permits
   the next dispatch. A retained or skipped unit with nil error does not stop
   scheduling.
7. A unit error, caller cancellation/deadline, or another frozen stop condition
   prevents new dispatch. Already-started units reach their safe terminal
   boundary and retain their truthful outcomes.
8. Aggregation is in global plan order: sealed order followed by active order.
   Completion timing cannot change result or error order.
9. The final eligibility boundary owns exactly one safe-path `Stat` before a
   destructive metadata commit. A live removal is credited only after `Remove`
   succeeds.
10. Overflow is the single explicit representational exception: all successful
    physical effects stay visible, while bytes remain the last exact
    non-overflowing plan-order prefix and a deterministic accounting error is
    returned at the first overflowing plan index.

There is no conflict with Phase 2. Phase 10 makes the scheduler, partial-result,
active-accounting, filesystem-failure, and overflow mechanics explicit while
preserving the previously frozen public compatibility boundary.

## 5. Phase 11 source and test contract

Production ownership is restricted to:

- `internal/maintenance/gc.go`, for worker-aware scheduling, per-unit private
  results, physical-byte capture, accumulated partial results, and surfaced
  filesystem/accounting errors;
- `internal/engine/default_engine_routing_helpers.go`, for worker forwarding,
  result projection before error translation, and maintenance error mapping.

`internal/engine/candidates.go` is a public-contract inspection point only;
`GarbageCollectResult` does not change shape. Focused tests may update the
existing Engine and maintenance GC contract suites, including
`internal/engine/gc_engine_test.go`,
`internal/engine/mutation_backend_contract_test.go`,
`internal/maintenance/gc*_test.go`, and
`internal/maintenance/mutation_cardinality_test.go` where signature or
preservation coverage requires it. Phase 3 filesystem and observer seams are
reused; no broad new testing infrastructure is authorized.

Primary regressions are:

- `TestGarbageCollectWorkersBoundConcurrencyAndPreserveOrder`;
- `TestGarbageCollectBytesReclaimedCreditsSuccessfulPhysicalRemovalOnly`.

The complete Phase 11 matrix must cover negative/zero/one/two/larger worker
values, PostgreSQL overlap and small-pool serialization, SQLite ceilings,
deterministic ordering, non-error continued dispatch, stop-new-dispatch,
already-started partials, multiple errors, unlock failure, race safety,
dry/live bytes, legacy/packed/mixed layouts, active accounting, filesystem
faults, negative sizes, and overflow.
