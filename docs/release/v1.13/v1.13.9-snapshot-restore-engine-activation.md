# Coldkeep v1.13.9 Phase 10 — Snapshot Restore Engine Activation

Starting SHA: `a88bc46fcb34aea18c4ec80c932d4976444c6be9`

Phase 10 activates `Engine.SnapshotRestore` for direct engine callers. The
production CLI remains on its existing direct snapshot restore route until
Phase 11.

## Scope

- activated `SnapshotRestore(context.Context, SnapshotRestoreRequest) (SnapshotRestoreResult, error)` on the active `Engine` interface;
- implemented `DefaultEngine.SnapshotRestore` as a request-validation and
  result-mapping adapter over `snapshot.RestoreSnapshot`;
- kept create and delete active and unchanged;
- preserved the production CLI `snapshot restore` direct route through
  `restoreSnapshotPhase`.

## Request preparation

- trims `SnapshotID` and rejects empty IDs;
- copies positional `Paths` without narrowing order or duplicates;
- preserves restore-specific selection ownership instead of reusing the
  narrower read-side engine query shape;
- validates explicit destination mode and explicit destination path/root;
- validates metadata mode;
- copies caller-owned size/time bounds so downstream code does not retain
  caller pointers.

## Restore adapter

- translates `SnapshotRestoreSelection` to `snapshot.RestoreSnapshotOptions.Query`;
- translates explicit destination mode to snapshot restore options;
- passes an explicit original-mode lexical root from the engine request;
- never calls `os.Getwd()` in the engine path;
- maps snapshot-domain restore warnings into the frozen structured engine
  warning contract.

## Lexical and trusted path behavior

- keeps lexical destination strings separate from trusted-root validation;
- preserves lexical output paths for explicit original, prefix, and override
  destinations;
- keeps trusted-root and symlink safety in the snapshot/path-safe layer;
- does not expose canonical or trusted roots in the engine result.

## Metadata and partial failure

- best-effort metadata remains success-oriented and now returns structured
  warning facts;
- strict metadata failure still returns an error;
- no-metadata mode still skips metadata application;
- restore remains non-atomic across multiple files;
- earlier files and created directories may remain after a later restore
  failure;
- no rollback, dry-run, parallel restore, GC, or repair work was added.

## CLI boundary

- production `runSnapshotRestoreCommand` still validates, parses, loads the
  storage context, calls `restoreSnapshotPhase`, and renders the existing human
  and JSON output;
- Phase 10 does not route production CLI restore through the engine;
- Phase 11 remains responsible for CLI routing.
