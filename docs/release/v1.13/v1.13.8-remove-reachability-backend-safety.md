## Stored-path unlink invariants

Expanded Phase 10 coverage proved:

- one successful unlink removes exactly one `physical_file` row;
- `logical_file.ref_count` decrements exactly once per successful mapping removal;
- one-of-many unlink preserves logical identity, file-chunk membership, chunk
  `live_ref_count`, chunk `pin_count`, and payload files;
- final-mapping unlink produces the stable zero-reference state:
  logical file retained, `ref_count=0`, zero `physical_file` rows;
- repeated unlink reports current already-removed / never-stored meaning
  without a second decrement;
- mixed batches preserve ordering, duplicate/blank behavior, fail-fast
  boundaries, and exact summary counts;
- dry-run remains read-only and still preserves its known live-parity limits.

## By-ID deletion invariants

Expanded Phase 10 coverage proved:

- snapshot-retained by-ID remove still refuses before mutation;
- by-ID remove deletes the target logical-file identity, all current mappings,
  and all target `file_chunk` rows;
- chunk `live_ref_count` decrements exactly once per removed logical
  association;
- shared chunks remain present when another logical file still owns them;
- surviving logical files remain verifiable after peer deletion;
- by-ID remove does not directly delete payload container files before GC.

## Snapshot-retention policy

Both live remove paths remain refusal-before-mutation operations for
snapshot-retained content:

- `Engine.Remove`
- `Engine.RemoveStoredPaths`

Required invariant code remains:

- `SNAPSHOT_RETAINED_DELETE_BLOCKED`

No physical mapping, ref-count, logical-file, or file-chunk mutation occurs
before refusal.

## Dry-run and fail-fast

Preserved behavior:

- stored-path dry-run still performs lookup-only planning and does not prove
  live success;
- stored-path fail-fast still stops only after an executable target fails;
- blank and duplicate prepared items still do not trigger fail-fast;
- by-ID dry-run semantics remain unchanged.

## Reachability

Phase 10 root coverage proved:

- one-of-many stored-path unlink keeps the logical file in current roots;
- final stored-path unlink removes the logical file from current roots but does
  not delete the logical/file-chunk graph;
- valid snapshot-retained zero-current-mapping state remains rooted through
  snapshot roots and reachable through GC roots;
- valid zero-reference non-snapshot state is neither a current root nor a
  snapshot root.

## GC ownership

Phase 10 GC coverage proved:

- one-of-many stored-path unlink does not make payload reclaimable;
- final stored-path unlink alone does not transfer payload ownership away from
  GC while live references remain positive;
- remove changes catalog reachability only;
- remove never directly deletes payload bytes or container files;
- GC remains the only physical reclamation owner.

## Verification

Phase 10 verification coverage proved:

- valid zero-reference logical files are accepted;
- positive-refcount/no-mapping corruption remains detectable;
- table-driven logical `ref_count` / physical mapping mismatches remain
  detectable;
- Phase 0C’s preserved corruption states remain visible to verify rather than
  being auto-healed.

## Migration and reopen
