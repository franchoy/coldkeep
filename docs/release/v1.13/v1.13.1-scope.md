# v1.13.1 Scope

## Release Name

`v1.13.1 - Explicit Deferred-Contract Boundaries`

## Release Objective

v1.13.1 exists to make deferred, partial, candidate-only, and misleading engine/catalog
boundaries explicit and safe before broader contract cleanup continues in later `v1.13.x` work.
The release should reduce overstatement of active support without pretending that engine or catalog
ownership is complete.

## Why v1.13.1 Exists After v1.13.0

v1.13.0 completed the baseline inventories and documented the main risks. Those inventories showed
that several engine and catalog surfaces currently look more complete than they really are:

- deferred operations already expose request/result shapes
- partial routes can look like full workflow ownership
- candidate-only operations can be mistaken for active runtime support
- deferred catalog methods can be mistaken for complete metadata boundaries

v1.13.1 exists to harden those boundaries narrowly and explicitly before broader contract cleanup,
error taxonomy work, or later routing decisions happen.

## Included Scope

- release-scope and validation documents for `v1.13.1`
- explicit unsupported-boundary hardening for deferred engine paths
- explicit deferred-boundary hardening for deferred catalog methods
- candidate-only operation guardrails
- partial-routing boundary clarification where current seams could mislead future callers
- request/result support-surface clarification where current contract shape overstates active
  support
- CLI-preservation testing to ensure narrow boundary hardening does not change existing command
  behavior
- final release validation and `v1.13.2` handoff notes

## Excluded Scope

- broad engine routing
- snapshot create, snapshot delete, or snapshot restore implementation in engine
- repair or recovery implementation in engine
- implementation of deferred catalog graph, placement, restore-plan, or GC-plan methods
- Go behavior changes outside narrowly scoped later-phase boundary hardening
- schema or migration changes
- storage or repository format changes
- default backend behavior changes
- CLI behavior, JSON output, or exit-code changes
- PostgreSQL compatibility removal
- daemon, API, UI, or v2.0 implementation work
- broad refactors
- style-only cleanup presented as stabilization work

## Compatibility Expectations

- `v1.13.1` must preserve repository, storage, schema, and migration compatibility.
- `v1.13.1` must preserve current SQLite and PostgreSQL compatibility expectations.
- `v1.13.1` must not narrow support to SQLite-only behavior or remove PostgreSQL compatibility.

## Behavior-Change Expectations

- Phase 0 is docs/scope only.
- Later phases may introduce narrow runtime boundary-hardening changes only when explicitly scoped
  to make unsupported or deferred behavior fail more honestly and safely.
- `v1.13.1` must not change CLI behavior, JSON output, exit codes, or current successful workflow
  semantics while hardening deferred boundaries.

## Backend Expectations

- Default backend behavior must remain unchanged throughout `v1.13.1`.
- Boundary clarification must preserve cross-backend expectations for currently supported paths.
- Deferred or unsupported catalog/engine behavior must not be mislabeled as backend-complete merely
  because neutral types or interfaces exist.

## v2.0 Handoff Relevance

`v1.13.1` matters because future daemon/API callers need honest boundaries before additional engine
or catalog contract cleanup can be trusted. This release is a correctness and expectation-setting
handoff, not a completeness release. It should leave later `v1.13.x` and `v2.0` work with clearer
unsupported surfaces, safer partial routes, and fewer misleading contract claims.

## Explicit Warning

`v1.13.1` does not claim engine completeness.

`v1.13.1` does not claim catalog completeness.

Active methods, exported request/result types, exported interfaces, or backend-neutral shapes must
not be read as proof that the full corresponding workflow or metadata responsibility is complete.
