# v1.13.x Release Train Proposal

## Purpose and Release-Train Rules

This document records the proposed `v1.13.x` release train derived from the completed `v1.13.0`
inventories. It is documentation/inventory only. It does not start implementation work, change Go
code, change tests, alter schema or migrations, change CLI behavior, JSON output, exit codes,
storage format, repository format, default backend behavior, engine routing, catalog
implementation, CI behavior, or scripts.

Release-train rules:

- The proposal is derived from completed `v1.13.0` inventories, not aspirational implementation
  work.
- Releases must stay small, correctness-first, and phase-scoped.
- Request/result contracts must not be frozen before deferred boundaries, error taxonomy, and
  validation ownership are clarified.
- Daemon/API/UI/v2 implementation remains out of scope for `v1.13.x`.
- All phases remain on one release branch. Remote validation uses
  release-branch workflows. A single pull request is opened only after the
  complete release phase list and pre-release gate are green.

Sequencing rules:

- Do not freeze request/result contracts before explicit deferred boundaries are documented.
- Do not route more operations through engine before error taxonomy and validation ownership are
  clear.
- Do not move catalog ownership before dependency direction and backend parity expectations are
  clear.
- Do not switch default SQLite behavior in `v1.13` unless a later release proves portability and
  parity gates.
- Do not remove PostgreSQL compatibility.
- Do not treat CLI thin-wrapper proof as complete while repair/recovery/snapshot mutation paths
  remain CLI-owned.
- Keep daemon/API/UI/v2 implementation out of `v1.13.x`.

## v2.0 Handoff Requirements

- deferred engine operations are explicit and safe
- engine error taxonomy exists
- engine request/result contracts are no longer accidentally CLI-shaped
- critical invariants are engine/domain/catalog protected, not CLI-only
- dependency direction is CI-enforced for key boundaries
- catalog contracts are honest about implemented vs deferred ownership
- SQLite-first direction has a documented portability baseline
- PostgreSQL compatibility gates remain active
- remaining CLI direct coupling is classified as acceptable, emergency-only, or deferred

## Bottom Line

The inventories justify preserving historical planning evidence while the
current authoritative train remains released v1.13.9, active v1.13.10, then
