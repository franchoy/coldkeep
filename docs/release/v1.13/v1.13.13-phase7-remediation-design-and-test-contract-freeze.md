## 5. Catalog typed-error current path

`FindLogicalFile`, `FindPhysicalFilesForLogicalFile`, `FindSnapshot`,
`ListSnapshots`, and `LoadReachabilityRoots` currently return raw
`fmt.Errorf(... %w ...)` database errors. `FindLogicalFile` and `FindSnapshot`
correctly reserve `(nil, nil)` for `sql.ErrNoRows`; the collection methods
correctly use empty results for absence. Other Catalog methods already use
`catalog.Error`, `ErrorCancelled`, and `ErrorOperationFailed` without changing
their signatures.

## 6. Catalog typed-error design

Add one private helper in `internal/catalog/errors.go`:

```text
translateServiceError(operation, message string, err error) error
```

Its fixed decision table is:

1. `nil` stays `nil`.
2. An existing `*catalog.Error` is returned unchanged.
3. A cause matching `context.Canceled` or `context.DeadlineExceeded` becomes
   `ErrorCancelled`, with the original cause preserved.
4. Every other query, scan, row-iteration, or close-reported failure becomes
   `ErrorOperationFailed`, with operation text and the original cause.

Invoke it exactly once at each of the five public Service boundaries, using a
named error return/deferred translation where a method has several helpers.
Private query/scan helpers continue returning contextual raw errors. Do not
map general `sql.ErrNoRows`: the two lookup methods intercept it first and
preserve `(nil, nil)`. No Catalog signature, DTO, or Engine translation changes.

## 7. Catalog error test contract

Extend the existing dual-backend Catalog contract suite for success, absence,
empty collections, cancellation, and deadlines. Add a Catalog-local test-only
`database/sql/driver` fault fixture for deterministic query, `QueryRow.Scan`,
row scan, and row-iteration failures. Every affected method must assert:

- stable `ErrorCancelled` or `ErrorOperationFailed` classification;
- `errors.Is` for cancellation, deadline, and injected sentinel causes;
- no backend-native message-string assertion;
- no double wrapping of an existing typed error.

SQLite and configured PostgreSQL execute the ordinary and context paths. The
test driver executes failure shapes that neither backend can portably induce.
Race execution is not required.

## 8. Restore current path

Every production planner already calculates an exact output path. The common
storage primitive then reinterprets an existing directory or trailing
separator as directory intent, performs path-string symlink checks, creates
parents and a temporary file by pathname, checks destination absence, and
uses ordinary rename. Stored-path and snapshot metadata are later applied by
pathname. This creates the two frozen restore blockers.

## 9. Restore destination semantic design

The request boundary may accept a directory/root, but the storage boundary is
exact-only:

| Route | Caller meaning | Exact path before storage |
| --- | --- | --- |
| `Engine.Restore`, single/batch, dry/live | destination root | `root/originalName` |
| `Engine.RestoreStoredPath`, original | stored physical path | resolved stored path |
| `Engine.RestoreStoredPath`, prefix | destination root | `root/stored/path` |
| `Engine.RestoreStoredPath`, override | exact file | requested exact path |
| `Engine.SnapshotRestore`, original/prefix | destination root | one planned exact path per selection |
| `Engine.SnapshotRestore`, override | exact file | requested exact path |

Remove directory detection, basename appending, trailing-separator directory
creation, and lower-layer destination reinterpretation from
`restoreFileWithDBAndDir`. Existing direct storage wrappers also define their
`outputPath` argument as exact. No destination-kind enum or interface change
is needed. Snapshot plan-wide collision checks remain preliminary; final
publication is authoritative per file.

## 10. Atomic no-replace platform design

All implementations create the temporary file in the retained final parent.

- **Linux:** use `unix.Renameat2(parentFD, tempName, parentFD, finalName,
  unix.RENAME_NOREPLACE)`. On `ENOSYS`, `EINVAL`, or a documented unsupported
  result, use `unix.Linkat` with no replacement flags, then unlink the temporary
  name relative to the same parent. If link publication is unsupported, fail
  closed. Overwrite uses handle-relative `unix.Renameat`.
- **macOS:** use `unix.RenameatxNp(parentFD, tempName, parentFD, finalName,
  unix.RENAME_EXCL)`, then the same `Linkat` fallback, otherwise fail closed.
  Overwrite uses handle-relative `unix.Renameat`.
- **Windows:** call `windows.NtSetInformationFile` with
  `windows.FileRenameInformation` on the retained temporary-object handle.
  `ReplaceIfExists=0` is no-overwrite; the exported replacement flag is used
  only for overwrite. Unsupported semantics fail closed.

There is no `Stat`/`Lstat` plus ordinary rename fallback. Link publication is
successful once the final link exists; a later temporary-name unlink failure
is returned truthfully while the published destination remains visible.

The pinned `golang.org/x/sys v0.38.0` source contains Linux `Renameat2`,
`RENAME_NOREPLACE`, `Linkat`, Darwin `RenameatxNp`, `RENAME_EXCL`, and Darwin
amd64/arm64 generated bindings. No dependency or private Darwin syscall is
needed.

## 11. Stable-parent confinement platform design

Create `internal/fsx/secureinstall` with a common internal request, pending
installation, publication result, metadata warning, and injectable syscall
seam. Its lifecycle is:

```text
Begin(exact destination, trusted root, overwrite, metadata)
→ Writer
→ SyncAndCloseWriter
→ Publish
→ post-publication object metadata
→ parent sync where supported
→ Close
```

The trusted-root path is lexically checked first. An existing trusted root is
opened once with final-component no-follow/reparse refusal; allowed aliases
above that boundary are not newly prohibited. For a missing root, the nearest
existing ancestor is resolved/opened once and remaining root/parent components
are created and reopened relative to retained handles. Every component below
the retained boundary is opened/created without following symlinks or reparse
points.

Unix retains root/final-parent descriptors and a duplicate descriptor for the
exact temporary inode. Windows retains root/final-parent handles and the exact
temporary object handle. Temporary creation, publication, metadata, and cleanup
are relative to those objects.

This guarantees that replacing the validated pathname with a symlink cannot
redirect mutation through the replacement. Pathname revalidation is a
fail-closed consistency check, not the security primitive. An open Unix
directory descriptor does not prevent that directory object from being
renamed; arbitrary hostile same-user relocation of the already-open directory
is outside the frozen v1 threat model. If later implementation evidence proves
that `P3-COR-002` requires that stronger guarantee, Phase 8 must stop with
`PHASE7_DESIGN_BLOCKER`.

For Windows, the exact pinned package supplies `NtCreateFile`,
`NtSetInformationFile`, `OBJECT_ATTRIBUTES`, `IO_STATUS_BLOCK`,
`NewNTUnicodeString`, `OBJ_DONT_REPARSE`, `FILE_OPEN_REPARSE_POINT`, create/
open/share/access constants, `DELETE`, and `FileRenameInformation`. Define the
narrow Windows-only variable-length rename buffer with fields
`uint32 ReplaceIfExists`, `windows.Handle RootDirectory`,
`uint32 FileNameLength`, and `[1]uint16 FileName`, matching the pinned module's
own native-file test. Create the object with `DELETE` and metadata rights,
retain that handle, duplicate it for the `os.File` writer, and never reopen the
temporary name. Abort uses handle-relative/unlink-at cleanup; Windows uses the
retained object with `FileDispositionInformation`.

## 12. Restore overwrite/durability behavior

Reconstruction, recipe order, chunk/file hashes, pins, buffered flush, file
sync, close-failure truthfulness, and temp-in-final-parent behavior remain.
No-overwrite never removes a destination. Overwrite publishes the completed
temporary object atomically and never removes the old destination first.

Metadata moves into a neutral internal `storage.RestoreMetadata` specification
carried by `RestoreOptions`; no Engine request changes. The installer retains
the published object and applies mode, owner, and timestamps through that
object. Unix uses descriptor operations; Windows uses the retained handle,
including `SetFileTime`. `RestoreFileResult` carries internal metadata warnings
so snapshot projection can preserve its existing warnings.

Strict incomplete stored metadata still fails before reconstruction, as it
does now. An actual strict metadata-application failure occurs after
publication and returns an error while correct bytes remain visible. Best-
effort failures preserve warnings/logging. Metadata failure never rolls back
the published file. Unix syncs the retained parent after publication; Windows
retains the existing explicit no-directory-sync bound.

## 13. Restore FS abstraction design

The existing broad `fsx.FS`/faultfs abstraction remains for its current tests;
it cannot express stable directory/object identity. Secure installation is a
new narrow `internal/fsx/secureinstall` package, not a broad `fsx` rewrite.

The common request contains exact destination, trusted root, overwrite mode,
metadata values, and metadata policy. A pending installation exposes only a
writer, `SyncAndCloseWriter`, `Publish`, and `Abort`; OS handles do not escape
the package. A package-private operation table supplies deterministic hooks for
before-create, before-publish, link fallback, metadata, sync, and cleanup
faults. Storage tests may inject a secure-installer factory through an
unexported `RestoreOptions` seam.

Snapshot planning stops calling `os.MkdirAll` and supplies metadata to storage.
Stored-path restore converts its descriptor into the same metadata
specification. This keeps all physical mutation inside one installer.

## 14. Restore regression contract

`P3-COR-001` has independent deterministic contracts for exact existing
directories, final-window occupation, no-replace, overwrite, dry/live parity,
all selectors, close/sync/publication faults, and destination preservation.

`P3-COR-002` independently swaps a validated parent for a symlink before
component creation and before publication. Tests assert fail-closed behavior,
no outside create/replace/metadata, retained-object metadata, and confined
cleanup. A separate post-publication pathname replacement test proves metadata
targets the retained object. Hooks/barriers replace sleeps. Race execution and
native Linux/macOS/Windows runtime proof are mandatory.

## 15. Deep verify current path

`verifyFileChunkHashes` currently inner-joins `file_chunk` to legacy `blocks`.
Packed-only recipe entries disappear; mixed recipes verify only their legacy
subset. The production Catalog already supplies the strict ordered
packed-or-legacy placement union and treats packed placement as authoritative
when a migration companion exists.

## 16. Deep verify placement design

Replace the legacy-only SQL with
`catalog.NewServiceFromSQL(db).LoadChunkPlacements(ctx, fileID)`. Process every
returned entry in order and require completed chunk state.

- Legacy: reuse current safe container read, transformer decode, size check,
  and chunk SHA-256 validation using `LegacyChunkPlacement` metadata.
- Packed: convert `PackedChunkPlacement` to `verify.BlockStorageMetadata`, call
  `VerifyStoredBlock` with `FilesystemContainerReader`, cache only successful
  verified blocks by block ID, require an exact decoded table entry matching
  chunk ID/offset/size, slice the decoded payload, then verify chunk size and
  SHA-256.

Catalog errors, missing/incomplete/conflicting placement, invalid status,
invalid segment/table correspondence, read/decode errors, and hashes all fail
closed. Do not add a second placement query or import storage into verify.

## 17. Deep verify result/count behavior

Each authoritative recipe entry is attempted and counted once. The internal
completion log records attempted and failed placement counts; the bounded
error list may truncate displayed details but not the failure total. Empty
completed files legitimately verify zero placements. A packed-only non-empty
file cannot report success without visiting all entries.

The public `VerifyResult` schema remains unchanged. Its existing
`BlocksChecked` field continues to mean distinct authoritative physical blocks,
not chunks; legacy blocks and distinct packed blocks remain counted once.

## 18. Deep verify regression contract

Freeze healthy and corrupted legacy-only, packed-only, and mixed fixtures for
SQLite and PostgreSQL. Include missing legacy payload, missing packed block,
missing/conflicting/incomplete placement, companion precedence, malformed
packed range/table correspondence, corrupt packed half of a mixed file,
selected file ID, truthful internal totals, and unchanged public block
summary. Fault/corruption injection is required; race execution is not.

## 19. Snapshot label current path

Both `listSnapshotsWithoutLimit` and `listSnapshotsWithLimit` use
`label LIKE $2`. SQLite's default and PostgreSQL's default produce different
opposite-case results. Engine and CLI route through this Catalog method and do
not add another label filter.

## 20. Snapshot label semantic design

Change the identical predicate in both SQL statements to:

```sql
($2 = '' OR LOWER(label) LIKE LOWER($2))
```

Keep `labelPattern` unchanged, including existing `%` and `_` treatment.
Ordering remains `created_at DESC, id DESC`; limit behavior is unchanged. The
guarantee is narrow ASCII case-insensitive matching. Non-ASCII locale/collation
behavior is outside the claim; no normalization, escaping, collation, schema,
or index work is added.

## 21. Catalog/label co-design

Both Catalog workstreams touch `snapshots.go`. Implement typed translation
first, then change both predicates in the same method boundary. The label
change does not create a query abstraction. Snapshot query errors pass through
the single translator exactly once.

## 22. Snapshot label regression contract

Seed `Alpha`, `alpha-two`, `BETA`, and `unrelated` with deterministic timestamps
and IDs. Opposite-case filters must return identical ordered IDs on SQLite and
PostgreSQL for unlimited and limited queries. Extend the Engine selector
backend contract and CLI JSON/human routing fixtures to prove the same filter
and order reach presentation unchanged. Race and fault injection are not
required solely for this finding.

## 23. simulate-gc current path

The top-level lease policy explicitly treats all `simulate` commands as
bypasses. `runSimulateGCCommand` calls `runObservabilitySimulateGCPhase`, which
opens the real application session before Engine GC planning. That opening may
bootstrap/migrate schema, and the shared plan read also belongs inside the
repository ownership interval.

## 24. simulate-gc coordination design

Add canonical `coordination.OperationSimulateGC = "simulate-gc"` and include
it in `isCanonicalOperation`. Add one shared pure request validator for the
existing `simulate gc` positional/flag shape. `runSimulateGCCommand` and the
policy classifier reuse it so help, unknown subcommands, extra positionals,
and invalid flags stay repository-free.

Only a valid `simulate gc` returns exclusive policy for
`OperationSimulateGC`. The existing top-level `executeCLICommand` then acquires
before dispatch, so `openCommandSession`, schema/application work, and
`PlanGarbageCollection` occur inside the lease. Session cleanup completes
before dispatch returns; output-spool cleanup and lease release retain their
existing ordering. `simulate store`, `simulate store-folder`, benchmarks,
init, help, version, and invalid commands remain bypasses. PostgreSQL advisory
ownership remains a separate backend barrier, not a repository identity lock.

## 25. simulate-gc regression contract

Freeze policy classification, safe bypass, no-repository invalid/help/version,
acquire-before-session-open, no pre-acquisition schema/plan hook, cleanup-
before-release, reacquisition, real independent holder contention, SQLite
planning, and configured PostgreSQL subprocess tests. Linux independent-
process proof is required; macOS/Windows require native policy/lifecycle proof,
not duplicate killed-holder subprocess shapes. Run relevant policy/registry
tests with `-race`.

## 28. Implementation order

1. Catalog typed errors establish the shared snapshot boundary.
2. Label semantics land on that stable boundary.
3. Packed deep verification closes the independent read-only defect.
4. `simulate gc` coordination closes the narrow policy defect.
5. Exact-only restore routing removes semantic drift.
6. Secure platform installer supplies retained-object atomic publication.
7. Metadata integration and complete restore regression finish the highest-risk
   workstream.

This creates four narrow green checkpoints before filesystem mutation changes.
