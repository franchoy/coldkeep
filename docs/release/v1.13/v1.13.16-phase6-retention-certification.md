## Certification invariant

For content owned by a committed snapshot, removing the current
`physical_file` mapping must not make any required logical file, chunk, block,
or container GC-reclaimable. After actual supported GC execution, restoring
from that snapshot must reproduce the original bytes exactly.

The canonical proof must enter through production Store with a real source
beneath an explicit capture root, create the snapshot through the Engine using
a relative explicit selector, remove the current mapping through the normal
Remove route, build the normal GC plan, execute GC, and restore through the
snapshot Engine/domain route. Direct SQL may inspect catalog state but may not
rewrite source identity, membership, Remove state, or GC reachability.

The proof will use three deliberately distinct content classes:

- snapshot-only retained content: current mapping removed, snapshot retained;
- truly unreachable control content: current mapping removed, no other root;
- current-live control content: current mapping preserved.

Before and after GC, assertions must establish the exact current mappings,
snapshot membership, absence of pins and second snapshots, plan inclusion or
exclusion, physical reclamation of the unreachable control where the active
storage form permits it, preservation of live and snapshot roots, successful
GC completion, and byte-identical post-GC snapshot restore.

## Backend and storage coverage

The permanent test must use isolated temporary roots and fresh repositories.
SQLite must certify the actual catalog and reachability implementation through
Store, snapshot creation, Remove, and GC planning. Live GC execution and
post-GC restore must be certified against disposable PostgreSQL databases in
both plain and AES-GCM profiles using `COLDKEEP_DB_AUTO_BOOTSTRAP=true`.
Supported loose/direct and packed/container-backed paths must be identified
from existing helpers and covered without inventing a storage mode or changing
codec behavior.

Any inability to satisfy the required retention invariant through an existing
supported route is a failing proof, not authority to change product code.
