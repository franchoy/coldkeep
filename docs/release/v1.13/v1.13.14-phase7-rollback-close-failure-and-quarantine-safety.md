| --- | --- | --- | --- | --- | --- |
| `APPEND_PENDING` | true | active ID only; no pending ID | open unless full-container finalization already ran | selectable | yes; lifecycle relied on caller ordering |

## 4. Private poisoned-state and identity design

`LocalWriter` now keeps a private pending append container ID beside the
existing pending file and pre-append size. A private poisoned flag and poisoned
container ID represent an unresolved unsafe boundary. These fields are
process-local and do not alter schema, migrations, public interfaces, or
container bytes.

The lifecycle is:

```text
successful AppendPayload
  -> pending file + size + exact container ID

successful commit acknowledgment
  -> clear pending bookkeeping, unless poison is already unresolved

successful rollback
  -> truncate + close + size verification
  -> clear active, pending, and poison state

failed rollback
  -> retain pending bookkeeping
  -> set poison with exact container ID
  -> refuse AppendPayload

successful durable quarantine
  -> DB row becomes quarantine=true/non-selectable
  -> clear active, pending, and poison state

failed durable quarantine
  -> retain poison and exact identity
  -> preserve every close/quarantine cause
  -> refuse AppendPayload; existing quarantine API may retry
```

`AcknowledgeAppendCommitted` is a no-op while poison is unresolved, so a late or
incorrect acknowledgment cannot erase the safety boundary.

## 5. Live-handle rollback matrix

| Truncate | Close | Result | Writer state | Quarantine result |
| --- | --- | --- | --- | --- |
| success | success | nil after size verification | clean; pending and active cleared | not invoked |
| failure | success | truncate cause | poisoned identity retained | durable success excludes row and clears poison |
| success | failure | close cause | poisoned identity retained | durable success excludes row and clears poison |
| failure | failure | `errors.Join` exposes both | poisoned identity retained | durable success excludes row and clears poison |

Post-truncate `SafeContainerPath`, `Stat`, and size verification failures enter
the same poisoned/quarantine path. Verification is skipped only when truncate
itself failed and the physical size is already uncertain.

## 6. Closed/full-container rollback audit

The full-container path may physically finalize the handle before the enclosing
metadata transaction fails. The pre-change writer retained file and size but
not the corresponding container ID, so failed path rollback could not identify
the exact row for quarantine.

Phase 7 retains the pending append container ID across `FinalizeContainer`.
Closed-path rollback now opens the exact safe path through the existing writer
filesystem, attempts truncate and close, joins both causes, preserves the
post-truncate size check, and poisons the retained ID on failure. This also
allows the Phase 3 `faultfs.OpTruncate` seam to prove the path deterministically
without a new production hook.

## 7. Durable quarantine ordering

`quarantineContainer` still attempts secondary handle close, but it no longer
clears local state before the durable DB quarantine operation. If the DB
operation fails, poison and exact identity remain. If the DB operation
succeeds, the row is non-selectable and local state clears even when the
secondary close returned an error; that close cause is still returned.

Successful quarantine proof queries the container row and then performs a
fresh append. Selection excludes `quarantine=true`, and the affected container
ID is not reused. Failed quarantine proof injects the existing faultfs `Stat`
failure before the DB update, confirms the row remains selectable, confirms
append refusal, and then retries quarantine after the one-shot fault is gone.
