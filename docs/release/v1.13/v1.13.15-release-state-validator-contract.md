# Coldkeep v1.13.15 Release-State Validator Contract

**Status:** Phase 8R boundary-aware merged-state contract
**Merge-complete phase:** 8
**Tag/publication phase:** 9
**Post-publication closure phase:** 10

## Aggregate Phase 0

The validator recognizes numeric level-two Phase headings and intentionally
ignores Phase 0A and Phase 0B evidence headings. Aggregate Phase 0 remains the
sole numeric representation of those bootstrap subphases.

## Generic lifecycle boundaries

Boundary metadata names three unique, consecutive terminal numeric phases.
Validator code must not contain release-specific version or phase literals.

    development
    -> pre-release
    -> merged-not-tagged
    -> tagged
    -> post-release-pending-closure
    -> post-release-closed

Boundary-aware progression is exact:

- development: Complete*, one Next before the merge phase, Not started*.
- pre-release: the merge phase is Next.
- merged-not-tagged: the publication phase is Next.
- tagged: the exact annotated tag peels to HEAD and the publication phase
  remains Next.
- post-release-pending-closure: the tag is a strict ancestor and the closure
  phase is Next.
- post-release-closed: the tag is a strict ancestor and every phase is
  Complete.

released is retained only for legacy contracts without boundary metadata.
An exact tag on a boundary-aware contract infers tagged. Git proves tag
identity; stable publication is proved separately by Phase 9 hosted evidence
and the post-publication tracked transition.

Historical contracts without metadata keep their prior all-phases-complete
candidate/released behavior. Missing, partial, duplicate, nonnumeric,
nonconsecutive, or nonterminal metadata fails closed when boundary-aware
progression is claimed.

## Git and pull-request contexts

The validator recognizes:

- the exact release branch/PR for development and pre-release;
- main plus recovery/v{version}-* and its validated same-repository PR for
  merged-state recovery;
- exact detached annotated tag targets for tagged or legacy released;
- main, the legacy release branch, and
  release/v{version}-post-publication-closure plus validated same-repository
  PRs for post-publication states.

Recovery and closure PR payloads must prove base main, environment/payload
head agreement, and a head repository equal to GITHUB_REPOSITORY.

## Gate contract

Exact boundary-aware gate statuses are:

    development: no Passed status
    pre-release: Passed — pre-merge prerequisites complete
    merged-not-tagged/tagged: Passed — pre-publication prerequisites complete
    post-release-pending-closure: Passed and released — closure pending
    post-release-closed: Passed and released

Candidate and tagged verdicts are nonempty and nonpending. Terminal closure
requires every phase Complete and a nonempty, nonpending verdict. A premature
Passed and released claim fails before publication.

## Final planned v1.x closure

Phase 8R does not close v1.x. Phase 9 publication does not close v1.x. Only
successful Phase 10 post-publication reconciliation, terminal authority,
exact-final-main recertification, zero-unique branch proofs, cleanup, and the
read-only Phase 10T audit may return V1_X: FULLY_CLOSED.

v1.13.15 is the final planned v1.x release. A later v1 maintenance train is
permitted only for a newly discovered critical correctness or security defect
under a separate plan and explicit authorization. V2 planning review may be
authorized after closure; v2 implementation always requires a separate plan.

## Phase 8R activation

The Phase 8R assertions are conditional until a normal protected recovery
merge places the accepted recovery commits on main and that exact final main
passes the complete recertification contract. No recursive evidence commit is
authorized.
