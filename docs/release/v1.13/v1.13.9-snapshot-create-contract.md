## Purpose

Convert the accepted Phase 1 snapshot-mutation inventory into the exact target
contract for a future engine-owned snapshot create operation.

This phase is contract-design only. It does not:

- activate `SnapshotCreate`;
- change the active `Engine` interface;
- change CLI behavior, SQL, schema, tests, or runtime routing; or
- begin Phase 3 delete-contract work.

## Executive decision

Snapshot create should become an honestly engine-owned mutation boundary later,
but the target contract must preserve the full Phase 1 behavior freeze.

The final Phase 2 design is:

- `SnapshotCreateRequest` remains a four-field request with no caller-selected
  `Type`;
- `SnapshotCreateResult` carries only committed outcome facts and removes the
  speculative `Warnings` field;
- engine-owned ID generation uses a per-engine internal generator seam;
- `FilesInserted` must come from the committed mutation itself, not from later
  CLI SQL; and
- future CLI routing becomes a thin adapter that preserves existing parser,
  output, timing, and explicit-empty validation behavior.

## Final request contract

Final request shape:

```go
type SnapshotCreateRequest struct {
	ID       string
	Label    string
	ParentID string
	Paths    []string
}
```

### Request invariants

- `ID == ""` means engine-owned ID generation.
- `ID != ""` means caller-supplied after engine normalization.
- `Label == ""` means no label.
- `ParentID == ""` means no parent.
- `len(Paths) == 0` means full snapshot.
- `len(Paths) > 0` means partial snapshot.
- `ParentID != "" && len(Paths) > 0` is invalid at the engine boundary.

The request must not include `Type`. Contradictory states such as
`Type=full with paths` or `Type=partial without paths` must not be representable
at the engine boundary.

### ID semantics

Final decision:

- the engine trims surrounding whitespace from `req.ID`;
- trimmed empty `ID` always means generate;
- a whitespace-only direct engine `ID` means generate, not validation failure;
- the result returns the normalized final ID;
- generated IDs preserve the current format exactly:
  `snap-<16 lowercase hexadecimal characters>`;
- generation uses eight cryptographically random bytes;
- generation performs exactly one attempt;
- generated-ID collisions and supplied-ID collisions share the same downstream
  duplicate-ID catalog failure class;
- no hidden collision retry is added in `v1.13.9`; and
- no new ID syntax policy is added in this release.

CLI compatibility remains:

- an explicitly provided empty or whitespace-only `--id` is still rejected by
  the CLI before repository initialization;
- the engine request does not encode CLI flag-presence metadata.

### Paths semantics

Final decision:

- the engine copies `Paths` before any downstream processing;
- the copied slice preserves caller order for compatibility accounting;
- normalized or deduplicated filters are not exposed in the engine result;
- path normalization remains snapshot-domain-owned for now;
- duplicate and overlapping filters remain accepted;
- request-only path syntax validation should move before row mutation and
  preferably before transaction begin in the future result-returning core,
  provided stable error behavior is preserved; and
- empty prefix-only partial snapshots remain valid.

`PathsCount` meaning:

- `PathsCount` is the number of path filters supplied in the engine request
  before normalization and deduplication;
- for full snapshots, `PathsCount == 0`;
- `PathsCount` is not redefined as normalized unique-filter count.

### Label semantics

Final decision:

- the engine trims surrounding whitespace from `Label`;
- trimmed empty label means absent;
- a whitespace-only direct engine label becomes absent;
- empty labels must not be persisted; and
- the result returns the normalized committed label or `""` when absent.

CLI compatibility remains:

- an explicitly provided empty or whitespace-only `--label` is still rejected
  by the CLI before repository initialization.

### Parent semantics

Final decision:

- the engine trims surrounding whitespace from `ParentID`;
- trimmed empty parent means absent;
- the result returns the normalized committed parent ID or `""` when absent;
- `ParentID != "" && len(Paths) > 0` is rejected before transaction begin;
- self-parenting is rejected after ID normalization/generation and parent
  normalization, before transaction begin;
- parent existence, parent type, and cycle validation remain inside the create
  transaction;
- full-only lineage policy remains unchanged; and
- missing-parent, partial-parent, self-parent, and cycle failures must preserve
  today’s stable user-facing substrings.

## Final result contract

Final result shape:

```go
type SnapshotCreateResult struct {
	SnapshotID    string
	Type          SnapshotType
	PathsCount    int
	FilesInserted int
	Label         string
	ParentID      string
}
```

Field meanings:

- `SnapshotID`
  - always populated on success
  - contains the final supplied or generated committed ID
- `Type`
  - always populated on success
  - derived only from request paths
  - uses `SnapshotTypeFull` or `SnapshotTypePartial`
- `PathsCount`
  - always populated on success
  - equals raw request path-filter count before normalization/deduplication
- `FilesInserted`
  - always populated on success
  - equals the exact committed `snapshot_file` membership-row count
  - may be zero for a successful empty full or partial snapshot
- `Label`
  - normalized committed label or `""`
- `ParentID`
  - normalized committed parent ID or `""`

`Warnings` is removed from the create result because:

- successful snapshot create has no live warning class today;
- preserving a speculative warning field would misrepresent runtime truth; and
- the change affects only inactive candidate surfaces, their tests, and release
  docs.

## ID generator design

Preferred internal seam:

```go
type snapshotIDGenerator func() (string, error)
```

Target ownership:

- unexported field on `DefaultEngine`
- defaulted during `New`
- nil or unset uses the secure default generator
- deterministic IDs and injected generator failures are provided only through
  package-private engine test helpers or constructors
- not exposed on public `Config`
- immutable after engine construction

Generator rules:

- the default generator uses `crypto/rand` and is concurrency-safe;
- generated IDs must still be validated as non-empty before mutation begins;
- generator errors happen before transaction begin and before any catalog
  mutation;
- no package-global mutable test hook is introduced.

## Domain result-return strategy

Preferred migration path:

- add a new result-returning snapshot-domain create core;
- keep the current error-only wrapper temporarily for compatibility with old
  callers; and
- route future engine activation to the result-returning core.

Recommended domain result:

```go
type CreateSnapshotResult struct {
	SnapshotID    string
	Type          string
	PathsCount    int
	FilesInserted int
	Label         string
	ParentID      string
}
```

Why this design:

- the create domain already computes `insertedCount := len(insertRows)`;
- the committed count can be returned honestly without a second SQL query;
- transaction atomicity remains unchanged; and
- existing direct callers can keep using the compatibility wrapper until later
  routing work migrates them.

Rejected as the preferred design:

- engine-side post-create count query;
- callback or mutable output-parameter designs.

## Transaction contract

The future successful create path must freeze this boundary:

1. engine copies request paths
2. engine normalizes ID, label, and parent
3. engine derives full vs partial from paths
4. engine validates parent-with-paths and self-parent request invariants
5. domain performs request-only path normalization/validation
6. domain begins transaction
7. domain performs transactional parent and ancestry checks
8. domain inserts the snapshot row
9. domain resolves source rows and validates missing exact paths against the
   same transactional view used for membership insertion
10. domain resolves `snapshot_path` rows and inserts membership rows
11. domain commits
12. result is returned only after commit succeeds

Transaction guarantees:

- parent existence/type/cycle validation stays in the same transaction as the
  snapshot mutation;
- exact-path existence validation uses the same transactional source-row view as
  membership insertion;
- `FilesInserted` may be computed before commit, but it must never be returned
  on commit failure;
- failures after `BeginTx` guarantee rollback attempt;
- commit failure returns error and no success result;
- empty full snapshots remain valid with `FilesInserted == 0`;
- empty prefix-only partial snapshots remain valid with `FilesInserted == 0`;
- Phase 2 does not redesign isolation levels.

## Validation ordering

| Validation or step | Owner | Requires DB | Requires transaction | Occurs before mutation | Compatibility note |
| --- | --- | --- | --- | --- | --- |
| Copy request `Paths` | engine | no | no | yes | prevents caller-slice mutation |
| Normalize/generate `ID` | engine | no | no | yes | preserves CLI explicit-empty distinction outside engine |
| Normalize `Label` and `ParentID` | engine | no | no | yes | trims only; no new policy |
| Derive full vs partial | engine | no | no | yes | still path-driven |
| Reject parent with paths | engine | no | no | yes | preserves full-only lineage policy |
| Reject self-parent | engine | no | no | yes | same meaning as current runtime |
| Normalize/validate path syntax | snapshot domain core | no | no | yes | move before row mutation if stable errors preserved |
| Deduplicate/overlap handling | snapshot domain core | no | no | yes | duplicates stay accepted |
| Begin transaction | snapshot domain core | yes | yes | n/a | preserves transactional consistency |
| Parent missing / parent partial / cyclic ancestry | snapshot domain core | yes | yes | no | must keep stable substrings |
| Insert snapshot row / detect duplicate ID | snapshot domain core + catalog | yes | yes | no | duplicate-ID behavior preserved |
| Source-row query / missing exact path / path-ID resolution / membership insert | snapshot domain core | yes | yes | no | rollback on failure |
| Commit | snapshot domain core | yes | yes | no | no success result on commit failure |

## Error contract

Phase 2 does not introduce a broad new error framework.

### Required categories

- request validation
- ID-generation failure
- lineage/domain invariant
- not found
- duplicate/conflict
- catalog query/write
- transaction begin
- transaction commit
- backend/runtime

### Wrapping and compatibility

- keep existing wrapped errors and stable substrings;
- do not collapse useful domain errors into a generic
  `snapshot create failed` surface;
- add only light context wrapping where existing CLI-visible substrings survive;
- do not require a new typed taxonomy unless later routing proves a concrete
  classification need.

Current representative stable substrings to preserve:

- `generate snapshot id entropy:`
- `--from is currently supported only for full snapshots`
- `parent snapshot "<id>" not found`
- `cannot reference itself`
- `cyclic ancestry`
- `path not found in current state:`
- `begin snapshot transaction:`
- `commit snapshot transaction:`

Mutation and rollback expectations:

- request-validation and generator errors occur before mutation begins;
- transactional invariant, query, write, and duplicate-ID failures may occur
  after `BeginTx` and must roll back;
- commit failure must not return a success result.

## DB and dependency boundary

Future `DefaultEngine.SnapshotCreate` should require only:

- `Config.DB`
- a context
- the snapshot-domain create function
- operation-context setup if the engine continues that pattern

It should not require:

- `StoreContext`
- container directory
- payload readers or writers
- chunkers or codecs
- restore destinations
- filesystem mutation dependencies

Snapshot create is a catalog-only engine operation. Correctness must not depend
on storage-writer dependencies.

## Future engine method target

Target future method:

```go
SnapshotCreate(
	ctx context.Context,
	req SnapshotCreateRequest,
) (SnapshotCreateResult, error)
```

Future method expectations:

- belongs directly on `Engine` only when a later activation phase approves it;
- normalizes `nil` context to `context.Background()` before DB work;
- is safe for concurrent calls;
- does not add new mutation serialization in this release; and
- does not place duration, perf spans, output mode, writers, or JSON-specific
  fields in the engine result.

Timing and human/JSON shaping remain caller-owned.

## Future CLI translation

Future thin adapter:

```text
CLI
  -> reject explicit empty/blank --id, --label, --from
  -> collect raw positional paths
  -> build SnapshotCreateRequest
  -> call Engine.SnapshotCreate
  -> render existing human/JSON output
```

After later routing, the CLI must stop:

- generating snapshot IDs;
- deriving an independently supplied create `Type`;
- calling snapshot create domain functions directly; and
- querying `snapshot_file` after create.

CLI remains owner of:

- parsing
- explicit flag-presence validation
- output mode
- timing/perf spans
- human rendering
- JSON envelope

### `files_inserted` compatibility decision

Final Phase 2 decision:

- `data.files_inserted` should become unconditional on successful engine-routed
  creates.

Why:

- the engine result will always have an exact committed count;
- the current omission path exists only because of a separate best-effort
  post-create count query;
- that query is intentionally removed by this contract; and
- Phase 1 marked omission-on-count-query-failure as uncovered rather than a
  behavior that must be preserved.

If later evidence proves historical omission must remain, that should require a
dedicated regression and compatibility note rather than reintroducing
post-create SQL.

## SQLite/PostgreSQL parity requirements

Both backends must agree on:

- generated ID format and returned value;
- supplied ID normalization;
- full/partial derivation;
- label and parent normalization;
- parent-plus-paths rejection;
- duplicate and overlapping path acceptance;
- exact missing-path rollback;
- parent missing/partial/self/cycle behavior;
- empty full and partial snapshot behavior;
- duplicate snapshot ID behavior;
- exact `PathsCount`;
- exact committed `FilesInserted`; and
- no success result on commit failure.

Dialect-sensitive areas that later validation must cover explicitly:

- snapshot insertion
- source-row query
- optional `FOR UPDATE` behavior
- path-ID resolution
- batch membership insertion
- ancestry queries
- unique-constraint failures
- placeholder and driver-error wrapping

SQLite-only coverage is not sufficient proof of PostgreSQL parity.

## Security and correctness review

This contract prevents or explicitly constrains the key create-boundary risks:

- contradictory type/path state cannot be represented
- empty ID has one precise engine meaning: generate
- CLI explicit-empty ID rejection remains preservable
- returned `SnapshotID` must equal the committed final snapshot ID
- `FilesInserted` cannot be reported from uncommitted or guessed state
- caller-owned path slices are not mutated
- whitespace-only optional metadata is not persisted unintentionally
- parent relationships cannot escape the current full-only restriction
- success cannot be reported after rollback or commit failure
- no storage-writer dependency is introduced for a catalog-only operation

Generated IDs keep the current cryptographic format. Phase 2 does not justify:

- collision retry
- stronger entropy
- length changes
- additional syntax validation

without new defect evidence.
