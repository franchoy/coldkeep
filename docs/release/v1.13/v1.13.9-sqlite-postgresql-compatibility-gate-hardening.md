# v1.13.9 Phase 17 — SQLite/PostgreSQL Compatibility Gate Hardening

Starting SHA: `7b7b21f37094c83820dfff2e846c244f1f32cdb3`

## Summary

Phase 17 closes the remaining tracker-definition gap after Phase 16 proved the
repair/recovery boundary honestly but left the next backend-compatibility
follow-up only named in the broader release train.

This phase is docs-only. It does not implement backend-parity hardening, does
not change runtime backend behavior, and does not change any schema, storage,
workflow, or CLI behavior.

Its purpose is to define the exact next implementation phase for `v1.13.9`
using the checked-in release documents as the source of truth.

## Current confirmed backend posture

The checked-in release train and current tests already establish that:

- PostgreSQL remains the normal runtime backend for current release-gate work
- SQLite compatibility remains part of the supported compatibility posture
- stronger ongoing parity proof is still needed in selected backend-sensitive
  areas
- no backend-default transition is authorized by this phase

## Defined next implementation phase

The next implementation phase after Phase 17 is:

`Phase 18 — CLI Thin-Wrapper Proof and Remaining Coupling Review`

Phase 17 itself does not start that work. It only freezes the next handoff so
the `v1.13.9` tracker matches the already checked-in `v1.13.x` release train.

## Allowed future Phase 18 areas

If Phase 18 proceeds, the intended implementation surface is limited to:

- `cmd/coldkeep`
- `internal/engine`
- related parity tests and release artifacts

Phase 18 should stay focused on thin-wrapper proof and direct CLI-ownership
classification rather than new routing migrations or daemon/API work.

## Allowed future backend-hardening areas

If the later backend-hardening implementation proceeds from this Phase 17
definition, the intended surface is limited to:

- `internal/db`
- `internal/catalog`
- selected `internal/engine` tests
- integration harness parity checks
- CI validation coverage only if the later phase explicitly requires it

That later work must preserve current backend defaults and avoid speculative
compatibility rewrites.

## Forbidden in Phase 17

Phase 17 does not:

- change SQLite or PostgreSQL runtime behavior
- change backend defaults
- change schemas or migrations
- change storage format
- change engine contracts
- change CLI output or parser behavior
- change snapshot, doctor, repair, recovery, or verify behavior
- change workflows
- begin Phase 18 implementation
- open or reopen a pull request
