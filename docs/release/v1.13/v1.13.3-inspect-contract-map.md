# Coldkeep v1.13.3 — Inspect Contract Cleanup Map

## Status

`complete`

## Purpose

This document maps the current `inspect` read-side contract and identifies the
safe cleanup and test-hardening plan for later `v1.13.3` phases.

This document does not change `inspect` behavior.

This document does not change `inspect` routing.

This document does not change `inspect` JSON output.

This document does not change `inspect` exit codes.

This document does not introduce new `inspect` request or result types.

This document is input for Phases 6, 7, and 8.

## Relationship to Phase 1

Phase 1 established the key `inspect` finding that drives this phase:

`inspect` still bypasses engine in production and calls observability directly.

Current `inspect` ownership summary:

- current CLI entry point: `runInspectCommand`
- current engine involvement: `engine.Inspect` and `engine.InspectRequest` /
  `engine.InspectResult` exist, but the production CLI path does not call the
  engine wrapper
- current observability ownership: `runObservabilityInspectPhase` opens the
  repository DB, creates the observability service, and calls
  `observability.Service.Inspect`
- current renderer ownership: `internal/cli/render` owns public human and JSON
  success rendering
- current backend, catalog, and storage dependencies: inspect uses direct DB
  queries, maintenance-derived repository block stats, graph-style relation
  reads, and storage-adjacent metadata through chunk, container, logical-file,
  and snapshot views
- current entity-target behavior: the CLI supports `repository`, `file`,
  `logical-file`, `snapshot`, `chunk`, and `container`; `logical-file` is a
  CLI alias to `observability.EntityFile`

## Current Inspect Flow

Current code-path flow:

```text
CLI inspect command
  -> flag parsing and validation
  -> target and entity parsing
  -> trace option resolution
  -> output mode selection
  -> runObservabilityInspectPhase
  -> storage context / DB opening
  -> observability service creation
  -> observability.Service.Inspect
  -> entity-specific DB / graph / maintenance / storage-adjacent reads
  -> observability.InspectResult
  -> renderer human or JSON output
```

## Current Request / Result Shape

Current shape facts:

- `engine.InspectRequest` exists in `internal/engine`
- `observability.InspectOptions` exists in `internal/observability`
- `engine.InspectResult` exists, but is only a thin wrapper around
  `Raw *observability.InspectResult`
- the concrete result type lives in `internal/observability`
- `internal/cli/render` aliases `InspectResult = observability.InspectResult`
- JSON output maps directly from the observability result through renderer
  normalization and envelope wrapping
- human output maps directly from the observability result through renderer
  formatting
- the CLI does not apply a separate success-payload transformation beyond
  parsing, calling the observability phase, and passing the result to the
  renderer
- entity-specific summary and relation fields are embedded in the common
  `observability.InspectResult` envelope

| Shape | Type / name | Package | Current role | v1.13.3 decision |

| CLI target / flag surface | `inspect` command flags and positionals | `cmd/coldkeep` | public command contract | `preserve as-is` |
| Engine request | `InspectRequest` | `internal/engine` | adjacent wrapper request surface | `document as provisional` |
| Observability options | `InspectOptions` | `internal/observability` | active service input shape | `preserve as-is` |
| Engine result | `InspectResult` | `internal/engine` | thin wrapper over observability result | `document as provisional` |
| Concrete result | `InspectResult` | `internal/observability` | active read-side success model | `candidate for later engine-owned result` |
| Renderer JSON envelope | `JSONRenderer.RenderInspect` | `internal/cli/render` | public JSON success contract | `candidate for Phase 7 preservation test` |

## Current Inspect Behavior To Preserve

Verified current public behavior that must remain unchanged:

- command name is `inspect`
- accepted flags are `--output`, `--json`, `--relations`, `--reverse`,
  `--deep`, `--limit`, `--trace`, `--trace-json`, `--help`, and `-h`
- supported targets are `repository`, `file`, `logical-file`, `snapshot`,
  `chunk`, and `container`
- target and entity parsing behavior:
  - repository takes no ID
  - file, chunk, and container IDs must be positive integers
  - snapshot ID is a trimmed string and may be non-numeric
  - `logical-file` routes to the file entity path
- human output is renderer-owned and includes the `Inspect ...` title,
  `Summary`, and relation sections when present
- JSON success output uses the renderer envelope with:
  - `type: "inspect"`
  - `meta.version: "v1.7"`
  - `meta.exact: true`
- not-found behavior is translated to public `NOT_FOUND` in the CLI when
  observability returns `ErrNotFound` or `sql.ErrNoRows`
- unsupported target behavior is currently CLI validation with
  `INVALID_ARGUMENT`, not a runtime unsupported-engine seam
- invalid-target behavior is currently split between CLI numeric or empty-ID
  validation and observability `ErrInvalidTarget` for service-level malformed
  targets
- trace flags alter trace-sink behavior, not the semantic result shape
- failures otherwise route through shared CLI error translation with no
  inspect-specific exit-code redesign
- backend-visible behavior is expected to remain equivalent across supported
  backends

## Error Taxonomy Mapping For `inspect`

| Error family | Current source | Current representation | Public behavior | v1.13.3 decision |
| --- | --- | --- | --- | --- |
| validation / usage errors | CLI parsing in `runInspectCommand`, `ensureAllowedFlags`, `resolveTraceOptions`, `usageErrorf`, and `--limit` validation | `usageErrorf(...)` / `cliError` | usage-style message and shared usage exit classification | `preserve as-is` |
| unsupported inspect target | CLI entity allowlist in `runInspectCommand` | `observabilityErrorf(exitUsage, "INVALID_ARGUMENT", ...)` | public `INVALID_ARGUMENT` behavior | `candidate for Phase 7 preservation test` |
| invalid inspect target | CLI empty-ID or numeric validation, plus observability invalid-target checks | CLI `INVALID_ARGUMENT` or `ErrInvalidTarget` under wrapped internal failure | current validation behavior must remain stable | `candidate for Phase 6 and Phase 7 protection` |
| wrong entity / wrong ID type | CLI numeric validation and engine-side adjacent wrapper validation | usage or invalid-argument style failure today | document carefully without overclassifying as invariant | `document as provisional` |
| domain not-found errors | observability lookup miss for valid entity and ID | `ErrNotFound` or `sql.ErrNoRows` translated by CLI | public `NOT_FOUND` behavior | `candidate for Phase 6 and Phase 7 protection` |
| invariant / integrity errors | indirect only unless lower-level reads surface consistency failures | no dedicated inspect invariant family today | must not be invented or overstated in Phase 3 | `document as indirect / provisional` |
| runtime DB errors | observability query and relation-load failures | wrapped query or service errors | shared CLI general failure behavior | `candidate for Phase 6 and Phase 7 protection` |
| catalog-origin errors | snapshot, logical-file, chunk, and relation queries through observability DB reads | wrapped runtime-like read failures | shared CLI general failure behavior | `document honestly; no new helper` |
| storage-origin errors | indirect through chunk, container, logical-file, and repository block-stat metadata | not a first-class typed inspect seam | surfaces, if at all, through lower-level wrapped failures or metadata fields | `document as indirect` |
| environment / config errors | storage context open, DB open, nil DB, or service setup failure | wrapped setup or DB-open failures | shared CLI general failure behavior | `candidate for later preservation checks` |
| unsupported / deferred errors | no active inspect unsupported-engine or deferred seam in production path | not current behavior | should not be introduced accidentally | `document as not current behavior` |
| unknown / provisional errors | wrapper ownership and result-type ownership seams | documentation-only classification | no public taxonomy leakage | `document as provisional only` |

Important mapping constraints:

- do not claim unified inspect taxonomy wrapping
- do not introduce new helper names
- do not classify all not-found behavior as invariant
- do not classify wrong-entity behavior more strongly than current code does

## Domain Vs Invariant Boundary For `inspect`

Current boundary guidance from repo truth:

- missing valid target and entity combinations are active domain not-found
  behavior when observability returns `ErrNotFound`
- malformed or unsupported targets are validation or current
  unsupported-target behavior, not domain not-found
- wrong-entity and wrong-ID-type behavior remains validation or provisional,
  not a settled invariant contract
- impossible metadata relationships or graph inconsistencies are invariant or
  integrity concerns only if current code already detects them or later phases
  establish them with tests
- runtime DB and read failures remain runtime, catalog-origin, storage-origin,
  or environment-origin failures, not domain not-found

## Backend Compatibility Notes

Current backend observations:

- `engine.InspectRequest` and `engine.Config` are backend-neutral by existing
  engine backend-compatibility tests
- observability inspect uses direct `QueryRowContext` and related DB queries
- inspect covers chunk, container, snapshot, logical-file, and repository
  summary views
- inspect touches packed, legacy, and block-adjacent information through
  repository block-compression summary, chunk relations, and container
  relations
- no direct observability dependency on `internal/snapshot` was found in the
  current inspect production path; snapshot-target behavior uses DB reads
  directly
- supported behavior is expected to be backend-equivalent

## Public CLI Preservation Notes

Preservation concerns that later phases must keep explicit:

- human output preservation:
  - renderer-owned layout, `Inspect ...` titles, `Summary`, and relation
    sections must not drift accidentally
- JSON output preservation:
  - success envelope shape, `type`, `meta.version`, and warning handling must
    remain stable
- JSON error-envelope preservation:
  - inspect uses shared CLI error JSON and must not grow inspect-specific
    taxonomy fields
- exit-code preservation:
  - inspect depends on shared CLI exit classification and must not get a
    custom redesign
- startup / logging / noise concerns:
  - trace flags intentionally affect stderr trace sinks without changing the
    semantic success result shape
- taxonomy helper leakage concerns:
  - no taxonomy helper names or internal classification fields should appear
    in public `inspect` JSON

## Risks If `inspect` Contract Is Cleaned Incorrectly

- accidental JSON drift
- accidental human-output drift
- accidental exit-code drift
- changing not-found behavior
- changing unsupported-target behavior
- changing wrong-entity behavior
- treating runtime DB failure as domain not-found

- leaking internal taxonomy labels

- duplicating result shapes

## Final Phase 3 Decision

`inspect` is acceptable for `v1.13.3` as a read-side surface that still calls
observability directly from the CLI, provided later phases protect public
CLI/JSON/exit-code behavior and document direct observability ownership as
provisional for later engine-contract cleanup.
