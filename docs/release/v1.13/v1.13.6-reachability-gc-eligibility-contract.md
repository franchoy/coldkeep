# Coldkeep v1.13.6 Reachability and GC Eligibility Contract Review

**Release:** `v1.13.6 — Catalog Contract Expansion and Backend Parity Review`  
**Phase:** Phase 5  
**Status:** Complete  
**Branch:** `release/v1.13.6`

## Purpose

This document reviews how Coldkeep currently determines whether data is
reachable, retained, reclaimable, unsafe, refused, or repairable.

It connects the Phase 2 snapshot membership review, the Phase 3
logical/physical mapping review, and the Phase 4 placement/restore-plan review
into the current GC and repair safety model.

This phase performs no implementation work and adds no tests.

## Contract under review

The current reachability and GC eligibility contract is defined by:

- current/live roots
  - logical-file IDs referenced by current `physical_file` rows
- snapshot roots
  - logical-file IDs referenced by retained `snapshot_file` rows
- snapshot-retained data
  - logical content that remains protected even after current-state physical
    mappings disappear
- logical/physical mapping roots
  - current-state reachability starts from the physical mapping graph rather
    than from snapshot membership or placement rows directly
- file_chunk/chunk reachability
  - logical-file roots traverse through `file_chunk` into chunk reachability
- packed block reachability
  - packed block liveness is derived from reachable or otherwise live chunk
    membership through `chunk_block_refs` and `storage_blocks`
- legacy container reachability
  - legacy container liveness is derived from chunk placement through `blocks`
    and `container`
- dry-run GC eligibility
  - read-only planning that computes what would become reclaimable without
    mutating metadata or storage
- live GC deletion eligibility
  - state-changing deletion that is allowed only after the same integrity gate
    and reachability assumptions are satisfied
- repair/refcount refusal boundaries
  - repair recomputes current-state `logical_file.ref_count` from
    `physical_file` rows and refuses orphan physical mappings
- orphan/dangling row behavior
  - physical-graph or snapshot-graph drift is treated as integrity territory,
    not as silently repairable GC input
- invariant metadata and recommended actions
  - machine-readable invariant codes and operator-facing recommended actions are
    produced below CLI rendering
- backend compatibility expectations
  - SQLite and PostgreSQL are both in scope, but parity decisions remain
    deferred to Phase 6

## Root-set construction

Current reachability root construction is broader than the narrow catalog-owned
surface.

- What counts as a root:
  - current/live roots are logical-file IDs referenced by `physical_file`
  - snapshot roots are logical-file IDs referenced by `snapshot_file`
  - the active GC root set is the union of both, deduped at logical-file level
- Root identity:
  - root identity is primarily logical-file based
  - traversal then expands from logical files into `file_chunk`, chunk, block,
    and container state as needed
- Current-root ownership:
  - `graph.CurrentLogicalFileRoots` queries `SELECT DISTINCT logical_file_id
    FROM physical_file`
  - `retention.ListCurrentReferencedLogicalFileIDs` and
    `catalog.LoadReachabilityRoots` expose the same current-root concept at
    different layers
- Snapshot-root ownership:
  - `graph.SnapshotRoots` reads `snapshot_file` directly and filters excluded
    snapshot IDs in memory for hypothetical delete planning
  - `retention.ListSnapshotReferencedLogicalFileIDs` and
    `catalog.LoadReachabilityRoots` expose the same underlying snapshot-root
    source without owning the full operational traversal
- Catalog boundary:
  - `internal/catalog` owns only the neutral root-set loader through
    `LoadReachabilityRoots`
  - active root merging and traversal remain graph-owned, with retention/GC and
    maintenance consuming those lower-layer results
- Mapping and placement participation:
  - Phase 3 current-state mapping feeds current roots through `physical_file`
  - Phase 2 snapshot membership feeds snapshot roots through `snapshot_file`
  - Phase 4 placement rows participate indirectly only after chunk reachability
    is derived; they are not independent top-level roots
- Ordering:
  - ordering appears in root queries for determinism and tests, but set
    membership is the material contract for reachability
- Backend-sensitive observations:
  - root queries themselves are simple and documented as portable
  - lower-layer consequences remain sensitive to FK enforcement, aggregate
    behavior, and how orphaned rows are surfaced

## GC dry-run planning

`gc.BuildPlan` is the shared read-only planner used by simulation and by real
GC before any sweep happens.

- Shared planner:
  - `gc.BuildPlan` validates assumed-deleted snapshots, applies the physical
    integrity refusal gate, loads `graph.GCRoots`, traverses reachable chunks,
    and computes reclaimability without writing anything
- Assumed-deleted snapshots:
  - `PlanOptions.AssumeDeletedSnapshots` supports hypothetical snapshot-delete
    planning
  - each requested snapshot ID must already exist or the plan fails closed
- Reclaimability inputs:
  - roots determine reachable logical files
  - graph traversal determines reachable chunks
  - chunk `live_ref_count` and `pin_count` remain part of chunk reclaimability
  - packed-block and container state then determine what is immediately
    reclaimable physically
- Snapshot-retained protection:
  - snapshot-referenced logical files are protected before chunk- and
    placement-level reclaimability is derived
  - delete simulation changes GC eligibility only by excluding selected
    snapshot roots; it does not mutate snapshot metadata
- Logical vs physical reclaimability:
  - the plan explicitly separates logical reclaimability from immediate
    physical reclaimability
  - packed dead bytes retained inside still-live packed blocks are tracked
    separately from bytes that current GC can free immediately
- Packed and legacy representation:
  - both packed-block and legacy-container impacts are represented in the
    planner
  - mixed repositories are therefore part of the active dry-run contract
- Refusal semantics:
  - dry-run refuses the same unsafe physical-graph integrity states as real GC
  - the refusal happens before any mark traversal rather than after partial
    planning
- Backend-sensitive observations:
  - the root and planning queries use portable `$1`-style placeholders
  - parity questions remain around grouped aggregates, FK assumptions,
    packed/legacy equivalence, and release-gate-only PostgreSQL evidence

## Live GC deletion planning

`maintenance.RunGCWithDB` remains the active mutating owner of live GC.

- Ownership:
  - live GC acquires backend-appropriate locking, runs the same integrity gate,
    computes pre-flight state, and then sweeps eligible units
- Pre-flight refusal:
  - `gcIntegrityPreFlight` refuses orphan `physical_file` rows, refcount
    mismatches, and negative refcounts before any deletion logic proceeds
  - operators are directed toward `repair ref-counts` first
- Pre-flight state:
  - live GC computes a retention summary, marks reachable chunks, loads live
    packed-block IDs, and loads live legacy-container IDs before the sweep
- Candidate deletions:
  - sealed, non-quarantined containers are evaluated during the main sweep
  - fully dead active containers may be cleaned up afterward in non-dry-run
    mode
  - the active deletion surface is container/block/chunk-adjacent rather than
    direct deletion of currently rooted logical-file metadata
- Protected objects:
  - objects protected by current roots stay protected through `physical_file`
  - objects protected by snapshot roots stay protected through `snapshot_file`
  - chunk `live_ref_count`, `pin_count`, packed-block sharing, and live legacy
    placement keep additional lower-layer state from being treated as
    reclaimable too early
- Transaction and fail-closed posture:
  - live GC applies refusal before mutation
  - sweep behavior is wrapped in transaction-aware and rollback-aware storage
    code paths
  - FK violations are treated as safety signals rather than as conditions to
    force through
- Backend support:
  - SQLite supports dry-run only
  - PostgreSQL is the current live-GC backend because advisory locking and live
    mutation support are implemented there
- Backend-sensitive observations:
  - advisory locking is PostgreSQL-only
  - live delete safety depends on FK behavior, transaction semantics, and dry
    run/live equivalence that Phase 6 must review, not assume

## Snapshot retention interactions

Snapshot retention is a first-class protection dimension separate from current
physical mappings.

- Detection:
  - snapshot-retained logical data is detected through `snapshot_file`
  - `retention.ComputeReachabilitySummary` builds `CurrentLogicalIDs`,
    `SnapshotLogicalIDs`, and `RetainedLogicalIDs`
- Retention classification:
  - `retention.ClassifyRetention` separates current-only, snapshot-only, and
    shared logical IDs for operator-facing reporting
- Snapshot delete interaction:
  - `DeleteSnapshot` removes snapshot metadata and `snapshot_file` rows only
  - this can reduce later GC protection indirectly, but it does not delete
    logical content itself
- Delete preview interaction:
  - `LoadDeleteLineagePreview` provides lineage, unique/shared-file counts, and
    delete-preview context
  - it is retention-adjacent evidence, not the owner of root-set truth
- Orphan/dangling membership behavior:
  - orphan snapshot path refs, orphan snapshot logical refs, duplicate snapshot
    path pairs, and invalid snapshot lifecycle states are currently surfaced in
    verify/invariant paths
  - this phase records them as safety-critical observations rather than as
    catalog-owned behavior
- Phase 6 follow-up items:
  - FK-enforced versus permissive handling of corrupt snapshot membership rows
  - parity of snapshot-exclusion semantics during hypothetical delete planning
  - whether missing-table and missing-row edge handling stays equivalent across
    backends

## Packed/legacy reachability interactions

Reachability starts with logical roots, but GC eligibility ultimately depends
on placement structure.

- Chunk bridge:
  - chunk reachability is the bridge from logical roots into lower placement
    reclaimability
  - chunks remain the common unit between current-state logical identity and
    packed/legacy physical storage
- Packed reachability:
  - packed block liveness is derived from reachable or live chunks via
    `chunk_block_refs` and `storage_blocks`
  - a packed block that still contains any reachable or otherwise live chunk
    segment remains protected
- Legacy reachability:
  - legacy container liveness is derived from chunk placement through `blocks`
    and `container`
  - reclaimability remains container-oriented, not just chunk-oriented
- Mixed repository behavior:
  - packed and legacy placement are both first-class current behavior
  - the GC contract must therefore handle mixed repositories without implying
    that one storage model is transitional or secondary
- Shared protection:
  - shared packed blocks survive if any referenced chunk remains live or
    reachable
  - legacy containers with mixed live/dead chunk membership remain only
    partially reclaimable
- Restore/verify assumptions:
  - Phase 4 ordering and placement assumptions feed GC safety because GC must
    not reclaim bytes that restore or verify still need to interpret as live
  - placement ownership remains in storage/verify rather than catalog
- No Phase 5 conclusion:
  - packed/legacy parity remains a review subject for Phase 6, not a decision
    in this document

## Repair/refcount and orphan-row boundaries

Repair and GC share the same current-state physical-graph trust boundary.

- Repair input assumptions:
  - `RepairLogicalRefCountsResultWithDB` treats `physical_file` rows as the
    source of truth for current-state refcount repair
  - it does not recompute from snapshot roots or from catalog-level root
    abstractions
- Refusal boundary:
  - repair refuses orphan `physical_file` rows before it rewrites any
    `logical_file.ref_count`
  - this is fail-closed behavior, not best-effort normalization
- Recalculation scope:
  - repair recalculates only current-state `logical_file.ref_count`
  - snapshot-retention protection remains a separate safety dimension
- Broken-graph handling:
  - repair is not positioned as a tool to legitimize dangling mappings
  - GC likewise refuses to reason over a drifted physical graph
- Invariant metadata:
  - orphan-row refusal is surfaced with stable invariant metadata through
    `CodeRepairRefusedOrphanRows`
  - recommended actions are attached lower in the stack and preserved into CLI
    rendering
- Backend-sensitive observations:
  - transaction visibility, FK enforcement, and aggregate query behavior remain
    parity questions for Phase 6

## Invariant metadata and public rendering separation

Invariant metadata is created below the public rendering layer and then carried
through higher boundaries.

- Metadata creation:
  - `internal/invariants` defines stable codes such as
    `GC_REFUSED_INTEGRITY`, `GC_FK_VIOLATION`, and
    `REPAIR_REFUSED_ORPHAN_ROWS`
  - maintenance and verify flows wrap domain failures with those codes
- Recommended actions:
  - recommended actions are derived from invariant codes in
    `internal/invariants/errors.go`
  - they describe operator recovery steps such as running
    `coldkeep repair ref-counts` or investigating orphan physical rows
- Preservation:
  - engine and CLI layers preserve this metadata rather than originating it
  - Phase 5 builds on the v1.13.5 invariant-propagation review by adding the
    GC/reachability ownership context
- Rendering boundary:
  - human-readable output and JSON rendering remain CLI-owned
  - Phase 5 documents the underlying metadata ownership, not public wording or
    envelope shape changes
- Out of scope:
  - output-shape decisions, CLI phrasing changes, and JSON envelope changes
    remain outside this phase

## Backend posture

### Backend-neutral reachability surfaces

- `internal/catalog.LoadReachabilityRoots` uses two simple `SELECT DISTINCT`
  logical-ID queries and documents them as identical across SQLite and
  PostgreSQL
- `graph.CurrentLogicalFileRoots`, `graph.SnapshotRoots`, and
  `retention.ComputeReachabilitySummary` operate on backend-portable logical-ID
  sets
- logical-root identity itself does not differ between packed and legacy
  storage

### Backend-sensitive reachability surfaces

- set-membership equivalence below the root-set layer depends on JOIN
  cardinality and aggregate behavior staying consistent
- live GC support diverges by backend: PostgreSQL supports live mutation while
  SQLite is dry-run-only
- dry-run/live equivalence depends on lower-layer placement and transaction
  behavior, not only on shared roots
- FK enforcement materially affects how orphan/dangling rows are prevented or
  surfaced

### SQLite-specific assumptions, if any

- much of the directly visible unit coverage is SQLite-heavy
- some retention helpers treat a missing `snapshot_file` table as empty
  retention state, matching SQLite-compatible bootstrap/error handling
- live GC is explicitly unsupported on SQLite and must remain dry-run-only in
  the current implementation

### PostgreSQL-specific assumptions, if any

- advisory locking for live GC is PostgreSQL-only
- live GC execution currently depends on PostgreSQL backend support
- the strongest explicit end-to-end backend evidence outside focused unit tests
  remains concentrated in PostgreSQL-capable integration and release-gate paths

### Dialect-adapted areas

- backend selection for live GC behavior happens through `db.BackendFromDB`
- snapshot-exclusion validation, GC planning, and live sweep share portable
  query style but run inside backend-adapted execution paths
- CLI and maintenance behavior depend on backend-sensitive FK and transaction
  effects even when the top-level contract language is neutral

### Phase 6 follow-up items

- set-membership equivalence across SQLite and PostgreSQL
- JOIN cardinality assumptions in chunk/block/container reachability
- NULL/default handling in retention and placement-adjacent aggregates
- COUNT/GROUP BY aggregation differences in GC planning and integrity checks
- ORDER BY stability where deterministic public summaries matter
- DELETE behavior and FK enforcement during live GC
- transaction isolation and rollback safety
- PostgreSQL locking/isolation behavior
- SQLite FK-disabled behavior if misconfigured
- packed/legacy eligibility parity
- dry-run/live equivalence across backends
- release-gate-only PostgreSQL evidence outside focused contract suites

## Phase 5 findings

### Stable current contract observations

- The current GC root set is explicitly logical-file based and merges current
  `physical_file` roots with snapshot-retained `snapshot_file` roots.
- Catalog ownership remains intentionally narrow at the root-set layer, while
  active traversal, planning, and mutation stay in graph, GC, maintenance, and
  verify layers.
- `gc.BuildPlan` is the shared exact read-only planner for simulation and real
  GC preparation.
- GC and repair both fail closed when the current physical graph is drifted.
- Snapshot deletion is metadata-only and affects later GC eligibility only by
  changing root membership.

### Backend-sensitive observations for Phase 6

- Live GC backend support is intentionally asymmetric today: PostgreSQL supports
  live mutation while SQLite is dry-run-only.
- FK enforcement differences can affect how orphan physical or snapshot rows
  are surfaced before GC or repair runs.
- Chunk/block/container reachability depends on grouped aggregate and join
  behavior that should be reviewed explicitly for parity.
- Dry-run/live equivalence should be treated as a parity question across
  backends, not assumed from the shared planner alone.
- PostgreSQL evidence outside focused contract tests remains concentrated in
  integration and release-gate paths.

### Coverage evidence for Phase 7

- Root-set behavior has direct catalog, graph, and retention test evidence.
- GC planning and simulation equivalence have direct focused evidence.
- Live GC, packed/legacy reclaimability, repair refusal, and invariant
  propagation each already have visible evidence clusters to classify.
- Backend parity evidence exists, but Phase 7 still needs to classify how much
  of it is focused, duplicated, release-gate-only, or still deferred.

### Placement/mapping/membership interactions confirmed

- Phase 2 snapshot membership feeds GC through `snapshot_file`-derived snapshot
  roots and delete-simulation exclusions.
- Phase 3 logical/physical mapping feeds GC and repair through
  `physical_file`-rooted current-state reachability and refcount invariants.
- Phase 4 placement assumptions feed GC through chunk reachability,
  packed-block liveness, legacy-container liveness, and restore/verify safety
  expectations around bytes that must remain protected.

### Immediate blockers

None found.

## Phase 5 decision

The current reachability and GC eligibility contract is broad but reviewable.

No Phase 5 production or test change is required.

`v1.13.6` can proceed to SQLite/PostgreSQL schema and query parity review in
Phase 6.

Backend parity and test sufficiency remain intentionally deferred to Phases 6
and 7.
