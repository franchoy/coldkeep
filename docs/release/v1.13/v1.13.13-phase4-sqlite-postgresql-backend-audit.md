## 1. Audit purpose

This source-first audit establishes the exact SQLite and PostgreSQL backend
contract without confusing backend support, behavioral equivalence,
backend-specific capabilities, or product defaults. Source and current
authority were audited before tests and before documentation was edited.
Passing tests supplement source proof and cannot override a source defect.
No implementation, test, schema, migration, validator, version, or CI change
was made.

## 3. Backend architecture inventory

`internal/db/backend.go` detects SQLite and PostgreSQL from the driver. The
database package owns schema loading, migrations, placeholder-compatible SQL,
transaction helpers, affected-row guards, and conditional lock clauses.
SQLite configuration enables foreign keys and a busy timeout; PostgreSQL
configuration supplies pool and session timeout behavior. Catalog is built on
`database/sql` and deliberately uses `$n` placeholders accepted by both
drivers. Engine operations consume Catalog and lower services through the
same application composition path on both backends.

The complete operation inventory and classifications are in the
[backend capability matrix](v1.13.13-backend-capability-matrix.md). Evidence
strength and skip ownership are in the
[backend contract evidence matrix](v1.13.13-backend-contract-evidence-matrix.md).

## 4. Capability model

The audit applies four separate levels:

1. **Supported backend contract:** a production path has a real implementation,
   stable failure behavior, and appropriate evidence.
2. **Behavioral equivalence:** a shared claim produces equivalent meaning on
   both backends.
3. **Backend-specific capability:** a deliberate difference is explicit and
   fail closed rather than silently normalized.
4. **Product default:** repository layout and deployment mode, which do not
   determine whether a backend contract is implemented.

SQLite is a supported backend without already being the default portable
product. PostgreSQL is a required compatible backend without already being a
centralized multi-user product.

## 5. SQLite v1 claim

SQLite v1 scope includes architecture, schema/bootstrap/migrations, Catalog
contracts, Engine routes, relevant correctness behavior, snapshot and GC
planning, dry-run GC, verification, repair, and recovery. It does not include
the v2 repository-local default, one mutation-owner daemon workflow, or
clean-close portability product surface. Local source and tests prove the
supported contract within the explicit live-GC and later coordination bounds.

## 6. SQLite live-GC classification

The decision chain was authority, then source behavior, then contract tests:

- Phase 1 freezes SQLite backend correctness as v1 and SQLite-default local
  productization as v2.
- The reaffirmed v1.13.11 backend claim `BKC-014` explicitly defines SQLite
  live GC as rejected while retaining dry-run, and defines PostgreSQL live GC
  as the intentional backend-specific execution contract.
- `internal/maintenance/gc.go::acquireGCAdvisoryLock` permits SQLite dry-run
  and returns an explicit error before live execution; PostgreSQL obtains its
  dedicated advisory-lock session.
- `Engine.GarbageCollect` routes both modes through this production boundary.
  `TestGCDryRunAllowedOnSQLiteBackend`, `TestGCLiveRunFailsClosedOnSQLiteBackend`,
  and `TestGCLiveRefusedOnSQLite` prove planning success, explicit refusal,
  and absence of false success.

Therefore:

```text
SQLITE_LIVE_GC:
EXPLICIT_V2_PRODUCTIZATION_BOUND
```

This conclusion is not inferred merely from the future existence of
`coldkeepd`. It follows from current authority and the explicit current
backend contract. The Engine currently translates the refusal through its
stable operation-failure boundary rather than a distinct unsupported code;
that is recorded as maintenance evidence, not a new v1 backend root, because
the capability is explicit and fail closed.

## 7. PostgreSQL v1 claim

PostgreSQL compatibility remains mandatory through v1 and retained through
v2. It includes current schema/bootstrap and supported migrations, all shared
Catalog/Engine contracts, correctness-critical integration, transactions,
conditional row locks, cancellation, mutation cardinality, and the dedicated
live-GC advisory session. PostgreSQL server productization with networked,
multi-user behavior remains v3; that product boundary is not a compatibility
defect.

## 8. Schema bootstrap parity

The current schema version was derived mechanically rather than copied from
the plan. These independent sources agree on version `16`:

- `internal/db/migrations.go` sets `requiredPostgresSchemaVersion = 16`;
- the effective SQLite migration endpoint installs version 16;
- `db/schema_sqlite.sql` normalizes to version 16; and
- `db/schema_postgres.sql` updates the current schema to version 16.

Fresh SQLite runs the embedded SQLite schema and the idempotent migration
pipeline. PostgreSQL requires an initialized schema unless explicitly
configured for auto-bootstrap, then applies the embedded PostgreSQL schema.
Both reach semantic version 16. Bootstrap policy differs intentionally; the
current version does not.

## 9. Migration parity

Supported entry paths were derived from migration dispatch and executable
fixtures, not from every historical DDL fragment. SQLite migrations cover the
reachable pre-v6 physical mapping shape and subsequent snapshot, chunker,
repository-configuration, storage-block, transform, compression-metadata, and
unique-offset generations. PostgreSQL auto-migration applies the current
schema transactionally to older supported versions, with executable legacy
v5/pre-v6, v7, and v11 fixtures.

No supported path was found that reaches version 16 with a weaker frozen
constraint or metadata invariant. Historical shapes not reachable through a
supported migration are maintenance history rather than synthetic blockers.
Details are in the
[schema/migration parity matrix](v1.13.13-schema-migration-parity-matrix.md).

## 10. Fresh/upgraded equivalence

The parity rule is semantic, not textual. Fresh and supported-upgraded
repositories converge on the required tables, keys, uniqueness, foreign-key
actions, defaults, storage placement, configuration metadata, and version.
The version changes only after the migration body succeeds, migrations are
idempotent, duplicate storage offsets fail closed before the v16 uniqueness
claim, and transactional failures preserve the earlier valid state. No
reachable fresh/upgraded divergence creates a new Phase 4 finding.

## 11. SQL dialect isolation

Shared SQL deliberately uses `$n` parameters because both current drivers
accept them. Backend helpers isolate `FOR UPDATE`, `NOWAIT`, and
`SKIP LOCKED`; SQLite omits unsupported clauses while PostgreSQL appends them.
Conflict/upsert and `RETURNING` usage were traced through both schemas and
tests. SQLite pragmas and PostgreSQL session settings remain configuration,
not leaked Engine contracts.

One unisolated semantic difference remains: `Catalog.ListSnapshots` uses
`label LIKE $2`. SQLite default `LIKE` matches ASCII case-insensitively, while
PostgreSQL `LIKE` is case-sensitive. That production difference is
`P4-BE-001`.

## 12. Transaction semantics

Shared mutations use explicit transactions, rollback-on-error, checked
commit, and fail-closed required-row cardinality. The cross-backend transaction
contract exercises commit and rollback. PostgreSQL supplies server-side row
lock behavior; SQLite serializes through its database/file locking model and
omits unsupported row-lock clauses. Equivalent outcomes are required where
the operation is shared, not identical lock implementations.

## 13. Row-locking semantics

`FOR UPDATE`, `NOWAIT`, and `SKIP LOCKED` are explicit PostgreSQL capabilities.
Tests prove server-observed acquisition, `55P03` refusal, deterministic skipped
rows, cancellation, and lock release. SQLite omission is deliberate and
bounded; it is not presented as PostgreSQL-equivalent row locking. Phase 5
retains repository-coordination ownership.

## 14. G6 backend equivalence

`Catalog.LoadGCPlanMetadata` loads protected snapshot metadata, snapshot roots,
and current roots in one compound `UNION ALL` statement and validates the
result before returning it. SQLite WAL race tests prove five mutation cases
observe one coherent statement. PostgreSQL Read Committed assigns one MVCC
snapshot per statement; because G6 is one statement, the source shape meets
that semantic rule. Exact-Phase-4 hosted execution of
`TestGCPlanCompoundReadIsStatementCoherentAcrossBackends` supplies the required
PostgreSQL runtime evidence. Neither SQL shape nor a generic green job alone
is treated as sufficient.

## 15. Snapshot equivalence

Create, delete, restore, graph, lookup, list, stats, diff, and selector routes
exist on both backends and share transaction and typed Engine behavior. The
new label-filter root prevents an aggregate equivalence claim for snapshot
listing, even though lifecycle operations and tested same-case queries remain
equivalent.

## 16. Placement/restore-plan equivalence

Catalog placement and restore-plan contracts use the same tagged packed/legacy
meaning on both backends and are adopted by all production restore routes.
Current source shows no backend-specific alternate planner. Restore execution
still carries `P3-COR-001` and `P3-COR-002`; Phase 4 refines their scope to
both backends and does not duplicate them.

## 17. Verify equivalence

System/repository and file verification use shared SQL and payload readers.
The packed/mixed file-deep omission in `P3-COR-003` affects SQLite and
PostgreSQL through the same legacy-only query root. This backend audit records
the two-backend scope without creating a `P4-BE-*` duplicate.

## 18. Recovery/repair equivalence

Recovery and repair share production implementation, transactions, topology
checks, affected-row guards, and Engine error translation. SQLite executes
locally. PostgreSQL source routes and named backend contracts supplement the
exact-head hosted execution. No backend-only recovery or repair root was
found.

## 19. Engine behavioral neutrality

All 25 Engine methods retain one neutral request/result surface. Backend
selection remains in composition and lower services. Engine does not expose a
SQLite/PostgreSQL result type or branch caller-visible success by backend.
Explicit capability refusal for SQLite live GC is returned as an error, not a
false successful result. Snapshot label filtering inherits `P4-BE-001` from
Catalog.

## 20. Catalog behavioral neutrality

All 13 Catalog methods use neutral DTOs and shared interfaces. Graph,
placement, restore-plan, and GC-plan ownership is unchanged. The SQL layer is
mostly behaviorally neutral, but neutral types alone do not prove semantic
equivalence: `ListSnapshots` demonstrates the exact gap through backend-native
`LIKE` behavior.

## 21. Error equivalence

Catalog typed errors and deterministic Engine translation preserve invalid
argument, not found, conflict, invariant, cancellation, and operation-failure
meaning across backends for the claimed contracts. Raw driver details are
wrapped rather than exposed as a separate public contract. `P2-ARCH-001`
remains unchanged for five aggregate Catalog methods lacking the stable typed
boundary. It is not a new backend finding.

## 22. Cancellation/timeouts

Database operations receive caller contexts; transactions roll back on
cancellation. PostgreSQL lock-wait cancellation and session cleanup have named
tests. SQLite busy timeout is configured and shared operations propagate
context failures. The audit does not claim identical timing or server error
codes, only equivalent cancellation meaning within each backend's mechanics.

## 23. ID/order/type/time semantics

Integer IDs and counts are scanned without float projection; nullable values
use explicit SQL/null handling; booleans are normalized by the drivers; and
timestamp values are converted through common contract types. Queries that
promise order include explicit sort keys and tie-breakers. Natural text
comparison is not assumed equivalent across database collations. The concrete
unbounded difference discovered is the label `LIKE` predicate in
`P4-BE-001`.

## 24. Packed/legacy/mixed matrix

Placement, restore, snapshot retention, GC planning, recovery, containers,
and system verification support legacy-only, packed-only, and mixed
repositories through shared implementations and schemas. PostgreSQL live GC
and SQLite dry-run consume the same authoritative plan. `P3-COR-003` remains
the one known packed/mixed file-deep verification root and is not counted as a

## 25. Repository configuration

## 28. Findings

### `P4-BE-001` — snapshot label filtering has backend-dependent case semantics

- **Requirement:** `V1R-BE-003`.
- **Backend/operation:** both backends; Catalog `ListSnapshots`, Engine
  `SnapshotList`.
- **Source:** `internal/catalog/snapshots.go` uses `label LIKE $2` in both its
  limited and unlimited production queries.
- **Divergence:** SQLite default `LIKE` matches ASCII case-insensitively;
  PostgreSQL `LIKE` is case-sensitive. A label `Alpha` matches `%alpha%` on
  SQLite and does not match on PostgreSQL.
- **Evidence gap:** existing dual-backend tests use same-case labels and
  filters. Historical evidence explicitly excluded label-case behavior, which
  preserves honesty but does not make the shared ambiguity an intended
  capability.
- **Consequence:** the same supported Engine request silently returns a
  different snapshot set by backend.
- **Severity:** v1 blocker; this is not product-default or v3 server scope.
- **Remediation:** required, with disposition in Phase 6; no fix is designed or
  implemented here.
- **Relationship:** distinct from `P2-ARCH-001` and all `P3-COR-*` roots.

No other new backend root was found. Backend-independent restore and verify
defects remain their existing Phase 3 identities.
