- Read-side CLI behavior must remain backend-agnostic at the public contract
  layer.
- Backend selection remains a lower-layer concern driven by the provided
  `*sql.DB`, not a read-side CLI contract distinction.
- SQLite compatibility must remain preserved.
- PostgreSQL compatibility must remain preserved.
- No ownership review in `v1.13.4` should imply a backend-specific result shape
  or package dependency rewrite unless a real correctness issue is discovered.

## Stats backend review

### Current production path

`runStatsCommand` validates CLI input, resolves trace options, then routes
through the engine seam into `DefaultEngine.Stats`, which delegates to
`observability.Service.Stats`. Concrete aggregation remains observability-owned
and reaches maintenance/database-backed reads beneath that seam.

### Backend-facing packages touched

- `internal/engine`
- `internal/observability`
- `internal/maintenance`
- `internal/db`

### SQLite/PostgreSQL compatibility evidence

- `internal/engine/backend_compat_test.go` keeps engine public request/result
  surfaces backend-neutral
- `internal/observability/equivalence_phase7_test.go` protects stats behavior
  across empty, large, churned, and multi-snapshot repository states
- `internal/observability/cross_consistency_test.go` checks stats/inspect
  agreement on repository state
- `internal/maintenance/stats_test.go` and observability stats tests protect
  empty-repository and aggregation behavior at the SQLite-backed package level

### Package dependency-direction finding

`stats` remains engine-mediated over observability. That dependency direction
is still acceptable for `v1.13.x`, and no backend-specific behavior leak was
found at the CLI or engine contract surface.

## Inspect backend review

### Current production path

`runInspectCommand` validates the public target set, numeric IDs, limits, and
trace options, then calls the direct `runObservabilityInspectPhase` path.
Production `inspect` still bypasses engine and uses `observability.Service`
directly for DB and relation expansion work.

### Backend-facing packages touched

- `internal/observability`
- `internal/db`

### SQLite/PostgreSQL compatibility evidence

- `internal/observability/inspect_test.go` exercises repository, file,
  snapshot, chunk, and container inspect behavior against migrated SQLite state
- `internal/observability/service_test.go` protects service-level read behavior
  and non-mutating assumptions
- `internal/engine/backend_compat_test.go` still protects the inactive engine
  request/result surface from backend-specific field leakage
- Phase 7 CLI guard tests protect the public inspect target set and output
  families independently from backend naming

### Package dependency-direction finding

`inspect` remains a direct `CLI -> observability` seam. That dependency
direction remains acceptable for `v1.13.x`. The repo does not show evidence
that PostgreSQL compatibility requires inserting engine into the live path for
this release.

## Snapshot show backend review

### Current production path

`runSnapshotShowCommand` validates CLI flags and snapshot ID, parses the query,
then assembles the result from mixed seams:

- metadata through `getSnapshotPhase`
- file listing through `listSnapshotFilesPhase` -> `snapshot.ListSnapshotFiles`
- stats/counts through `snapshotStatsPhase`
- success JSON assembly in the CLI

The engine implementation mirrors a similar mixed dependency pattern:
`DefaultEngine.SnapshotShow` uses catalog metadata lookup, snapshot package file
listing, and snapshot stats lookup over the same provided `*sql.DB`.

### Backend-facing packages touched

- `internal/engine`
- `internal/catalog`
- `internal/snapshot`
- `internal/db`

### SQLite/PostgreSQL compatibility evidence

- `internal/catalog/backend_contract_backends_test.go` is the strongest
  dual-backend contract anchor for catalog-backed snapshot metadata behavior
- that suite always runs SQLite and runs PostgreSQL when `COLDKEEP_TEST_DB` is
  set
- PostgreSQL coverage provisions a fresh temporary database per test, applies
  schema with `db.EnsurePostgresSchema`, terminates live connections during
  cleanup, and drops the temporary database to keep subtests isolated
- `internal/snapshot/snapshot_test.go` protects snapshot file listing, missing
  snapshot handling, query behavior, and stats-sensitive paths at the package
  layer
- `internal/engine/backend_compat_test.go`, engine snapshot tests, CLI
  preservation tests, and routing tests protect the backend-neutral public seam
  and count behavior

### Package dependency-direction finding

`snapshot show` remains mixed `CLI/engine/catalog/snapshot` ownership. That
dependency direction is acceptable for `v1.13.x` as a documented transitional
seam. No backend correctness bug was found that justifies consolidating these
layers in Phase 8.

## Snapshot diff backend review

### Current production path

`runSnapshotDiffCommand` validates IDs, filter, and query input, then chooses
between:

- summary fast path through `diffSnapshotSummaryPhase`
- detailed/general path through `diffSnapshotsPhase`

The engine continues to own the routing split:

- summary mode uses `snapshot.DiffSnapshotsSummarySQL`
- detailed mode uses `snapshot.DiffSnapshots`

CLI still owns `--filter` post-processing, matched-versus-total projection, and
success JSON assembly.

### Backend-facing packages touched

- `internal/engine`
- `internal/snapshot`
- `internal/db`

### SQLite/PostgreSQL compatibility evidence

- `internal/snapshot/snapshot_test.go` directly protects
  `DiffSnapshotsSummarySQL`, `DiffSnapshots`, missing snapshot behavior, empty
  diff behavior, deterministic ordering, and query narrowing behavior
- `internal/observability/equivalence_phase7_test.go` checks summary/detailed
  parity across multiple seeded scenarios
- CLI preservation tests, routing tests, and Phase 7 guard tests protect
  summary-versus-detailed output and matched-versus-total count behavior
- `internal/engine/backend_compat_test.go` continues to protect backend-neutral
  engine public type naming

### Package dependency-direction finding

`snapshot diff` remains mixed `CLI/engine/snapshot` ownership. That dependency
direction is acceptable for `v1.13.x`. The current evidence supports preserving
the split rather than rewriting it in a backend review phase.

## Existing backend protection

The current repo already provides meaningful backend protection for the
read-side seams reviewed in `v1.13.4`.

Key anchors include:

- `internal/catalog/backend_contract_backends_test.go`
  - dual-backend catalog contract suite
  - SQLite always runs
  - PostgreSQL runs when `COLDKEEP_TEST_DB` is set
  - PostgreSQL path uses temporary per-test databases and explicit schema setup
- `internal/engine/backend_compat_test.go`
  - protects engine public types from backend-specific exported fields
  - confirms engine requires a caller-provided `*sql.DB`
- `internal/observability/inspect_test.go`
  - package-level inspect behavior coverage on migrated SQLite state
- `internal/observability/equivalence_phase7_test.go`
  - cross-scenario parity checks for stats, inspect, snapshot stats, and
    snapshot diff
- `internal/observability/cross_consistency_test.go`
  - cross-surface consistency checks for stats and inspect
- `internal/snapshot/snapshot_test.go`
  - file listing, snapshot stats, summary SQL diff, and detailed diff coverage
- CLI preservation, routing, taxonomy, and Phase 7 guard tests
  - protect public output contracts independently from backend naming or helper
    internals

## Package dependency-direction findings

- `stats` remains engine-mediated over observability.
- `inspect` remains direct `CLI -> observability`.
- `snapshot show` remains mixed `CLI/engine/catalog/snapshot`.
- `snapshot diff` remains mixed `CLI/engine/snapshot`.
- backend selection is still intentionally outside the read-side command
  contract and is supplied through the provided DB connection
- no backend rewrite, backend-specific dependency inversion, or package
  consolidation is justified by the current evidence

## Test decision

Phase 8 adds no new tests.

Current coverage is already sufficient to support a docs-only decision because:

- backend-neutral engine public-type protections already exist
- dual-backend catalog contract coverage already exists
- snapshot package behavior is already protected at the package layer
- Phase 7 already added the narrow CLI guard tests most relevant to public
  contract preservation

that should be handled as a targeted follow-up rather than widened speculatively
in Phase 8.
