# Coldkeep v1.13.8 Scope

**Release:** `v1.13.8 — Restore / Remove Contract Split and Stored-Path Boundary`
**Status:** In progress
**Branch:** `release/v1.13.8`
**Starting baseline:** `3813dc32f85c72641dd516dfa41c439d2b4c916c`

## Goal

Make restore and remove contracts honest and suitable for future daemon/API
callers by separating:

- by-ID restore from stored-path restore;
- by-ID logical removal from stored-path mapping removal;
- repository-stored paths from restore destinations and payload locations.

The release will route mature stored-path restore/remove behavior through
dedicated engine boundaries while preserving current observable behavior.

## Phase 0 inherited corrective baseline

Before boundary work begins, Phase 0 must:

- close the v1.13.7 release records;
- reconcile source version and active documentation;
- correct release-train ownership and numbering drift;
- add a release-gate version assertion;
- fix migration behavior that can resurrect a valid zero-reference logical file;
- prove the correction on SQLite and PostgreSQL;
- freeze a green corrective baseline.

## Required final contract

- `Engine.Restore` represents by-ID restore only.
- `Engine.Remove` represents by-ID logical deletion only.
- stored-path restore has a dedicated engine method and request/result.
- stored-path removal has a dedicated batch-capable engine method and request/result.
- stored-path CLI operations route through those methods.
- CLI owns input reading and presentation.
- engine/domain layers own validation and mutation semantics.

## Release-wide invariants

1. Restore never mutates catalog state.
2. Restore never writes outside the intended destination.
3. By-ID removal and stored-path unlink remain distinct.
4. Stored-path unlink removes one current mapping and maintains ref count.
5. `ref_count=0` with no physical mapping is valid.
6. Migration must not resurrect removed mappings.
7. Genuine legacy repositories still receive compatibility mappings.
8. Payload deletion remains reachability/GC-owned.
9. Snapshot-retention refusal behavior remains unchanged.
10. Human output, JSON output, ordering, and exit behavior remain compatible.
11. SQLite and PostgreSQL preserve equivalent catalog meaning.
12. PostgreSQL remains the normal local runtime backend.

## In scope

- v1.13.7 closure and inherited correction work;
- version and active-documentation reconciliation;
- zero-reference migration correction;
- restore/remove contract inventory;
- stored-path taxonomy;
- by-ID request/result narrowing;
- dedicated stored-path restore engine boundary;
- dedicated stored-path remove engine boundary;
- CLI routing migration;
- destination safety;
- ref-count, reachability, snapshot-retention, and backend guards;
- final boundary audit;
- v1.13.9 handoff.

## Out of scope

- snapshot mutation routing;
- repair/recovery routing;
- snapshot-retention policy redesign;
- GC redesign;
- payload-deletion redesign;
- normal SQLite runtime;
- backend-default transition;
- repository move/copy commands;
- storage or repository format changes;
- schema-version bump unless a newly proven requirement makes it unavoidable;
- daemon, API, UI, NAS, cloud, distributed, or multi-user work.

## Release workflow

All phases remain on `release/v1.13.8`.

One pull request is opened only after:

- every phase is complete;
- the complete Profile A gate passes;
- live PostgreSQL validation passes;
- the built CLI reports exactly `1.13.8`;
- the release branch is clean and pushed.
