# Coldkeep v1.13.8 Scope

**Release:** `v1.13.8 — Restore / Remove Contract Split and Stored-Path Boundary`
**Status:** Released
**Branch:** `release/v1.13.8`
**Starting baseline:** `3813dc32f85c72641dd516dfa41c439d2b4c916c`

## Goal

Make restore and remove contracts honest and suitable for future daemon/API
callers by separating:

- by-ID restore from stored-path restore;
- by-ID logical removal from stored-path mapping removal;
- repository-stored paths from restore destinations and payload locations.

The release will route mature stored-path restore/remove behavior through
dedicated engine boundaries while preserving current observable behavior.

## Phase 0 inherited corrective baseline

Before boundary work begins, Phase 0 must:

- close the v1.13.7 release records;
- reconcile source version and active documentation;
- correct release-train ownership and numbering drift;
- add a release-gate version assertion;
- fix migration behavior that can resurrect a valid zero-reference logical file;
- prove the correction on SQLite and PostgreSQL;
- freeze a green corrective baseline.

## Required final contract

- `Engine.Restore` represents by-ID restore only.
- `Engine.Remove` represents by-ID logical deletion only.
- stored-path restore has a dedicated engine method and request/result.
- stored-path removal has a dedicated batch-capable engine method and request/result.
- stored-path CLI operations route through those methods.
- CLI owns input reading and presentation.
- engine/domain layers own validation and mutation semantics.

## Release-wide invariants

1. Restore does not persistently mutate logical identity, physical mappings,
   logical ref counts, snapshots, file-chunk ownership, or chunk
   live-reference ownership.
2. Restore may temporarily mutate `chunk.pin_count` and must restore pin state
   on success and failure.
3. Restore never writes outside the intended destination.
4. By-ID removal and stored-path unlink remain distinct.
5. Stored-path unlink removes one current mapping and maintains ref count.
6. `ref_count=0` with no physical mapping is valid.
7. Migration must not resurrect removed mappings.
8. Genuine legacy repositories still receive compatibility mappings.
9. Payload deletion remains reachability/GC-owned.
10. Snapshot-retention refusal behavior remains unchanged.
11. Human output, JSON output, ordering, and exit behavior remain compatible.
12. SQLite and PostgreSQL preserve equivalent catalog meaning.
13. PostgreSQL remains the normal local runtime backend.
