# Coldkeep v1.13.5 Read-Side Guard Follow-up

**Release:** `v1.13.5 — Release Record Closure and Engine-Level Invariant Ownership`  
**Phase:** Phase 6  
**Status:** Complete  
**Branch:** `release/v1.13.5`

## Purpose

This document reviews the read-side guard tests and ownership decisions added
in `v1.13.4` and decides whether any documented count-field, JSON-envelope,
taxonomy-invisibility, or public-target guard remains underprotected.

This phase performs no ownership migration and no behavior change.

- `stats`
- `inspect`
- `snapshot show`
- `snapshot diff`

- read-side JSON error-envelope ownership
- public inspect target set

- count-field stability
- current test protection

## v1.13.4 guard baseline

The active `v1.13.4` guard baseline lives in
`cmd/coldkeep/read_side_dependency_direction_test.go` and consists of:

- `TestReadSideJSONOwnershipFamiliesRemainDistinct`
- `TestReadSideJSONErrorsRemainCLIEnvelopeOwned`
- `TestInspectPublicTargetsRemainDocumentedSet`
- `TestReadSideOutputDoesNotLeakTaxonomyHelperNames`

What these tests protect:

- `TestReadSideJSONOwnershipFamiliesRemainDistinct`
  - preserves renderer-envelope success JSON for `stats` and `inspect`
  - preserves CLI-envelope success JSON for `snapshot show` and `snapshot diff`
  - guards the family split without freezing every field of every payload
- `TestReadSideJSONErrorsRemainCLIEnvelopeOwned`
  - preserves CLI-owned JSON error envelopes for representative read-side
    failures
  - guards `status`, `error_class`, `exit_code`, and nested `error` structure
    without freezing exact human phrasing
- `TestInspectPublicTargetsRemainDocumentedSet`
  - preserves the public inspect target set
  - preserves the `logical-file` alias
  - preserves `physical-file` remaining unsupported publicly
- `TestReadSideOutputDoesNotLeakTaxonomyHelperNames`
  - preserves the public/private taxonomy boundary across representative
    success and error payloads
  - stays broad enough to catch likely leaks without forcing one exact payload
    shape

These tests intentionally protect ownership families and public boundaries
without freezing every incidental field, implementation helper, or exact error
string.

## Stats guard review

Current ownership:

- success JSON remains renderer-envelope owned through
  `internal/cli/render.JSONRenderer.RenderStats`
- human output remains renderer-owned
- public JSON error rendering remains CLI-owned

Existing guard coverage:

- `TestReadSideJSONOwnershipFamiliesRemainDistinct` verifies that `stats`
  success JSON uses the renderer envelope family and does not expose CLI
  success-envelope fields such as `status` or `command`
- `cmd/coldkeep/read_side_cli_preservation_test.go` verifies representative
  `stats` JSON behavior
- `cmd/coldkeep/main_test.go` verifies renderer-envelope fields such as
  `generated_at_utc` and `meta`
- renderer and observability tests protect the deeper success-shape and result
  behavior below the CLI

Additional Phase 8 guard needed:

- no

Decision:

- current `stats` renderer-envelope guard coverage is already sufficient for
  `v1.13.5`
- adding another guard here would mostly duplicate existing renderer-envelope
  and CLI-preservation coverage

## Taxonomy/helper invisibility review

Currently protected internal names:

- internal helper and taxonomy terminology is guarded broadly rather than by a
  short allowlist
- the existing review baseline explicitly protects internal-only
  `EntityPhysicalFile` and public `physical-file` rejection
- the current suite also preserves the public `logical-file` alias

Public/private boundary:

- public read-side output should stay contract-oriented
- internal helper names, unsupported/deferred terminology, and private
  taxonomy concepts should not surface in success or error payloads

Whether the current guard is broad enough:

- yes
- `TestReadSideOutputDoesNotLeakTaxonomyHelperNames` checks representative
  renderer-envelope success, CLI-envelope success, and CLI error paths
- `cmd/coldkeep/read_side_cli_preservation_test.go` also includes no-taxonomy
  leak assertions on specific surfaces
- this is broad enough to catch likely accidental leaks without becoming
  brittle around harmless wording changes

Additional Phase 8 guard needed:

- no

Decision:

- the current taxonomy/helper invisibility guard is acceptable for `v1.13.5`
- no extra Phase 8 guard is justified unless later review finds a specific
  currently unprotected public leak path

## Findings

### Stable enough for v1.13.5

- The `v1.13.4` guard baseline still protects the key success-envelope family
  split between renderer-owned `stats` / `inspect` and CLI-owned
  `snapshot show` / `snapshot diff`.
- CLI-owned read-side JSON error envelopes are still guarded distinctly from
  success-envelope ownership.
- The public inspect target set, the `logical-file` alias, and the internal
  `physical-file` boundary are already explicitly protected.
- Snapshot-show and snapshot-diff count fields already have direct CLI output
  assertions in existing tests.

### Transitional but acceptable

- `stats` and `inspect` still use renderer-owned success JSON while the CLI
  owns error envelopes.
- `snapshot show` remains a mixed ownership seam.
- `snapshot diff` remains a split ownership seam with CLI-owned summary and
  count projection behavior.
- These seams remain transitional, but the current guard coverage is adequate
  for this release.

### Candidate Phase 8 guard gaps

- None identified from the current repo evidence.

### Explicitly not needed

- An additional snapshot-show count-field guard is not needed because
  `matched_file_count` and `total_snapshot_file_count` already have direct CLI
  assertions.
- An additional snapshot-diff count-field guard is not needed because
  `matched_entry_count` and `total_diff_entry_count` already have direct CLI
  assertions.
- An additional summary-mode ownership guard is not needed because `entries`
  omission and `summary_mode` behavior are already directly asserted.
- An additional generic inspect-target guard is not needed because the
  documented target set and `physical-file` exclusion are already explicitly
  covered.
- A broader taxonomy-helper-name guard is not needed because the current
  representative success and error checks are already wide enough without
  becoming brittle.

## Phase 6 decision

The `v1.13.4` read-side guard baseline is acceptable for `v1.13.5`.
No ownership migration is needed.
No Phase 6 production or test change is required.
Any additional guard tests should be deferred to Phase 8 and limited to
documented narrow gaps if a later backend-neutral review still finds one.
