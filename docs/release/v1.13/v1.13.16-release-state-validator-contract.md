# v1.13.16 Release-State Validator Contract

**Release:** v1.13.16 — Snapshot Retention Integrity, Observability Truth, and Final v1.x Closure
**Status:** Active
**Branch:** release/v1.13.16

**Merge-complete phase:** 16
**Tag/publication phase:** 18
**Post-publication closure phase:** 19
**Lifecycle declaration model:** immutable-transition-v1
**Canonical repository:** franchoy/coldkeep

## Topology

Numeric lifecycle phases are contiguous from Phase 0 through Phase 19. Merge,
publication, and closure boundaries are ordered but need not be consecutive;
closure must be the last numeric phase. Phase 17 is the separate read-only
publication-authorization boundary between exact-main certification and
publication execution.

Phase 13A/13B/13C and Phase 19A/19B/19C/19T are level-three operational
subdivisions, not numeric lifecycle phases.

## Progression

- Development has exactly one `Next` phase strictly before Phase 16.
- Pre-release has exactly Phase 16 `Next`.
- Merged-not-tagged and tagged allow exactly one `Next` phase strictly after
  Phase 16 and at or before Phase 18.
- Post-release-pending-closure has exactly Phase 19 `Next`.
- Post-release-closure-candidate requires every numeric phase Complete while
  preserving the closure-pending gate. `post-release-closed` is not a valid
  `immutable-transition-v1` projection; Phase 19T alone owns that terminal
  transition.

All earlier consecutive lifecycle contracts remain valid.

## Immutable transition states

The two declaration fields are one versioned opt-in. Missing both preserves
legacy behavior. A partial, duplicate, empty, malformed, unsupported, or
contradictory declaration fails CKRS019 and cannot fall back to legacy
interpretation.

- `pre-release` is the immutable release-branch candidate at Phase 16 Next.
- `merged-pending-final-main-certification` requires a normal two-parent main
  merge whose first parent is the previous main head and whose tree is exactly
  the second-parent candidate tree. It is not proof of authorization or CI.
- `tagged-pending-tag-certification` requires the exact annotated tag to peel
  to that candidate-derived merge artifact. It is not proof of tag authority,
  tag-native CI, or publication.
- `post-release-pending-closure` requires the annotated tag as a strict
  ancestor, Phase 19 Next, an allowed closure context, and the exact
  closure-pending gate.
- `post-release-closure-candidate` requires the same tag ancestry, context,
  and gate with all numeric phases Complete. It remains structurally
  conditional pending protected closure certification and Phase 19T.

The existing `merged-not-tagged` and `tagged` states remain available only for
their pre-existing reconciled predicates. The validator never promotes a
local artifact to an authorization, certification, publication, or terminal
closure fact.

## Context contract

Local main evidence is `LOCAL_ARTIFACT_ONLY`: exactly two ordered parents,
first-parent ancestry into the immutable second parent, and a merge tree equal
to the second-parent tree. A hosted main push additionally requires a readable
`push` payload, canonical repository, exact `refs/heads/main`, consistent
`GITHUB_SHA`, `before`, `after`, repository and ref, and non-created,
non-deleted, non-forced semantics.

A release PR accepts either the exact declared head checkout or GitHub's
synthetic two-parent merge checkout. The payload repository, base/head
repositories, refs and object IDs must agree with the environment and actual
Git objects. Fork, recovery, wrong-base, wrong-head, absent-object, or
conflicting contexts fail closed.

For tag creation, the annotated tag object ID, peeled target commit, event
`after`, and checked-out `GITHUB_SHA` are separately checked facts. The event must be a
canonical-repository tag push with zero `before`, created true, deleted and
forced false, and the documented commit-valued `after` and `GITHUB_SHA` equal
HEAD while the exact tag ref remains an annotated tag object that peels to
HEAD. Local tag presence authenticates neither publication nor authority.

## Gate projections

The exact candidate status `Passed — pre-merge prerequisites complete` may be
projected only by `pre-release`,
`merged-pending-final-main-certification`, and
`tagged-pending-tag-certification` when their structural predicates pass. The
closure states require exactly `Passed and released — closure pending` and a
nonempty verdict under the closure-pending grammar. Reconciled legacy states
retain their prior gate rules.

## Machine-readable output

JSON output always keeps `state` equal to `artifact_state` and emits:

```text
authorization_status=NOT_EVALUATED_BY_VALIDATOR
certification_status=PENDING_EXTERNAL_EVIDENCE
```

`evidence_scope` identifies only the structural context actually inspected.
`outstanding_obligations` is ordered deterministically as applicable:

1. `phase15-protected-merge-authorization`
2. `protected-main-merge`
3. `final-main-certification`
4. `phase17-tag-authorization`
5. `tag-certification`
6. `publication-authorization`
7. `publication-verification`
8. `protected-closure-certification`
9. `phase19t-terminal-audit`

An explicit `--state` is an expected structural state, not a permission. It
runs the same declaration, progression, context, tag and gate checks as auto
mode. A successful local or fixture result does not consume any listed
obligation or assert that a future operation occurred.

## Bounded diagnostic capture

`--diagnostic-json PATH` opts one invocation into
`coldkeep-release-state-diagnostic/v1`. Omitting the option preserves the
ordinary interface. Capture is observational and non-authorizing: it does not
change accepted inputs, validation order, ordinary stdout/stderr, exit status,
artifact state, authorization status, certification status, or outstanding
obligations. In particular, a synthetic PR still requires a present
`merge_commit_sha` whose value is null or exactly the checked-out commit,
followed by the existing ordered-parent and tree checks.

The exact top-level object contains only:

```text
schema
created_at_utc
validator
attribution
event_snapshots
evaluations
capture
```

`validator` records requested/resolved state, original result and exit code,
ordered unique CKRS rule codes, the fixed non-authorizing status vocabulary,
the actual checkout commit/tree, and a two-entry `sources` array. Each source
entry names one loaded implementation path, the checkout's Git blob when
available, the Git blob calculated from the measured bytes, SHA-256 and byte
count of those startup bytes, loaded-path agreement, and measured/Git-blob
agreement. Dirty measured bytes are never described as the checkout blob.

`attribution` has fixed repository, run ID, run attempt, job, workflow and
event-name fields. `event_snapshots` is ordered by actual read. Each snapshot
has an integer ID, the fixed `GITHUB_EVENT_PATH` selector, a safe basename
representation and path-string hash, derived presence/readability facts,
byte count and SHA-256 of the exact bytes parsed when readable, null configured
size limit with `NOT_EVALUATED`, UTF-8/JSON statuses, top-level shape, and the
fixed repository/PR/base/head/merge projection. A hash identifies bytes; it
does not recover excluded fields or authorize the payload.

Every `evaluations` entry has an integer ID/sequence, fixed site, nullable
snapshot reference, fixed runtime context, aggregate result, nullable first
rejecting predicate and ordered predicate records. Predicate results are
exactly `PASS`, `FAIL`, `NOT_EVALUATED`, or `UNAVAILABLE`. Each record contains
its stable ID, measured source path/SHA-256/line, input-source category,
required relation, result and fixed-shape sanitized observation. Conditions
after a rejecting short circuit are `NOT_EVALUATED`; direct-head success leaves
all synthetic-only predicates `NOT_EVALUATED`. Distinct reads retain distinct
snapshot IDs even when their hashes match.

The diagnostic refactor preserves these prior operations in the same order:

| Prior decision | Instrumented equivalent |
|---|---|
| GitHub Actions/event/ref/head/base/repository/runtime-SHA compound prefix | sequential predicates `pr.env.*`, returning at the same first false condition |
| one event-file read and object parse | one byte snapshot parsed by that evaluation, with `pr.event.*` observations |
| PR object, number/ref and repository checks | sequential `pr.payload.pull_request`, `number`, `number_ref`, and `repository` predicates |
| base/head ref, repository, SHA and object checks | sequential `pr.payload.*` then `pr.git.base_object`/`head_object`, retaining Git-probe order |
| direct-head early return | `pr.route=direct-head`, followed by the same immediate success |
| required merge member | `pr.payload.merge_member` |
| null-or-exact-checkout merge value | `pr.payload.merge_value`; parent probing retains its pre-existing placement |
| ordered parents and tree equality | `pr.git.parents` then `pr.git.tree`, with the same short circuit |

Release-push probing already precedes PR probing in the lifecycle scope
function and reads the selected event before its Boolean expression. Diagnostic
mode preserves and records that separate read as a `*-release-push` evaluation;
it does not cache, merge, or remove the later strict-PR read.

Only validated canonical identity fields are emitted verbatim. Unexpected
strings, shapes, names and paths use a closed category/type/length/SHA-256
representation with no raw value. The record excludes the whole event,
environment and GitHub context; PR title/body; actor/contact objects; tokens,
cookies, authorization/signature headers; remote URLs; runner user/home;
arbitrary exception text and filesystem paths. It performs zero network
lookups. `capture.complete=false` and its closed incomplete-reason list prevent
an attribution or recorder failure from masquerading as a complete trace.

Unknown keys are not part of schema v1. Nested objects and arrays have these
exact key sets:

```text
validator = requested_state, resolved_state, result, exit_code, rule_codes,
            authorization_status, certification_status, checkout_commit,
            checkout_tree, sources
source = path, loaded_path_match, git_blob, measured_git_blob,
         measured_sha256, matches_git_blob, bytes
attribution = repository, run_id, run_attempt, job, workflow, event_name
event_snapshot = id, selector, path_basename, path_sha256, present, readable,
                 size_bytes, content_sha256, configured_size_limit_bytes,
                 size_limit_status, utf8_status, json_status,
                 top_level_shape, projection
projection = repository, number, pull_request_shape, base_shape, head_shape,
             base_ref, base_sha, base_repository, head_ref, head_sha,
             head_repository, merge_member, merge_type, merge_value
evaluation = id, site, sequence, event_snapshot_id, runtime_context, result,
             first_rejecting_predicate, predicates
runtime_context = github_actions, event_name, full_ref, short_ref, head_ref,
                  base_ref, repository, runtime_sha, actual_checkout_commit,
                  actual_branch, checkout_parents, checkout_tree,
                  payload_head_tree, object_availability
object_availability_entry = role, sha, available
predicate = id, source_path, source_sha256, source_line, input_source,
            required_relation, result, observed
sanitized_identity = category, type, length, sha256, value
capture = complete, incomplete_reasons, same_process, network_lookups,
          whole_event_included, whole_environment_included, non_authorizing
```

`result` is `pass`, `failed`, or `error` in `validator`; evaluation/predicate
results use the uppercase diagnostic enum. Parse statuses use `PASS`, `FAIL`,
`NOT_EVALUATED`, or `UNAVAILABLE` where applicable. Shapes use only JSON type
names plus `unavailable`; merge membership uses `present`, `missing`, or
`unavailable`. Incomplete reasons are limited to source attribution, event
snapshot, predicate recording, or diagnostic construction being unavailable.
Arrays retain execution order; rule codes are sorted and deduplicated.

Publication uses a fresh same-directory temporary file with mode 0600 and an
atomic no-replace link to the requested path. An existing destination, unsafe
destination relationship, serialization failure or write failure emits only
the bounded warning `diagnostic capture failed: output unavailable` and keeps
the already determined validator exit 0, 1 or 2. Invalid CLI syntax before a
usable destination remains ordinary argparse behavior.

For release-headed PR validation, required CI removes only its exact prior
diagnostic path, proves that path absent, runs the one real auto validator with
the option, and immediately attempts an `always()`-scoped
`actions/upload-artifact@v4` upload. The single file name includes run, attempt,
job and checkout SHA, missing-file behavior is `error`, and retention is 14
days. The validator step remains blocking; upload success cannot replace its
status, and local enforcement does not claim hosted delivery against runner or
service loss.
