# v1.13.9 Phase 18 — CLI Thin-Wrapper Proof and Remaining Coupling Review

Starting SHA: `346fb49d046c5a17594cafd55bf711ae79419905`

## Summary

Phase 18 closes the remaining tracker-definition gap after Phase 17 froze the
thin-wrapper review title but did not define a concrete `v1.13.9` Phase 18
section, artifact, or acceptance criteria.

This phase is docs-only. It does not implement CLI or engine hardening, does
not change command behavior, and does not change any parser, JSON contract,
schema, storage, or workflow behavior.

Its purpose is to define the exact checked-in Phase 18 scope using the current
code and release documents as the source of truth.

## Current confirmed coupling posture

The checked-in code and tests already establish that:

- production CLI snapshot create routes through `Engine.SnapshotCreate`
- production CLI snapshot delete routes through `Engine.SnapshotDelete`
- production CLI snapshot restore routes through `Engine.SnapshotRestore`
- CLI still intentionally owns argument parsing, flag compatibility,
  pre-initialization usage errors, current-working-directory discovery where
  required, output rendering, JSON projection, performance spans, and
  user-facing hints
- compatibility-only direct snapshot seams remain in `cmd/coldkeep/main.go`
  for lower-level tests and non-CLI callers
- doctor and repair remain intentionally CLI-owned orchestration over
  lower-layer recovery and maintenance primitives
- verify and GC include engine-owned execution paths but remain outside the
  primary snapshot mutation proof target for this phase definition
- snapshot read-side commands still include mixed routing and adaptation seams,
  so the release must not overclaim repo-wide thin-wrapper completion

## Primary proof targets for a later implementation pass

If a later proof or hardening pass proceeds from this definition, its intended
primary target surface is:

- `snapshot create`
- `snapshot delete`
- `snapshot restore`

That later pass should prove:

- engine ownership for mutation execution remains active
- CLI ownership is limited to translation, parsing, projection, and rendering
- compatibility seams are not reachable from the production mutation paths
- intentional remaining CLI ownership is documented honestly rather than
  described as already thin where it is not

## Adjacent command-family classification

The current baseline for adjacent CLI coupling remains:

- snapshot list/show/stats/diff: mixed read-side coupling, deferred
- verify: intentional CLI parsing and rendering around engine execution
- GC: engine-routed execution with CLI-owned request construction and rendering
- doctor: intentionally CLI-owned orchestration
- repair: intentionally CLI-owned orchestration
- store/remove/restore non-snapshot paths: adjacent evidence only, not the
  primary scope for this definition

These areas are classification inputs for a later proof pass, not authorization
to expand routing or mutate behavior in Phase 18 itself.

## Forbidden in Phase 18

Phase 18 does not:

- change CLI output
- change JSON contracts
- change parser behavior
- change engine contracts
- change snapshot create/delete/restore semantics
- route doctor or repair through the engine
- add repair or recovery engine methods
- change verify, GC, storage, schema, migrations, or workflows
- begin the later proof or hardening implementation
- open or reopen a pull request
