# Coldkeep v1.13.8 Remove Contract Inventory

**Release:** `v1.13.8 — Restore / Remove Contract Split and Stored-Path Boundary`
**Phase:** Phase 2
**Status:** Complete
**Branch:** `release/v1.13.8`

## Purpose

Create one authoritative inventory of every current remove surface before
changing remove request types, engine methods, CLI routing, batch ownership,
or result models.

## Executive conclusion

Coldkeep currently has one active by-ID `Engine.Remove` contract and two
supported stored-path remove implementations that bypass `Engine.Remove`:
single stored-path unlink and stored-path batch unlink. The mixed
request/result model represents all three behaviors, but its active engine
semantics do not.

## Current remove modes

- By-ID remove:
  - CLI batch orchestration
  - one-item `removeByIDPhase` execution
  - `Engine.Remove` with `RemoveModeFileIDs`
  - `storage.RemoveFileWithDBResult`
- Single stored-path remove:
  - CLI validation and orchestration
  - direct `storage.RemoveFileByStoredPathWithStorageContextResult`
  - no engine remove call
- Batch stored-path remove:
  - CLI raw-target loading
  - CLI trim/invalid/duplicate preparation
  - sequential CLI execution
  - direct storage call per executable stored path

## Active engine interface

Active signature:

```go
Remove(ctx context.Context, req RemoveRequest) (RemoveResult, error)
```

Current engine truth from `internal/engine/default_engine.go` and
`internal/engine/default_engine_routing_helpers.go`:

- context cancellation is checked first;
- `validateRemoveRequest` runs second;
- only `RemoveModeFileIDs` is accepted;
- `RemoveModeStoredPath` and `RemoveModeStoredPaths` return
  `ErrNotImplemented`;
- accepted requests execute through `removeFileIDs`;
- execution mode is sequential.

The engine interface comment describes logical-file removal generally, but the
mixed request can represent file-ID and stored-path modes while implementation
only activates file-ID mode today.

## By-ID CLI call graph

Normal by-ID CLI execution:

```text
runRemoveCommand
  -> batch.LoadRawTargets
  -> batch.PrepareTargets
  -> loadDefaultStorageContextPhase
  -> batch.ExecutePrepared
  -> removeByIDPhase
  -> Engine.Remove
```

CLI-owned by-ID responsibilities:

- positional and optional `--input` loading;
- comment and blank-line skipping in batch input files;
- invalid-target and duplicate-target handling;
- ordering preservation;
- decision about whether any executable target exists;
- normal CLI fail-fast behavior;
- human rendering, JSON rendering, and exit behavior.

## By-ID engine call graph

Direct engine path:

```text
DefaultEngine.Remove
  -> ctx.Err
  -> validateRemoveRequest
  -> removeFileIDs
  -> removeFileID per item
  -> dryRunRemoveByID or liveRemoveFileID
  -> storage.RemoveFileWithDBResult
```

Engine-owned by-ID responsibilities:

- request validation;
- unsupported-mode classification;
- item-level validation for non-positive file IDs;
- dry-run versus live branching;
- direct-engine fail-fast when multiple IDs are supplied in one request;
- per-item result shaping and summary generation.

Important freeze point:

CLI batch execution invokes the seam one item at a time, so normal CLI
ordering and fail-fast are CLI-owned. Direct engine fail-fast exists for
non-CLI callers that send multiple IDs in one request.

## Single stored-path CLI call graph

Current single stored-path route:

```text
runRemoveCommand
  -> rejectBlankFlagValues
  -> stored-path-specific CLI validation
  -> loadDefaultStorageContextPhase
  -> storage.RemoveFileByStoredPathWithStorageContextResult
  -> CLI human/JSON rendering
```

Confirmed current truth:

- `Engine.Remove` is not called;
- `removeByIDPhase` is not called;
- direct-path proof is `TestRemoveStoredPathPreservesDirectCLIStoragePath`.

## Batch stored-path CLI call graph

Current stored-path batch route:

```text
runRemoveCommand
  -> batch.LoadRawTargets
  -> prepareRemoveStoredPathTargets
  -> optional report-only short circuit
  -> loadDefaultStorageContextPhase
  -> executeRemoveStoredPathPrepared
  -> executeRemoveStoredPathDryRunItem or executeRemoveStoredPathItem
  -> storage.RemoveFileByStoredPathWithStorageContextResult
```

Confirmed current truth:

- stored-path batch remove is supported CLI behavior;
- it bypasses `Engine.Remove`;
- prepared targets preserve input order;
- duplicate detection is based on trimmed string equality, not filesystem
  canonicalization.

## Current validation ordering

Top-level engine validation order:

1. context cancellation
2. `validateRemoveRequest`
3. by-ID execution

Engine validation behavior:

- mode other than `RemoveModeFileIDs` returns `ErrNotImplemented`;
- empty `FileIDs` returns a validation error;
- non-positive IDs become per-item failures;
- top-level remove can succeed while items fail;
- direct engine `FailFast` stops after the first failed item;
- summary skipped count includes remaining unexecuted items;
- `DryRun` uses `dryRunRemoveByID`;
- live execution uses `storage.RemoveFileWithDBResult`.

Single stored-path CLI validation order:

1. reject unknown flags
2. reject blank `--stored-path`
3. reject `--stored-path` plus `--stored-paths`
4. reject positional arguments
5. reject `--input`
6. reject `--dry-run`
7. reject `--fail-fast`
8. load storage context
9. execute `storage.RemoveFileByStoredPathWithStorageContextResult`

Batch stored-path CLI validation and preparation order:

1. load raw targets from args and optional input file
2. trim whitespace
3. mark blank entries failed
4. mark later duplicate trimmed paths skipped
5. preserve first unique trimmed path as executable
6. if no executable targets exist, report without opening storage
7. otherwise load storage context
8. execute sequential direct storage calls or stored-path dry-run planning
9. stop on fail-fast only after an executable item fails

## Retention and invariant ordering

By-ID live remove:

- verifies the logical file exists;
- refuses `PROCESSING` status;
- checks snapshot retention before mutation;
- removes current `physical_file` mappings via path-by-path unlink;
- decrements `chunk.live_ref_count`;
- deletes `file_chunk` rows;
- deletes the `logical_file`;
- commits only after invariant-preserving transitions succeed.

Single stored-path live remove:

- normalizes the stored path;
- resolves the owning logical file ID under transaction;
- checks snapshot retention before deletion;
- deletes exactly one `physical_file` row;
- decrements `logical_file.ref_count` only when positive;
- verifies `remaining_ref_count == current physical mapping count`;
- commits only after the invariant holds.

Stored-path unlink currently distinguishes:

- never stored;
- already removed in a concurrent race after lookup;
- snapshot-retained delete blocked;
- ref-count mismatch drift.

## Catalog mutation analysis

By-ID live remove mutates catalog state by:

- removing all current `physical_file` mappings for the logical file;
- removing all `file_chunk` rows for the logical file;
- decrementing `chunk.live_ref_count`;
- deleting the `logical_file`.

By-ID live remove does not directly:

- reclaim payload bytes;
- delete containers;
- remove chunk rows solely because they became unreachable.

Single stored-path live remove mutates catalog state by:

- deleting exactly one `physical_file` row;
- decrementing `logical_file.ref_count` when positive.

Single stored-path live remove preserves:

- the `logical_file` row;
- all `file_chunk` rows;
- all chunk rows and payload bytes;
- snapshot rows and references.

Valid last-path end state:

- logical file remains present;
- `ref_count == 0`;
- zero current `physical_file` mappings remain.

## Reachability and GC ownership

Current reachability and retention ownership:

- current logical-file roots come from `physical_file`;
- snapshot roots come from `snapshot_file`;
- stored-path unlink changes current-root reachability only;
- by-ID remove deletes the logical file after retention checks;
- neither remove path directly reclaims payload storage.

GC remains responsible for deciding reclaimability from:

- current reachability;
- snapshot reachability;
- `chunk.live_ref_count`;
- `chunk.pin_count` when relevant elsewhere in the system.

## Dry-run versus live behavior

By-ID dry-run:

- checks only that the logical file exists;
- checks only that the logical file is not `PROCESSING`;
- does not prove snapshot-retention success;
- does not prove chunk or mapping invariant success;
- can report a planned remove that live execution would later refuse.

Stored-path batch dry-run:

- trims the stored path;
- checks only whether the stored path resolves to a current mapping;
- returns the owning logical file ID when found;
- does not prove snapshot-retention success;
- does not prove invariant success;
- does not prove concurrent live success.

Single stored-path mode has no dry-run path.

## Human output contract

By-ID human output is produced through existing batch reporting helpers and
CLI wrappers, including routed messages such as:

- `removed mappings=<n>` for by-ID success;
- summary lines that distinguish success, failed, planned, and skipped items.

Single stored-path human success lines are:

- `Stored path mapping removed: <path>`
- `LogicalFileID: <id>`
- `Remaining refs: <count>`
- `Hint: <doctor hint>`

Stored-path batch human output preserves:

- input order;
- duplicate target reporting;
- invalid target reporting;
- planned versus success versus failed versus skipped status lines;
- fail-fast truncation after the first failed executable item.

## JSON output contract

By-ID JSON output is produced through the existing batch envelope and per-item
result rendering.

Single stored-path success JSON fields are:

- `status`
- `command`
- `data.stored_path`
- `data.logical_file_id`
- `data.remaining_ref_count`
- `data.removed`

Stored-path batch JSON output preserves:

- per-item ordering;
- planned, success, failed, and skipped statuses;
- duplicate reporting as skipped items;
- the normal batch summary counters.

## Error and unsupported taxonomy

- CLI usage/setup errors:
  - unknown flags
  - forbidden flag combinations
  - invalid positional and input usage
  - blank stored-path flag values
- Engine unsupported-mode errors:
  - `ErrNotImplemented` for `RemoveModeStoredPath`
  - `ErrNotImplemented` for `RemoveModeStoredPaths`
- Engine validation errors:
  - empty `FileIDs`
- By-ID item-level failures:
  - non-positive file IDs
  - retained snapshot refusal
  - invalid live-ref-count transitions
- Stored-path storage failures:
  - never stored
  - already removed in concurrent race
  - retained snapshot refusal
  - ref-count mismatch drift
- Filesystem/DB/concurrency failures:
  - input-file open/read failures
  - DB transaction and query failures
  - concurrent row-loss behavior surfaced by storage

Important freeze point:

stored-path remove is unsupported only for direct mixed-engine calls. The
actual CLI stored-path remove commands are supported because they bypass the
engine.

## Ordering, duplicate, and fail-fast behavior

By-ID CLI batch behavior:

- input-file blank lines and comment lines are ignored before preparation;
- duplicate detection is by parsed integer ID;
- first unique valid ID is executable;
- later duplicate IDs are skipped;
- invalid IDs become failed items;
- ordering is preserved;
- fail-fast belongs to CLI because normal CLI execution invokes one engine call
  per executable ID.

Stored-path batch behavior:

- duplicate detection is by trimmed string equality;
- no filesystem canonicalization occurs at prep time;
- blank stored-path items become failed results;
- first unique trimmed path is executable;
- later duplicates are skipped;
- ordering is preserved;
- fail-fast stops only after an executable stored-path item fails.

## Backend and storage-context coupling

Current ownership split:

- engine by-ID removal uses `e.config.DB` directly for validation and storage
  calls;
- CLI by-ID removal still loads default storage context before calling the seam;
- stored-path single and batch removal require a loaded storage context;
- storage removal creates its own operation context from `context.Background()`
  rather than receiving the caller's context.

That context propagation mismatch is an inventory finding for later contract
cleanup, not a Phase 2 behavior change.

## Misleading and overloaded contract surfaces

- `RemoveRequest` currently combines:
  - by-ID logical deletion concerns;
  - single stored-path unlink concerns;
  - stored-path batch concerns;
  - CLI batch-input concerns.
- `RemoveResult` and `RemoveItemResult` currently combine:
  - logical deletion outcomes;
  - mapping-unlink outcomes;
  - CLI batch reporting concerns.
- `RemovedMappings` is currently misleading in by-ID live mode because it
  counts removed `file_chunk` associations rather than deleted
  `physical_file` mappings.
- `Removed` is overloaded:
  - by-ID means logical file deleted;
  - stored-path mode means one mapping removed.
- Interface and candidate comments that over-generalize active support should
  be cleaned up later, not in Phase 2.

## Frozen behavior baseline

- `Engine.Remove` currently supports only `RemoveModeFileIDs`.
- `RemoveModeStoredPath` and `RemoveModeStoredPaths` are unsupported through
  the engine and return `ErrNotImplemented`.
- Normal CLI by-ID remove is a batch shell around one-item engine calls.
- Single stored-path remove is a supported CLI command because it bypasses the
  engine.
- Batch stored-path remove is also a supported CLI path that bypasses the
  engine.
- By-ID live remove deletes the logical file and its current mapping/content
  graph edges after retention checks.
- Single stored-path live remove unlinks exactly one current mapping and
  preserves the logical/content graph.
- Valid last-path stored-path unlink leaves `0 == 0` current-state residue:
  retained logical file, zero ref count, zero mappings.
- Current and snapshot reachability remain separate ownership domains.
- GC, not remove, decides whether payload storage is reclaimable.
- By-ID dry-run is weaker than live remove and can over-predict success.
- Stored-path batch dry-run is weaker than live remove and can over-predict
  success.
- Single stored-path mode has no dry-run behavior.
- CLI duplicate handling and fail-fast semantics differ between by-ID integer
  preparation and stored-path string preparation, and both are currently part
  of the public CLI contract.
- No Phase 2 inventory work changes engine interfaces, CLI routing, storage
  mutation, output shape, or error classification.

## Questions handed to Phase 4

- Should by-ID and stored-path remove use separate request types?
- Does stored-path batch remove need its own dedicated engine boundary or
  should it remain CLI-owned?
- Should `RemovedMappings` be renamed or split so by-ID and stored-path results
  cannot misstate what was deleted?
- Should `Removed` be split into logical-file deletion versus mapping-unlink
  outcomes?
- Should remove paths propagate caller context into storage operations rather
  than creating a background-derived operation context?
- Should dry-run/live parity be strengthened, or should the weaker planning
  contract remain explicit?
