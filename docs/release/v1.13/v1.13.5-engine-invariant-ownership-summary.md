## Final ownership decisions

### Verify

`Verify` remains acceptable as a transitional seam for `v1.13.5`.

- CLI owns command-shape parsing, verify-level parsing, `verify file` string
  parsing and platform-range rejection, public success rendering, and public
  error-envelope projection.
- Engine owns `VerifyRequest` validation for the active seam and protects
  non-CLI callers from invalid typed requests.
- Maintenance and `internal/verify` own the deeper verification logic,
  corruption detection, and invariant-producing integrity checks.
- `VerifyResult` remains intentionally minimal, which keeps the public verify
  envelope CLI-owned rather than engine-result-owned.

### Remove

`Remove` remains acceptable as a transitional seam for `v1.13.5`.

- Engine support is active only for `RemoveModeFileIDs`.
- CLI owns command-shape parsing, stored-path branch selection, and public
  batch rendering.
- Engine owns by-ID request validation and structured by-ID item result
  shaping.
- Storage owns destructive-operation semantics, snapshot-retention blocking,
  ref-count consistency, and fail-closed mutation safety.
- Unsupported stored-path and stored-paths engine calls remain explicit
  `ErrNotImplemented` boundaries while direct CLI/storage paths remain public.

### Restore

`Restore` remains acceptable as a transitional seam for `v1.13.5`.

- Engine support is active only for `RestoreModeFileIDs`.
- CLI owns command-shape parsing, stored-path branch selection, destination
  mode policy, `--strict` / `--no-metadata` public flag policy, and public
  batch rendering.
- Engine owns by-ID request validation and structured by-ID result shaping.
- Storage owns restore-safety behavior including path safety, overwrite
  protection, temp-file and rename durability, chunk/hash validation, and
  metadata application.
- Stored-path restore remains an explicit `ErrNotImplemented` engine boundary
  while direct CLI/storage restore remains public.

### GC and maintenance invariants

GC and maintenance invariant propagation remains acceptable for `v1.13.5`.

- Invariant metadata is created in domain and maintenance layers through
  `internal/invariants.Error`.
- Invariant codes remain machine-readable strings extracted through
  `errors.As`.
- Recommended actions are derived from invariant-code mapping.
- Active engine GC preserves maintenance/domain errors rather than introducing
  a richer engine-native invariant result structure.
- CLI remains the public rendering boundary for maintenance and verify-class
  invariant metadata.
- Recovery and quarantine-adjacent paths remain a narrower plain-error/report
  seam and are acceptable as transitional for this release.

### Read-side surfaces

The `v1.13.4` read-side guard baseline remains sufficient for `v1.13.5`.

- `stats` and `inspect` success JSON remain renderer-envelope owned.
- `snapshot show` and `snapshot diff` success JSON remain CLI-envelope owned.
- CLI-owned read-side JSON error envelopes remain intentionally distinct from
  renderer-owned success envelopes.
- `logical-file` remains a public inspect alias.
- `physical-file` and `EntityPhysicalFile` remain internal-only.
- No new read-side Phase 8 guards were justified.

## Backend posture

- SQLite compatibility is preserved.
- PostgreSQL compatibility is preserved.
- No SQLite-only assumptions were introduced.
- The request/guard decisions recorded in Phases 1–8 remain backend-neutral.
- The deeper execution seams reviewed in Phases 2–7 remain backend-compatible
  rather than backend-unified.
- Final PostgreSQL-backed validation still belongs to
  `PRE_RELEASE_CHECKLIST.md Profile A` in Phase 10.
