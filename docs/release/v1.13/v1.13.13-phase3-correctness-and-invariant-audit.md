## 1. Audit purpose

This source-first, read-only audit attempted to disprove every frozen v1
correctness invariant. It traced all production restore routes plus snapshot,
GC, verify, recovery, repair, container, transform, numeric, transaction, and
concurrency-sensitive code before any documentation edit. Tests supplement
source proof; passing tests and hosted jobs do not override a source defect.
No defect was remediated.

## 2. Normative requirements

The authority is the
[frozen v1.x normative requirements matrix](v1.13.13-v1x-normative-requirements.md).
Every `V1R-COR-001`–`014` row and restore/path requirement
`V1R-XPLAT-002` is classified in the
[correctness invariant matrix](v1.13.13-correctness-invariant-matrix.md).
There are three distinct blocker roots and no partial dispositions. No new
normative-gap candidate is needed: both newly discovered roots are already
covered by `V1R-COR-004`, `006`, and `007`.

## 4. Restore architecture and paths

`Engine.Restore`, `Engine.RestoreStoredPath`, and `Engine.SnapshotRestore` all
reach Catalog-backed metadata/placement and the same storage reconstruction
and installation primitive. Single/batch, dry/live, overwrite/no-overwrite,
original/prefix/override, and full/exact/prefix/query snapshot forms are
enumerated in the
[restore correctness matrix](v1.13.13-restore-correctness-matrix.md).
Catalog remains metadata/planning authority; storage remains payload and final
filesystem owner. This audit does not change the Phase 2 ownership verdict.

## 5. Restore installation contract

The preliminary finding is independently confirmed as `P3-COR-001`.

- `P3-COR-001A`: with overwrite disabled, storage checks destination absence,
  reconstructs a temp file, checks absence again, and calls ordinary rename.
  Another actor can create the destination after the last check; the source
  does not use an atomic no-replace primitive.
- `P3-COR-001B`: `restoreFileWithDBAndDir` receives a planned exact path, then
  treats an existing directory at that path as a directory destination and
  appends `originalName`. Snapshot collision checks and Engine dry-run happen
  before that reinterpretation.

The root affects by-ID single/batch live restores, all stored-path destination
modes, and all snapshot restore selections; dry-run is also not authoritative
where the live layer can reinterpret its path. Ordinary rename cannot prove
the required Linux, macOS, or Windows no-replace contract. The two subcases
remain one inherited root because both require the destination-install
contract to become authoritative at the final publication boundary.

## 6. Path confinement

Current lexical defenses reject NULs, `..`, absolute/rooted paths, Windows
drive paths, UNC paths, mixed separators that normalize outside the root,
unsafe container names, malicious stored paths, and corrupt snapshot paths.
Existing symlink components and symlink targets are rejected below trusted
roots.

`P3-COR-002` is a separate blocker: `ValidateWritePathUnderTrustedRoot` walks
components with `Lstat`, returns a string path, and later `MkdirAll`,
`CreateTemp`, metadata operations, and rename use that path. A checked parent
can be replaced with a symlink between check and use. There is no pinned
directory handle or handle-relative create/install protecting the final
destination. Static symlink tests therefore do not prove symlink-replacement
confinement.

## 7. Restore durability/partial failure

Reconstruction uses a random temp file in the destination directory, buffered
flush, file `Sync`, close, final hash validation, rename, and parent-directory
sync outside Windows. Read/decode/hash/write/sync/close/rename failures return
failure and retain an existing destination until final installation. Cleanup
removes owned temp files, and a deferred operation unpins chunks on success or
failure; unpin failure turns otherwise successful execution into an error.

Bounds are explicit: snapshot batch publication is sequential per file, not
all-or-nothing, and strict metadata failure can be reported after correct file
bytes become visible. Best-effort metadata mode returns structured warnings.
Those documented bounds are not new blockers. The misleading/destructive
final no-overwrite race remains `P3-COR-001`.

## 8. Deterministic reconstruction

Catalog returns ordered complete metadata and exactly one authoritative packed
or legacy placement per chunk. Storage validates recipe order, emits in
`chunk_order`, validates packed segment bounds, plaintext lengths, per-chunk
SHA-256, and final file SHA-256. Missing or skipped chunks cannot become
success because the final file hash fails. Selection order and duplicate
handling are deterministic. Legacy-only, packed-only, and mixed restore
fixtures plus the focused concurrent determinism race pass. Reconstruction is
`PROVEN`; destination installation is independently blocked.

## 9. Snapshot correctness

Snapshot creation reads and inserts within one transaction, normalizes paths,
uses deterministic selectors, rolls back mixed invalid input, and exposes no
production update operation. Parent/lineage validation rejects missing,
self-parented, partial-parent, and cyclic-invalid meanings. Delete removes
memberships and exactly one snapshot row in a transaction, while current and
other snapshot roots continue to protect payload. Full, exact, directory, and
query selectors do not silently broaden. Snapshot safety is `PROVEN` within
the explicit per-file restore and later backend-isolation bounds; its restore
install step inherits `P3-COR-001` and `P3-COR-002`.

## 10. GC reachability

Catalog supplies current roots, snapshot roots, protected snapshot metadata,
and exclusions. `gc.BuildPlan` combines those with pins and both legacy and
packed placement. Invalid roots, missing placement, orphan snapshot metadata,
duplicates, incomplete rows, and physical graph corruption fail closed or are
conservatively retained. Live deletion revalidates liveness inside its
transaction, uses FK and affected-row guards, and does not physically delete
after a failed expected metadata deletion. Dry-run and live share the
authoritative reachability calculation. `GC_SAFETY` is `PROVEN` within the
current PostgreSQL live-GC and Phase 5 coordination bounds.

## 11. G6 coherent-plan revalidation

`catalog.Service.LoadGCPlanMetadata` constructs one compound `UNION ALL`
statement containing protected snapshot metadata, snapshot-file roots, and
current physical-file roots. It then validates orphan/duplicate/incomplete
rows before producing sorted metadata. Production GC consumes this contract.
The deterministic SQLite race matrix passes creation, deletion, excluded
deletion, current-root insertion, and current-root removal cases under `-race`.
Current source therefore confirms the v1.13.12 G6 correction; PostgreSQL
isolation equivalence remains Phase 4.

## 12. Packed/legacy/mixed parity

Restore, placement, snapshot retention, GC, recovery, container bounds, and
system/repository verification handle legacy-only, packed-only, and mixed
repositories. One hidden legacy-only join breaks aggregate parity:
file-level deep verification joins `file_chunk` to legacy `blocks` and never
loads `chunk_block_refs`/`storage_blocks`. This is `P3-COR-003`; packed-only
files can return deep-verification success without hashing any packed chunk,
and mixed files hash only their legacy subset. `PACKED_LEGACY_PARITY` is
therefore `BLOCKED`.

## 13. Verification fail-closed behavior

System/repository verification checks physical graph, snapshot reachability,
legacy payloads, packed block metadata/ranges, transform stages, decoded
segments, and hashes. Corruption-stage fixtures confirm precise failure, and
fast level's smaller scope is explicit. File standard/full verify presence,
status, containers, and ranges for both placement shapes.

File deep then calls `verifyFileChunkHashes`, whose SQL uses inner joins to
legacy `blocks` and containers. Zero returned rows are treated as success, so
the level's claimed chunk-hash proof is false for packed-only data. Existing
system packed tests do not cover this distinct production file route, and no
packed file-deep regression test exists. `VERIFY_FAIL_CLOSED` is `BLOCKED` by
`P3-COR-003`.

## 14. Recovery

Startup and manual recovery share Engine-owned execution. Strict recovery is
the default; it validates safe container filenames, reconciles sizes and
states, quarantines suspect/orphan payload, reports filesystem failures, and
is repeatable. Orphan bytes are not made reachable simply to silence an
inconsistency. Fault-FS tests prove stat/readdir/quarantine failures remain
errors. Optional non-strict warnings do not authorize corrupt mappings.
`RECOVERY_SAFETY` is `PROVEN`.

## 15. Repair

Logical and chunk refcount repair validate topology and refuse orphan physical
relationships before calculating truth. Mutations run in transactions and
require the computed affected-row count. Repair cannot make an invalid graph
look healthy merely by balancing counters. Healthy runs are idempotent/no-op,
and Engine error translation preserves invariant meaning. `REPAIR_SAFETY` is
`PROVEN`.

## 16. SQL cardinality

The current tree retains the prior 70-mutation inventory's distinction among
20 exact required-row transitions, safe zero-row cleanup, CAS/upsert,
returning, bulk, and structural operations. `RequireRowsAffected` and
`RequireExactlyOneRow` guard required store/remove, snapshot, repair, recovery,
container, and GC transitions; mismatch causes rollback or prevents physical
follow-up. Current source and cardinality selectors reveal no regression.
`SQL_MUTATION_CARDINALITY` is `PROVEN`; Phase 4 owns backend-specific behavior.

## 17. Transaction/state transitions

Store tracks append ownership, hides catalog metadata before commit,
acknowledges committed appends, and rolls back/truncates or quarantines failed
payload transitions. Remove, snapshot create/delete, repair, recovery, and GC
check commit errors and represent committed results truthfully. Container seal
and current-size transitions fail closed on missing expected rows. Filesystem
deletion after GC catalog commit may leave orphan bytes on failure but cannot
delete live metadata/payload. No additional root finding was established.

## 18. Container bounds

Container paths accept only safe opaque filenames. Open validates the fixed
header, magic, supported version, header length, CRC, declared maximum,
catalog/header maximum equality, and current physical size. Range validation
rejects negatives, addition overflow, past-end ranges, maximum violations, and
host-`int` allocation overflow before reading or allocating. Sealed/quarantine
state is explicit. `CONTAINER_BOUNDS` is `PROVEN` for supported formats.

## 19. Decompression/transform bounds

Both identity and zstd codecs validate expected plaintext size against the
absolute block bound before output allocation. Zstd configures decoder
memory/window limits and caps aggregate output, including concatenated frames;
decoded length must equal the declared size. Packed reads validate physical
hash, authenticate/decrypt AES-GCM, validate compressed hash, decompress, then
validate logical payload and segments. `BOUNDED_DECOMPRESSION` is `PROVEN`.

## 20. Numeric fidelity

Engine dynamic values preserve signed and unsigned integers as tagged decimal
tokens, recursively through maps and slices. CLI compatibility projection uses
`int64` when exact and `json.Number` for larger unsigned values; correctness-
critical data does not transit a `float64` map. Tests cover above `2^53`,
`MaxInt64`, unsigned boundaries, nested values, and stable stats JSON numbers.
Invalid negative request values are rejected. `NUMERIC_FIDELITY` is `PROVEN`.

## 21. Concurrency correctness

Focused `-race` execution proves SQLite G6 statement coherence, deterministic
restore during concurrent writes, restore pins during removal, and pin cleanup
on success/failure. Store and mutation source uses transaction/CAS boundaries;
the SQLite backend cannot exercise the PostgreSQL live store/GC overlap or
nested retry-claim lock path, and those skips are explicit. Correctness relies
on the same-host/local-filesystem repository coordination claim that Phase 5
must independently verify. `CONCURRENT_GC_PLANNING` is `PROVEN` within this
bound; no distributed claim is made.

## 22. Cross-platform correctness

Lexical tests model Unix, Windows drive, UNC, separator, outer-alias, and
trusted-root forms. macOS has a dedicated native temp-path alias regression
that skips on Linux and runs in hosted coverage. Windows explicitly omits
parent-directory sync. More importantly, all OS paths use ordinary rename,
not a proved atomic no-replace primitive, and all use pre-operation string-
path symlink checks. `V1R-XPLAT-002` is blocked by `P3-COR-001` and
`P3-COR-002`; Phase 7 must design and Phases 8–9 must implement/prove the
cross-platform install contract.

## 27. Findings

### `P3-COR-001` — `RESTORE_INSTALL_CONTRACT`

- **Root invariant:** authoritative, atomic, non-destructive destination
  installation.
- **Normative requirements:** `V1R-COR-001`, `V1R-COR-005`,
  `V1R-XPLAT-002`.
- **Severity for v1 closure:** blocker.
- **Source/functions:** `internal/storage/restore.go::restoreFileWithDBAndDir`;
  Engine by-ID planner; snapshot plan/collision validation.
- **Production routes:** every live by-ID, stored-path, and snapshot restore;
  dry-run truth is also affected by destination reinterpretation.
- **Reasoning:** the last absence check and ordinary rename are separable;
  storage also appends the original name when the exact planned path is an
  existing directory.
- **Existing tests:** overwrite/no-overwrite, destination preservation,
  rename/sync fault tests; none occupies the final race or asserts an existing
  directory remains the exact target.
- **Why evidence missed it:** tests exercise stable before/after states, not
  an interposed filesystem actor or planner/lower-layer semantic disagreement.
- **Scope:** Linux, macOS, Windows; backend-independent.
- **Risk/consequence:** a concurrently created destination may be replaced
  despite no-overwrite, or content may be installed at an unplanned path.
- **Likely remediation needed:** YES.
- **Phase 6 classification required:** YES.
- **Prior relationship:** independently confirms the entering
  `RESTORE_INSTALL_CONTRACT`; it is counted once, with subcases A/B.

### `P3-COR-002` — destination parent symlink replacement TOCTOU

- **Root invariant:** confinement against symlink escape at the actual write
  and installation boundary.
- **Normative requirements:** `V1R-COR-004`, `V1R-XPLAT-002`.
- **Severity for v1 closure:** blocker.
- **Source/functions:** `internal/pathsafe/pathsafe.go::ValidateWritePathUnderTrustedRoot`,
  `validateNoSymlinksUnderRoot`; storage restore create/install and snapshot
  directory creation.
- **Production routes:** every live by-ID, stored-path, and snapshot restore.
- **Reasoning:** component `Lstat` validation and later path-string operations
  are separate; a checked writable parent can be replaced by a symlink.
- **Existing tests:** comprehensive static symlink and traversal fixtures, but
  no concurrent parent replacement.
- **Why evidence missed it:** fixtures install the symlink before validation;
  they do not mutate the component after validation.
- **Scope:** supported local filesystems on Linux/macOS/Windows; independent of
  Catalog backend.
- **Risk/consequence:** restored bytes or metadata can be directed outside the
  trusted root by a concurrent filesystem actor.
- **Likely remediation needed:** YES.
- **Phase 6 classification required:** YES.
- **Prior relationship:** newly identified root, separate from exact/no-replace
  installation semantics.

### `P3-COR-003` — packed chunks omitted by file-deep verification

- **Root invariant:** fail-closed claimed deep verification across supported
  repository shapes.
- **Normative requirements:** `V1R-COR-006`, `V1R-COR-007`.
- **Severity for v1 closure:** blocker.
- **Source/functions:** `internal/verify/verify_file.go::verifyFileChunkHashes`,
  `VerifyFileDeepWithContainersDir`; production dispatch in
  `internal/maintenance/verify_command.go::verifyFile`.
- **Production route:** `Engine.Verify` / CLI `verify file <id> --deep`.
- **Reasoning:** the query inner-joins `blocks` and has no packed
  `chunk_block_refs`/`storage_blocks` branch. Packed-only files yield no hash
  rows and success; mixed files check only legacy chunks.
- **Existing tests:** system/repository packed corruption fixtures and legacy
  file-deep tests; no packed/mixed file-deep corruption fixture.
- **Why evidence missed it:** system verification exercises a different packed
  pipeline; route-level file-deep parity was not asserted.
- **Scope:** packed-only and mixed repositories on all supported platforms and
  both backends where the route executes.
- **Risk/consequence:** corruption in packed payload can receive false success
  at the explicitly requested deep file verification level.
- **Likely remediation needed:** YES.
- **Phase 6 classification required:** YES.
- **Prior relationship:** newly discovered parity regression/gap; not a
  reopening based on historical prose.

No `PARTIAL` root exists. Explicit bounds are snapshot per-file publication,
Windows parent-sync limitation, current live-GC/backend scope, and Phase 5
coordination dependency. The S3 marker is optional future scope.
