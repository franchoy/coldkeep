# Coldkeep v1.13.7 Portability Evidence Inventory

**Release:** `v1.13.7 — SQLite-First Repository Portability Baseline`
**Phase:** Phase 4
**Status:** Complete
**Branch:** `release/v1.13.7`

## Purpose

This document classifies current executable and documentary evidence against the
repository portability contract defined in Phases 2 and 3.

This phase changes no runtime behavior and adds no tests.

## Scope boundaries

This phase is:

- evidence inventory only
- not a new test phase
- not a runtime SQLite local implementation
- not a backend-default change
- not a final Phase 7 decision
- still PostgreSQL-compatible by requirement

## Evidence classification model

Strength levels used in this inventory:

- **Direct evidence**: an executable scenario exercises the portability
  requirement itself
- **Partial evidence**: executable coverage proves a major contract component,
  but not the full portability scenario
- **Indirect evidence**: component behavior supports the contract, but only as
  a prerequisite or adjacent guarantee
- **Test-helper-only evidence**: a helper or fixture proves setup capability,
  not a user-facing or production-path contract
- **CI/release-gate evidence**: smoke, workflow, or release-gate automation
  proves recurring coverage, but not necessarily portability semantics
- **Documentation-only claim**: the requirement appears in docs/contracts but
  lacks executable proof
- **No evidence found**: no supporting executable or documentary artifact was
  found during this phase

Evidence scopes used in this inventory:

- SQLite
- PostgreSQL
- both backends
- backend-neutral
- test-only
- production-path

## Stage A — Catalog lifecycle evidence

Current evidence is strongest around bootstrap, migration, schema versioning,
and reconnect behavior.

- SQLite fresh bootstrap has strong direct seam-level coverage in
  `internal/db/migrations_test.go`, including table presence, schema version,
  and repository defaults.
- SQLite migration on existing databases is directly covered in
  `internal/db/migrations_test.go` and compatibility integration suites.
- Simulated SQLite uses `sql.Open("sqlite3", temp path)`,
  `ApplySQLiteSessionPragmas()`, and `RunMigrations()` in
  `internal/storage/context.go`, which is strong production-seam evidence but
  still not a normal local runtime path.
- PostgreSQL bootstrap, missing-schema refusal, and auto-migration are covered
  in `internal/db/migrations_test.go` and
  `tests/integration/integration_test.go`.
- Explicit close-and-reconnect patterns in integration and compatibility tests
  support clean-open lifecycle components, but they do not prove relocation.

Phase 4 conclusion for catalog lifecycle:

- strong SQLite bootstrap and migration evidence exists
- much of it is seam-level or helper-driven rather than relocation-level
- PostgreSQL reconnect/bootstrap evidence supports operational compatibility,
  not directory portability

## Stage B — Payload continuity evidence

Current evidence is also strong for payload continuity, corruption detection,
restore determinism, and fail-closed verify behavior under stable configured
roots.

- legacy container readability is covered in compatibility and integration
  suites
- packed-block readability is covered in integration and adversarial suites
- mixed legacy/packed continuity is covered in compatibility, GC, and verify
  flows
- missing payload and corruption detection are exercised by
  `internal/verify/*`, restore tests, and adversarial suites such as
  `tests/adversarial/g7_deep_corruption_adversarial_test.go`
- GC safety under inconsistent state is covered in adversarial suites such as
  `g4_non_destructive_gc_adversarial_test.go` and
  `g69_gc_safety_matrix_test.go`
- verify fail-closed posture is covered by verify-system tests and
  adversarial invariant suites

Phase 4 conclusion for payload continuity:

- strong evidence exists for payload continuity and integrity under stable roots
- the evidence proves continuity, corruption detection, and recovery behavior
- it does not by itself prove repository relocation safety

## Stage D — Post-relocation trust evidence

Coldkeep already has strong trust-check evidence, but it is largely tied to
same-root or same-configuration scenarios.

- same-process and separate-process store/restore coverage is strong across
  integration tests and `scripts/smoke.sh`
- reopen-at-same-path or reopen-under-same-config coverage exists in
  compatibility and recovery suites
- verify after reopen and restore after reopen exist in upgrade and recovery
  scenarios
- byte-perfect restore evidence exists in smoke and integration flows
- actual verify or restore after relocation was not found

Phase 4 conclusion for post-relocation trust:

- strong verify/restore evidence exists
- direct post-relocation trust evidence does not

## Stage E — Operational-constraint evidence

Evidence around operational constraints is mixed.

- encryption behavior is strongly covered, including correct-key success and
  wrong-key or malformed-key refusal
- external secrets and configuration boundaries are evidenced through env-driven
  tests and the accepted Phase 1 inventory
- backend selection is evidenced through storage-context and DB-env behavior
- machine-specific path risk is indirectly evidenced because current payload
  roots can still be configured externally or fall back to
  `./storage/containers`
- repository identity and independent-clone semantics have no direct executable
  evidence
- PostgreSQL runtime compatibility is strong, but PostgreSQL operational
  portability is not yet directly proven

## SQLite evidence summary

Production-path evidence:

- simulated SQLite open/migrate behavior exists in `internal/storage/context.go`
- pragma application and migration behavior are well covered

Simulated/test-only evidence:

- extensive in-memory SQLite and helper-created SQLite coverage exists across
  `internal/db/*_test.go`, `internal/storage/*_test.go`, and other internal
  suites

Direct portability evidence:

- no direct root-relocation portability proof was found

Missing evidence:

- normal local SQLite runtime path
- move/copy to a new repository root
- reopen using only the destination root
- verify after relocation
- restore after relocation
- restored-byte equality after relocation

In-memory SQLite and helper-created temporary databases do not count as
move/reopen portability evidence by themselves.

## PostgreSQL evidence summary

Runtime compatibility:

- strong evidence exists for DSN/env validation, bootstrap, auto-migration,
  reconnect, and ongoing command execution

Schema/bootstrap:

- `internal/db/migrations_test.go` and `tests/integration/integration_test.go`
  cover fresh bootstrap, missing-schema refusal, and auto-bootstrap behavior

Reconnect behavior:

- compatibility and recovery tests explicitly close and reconnect DB handles

Backup/restore evidence:

- no direct PostgreSQL catalog backup/restore plus payload-transfer proof was
  found

Operational portability evidence:

- current evidence supports runtime compatibility, not a full operational
  portability claim

## Phase 5 inputs

Backend-compatibility questions that should feed Phase 5 are:

- whether any narrow compatibility guard can be justified without introducing a
  backend-default change
- whether portability-related refusal posture around backend/config
  contradictions needs targeted guard coverage
- whether current PostgreSQL runtime compatibility evidence is sufficient for
  the release’s “PostgreSQL compatibility preserved” promise
- whether clean-close and reopen ownership expectations need a narrow
  compatibility assertion rather than a relocation test

## Phase 6 inputs

Minimum future smoke requirements suggested by confirmed gaps:

- temporary repository root
- in-repository SQLite catalog fixture or a production-equivalent seam
- representative payload roots
- normal SQLite migration/bootstrap path
- representative stored data
- close all DB handles before transfer
- copy or rename the complete root
- reopen using only the destination root
- verify
- restore
- byte comparison
- proof that the source path is no longer required

This phase does not finalize the smoke-test design details.

## Phase 7 candidate posture

No Phase 7 implementation is authorized by Phase 4 alone.

Phase 6 must first design the narrow portability smoke scenario and decide
whether it can be implemented as a test-only guard without changing runtime
behavior.

## Phase 4 conclusion

Existing tests provide strong supporting evidence for catalog lifecycle,
storage-format continuity, verification, restore, encryption failure behavior,
and PostgreSQL runtime compatibility.

No existing test directly proves the complete directory-portability contract.

A narrow end-to-end move/reopen/verify/restore smoke scenario should be
designed in Phase 6.
