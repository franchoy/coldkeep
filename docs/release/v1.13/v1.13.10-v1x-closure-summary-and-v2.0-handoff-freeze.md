# Coldkeep v1.13.10 Phase 7 — v1.x Closure Summary and v2.0 Handoff Freeze

> **Current-status notice (post-release correction):** This artifact accurately
> describes the v1.13.10 tagged-release decision and its then-current final-v1.x
> conclusion. That conclusion was superseded after release by a roadmap-to-code
> audit that restored substantive v1.13.11–v1.13.13 work. The authoritative
> current planning sources are `v1.13.x-release-train.md` and the v1.13.11
> Phase 0 artifact; v2.0 implementation remains not started.

## Purpose

Freeze the checked-in v1.x baseline from which v2.0 planning may begin. This
artifact records final guarantees, compatibility baselines, intentional seams,
explicit deferrals, and the local-first v2.x boundary without starting v2.0
implementation or changing runtime behavior.

## Evidence baseline

The authoritative sources are `README.md` and `VALIDATION_MATRIX.md` for G1
through G17; `PRE_RELEASE_CHECKLIST.md` for release-gate, JSON, exit-code, and
PostgreSQL expectations; the v1.13.9 release gate and handoff review for
closure and deferrals; and the v1.13.10 reconciliation, engine-contract,
release-state-validator, and CI artifact-migration records for current truth.

`docs/release/v1.13/v1.13.7-repository-portability-contract.md` is evidence
for a future SQLite-first target, not evidence of a current portable local
runtime. The active `Engine` interface and its exact-method tests remain the
authoritative source for active engine operations.

## Meaning of v1.x closure

v1.x closure means no known mandatory v1.x runtime remediation remains, the
engine and safety baseline is sufficient for v2.0 planning, and known
limitations and deferrals are explicit. It does not mean Coldkeep has no
defects, and it does not prohibit a corrective v1.x release if a later blocker
is found. v1.13.10 remains active and unreleased during this phase.

## Hard non-regression invariants

The following properties may not be weakened by v2.x work:

- Deterministic, byte-identical restore and atomic replacement within
  single-node local filesystem semantics (G1 and G5).
- No exposure of partially written or inconsistent catalog/storage state (G2
  and G3).
- Reachable current or snapshot-retained data is never reclaimed by GC; GC
  executes only on an audited coherent physical-root graph (G4, G11, and G14).
- Verification fails closed for inconsistent catalog/storage state and reports
  persisted snapshot reachability integrity (G7, G10, and G17).
- Snapshot deletion changes metadata and future eligibility only; referenced
  content remains protected (G15).
- Recovery must not legitimize corrupt mappings, and packed and legacy storage
  behavior remains aligned, as required by the engine package invariants.
- CLI parsing cannot be the only place where correctness invariants live; new
  engine APIs cannot weaken existing safety guarantees.

## Compatibility baselines

Current human CLI behavior, JSON envelopes, exit-code/error classification,
active engine operation meaning, schema/migration behavior, packed and legacy
repository reads, PostgreSQL validation, and the SQLite-first direction are
compatibility baselines.

A v2.x compatibility-baseline change requires an explicit design decision,
targeted regression tests, migration or compatibility handling where
applicable, release documentation, and preservation of the underlying
non-regression invariants.

PostgreSQL remains the normal v1.x local runtime and a required release-gate
compatibility path. SQLite migration and catalog seams are protected, but
SQLite is not yet the normal local runtime or a completed directory-portable
repository mode.

## Implementation details permitted to evolve

Provided the invariants and compatibility baselines hold, v2.x may change
package topology, routing, CLI rendering location, process ownership, and
daemon/API transport design. It may not infer that active interface presence
means a workflow is complete or daemon/API-ready.

The current CLI owns parsing, command-shape validation, compatibility
projection, and human/JSON rendering. Engine owns typed request/result
coordination and request-level validation; domain and storage layers retain
transactions, path safety, data mutation, and retention enforcement. These
locations may evolve only through an explicit, tested design.

## Intentional ownership seams

Snapshot create, delete, and restore are production CLI-routed engine
mutations. Snapshot list, show, stats, and diff remain active but provisional
read-side seams; they do not prove complete workflow or daemon/API ownership.

`Store` is active only for single files. `doctor` and `repair` remain
CLI/domain orchestration over lower-level corrective primitives. Repair and
Recover contracts are candidate-only and must not be activated merely because
their request/result types exist. `VerifyResult` remains intentionally empty
on success.

## v2.x local-first scope

v2.x is limited to a local daemon, daemon-owned mutations, local operation
queue, SQLite-first portable-repository direction, CLI client behavior, local
API/UI, local scheduling, catalog export/import, local verification/recovery
workflows, and retained PostgreSQL compatibility.

## v3.x beyond-local boundary

LAN/network service, NAS or multiple storage roots, centralized PostgreSQL
production/server mode, multi-user authorization, cloud/object storage,
distributed repositories, replication/synchronization, and cross-machine
coordination are v3.x or later scope. They do not enter v2.x without an
explicit roadmap revision.

## v2.0 entry conditions

1. v1.13.10 is merged, tagged, published, and operationally closed.
2. The final Phase 8 release gate is green.
3. This artifact is committed before the v1.13.10 tag.
4. v2.0 begins from the released v1.13.10 main/tag baseline.
5. A v2.0 branch and trackers begin only after v1.13.10 closure.
6. Existing v1.x correctness and compatibility tests remain active.
7. No candidate-only v1.x boundary is silently activated.
8. Contract changes include migration/compatibility tests and release notes.
9. v3.x scope does not enter v2.0 without an explicit roadmap revision.
10. Release-state validation advances deliberately for v2.0 rather than being bypassed.

The tagged tree must retain truthful pre-publication release evidence. Manual
publication, CI, Codacy, and branch-cleanup facts belong in the required later
post-release closure commit and never rewrite the tag.

## Change-control requirements

v2.x design and implementation must preserve the hard invariants, follow the
compatibility-baseline rule above, keep deferred boundaries explicit, and
record all intentional public-contract changes. The release-state validator
continues to distinguish tagged-tree truth from later operational closure.

## Explicit non-claims

- v2.0 implementation has not started.
- SQLite is not claimed as the current default local catalog.
- CLI workflows are not claimed fully engine-owned where they remain mixed.
- Repair and Recover are not active Engine operations.
- Recursive/folder Store is not active through `Engine.Store`.
- Backend parity is not claimed beyond current compatibility gates.
- Repository portability is not claimed complete.
- v1.x is not claimed defect-free.
- v1.13.10 is not merged, tagged, published, or released during Phase 7.
