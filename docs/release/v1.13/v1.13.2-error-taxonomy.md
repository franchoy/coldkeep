# Coldkeep v1.13.2 — Error Taxonomy

## Status

`complete`

## Purpose

This document defines the taxonomy language that later `v1.13.2` phases and
later `v1.13.x` releases should use when describing Coldkeep error behavior.

This is a contract-language baseline.

This is not a new error framework.

This is not an implementation of all categories.

This is not a CLI behavior change.

This does not change JSON error envelopes or exit codes.

This does not change engine routing.

## Design Principles

1. `ErrNotImplemented` remains distinct from validation, domain, invariant,
   runtime, catalog, storage, and environment failures.
2. Unsupported and deferred are not synonyms.
3. Validation errors mean the request is malformed or contradictory before
   execution.
4. Domain errors mean the request is valid but cannot be satisfied by current
   repository state.
5. Invariant errors mean Coldkeep detected a violated correctness guarantee.
6. Runtime, storage, catalog, and environment failures must not be mistaken for
   domain or validation errors.
7. CLI translation must remain stable until explicitly changed in a later
   release.
8. The taxonomy may begin as partly document-backed and partly code-backed.
9. Do not overclassify provisional surfaces.
10. Prefer small, sentinel-compatible, `errors.Is` / `errors.As` friendly
    evolution over a large framework.

## Taxonomy Categories

### Unsupported

Meaning:
An operation, mode, option, or request shape is intentionally outside the
active engine or catalog contract today.

Examples:

- recursive `Engine.Store`
- stored-path `Engine.Restore`
- stored-path `Engine.Remove`
- stored-paths `Engine.Remove`

Rules:

- should remain `errors.Is(..., engine.ErrNotImplemented)` where already
  code-backed
- must not be confused with malformed input
- must not be silently downgraded into a supported operation
- later implementation belongs to specific later `v1.13.x` releases

Later owner notes:

- `v1.13.7` owns stored-path restore/remove boundary cleanup
- recursive store implementation remains outside the current `v1.13.2` scope

### Deferred

Meaning:
A contract surface exists as a future, candidate, or deferred boundary but is
intentionally not active yet.

Examples:

- candidate-only snapshot create/delete/restore engine contracts
- candidate-only repair/recover engine contracts
- catalog graph/placement/restore-plan/gc-plan methods
- candidate or provisional request/result shapes not yet acting as full
  contracts

Rules:

- may be represented by `ErrNotImplemented` today
- must not imply runtime failure
- must not imply active engine ownership
- must have a later owner release where possible

Later owner notes:

- `v1.13.6` owns catalog contract expansion work
- `v1.13.8` owns snapshot mutation boundary cleanup
- `v1.13.9` owns repair/recovery boundary decisions

### Validation

Meaning:
The request is malformed, incomplete, contradictory, out of allowed range, or
invalid before execution.

Examples:

- missing required flag/value
- invalid mode name
- invalid ID format
- invalid limit/workers value
- mutually incompatible options
- empty value where a real value is required

Rules:

- validation is different from unsupported
- validation should happen as early as the current architecture allows
- `v1.13.2` must not change CLI validation behavior unless a later phase
  explicitly permits a preservation-only check

### Domain

Meaning:
The request is structurally valid, but the current repository state cannot
satisfy it.

Examples:

- file/logical file not found
- snapshot not found
- duplicate snapshot ID
- valid restore target missing from repository
- valid remove target no longer exists

Rules:

- domain failure is not malformed input
- domain failure is not necessarily repository corruption
- domain failure should not be classified as invariant failure unless a
  correctness guarantee is violated

### Invariant

Meaning:
Coldkeep detected a violation of a correctness guarantee or a
catalog/storage-consistency rule.

Examples:

- refcount mismatch
- missing chunk graph
- missing referenced container/block/chunk
- snapshot reachability anomaly
- GC refused because integrity is unsafe
- verify detected catalog/storage inconsistency

Rules:

- invariant failures must fail closed
- GC must not proceed through unsafe invariant failures
- invariant failures should remain distinguishable from ordinary domain
  not-found failures
- existing invariant wrappers must not be broken

### Runtime

Meaning:
The operation failed while executing a valid request because an expected runtime
action failed.

Examples:

- filesystem operation failed
- DB transaction failed
- context cancellation
- unexpected IO failure
- permission denied during actual operation
- container/block read failed during execution

Rules:

- runtime failure is not validation failure
- runtime failure is not unsupported
- runtime failure may wrap lower-level catalog/storage/environment errors

### Catalog

Meaning:
A database/catalog access, transaction, schema, or catalog-consistency
operation failed.

Examples:

- query failure
- transaction failure
- scan failure
- schema/bootstrap failure
- catalog backend error
- catalog deferred method returning `catalog.ErrNotImplemented`

Rules:

- catalog failure can be runtime-like, but taxonomy should keep catalog origin
  visible where useful
- catalog `ErrNotImplemented` must remain distinct from engine
  `ErrNotImplemented`
- PostgreSQL compatibility must be preserved

### Storage

Meaning:
A filesystem/container/block/chunk storage operation failed or reported invalid
storage state.

Examples:

- open/read/write/stat/remove/rename failure
- missing container
- invalid container header
- chunk/block payload mismatch
- restore read failure
- container placement failure

Rules:

- storage failure can be runtime-like, but taxonomy should keep storage origin
  visible where useful
- storage corruption that violates a guarantee may also surface as invariant
  failure through verify/GC

### External / Environment

Meaning:
The operation cannot proceed because required external environment or tooling is
unavailable or misconfigured.

Examples:

- missing env var
- DB host unreachable
- Docker/PostgreSQL unavailable during validation
- missing local tool
- GitHub API/auth/network unavailable during CI audit
- filesystem permission model unavailable in the environment

Rules:

- environment failures should be recorded honestly in release gates
- environment failure is not product behavior failure unless it occurs in a
  supported runtime configuration

### CLI Translation

Meaning:
The CLI maps internal/domain/runtime errors to user-visible human output, JSON
envelopes, and exit codes.

Examples:

- usage exit code `2`
- general failure exit code `1`
- verify/recovery-specific exit codes where the current contract requires them
- JSON error envelope
- fallback text matching where currently present

Rules:

- `v1.13.2` must preserve current CLI translation behavior
- taxonomy additions must not leak a new JSON shape
- taxonomy additions must not change exit codes
- CLI translation cleanup belongs to later releases unless explicitly scoped

### Unknown / Needs later decision

Meaning:
A current surface exists but should not be force-classified yet because the
active contract is provisional, partial, or dependent on later ownership work.

Examples:

- snapshot diff/query narrowing
- minimal/provisional `VerifyResult`
- verify category-prefixed failures
- surfaces where CLI fallback matching depends on text
- mixed ownership seams awaiting `v1.13.3` / `v1.13.5` / `v1.13.7+`

Rules:

- do not overclassify
- record later owner
- preserve current behavior

## Category Decision Guide

1. Is the operation/mode intentionally outside the active contract?
   - yes: `Unsupported`
2. Does the surface exist for future ownership but is not active?
   - yes: `Deferred`
3. Is the request malformed before execution?
   - yes: `Validation`
4. Is the request valid but target/state cannot satisfy it?
   - yes: `Domain`
5. Did Coldkeep detect a violated correctness guarantee?
   - yes: `Invariant`
6. Did an IO/DB/context/permission action fail during execution?
   - yes: `Runtime`, with `Catalog` / `Storage` / `Environment` origin if
     useful
7. Is the concern about public error rendering/exit code?
   - yes: `CLI Translation`
8. Is the surface provisional or mixed ownership?
   - yes: `Unknown / Needs later decision`

## Code-Backed vs Document-Backed Taxonomy

| Category | Code-backed today? | Current mechanism | Notes |
| --- | --- | --- | --- |
| `Unsupported` | partially | `engine.ErrNotImplemented` sentinel and existing `errors.Is` checks | Active engine unsupported modes are already code-backed, but the category is not yet taxonomized globally |
| `Deferred` | partially | engine/catalog `ErrNotImplemented`; candidate-only surfaces remain documentation-only | Some deferred seams are code-backed, candidate-only types remain doc-backed |
| `Validation` | partially | mixed CLI/domain validation paths and typed CLI usage errors | Not unified under one product-wide mechanism |
| `Domain` | partially | mixed string errors, wrapped `sql.ErrNoRows`, and observability sentinels | Not unified; some not-found flows are typed, many are string-based |
| `Invariant` | partially | invariant wrappers and verify/integrity failures | Code-backed where wrappers exist, but not unified across all packages |
| `Runtime` | partially | wrapped lower-level execution errors | Code-backed through existing error chains, not taxonomy-unified |
| `Catalog` | partially | `catalog.ErrNotImplemented`, DB/query/scan/transaction failures | Catalog origin exists in code, but the category is not unified |
| `Storage` | partially | storage and verify-related errors, filesystem/container/block/chunk wrappers | Code-backed, but origin visibility is not unified as taxonomy |
| `External / Environment` | mostly document-backed | release-gate/env/tooling failures and some runtime configuration failures | Important in validation and release gates; not unified as code taxonomy |
| `CLI Translation` | yes | current CLI rendering, `error_class`, `exit_code`, and exit-code logic | Code-backed today, but taxonomy-neutral and intentionally preserved |
| `Unknown / Needs later decision` | no | documentation only | Reserved for provisional or mixed-ownership surfaces |

## Explicit Non-Claims

`v1.13.2` Phase 2 does not claim:

- all current errors are taxonomy-wrapped
- all packages expose typed errors
- CLI rendering has been redesigned
- JSON envelopes have changed
- exit codes have changed
- engine routing has changed
- catalog methods have been implemented
- candidate-only surfaces are active

## Phase 3 Input

Phase 3 should decide the smallest safe engine-side code-backed primitive set.

That work should likely center on preserving `engine.ErrNotImplemented` and, if
needed, adding only narrow classification helpers where current behavior
already supports them.

Phase 3 must avoid a large error framework.
