# Coldkeep v1.13.2 — Domain, Invariant, Runtime Classification Map

## Status

`complete`

## Purpose

This document maps representative current `v1.13.2` error surfaces after the
Phase 2 taxonomy language and the Phase 3, 4, and 5 narrow classification
primitives.

This is a map of current behavior.

This is not implementation.

This is not a behavior change.

This does not claim that all errors are unified.

This is input for later `v1.13.x` releases and for Phase 7 CLI translation
preservation.

## Relationship to earlier phases

- Phase 1 inventoried broad error surfaces across engine, catalog, CLI,
  storage, verify, recovery, and observability.
- Phase 2 defined the taxonomy language for unsupported, deferred, validation,
  domain, invariant, runtime, catalog, storage, environment, and CLI
  translation surfaces.
- Phase 3 added narrow `engine.IsUnsupported` support for active unsupported
  engine modes backed by `engine.ErrNotImplemented`.
- Phase 4 added narrow `catalog.IsDeferred` support for deferred catalog
  metadata seams backed by `catalog.ErrNotImplemented`.
- Phase 5 protected the validation versus unsupported boundary in active engine
  request handling.
- Phase 6 maps domain, invariant, runtime, catalog-origin, storage-origin, and
  environment-origin surfaces without adding code.


Packages and directories inspected:

- `internal/storage`
- `internal/snapshot`
- `internal/maintenance`
- `internal/recovery`
- `internal/verify`
- `internal/observability`
- `internal/catalog`
- `internal/engine`
- `cmd/coldkeep`

Summary of findings:

- Domain-style current-state misses are already common in `internal/snapshot`,
  `internal/storage`, `internal/engine`, and `internal/observability`, but they
  are mostly string-backed rather than taxonomy-unified.
- Invariant failures already have a real machine-readable wrapper in
  `internal/invariants`, and some maintenance, storage, engine, and verify
  flows already preserve those codes.
- Runtime failures are widely wrapped with `%w` across storage, verify,
  recovery, maintenance, and catalog DB access paths.
- Catalog-origin and storage-origin are already visible in error text and call
  boundaries, but not yet normalized into a typed cross-package taxonomy.
- CLI translation still depends on current typed `cliError` handling plus some
  narrow fallback text matching, so later taxonomy work must not assume the CLI
  is purely type-driven today.

## Classification Boundary Summary

| Category | Meaning in v1.13.2 | Current code-backed status | Risk if confused |
| --- | --- | --- | --- |
| Domain | Structurally valid request, but repository state cannot satisfy it | Partially code-backed through current not-found and already-exists style errors, not unified | Can be over-escalated into corruption or under-escalated into validation |
| Invariant | Coldkeep detected a violated correctness guarantee and must fail closed | Code-backed where `invariants.Error` is used, not unified everywhere | Can be mistaken for ordinary not-found or generic runtime failure |
| Runtime | Valid operation failed while doing work because IO, DB, context, permission, or cleanup failed | Broadly code-backed through wrapped lower-level errors, not unified | Can be misread as validation, unsupported, or pure domain state |
| Catalog | DB/catalog-specific origin for failure or deferred metadata seam | Partially code-backed through DB wrappers and `catalog.IsDeferred` | Can be collapsed into engine unsupported or into generic runtime with lost origin |
| Storage | Filesystem/container/block/chunk origin for failure | Broadly code-backed through storage wrappers and hash/read/check failures | Can be mistaken for domain state or invariant corruption without enough context |
| External / Environment | Required environment, service, tooling, or permission state is missing or misconfigured | Mostly document-backed and release-gate-backed | Can be hidden behind false-green validation or mislabeled as product logic failure |
| CLI Translation interaction | Public rendering, JSON envelope, and exit-code mapping for internal failures | Code-backed in `cmd/coldkeep/main.go`, taxonomy-neutral | Can drift if internal errors change shape or wording |
| Unknown / Later decision | Mixed or provisional surfaces that should not be force-classified yet | Document-backed only | Premature typing can harden the wrong ownership seam |

## Invariant/Integrity Failure Map

| Surface | Package/owner | Representative current trigger | Current error style/wrapper | Why invariant | Fail-closed expectation | Later owner/notes |
| --- | --- | --- | --- | --- | --- | --- |
| Machine-readable invariant wrapper | `internal/invariants` | invariant-producing caller wraps a correctness violation | `*invariants.Error`, exposed through `errors.As` | Explicitly marks a violated guarantee, not a generic failure | Callers should preserve code and stop unsafe work | Broader ownership in `v1.13.5` |
| `PHYSICAL_GRAPH_INTEGRITY` | `internal/invariants` and `internal/verify` | verify metadata summary detects graph inconsistency | `invariants.New(..., nil)` or wrapped invariant error | Signals repository graph inconsistency, not ordinary absence | Verification should fail closed | `v1.13.5` |
| `PHYSICAL_GRAPH_REFCOUNT_MISMATCH` | `internal/invariants` and storage/repair semantics | logical versus physical refcount mismatch | invariant code + message | Violated count guarantee inside physical graph | Repair/verify gate should stop and diagnose | `v1.13.5` |
| `PHYSICAL_GRAPH_NEGATIVE_REFCOUNT` | `internal/invariants` | negative refcount state | invariant code + message | Impossible healthy state in reference accounting | Must be treated as unsafe state | `v1.13.5` |
| `SNAPSHOT_GRAPH_INTEGRITY` | `internal/invariants` | snapshot metadata graph inconsistency | invariant code + message | Snapshot correctness guarantee is broken | Snapshot-related operations should fail closed until repaired | `v1.13.8` with `v1.13.5` invariant ownership |
| `GC_REFUSED_INTEGRITY` | `internal/invariants` and maintenance/CLI flows | GC detects unsafe integrity state | invariant-wrapped error with recommended action | GC must not reclaim reachable or uncertain data | GC should refuse to proceed | `v1.13.5` |
| `GC_FK_VIOLATION` | `internal/maintenance` | DB FK violation while deleting a container/GC path | invariant-wrapped error preserving lower-level cause | Indicates metadata reachability inconsistency, not ordinary DB noise | GC should halt and direct operator to verify | `v1.13.5` |
| `REPAIR_REFUSED_ORPHAN_ROWS` | `internal/maintenance` | repair detects orphan `physical_file` rows before recalculating refcounts | invariant-wrapped error via `invariants.New` | Repair refuses to normalize state that is already inconsistent | Repair should stop before mutation | `v1.13.9` repair/recovery decisions plus `v1.13.5` |
| `SNAPSHOT_RETAINED_DELETE_BLOCKED` | `internal/storage` and engine batch result projection | remove attempts to delete logical data retained by snapshot references | invariant-wrapped error, surfaced with invariant code and recommended action | Reachability guarantee blocks destructive remove | Delete should fail closed and preserve data | `v1.13.7` restore/remove split |
| Verify metadata integrity failure | `internal/verify` | metadata verification returns `CodePhysicalGraphIntegrity` | typed invariant wrapper, sometimes under verify wrapper chains | Detects catalog/storage inconsistency during verification | Verify should fail closed | `v1.13.5` |
| Missing referenced chunk/container/block under verify paths | `internal/verify` and `internal/storage` | reachability or block metadata references disappear or conflict | verify category error and/or invariant-backed message, depending path | Reference graph says object must exist for consistency | Deep verify should fail closed | Mixed ownership; keep partly `Unknown / Needs later decision` |
| Recovery quarantine of unsafe state | `internal/recovery` | missing container, corrupt tail, unresolved sealing state, orphan container rows | quarantine side effect plus wrapped runtime error text or report counters | Behavior isolates unsafe state rather than treating it as ordinary not-found | Recovery must quarantine rather than proceed as healthy | `v1.13.9` repair/recovery |

Ordinary not-found cases must stay separate from invariant failures. A missing
snapshot ID, logical file ID, or observability target is currently a domain
surface. Invariant handling only applies where the repo-backed code treats the
state as violating a correctness guarantee or explicitly blocks mutation for
safety.

## Runtime Failure Map

| Surface | Package/owner | Representative current trigger | Current error style | Origin | Later owner/notes |
| --- | --- | --- | --- | --- | --- |
| DB connect failure | `internal/storage`, `internal/recovery`, `internal/maintenance` | `failed to connect to DB` or local DB startup failure | wrapped `%w` error | Catalog / Environment | Preserve as runtime-origin plus environment/catalog detail |
| Query / exec / scan / iterate failure | `internal/catalog`, `internal/storage`, `internal/verify`, `internal/recovery`, `internal/maintenance` | query row fails, scan fails, rows iteration fails, transaction begin/commit fails | wrapped `%w` error with query-specific text | Catalog | Later taxonomy may add typed catalog origin, not in Phase 6 |
| Filesystem stat/read/open failure | `internal/storage`, `internal/recovery` | stat/open/read container or output path fails | wrapped `%w` error | Storage / Environment | Do not confuse with validation or unsupported |
| Restore source container/block read failure | `internal/storage` | open/read container data, query chunk rows, payload read, chunk pin/unpin failure | wrapped `%w` error | Storage | Some of these may also reveal invariant problems later |
| Write/rename/fsync/output directory failure | `internal/storage` | create temp/output file, fsync dir, rename output, cleanup after failure | wrapped `%w` error | Storage / Environment | Runtime today; later may gain storage-origin wrapper |
| Cleanup, rollback, quarantine follow-up failure | `internal/storage/store.go` | rollback fails, active container quarantine also fails | `errors.Join` plus wrapped `%w` errors | Storage / Runtime | Preserve joined chain compatibility; no wrapper redesign in this release |
| Recovery filesystem operation failure | `internal/recovery` | stat container file, read containers dir, quarantine/resync path update | wrapped `%w` error | Storage / Environment | Quarantine counts remain report-driven, but errors stay runtime-like |
| Verify DB and scan failure | `internal/verify` | failed to query counts, scan rows, iterate verification rows | wrapped `%w` error or verify category error | Catalog / Runtime | Keep verify typed surface intact |
| Context-driven operation failure | storage/DB operations using operation contexts | context cancellation or deadline during query, transaction, or IO | underlying wrapped error chain when surfaced | Runtime / Environment | Record honestly; do not invent a new wrapper in Phase 6 |
| Permission / sandbox filesystem failure | storage/recovery/output path handling | permission denied or unsupported FS behavior during file operations | wrapped OS error | Environment / Storage | Relevant to supported-runtime versus dev-sandbox distinction |

Runtime failure means a valid operation failed while doing work. In v1.13.2
these failures often preserve useful lower-level origin through `%w`, but they
are not yet unified into a cross-package runtime taxonomy.

## Catalog-Origin Failure Map

Catalog-origin failures are currently visible through DB-centric wrapped errors
and through the separate deferred metadata seam represented by
`catalog.ErrNotImplemented`.

Representative catalog-origin surfaces:

- query / exec / scan / row-iteration failures in `internal/catalog`,
  `internal/storage`, `internal/verify`, `internal/recovery`, and
  `internal/maintenance`
- transaction begin / commit / rollback failures in storage and maintenance
- schema/bootstrap/connect failures such as `failed to connect to DB`
- deferred catalog metadata methods returning `catalog.ErrNotImplemented`,
  recognized by `catalog.IsDeferred`
- SQLite and PostgreSQL compatibility-sensitive paths such as FK violations,
  row scanning, and backend-neutral query behavior

Current interpretation:

- Catalog-origin failure may later be represented as runtime plus catalog
  origin.
- Deferred catalog methods remain distinct from active engine unsupported
  boundaries.
- PostgreSQL compatibility remains a constraint on any later typed catalog
  classification work.

## Storage-Origin Failure Map

Storage-origin failures are currently visible through direct filesystem,
container, block, chunk, and restore/store pipeline errors.

Representative storage-origin surfaces:

- container open/read/stat failures
- block metadata lookup and range validation failures
- chunk hash, block hash, compressed hash, and physical hash mismatch paths
- missing physical object referenced by metadata
- invalid container filename or unsafe restore path resolution
- restore source read failure and restore descriptor resolution failure
- output write, rename, fsync, cleanup, rollback, and quarantine failure paths

Current interpretation:

- Storage-origin failure may be runtime when work fails during execution.
- Storage-origin corruption may become invariant when catalog/storage
  consistency is violated or verify detects an impossible state.
- This phase only maps these surfaces; it does not add typed wrappers or
  wrappers around existing chains.

## External / Environment Failure Map

Representative environment-origin surfaces already visible in repo behavior or
release-gate practice:

- `COLDKEEP_*` environment parsing and configuration validation paths
- DB unreachable or DB bootstrap unavailable during startup or command runtime
- Docker/PostgreSQL unavailable during validation or compatibility checks
- GitHub/network/auth unavailable during CI or release audit work
- missing local tools such as `shellcheck`, `jq`, or `golangci-lint`
- Go toolchain resolution or module cache issues during validation
- filesystem permission, sandbox, or unsupported environment behavior during
  file operations

Current interpretation:

- Release gates must record these honestly rather than implying green status.
- Environment failures are not automatically product bugs unless they happen in
  a supported runtime configuration with valid prerequisites.
- Environment blockers should not be hidden behind generic success summaries.

## CLI Translation Interaction

Current CLI translation behavior in `cmd/coldkeep/main.go` remains the public
contract for `v1.13.2`.

Current interaction points:

- usage-style errors map to exit code `2`
- general command failures map to exit code `1`
- verify paths use typed verify exit handling
- recovery and doctor recovery paths use typed recovery exit handling
- JSON error envelopes include `error_class` and `exit_code`
- some classification still depends on narrow fallback message matching in
  `classifyExitCode`

Phase 6 implications:

- no JSON `error_class` or `exit_code` shape changes
- no exit-code mapping changes
- no human output changes
- no taxonomy string should leak into public JSON or stderr rendering in this
  phase
- Phase 7 should preserve representative validation, domain, invariant, and
  runtime translation behavior explicitly

## Unknown / Needs Later Decision

These surfaces exist today but should not be force-classified yet:

| Surface | Why it remains mixed or provisional | Suggested later owner |
| --- | --- | --- |
| Verify category-prefixed failures | `VerifyFailure.Category` strings mix metadata, physical, hash, and repository semantics without a final taxonomy mapping | `v1.13.5` |
| Provisional `VerifyResult` | Engine verify contract is still intentionally thin and delegates underlying error chains | `v1.13.5` |
| Snapshot diff/query narrowing | Current behavior narrows query shapes at mixed snapshot/engine/CLI seams | `v1.13.3` |
| Mixed CLI/engine ownership paths | Some restore/remove/snapshot behaviors still cross read-side and direct-path seams | `v1.13.7` |
| String-dependent CLI fallback matching | Exit-code fallback logic still relies partly on message text | `v1.13.11` |
| Mixed storage/quarantine semantics | Quarantine can represent runtime containment, safety isolation, or integrity suspicion depending path | `v1.13.9` |
| Snapshot mutation candidate-only surfaces | Snapshot create/delete/restore engine ownership is still candidate-only | `v1.13.8` |

## Risks for Later Phases

- classifying domain not-found as invariant corruption
- classifying invariant failure as ordinary domain failure
- classifying DB failure as validation
- classifying unsupported or deferred behavior as runtime
- changing CLI exit codes while adding taxonomy
- changing JSON envelopes while adding taxonomy
- overfitting taxonomy to current error text
- adding broad wrappers that break `errors.Is` or `errors.As`

## Phase 7 Input

Phase 7 should preserve CLI translation behavior for representative
validation, domain, invariant, and runtime paths without changing JSON output,
exit codes, or human-facing behavior.
