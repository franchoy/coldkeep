# v1.13.0 Dependency-Direction Baseline

## Purpose and Dependency Rules

This document records the v1.13.0 dependency-direction baseline. It is documentation only. It does
not add enforcement code, scripts, or tests in this phase.

Key principle:

- Dependency direction should protect correctness boundaries, not create abstract purity work.

Allowed directions:

- `cmd/coldkeep` may import `internal/engine`
- `internal/engine` may import domain packages
- `internal/engine` may import `internal/catalog`
- `internal/catalog` may import lower-level DB/backend abstractions only as needed
- domain packages may import lower-level packages
- tests may import test helpers where appropriate

Forbidden directions:

- `internal/engine` must not import `cmd/coldkeep`
- `internal/catalog` must not import `cmd/coldkeep`
- `internal/catalog` must not import `internal/engine`
- domain packages must not import `internal/engine`
- `cmd/coldkeep` should not import `internal/catalog` directly
- lower-level packages must not import CLI/rendering packages
- engine/catalog contracts must not depend on CLI rendering types

## Current Evidence

- `internal/engine/dependency_guard_test.go` already enforces:
  - engine must not depend on CLI
  - non-engine internal packages must not directly import engine
  - CLI must not import catalog directly
- `internal/catalog/dependency_test.go` already enforces:
  - catalog must not depend on engine
  - catalog must not depend on CLI
  - catalog must not depend on `internal/cli` / renderer packages
- `go list -deps ./cmd/coldkeep ./internal/engine ./internal/catalog` succeeds in this environment
  but emits the known read-only stat-cache warning. That warning is environment noise only.
- Phase 4 direct CLI/domain imports are real and important, but they are transitional ownership
  seams, not automatic dependency-direction violations by themselves.

### Current Violations

- No current production dependency-direction violations were identified for the core forbidden
  back-edge rules covered here.

That is acceptable. The value of Phase 6 is not proving the repo is already violating layering. It
is identifying which boundaries are already clean enough to harden in CI and which couplings remain
transitional for correctness reasons.

### Transitional Couplings That Must Remain Documented

- `cmd/coldkeep` still directly imports and orchestrates `internal/storage`, `internal/snapshot`,
  `internal/maintenance`, `internal/recovery`, `internal/observability`, and `internal/verify`
  across real product workflows.
- `internal/engine` still imports domain packages such as `internal/observability`,
  `internal/storage`, `internal/snapshot`, `internal/maintenance`, and `internal/verify`.
- These are not currently forbidden dependency-direction violations by themselves. They are
  documented transitional seams tied to Phase 2 contract-shape work and Phase 4 ownership
  migration work.

### Most Important Future CI-Enforced Rules

The highest-value rules to keep or harden first are:

- `internal/engine -> cmd/coldkeep` forbidden
- domain/internal packages -> `internal/engine` forbidden
- `cmd/coldkeep -> internal/catalog` forbidden
- `internal/catalog -> internal/engine` forbidden
- `internal/catalog -> cmd/coldkeep` forbidden
- `internal/catalog -> internal/cli` / renderer forbidden

### Bottom Line

The current dependency direction baseline is healthier than the ownership baseline.

What still needs work is not mainly forbidden import cleanup. It is:

- contract-shape stabilization in engine
- ownership migration out of CLI-only sequencing and recovery paths
- later enforcement of broader lower-level / renderer separation once current stabilization work is done

That keeps Phase 6 aligned with the release principle: protect correctness boundaries first, and do
not turn transitional architecture work into abstract purity cleanup.
