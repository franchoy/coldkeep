**Release:** `v1.13.11 — Safety and Backend Compatibility Gate Closure`

**Status:** Complete

**Evidence basis:** source and checked-in test/CI inspection at `40a9462a`

## Executive finding

PostgreSQL is the normal CLI/runtime backend and is exercised by required
integration, smoke, benchmark, and adversarial CI. SQLite has substantial
unit/package coverage and targeted repository-portability evidence. That is
mostly separate evidence, not same-contract parity proof.

The catalog contract suite is the concrete exception. It shares fixtures and
assertions for SQLite and PostgreSQL, but its PostgreSQL subtests require
`COLDKEEP_TEST_DB`. Required `quality` CI runs `./cmd/... ./internal/...`
without that variable or a PostgreSQL service, so those subtests skip there.

| `adversarial`, `smoke`, `benchmark-matrix` | PostgreSQL service and CLI/runtime evidence. | PostgreSQL safety/performance evidence, not SQLite parity. |

No required job executes a reusable same-contract SQLite/PostgreSQL harness.

## Corrections and exclusions

- `internal/catalog/backend_contract_backends_test.go` states that CI runs the
  PostgreSQL catalog path. Current required CI does not; Phase 4 owns the
  execution correction and Phase 6 owns expanded catalog parity proof.
- “Dual-backend” catalog descriptions currently describe intended coverage, not
  required-CI-executed coverage.
- PostgreSQL integration evidence plus SQLite unit evidence is classified as
  separate evidence, never as parity.
- This matrix does not implement a harness, activate PostgreSQL package tests,
  change backend behavior, or add locking.

## Phase ownership

Phase 3 owns reusable dual-backend fixture infrastructure; Phase 4 activates
currently skipped PostgreSQL-gated package tests in required CI; Phases 5–10
own schema, catalog, read-side, selector, mutation, and lock proof gaps in
their respective order. Phases 11–13 own coordination and contention. Deferred
catalog APIs belong to v1.13.12; SQLite-first product behavior belongs to v2.x.
