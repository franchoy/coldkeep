# Coldkeep v1.13.10 Phase 3 — Engine Contract Documentation Truthfulness

## Purpose

Align engine-contract comments, test terminology, and release tracking with the
active Coldkeep Engine boundary established after v1.13.9. This is a
behavior-preserving documentation and terminology phase.

## Authoritative active method set

`internal/engine/engine.go` and the exact-method reflection tests are
authoritative. The active `Engine` interface contains exactly:

- `Stats`
- `Inspect`
- `Verify`
- `SnapshotList`
- `SnapshotShow`
- `SnapshotStats`
- `SnapshotDiff`
- `SnapshotCreate`
- `SnapshotDelete`
- `SnapshotRestore`
- `GarbageCollect`
- `Store`
- `Remove`
- `RemoveStoredPaths`
- `Restore`
- `RestoreStoredPath`

## Active contract categories

- Observability: `Stats`, `Inspect`.
- Verification: `Verify`.
- Snapshot read side: `SnapshotList`, `SnapshotShow`, `SnapshotStats`,
  `SnapshotDiff`.
- Snapshot mutation: `SnapshotCreate`, `SnapshotDelete`, `SnapshotRestore`.
- Maintenance: `GarbageCollect`.
- Storage mutation: `Store`, `Remove`, `RemoveStoredPaths`.
- Restore: `Restore`, `RestoreStoredPath`.

## Active but bounded or provisional contracts

- `Store` is active for single-file store only; recursive/folder store remains
  outside the active route.
- GC preserves its reachable-data safety invariant. Dry-run works on SQLite
  and PostgreSQL; live mode is PostgreSQL-only.
- Snapshot read-side methods are active, but complete CLI workflow ownership
  and some shape semantics remain provisional.
- `VerifyResult` is intentionally empty and success-only.
- An active method does not by itself establish a frozen daemon/API-ready
  contract.

## Candidate-only corrective contracts

`Repair` and `Recover` request/result types exist, but neither operation has
an active method on the current `Engine` interface. Phase 14 and the Phase 16
honesty proof confirmed their present CLI/domain ownership.

## CLI/domain ownership that remains intentional

- Doctor/recovery orchestration remains CLI/domain-owned.
- Repair remains CLI/maintenance-owned.
- Snapshot read-side workflows remain partially mixed.
- These boundaries are explicit, intentional ownership decisions rather than
  accidental omissions.

## Source and test terminology corrections

Historically named `candidates.go` now documents its mix of active contracts
and candidate-only corrective contracts. Comments distinguish active contracts
from complete workflow ownership and from frozen daemon/API contracts. Tests
now refer to engine contract types, while retaining a distinct
candidate-corrective category for repair and recovery.

## Explicit non-changes

Phase 3 changes no interface method, request/result field, runtime branch,
validation, storage or repository format, schema, backend support, CLI output,
JSON shape, error taxonomy, or ownership decision.

## Validation evidence

The exact active-interface guardrail, complete `internal/engine` and
`cmd/coldkeep` tests, `go vet`, semantic wording searches, documentation
validators, and staged diff review passed. `internal/engine/engine.go` has no
diff, and runtime-source diffs are comments only.

`ENGINE CONTRACT DOCUMENTATION ALIGNED`
