# Coldkeep v1.13.14 GC Byte-Accounting and Partial-Result Design

**Owner finding:** `CK-V1-AUD-004`
**Implementation phase:** `Phase 11 — GC Workers and Accurate Reclaimed Bytes`
**State:** `CONFIRMED_OPEN_DESIGN_FROZEN`

## Public and internal result contract

Phase 11 extends only `maintenance.GCResult` with
`BytesReclaimed int64`. The existing public Engine
`GarbageCollectResult.BytesReclaimed` field does not change shape. Engine maps
the maintenance result before error translation so accumulated work survives a
non-nil maintenance error.

In the normal case, `AffectedContainers`, `ContainerFilenames`, and
`BytesReclaimed` describe the same physically successful population. For live
GC, that population includes both sealed containers and fully-dead active
containers. Legacy dry-run remains sealed-only.

## Authoritative physical-byte source

Physical reclaimed bytes are the size of the authoritative container file at
the final safety boundary, not a metadata estimate, logical chunk sum, block
sum, codec input size, or post-removal observation. The unit resolves the path
through `container.SafeContainerPath` and calls the invocation-local
`fsx.FS.Stat` exactly once. `Stat(path).Size()` is captured after final
eligibility, liveness, and retention revalidation and before destructive DB
commit.

An invalid path, missing file, `Stat` error, or negative reported size fails the
unit before commit, rolls back its transaction, and earns no affected entry,
filename, or bytes. There is no fallback byte source and no retrying second
`Stat` inside the unit.

## Dry-run sequence

For each sealed dry-run candidate:

1. begin its transaction;
2. revalidate sealed eligibility, liveness, and retention;
3. resolve the safe path and call `Stat` exactly once;
4. capture the non-negative physical size;
5. preserve the existing rollback/read-only behavior;
6. return an `affected` private outcome carrying that size.

A retained or skipped candidate returns a non-error terminal result and no byte
credit. Dry-run never removes a file and never discovers or credits active
containers.

## Live sequence

For each sealed or fully-dead-active live candidate:

1. begin its independent transaction;
2. lock and revalidate all applicable eligibility, liveness, and retention
   predicates;
3. resolve the authoritative safe path and call `Stat` exactly once;
4. reject an invalid, missing, failed, or negative-size observation;
5. mutate the eligible metadata;
6. delete exactly one container row;
7. commit the transaction;
8. call `fsx.FS.Remove` on the already-resolved path;
9. only after successful removal, return `affected` with the filename and
   captured physical size.

If `Remove` fails after commit, the unit returns an operation error with zero
unit credit and no successful affected entry or filename. Committed metadata is
not synthetically restored or reported as rolled back. The filesystem error is
never reduced to a log-only event.

## Active-container accounting

`ACTIVE_CONTAINER_ACCOUNTING_CONTRACT: VERIFIED`.

The public result counts physical containers deleted, or that would be deleted,
without a sealed-only qualification. The planning and user-facing simulation
contracts already treat fully-dead active containers as physical reclaim in
real GC. A successful live active removal therefore contributes one affected
container, its filename, and its captured physical size. Active candidates are
absent from legacy dry-run, so no active dry-run credit is introduced.

## Failure and partial-result matrix

| Terminal condition | DB effect | affected/filename credit | byte credit | returned error |
| --- | --- | --- | --- | --- |
| retained or safely skipped | none | none | none | nil |
| dry-run eligible and successfully evaluated | rolled back/read-only | yes | captured physical size | nil |
| live `Stat`/path/missing/negative-size failure | rolled back | none | none | operation error |
| live metadata/cardinality/commit failure | rolled back where possible | none | none | operation error |
| live commit plus successful `Remove` | committed and file absent | yes | captured physical size | nil |
| live commit plus failed `Remove` | committed and file may remain | none | none | operation error |
| later peer/unit failure | each unit keeps its real terminal state | prior and concurrently completed successes remain | prior and concurrently completed exact credit remains | deterministic joined error |
| advisory unlock failure | completed work unchanged | completed success evidence remains | completed exact credit remains | unlock error joined last |

Maintenance aggregates every terminal started-unit result and returns the
accumulated `GCResult` with any non-nil error. It no longer returns `GCResult{}`
for a sealed or active execution error. Preflight errors before meaningful unit
execution retain a zero result. Engine projects first and translates the error
second.

## Checked `int64` accumulation

Bytes are aggregated only by the coordinator in global plan order: sealed plan
order followed by active plan order. For a non-negative unit size, addition is
accepted only when:

```text
current BytesReclaimed <= math.MaxInt64 - unit physical bytes
```

The first unit for which that predicate is false creates a deterministic
accounting-overflow error containing its global plan index, unit kind,
container ID, and filename. That error occupies the unit's plan-index position
among joined unit errors.

The overflow case is the sole representational exception to normal
same-population byte reporting:

- every physically successful unit remains truthfully represented in
  `AffectedContainers` and `ContainerFilenames`;
- `BytesReclaimed` remains the last exact non-overflowing plan-order prefix;
- the overflowing addition and every later byte addition are excluded;
- a non-nil deterministic accounting-overflow error is returned;
- the total never wraps, saturates, erases earlier exact credit, or becomes
  negative.

Later physical successes still appear in count and filenames, and later unit
errors remain ordered normally. Completion timing cannot move the overflow
point because accumulation follows the global plan index.

## Compatibility matrices

### Operation matrix

| Mode | Sealed affected | Active affected | physical `Stat` | physical `Remove` | bytes |
| --- | --- | --- | --- | --- | --- |
| dry-run | yes | not discovered | exactly once per finally eligible sealed unit | no | captured sealed sizes |
| live | yes | yes | exactly once per finally eligible unit | after commit | only successful removals |

### Layout and codec matrix

| Dimension | Required proof |
| --- | --- |
| storage layout | legacy, packed, and mixed candidate populations |
| compression | none and zstd where physical fixtures differ |
| codec | plain and AES-GCM where the existing GC integration tier applies |
| backend | SQLite semantic/ordering proof and PostgreSQL transaction/overlap proof |
| population | none, single, multiple, sealed, active, retained, skipped, and partial failure |

Expected bytes are captured by fixture `Stat` before invocation, never derived
from logical metadata. Regressions cover dry/live success, successful active
accounting, missing file, path/`Stat`/`Remove` faults, negative size, later
failure, concurrent plan-ordered summation, exact `math.MaxInt64`, first-unit
overflow, later overflow after valid credit, and continued affected/filename
truth after overflow.
