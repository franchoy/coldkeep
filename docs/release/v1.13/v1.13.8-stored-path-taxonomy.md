# Coldkeep v1.13.8 Stored-Path Taxonomy

**Release:** `v1.13.8 — Restore / Remove Contract Split and Stored-Path Boundary`
**Phase:** Phase 3
**Status:** Complete
**Branch:** `release/v1.13.8`

## Purpose

Define one authoritative vocabulary for every path-like value used by
Coldkeep before Phase 4 designs the restore/remove contract split.

## Executive conclusion

Coldkeep uses several materially different path-like values that currently
share generic names such as `path`, `stored-path`, `destination`, `filename`,
or `input`. Those values belong to different persistence layers, owners, and
security rules.

After Phase 3, future contracts must not use an unqualified field such as
`Path string` when the real meaning is one of `SourcePath`, `StoredPath`,
`SnapshotPath`, `RepositoryRoot`, `CatalogPath`, `ContainerFilename`,
`BlockFilename`, `DestinationRoot`, `DestinationPath`, `InputFile`, or
`RawTarget`.

Phase 3 does not rename any existing code fields, CLI flags, or catalog
columns.

## Decisive distinctions

- `StoredPath` identifies a current catalog mapping. It does not identify where
  Coldkeep payload bytes are stored.
- `SnapshotPath` identifies a historical namespace entry. It is not a live
  filesystem locator.
- `OriginalName` is descriptive logical metadata. It is not an `OriginalPath`.
- `DestinationRoot` defines where restore may create output. It does not
  identify the catalog object being restored.
- `DestinationPath` is the exact override output path for one restore target.
  It is not interchangeable with `DestinationRoot`.
- batch-input files and raw target text are CLI transport concerns and should
  not remain mixed into final engine-domain request shapes.

## Category definitions

### Source filesystem path

Canonical meaning:

- caller-supplied path to a source file or directory for store/import work
- external filesystem identity, not repository payload identity

Current properties:

- ephemeral request input
- may be absolute or relative at CLI entry
- resolved against the caller's working environment
- canonicalization may include absolute-path conversion and symlink resolution
- may contribute to `physical_file.path` and `logical_file.original_name`, but
  is not automatically identical to either

Recommended future field: `SourcePath string`

### Stored physical path

Canonical meaning:

- the persisted current-state mapping for one filesystem representation of a
  logical file
- catalog representation: `physical_file.path`

Current properties:

- persisted current-namespace metadata
- exact lookup key for current stored-path restore/remove
- one logical file may have multiple stored physical paths
- `logical_file.ref_count` counts these mappings
- remove-by-stored-path deletes one mapping; deleting the last mapping validly
  leaves zero mappings and `ref_count == 0`
- current storage code canonicalizes it with trim, absolute-path conversion,
  clean, and symlink evaluation
- may remain platform-qualified or absolute as catalog metadata
- repository relocation does not require rewriting it because it is not a
  payload locator

Recommended future field: `StoredPath string`

### Logical original name

Canonical meaning:

- descriptive metadata associated with a logical file identity
- catalog representation: `logical_file.original_name`

Current properties:

- persisted logical metadata
- not guaranteed unique
- not a current mapping
- not sufficient by itself to identify a file safely
- survives when `ref_count == 0`
- may be used for default naming, reporting, or observability

Recommended future field: `OriginalName string`

### Snapshot path

Canonical meaning:

- immutable namespace entry recorded inside a snapshot
- catalog representation: `snapshot_path.path` referenced by `snapshot_file.path_id`

Current properties:

- persisted separately from `physical_file.path`
- snapshot-owned and immutable within snapshot history
- remains meaningful even when no current stored mapping exists
- validated through stored/snapshot-style relative-path rules
- not a live filesystem locator
- not rewritten merely because repository payload placement changes

Recommended future field: `SnapshotPath string`

### Repository root

Canonical meaning:

- filesystem directory that conceptually owns the complete local repository

Current properties:

- configuration/runtime location, not object identity
- future portable local layout concept for catalog plus payload roots
- not a stored path, restore destination, or payload locator itself
- may be absolute at runtime

Required Phase 3 honesty:

- `RepositoryRoot` is a future first-class local-repository concept
- `v1.13.8` does not enable normal SQLite repository-root discovery
- `v1.13.8` does not change the current PostgreSQL-backed startup path

Recommended future field: `RepositoryRoot string`

### Catalog path

Canonical meaning:

- filesystem path to a file-backed catalog, specifically the future local
  SQLite catalog such as `<repository-root>/.coldkeep/catalog.sqlite`

Current properties:

- infrastructure/runtime location
- relevant to SQLite file-backed mode
- not a meaningful filesystem path concept for PostgreSQL catalogs
- never a stored path, payload path, or restore destination

Recommended future field: `CatalogPath string`

### Container payload path

Canonical meaning:

- resolved repository-owned filesystem path to a container file holding payload
  bytes

Current properties:

- derived from trusted `containersDir` plus a validated container filename
- not user source identity
- not a current stored-path mapping
- not snapshot namespace
- read/write lifecycle owned by storage/container layers
- physical reclamation owned by GC

Recommended future field: `ContainerPath string`

### Block payload path

Canonical meaning:

- resolved repository-owned filesystem path to a block payload object when
  block storage is represented separately from logical object namespaces

Current properties:

- same payload-family semantics as container payload placement
- repository-owned locator, not user object identity
- relevant as a future precise field even where active code mostly resolves
  through container metadata today

Recommended future field: `BlockPath string`

### Restore destination root

Canonical meaning:

- caller-selected root beneath which restore reconstructs one or more relative
  output paths

Current properties:

- ephemeral request value
- relevant to by-ID output directory semantics, stored-path prefix mode, and
  snapshot restore roots
- may be absolute or relative when received
- normalized before writes
- protected by traversal, symlink, and overwrite rules
- defines an allowed output boundary, not the identity of the restored object

Recommended future field: `DestinationRoot string`

### Restore destination path

Canonical meaning:

- exact filesystem output path for a single restore target

Current properties:

- ephemeral request value
- especially relevant to stored-path override mode
- may be derived by storage in original/prefix modes
- may be supplied directly in override mode
- protected by write-path and parent-path safety checks
- not persisted

Recommended future field: `DestinationPath string`

### Recovery path

Canonical meaning:

- repository-owned operational filesystem path used during maintenance,
  inspection, or corrective recovery flows

Current properties:

- derived from trusted repository/container roots plus validated filenames
- not a user source path
- not a stored path
- not a snapshot path
- not a restore destination

Recommended future field: `RecoveryPath string`

### Quarantine path

Canonical meaning:

- repository-owned operational path associated with quarantined artifacts during
  recovery or safety handling

Current properties:

- repository maintenance concept
- lifecycle owned by recovery/container handling
- may appear in logs or operational reasoning
- not a user object identity

Recommended future field: `QuarantinePath string`

### Batch-input file

Canonical meaning:

- caller-side file read by the CLI to obtain restore/remove targets

Current properties:

- ephemeral CLI transport concern
- not repository state
- not a target object
- CLI owns opening, line splitting, comment/blank filtering, ordering, and I/O
  errors
- engine/storage should receive typed targets rather than this file path

Recommended future field: `InputFile string`

### Raw target

Canonical meaning:

- untyped textual token captured from positional args or a batch-input file
  before semantic parsing

Current properties:

- CLI/batch-layer concern
- not persisted
- preserves original user input for diagnostics
- may differ from normalized domain values
- examples include `"123"`, `" /home/a.txt "`, duplicates, or blankish text

Recommended future field: `RawTarget string`

## Normalization, validation, canonicalization, and resolution

Definitions:

- normalization:
  - syntax-preserving cleanup such as trimming surrounding whitespace
  - examples: trimming `--stored-path`, trimming `--destination`, trimming raw
    batch text
- validation:
  - rejecting values that violate the domain
  - examples: blank stored path, traversal, unsafe filename, invalid
    destination-mode combination
- canonicalization:
  - identity-changing transformation such as absolute-path conversion or
    symlink resolution
  - current example: `normalizePhysicalFilePath` can convert a caller string to
    an absolute cleaned path and evaluate symlinks
- resolution:
  - combining trusted roots with already-validated relative locators to obtain
    a filesystem path
  - current examples: `pathsafe.SafeJoin`, `container.SafeContainerPath`

Required rule:

Do not resolve by joining first and validating afterward.

Current code-backed examples:

- stored physical path:
  - normalized and canonicalized by storage before persistence or lookup
- snapshot path:
  - treated as already normalized and validated as a stored/snapshot-style
    relative path before persistence
- payload filename:
  - validated as a safe filename before joining under a trusted container root
- restore prefix destination:
  - trusted destination root resolved first, then safe relative reconstruction
    occurs beneath it

## Restore destination mode mapping

| Restore mode | Caller field | Derived final output |
|---|---|---|
| `original` | no destination field | derived from current stored physical path under original-mode rules |
| `prefix` | `DestinationRoot` | root plus safe relative representation of the stored path |
| `override` | `DestinationPath` | exact requested output path |

This is a naming rule for Phase 4. It does not rename the current CLI
`--destination` flag in `v1.13.8`.

## Relocation behavior

| Category | Must change when repository root moves? | Reason |
|---|---:|---|
| source filesystem path | No automatic rewrite | external caller filesystem identity |
| stored physical path | No automatic rewrite | current namespace metadata, not payload locator |
| logical original name | No | descriptive logical metadata |
| snapshot path | No | historical namespace metadata |
| repository root | Yes at reopen/configuration | repository location changed |
| catalog path | Re-derived | repository-owned SQLite location |
| relative payload path / filename | No | remains relative metadata |
| resolved payload path | Yes, recomputed | depends on trusted repository/container root |
| restore destination | No automatic rewrite | external caller output request |
| quarantine/recovery path | Re-derived | repository-owned operational path |

## Naming and ownership rules for Phase 4

- future restore/remove contracts must not use generic `Path` when the real
  meaning is more precise
- `StoredPath` must remain reserved for current catalog mappings
- `SnapshotPath` must remain reserved for snapshot namespace entries
- `OriginalName` should remain a name unless code truly preserves a path
  contract
- payload paths should prefer `ContainerFilename`, `BlockFilename`,
  `ContainerPath`, or `BlockPath` depending on whether the value is persisted
  metadata or a resolved filesystem location
- CLI transport concerns should prefer `InputFile` and `RawTarget`, not
  `InputPath`

## Phase 4 input

Phase 4 should use this taxonomy to split restore/remove contracts without
reusing generic path names across:

- current catalog mappings
- snapshot namespace entries
- restore output boundaries
- payload locators
- CLI transport inputs
