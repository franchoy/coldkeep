# Coldkeep v1.13.8 Zero-Reference Migration Remediation

**Release:** `v1.13.8 — Restore / Remove Contract Split and Stored-Path Boundary`
**Phase:** Phase 0C
**Status:** Complete
**Branch:** `release/v1.13.8`

## Purpose

Stop the v6 compatibility backfill from resurrecting valid current-state
zero-reference logical files during SQLite reopen or PostgreSQL schema rerun,
while preserving genuine legacy pre-v6 backfill behavior.

## Pre-fix behavior

Before Phase 0C:

- SQLite migration always normalized `logical_file.ref_count < 1` to `1`;
- SQLite migration always inserted a synthetic `/migrated/...` mapping for any
  logical file with no `physical_file` row;
- PostgreSQL schema reruns performed the same v6 compatibility data backfill
  unconditionally;
- valid current-state remove results with `ref_count = 0` and zero mappings were
  silently resurrected on reopen or rerun;
- current positive-refcount and zero-mapping drift was silently papered over by
  migration instead of remaining detectable by verify/GC.

## Valid-state table

| State | Expected post-Phase 0C result |
|---|---|
| current logical file with `ref_count = 0`, zero mappings | preserve `0 == 0` |
| snapshot-retained logical file with `ref_count = 0`, zero mappings | preserve `0 == 0`; keep snapshot linkage |
| current logical file with `ref_count = 1`, zero mappings | preserve mismatch for verify/GC detection |
| legacy pre-v6 logical file without mapping | backfill one compatibility mapping |

## Root cause

The v6 physical-file compatibility backfill was keyed only to present-row shape.
It did not distinguish:

- genuine legacy repositories being upgraded from pre-v6 state; from
- current-schema repositories whose zero-reference or zero-mapping state was
  already intentional or diagnostically meaningful.

That meant normal reopen/rerun paths could rewrite valid current state.

## SQLite correction

`internal/db/migrations.go` now captures pre-schema SQLite version state before
schema application:

- whether `schema_version` existed at all;
- the maximum pre-schema schema version when it existed.

Phase 0C added `sqlitePreSchemaState.requiresLegacyPhysicalFileBackfill()` with
the following rule:

- fresh empty install: no backfill;
- non-empty app state with no `schema_version` table: backfill;
- pre-schema version `< 6`: backfill;
- pre-schema version `>= 6`: no backfill.

Structural v6 migration remains unconditional:

- `logical_file.ref_count` column presence;
- `physical_file` table/index compatibility;
- schema version advancement to v6.

Only the compatibility data mutations are now gated:

- `UPDATE logical_file SET ref_count = 1 WHERE ref_count IS NULL OR ref_count < 1`
- synthetic `/migrated/...` mapping insertion for unmapped logical files

## PostgreSQL correction

`db/schema_postgres.sql` now captures pre-migration schema state into
transaction-local settings:

- `coldkeep.migration_had_schema_version`
- `coldkeep.migration_schema_version_before`

Structural v6 schema work remains unconditional, including schema-version
advancement. Only the compatibility data backfill now runs conditionally when
`schema_version_before < 6`.

That preserves:

- current v16 schema reruns without synthetic backfill; and
- genuine legacy PostgreSQL pre-v6 upgrades with one compatibility mapping.

## Verification fixture reconciliation

One existing verification regression fixture relied on the previous migration
behavior automatically creating a synthetic physical mapping for an unmapped
current-schema logical file.

That expectation became invalid after the migration correction.

The fixture was updated so it constructs the intended verification state
explicitly rather than relying on migration auto-healing.

This is a test-fixture correction only:

- verification behavior was not weakened;
- mismatch detection remains active;
- migration no longer conceals current-schema mismatches;
- no production verification code changed.
