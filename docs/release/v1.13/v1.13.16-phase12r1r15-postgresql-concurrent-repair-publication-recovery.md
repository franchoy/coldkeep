The PostgreSQL failure is an incomplete implementation of the already-frozen
CK-V11316-015 atomic-publication architecture. The publication transaction
does not currently lock every affected chunk row before its final fingerprint
revalidation. A normal `ABORTED -> PROCESSING` claim can therefore displace
the validated tuple before publication updates it. This phase completes the
original locking contract; it does not create a new recovery mechanism or a
new finding.

## Frozen publication protocol

Inside the publication transaction, acquire the existing advisory and logical
publication exclusions, then lock affected rows in deterministic order:

1. active packed-placement rows that publication may retire;
2. every distinct affected existing `chunk` row;
3. active legacy-placement rows that publication may retire.

Only after all those locks are held may publication reload the complete
authoritative logical, ordered-recipe, chunk identity/status/retry,
placement/accounting, mapping, and repair-attempt fingerprint. Locks remain
held through commit or rollback.

If locked revalidation observes `PROCESSING`, or a supported competing Store
transition has changed the terminal status/retry tuple, publication performs
no placement, path, logical-counter, chunk-counter, or other authoritative
mutation. It rolls back first, safely cleans only losing attempt-owned staging,
releases the repair mutex, and then uses the existing bounded R1R13 contention
wait or fresh validation. No pre-lock snapshot may be reused.

The publication update retains an exact `id + validated status + validated
retry_count` compare-and-swap as a defensive invariant. Zero affected rows
after locked revalidation is a terminal publication/cardinality failure, not
ordinary contention.

No wait may occur while the publication transaction, advisory lock, row lock,
or completed-repair mutex remains held. Cancellation and bounded timeout remain
mutation-free.

## Writer and deadlock boundary

Normal claim, completion, abort, repair publication, Restore pin accounting,
retention/reference accounting, GC, and recovery writers must respect the
PostgreSQL row locks on affected chunk or placement rows. The order above is
compatible with the packed replacement path, which already locks packed
placement membership before changing a chunk. Independent logical files that
share a chunk must not deadlock.

Deterministic PostgreSQL regression coverage must prove both orderings:

- competitor first: a `PROCESSING` transition that owns the chunk row first is
  observed during fresh locked validation; the losing attempt backs out
  without authoritative mutation and terminal completion/abort converges
  through R1R13;
- publisher first: publication holds the chunk row lock through authority
  mutation, so a competing normal claim remains blocked until publication
  terminates.

Existing healthy-reuse, aborted-repair, retry-accounting, shared-chunk,
mutation-free cancellation/timeout, and
`TestConcurrentRetryAfterAbortedChunkStress` worker-success contracts remain
binding.
