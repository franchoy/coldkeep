## 2. Baseline defect reproduction

Focused verify, maintenance, and Engine suites passed unchanged before the
new regression was added. With production accounting still unchanged, the
test-only candidate at the entry SHA failed:

```text
BASELINE_TEST: TestVerifyResultFastCountsOnlyExecutedStages
BASELINE_RESULT: FAIL
EXPECTED_FILE_FAST_RESULT: all counters zero
ACTUAL_FILE_FAST_RESULT: BlocksChecked=1, PhysicalHashChecked=1,
  CompressedHashChecked=1, LogicalHashChecked=1,
  CompressedBlocksChecked=0
```

The fixture was a valid packed repository. File-target fast verification
completed successfully but executed no payload stages. The returned non-zero
counters therefore proved the precise defect: catalog metadata was being used
as post-hoc evidence of work the invocation had not executed.

## 3. Root cause and retired path

`DefaultEngine.Verify` formerly ran the error-only maintenance command and
then called `collectVerifyResult`. The system and file helpers in
`internal/engine/verify_summary.go` counted `storage_blocks`, hash presence,
compression metadata, and legacy block rows after the operation. Metadata
existence was consequently indistinguishable from successful stage execution.

Engine now receives the current invocation's execution result directly from
verification through maintenance. The obsolete summary file and all three
catalog-derived helper functions were removed. A final source search contains
no `collectVerifyResult`, `countVerifyResultForSystem`, or
`countVerifyResultForFile` reference. Benchmark final-state diagnostics remain
separate metadata inventory and are not a production `Engine.Verify` result
producer.

## 4. Invocation ledger and identity

The private ledger is allocated for one verification invocation, is protected
by a mutex, is neither global nor persisted, and is discarded after the call.
It consumes only the Phase 3 successful-stage observer events and deduplicates
by:

```text
(layout, authoritative block ID, stage)
```

`layout=legacy` identifies a legacy `blocks` row; `layout=packed` identifies a
packed `storage_block`. Equal numeric IDs in different layouts remain distinct.
Repeated observations and repeated file/chunk references earn one credit per
authoritative block and stage. Callback order does not affect the final result.

The public counters are projections of unique successful observations:

| Counter | Required successful observer stage |
| --- | --- |
| `BlocksChecked` | `block_verification_complete` |
| `PhysicalHashChecked` | `physical_hash` |
| `CompressedHashChecked` | `compressed_hash` |
| `LogicalHashChecked` | `logical_hash` |
| `CompressedBlocksChecked` | `decompression` for a non-`none` compressed payload |

No metadata-presence query supplies these fields.

## 5. Verification orchestration and transport

The result-bearing verification entry points create the private ledger and
dispatch the unchanged fast, standard, full, or deep orchestration. Existing
error-only verify and maintenance entry points remain and delegate while
discarding the execution result. The Engine result-bearing maintenance path
maps the non-failing summary into the existing `VerifyResult` shape.

The Phase 3 packed observation points already covered physical hash,
compressed hash, decompression, logical hash, and block completion. File-deep
legacy placement already covered logical hash and block completion. System
standard/full/deep legacy verification lacked the corresponding successful
legacy observation, so Phase 4 added only the missing legacy block ID to its
query and emits logical-hash and block-complete events after the existing hash
comparison succeeds.

Instrumentation is attached to the operation contexts the lower verification
paths already create from `context.Background()`. The Engine caller context is
not threaded deeper, and no cancellation checkpoint or operational context
owner changed. `CK-V1-AUD-002` remains open for Phase 5.

## 6. Level, target, layout, and skip behavior

The ledger reports the stages each existing level actually executes; it does
not expand level coverage. System fast/standard/full report successful packed
payload stages, standard/full additionally include successful legacy hash work,
and deep deduplicates packed work repeated by its existing orchestration.
File fast/standard/full report zero payload counters when they perform only
metadata/placement checks; file deep reports only its authoritative reached
placements.

Regression proof covers:

- system and file targets at fast, standard, full, and deep levels;
- packed-only, legacy-only, and mixed repositories;
- equal-layout repeated references and layout-aware identity;
- uncompressed and successfully decompressed zstd payloads;
- quarantined packed metadata that verification intentionally skips;
- a late logical-hash failure after earlier packed stages succeeded.

Quarantined, skipped, unselected, aborted-before-stage, and failed-stage
objects earn no credit. Metadata remains present in the quarantine fixture,
independently proving that the corrected zero is execution-derived.

## 7. Failure contract

A verification error discards the internal ledger summary. Engine returns the
zero `VerifyResult` together with the existing translated verification error,
even when earlier stages emitted successful observations. Phase 4 does not
introduce partial-result-plus-error behavior or change error taxonomy.
