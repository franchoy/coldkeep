**Release:** `v1.13.4 — Read-Side Dependency Direction and Result Ownership Review`  
**Phase:** Phase 5  
**Status:** Complete  
**Branch:** `release/v1.13.4`

## Purpose

This document reviews the current ownership, dependency direction, result
ownership, renderer ownership, JSON ownership, and taxonomy boundaries for the
`snapshot diff` read-side surface.

The goal is to decide whether the current split `snapshot diff` ownership model
is acceptable for `v1.13.x` and what, if anything, should be deferred to later
releases.

This phase is documentation-only and does not change runtime behavior.

## Current `snapshot diff` flow

Observed current production flow begins in `runSnapshotDiffCommand`, which owns
command validation, query parsing, summary-fast-path selection, final filter
post-processing, final count projection, and JSON success envelope assembly.

Current path details:

- CLI entrypoint is `runSnapshotDiffCommand` in `cmd/coldkeep/main.go`
- CLI parsing and validation stay in `cmd/coldkeep` through:
  - `ensureAllowedFlags`
  - positional arity checks
  - `baseID` and `targetID` trim and empty checks
  - `--filter` normalization and allowed-value validation
  - `parseSnapshotQuery`
- summary fast-path selection is CLI-owned:
  - `useSummaryFastPath := summaryMode && filterType == "" && query == nil`
- summary fast path uses `diffSnapshotSummaryPhase`
  - the helper constructs an engine and calls `eng.SnapshotDiff` with
    `Summary: true`
  - the engine then uses the SQL-backed summary helper underneath when the
    request still qualifies for the fast path
- detailed/general path uses `diffSnapshotsPhase`
  - `diffSnapshotsPhase` adapts richer CLI `snapshot.SnapshotQuery` semantics
    into the narrower `engine.SnapshotDiffRequest`
  - only one exact path and one prefix cross this seam today
  - regex and size/mtime constraints are forwarded into the engine request
- engine detailed routing remains active behind `eng.SnapshotDiff`
  - detailed engine execution delegates to `snapshot.DiffSnapshots`
  - engine request/result types remain active as a provisional seam
- snapshot package owns the core detailed diff computation
  - `snapshot.DiffSnapshots` computes entries and a summary from snapshot data
  - `snapshot.DiffSnapshotsSummarySQL` owns the SQL-only summary fast path
- CLI owns `--filter` post-processing after the detailed/general phase returns
  entries
- CLI recomputes matched summary counts after post-filtering
- CLI JSON success output is assembled in `runSnapshotDiffCommand`
  - summary fast path sets `entry_count`, `matched_entry_count`,
    `total_diff_entry_count`, `summary`, and `summary_mode`, while omitting
    `entries`
  - detailed JSON sets `entry_count`, `matched_entry_count`,
    `total_diff_entry_count`, `summary`, and includes `entries`
  - detailed `--summary` still uses the detailed/general path when a filter or
    query is present, then omits `entries` and sets `summary_mode`
- human renderer path stays in `internal/cli/render`
  - `RenderSnapshotDiffSummaryHuman` renders summary output
  - `RenderSnapshotDiffDetailedHuman` renders detailed output
- JSON error output path remains CLI-owned through propagated command errors
- taxonomy-boundary behavior currently centers on:
  - empty base or target IDs remaining usage errors
  - invalid `--filter` and invalid regex/query values remaining CLI validation
    failures
  - missing snapshots remaining current domain/general error paths
  - taxonomy helper names not surfacing in public JSON or human output

## Current flow diagram

```text
runSnapshotDiffCommand
  -> CLI validation
  -> parseSnapshotQuery
  -> summary fast path?
       -> diffSnapshotSummaryPhase
            -> engine SnapshotDiff(summary fast path)
            -> snapshot.DiffSnapshotsSummarySQL
  -> or diffSnapshotsPhase
       -> CLI query narrowing into engine SnapshotDiffRequest
       -> engine SnapshotDiff(detailed path)
       -> snapshot.DiffSnapshots
       -> CLI reprojection into snapshot-owned shapes
  -> CLI --filter post-processing
  -> CLI summary/count reprojection
  -> CLI JSON assembly or renderer human output
```

## Public behavior baseline

Current public behavior that must not drift:

- required base and target behavior:
  - exactly two snapshot ID positionals are required
- empty base/target ID behavior:
  - trimmed empty IDs remain usage errors
- missing base or target behavior:
  - missing valid snapshots remain the current domain/general error path
- invalid filter behavior:
  - invalid `--filter` values remain rejected by the CLI
- invalid query behavior:
  - invalid regex/query input remains rejected before execution
- summary-versus-detailed routing:
  - pure `--summary` with no `--filter` and no query remains the distinct fast
    path
  - detailed `--summary` with a filter or query still uses the detailed/general
    path and only changes final presentation
- summary JSON behavior:
  - summary JSON omits `entries`
  - summary JSON sets `summary_mode: true`
- detailed JSON behavior:
  - detailed JSON includes `entries`
  - detailed JSON reports filtered matched counts and pre-filter total counts
- `--filter` behavior:
  - remains CLI-owned post-processing over returned entries
- empty diff behavior:
  - remains a success path with zero counts
- `matched_entry_count`:
  - remains the post-filter matched count
- `total_diff_entry_count`:
  - remains the pre-filter total count
- human output behavior:
  - remains renderer-owned
- JSON output envelope:
  - remains CLI-owned with `status`, `command`, and `data`
- JSON error envelope:
  - remains unchanged
- exit-code behavior:
  - remains unchanged

## Ownership finding

The current `snapshot diff` ownership model is acceptable for `v1.13.x` as a
documented split transitional seam: CLI owns the richer query parsing and final
public result projection, engine owns the provisional diff request seam and the
summary-versus-detailed routing split, and the snapshot package owns the core
detailed diff computation.

Observed findings supporting that decision:

- CLI owns richer query parsing and summary-fast-path selection
- engine owns the provisional diff request seam and routing split
- snapshot owns the core detailed diff computation
- CLI owns `--filter` post-processing and matched-versus-total count projection
- renderer owns human output
- CLI owns JSON success and error envelopes
- taxonomy helper names are not exposed publicly
- backend behavior remains protected by existing tests

This is a split-but-stable seam rather than a broken seam. The repo evidence
shows active production use, preserved count and output behavior, and no
current correctness or contract bug that requires consolidation in `v1.13.4`.

## Why not consolidate now

`v1.13.4` should not immediately consolidate all `snapshot diff` logic behind a
single new engine-owned result owner.

Reasons:

- consolidating now risks summary-versus-detailed behavior drift
- it risks `--filter` drift
- it risks `matched_entry_count` versus `total_diff_entry_count` drift
- it risks JSON envelope drift
- it risks query narrowing drift
- it would likely force a broader engine-owned result migration outside this
  release scope
- no discovered correctness bug justifies that change in Phase 5

## Gaps and deferred work

| Gap | Risk | Recommended handling |
| --- | ---: | --- |
| CLI-owned richer query semantics over engine seam | Medium | Document as transitional and defer broader ownership consolidation |
| Engine request/result seam reprojected back into snapshot-owned shapes | Medium | Defer result-ownership migration |
| CLI-owned `--filter` post-processing and count reprojection | Medium | Review alongside JSON boundary work in Phase 6 |
| Summary fast path remaining distinct from detailed path | Low/Medium | Preserve and protect rather than refactor |
| Backend parity evidence mostly indirect at CLI level | Low/Medium | Review in Phase 8 |

These are ownership and guardrail gaps, not current correctness blockers.

## Decision for v1.13.4

For `v1.13.4`, keep the current `snapshot diff` ownership model unchanged.

Treat the current CLI/engine/snapshot split as a documented transitional seam.

Preserve summary behavior, detailed behavior, filter semantics, counts, and
output rather than introducing a new consolidated result owner in this release.
