# Coldkeep v1.13.8 Handoff

**Recommended release:** `v1.13.8 — Restore / Remove Contract Split and Stored-Path Boundary`
**Status:** Planned — activate only after v1.13.7 is released

## Why this follows v1.13.7

`v1.13.7` clarified:

- logical versus physical repository state
- repository-owned payload paths
- backend-neutral catalog semantics
- physical-file mapping integrity
- destination-only restore behavior

The next useful boundary is to separate restore semantics from remove semantics
and define which stored paths belong to each layer.

## Primary objective

Define and harden the boundary between:

- logical user-visible paths
- physical-file mappings
- repository payload locations
- restore destinations
- removal selectors
- catalog deletion
- payload deletion
- snapshot retention
- quarantine and recovery state

## Current risk questions

- Can restore paths be confused with stored repository paths?
- Which layer owns path normalization?
- Does remove select logical files, physical mappings, snapshots, or payload?
- When can a physical mapping be removed without deleting logical content?
- How are multiple physical mappings represented during remove?
- How do snapshots retain removed current-state files?
- Which errors are validation failures versus unsupported operations?
- Can CLI wrappers bypass engine-owned request/result semantics?
- Which stored paths may be absolute, logical, repository-relative, or
  external?

## In scope

- restore request/result inventory
- remove request/result inventory
- stored-path taxonomy
- logical/physical path ownership
- selector and validation ordering
- snapshot-retention boundary
- quarantine/recovery interaction
- CLI-to-engine routing review
- narrow contract guards where justified
- SQLite/PostgreSQL semantic preservation

## Out of scope

- normal SQLite runtime implementation
- backend-default transition
- repository move/copy commands
- clone semantics
- tenant/server deletion policy
- legal-hold workflow
- broad GC redesign
- storage-format rewrite
- schema rewrite
- UI/API/daemon work

## Required invariants

- restore never mutates catalog state
- remove never changes restore destinations
- logical-file removal and physical-mapping removal are distinct
- payload deletion requires proven unreachability
- snapshot-retained content remains restorable
- multiple physical mappings remain representable
- stored repository paths are not confused with user output paths
- unsupported operations fail explicitly
- backend selection does not change semantic meaning

## Suggested initial phases

1. release frame and prior-record review
2. restore contract inventory
3. remove contract inventory
4. stored-path taxonomy
5. logical/physical ownership matrix
6. snapshot and reachability boundary
7. CLI/engine routing review
8. evidence inventory
9. minimal guard design
10. implementation or explicit no-change decision
11. documentation closure
12. final Profile A gate

This is a handoff, not the final `v1.13.8` phase list.

## v1.13.7 constraints carried forward

- PostgreSQL remains current normal runtime
- SQLite-first remains future direction
- no backend-default assumption
- no user-facing portability claim
- migration-idempotency invariant must remain protected
- all phases stay on one release branch
- one PR only after the full gate passes

## Activation condition

Do not start `v1.13.8` until:

- `v1.13.7` Profile A passes
- the `v1.13.7` pull request is merged
- `main` CI passes
- `v1.13.7` is tagged from `main`
- the `v1.13.7` release record is finalized
