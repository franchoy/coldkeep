# Coldkeep v1.13.6 Catalog/Backend Test Coverage Classification

**Release:** `v1.13.6 — Catalog Contract Expansion and Backend Parity Review`  
**Phase:** Phase 7  
**Status:** Complete  
**Branch:** `release/v1.13.6`

## Purpose

This document classifies existing catalog/backend test evidence before deciding
whether Phase 8 should add any narrow guard tests.

It connects the catalog inventory, snapshot membership, logical/physical
mapping, placement/restore-plan, reachability/GC, and SQLite/PostgreSQL parity
reviews completed in Phases 1-6.

This phase performs no implementation work and adds no tests.

## Classification model

Classification values used in this phase:

- `directly covered`
- `indirectly covered`
- `release-gate-only`
- `duplicate / over-brittle`
- `backend-sensitive and deferred`
- `backend-neutral candidate for Phase 8`
- `not applicable`

Evidence strength values used in this phase:

- `strong`
- `medium`
- `weak`
- `none found`

Phase 8 recommendation values used in this phase:

- `no action`
- `carry candidate to Phase 8`
- `defer`
- `reject duplicate`

In the current release context:

- `directly covered` means a targeted suite clearly exercises the contract
  itself rather than only a surrounding workflow.
- `indirectly covered` means broader workflow, integration, cross-consistency,
  or engine/CLI evidence exists without one narrow contract-only guard.
- `release-gate-only` means confidence is concentrated in Profile A,
  `COLDKEEP_TEST_DB=1`, or broader release matrices instead of a focused suite.
- `duplicate / over-brittle` means a new narrow guard would mostly restate
  evidence already present or would freeze incidental query/output details.
- `backend-sensitive and deferred` means the area is real but better handled by
  focused backend suites, existing matrices, or release-gate validation than by
  a narrow Phase 8 guard.
- `backend-neutral candidate for Phase 8` means a narrow, stable, non-duplicative
  guard could plausibly be added later if current evidence is not already
  sufficient.
- `not applicable` means the reviewed area does not map cleanly to a new
  v1.13.6 guard decision.

## Direct coverage found

Strong direct evidence already exists for the most contract-shaped areas:

- schema/bootstrap/migration ownership through focused `internal/db` tests
- repository capability derivation through focused dialect-aware tests
- catalog logical/physical/snapshot/reachability lookups through
  `internal/catalog/backend_contract_test.go`,
  `internal/catalog/backend_contract_backends_test.go`, and `service_test.go`
- snapshot membership, path identity, delete-lineage, and retention-related
  behavior through targeted `internal/snapshot` suites
- logical/physical mapping, stored-path identity, restore path reconstruction,
  and remove behavior through targeted `internal/storage` suites
- placement, chunk ordering, packed/legacy metadata, and restore-plan
  derivation through storage, verify, and maintenance tests
- reachability roots, GC dry-run planning, dry-run/live equivalence, packed and
  legacy GC behavior, and repair/refcount refusal through graph, GC,
  maintenance, observability, and verify suites
- verify integrity expectations across physical, snapshot, placement, and block
  metadata surfaces

## Indirect or release-gate-only coverage found

Some areas are covered primarily through broader workflow or release-gate
evidence rather than one narrow contract-only suite:

- snapshot show/list/diff membership semantics are exercised mostly through
  engine routing, mixed-seam snapshot tests, and CLI/read-side boundary tests
- snapshot restore membership confidence is spread across snapshot-level and
  storage-level restore coverage rather than one catalog-owned membership suite
- invariant metadata preservation is visible through CLI and boundary tests
  that confirm metadata survives translation layers
- stats read-side queries are supported by observability service tests,
  cross-consistency tests, and CLI rendering tests more than by one isolated
  backend-parity guard
- PostgreSQL confidence for broader parity remains concentrated in focused
  backend-contract suites, `COLDKEEP_TEST_DB=1` runs, and final
  `PRE_RELEASE_CHECKLIST.md` Profile A evidence

## Duplicate or over-brittle guard ideas

These ideas do not justify new narrow Phase 8 guards because they would mostly
duplicate existing evidence or freeze incidental details:

- restating catalog logical/physical/snapshot/reachability lookup behavior that
  is already covered directly by focused backend-contract tests
- adding another GC dry-run/live equivalence guard where
  `internal/observability/cross_consistency_test.go` and maintenance parity
  tests already assert the shared planner contract
- adding narrow restore ordering guards that would mainly restate existing
  restore/store/verify coverage while locking incidental query shapes
- adding a second inspect relationship consistency guard where
  `internal/observability/inspect_test.go` and cross-consistency tests already
  cover relation exposure and determinism

## Backend-sensitive deferrals

These areas are real but are poor Phase 8 targets because the remaining
uncertainty is mostly backend-sensitive or matrix-shaped:

- SQLite/PostgreSQL parity as a whole remains partly dependent on focused
  backend-contract tests, PostgreSQL-gated suites, and final release-gate
  validation rather than on one narrow add-on test
- live GC confidence still depends on PostgreSQL-only mutation semantics,
  advisory locking, transaction behavior, and release-gate-backed execution
- packed/legacy aggregate parity questions tend to blend restore, GC,
  observability, and verify semantics in ways that are broader than a narrow
  backend-neutral guard
- text/filter parity questions around snapshots and read-side queries depend on
  backend string/path behavior, existing engine shaping, and CLI boundary
  contracts more than on one isolated catalog contract

## Phase 7 findings

### Strongly covered areas

- schema bootstrap/migration
- repository capability derivation
- catalog logical/physical/snapshot/reachability lookups
- snapshot membership, path identity, and delete-lineage behavior
- logical/physical mapping, stored-path identity, and remove/restore mapping
- placement metadata, chunk ordering, and restore-plan derivation
- reachability roots, GC dry-run, packed/legacy GC, and dry-run/live
  equivalence
- repair/refcount refusal and verify integrity expectations

### Adequately covered by indirect or release-gate evidence

- snapshot show/list/diff membership behavior at the engine/read-side seam
- snapshot restore membership behavior as exercised through snapshot and
  storage-level workflows
- invariant metadata preservation across verify/maintenance to engine/CLI
  boundaries
- stats read-side summaries and CLI rendering
- PostgreSQL parity outside the focused backend-contract and gated migration
  suites

### Weak evidence areas

- no contract area reviewed in Phases 1-6 currently stands out as both weakly
  evidenced and a clear backend-neutral Phase 8 guard candidate
- the remaining weaker areas are primarily parity-shaped or matrix-shaped
  rather than narrow missing-unit-guard shaped

### Rejected duplicate/over-brittle guards

- additional direct catalog lookup guards duplicating backend-contract suites
- additional dry-run/live equivalence guards duplicating observability and
  maintenance parity suites
- additional inspect relation determinism guards duplicating existing
  inspect/cross-consistency coverage
- read-side stats/inspect parity as a new narrow guard because the remaining
  uncertainty is already covered indirectly and would be brittle to presentation
  evolution

### Candidate Phase 8 guard areas

- snapshot metadata/text-filter parity remains visible, but it is better
  classified as backend-sensitive and deferred than as a narrow new guard
- packed/legacy placement aggregate parity remains visible, but it is broader
  than a stable add-on guard and is better deferred
- no backend-neutral candidate currently survives the stability,
  non-duplication, and narrow-scope filter

### Immediate blockers

None found.

## Phase 7 decision

Existing catalog/backend evidence is sufficient for v1.13.6.

No Phase 8 tests are justified.

Phase 8 should record a no-new-tests decision.
