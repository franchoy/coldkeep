# Coldkeep v1.13.8 Stored-Path CLI Routing Migration

**Release:** `v1.13.8 — Restore / Remove Contract Split and Stored-Path Boundary`
**Phase:** `Phase 8`
**Status:** Complete
**Branch:** `release/v1.13.8`
**Starting commit:** `cc5f05b46e9adb69205155d1d72437da256cecea`

## Summary

Phase 8 completed the stored-path routing split in production CLI code.

Stored-path restore, single stored-path remove, and batch stored-path remove
now route through the dedicated active engine methods while preserving the
existing CLI command shapes, usage-error ordering, JSON field names, human
output, summary semantics, invariant projection, performance-span ownership,
and exit behavior.

## Production Routing Outcome

Stored-path restore now follows:

```text
CLI syntax validation
→ destination-mode parsing
→ loadDefaultStorageContextPhase
→ Engine.RestoreStoredPath
→ existing human/JSON projection
```

Single stored-path remove now follows:

```text
CLI syntax validation
→ loadDefaultStorageContextPhase
→ Engine.RemoveStoredPaths with one target
→ single-item compatibility projection
```

Batch stored-path remove now follows:

```text
CLI positional/--input loading
→ loadDefaultStorageContextPhase
→ Engine.RemoveStoredPaths with ordered raw targets
→ batch.Report compatibility projection
→ existing batch renderer
```

By-ID restore and by-ID remove remained unchanged.

## Direct CLI-to-Storage Paths Removed

After Phase 8, production `cmd/coldkeep` no longer calls:

- `storage.RestoreFileByStoredPathWithStorageContextResultOptions`
- `storage.RemoveFileByStoredPathWithStorageContextResult`

Stored-path execution now flows through:

- `Engine.RestoreStoredPath`
- `Engine.RemoveStoredPaths`

The CLI still owns:

- command-shape validation;
- usage-error wording and ordering;
- destination-mode text parsing;
- `--input` file reading and file-I/O errors;
- performance-span timing and emission;
- final human/JSON rendering.

The engine now owns:

- stored-path restore typed request validation;
- stored-path batch trim/blank/duplicate preparation;
- stored-path batch dry-run/live execution;
- stored-path batch fail-fast behavior.

## Compatibility Projection Rules

Stored-path restore preserves the existing success envelope:

- `stored_path <- result.StoredPath`
- `output_path <- result.DestinationPath`
- `file_id <- result.FileID`
- `restored_hash <- result.RestoredHash`
- `mode <- normalized destination mode`
- `perf_spans <- CLI command layer`

Stored-path remove preserves the existing single-item success envelope:

- `stored_path`
- `logical_file_id`
- `remaining_ref_count`
- `removed`

Batch stored-path remove preserves the existing batch renderer behavior:

- item ordering remains stable;
- blank-target failures still render with CLI-facing invalid stored-path
  wording;
- duplicate targets still render as skipped;
- planned/success/failed/skipped status mapping is unchanged;
- summary counts remain compatible with the existing JSON/text report format;
- invariant code and recommended action still project through the batch report;
- single stored-path mode still rejects `--dry-run` and `--fail-fast`;
- batch stored-path mode still keeps current dry-run parity gaps.

## Observable Parity Notes

Observed parity points locked by Phase 8:

- stored-path restore original/prefix/override modes remained unchanged;
- stored-path restore still does not expose new engine field names in JSON;
- stored-path remove snapshot-retained refusal stayed unchanged;
- stored-path remove ref-count mismatch rollback stayed unchanged;
- batch stored-path remove still preserves ordered raw targets at the CLI
  boundary and engine-executed trim/duplicate classification afterward;
- `emitBatchCommandReport` remained the final remove batch renderer;
- by-ID restore/remove routing and output remained unchanged.
