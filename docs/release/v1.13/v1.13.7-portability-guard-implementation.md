**Release:** `v1.13.7 — SQLite-First Repository Portability Baseline`

## Purpose and scope

Phase 7B completes the single narrow relocation guard authorized by Phase 6.

It adds one self-contained integration test that proves a file-backed SQLite
catalog and repository-owned payload directory remain usable after the complete
repository root is renamed and reopened from the destination only.

No production code, runtime behavior, schema version, backend default, CLI
behavior, or CI workflow changed in this phase.

## Test added

- file: `tests/integration/repository_portability_integration_test.go`
- test: `TestSQLiteRepositoryRelocationReopenVerifyRestoreIntegration`

## Prior blocker and resolved role

The first attempt at the relocation guard exposed the Phase 7A migration
defect: schema reopen incorrectly added synthetic `/migrated/...` physical-file
rows to already-mapped logical files.

Phase 7A remediated that defect by changing both SQLite and PostgreSQL
backfill predicates to key on logical-file mapping absence rather than
synthetic-path absence.

Phase 7B reruns `db.RunMigrations` during destination reopen and now proves the
fix holds inside the end-to-end relocation workflow.

## Scenario steps

1. Create `<source-root>/.coldkeep/catalog.sqlite` and `<source-root>/containers`.
2. Open a file-backed SQLite catalog, apply pragmas, and run migrations.
3. Store one deterministic plaintext file through the engine into the source
   repository.
4. Verify the source repository through the engine.
5. Close the source storage context before relocation.
6. Rename the complete repository root to a new sibling path.
7. Reopen the destination catalog only from the destination paths and rerun
   migrations.
8. Assert the reopened logical file still has exactly one physical mapping and
   zero synthetic `/migrated/...` mappings.
9. Verify the destination repository through the engine.
10. Restore the stored file from the destination repository only.
11. Compare restored bytes exactly with the original input bytes.
12. Reassert that the source root, source catalog path, and source containers
    path are absent.

## Direct evidence gained

- a repository-owned SQLite catalog under `.coldkeep/catalog.sqlite` can be
  reopened successfully after complete-root rename
- a repository-owned `containers/` directory remains readable after the move
- destination-only verify succeeds after source-root removal
- destination-only restore succeeds after source-root removal
- restored bytes match the original bytes exactly
- destination reopen reruns SQLite migrations without mutating an already-valid
  physical-file graph
